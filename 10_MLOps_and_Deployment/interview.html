Section 1: MLOps Fundamentals (Q1–Q25)

Q1. What is MLOps and why is it needed?

MLOps = ML + DevOps. It applies DevOps principles (CI/CD, automation, monitoring) to the ML lifecycle:

TRADITIONAL SOFTWARE:   Code → Build → Test → Deploy → Monitor
ML SYSTEMS:             Data → Train → Validate → Deploy → Monitor → Retrain
                           ↑                                    ↓
                           └────────── Feedback Loop ──────────┘

Why needed: 87% of ML models never reach production (Gartner). MLOps solves: reproducibility, versioning, deployment automation, monitoring, and retraining.

Q2. What are the MLOps maturity levels?

Level Name Description
0 No MLOps Manual notebook experiments, no versioning
1 DevOps, no MLOps CI/CD for code, but manual ML pipeline
2 Automated Training Automated pipeline for training, manual deployment
3 Automated Deployment CI/CD for models, A/B testing, canary releases
4 Full MLOps Automated retraining on drift, self-healing, feature stores

Q4. What is a feature store and why is it important?

A centralized repository for storing, managing, and serving ML features:

DATA SOURCES → Feature Engineering → FEATURE STORE → Training / Serving
                                          ↓
                              ┌───────────┴───────────┐
                              │ Offline Store (batch) ││  → Training
                              │ Online Store (low-lat)││  → Inference
                              └───────────────────────┘
  • Prevents training-serving skew: Same feature computation for training and inference
  • Tools: Feast (open-source), Tecton, Hopsworks, SageMaker Feature Store
  • Key features: Point-in-time joins, feature versioning, data lineage, access control

Q9. What is A/B testing for ML models?

USER TRAFFIC (100%)
     ├── 90% → Model A (current production)  ─→ Measure metrics
     └── 10% → Model B (challenger)          ─→ Measure metrics
                                                    ↓
                                             Statistical test
                                             (t-test, chi-square)
                                                    ↓
                                         If B is significantly better
                                             → Promote B to 100%

Key considerations: - Minimum sample size for statistical significance - Duration (typically 1-4 weeks) - Guard rails (stop if B is significantly worse) - Metric selection (primary: business metric, secondary: model metric)

Q10. What is shadow deployment (dark launching)?

USER TRAFFIC (100%)
     └── 100% → Model A (serves response to user)
     └── 100% → Model B (runs in parallel, response DISCARDED)
                    ↓
              Compare predictions offline
              No risk to users
  • Advantage: Zero risk — users always see current model
  • Disadvantage: Doesn't test user-facing effects, double compute cost
  • Use case: Validate new model before any traffic switch

Q11. What is canary deployment?

Phase 1: 1% traffic → New model  (monitor for errors)
Phase 2: 5% traffic → New model  (monitor metrics)
Phase 3: 25% traffic → New model (compare against old)
Phase 4: 100% traffic → New model (full rollout)

ROLLBACK: If any phase shows degradation → instant rollback to old model

Q12. What is model drift and how do you detect it?

Drift Type What Changes Detection
Data drift Input feature distributions KS test, PSI, Jensen-Shannon divergence
Concept drift Relationship between features and target Monitor prediction accuracy, ADWIN
Label drift Target distribution Chi-square test on predicted labels

Q14. What is CI/CD for ML?

CI (Continuous Integration):
  Push code → Run unit tests → Run data validation → Train model
  → Run model validation → Integration tests → Build Docker image

CD (Continuous Deployment):
  Build image → Push to registry → Deploy to staging
  → Run smoke tests → Shadow/canary deploy → Promote to production

ML-SPECIFIC CI/CD:
  - Data validation (Great Expectations, Pandera)
  - Model performance tests (accuracy above threshold)
  - Bias/fairness checks
  - Latency benchmarks
  - Model size checks (fits in serving infra)

Q25. What is the ML lifecycle end-to-end?

  1. PROBLEM DEFINITION → Business objective, success metrics
  2. DATA COLLECTION → Sources, labeling, privacy compliance
  3. EDA & CLEANING → Distributions, missing values, outliers
  4. FEATURE ENG. → Transforms, encoding, selection

Q26. What is Docker and why is it essential for ML?

Docker packages applications with all dependencies into portable containers:

FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

Why for ML: Reproducibility, consistent environments, easy scaling, GPU support (nvidia-docker).

Q28. What is multi-stage Docker build and why use it for ML?

# Stage 1: Build (large, with build tools)
FROM python:3.11 AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

# Stage 2: Runtime (small, production-ready)
FROM python:3.11-slim
WORKDIR /app
COPY --from=builder /root/.local /root/.local
COPY . .
ENV PATH=/root/.local/bin:$PATH
CMD ["uvicorn", "main:app", "--host", "0.0.0.0"]
  • Result: 2-5× smaller image (no build tools, compilers in final image)
  • ML benefit: PyTorch build deps are huge, but runtime is much smaller

Q33. What is Helm and why is it used?

Q37. What is container networking and service discovery in K8s?

POD-TO-POD:    ClusterIP service → DNS (model-api.default.svc.cluster.local)
POD-TO-EXTERNAL: NodePort or LoadBalancer service
INGRESS:        Route external HTTP to internal services

Example:
  Client → Ingress (nginx) → Service (model-api) → Pod1, Pod2, Pod3

Service types:
  ClusterIP:    Internal only (default)
  NodePort:     Expose on each node's IP (30000-32767)
  LoadBalancer: Cloud provider LB (AWS ALB, GCP LB)

Q39. How do you handle GPU scheduling in Kubernetes?

Q40. What is ArgoCD and GitOps?

GITOPS WORKFLOW:
  1. Developer pushes model config to Git
  2. ArgoCD watches Git repo
  3. Detects diff between desired (Git) and actual (K8s)
  4. Automatically syncs — deploys new model version
  5. K8s state always matches Git

BENEFITS:
  - Git = single source of truth
  - Full audit trail (Git history)
  - Easy rollback (git revert)
  - PR-based deployments (review before deploy)

Q47. What is container security best practices for ML?

  1. Base image: Use slim/distroless images (not python:latest)
  2. Non-root: Run as non-root user (USER 1000)
  3. Scan images: Trivy, Snyk, Docker Scout
  4. Pin versions: python:3.11.7-slim not python:3.11
  5. Multi-stage build: Don't ship build tools
  6. Read-only filesystem: Mount as read-only where possible
  7. Network policies: Restrict pod-to-pod communication
  8. SBOM: Software Bill of Materials for supply chain security

Q52. How do you build a basic ML prediction API?

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field
import joblib
import numpy as np

app = FastAPI(title="ML Model API", version="1.0")
model = joblib.load("model.pkl")

class PredictionRequest(BaseModel):
    features: list[float] = Field(..., min_length=10, max_length=10)
    
class PredictionResponse(BaseModel):
    prediction: int
    probability: float
    model_version: str = "v3.2"

@app.post("/predict", response_model=PredictionResponse)
async def predict(request: PredictionRequest):
    try:
        X = np.array(request.features).reshape(1, -1)
        pred = model.predict(X)[0]
        proba = model.predict_proba(X)[0].max()
        return PredictionResponse(prediction=int(pred), probability=float(proba))
    except Exception as e:
        raise HTTPException(status_code=500, detail=str(e))

@app.get("/health")
async def health():
    return {"status": "healthy", "model_loaded": model is not None}

Q53. How do you handle model loading and lifecycle in FastAPI?

from contextlib import asynccontextmanager
import torch

@asynccontextmanager
async def lifespan(app: FastAPI):
    # Startup: load model once
    app.state.model = torch.load("model.pt", map_location="cpu")
    app.state.model.eval()
    print("Model loaded successfully")
    yield
    # Shutdown: cleanup
    del app.state.model
    torch.cuda.empty_cache()
    print("Model unloaded")

app = FastAPI(lifespan=lifespan)

@app.post("/predict")
async def predict(request: PredictRequest):
    model = app.state.model
    with torch.no_grad():
        output = model(torch.tensor(request.features))
    return {"prediction": output.argmax().item()}

Q58. What is middleware in FastAPI and how is it used for ML?

import time
from starlette.middleware.base import BaseHTTPMiddleware

class LatencyMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        start = time.perf_counter()
        response = await call_next(request)
        latency = time.perf_counter() - start
        response.headers["X-Latency-Ms"] = str(round(latency * 1000, 2))
        LATENCY_HISTOGRAM.observe(latency)  # Prometheus metric
        return response

app.add_middleware(LatencyMiddleware)

Q79. How do you handle model A/B testing with statistical rigor?

from scipy import stats
import numpy as np

# Collect conversion data from A and B
conversions_a = np.array([1, 0, 1, 1, 0, ...])  # Control
conversions_b = np.array([1, 1, 1, 0, 1, ...])  # Treatment

# Chi-square test for proportions
rate_a = conversions_a.mean()
rate_b = conversions_b.mean()
n_a, n_b = len(conversions_a), len(conversions_b)

# Minimum sample size for 80% power, 5% significance
min_sample = (1.96 + 0.84)**2 * 2 * rate_a * (1 - rate_a) / (0.01)**2

stat, p_value = stats.chi2_contingency([[sum(conversions_a), n_a - sum(conversions_a)],
                                         [sum(conversions_b), n_b - sum(conversions_b)]])[:2]
if p_value < 0.05:
    print(f"Significant difference: A={rate_a:.4f}, B={rate_b:.4f}, p={p_value:.4f}")
