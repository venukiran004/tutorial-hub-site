MLOps — Scenario-Based Questions

Scope: 25 real-world MLOps scenario questions covering CI/CD for ML, deployment strategies, monitoring, Docker/Kubernetes, pipeline orchestration, feature stores, model serving, and infrastructure decisions.

•

Scenario 1: CI/CD Pipeline for ML

SituationQuestionAnswer

Situation: Your team trains and deploys ML models manually. A data scientist trains in Jupyter, exports a pickle, and an engineer deploys it. Last week, a model was deployed with the wrong preprocessing code, causing a 3-hour outage.

Question: Design a CI/CD pipeline for this team.

Answer:

Pipeline Design:
  1. CODE COMMIT (Git)
     ├── Model code + preprocessing in same repo
     ├── Feature engineering as shared library (not notebooks)
     └── Config files for hyperparameters (YAML)
  
  2. CI (GitHub Actions / GitLab CI)
     ├── Unit tests: feature engineering functions
     ├── Integration test: train small model on sample data
     ├── Preprocessing parity test: compare training vs serving output
     ├── Model quality gate: accuracy > threshold on validation set
     └── Linting + type checking (mypy, ruff)
  
  3. MODEL REGISTRY (MLflow)
     ├── Register model artifact + metadata
     ├── Log: data hash, code commit, metrics, config
     └── Stage: Development → Staging → Production
  
  4. CD (ArgoCD / custom)
     ├── Deploy to staging (shadow mode)
     ├── Run integration tests against staging
     ├── Canary deployment (5% traffic → 25% → 100%)
     └── Automated rollback if metrics degrade
  
  Key principle: Preprocessing code MUST be packaged with the model
  (sklearn Pipeline, or shared feature engineering library).

Scenario 2: Model Retraining Strategy

SituationQuestionAnswerTrigger-based retrainingPerformance-basedScheduled

Situation: Your fraud detection model was trained 6 months ago. The fraud team reports that the model is missing 30% more fraudulent transactions than before. Business impact: $2M/month in undetected fraud.

Question: Design a retraining strategy and prevent this from happening again.

Answer:

Immediate: Retrain on last 3 months of labeled data. Deploy via canary (monitor false positive rate carefully — blocking legitimate transactions is worse than missing some fraud).

Long-term retraining strategy: - Trigger-based retraining: Monitor PSI on top features weekly. If PSI > 0.2 on 3+ features → trigger retraining pipeline. - Performance-based: Track fraud detection rate with 2-week label delay. If recall drops > 5% → alert + retrain. - Scheduled: Monthly retraining as baseline, regardless of drift metrics. - Online learning component: Warm-start from previous model on new data (not full retrain — preserves patterns from rare fraud types).

Prevention: - Automated drift monitoring dashboard (Evidently AI) - Alerting: PSI thresholds + recall monitoring with delayed labels - Automated retraining pipeline (Airflow DAG) with quality gates - A/B test every retrained model against current production model before full deployment

Scenario 3: Docker Container Size Issue

SituationQuestionAnswer

Situation: Your ML model's Docker image is 8GB. Deployment takes 15 minutes, and auto-scaling new pods is too slow during traffic spikes.

Question: How do you reduce the image size and improve scaling?

Answer:

IMAGE SIZE OPTIMIZATION:
  1. Multi-stage build:
     - Stage 1: Install build dependencies, compile packages
     - Stage 2: Copy only runtime artifacts (no compilers, no pip cache)
     
  2. Use slim base images:
     - python:3.11-slim instead of python:3.11 (saves ~700MB)
     - Or distroless images (Google) — even smaller
  
  3. Minimize dependencies:
     - Don't install torch+tensorflow+sklearn if you only need sklearn
     - Use pip install --no-cache-dir
     - Remove test files: find . -name "tests" -type d -exec rm -rf {} +
  
  4. Model artifact optimization:
     - Quantize model (FP32 → INT8 = 4x smaller)
     - Store model in external storage (S3), download at startup
       (smaller image, slightly slower cold start)
     - Use ONNX format (often smaller than pickle)
  
  5. Layer caching:
     - Put rarely-changing layers first (OS, Python, deps)
     - Put frequently-changing layers last (model code, config)

SCALING OPTIMIZATION:
  - Pre-pull images to nodes (DaemonSet that pulls image)
  - Use Kubernetes HPA with custom metrics (QPS, GPU utilization)
  - Keep warm spare replicas (min_replicas > 0)
  - Use KEDA for event-driven scaling
  
  Target: Image < 2GB, pod startup < 60 seconds

Scenario 4: Feature Store Implementation

SituationQuestionAnswerOffline storeOnline storeFeature registry

Situation: Your company has 15 ML models sharing many features. Each team computes features independently, leading to: (a) inconsistent feature definitions, (b) training-serving skew, (c) duplicated compute costs.

Question: How would you implement a feature store?

Answer:

Architecture: - Offline store (batch): BigQuery/Hive — historical features for training. Compute via Spark/Airflow on a schedule. - Online store (real-time): Redis/DynamoDB — low-latency serving features. Materialized from offline store or computed from streaming (Kafka + Flink). - Feature registry: Catalog of all features with definitions, owners, data lineage, freshness SLA.

Implementation with Feast:

# feature_store.yaml
project: ml_platform
registry: gs://bucket/registry.db
online_store:
  type: redis
  connection_string: redis://redis:6379
offline_store:
  type: bigquery

# Feature definition
from feast import Entity, FeatureView, Field
from feast.types import Float32, Int64

user = Entity(name="user_id", join_keys=["user_id"])

user_features = FeatureView(
    name="user_features",
    entities=[user],
    schema=[
        Field(name="avg_order_value_30d", dtype=Float32),
        Field(name="order_count_30d", dtype=Int64),
    ],
    source=bigquery_source,
    ttl=timedelta(days=1),
)

Key decisions: - Feature freshness: Real-time features (streaming) for fraud detection. Daily batch for recommendation. - Backfill: When adding new features, backfill historical values for training data. - Governance: Feature ownership, deprecation policy, access control.

Scenario 5: Canary vs Blue-Green Deployment

SituationQuestionAnswerCanary deployment

Situation: You're deploying a new recommendation model that was trained on a different feature set than the current production model. The risk is higher than usual.

Question: Which deployment strategy would you choose and why?

Answer:

Canary deployment — gradually roll out to increasing percentages of traffic while monitoring metrics at each stage.

Rationale: Higher risk → need gradual exposure. Blue-green is all-or-nothing (50/50 or 100% switch). Canary allows 1% → 5% → 25% → 100% with metric gates at each step.

CANARY ROLLOUT PLAN:
  Stage 1 (1%, 24 hours):
    Monitor: latency, error rate, recommendation diversity,
             click-through rate
    Gate: No latency increase > 20%, error rate < 0.1%
  
  Stage 2 (10%, 48 hours):
    Monitor: Above + business metrics (revenue per user, engagement)
    Gate: CTR within 5% of baseline, no revenue decrease
  
  Stage 3 (50%, 72 hours):
    Monitor: All metrics + A/B test statistical significance
    Gate: Statistically significant improvement or non-degradation
  
  Stage 4 (100%):
    Full rollout. Keep old model warm for 7 days for rollback.

AUTOMATED ROLLBACK TRIGGERS:
  - Error rate > 1%
  - P99 latency > 3x baseline
  - CTR drop > 10% (with statistical significance)
  - Any critical alert from monitoring

When to use Blue-Green instead: Simple model updates (same features, same architecture, just retrained on new data), or when you need instant rollback capability (both versions always running).

Scenario 6: Kubernetes Resource Allocation

SituationQuestionAnswerIncrease memory limitsSet requests = limitsLimit batch size

Situation: Your ML serving pods keep getting OOMKilled. You've set memory limits to 4GB, but the model loads at 3.5GB and spikes to 5GB during inference on large batches.

Question: How do you fix this?

Answer:

Immediate fixes: 1. Increase memory limits to 8GB (2x peak usage as buffer) 2. Set requests = limits for GPU/memory to get guaranteed QoS class 3. Limit batch size — cap maximum batch size to control memory spikes

resources:
  requests:
    memory: "6Gi"      # Guaranteed memory
    cpu: "2"
    nvidia.com/gpu: "1"
  limits:
    memory: "8Gi"      # Hard limit
    cpu: "4"
    nvidia.com/gpu: "1"

Root cause solutions: - Model optimization: Quantize INT8 (4x smaller memory footprint) - Dynamic batching: Triton's dynamic batcher respects memory limits - Memory profiling: Use torch.cuda.memory_summary() to find peak allocation - Gradient checkpointing (if doing online learning): Trade compute for memory - Model sharding: Split model across multiple pods for very large models

Monitoring: - Alert when memory usage > 80% of limit - Track memory usage over time — detect memory leaks - Use kubectl top pods and Prometheus for continuous monitoring

Scenario 7: A/B Testing ML Models

SituationQuestionAnswer

Situation: You have two candidate recommendation models. Model A uses collaborative filtering, Model B uses a deep learning approach. You need to determine which to deploy permanently.

Question: Design the A/B test.

Answer:

A/B TEST DESIGN:
  Primary metric:    Revenue per user (RPU) — directly tied to business
  Secondary metrics: Click-through rate (CTR), add-to-cart rate
  Guardrail metrics: Latency P99, diversity score, coverage (% items recommended)
  
  SAMPLE SIZE:
  - Baseline RPU: $5.00, MDE: 2% ($0.10)
  - Standard deviation: $3.00
  - Power: 80%, significance: 5%
  - n ≈ 2 * (1.96 + 0.84)² * 3² / 0.1² ≈ 28,224 per group
  - At 10K users/day → run for ~6 days minimum
  - Add buffer for weekly patterns → run 14 days
  
  RANDOMIZATION:
  - User-level (not session-level) — consistent experience
  - Stratify by: user tier (new/returning), platform (mobile/web)
  
  ANALYSIS:
  - Two-sample t-test for RPU difference
  - Check for SRM (Sample Ratio Mismatch) before analyzing
  - Segment analysis: does one model win for specific user segments?
  
  GUARDRAIL CHECKS:
  - Latency: Model B (deep learning) may be slower — acceptable?
  - Diversity: Is Model B recommending more diverse items?
  - Cold-start: How do models handle new users/items?

Scenario 8: Pipeline Orchestration Failure

SituationQuestionAnswerImmediate responsePrevention

Situation: Your daily model retraining Airflow DAG failed at 3 AM. The data extraction task succeeded, but the feature engineering task failed due to a schema change in the source database. The model serving is still running yesterday's model.

Question: How do you handle this and prevent future failures?

Answer:

Immediate response: 1. Yesterday's model is still serving — no user impact (yet). No emergency. 2. Investigate: Check Airflow task logs for the feature engineering failure. 3. Fix: Update feature engineering code to handle the schema change. Add backward compatibility. 4. Rerun: Clear the failed task and rerun from the failed step (Airflow allows task-level retry).

Prevention:

1. DATA CONTRACTS:
   - Define expected schema with upstream teams (column names, types, ranges)
   - Validate schema at pipeline entry (Great Expectations)
   - Version data contracts — breaking changes require coordinated migration
   
2. PIPELINE RESILIENCE:
   - Schema validation as first task (fail fast)
   - Retry with exponential backoff for transient failures
   - Dead letter queue for malformed records
   - Graceful degradation: if non-critical features fail, train without them
   
3. ALERTING:
   - PagerDuty alert if retraining DAG fails
   - Slack alert with failure summary and link to logs
   - Dashboard showing last successful retrain date
   
4. FALLBACK:
   - If retraining fails for 3+ days → alert on-call + auto-trigger investigation
   - Serve stale model with increasing staleness warning
   - Have a "last known good model" checkpoint that can be restored

Scenario 9: Multi-Model Serving Architecture

SituationQuestionAnswer

Situation: Your e-commerce platform needs 5 ML models for a single page load: (1) search ranking, (2) recommendation, (3) fraud scoring, (4) ad ranking, (5) price optimization. Total latency budget: 200ms.

Question: Design the serving architecture.

Answer:

ARCHITECTURE:
                    ┌─────────────┐
  Request ────────→ │ API Gateway  │
                    │ (FastAPI)    │
                    └──────┬──────┘
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
        ┌──────────┐ ┌──────────┐ ┌──────────┐
        │ PARALLEL  │ │ PARALLEL  │ │ PARALLEL  │
        │ Search    │ │ Recommend │ │ Ad Rank   │
        │ (50ms)    │ │ (80ms)    │ │ (40ms)    │
        └──────────┘ └──────────┘ └──────────┘
                           │
                           ▼
                    ┌──────────────┐
                    │ SEQUENTIAL   │
                    │ Fraud Score  │ (can't parallelize — needs
                    │ (30ms)       │  ranking results)
                    └──────────────┘
                           │
                           ▼
                    ┌──────────────┐
                    │ Price Opt    │ (depends on fraud score
                    │ (20ms)       │  and recommendations)
                    └──────────────┘

KEY DESIGN DECISIONS:
  1. PARALLEL execution for independent models (search, recommend, ads)
     Use asyncio.gather() or gRPC async calls
  2. SEQUENTIAL for dependent models (fraud → price)
  3. Each model has its own serving pod (independent scaling)
  4. Feature store shared across models (avoid redundant feature computation)
  5. Circuit breaker per model — if one times out, return default
  6. Total: max(50, 80, 40) + 30 + 20 = 130ms < 200ms budget ✓
  
INFRASTRUCTURE:
  - Triton Inference Server (multi-model, dynamic batching)
  - gRPC between services (lower overhead than REST)
  - Redis for shared feature cache
  - Kubernetes with per-model HPA

Scenario 10: Model Monitoring Alert Fatigue

SituationQuestionAnswerAlert auditTiered alertingP0 (Critical)

Situation: Your monitoring system generates 50+ alerts per day for your ML models. The team has started ignoring alerts. Last week, a real model degradation was missed for 3 days.

Question: How do you fix the alerting system?

Answer:

  1. Alert audit: Review all 50 alerts. Categorize as: actionable (requires human intervention), informational (dashboard only), or noise (remove).

  2. Tiered alerting: - P0 (Critical): Model serving down, error rate > 5%, revenue impact. → PagerDuty, immediate. - P1 (Warning): Accuracy drop > 2%, significant drift, latency > 2x baseline. → Slack, within 4 hours. - P2 (Info): Minor feature drift, single metric fluctuation. → Dashboard, daily review.

  3. Composite alerts: Replace per-feature drift alerts with a composite "overall data health score." Alert only when the composite score breaches threshold, not individual features.

  4. Suppression: Auto-suppress alerts during known events (deployments, data backfills, holidays).

  5. Runbooks: Every alert must have a runbook. If there's no clear action → it's informational, not an alert.

  6. Weekly review: Analyze alert volume, false positive rate, mean time to acknowledge. Target: < 5 actionable alerts/day.

Scenario 11: MLOps for a Small Team

SituationQuestionAnswerGitDVCMLflow

Situation: You're the sole ML engineer at a startup with 2 data scientists. Budget is limited. Currently: models trained in Jupyter, deployed manually to a single EC2 instance.

Question: What's your minimal viable MLOps setup?

Answer:

Phase 1 (Week 1-2): Foundation - Git: All code in GitHub. No more training in notebooks (convert to scripts). - DVC: Track data versions alongside code. - MLflow (self-hosted): Experiment tracking + model registry. Free. - Docker: Containerize model serving. Single Dockerfile. - GitHub Actions: Basic CI — run tests, build Docker image, push to ECR.

Phase 2 (Month 2): Automation - FastAPI + Docker on ECS Fargate (serverless containers): No K8s complexity. - Scheduled retraining: Cron job or GitHub Actions scheduled workflow. - Basic monitoring: CloudWatch metrics + Slack webhook for errors.

Phase 3 (Month 3+): Scale - Feature store: Feast (open source) when feature sharing becomes a bottleneck. - Airflow (managed, e.g., MWAA): When pipelines become complex. - Kubernetes: Only when you need multi-model serving or complex scaling.

Key principle: Don't over-engineer. Most startups don't need Kubernetes, Kubeflow, or a full MLOps platform. Grow infrastructure with actual needs.

Scenario 12: Handling GPU Shortages

SituationQuestionAnswerInference (team 3)LLM fine-tuning (team 2)Training (team 1)

Situation: Your company has limited GPU budget. Three teams need GPUs: (1) training new models, (2) fine-tuning LLMs, (3) real-time GPU inference. Total GPU capacity: 8 A100s.

Question: How do you allocate and optimize GPU usage?

Answer:

Allocation strategy: - Inference (team 3): 3 A100s dedicated (always available, SLA-bound) - LLM fine-tuning (team 2): 3 A100s shared (schedule: nights + weekends priority) - Training (team 1): 2 A100s + overflow to cloud spot instances

Optimization: 1. Training efficiency: Mixed precision (AMP) = 2x throughput. Gradient accumulation = simulate larger batches. DeepSpeed ZeRO for memory efficiency. 2. LLM fine-tuning: QLoRA (4-bit quantized base + LoRA adapters) = fits on 1 GPU instead of 4. 3. Inference: Quantize to INT8. Dynamic batching. Multi-model on single GPU (if models are small enough). 4. Scheduling: NVIDIA MIG (Multi-Instance GPU) on A100s — split one A100 into 2-7 instances. Slurm or Kubernetes for job scheduling with GPU quotas per team. 5. Cloud burst: Use cloud spot instances (70% cheaper) for non-urgent training jobs when on-prem GPUs are full.

Scenario 13: Migrating from Monolith to Microservices

SituationQuestionAnswer

Situation: Your ML system is a monolithic Python application: data loading, feature engineering, model training, and API serving all in one codebase. Deployments take 2 hours and a bug in feature engineering takes down the API.

Question: How do you decompose this into microservices?

Answer:

DECOMPOSITION STRATEGY (Strangler Fig Pattern):

  Phase 1: Extract API serving
    Monolith ─── extract ──→ [Model Serving API] (FastAPI + Docker)
    Keep: training, feature eng in monolith
    Benefit: API can scale independently, no downtime from training bugs
  
  Phase 2: Extract feature engineering  
    Monolith ─── extract ──→ [Feature Service] (shared library or API)
    Both training and serving use same Feature Service
    Benefit: Eliminates training-serving skew
  
  Phase 3: Extract training pipeline
    Monolith ─── extract ──→ [Training Pipeline] (Airflow + MLflow)
    Triggered by: schedule, drift alert, or manual
    Outputs: Model artifact to Model Registry
  
  Phase 4: Add infrastructure
    [Feature Store] ← Feature Service writes to
    [Model Registry] ← Training Pipeline registers to
    [Monitoring] ← All services emit metrics to

SERVICE BOUNDARIES:
  ┌─────────────┐  ┌──────────────┐  ┌──────────────┐
  │ Training     │  │ Feature      │  │ Model Serving│
  │ Pipeline     │──│ Service      │──│ API          │
  │ (batch)      │  │ (shared)     │  │ (real-time)  │
  └─────────────┘  └──────────────┘  └──────────────┘
        │                                     │
        ▼                                     ▼
  ┌─────────────┐                    ┌──────────────┐
  │ Model       │                    │ Monitoring   │
  │ Registry    │                    │ & Alerting   │
  └─────────────┘                    └──────────────┘

Key: Don't decompose everything at once. Extract one service at a time,
validate it works, then move to the next.

Scenario 14: Data Pipeline SLA Miss

SituationQuestionAnswerIncremental processingStreaming architecturePipeline parallelism

Situation: Your ML pipeline has a 6 AM SLA for daily predictions. The data extraction from the data warehouse takes 3 hours (midnight to 3 AM), feature engineering takes 1.5 hours, model inference takes 30 minutes. Lately, data warehouse queries are running longer, and you're missing the SLA.

Question: How do you fix this?

Answer:

Short-term: (1) Optimize DW queries (add partitioning, push filters down, use incremental extraction instead of full table scan). (2) Start pipeline earlier (10 PM) to absorb delays. (3) Add timeout with fallback — if DW extraction isn't done by 4 AM, use yesterday's features with a "stale data" flag.

Long-term: - Incremental processing: Only process new/changed records, not full table. Reduces extraction from 3 hours to ~30 minutes. - Streaming architecture: Move from batch to streaming for critical features (Kafka → Flink → Feature Store). Predictions available continuously, no SLA dependency on batch. - Pipeline parallelism: If extracting from multiple tables, parallelize extractions. Pipeline features while still extracting later tables. - SLA monitoring: Track each pipeline stage duration over time. Alert when any stage exceeds 150% of expected duration (early warning before SLA miss).

Scenario 15: Secure Model Deployment

SituationQuestionAnswerData encryptionAccess controlData minimization

Situation: Your healthcare ML model processes patient data (PHI). You need to deploy it while complying with HIPAA regulations.

Question: What security measures do you implement?

Answer:

  1. Data encryptionAt rest (AES-256) and in transit (TLS 1.3). Encrypt model artifacts if they memorize training data.
  2. Access controlRBAC for model serving API. API keys + OAuth2. Audit logs for all model queries.
  3. Data minimizationOnly send necessary features to the model. No raw patient identifiers in model input.
  4. Network isolationModel serving in VPC, no public internet access. Private endpoints only.
  5. BAA (Business Associate Agreement)With cloud provider (AWS, GCP, Azure all offer HIPAA-eligible services).
  6. LoggingAudit trail of all predictions (who queried, when, what). Logs must be immutable and retained per HIPAA requirements.
  7. Model privacyDifferential privacy during training (if model could memorize patient data). Regular membership inference attack testing.
  8. DeploymentUse HIPAA-compliant compute (dedicated hosts or compliant managed services). No shared tenancy for sensitive workloads.
  9. Incident responseDocumented plan for data breach. Regular penetration testing. 72-hour notification requirement.

gRPC vs REST — Complete Comparison Guide

•

What is REST?

REST (Representational State Transfer) is an architectural style for building APIs over HTTP. It uses standard HTTP methods and JSON (or XML) to transfer data between client and server.

  • Introduced by Roy Fielding in 2000
  • Built on top of HTTP/1.1
  • Uses human-readable JSON payloads
  • Stateless — each request is self-contained( Every request is independent.)
  • The server doesn't store client session state between requests.

REST Example

GET /api/users/42 HTTP/1.1
Host: api.example.com
Accept: application/json
{
  "id": 42,
  "name": "Priya",
  "email": "priya@example.com"
}
•

What is gRPC?

gRPC (Google Remote Procedure Call) is a high-performance, open-source RPC framework developed by Google. It uses HTTP/2 for transport and Protocol Buffers (Protobuf) for serialization.

  • Released by Google in 2016
  • Built on top of HTTP/2
  • Uses binary Protobuf encoding
  • Supports 4 types of streaming

gRPC Example

// user.proto
service UserService {
  rpc GetUser (UserRequest) returns (UserResponse);
}

message UserRequest {
  int32 id = 1;
}

message UserResponse {
  int32 id = 1;
  string name = 2;
  string email = 3;
}
•

Performance

Binary encodingHTTP/2 multiplexingHeader compressionPersistent connectionsRule of thumb2–5× faster

gRPC is significantly faster than REST due to:

  1. Binary encodingProtobuf is much more compact than JSON
  2. HTTP/2 multiplexingmultiple requests over a single connection
  3. Header compressionHPACK compression reduces overhead
  4. Persistent connectionsno repeated TCP handshakes
Benchmark (typical):
  REST  (JSON/HTTP1.1) : ~10ms avg latency, ~5,000 req/sec
  gRPC  (Proto/HTTP2)  : ~2ms avg latency, ~20,000 req/sec
                                          ↑ ~4× throughput gain

Rule of thumb: gRPC is typically 2–5× faster than REST for equivalent operations.

•

Streaming Modes (gRPC only)

UnaryServer StreamingClient StreamingBidirectional

gRPC supports 4 types of communication that REST cannot natively handle:

ModeDescriptionUse Case
UnaryOne request → one responseStandard API call
Server StreamingOne request → stream of responsesLive feeds, ML token output
Client StreamingStream of requests → one responseFile upload, batch writes
BidirectionalStream both ways simultaneouslyChat, real-time collaboration
// All 4 streaming modes in one service
service DataService {
  rpc Unary          (Request)        returns (Response);
  rpc ServerStream   (Request)        returns (stream Response);
  rpc ClientStream   (stream Request) returns (Response);
  rpc Bidirectional  (stream Request) returns (stream Response);
}
•

When to Use REST

public-facing APIswide tooling supporthuman-readablesimple CRUDnative browser supportwebhooks or callbacks

✅ Use REST when:

  • Building public-facing APIs consumed by browsers, mobile apps, or third-party developers
  • You need wide tooling support — Postman, Swagger, curl, any HTTP client
  • Your team values human-readable payloads for easy debugging
  • Building simple CRUD operations with low-to-medium traffic
  • You need native browser support without extra libraries
  • Integrating with webhooks or callbacks to external systems
  • You want optional contracts (OpenAPI/Swagger)

REST is a great fit for:

  • Public REST APIs (Twitter, GitHub, Stripe)
  • Mobile app backends
  • Third-party integrations
  • Web application backends
•

When to Use gRPC

low latencyML model inferencepolyglot environmenthigh-throughputtrue bidirectional streamingstrict schema enforcement

✅ Use gRPC when:

  • Building internal microservice-to-microservice communication
  • You need low latency — real-time ranking, fraud detection, routing
  • Serving ML model inference — especially with token streaming
  • Working in a polyglot environment — auto-generated stubs in Python, Go, Java, C++, Rust
  • Handling high-throughput workloads (thousands of req/sec)
  • You need true bidirectional streaming
  • You want strict schema enforcement via .proto contracts

gRPC is a great fit for:

  • ML inference servers (TensorFlow Serving, Triton)
  • Kubernetes internal services
  • Real-time data pipelines

Common Architecture Pattern

A typical production system uses both:

[Browser / Mobile App]
         │
         │  REST (HTTP/JSON) — public, flexible, browser-native
         ▼
[API Gateway / Backend for Frontend]
         │
         │  gRPC (Protobuf/HTTP2) — fast, streaming, typed
         ▼
[Internal Microservices]
    ┌────┴─────┐
[Model Server] [Auth Service] [Data Service]

Expose REST externally for compatibility. Use gRPC internally for performance.

•

Code Comparison

REST — Python (Flask)

from flask import Flask, jsonify

app = Flask(__name__)

@app.route('/api/users/<int:user_id>', methods=['GET'])
def get_user(user_id):
    return jsonify({"id": user_id, "name": "Priya"})

gRPC — Python (grpcio)

# user_pb2_grpc.py (auto-generated from .proto)
import grpc
import user_pb2, user_pb2_grpc

class UserService(user_pb2_grpc.UserServiceServicer):
    def GetUser(self, request, context):
        return user_pb2.UserResponse(
            id=request.id,
            name="Priya"
        )

Decision Checklist

Is your consumer a browser or unknown third party?
  → YES → Use REST

Do you need streaming (tokens, events, live data)?
  → YES → Use gRPC

Is this internal service-to-service communication?
  → YES → Use gRPC

Do you need human-readable payloads for easy debugging?
  → YES → Use REST

Is latency or throughput critical (>10k req/sec)?
  → YES → Use gRPC

Building a public API others will integrate with?
  → YES → Use REST

Not sure? → Use REST externally + gRPC internally
