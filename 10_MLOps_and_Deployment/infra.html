1. Linux File System

The Linux file system follows a hierarchical directory structure rooted at /, with standardized paths for binaries (/bin, /usr/bin), configuration (/etc), user data (/home), logs (/var/log), and temporary files (/tmp). Understanding this layout and the essential navigation commands is fundamental to working effectively in any Linux-based development or production environment.

/               Root of everything
├── bin/        Essential binaries (ls, cp, mv)
├── etc/        Configuration files
├── home/       User home directories
├── var/        Variable data (logs, databases)
│   ├── log/    System logs
│   └── tmp/    Temporary files (persist across reboot)
├── tmp/        Temporary files (cleared on reboot)
├── usr/        User programs and data
│   ├── bin/    User binaries
│   ├── lib/    Libraries
│   └── local/  Locally installed software
├── opt/        Optional/third-party packages
├── proc/       Virtual filesystem (process info)
├── dev/        Device files
└── mnt/        Mount points

KEY COMMANDS:
  pwd                       # Print working directory
  ls -la                    # List all files with details
  cd ~                      # Go to home directory
  find / -name "*.py"       # Find files by name
  locate filename           # Fast search (uses index)
  du -sh /var/log           # Disk usage of directory
  df -h                     # Filesystem disk space
  tree -L 2                 # Directory tree (depth 2)

2. File Operations & Permissions

Linux file operations (copy, move, link, search) and the permission system (read/write/execute for owner, group, and others) control how files are accessed and manipulated. The numeric permission model (e.g., 755 = rwxr-xr-x) and text processing tools (grep, sed, awk) are daily essentials for system administration and data engineering workflows.

# ── File operations ──────────────────────────────────────
cp -r src/ dest/            # Copy recursively
mv old.txt new.txt          # Move/rename
rm -rf directory/           # Remove recursively (DANGEROUS)
mkdir -p a/b/c              # Create nested directories
ln -s target link           # Symbolic link
cat file.txt                # Print file
head -n 20 file.txt         # First 20 lines
tail -f /var/log/syslog     # Follow log file (live)
wc -l file.txt              # Count lines
sort file.txt | uniq        # Sort and deduplicate
diff file1.txt file2.txt    # Compare files

# ── Permissions ──────────────────────────────────────────
# Format: rwxrwxrwx = owner|group|others
# r=4, w=2, x=1

chmod 755 script.sh         # rwxr-xr-x (owner full, others read+execute)
chmod 644 config.txt        # rw-r--r-- (owner read+write, others read)
chmod +x script.sh          # Add execute permission
chown user:group file       # Change owner
chgrp group file            # Change group

# SPECIAL PERMISSIONS:
# SUID (4xxx): Run as file owner          chmod 4755 file
# SGID (2xxx): Run as file group          chmod 2755 dir
# Sticky (1xxx): Only owner can delete    chmod 1777 /tmp

# ── Text processing ─────────────────────────────────────
grep -rn "pattern" .        # Recursive search with line numbers
grep -i "error" log.txt     # Case-insensitive
sed 's/old/new/g' file.txt  # Replace text
awk '{print $1, $3}' file   # Print columns 1 and 3
cut -d',' -f2 data.csv      # Extract field 2 (comma delimiter)
xargs                       # Build commands from input

3. Process Management

Process management in Linux involves viewing, controlling, and monitoring running processes using tools like ps, top, kill, and background job control. Understanding how to gracefully terminate processes, run long-running jobs in the background with nohup, and monitor system resources (CPU, memory, GPU) is critical for managing training jobs and production services.

# ── Process viewing ──────────────────────────────────────
ps aux                      # All processes
ps aux | grep python        # Find Python processes
top                         # Interactive process monitor
htop                        # Better interactive monitor
pgrep -f "train.py"         # Find PID by name

# ── Process control ─────────────────────────────────────
kill PID                    # Graceful kill (SIGTERM)
kill -9 PID                 # Force kill (SIGKILL)
killall python              # Kill all Python processes
nohup python train.py &     # Run in background, survive logout
disown %1                   # Detach background job from shell

# ── Background jobs ─────────────────────────────────────
python train.py &           # Start in background
jobs                        # List background jobs
fg %1                       # Bring job 1 to foreground
bg %1                       # Continue job 1 in background
Ctrl+Z                      # Suspend foreground process

# ── Resource monitoring ─────────────────────────────────
free -h                     # Memory usage
nvidia-smi                  # GPU usage
watch -n 1 nvidia-smi       # GPU usage (refresh every 1s)
lsof -i :8000               # What's using port 8000

4. Systemd & Services

Systemd is the Linux init system and service manager that controls starting, stopping, enabling, and monitoring background services (daemons) via unit files. Creating custom systemd services for ML APIs or training workers ensures they start on boot, restart on failure, and produce structured logs accessible via journalctl.

# ── Service management ───────────────────────────────────
sudo systemctl start nginx        # Start service
sudo systemctl stop nginx         # Stop service
sudo systemctl restart nginx      # Restart service
sudo systemctl status nginx       # Check status
sudo systemctl enable nginx       # Start on boot
sudo systemctl disable nginx      # Don't start on boot
journalctl -u nginx -f            # Follow service logs

# ── Create a custom service ─────────────────────────────
# /etc/systemd/system/ml-api.service
[Unit]
Description=ML API Server
After=network.target

[Service]
User=ml-user
WorkingDirectory=/opt/ml-api
ExecStart=/opt/ml-api/venv/bin/uvicorn main:app --host 0.0.0.0 --port 8000
Restart=always
RestartSec=5
Environment=MODEL_PATH=/opt/models/latest

[Install]
WantedBy=multi-user.target

# Then:
sudo systemctl daemon-reload
sudo systemctl enable ml-api
sudo systemctl start ml-api

5. Cron Jobs

Cron is the Linux time-based job scheduler that executes commands at specified intervals defined by a five-field syntax (minute, hour, day, month, weekday). It is commonly used to automate recurring ML tasks like model retraining, data pipeline runs, and report generation — with careful attention to PATH, logging, and timezone settings.

# ── Crontab syntax ───────────────────────────────────────
# ┌───────── minute (0-59)
# │ ┌───────── hour (0-23)
# │ │ ┌───────── day of month (1-31)
# │ │ │ ┌───────── month (1-12)
# │ │ │ │ ┌───────── day of week (0-7, 0=Sun)
# │ │ │ │ │
# * * * * * command

crontab -e                  # Edit crontab
crontab -l                  # List cron jobs

# EXAMPLES:
0 2 * * * /opt/scripts/retrain.sh       # Daily at 2 AM
*/15 * * * * /opt/scripts/monitor.sh     # Every 15 minutes
0 0 * * 0 /opt/scripts/weekly_report.sh  # Sunday midnight
0 6 1 * * /opt/scripts/monthly_cleanup.sh # 1st of month at 6 AM

# BEST PRACTICES:
# - Redirect output: command >> /var/log/cron.log 2>&1
# - Use full paths (cron has minimal PATH)
# - Test command manually first

6. Networking

Linux networking commands — curl, wget, ping, ss, netstat, and firewall tools — enable HTTP requests, file downloads, connectivity diagnostics, port management, and access control. Proficiency with these tools is essential for debugging API endpoints, configuring service communication, and securing production servers.

# ── HTTP requests ────────────────────────────────────────
curl https://api.example.com/data                    # GET request
curl -X POST -H "Content-Type: application/json" \
     -d '{"key": "value"}' https://api.example.com   # POST with JSON
curl -o file.zip https://example.com/file.zip         # Download file
curl -s https://api.example.com | jq '.'              # Parse JSON output
wget https://example.com/dataset.csv                  # Download file
wget -r -np https://example.com/docs/                 # Recursive download

# ── Network diagnostics ─────────────────────────────────
ping google.com             # Test connectivity
traceroute google.com       # Trace route to host
nslookup example.com        # DNS lookup
dig example.com             # Detailed DNS query

# ── Ports & connections ─────────────────────────────────
ss -tlnp                    # List listening TCP ports (modern)
netstat -tlnp               # Same (legacy)
lsof -i :8000               # What process uses port 8000
nc -zv host 80              # Test if port is open

# ── Firewall ────────────────────────────────────────────
sudo ufw allow 8000         # Allow port 8000
sudo ufw status             # Check firewall status
sudo iptables -L            # List firewall rules

7. Shell Scripting

Shell scripting (Bash) automates sequences of commands into reusable, parameterized scripts with variables, conditionals, loops, and functions. Using set -euo pipefail for strict error handling and mastering pipelines, subshells, and here documents makes scripts robust enough for production automation of ML training, data processing, and deployment workflows.

#!/bin/bash
set -euo pipefail  # Exit on error, undefined vars, pipe failures

# ── Variables ────────────────────────────────────────────
NAME="model_v2"
EPOCHS=${1:-10}              # First arg or default 10
echo "Training $NAME for $EPOCHS epochs"

# ── Conditionals ─────────────────────────────────────────
if [ -f "model.pt" ]; then
    echo "Model exists"
elif [ -d "data/" ]; then
    echo "Data directory exists"
else
    echo "Nothing found"
fi

# ── Loops ────────────────────────────────────────────────
for file in data/*.csv; do
    echo "Processing $file"
    python preprocess.py --input "$file"
done

for i in {1..5}; do echo "Epoch $i"; done

# ── Functions ────────────────────────────────────────────
train_model() {
    local model_name=$1
    local lr=$2
    python train.py --model "$model_name" --lr "$lr"
    return $?
}
train_model "resnet50" 0.001

# ── Useful patterns ─────────────────────────────────────
# Pipeline: cat data.csv | grep "error" | wc -l
# Subshell: result=$(python evaluate.py)
# Here document:
cat << EOF > config.yaml
model: resnet50
epochs: $EPOCHS
EOF

8. Makefile

A Makefile defines a set of named targets (setup, train, test, lint, deploy) with their commands and dependencies, providing a standardized, self-documenting entry point for project tasks. It serves as the project's command interface — make train, make test, make deploy — eliminating the need to remember or document long, complex commands.

# ── ML Project Makefile ──────────────────────────────────
.PHONY: setup train test lint clean deploy

PYTHON := python3
VENV := .venv

setup:
	$(PYTHON) -m venv $(VENV)
	$(VENV)/bin/pip install -r requirements.txt

train:
	$(VENV)/bin/python train.py --config config.yaml

test:
	$(VENV)/bin/pytest tests/ -v --cov=src

lint:
	$(VENV)/bin/ruff check src/
	$(VENV)/bin/mypy src/

format:
	$(VENV)/bin/ruff format src/

clean:
	rm -rf $(VENV) __pycache__ .pytest_cache
	find . -name "*.pyc" -delete

docker-build:
	docker build -t ml-api:latest .

deploy: docker-build
	docker push registry.example.com/ml-api:latest
	kubectl apply -f k8s/deployment.yaml

# Run with: make train, make test, make deploy

9. SSH & Remote

SSH (Secure Shell) provides encrypted remote terminal access, key-based authentication, and port forwarding for securely connecting to remote servers. Local port forwarding (-L) is especially important for ML workflows, enabling access to remote Jupyter notebooks, TensorBoard dashboards, and MLflow UIs from a local browser.

# ── SSH basics ───────────────────────────────────────────
ssh user@hostname                     # Connect
ssh -i ~/.ssh/key.pem user@hostname   # Connect with key
ssh -p 2222 user@hostname             # Custom port

# ── SSH config (~/.ssh/config) ───────────────────────────
Host gpu-server
    HostName 10.0.1.50
    User ml-engineer
    IdentityFile ~/.ssh/gpu_key
    Port 22
    ForwardAgent yes
# Then: ssh gpu-server

# ── Port forwarding ─────────────────────────────────────
ssh -L 8888:localhost:8888 gpu-server   # Local: access remote Jupyter locally
ssh -R 8000:localhost:8000 gpu-server   # Remote: expose local port on remote

# ── File transfer ────────────────────────────────────────
scp file.txt user@host:/path/          # Copy to remote
scp -r user@host:/path/dir/ ./local/   # Copy from remote (recursive)
rsync -avz --progress src/ user@host:/dest/  # Efficient sync

10. Git Fundamentals

Git is a distributed version control system that tracks changes to files, enabling collaboration, history exploration, and safe rollback of code changes. Mastering the core workflow — status, add, commit, push, pull — along with diff, log, blame, stash, and undo operations is essential for every developer and data scientist.

# ── Setup ────────────────────────────────────────────────
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git init                    # Initialize repo
git clone url               # Clone remote repo

# ── Daily workflow ───────────────────────────────────────
git status                  # Check what's changed
git add .                   # Stage all changes
git add -p                  # Stage interactively (hunk-by-hunk)
git commit -m "feat: add model training pipeline"
git push origin main
git pull origin main

# ── Viewing history ──────────────────────────────────────
git log --oneline --graph --all   # Visual commit graph
git log --author="name"           # Filter by author
git diff                          # Unstaged changes
git diff --staged                 # Staged changes
git show commit_hash              # Show specific commit
git blame file.py                 # Who changed each line

# ── Undoing changes ──────────────────────────────────────
git checkout -- file.py     # Discard unstaged changes (old)
git restore file.py         # Discard unstaged changes (new)
git reset HEAD file.py      # Unstage file
git reset --soft HEAD~1     # Undo last commit (keep changes staged)
git reset --hard HEAD~1     # Undo last commit (DISCARD changes)
git revert commit_hash      # Create new commit that undoes a commit (safe)

# ── Stashing ────────────────────────────────────────────
git stash                   # Save uncommitted changes
git stash pop               # Apply and remove stash
git stash list              # List stashes
git stash apply stash@{2}   # Apply specific stash

11. Branching & Merging

Git branching creates lightweight, independent lines of development that can be merged back together, enabling parallel work on features, experiments, and hotfixes. Understanding merge vs. rebase, interactive rebase for commit cleanup, and branching strategies (GitHub Flow, trunk-based) is critical for clean collaboration in ML and software teams.

# ── Branches ─────────────────────────────────────────────
git branch feature/training-pipeline  # Create branch
git checkout -b feature/new-model     # Create and switch
git switch -c feature/new-model       # Create and switch (new syntax)
git branch -d feature/merged          # Delete merged branch
git branch -D feature/unmerged        # Force delete

# ── Merging ──────────────────────────────────────────────
git merge feature/training-pipeline   # Merge into current branch
# If conflict:
#   1. Edit conflicted files (look for <<<< ==== >>>>)
#   2. git add resolved_file.py
#   3. git commit

# ── Rebasing ────────────────────────────────────────────
git rebase main             # Replay current branch on top of main
git rebase -i HEAD~3        # Interactive rebase (squash, reorder, edit)
# In interactive rebase:
#   pick   = keep commit
#   squash = merge into previous
#   reword = change commit message
#   drop   = remove commit

# REBASE vs MERGE:
#   Merge:  Preserves history, creates merge commit
#   Rebase: Linear history, cleaner log
#   RULE:   Never rebase public/shared branches
#           Rebase local feature branches before merging

# ── Branching strategies ────────────────────────────────
# Git Flow:       main, develop, feature/*, release/*, hotfix/*
# GitHub Flow:    main + short-lived feature branches + PRs
# Trunk-based:    Single main branch, feature flags, very short branches
# RECOMMENDED for ML: GitHub Flow (simple, CI/CD friendly)

12. Advanced Git

Advanced Git features — bisect for binary-search bug finding, worktree for parallel working directories, cherry-pick for selective commit application, and reflog for recovering "lost" commits — provide powerful tools for debugging, multitasking, and safely navigating complex repository histories.

# ── Git bisect (find the commit that introduced a bug) ──
git bisect start
git bisect bad                    # Current commit is bad
git bisect good v1.0              # v1.0 was good
# Git checks out middle commit → you test → mark good/bad
git bisect good                   # or: git bisect bad
# Repeats binary search until it finds the bad commit
git bisect reset                  # Done, return to original branch

# Automated bisect:
git bisect start HEAD v1.0
git bisect run pytest tests/test_model.py  # Runs test on each commit

# ── Git worktree (multiple working directories) ─────────
git worktree add ../hotfix hotfix/urgent   # Checkout branch in another directory
git worktree list                          # List all worktrees
git worktree remove ../hotfix              # Remove worktree
# Useful: work on hotfix without stashing current work

# ── Cherry-pick ─────────────────────────────────────────
git cherry-pick commit_hash       # Apply specific commit to current branch

# ── Tags ─────────────────────────────────────────────────
git tag v1.0.0                    # Lightweight tag
git tag -a v1.0.0 -m "Release"   # Annotated tag
git push origin v1.0.0            # Push tag

# ── Submodules ──────────────────────────────────────────
git submodule add url path        # Add submodule
git submodule update --init       # Initialize submodules after clone

# ── Reflog (recover "lost" commits) ─────────────────────
git reflog                        # History of HEAD movements
git checkout HEAD@{5}             # Go back to state 5 moves ago
# Reflog is your safety net — almost nothing is truly lost in Git

13. Pre-commit Hooks

Pre-commit hooks are automated checks that run before every git commit, enforcing code quality standards like linting, formatting, type checking, and preventing accidental commits of large files or merge conflicts. Using the pre-commit framework with tools like Ruff, mypy, and detect-secrets ensures consistent code quality across a team without manual review burden.

# ── .pre-commit-config.yaml ─────────────────────────────
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.5.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-yaml
      - id: check-added-large-files
        args: ['--maxkb=5000']      # Prevent large files (model weights!)
      - id: check-merge-conflict

  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.3.0
    hooks:
      - id: ruff                    # Linting
        args: ['--fix']
      - id: ruff-format             # Formatting

  - repo: https://github.com/pre-commit/mirrors-mypy
    rev: v1.8.0
    hooks:
      - id: mypy                    # Type checking
        additional_dependencies: [types-requests]

# Install: pip install pre-commit && pre-commit install
# Run on all files: pre-commit run --all-files
# Skip: git commit --no-verify (emergency only)
# ── Custom hooks (.git/hooks/pre-commit) ─────────────────
#!/bin/bash
# Prevent committing notebook outputs (large, noisy diffs)
if git diff --cached --name-only | grep -q '\.ipynb$'; then
    echo "WARNING: Committing notebooks — strip outputs first!"
    echo "Run: jupyter nbconvert --clear-output --inplace *.ipynb"
    exit 1
fi

14. Interview Deep Dive

Q1: Explain Linux file permissions. What does chmod 755 mean?

A: Linux permissions: 3 groups of 3 bits each — owner, group, others. Each group has read(4), write(2), execute(1). 755 = owner: rwx (7=4+2+1), group: r-x (5=4+1), others: r-x (5). Owner can read, write, execute. Everyone else can read and execute but not write. Common patterns: 644 for files (owner writes, others read), 755 for scripts/directories (need execute to enter directory). Special: SUID (4xxx) runs as file owner, Sticky bit (1xxx on /tmp) prevents others from deleting your files.

Q2: What is the difference between git merge and git rebase?

A: Merge: Creates a merge commit that combines two branches. Preserves complete history. Non-destructive. Rebase: Replays commits from your branch on top of the target branch. Creates linear history (no merge commits). Rewrites commit hashes. Rule: Never rebase commits that have been pushed to a shared branch (rewrites history others depend on). Use rebase for local feature branches before merging to keep history clean. Use merge for integrating shared branches. Interactive rebase (git rebase -i) lets you squash, reorder, or edit commits before merging.

Q3: How do you debug a regression using git bisect?

A: git bisect performs binary search across commits to find which one introduced a bug. Steps: (1) git bisect start (2) git bisect bad (current is broken) (3) git bisect good v1.0 (this version worked). Git checks out the middle commit. Test it, mark good or bad. Repeat ~log2(N) times. For automation: git bisect run pytest tests/test_model.py — Git automatically runs the test on each commit and finds the culprit. git bisect reset to return to original state. Essential for ML: finding which commit degraded model accuracy.

Q4: How do you set up a cron job? What are common pitfalls?

A: crontab -e to edit, format: minute hour day month weekday command. Example: 0 2 * * * /opt/retrain.sh runs daily at 2 AM. Pitfalls: (1) PATH is minimal in cron — use full paths to binaries. (2) No environment variables — export them in the script or crontab. (3) No output by default — redirect: >> /var/log/job.log 2>&1. (4) Timezone — cron uses system timezone, not UTC by default. (5) No error notifications — pipe errors to mail or alerting system. Alternative: systemd timers (more features, better logging).

Q5: Explain Linux process signals. What's the difference between SIGTERM and SIGKILL?

A: SIGTERM (15, default kill): Asks process to terminate gracefully. Process can catch it, clean up resources, save state, then exit. SIGKILL (9, kill -9): Immediately terminates process. Cannot be caught or ignored. Use as last resort — may leave corrupted files, zombie processes, unreleased ports. SIGINT (2, Ctrl+C): Interrupt from keyboard. SIGHUP (1): Terminal closed. Best practice: Always try SIGTERM first, wait a few seconds, then SIGKILL if needed. For ML training: catch SIGTERM to save checkpoint before shutdown.

Q6: What branching strategy do you recommend for ML projects?

A: GitHub Flow (recommended): Single main branch, short-lived feature branches, pull requests. Simple, works with CI/CD. For ML additions: (1) data/ branch or DVC for data versioning. (2) experiment/ branches for model experiments (can be long-lived). (3) Tag releases with model version: v1.0.0-model-resnet50. (4) Use .gitignore rigorously: exclude model weights, data files, notebook outputs. (5) Pre-commit hooks to prevent large file commits. Avoid Git Flow for ML — too complex, ML doesn't have "releases" the same way.

Q7: How do you use SSH port forwarding for ML work?

A: Local forwarding (ssh -L 8888:localhost:8888 gpu-server): Access remote Jupyter notebook from local browser at localhost:8888. Remote Jupyter runs on GPU server, SSH tunnels traffic. Remote forwarding (ssh -R 8000:localhost:8000): Expose local service on remote machine. Dynamic forwarding (ssh -D 1080): SOCKS proxy through remote machine. Practical ML use: Run training on remote GPU, forward TensorBoard (port 6006), forward Jupyter (8888), forward MLflow (5000). Use SSH config file for convenience — one ssh gpu command instead of remembering flags.

Q8: How do you prevent sensitive data from being committed to Git?

A: Layered defense: (1) .gitignore: Exclude .env, credentials, API keys, model weights, data files. (2) Pre-commit hooks: detect-secrets hook scans for API keys/passwords. check-added-large-files prevents data file commits. (3) .gitattributes: Configure Git LFS for large files if needed. (4) Environment variables: Never hardcode secrets — use .env files (gitignored) or secret managers. (5) If already committed: git filter-repo to rewrite history (not just delete — it's in history). Rotate any exposed credentials immediately. (6) GitHub: Enable secret scanning alerts and push protection.

1. What Is Docker?

Docker is a platform that packages applications and their dependencies into containers — lightweight, portable, self-sufficient units that run consistently anywhere.

"It works on my machine"          →  "It works in a container"
                                       (which runs ANYWHERE)

Developer's Laptop  →  Container  →  CI/CD Server  →  Production Server
     Same container, same behavior, everywhere.

Why Docker?

Problem Docker Solution
"Works on my machine" Identical environment everywhere
Dependency conflicts (Python 3.8 vs 3.11) Each container has its own dependencies
Slow setup for new developers docker compose up → running in seconds
Environment inconsistency Image = immutable snapshot
Resource waste (VMs are heavy) Containers share OS kernel = lightweight

5.3 Image Layers

Image = Stack of read-only layers

Layer 4: COPY . /app            ← Your application code
Layer 3: RUN pip install -r ...  ← Python packages
Layer 2: RUN apt-get install ... ← System packages
Layer 1: FROM python:3.11-slim   ← Base OS + Python

Each layer is cached! Change in Layer 4 → only rebuilds Layer 4.

10. Docker Compose

10.1 What Is Docker Compose?

Docker Compose defines and runs multi-container applications using a single YAML file.

Without Compose:                    With Compose:
─────────────────                   ─────────────
docker network create ...           docker compose up
docker run postgres ...                 ↓
docker run redis ...                Starts ALL services
docker run api ...                  with networking,
docker run nginx ...                volumes, env vars
(4+ commands, easy to mess up)      (one command, reproducible)

10.2 docker-compose.yml Structure

# docker-compose.yml

version: "3.8"  # Optional in newer Docker

services:
  # --- Web Application ---
  api:
    build: .                          # Build from local Dockerfile
    # image: my-app:latest            # OR use pre-built image
    ports:
      - "8000:8000"                   # host:container
    environment:
      - DATABASE_URL=postgresql://postgres:secret@db:5432/mydb
      - REDIS_URL=redis://redis:6379
      - SECRET_KEY=mysecretkey
    depends_on:
      db:
        condition: service_healthy    # Wait for DB to be ready
      redis:
        condition: service_started
    volumes:
      - .:/app                        # Bind mount for development
    networks:
      - backend
    restart: unless-stopped

  # --- PostgreSQL Database ---
  db:
    image: postgres:15
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: mydb
    ports:
      - "5432:5432"                   # Expose for local tools
    volumes:
      - pgdata:/var/lib/postgresql/data  # Persist data
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql  # Init script
    networks:
      - backend
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 10s
      timeout: 5s
      retries: 5
    restart: unless-stopped

  # --- Redis Cache ---
  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"
    volumes:
      - redisdata:/data
    networks:
      - backend
    restart: unless-stopped

  # --- Nginx Reverse Proxy ---
  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro
      - ./certs:/etc/nginx/certs:ro
    depends_on:
      - api
    networks:
      - backend
    restart: unless-stopped

# --- Named Volumes ---
volumes:
  pgdata:
  redisdata:

# --- Networks ---
networks:
  backend:
    driver: bridge

11. Multi-Stage Builds

Reduce final image size by separating build and runtime stages.

11.1 Python Multi-Stage

# ---- Stage 1: Builder ----
FROM python:3.11-slim AS builder

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# ---- Stage 2: Runtime ----
FROM python:3.11-slim

WORKDIR /app

# Copy only installed packages from builder
COPY --from=builder /install /usr/local

COPY . .

RUN adduser --disabled-password appuser
USER appuser

EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

11.2 Node.js Multi-Stage

# ---- Build Stage ----
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# ---- Production Stage ----
FROM node:20-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
EXPOSE 3000
CMD ["node", "dist/server.js"]

11.3 Size Comparison

Without multi-stage:     ~1.2 GB  (includes build tools, dev deps)
With multi-stage:        ~150 MB  (only runtime + production deps)
12. Docker Best Practices

12.1 Dockerfile Best Practices

# ✅ 1. Use specific base image tags (not 'latest')
FROM python:3.11-slim    # Good
# FROM python:latest     # Bad — unpredictable

# ✅ 2. Minimize layers — combine RUN commands
RUN apt-get update && \
    apt-get install -y --no-install-recommends gcc curl && \
    rm -rf /var/lib/apt/lists/*

# ✅ 3. Copy requirements first (leverage layer caching)
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .    # Code changes don't invalidate dependency cache

# ✅ 4. Use .dockerignore to exclude unnecessary files

# ✅ 5. Run as non-root user
RUN adduser --disabled-password appuser
USER appuser

# ✅ 6. Use HEALTHCHECK
HEALTHCHECK CMD curl -f http://localhost:8000/ || exit 1

# ✅ 7. Set meaningful labels
LABEL maintainer="team@example.com" \
      version="1.0" \
      description="FastAPI Application"

12.2 Security Best Practices

  1. Never run as root → USER appuser
  2. Don't store secrets in images → Use env vars / Docker secrets
  3. Scan images for vulnerabilities → docker scout cves my-app
  4. Use minimal base images → alpine, slim, distroless
  5. Keep images up to date → Regular rebuilds
  6. Don't expose unnecessary ports
  7. Use read-only file systems when possible → --read-only

12.3 Production Checklist

□ Multi-stage build for small image size
□ Non-root user
□ Health checks defined
□ .dockerignore configured
□ Specific image tags (no :latest)
□ Resource limits set (--memory, --cpus)
□ Logs go to stdout/stderr (not files)
□ Graceful shutdown handling (SIGTERM)
□ Secrets via environment or Docker secrets
□ Image scanning in CI/CD pipeline

15. Interview Questions & Answers

Fundamentals

•

Q1: What is Docker and why do we use it?

Docker is a containerization platform that packages applications with their dependencies into isolated, portable containers. Benefits: consistent environments, fast deployment, resource efficiency, microservice enablement, and simplified CI/CD pipelines.

•

Q2: What is the difference between a Docker image and a container?

ImageContainer
  • ImageRead-only template containing the application, dependencies, and configuration. Like a class in OOP.
  • ContainerRunning instance of an image with a writable layer. Like an object instantiated from a class. Multiple containers can run from the same image.
•

Q3: How do Docker containers differ from virtual machines?

Containers share the host OS kernel and are process-level isolated (lightweight, seconds to start, MB-sized). VMs run a full guest OS with hardware virtualization (heavy, minutes to start, GB-sized). Containers are ideal for application packaging; VMs for full OS isolation.

•

Q4: What is a Dockerfile?

A text file with instructions to build a Docker image. Key instructions: FROM (base image), COPY (add files), RUN (execute commands), CMD (default command), EXPOSE (document port), ENV (set variables).

•

Q5: Explain Docker image layers and caching.

Each Dockerfile instruction creates a layer. Layers are cached — if an instruction and its inputs haven't changed, Docker reuses the cached layer. This is why we copy requirements.txt and install dependencies before copying source code — code changes don't invalidate the dependency cache.

Dockerfile

•

Q6: What is the difference between CMD and ENTRYPOINT?

CMDENTRYPOINT
  • CMDDefault command that can be overridden when running the container. docker run myapp bash replaces CMD.
  • ENTRYPOINTFixed command; CMD becomes arguments. docker run myapp arg1 passes arg1 to ENTRYPOINT.
  • Combined: ENTRYPOINT ["python"] + CMD ["app.py"] → python app.py by default.
•

Q7: What is the difference between COPY and ADD?

COPYADD
  • COPYSimply copies files from host to image. Preferred for most cases.
  • ADDSame as COPY but also auto-extracts .tar archives and supports URLs.
  • Best practice: Always use COPY unless you specifically need ADD's extra features.
•

Q8: What is a multi-stage build and why use it?

Multi-stage builds use multiple FROM statements to separate build and runtime stages. Build stage includes compilers and dev tools; runtime stage copies only the compiled output. This reduces final image size dramatically (e.g., from 1.2GB to 150MB).

•

Q9: How do you reduce Docker image size?

  1. Use slim/alpine base images
  2. Multi-stage builds
  3. Combine RUN commands (fewer layers)
  4. Use .dockerignore
  5. Remove cache (rm -rf /var/lib/apt/lists/*, --no-cache-dir)
  6. Don't install unnecessary packages

Networking & Volumes

•

Q10: How do Docker containers communicate with each other?

Containers on the same Docker network can communicate using container names as hostnames. Use docker network create for custom networks. In Compose, all services are automatically on the same network and can reach each other by service name.

•

Q11: What are Docker volumes and why are they important?

Volumes provide persistent storage that survives container restarts and removal. Container's writable layer is ephemeral — when removed, data is lost. Types: Named volumes (Docker-managed), Bind mounts (host directory), tmpfs (memory only).

•

Q12: What is the difference between a bind mount and a named volume?

Bind mountNamed volume
  • Bind mountMaps a specific host directory to a container path. You manage the data. Good for development (live code reload).
  • Named volumeDocker manages the storage location. More portable, better for production. Supports volume drivers for cloud storage.

Docker Compose

•

Q13: What is Docker Compose?

Docker Compose is a tool for defining and running multi-container applications using a YAML file (docker-compose.yml). It manages services, networks, volumes, and dependencies with a single docker compose up command.

•

Q14: What does depends_on do in Docker Compose?

depends_on controls startup order — a service starts only after its dependencies. With condition: service_healthy, it waits until the health check passes (not just until the container starts). This prevents "database not ready" errors.

•

Q15: How do you handle different environments (dev/prod) with Docker Compose?

Use override files:

# Base config + development overrides
docker compose -f docker-compose.yml -f docker-compose.dev.yml up

# Base config + production overrides
docker compose -f docker-compose.yml -f docker-compose.prod.yml up

Dev adds volume mounts and debug flags; prod adds resource limits and restart policies.

Q16: How do you handle secrets in Docker?

Environment variablesDocker SecretsExternal vaultNever
  1. Environment variables (via .env file or orchestrator) — simple but visible in docker inspect
  2. Docker Secrets (Swarm mode) — encrypted at rest, mounted as files in /run/secrets/
  3. External vault (HashiCorp Vault, AWS Secrets Manager) — most secure
  4. Never bake secrets into images!
•

Q17: What is Docker's health check and why is it important?

Health checks periodically test if a container's application is functioning correctly (not just if the process is running). Docker marks containers as healthy/unhealthy, enabling orchestrators to restart unhealthy containers and Compose depends_on to wait for readiness.

•

Q18: How do you debug a crashing container?

docker logs container_name              # Check logs
docker inspect container_name           # Check config
docker run -it image_name bash          # Start shell to investigate
docker events                           # Watch Docker events
docker stats                            # Check resource usage

Q19: Explain the Docker build cache invalidation.

Docker caches each layer. A layer is invalidated if: 1. The instruction changed 2. Any file referenced by COPY/ADD changed 3. A previous layer was invalidated (all subsequent layers rebuild)

Optimization: Put rarely-changing instructions (install deps) early and frequently-changing ones (copy code) late.

•

Q20: What is the difference between docker compose up and docker compose run?

allsingle serviceEnd of Docker Guide
  • docker compose up: Starts all services defined in the compose file, respecting depends_on.
  • docker compose run service_name command: Starts a single service with a one-off command (e.g., running migrations, tests). Doesn't start dependent services by default (use --service-ports for port mapping).

gRPC vs REST — Complete Comparison Guide

•

What is REST?

REST (Representational State Transfer) is an architectural style for building APIs over HTTP. It uses standard HTTP methods and JSON (or XML) to transfer data between client and server.

  • Introduced by Roy Fielding in 2000
  • Built on top of HTTP/1.1
  • Uses human-readable JSON payloads
  • Stateless — each request is self-contained( Every request is independent.)
  • The server doesn't store client session state between requests.

REST Example

GET /api/users/42 HTTP/1.1
Host: api.example.com
Accept: application/json
{
  "id": 42,
  "name": "Priya",
  "email": "priya@example.com"
}
•

What is gRPC?

gRPC (Google Remote Procedure Call) is a high-performance, open-source RPC framework developed by Google. It uses HTTP/2 for transport and Protocol Buffers (Protobuf) for serialization.

  • Released by Google in 2016
  • Built on top of HTTP/2
  • Uses binary Protobuf encoding
  • Supports 4 types of streaming

gRPC Example

// user.proto
service UserService {
  rpc GetUser (UserRequest) returns (UserResponse);
}

message UserRequest {
  int32 id = 1;
}

message UserResponse {
  int32 id = 1;
  string name = 2;
  string email = 3;
}
•

Performance

Binary encodingHTTP/2 multiplexingHeader compressionPersistent connectionsRule of thumb2–5× faster

gRPC is significantly faster than REST due to:

  1. Binary encodingProtobuf is much more compact than JSON
  2. HTTP/2 multiplexingmultiple requests over a single connection
  3. Header compressionHPACK compression reduces overhead
  4. Persistent connectionsno repeated TCP handshakes 
Benchmark (typical):
  REST  (JSON/HTTP1.1) : ~10ms avg latency, ~5,000 req/sec
  gRPC  (Proto/HTTP2)  : ~2ms avg latency, ~20,000 req/sec
                                          ↑ ~4× throughput gain

Rule of thumb: gRPC is typically 2–5× faster than REST for equivalent operations.

•

Streaming Modes (gRPC only)

UnaryServer StreamingClient StreamingBidirectional

gRPC supports 4 types of communication that REST cannot natively handle:

Mode Description Use Case
Unary One request → one response Standard API call
Server Streaming One request → stream of responses Live feeds, ML token output
Client Streaming Stream of requests → one response File upload, batch writes
Bidirectional Stream both ways simultaneously Chat, real-time collaboration 
// All 4 streaming modes in one service
service DataService {
  rpc Unary          (Request)        returns (Response);
  rpc ServerStream   (Request)        returns (stream Response);
  rpc ClientStream   (stream Request) returns (Response);
  rpc Bidirectional  (stream Request) returns (stream Response);
}

When to Use REST

public-facing APIswide tooling supporthuman-readablesimple CRUDnative browser supportwebhooks or callbacks

✅ Use REST when:

  • Building public-facing APIs consumed by browsers, mobile apps, or third-party developers
  • You need wide tooling support — Postman, Swagger, curl, any HTTP client
  • Your team values human-readable payloads for easy debugging
  • Building simple CRUD operations with low-to-medium traffic
  • You need native browser support without extra libraries
  • Integrating with webhooks or callbacks to external systems
  • You want optional contracts (OpenAPI/Swagger)

REST is a great fit for:

  • Public REST APIs (Twitter, GitHub, Stripe)
  • Mobile app backends
  • Third-party integrations
  • Web application backends
•

When to Use gRPC

low latencyML model inferencepolyglot environmenthigh-throughputtrue bidirectional streamingstrict schema enforcement

✅ Use gRPC when:

  • Building internal microservice-to-microservice communication
  • You need low latency — real-time ranking, fraud detection, routing
  • Serving ML model inference — especially with token streaming
  • Working in a polyglot environment — auto-generated stubs in Python, Go, Java, C++, Rust
  • Handling high-throughput workloads (thousands of req/sec)
  • You need true bidirectional streaming
  • You want strict schema enforcement via .proto contracts

gRPC is a great fit for:

  • ML inference servers (TensorFlow Serving, Triton)
  • Kubernetes internal services
  • Real-time data pipelines
  • Service meshes (Istio, Envoy)
•

Common Architecture Pattern

A typical production system uses both:

[Browser / Mobile App]
               │
         │  REST (HTTP/JSON) — public, flexible, browser-native
         ▼
[API Gateway / Backend for Frontend]
               │
         │  gRPC (Protobuf/HTTP2) — fast, streaming, typed
         ▼
[Internal Microservices]
    ┌────┴─────┐
[Model Server] [Auth Service] [Data Service]

Expose REST externally for compatibility. Use gRPC internally for performance.

Decision Checklist

Is your consumer a browser or unknown third party?
  → YES → Use REST

Do you need streaming (tokens, events, live data)?
  → YES → Use gRPC

Is this internal service-to-service communication?
  → YES → Use gRPC

Do you need human-readable payloads for easy debugging?
  → YES → Use REST

Is latency or throughput critical (>10k req/sec)?
  → YES → Use gRPC

Building a public API others will integrate with?
  → YES → Use REST

Not sure? → Use REST externally + gRPC internally
