1. MLOps Fundamentals

MLOps (Machine Learning Operations) applies DevOps principles — CI/CD, automation, monitoring, and versioning — to the entire ML lifecycle from data preparation through model deployment and ongoing monitoring. It bridges the gap between experimental notebooks and reliable production services, ensuring that models are reproducible, automatically retrained, and continuously monitored for degradation.

MLOps MATURITY LEVELS:
  Level 0 — Manual:     Manual training, manual deployment
  Level 1 — Pipeline:   Automated training pipeline, manual deploy
  Level 2 — CI/CD:      Automated training + automated deployment
  Level 3 — Full:       + Monitoring, auto-retraining, feature store
  
  ML LIFECYCLE:
  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
  │  Data    │──→│  Train   │──→│  Deploy  │──→│ Monitor  │
  │ Pipeline │   │ Pipeline │   │ Pipeline │   │          │──→ Retrain
  └──────────┘   └──────────┘   └──────────┘   └──────────┘
  
  KEY PRINCIPLES:
  - Reproducibility (same data + code + params → same model)
  - Automation (manual steps = errors)
  - Monitoring (models degrade over time)
  - Versioning (data, code, model, config — ALL versioned)

2. MLflow

MLflow is an open-source platform for managing the end-to-end ML lifecycle, providing experiment tracking (parameters, metrics, artifacts), a model registry with staging/production lifecycle stages, and model serving capabilities. It enables teams to compare experiments, reproduce results, and promote models from development to production through a standardized workflow.

import mlflow

# ── Experiment tracking ──────────────────────────────────
mlflow.set_experiment("churn-prediction")

with mlflow.start_run(run_name="xgboost-v1"):
    # Log parameters
    mlflow.log_params({"learning_rate": 0.1, "max_depth": 6, "n_estimators": 100})
    
    # Train model
    model = xgb.XGBClassifier(**params)
    model.fit(X_train, y_train)
    
    # Log metrics
    y_pred = model.predict(X_test)
    mlflow.log_metrics({
        "accuracy": accuracy_score(y_test, y_pred),
        "f1": f1_score(y_test, y_pred),
        "auc_roc": roc_auc_score(y_test, model.predict_proba(X_test)[:, 1]),
    })
    
    # Log model
    mlflow.xgboost.log_model(model, "model", input_example=X_test[:1])
    
    # Log artifacts
    mlflow.log_artifact("feature_importance.png")

# ── Model Registry ──────────────────────────────────────
mlflow.register_model("runs:/<run_id>/model", "churn-model")
# Stages: None → Staging → Production → Archived

# ── Load and serve ──────────────────────────────────────
model = mlflow.pyfunc.load_model("models:/churn-model/Production")
predictions = model.predict(X_new)

# CLI: mlflow models serve -m "models:/churn-model/Production" -p 5001

3. Weights & Biases

Weights & Biases (W&B) is a cloud-hosted experiment tracking platform that provides interactive visualization of training runs, hyperparameter sweep orchestration, and team collaboration features. Its rich dashboards — including confusion matrices, custom plots, and sweep analyses — make it especially valuable for deep learning projects with complex training dynamics.

import wandb

wandb.init(project="churn-prediction", config={"lr": 0.1, "epochs": 10})

for epoch in range(10):
    train_loss = train_one_epoch()
    val_loss = validate()
    wandb.log({"train_loss": train_loss, "val_loss": val_loss, "epoch": epoch})

# Log tables, plots, confusion matrices
wandb.log({"confusion_matrix": wandb.plot.confusion_matrix(y_true, y_pred, labels)})

# Hyperparameter sweeps
sweep_config = {
    "method": "bayes",
    "metric": {"name": "val_loss", "goal": "minimize"},
    "parameters": {
        "learning_rate": {"min": 0.001, "max": 0.1},
        "batch_size": {"values": [16, 32, 64]},
    },
}
sweep_id = wandb.sweep(sweep_config)
wandb.agent(sweep_id, function=train, count=20)

wandb.finish()

4. DVC (Data Version Control)

DVC (Data Version Control) is a Git-like version control system for large data files and ML pipelines that stores lightweight pointer files in Git while keeping actual data in remote storage (S3, GCS, Azure). It enables reproducible pipelines by tracking data, code, and configuration dependencies together, allowing teams to replay any historical experiment exactly.

# ── Initialize DVC ──────────────────────────────────────
dvc init
dvc remote add -d s3store s3://mybucket/dvc

# ── Track data ──────────────────────────────────────────
dvc add data/training.csv        # Creates data/training.csv.dvc
git add data/training.csv.dvc .gitignore
git commit -m "Add training data"
dvc push                         # Upload data to remote storage

# ── Pipelines ───────────────────────────────────────────
# dvc.yaml
# stages:
#   preprocess:
#     cmd: python preprocess.py
#     deps: [data/raw.csv, preprocess.py]
#     outs: [data/processed.csv]
#   train:
#     cmd: python train.py
#     deps: [data/processed.csv, train.py]
#     outs: [models/model.pkl]
#     metrics: [metrics.json]

dvc repro    # Run pipeline (skips unchanged stages)
dvc metrics diff   # Compare metrics across commits

5. Feature Stores

A feature store is a centralized system for computing, storing, and serving ML features consistently across both training (offline/batch) and inference (online/low-latency) environments. It eliminates training-serving skew, enables feature reuse across models and teams, and ensures point-in-time correctness to prevent data leakage during training.

# ── Feast (Feature Store) ────────────────────────────────
from feast import FeatureStore

store = FeatureStore(repo_path="feature_repo/")

# Define features in feature_repo/features.py:

# Retrieve features for training

    features=["user_features:age", "user_features:total_orders"],

6. Data Validation

Data validation automatically checks that incoming data conforms to expected schemas, types, ranges, and distributions before it enters the training or inference pipeline. Tools like Great Expectations and Pandera catch data quality issues — missing values, out-of-range values, unexpected categories — early, preventing silent model degradation from garbage-in data.

# ── Great Expectations ───────────────────────────────────
import great_expectations as gx

context = gx.get_context()
ds = context.sources.add_pandas("my_ds")
asset = ds.add_dataframe_asset("training_data")
batch = asset.build_batch_request(dataframe=df)

# Define expectations
validator = context.get_validator(batch_request=batch)
validator.expect_column_values_to_not_be_null("age")
validator.expect_column_values_to_be_between("age", min_value=0, max_value=120)
validator.expect_column_values_to_be_in_set("status", ["active", "inactive"])

result = validator.validate()  # Returns pass/fail for each expectation

# ── Pandera (pandas validation) ──────────────────────────
import pandera as pa

schema = pa.DataFrameSchema({
    "age": pa.Column(int, pa.Check.between(0, 120)),
    "income": pa.Column(float, pa.Check.greater_than(0)),
    "status": pa.Column(str, pa.Check.isin(["active", "inactive"])),
})
validated_df = schema.validate(df)  # Raises SchemaError on failure

7. Model Serving

Model serving is the infrastructure layer that exposes trained models as scalable, low-latency prediction endpoints, handling request batching, auto-scaling, and multi-model management. The choice of serving framework — from general-purpose (FastAPI, BentoML) to LLM-specialized (vLLM, TGI) — depends on model type, latency requirements, and throughput needs.

# ── BentoML ──────────────────────────────────────────────
import bentoml

saved_model = bentoml.sklearn.save_model("churn_model", model)

@bentoml.service
class ChurnService:
    model_ref = bentoml.models.get("churn_model:latest")
    
    @bentoml.api
    def predict(self, input_data: dict) -> dict:
        return {"prediction": self.model_ref.predict([input_data])[0]}

# bentoml serve service:ChurnService

# ── Ray Serve ────────────────────────────────────────────
from ray import serve

@serve.deployment(num_replicas=2, ray_actor_options={"num_cpus": 1})
class ModelDeployment:
    def __init__(self):
        self.model = load_model()
    
    async def __call__(self, request):
        data = await request.json()
        return {"prediction": self.model.predict(data["features"])}

app = ModelDeployment.bind()
serve.run(app)

8. Model Monitoring

1. Establish a reference baselineInput data driftPrediction (output) driftData qualityModel performancelabels are usually delayed

Model monitoring continuously tracks data drift, concept drift, and prediction drift in production to detect when a deployed model's performance is degrading. Statistical tests like the Kolmogorov-Smirnov test and Population Stability Index (PSI) compare current input distributions against a reference baseline, triggering alerts or automated retraining when significant shifts are detected.

MONITORING TYPES:
  Data Drift:     Input distribution changes
  Concept Drift:  P(Y|X) changes (relationship between features & target shifts)
  Prediction Drift: Model output distribution changes
  
  DETECTION:
  - Statistical tests: KS test, PSI (Population Stability Index)
  - Distribution comparison: Wasserstein distance, KL divergence
  - Reference window vs current window comparison
  
  PSI (Population Stability Index):
    PSI = Σ (pᵢ - qᵢ) × ln(pᵢ / qᵢ)
    PSI < 0.1:  No significant change
    0.1 ≤ PSI < 0.25:  Moderate shift
    PSI ≥ 0.25:  Significant shift → investigate or retrain
# ── Evidently (drift detection) ──────────────────────────
from evidently.report import Report
from evidently.metric_preset import DataDriftPreset

report = Report(metrics=[DataDriftPreset()])
report.run(reference_data=train_df, current_data=prod_df)
report.save_html("drift_report.html")

# ── Custom monitoring ────────────────────────────────────
from scipy.stats import ks_2samp

for col in feature_columns:
    stat, p_value = ks_2samp(train_df[col], prod_df[col])
    if p_value < 0.05:
        alert(f"Drift detected in {col}: KS={stat:.4f}, p={p_value:.4f}")

Drift monitoring in practice — the post-deployment playbook

1. Establish a reference baseline. Snapshot the training (or a stable recent production) window as the reference for each feature distribution, the prediction distribution, and a performance baseline.

2. Monitor four things, on a schedule (sliding/tumbling windows — daily/weekly batch, near-real-time for high-velocity streams): - Input data drift — per feature, reference vs current window. - Prediction (output) drift — has the score/class distribution shifted? (early, label-free warning.) - Data quality — schema, missing %, ranges, unseen categories. - Model performance — when labels arrive (the only true concept-drift signal).

3. Pick the right test per feature type (correct for multiple comparisons across 100s of features — don't alert on every p<0.05):

Feature typeTests
NumericKS test, PSI, Wasserstein / JS distance, mean/variance shift
CategoricalChi-square, PSI, JS-divergence, new-category rate

PSI bands: <0.1 stable · 0.1–0.25 moderate · ≥0.25 significant → investigate/retrain.

4. Concept drift — the hard part (P(Y|X) changed): - The only direct measure is performance on labeled production data (rolling AUC/PR/accuracy) — but labels are usually delayed (churn known weeks later, fraud after a chargeback). - While you wait for labels: watch proxy signals — prediction drift, shifts in confidence/entropy, drift in the top-importance features — and label-free performance estimation (e.g. NannyML CBPE/DLE). - Streaming detectors on the running error stream once labels arrive: DDM, EDDM, ADWIN, Page-Hinkley. - Key distinction: data drift ≠ degradation (new inputs may still be predictable); concept drift = degradation (the old X→Y mapping is stale).

5. Watch segment-level drift. Global metrics can look fine while a key subpopulation (a region, a new device type) has drifted badly — slice drift by important segments.

6. Response loop: severity-tiered alert → investigate (which features / which segment) → act: refresh features, retrain with gated promotion (must beat the current model on a holdout → canary → auto-rollback), or roll back. Log everything for audit.

Tools: Evidently & NannyML (label-free performance estimation), Arize / WhyLabs / Fiddler (hosted observability), river (online drift detectors), Great Expectations / Pandera (data-quality gates), Prometheus/Grafana (alerting).

9. Orchestration

Orchestration tools like Apache Airflow and Prefect define, schedule, and monitor multi-step ML pipelines — from data extraction through training, evaluation, and deployment — as directed acyclic graphs (DAGs). They handle task dependencies, retries, and scheduling, ensuring that complex workflows run reliably and are observable end-to-end.

# ── Airflow DAG ──────────────────────────────────────────
from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime

with DAG("ml_pipeline", start_date=datetime(2024, 1, 1), schedule_interval="@weekly"):
    extract = PythonOperator(task_id="extract", python_callable=extract_data)
    transform = PythonOperator(task_id="transform", python_callable=transform_data)
    train = PythonOperator(task_id="train", python_callable=train_model)
    evaluate = PythonOperator(task_id="evaluate", python_callable=evaluate_model)
    deploy = PythonOperator(task_id="deploy", python_callable=deploy_model)
    
    extract >> transform >> train >> evaluate >> deploy

# ── Prefect (modern alternative) ────────────────────────
from prefect import flow, task

@task
def train_model(data):
    model = XGBClassifier().fit(data)
    return model

@flow(name="ml-pipeline", log_prints=True)
def ml_pipeline():
    data = extract_data()
    features = transform(data)
    model = train_model(features)
    deploy(model)

10. CI/CD for ML

CI/CD for ML extends traditional software CI/CD with data validation, model training, performance-gated promotion, and containerized deployment steps. A well-designed ML CI/CD pipeline ensures that only models that pass quality thresholds on holdout data are built into Docker images and deployed to staging or production environments.

# .github/workflows/ml-cicd.yml
name: ML CI/CD
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run data validation
        run: python validate_data.py
      - name: Run model tests
        run: pytest tests/ -v
      - name: Check model performance
        run: |
          python train.py
          python evaluate.py --threshold 0.85  # Fail if accuracy < 0.85

  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - name: Build Docker image
        run: docker build -t model-service:${{ github.sha }} .
      - name: Push to registry
        run: docker push model-service:${{ github.sha }}
      - name: Deploy to staging
        run: kubectl set image deployment/model-service model=model-service:${{ github.sha }}

11. A/B Testing & Deployment Strategies

A/B testing and graduated deployment strategies — shadow mode, canary, and blue-green — reduce the risk of deploying new models by controlling traffic splits and measuring real-world impact before full rollout. Statistical significance testing on business metrics ensures that model changes deliver genuine improvements rather than random fluctuations.

DEPLOYMENT STRATEGIES:
  Shadow:    Send real traffic to new model, compare outputs (no impact)
  Canary:    Route 5% traffic → new model, 95% → old. Gradually increase.
  Blue-Green: Two identical environments. Switch DNS/LB instantly.
  A/B:       Random split with metrics tracking. Statistical significance testing.
  
  ┌─────────┐        5%  ┌────────────┐
  │ Traffic  │───────────→│ New Model  │ (Canary)
  │         │        95% ┌────────────┐
  │         │───────────→│ Old Model  │
  └─────────┘           └────────────┘

A/B TESTING for ML:
  1. Define metrics (CTR, revenue, engagement)
  2. Calculate required sample size (power analysis)
  3. Run experiment for sufficient duration
  4. Check statistical significance (p < 0.05)
  5. Guard against novelty effects (run 2+ weeks)

12. Model Compression

Model compression techniques — quantization, knowledge distillation, and pruning — reduce model size and inference latency while preserving accuracy, enabling deployment on resource-constrained devices or cost-sensitive serving environments. Quantization alone (FP32 → INT8) can deliver 2–4× speedups with less than 1% accuracy loss for most models.

COMPRESSION TECHNIQUES:
  Quantization:   FP32 → INT8/INT4 (reduce precision)
                  2-4× faster, 2-4× less memory, <1% accuracy loss
                  Tools: ONNX Runtime, TensorRT, bitsandbytes
  
  Knowledge Distillation: Train small "student" model to mimic large "teacher"
                  10-100× smaller, variable accuracy loss
                  Used for: BERT → DistilBERT, GPT-4 → fine-tune small model
  
  Pruning:       Remove unimportant weights (set to zero)
                 Structured (remove neurons) vs Unstructured (sparse weights)
                 2-10× faster with structured pruning
  
  ONNX:          Framework-agnostic model format
                 Export PyTorch/TF → ONNX → optimize with ONNX Runtime
                 2-5× faster inference vs native PyTorch

13. Experiment Reproducibility

Experiment reproducibility ensures that any past training run can be exactly recreated by fixing random seeds, pinning dependency versions, versioning data and configuration, and containerizing the training environment. Without reproducibility, debugging model regressions, comparing experiments, and meeting audit requirements become impossible.

REPRODUCIBILITY CHECKLIST:
  ✅ Fix random seeds (numpy, torch, python random)
  ✅ Pin all dependencies (pip freeze > requirements.txt)
  ✅ Version data (DVC, data registry)
  ✅ Version code (git commit hash in experiment log)
  ✅ Version config (params.yaml, tracked by MLflow/W&B)
  ✅ Log hardware info (GPU type, CUDA version)
  ✅ Docker for environment reproducibility
  ✅ Unit tests for data pipeline
  ✅ Deterministic operations (disable CUDA non-determinism)

14. Kubeflow & Vertex Pipelines

Kubeflow Pipelines and Google Vertex AI Pipelines provide Kubernetes-native platforms for defining, deploying, and managing ML workflows as reusable, containerized pipeline components. They enable scalable, cloud-native orchestration with built-in experiment tracking, artifact management, and integration with GPU/TPU resources.

# ── Kubeflow Pipeline ────────────────────────────────────
from kfp import dsl

@dsl.component
def train_component(data_path: str) -> str:
    model = train_model(data_path)
    model_path = save_model(model)
    return model_path

@dsl.pipeline(name="ml-pipeline")
def ml_pipeline(data_path: str):
    preprocess_task = preprocess_component(data_path=data_path)
    train_task = train_component(data_path=preprocess_task.output)
    deploy_task = deploy_component(model_path=train_task.output)

15. Production Best Practices

Production ML best practices span the full lifecycle: automated data validation and versioning, experiment tracking with reproducible training, staged deployments with model registry promotion, and continuous monitoring for drift and performance degradation. Following a comprehensive checklist ensures that ML systems are reliable, auditable, and maintainable in production.

PRODUCTION CHECKLIST:
  DATA:
  ✅ Automated data validation (schema + distribution checks)
  ✅ Data versioning (DVC or cloud storage with versioning)
  ✅ Feature store for shared features
  
  TRAINING:
  ✅ Experiment tracking (MLflow / W&B)
  ✅ Reproducibility (seeds, pinned deps, Docker)
  ✅ Automated retraining pipeline (scheduled or drift-triggered)
  
  SERVING:
  ✅ Model registry with staging/production stages
  ✅ Canary/shadow deployment for new models
  ✅ Health checks and auto-scaling
  ✅ Latency monitoring (P50, P95, P99)
  
  MONITORING:
  ✅ Data drift detection (PSI, KS test)
  ✅ Prediction drift monitoring
  ✅ Business metric tracking
  ✅ Alerting on anomalies
  
  GOVERNANCE:
  ✅ Model cards (purpose, limitations, fairness)
  ✅ Audit trail (who deployed what, when)
  ✅ A/B testing for model changes

16. Interview Deep Dive

Data driftConcept driftTriggerDataTrainGate

Q1: What is MLOps? Why is it needed?

A: MLOps applies DevOps principles to ML: CI/CD, monitoring, automation. It bridges the gap between building a model (notebook) and running it in production (reliable service). Without MLOps: models are deployed ad-hoc, performance degrades without detection (data drift), experiments aren't reproducible, and retraining is manual. MLOps maturity levels: 0 (manual everything) → 1 (automated training pipeline) → 2 (CI/CD for models) → 3 (full automation with monitoring and auto-retraining).

Q2: Explain data drift vs concept drift. How do you detect each?

A: Data drift: Input feature distribution changes (P(X) changes). Example: user demographics shift after marketing campaign. Detect with KS test, PSI per feature, comparing reference vs production distributions. Concept drift: The relationship P(Y|X) changes. Example: fraud patterns evolve. Detect by monitoring model performance metrics on labeled production data (delayed feedback). Data drift ≠ model degradation (new distribution might still be predictable). Concept drift = model degradation (old patterns no longer valid). Both require retraining, but concept drift is harder to detect without labels.

Q3: How would you design a model retraining pipeline?

A: (1) Trigger: Scheduled (weekly) or event-driven (drift detection alert, performance drop below threshold). (2) Data: Pull latest data, validate with Great Expectations, version with DVC. (3) Train: Run pipeline (Airflow/Prefect), log to MLflow/W&B, compare against current production model. (4) Gate: Only promote if new model beats production model on holdout set by ≥ 1%. (5) Deploy: Canary deployment (5% traffic), monitor for 24-48 hours. (6) Rollback: Auto-rollback if latency or error rate spikes.

Q4: Compare MLflow and Weights & Biases.

A: MLflow: Open-source, self-hosted, model registry + serving built-in, simpler UI, works offline. W&B: SaaS (cloud-hosted), superior visualization (interactive plots, tables), better hyperparameter sweep support, supports teams/collaboration. Both: experiment tracking, parameter logging, artifact storage. Choose MLflow for: self-hosted, air-gapped environments, model registry focus. Choose W&B for: team collaboration, complex experiments, rich visualization. Many teams use both: W&B for experiment tracking + MLflow for model registry.

Q5: How do you version data in ML projects?

A: (1) DVC: Git-like CLI, tracks data files via .dvc pointers, stores actual data in S3/GCS. Can version pipelines and reproduce experiments. (2) Delta Lake: Versioned data lake on top of Parquet (Databricks). (3) Cloud storage versioning: S3 versioning, GCS object versioning. (4) Feature store: Feast stores point-in-time correct feature snapshots. Best practice: Version data + code + config together. Each experiment links to a specific data version (DVC hash), code version (git commit), and config (params.yaml).

Q6: What is a feature store? When do you need one?

A: A feature store is a centralized system for computing, storing, and serving ML features. Two serving modes: offline (historical features for training) and online (low-latency features for inference). Need one when: (1) Multiple models share features (avoid recomputation). (2) Training-serving skew is a risk (ensures same feature logic). (3) Features need point-in-time correctness (avoid data leakage). (4) Teams share features across projects. Tools: Feast (open-source), Tecton (managed), Hopsworks. Overkill for: single model, small team, batch-only inference.

Q7: How do you deploy ML models? Compare different approaches.

A: (1) REST API (FastAPI/Flask): Most common, works for any model. (2) BentoML: ML-specific, handles batching, multi-model. (3) Ray Serve: Scalable, multi-model, built-in A/B testing. (4) vLLM/TGI: Specialized for LLMs (continuous batching, PagedAttention). (5) Seldon/KServe: Kubernetes-native, supports canary and A/B. (6) Batch: No API — run predictions on a schedule (Spark, Airflow). Choose based on: latency requirements, scale, model type, infrastructure.

Q8: What is model monitoring? What metrics do you track?

A: Four levels of monitoring: (1) Infrastructure: Latency (P50/P95/P99), throughput (QPS), error rate, CPU/GPU utilization. (2) Data quality: Missing values, schema violations, outliers in input features. (3) Data/prediction drift: PSI per feature, KS test, output distribution changes. (4) Business metrics: Revenue impact, user engagement, conversion rate. Tools: Evidently (drift), Prometheus/Grafana (infra), custom dashboards (business). Alert priorities: infra issues = P0, drift detected = P1, performance degraded = P2.

1. DevOps Fundamentals

DevOps is a set of practices that unifies software development and IT operations, emphasizing automation, continuous integration/delivery, infrastructure as code, and monitoring throughout the application lifecycle. Its core goal is to shorten the development cycle, increase deployment frequency, and deliver reliable software at scale.

DevOps = Development + Operations

  3. Containerization: Docker + Kubernetes
  4. Monitoring: Prometheus, Grafana, ELK
  5. Collaboration: GitOps, PRs, code review

2. Docker

Docker packages applications and their dependencies into lightweight, portable containers that run consistently across any environment — development, testing, and production. Multi-stage builds, minimal base images, and non-root user execution are essential best practices for creating secure, production-ready container images.

# ── Multi-stage build (production best practice) ────────
# Stage 1: Build
FROM python:3.12-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --user -r requirements.txt

# Stage 2: Runtime (smaller image)
FROM python:3.12-slim
WORKDIR /app
COPY --from=builder /root/.local /root/.local
COPY . .
ENV PATH=/root/.local/bin:$PATH
EXPOSE 8000
USER 1000:1000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
# ── Essential Docker commands ────────────────────────────
docker build -t myapp:v1 .
docker run -d -p 8000:8000 --name myapp myapp:v1
docker exec -it myapp bash
docker logs myapp --tail 100 -f
docker stop myapp && docker rm myapp

# ── Image management ────────────────────────────────────
docker images                  # List images
docker rmi myapp:v1           # Remove image
docker system prune -a         # Clean everything unused

# ── Best practices ──────────────────────────────────────
# 1. Use specific base image tags (python:3.12-slim, NOT python:latest)
# 2. Multi-stage builds (reduce final image size)
# 3. .dockerignore (exclude .git, __pycache__, .env)
# 4. Non-root user (USER 1000)
# 5. COPY requirements.txt first (layer caching)
# 6. --no-cache-dir for pip (smaller image)

3. Docker Compose

Docker Compose defines and manages multi-container applications (e.g., API + database + cache) as a single declarative YAML file, handling networking, volume mounts, health checks, and startup ordering. It is the standard tool for local development environments and simple multi-service deployments.

# docker-compose.yml
version: "3.9"
services:
  api:
    build: .
    ports: ["8000:8000"]
    environment:
      - DATABASE_URL=postgresql://user:pass@db:5432/mydb
      - REDIS_URL=redis://redis:6379
    depends_on:
      db:
        condition: service_healthy
    volumes:
      - ./app:/app  # Dev mount
    restart: unless-stopped

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
      POSTGRES_DB: mydb
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user"]
      interval: 5s
      timeout: 5s
      retries: 5

  redis:
    image: redis:7-alpine
    ports: ["6379:6379"]

volumes:
  pgdata:
docker compose up -d           # Start all services
docker compose logs api -f     # Follow API logs
docker compose down -v         # Stop and remove volumes

4. Kubernetes Core

smallest → largestContainerapp + runtime + libraries + configPodsmallest thing K8s deploys1+ containers

Kubernetes (K8s) is a container orchestration platform that automates deployment, scaling, self-healing, and networking for containerized applications across clusters of machines. Its declarative model — where you define the desired state and controllers continuously reconcile actual state to match — is the foundation of modern cloud-native infrastructure.

The Hierarchy: Container → Pod → Node → Cluster

Before any YAML, get the four nesting layers straight. They sit inside each other, smallest → largest:

LayerWhat it isAnalogy
🟦 ContainerYour app + runtime + libraries + config, isolated from the host and built from an image (e.g. a Docker image). Shares the host kernel → fast and small (unlike a VM).A furnished apartment unit
🟩 PodThe smallest thing K8s deploys. Wraps 1+ containers that share one IP address, storage volumes, and lifecycle (e.g. an app + a logging sidecar). K8s schedules and scales pods, not individual containers. Pods are ephemeral — if one dies it's replaced by a new one with a new IP.A room with roommates sharing utilities
🟨 NodeA worker machine (cloud VM or physical server) that actually runs pods. Runs a kubelet (talks to the control plane) and a container runtime (containerd). One node hosts many pods, bounded by its CPU/RAM.One building
🟥 ClusterThe whole system: all nodes + the control plane (API server, scheduler, etcd). The control plane decides which pod runs on which node and handles scaling, self-healing, and rollouts. You talk to the cluster via kubectl.The whole complex + its manager

5. Kubernetes Workloads & Networking

Kubernetes Workloads (Deployments, ReplicaSets) manage the lifecycle and scaling of Pods, while Services and Ingress resources provide stable networking, load balancing, and HTTP routing to expose applications internally and externally. Rolling updates with readiness probes ensure zero-downtime deployments.

# ── Deployment ──────────────────────────────────────────
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 3
  selector:
    matchLabels:
      app: myapp
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
      - name: myapp
        image: myapp:v1
        ports:
        - containerPort: 8000
        envFrom:
        - configMapRef:
            name: myapp-config
        - secretRef:
            name: myapp-secrets
---
# ── Service (ClusterIP — internal) ──────────────────────
apiVersion: v1
kind: Service
metadata:
  name: myapp-svc
spec:
  selector:
    app: myapp
  ports:
  - port: 80
    targetPort: 8000
  type: ClusterIP
---
# ── Ingress ─────────────────────────────────────────────
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp-ingress
  annotations:
    nginx.ingress.kubernetes.io/rate-limit: "100"
spec:
  rules:
  - host: api.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: myapp-svc
            port:
              number: 80
  tls:
  - hosts: [api.example.com]
    secretName: tls-secret

6. Kubernetes Config, Storage & Autoscaling

ConfigMaps and Secrets externalize configuration and sensitive data from container images, PersistentVolumeClaims provide durable storage, and the Horizontal Pod Autoscaler (HPA) automatically adjusts replica counts based on CPU, memory, or custom metrics. Together, these resources make applications configurable, stateful when needed, and elastically scalable.

# ── ConfigMap ────────────────────────────────────────────
apiVersion: v1
kind: ConfigMap
metadata:
  name: myapp-config
data:
  DATABASE_HOST: "db-service"
  LOG_LEVEL: "INFO"
---
# ── Secret ───────────────────────────────────────────────
apiVersion: v1
kind: Secret
metadata:
  name: myapp-secrets
type: Opaque
data:
  DB_PASSWORD: cGFzc3dvcmQxMjM=  # base64 encoded
---
# ── PersistentVolumeClaim ────────────────────────────────
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data-pvc
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 10Gi
---
# ── Horizontal Pod Autoscaler ────────────────────────────
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70

7. Helm

Helm is the package manager for Kubernetes, allowing you to define, install, upgrade, and rollback complex multi-resource applications as reusable, parameterized charts. It templates Kubernetes manifests with configurable values, making it easy to manage environment-specific deployments and share application packages.

# Helm = Package manager for Kubernetes
helm repo add bitnami https://charts.bitnami.com/bitnami
helm install my-redis bitnami/redis --set auth.enabled=false
helm upgrade my-redis bitnami/redis --set replica.replicaCount=3
helm list                # List installed releases
helm rollback my-redis 1 # Rollback to revision 1

8. Terraform

Terraform is a declarative Infrastructure as Code (IaC) tool that provisions and manages cloud resources — VMs, networks, databases, Kubernetes clusters — across any provider using HCL configuration files. Its state-based approach tracks what exists, plans changes before applying them, and enables reproducible, version-controlled infrastructure.

# ── AWS EC2 instance ────────────────────────────────────
provider "aws" {
  region = "us-east-1"
}

resource "aws_instance" "ml_server" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "p3.2xlarge"
  
  tags = {
    Name = "ml-training-server"
  }
}

# terraform plan    → Preview changes
# terraform apply   → Apply changes
# terraform destroy → Tear down

9. CI/CD (GitHub Actions)

CI/CD (Continuous Integration / Continuous Delivery) automates the build, test, and deployment pipeline so that every code change is validated and delivered to production reliably. GitHub Actions implements CI/CD as event-driven YAML workflows with reusable steps for linting, testing, building Docker images, and deploying to Kubernetes.

name: CI/CD Pipeline
on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-python@v5
      with:
        python-version: "3.12"
    - name: Install deps
      run: pip install -r requirements.txt
    - name: Lint
      run: ruff check .
    - name: Test
      run: pytest tests/ -v --cov

  build-deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    - name: Build Docker image
      run: docker build -t myapp:${{ github.sha }} .
    - name: Push to ECR
      run: |
        aws ecr get-login-password | docker login --username AWS --password-stdin $ECR_URL
        docker push $ECR_URL/myapp:${{ github.sha }}
    - name: Deploy to K8s
      run: kubectl set image deployment/myapp myapp=$ECR_URL/myapp:${{ github.sha }}

10. GitOps (ArgoCD)

GitOps is an operational model where Git repositories serve as the single source of truth for declarative infrastructure and application state, with automated agents ensuring the live environment matches what is committed. ArgoCD implements GitOps for Kubernetes by continuously watching Git repos and syncing cluster state, enabling audit-trail-backed deployments and instant rollbacks via git revert.

GITOPS PRINCIPLES:
  1. Git is the single source of truth
  2. Desired state is declarative (YAML in Git)
  3. Changes are made via Pull Requests
  4. Automated reconciliation (ArgoCD watches Git → applies to cluster)
  
  Developer → PR to Git → Merge → ArgoCD detects → Syncs to K8s
  
  ARGOCD:
  - Watches Git repos for K8s manifest changes
  - Automatically syncs cluster state to match Git
  - Rollback = git revert
  - Self-healing (manual kubectl changes get reverted)

11. Monitoring (Prometheus + Grafana)

Prometheus scrapes and stores time-series metrics from services and infrastructure, while Grafana visualizes them in dashboards and Alertmanager routes threshold-based alerts. Monitoring the USE metrics (Utilization, Saturation, Errors) for infrastructure and RED metrics (Rate, Errors, Duration) for services provides comprehensive operational visibility.

MONITORING STACK:
  Prometheus:  Scrapes metrics from services (pull-based)
  Grafana:     Visualizes metrics in dashboards
  Alertmanager: Routes alerts (email, Slack, PagerDuty)
  
  KEY METRICS (USE / RED):
  USE (infrastructure):
    Utilization: CPU%, memory%, disk%
    Saturation:  Queue depth, thread pool usage
    Errors:      Disk errors, network errors
    
  RED (services):
    Rate:     Requests per second
    Errors:   Error rate (%)
    Duration: Latency (P50, P95, P99)

  GOLDEN SIGNALS (SRE):
    Latency, Traffic, Errors, Saturation

12. Logging

Centralized logging aggregates application and infrastructure logs into a searchable, indexed store — typically the ELK (Elasticsearch, Logstash, Kibana) or EFK (Elasticsearch, Fluentd, Kibana) stack. Structured JSON logging with consistent fields (timestamp, level, service, request_id) enables fast debugging, correlation across services, and long-term operational analysis.

LOGGING STACK:

13. Container Security

Container security encompasses a layered defense of minimal base images, non-root execution, image vulnerability scanning (Trivy, Snyk), secret management, network policies, and Kubernetes Pod Security Standards. Proactively hardening containers prevents supply-chain attacks, privilege escalation, and data exposure in production environments.

SECURITY CHECKLIST:
  ✅ Use minimal base images (python:3.12-slim, alpine)
  ✅ Run as non-root user (USER 1000)
  ✅ No secrets in images (use K8s Secrets or vault)
  ✅ Scan images for CVEs (Trivy, Snyk, Docker Scout)
  ✅ Use specific image tags (never :latest in production)
  ✅ Read-only filesystem where possible
  ✅ Drop all capabilities, add only needed ones
  ✅ Network policies to restrict pod-to-pod communication
  ✅ Pod Security Standards (restricted profile)
  ✅ RBAC for K8s access control

  # Scan image
  trivy image myapp:v1
  
  # K8s security context
  securityContext:
    runAsNonRoot: true
    readOnlyRootFilesystem: true
    allowPrivilegeEscalation: false

14. Deployment Strategies

Deployment strategies — recreate, rolling update, blue-green, and canary — control how new application versions replace old ones, each trading off between downtime risk, rollback speed, and resource cost. Rolling updates (Kubernetes default) and canary deployments are the most common choices for achieving zero-downtime, low-risk releases in production.

COMPARISON:
  Strategy    │ Downtime │ Risk   │ Rollback  │ Resource
  ────────────┼──────────┼────────┼───────────┼──────────
  Recreate    │ Yes      │ High   │ Slow      │ 1× 
  Rolling     │ No       │ Medium │ Medium    │ 1-2×
  Blue-Green  │ No       │ Low    │ Instant   │ 2×
  Canary      │ No       │ Low    │ Fast      │ 1.1×
  
  Rolling Update (K8s default):
    Replace pods one by one. maxSurge=1, maxUnavailable=0.
    
  Blue-Green:
    Run two full environments. Switch traffic via Service selector.
    Rollback = switch back.
    
  Canary:
    Route small % of traffic to new version. Monitor. Gradually increase.
    Tools: Istio, Flagger, Argo Rollouts.

15. Ansible

Ansible is an agentless configuration management and automation tool. Unlike Terraform (which provisions infrastructure), Ansible configures servers — installing packages, deploying code, managing services.

15.1 Core Concepts

Concept          Description
─────────────────────────────────────────────────────────
Inventory        List of target hosts (static file or dynamic)
Playbook         YAML file defining automation tasks
Role             Reusable, organized collection of tasks
Module           Unit of work (apt, copy, service, docker, etc.)
Handler          Task triggered by a notify (e.g., restart nginx)
Fact             System info gathered from hosts (OS, IP, RAM)
Idempotency      Running playbook twice = same result
Agentless        Uses SSH — no agent installed on targets

15.3 Playbook Examples

# deploy_ml_service.yml
---
- name: Deploy ML inference service
  hosts: mlservers
  become: yes          # Run as sudo
  vars:
    app_dir: /opt/ml-service
    model_version: "v2.1.0"

  tasks:
    - name: Install system dependencies
      apt:
        name:
          - python3-pip
          - python3-venv
          - nginx
        state: present
        update_cache: yes

    - name: Create application directory
      file:
        path: "{{ app_dir }}"
        state: directory
        owner: ubuntu
        mode: '0755'

    - name: Copy application code
      copy:
        src: ./app/
        dest: "{{ app_dir }}/"
      notify: Restart ML service       # Triggers handler

    - name: Install Python requirements
      pip:
        requirements: "{{ app_dir }}/requirements.txt"
        virtualenv: "{{ app_dir }}/venv"

    - name: Download model artifact
      get_url:
        url: "https://models.example.com/{{ model_version }}/model.pt"
        dest: "{{ app_dir }}/models/model.pt"

    - name: Configure systemd service
      template:
        src: templates/ml-service.service.j2
        dest: /etc/systemd/system/ml-service.service
      notify: Restart ML service

    - name: Ensure service is running
      systemd:
        name: ml-service
        state: started
        enabled: yes

  handlers:
    - name: Restart ML service
      systemd:
        name: ml-service
        state: restarted
        daemon_reload: yes

16. Interview Deep Dive

Q1: Explain Docker vs VMs.

A: VMs: Full OS on hypervisor, minutes to boot, GB-sized, strong isolation. Docker containers: Share host kernel, start in seconds, MB-sized, process-level isolation. Containers use Linux namespaces (process, network, mount isolation) and cgroups (resource limits). VMs are more isolated but heavier. In practice: containers for microservices, VMs for legacy apps or different OS requirements.

Q2: What happens when you run kubectl apply -f deployment.yaml?

A: (1) kubectl sends the manifest to the API Server. (2) API Server validates and stores in etcd. (3) Deployment Controller detects new desired state, creates/updates a ReplicaSet. (4) ReplicaSet Controller creates Pod objects. (5) Scheduler assigns Pods to Nodes based on resources/constraints. (6) kubelet on the assigned Node pulls the image and starts the container. (7) kube-proxy updates iptables/IPVS rules for networking. The entire system is reconciliation-based: controllers continuously compare desired vs actual state.

Q3: How do you implement zero-downtime deployment?

A: (1) Rolling update: maxSurge=1, maxUnavailable=0 — new pod starts before old one terminates. (2) Readiness probes: K8s only routes traffic to pods that pass the readiness check. (3) Graceful shutdown: Application handles SIGTERM, finishes in-flight requests (terminationGracePeriodSeconds). (4) PreStop hook: Add a small sleep (5s) to allow kube-proxy to update routing before pod stops. (5) PodDisruptionBudget: Ensure minimum pods during voluntary disruptions.

Q4: Explain Terraform vs Ansible.

A: Terraform: Declarative IaC for provisioning infrastructure (create VMs, networks, load balancers). State-based — tracks what exists. Best for: cloud infrastructure. Ansible: Procedural configuration management (install packages, configure services, deploy apps). Agentless (SSH). Best for: configuring existing servers. They're complementary: Terraform creates the infrastructure → Ansible configures it.

Q5: What is GitOps? How does ArgoCD implement it?

A: GitOps uses Git as the single source of truth for infrastructure/application state. All changes go through PRs. ArgoCD watches a Git repo containing K8s manifests. When a commit is merged, ArgoCD detects the diff and syncs the cluster to match Git. Self-healing: manual kubectl changes get reverted to match Git. Rollback = git revert. Benefits: audit trail (git log), consistency (Git = production), security (no direct cluster access needed).

Q6: How do you monitor a Kubernetes cluster?

A: Infrastructure: Prometheus scrapes node metrics (CPU, memory, disk via node-exporter) + container metrics (from kubelet/cAdvisor). Application: Instrument with Prometheus client library (request count, latency histogram). Visualization: Grafana dashboards (USE for infra, RED for services). Alerting: Alertmanager routes alerts (high CPU → Slack, pod crash loop → PagerDuty). Logging: EFK stack (Fluentd collects → Elasticsearch indexes → Kibana visualizes). Monitor golden signals: Latency, Traffic, Errors, Saturation.

Q7: How do you secure a Kubernetes cluster?

A: Layers: (1) RBAC: Least-privilege roles for users/service accounts. (2) Network Policies: Restrict pod-to-pod communication (default deny, allow only needed). (3) Pod Security: Non-root, read-only filesystem, drop capabilities. (4) Secrets: Use external secrets manager (Vault, AWS Secrets Manager), not plain K8s Secrets. (5) Image security: Scan images (Trivy), use signed images, private registry. (6) Audit logging: API server audit logs for forensics. (7) Admission controllers: OPA/Gatekeeper for policy enforcement.

Q8: Design a CI/CD pipeline for an ML application.

A: Stages: (1) Code CI: Lint (ruff), type check (mypy), unit tests (pytest). Triggered on PR. (2) Data validation: Run Great Expectations/Pandera on training data. (3) Model CI: Train model, evaluate on holdout set, compare with current production model (fail if worse). Log to MLflow. (4) Build: Docker multi-stage build, push to container registry. (5) Deploy staging: Deploy to staging K8s, run integration tests. (6) Deploy production: Canary deployment (5% → monitor → 100%). (7) Monitor: Prometheus metrics + drift detection. Tools: GitHub Actions → MLflow → Docker → ArgoCD → Prometheus.

Q1: How do you choose between AWS SageMaker, GCP Vertex AI, and Azure ML?

A: Decision factors: (1) Existing cloud: Use what your company already uses (data gravity, IAM). (2) GenAI focus: Azure for OpenAI models, GCP for Gemini, AWS for Bedrock (widest model selection). (3) Spark/data engineering: Databricks if heavy Spark usage. (4) MLOps maturity: SageMaker has most features; Vertex is simpler; Azure has best Responsible AI tools. (5) Cost: Compare specific instance pricing for your workload. (6) GPU availability: H100s may be more available on one cloud. Rule: Don't multi-cloud unless you have a strong reason — complexity is the enemy.

Q2: How do you handle spot instance interruptions during training?

A: (1) Checkpoint frequently: Save model + optimizer state every N steps to persistent storage (S3/GCS). (2) Use managed spot: SageMaker handles interruption/resumption automatically with use_spot_instances=True and checkpoint_s3_uri. (3) Elastic training: PyTorch Elastic / DeepSpeed can handle node failures. (4) Instance diversity: Use multiple instance types to reduce interruption probability. (5) Max wait: Set maximum time willing to wait for spot capacity. Never use spot for real-time serving endpoints.

Q3: How do you estimate GPU requirements for training a model?

A: VRAM estimation: Model params × bytes per param (FP16 = 2 bytes, FP32 = 4 bytes). For training, add optimizer states (Adam = 8 bytes/param for FP32), gradients (same size as params), and activations (depends on batch size). Rule of thumb: Training FP16 needs ~16 bytes per parameter. 7B model training needs ~112 GB VRAM → 2× A100 80GB. QLoRA reduces to ~5 GB for 7B. Inference: Only need model weights. 7B FP16 = 14 GB → fits on single A10G. Quantized to 4-bit = 3.5 GB → fits on T4.

Q4: How do you deploy ML models with autoscaling?

A: (1) Choose metric: InvocationsPerInstance (request rate) or CPUUtilization/GPUMemoryUtilization. (2) Set target: e.g., 70% GPU utilization. (3) Min/max instances: min=1 (or 0 for serverless), max based on budget and peak traffic estimate. (4) Cooldown: Scale-up fast (1-2 min), scale-down slow (5-10 min) to avoid flapping. (5) Load testing: Use Locust or k6 to validate scaling behavior. (6) Multi-model endpoints: Pack multiple models per instance for better utilization.

Q5: What is a Feature Store? Why is it critical?

A: A Feature Store provides a centralized repository for ML features with: (1) Offline store (S3/BigQuery): High-throughput reads for training data. (2) Online store (DynamoDB/Redis): Low-latency reads for real-time serving. (3) Single definition: Same feature transformation code for training and serving → eliminates training-serving skew. (4) Time-travel: Point-in-time correct features (avoid data leakage). (5) Discovery: Data scientists can search and reuse features. Tools: Feast (open-source), SageMaker Feature Store, Vertex Feature Store, Tecton, Databricks Feature Store.

Q6: How do you optimize inference costs?

A: Layered approach: (1) Model: Quantize (INT8/INT4), distill (teacher → student), prune unused weights. (2) Runtime: Use optimized runtimes (TensorRT, ONNX Runtime, vLLM for LLMs). (3) Batching: Dynamic batching to maximize GPU utilization. (4) Hardware: Use cheapest GPU that meets latency SLA (T4 > A10G > A100 for cost). (5) Architecture: Multi-model endpoints (share GPU), caching frequent predictions. (6) Scaling: Serverless for sporadic traffic, reserved instances for steady traffic. (7) Multi-tenancy: Triton Inference Server to serve multiple models on one GPU.

Q7: Compare Databricks vs SageMaker for ML workflows.

A: Databricks: Best when data engineering is heavy (Spark, Delta Lake, ETL). Native MLflow integration. Unity Catalog for governance. Collaborative notebooks. Good for teams doing data + ML. SageMaker: Best for dedicated ML teams. More ML-specific features (HPO, Model Monitor, Clarify, Pipelines). Better for production ML at scale. Bring-your-own-container flexibility. Both: Have feature stores, model registries, endpoints. Decision: If >50% of work is data engineering → Databricks. If dedicated ML platform needed → SageMaker.

Q8: How do you handle data governance for ML in the cloud?

A: (1) Data lineage: Track which data was used for each model version (DVC, MLflow, cloud-native tools). (2) Access control: IAM policies, column-level security for PII. (3) Encryption: KMS for at-rest, TLS for in-transit. (4) Residency: Deploy in correct regions for GDPR/sovereignty. (5) Deletion: Ability to retrain models without deleted user data (GDPR right to erasure). (6) Audit: All data access logged (CloudTrail/Stackdriver). (7) Cataloging: Tag PII/sensitive columns in data catalog (AWS Glue Catalog, GCP Data Catalog, Purview). (8) Model cards: Document training data sources, biases, intended use.

3. SDLC Models & Methodologies
•

3.1 Waterfall

WATERFALL MODEL:
  Requirements → Design → Implementation → Testing → Deployment → Maintenance
  
  ┌──────────┐
  │ Require- │
  │ ments    │──┐
  └──────────┘  │
                ▼
           ┌──────────┐
           │ Design   │──┐
           └──────────┘  │
                         ▼
                    ┌──────────┐
                    │ Coding   │──┐
                    └──────────┘  │
                                  ▼
                             ┌──────────┐
                             │ Testing  │──┐
                             └──────────┘  │
                                           ▼
                                      ┌──────────┐
                                      │ Deploy   │
                                      └──────────┘

CHARACTERISTICS:
  ✅ Simple, linear, easy to understand
  ✅ Clear milestones and deliverables
  ✅ Works for well-defined, stable requirements
  ✅ Good documentation
  
  ✗ No working software until late
  ✗ Very expensive to change requirements mid-project
  ✗ Testing happens too late (bugs are costly)
  ✗ Customer doesn't see product until the end
  
WHEN TO USE:
  • Requirements are crystal clear and won't change
  • Regulatory environments (defense, healthcare)
  • Short, simple projects
  • Hardware-dependent projects
•

3.2 V-Model (Verification & Validation)

V-MODEL:
  Each development phase has a corresponding testing phase.
  
  Requirements ────────────────────── Acceptance Testing
       ╲                                    ╱
    System Design ──────────────── System Testing
         ╲                              ╱
      Module Design ────────── Integration Testing
           ╲                        ╱
            Implementation & Unit Testing

  Left side: Verification (are we building it right?)
  Right side: Validation (did we build the right thing?)

WHEN TO USE:
  • Safety-critical systems (medical devices, aviation)
  • When testing must be planned upfront
•

3.3 Iterative & Incremental

ITERATIVE MODEL:
  Build a subset → Get feedback → Refine → Build next subset → ...
  
  Each iteration produces a working version with more features.
  
  Iteration 1: Core login + basic CRUD
  Iteration 2: + Search + Filters
  Iteration 3: + Reporting + Export
  Iteration 4: + Admin panel + Analytics
  
BENEFITS:
  ✅ Working software early
  ✅ Can adapt to changing requirements
  ✅ Risk is managed per iteration
  ✅ Feedback drives improvement
•

3.4 Spiral Model

SPIRAL MODEL (Barry Boehm):
  Combines iterative development with systematic risk management.
  
  Each cycle has 4 quadrants:
    1. Determine objectives, alternatives, constraints
    2. Evaluate alternatives, identify & resolve risks
    3. Develop and verify the product
    4. Plan the next iteration
  
  Best for: Large, complex, high-risk projects
  (e.g., building a new ML platform from scratch)
•

4.2 Scrum Framework

SCRUM ROLES:
  Product Owner (PO):
    • Owns the Product Backlog
    • Prioritizes features by business value
    • Single source of truth for "what to build"
    • Accepts/rejects sprint deliverables
  
  Scrum Master (SM):
    • Facilitates Scrum ceremonies
    • Removes blockers / impediments
    • Coaches team on Agile practices
    • Shields team from external distractions
    • NOT a project manager — a servant-leader
  
  Development Team:
    • Cross-functional (dev, QA, design, DevOps)
    • Self-organizing (decide HOW to do the work)
    • Typically 5-9 people
    • Collectively accountable for delivery

SCRUM ARTIFACTS:
  Product Backlog:   Ordered list of everything needed (features, bugs, tech debt)
  Sprint Backlog:    Subset of Product Backlog committed for current sprint
  Increment:         Working, potentially shippable product at end of sprint

4.3 User Stories & Estimation

USER STORY FORMAT:
  "As a [role], I want [feature], so that [benefit]."
  
  Example:
  "As an ML engineer, I want to version my training datasets,
   so that I can reproduce any experiment result."

ACCEPTANCE CRITERIA (GIVEN-WHEN-THEN):
  Given: I have uploaded a CSV file
  When:  I click "Train Model"
  Then:  A training job starts within 30 seconds
  And:   I see a progress indicator with estimated time

INVEST CRITERIA FOR GOOD STORIES:
  I — Independent (no dependencies between stories)
  N — Negotiable (details can be discussed)
  V — Valuable (delivers user/business value)
  E — Estimable (team can size it)
  S — Small (fits in one sprint)
  T — Testable (has clear acceptance criteria)

ESTIMATION METHODS:
  Story Points:     Relative sizing (Fibonacci: 1, 2, 3, 5, 8, 13, 21)
                    Measures complexity + effort + uncertainty
                    NOT hours — it's relative to a reference story
  
  Planning Poker:   Each team member shows their estimate simultaneously
                    Discuss outliers → re-estimate → converge
  
  T-Shirt Sizing:   XS, S, M, L, XL (for roadmap-level estimates)
•

4.4 Velocity & Burndown

VELOCITY:
  Average story points completed per sprint.
  Used for planning (how many points to commit next sprint).
  
  Sprint 1: 21 pts | Sprint 2: 25 pts | Sprint 3: 18 pts
  Average velocity = (21 + 25 + 18) / 3 = ~21 pts/sprint
  
  → Don't commit more than ~21 pts next sprint
  → Velocity stabilizes after 3-4 sprints

BURNDOWN CHART:

  X-axis: Days in sprint

8. Testing Strategies
•

8.1 Test-Driven Development (TDD)

TDD CYCLE (Red-Green-Refactor):
  1. RED:    Write a failing test first
  2. GREEN:  Write minimum code to pass the test
  3. REFACTOR: Clean up code while keeping tests green
  
  Repeat for each small behavior.

EXAMPLE (Python + pytest):
  # Step 1: RED — Write test
  def test_calculate_accuracy():
      y_true = [1, 0, 1, 1, 0]
      y_pred = [1, 0, 0, 1, 0]
      assert calculate_accuracy(y_true, y_pred) == 0.8
  
  # Step 2: GREEN — Write implementation
  def calculate_accuracy(y_true, y_pred):
      correct = sum(t == p for t, p in zip(y_true, y_pred))
      return correct / len(y_true)
  
  # Step 3: REFACTOR (if needed)
  # Maybe add input validation, handle empty lists, etc.
•

8.2 Behavior-Driven Development (BDD)

BDD uses Gherkin syntax (Given-When-Then):

Feature: Model Prediction API
  Scenario: Successful prediction
    Given the ML model is loaded and healthy
    And I have valid input features {"age": 25, "income": 50000}
    When I POST to /predict
    Then the response status code is 200
    And the response contains a "prediction" field
    And the prediction is a number between 0 and 1

  Scenario: Invalid input
    Given the ML model is loaded
    When I POST to /predict with empty body
    Then the response status code is 422
    And the response contains validation errors

TOOLS: Behave (Python), Cucumber (Java/JS), SpecFlow (C#)
•

16. Interview Deep Dive
•

Q1: What is SDLC? Why is it important?

A: SDLC is a structured process for software development covering planning, requirements, design, coding, testing, deployment, and maintenance. It matters because it brings predictability, quality assurance, risk management, and stakeholder alignment to software projects. Without it, projects suffer from scope creep, late bug discovery, missed deadlines, and unmaintainable code. Different methodologies (Waterfall, Agile, Spiral) implement SDLC phases differently based on project needs.

•

Q2: Compare Agile vs Waterfall. When would you use each?

WaterfallAgile

A: Waterfall: Sequential, phase-by-phase, no going back. Best for fixed requirements, regulatory environments, short simple projects. Agile: Iterative, incremental delivery, embraces change. Best for evolving requirements, complex projects, when early feedback is valuable. Key tradeoff: Waterfall gives predictability and documentation; Agile gives flexibility and faster time-to-value. Most modern software uses Agile; Waterfall still used in embedded systems, defense, and hardware-dependent projects. In practice, many teams use a hybrid — Agile sprints with Waterfall-style milestone gates for compliance.

•

Q3: Explain Scrum ceremonies and their purpose.

Sprint PlanningDaily StandupSprint Review/DemoSprint Retrospective

A: Sprint Planning: Team selects Product Backlog items for the sprint and defines how to implement them. Sets the Sprint Goal. Daily Standup: 15-minute sync — what I did yesterday, what I'll do today, any blockers. Not a status report — it's team coordination. Sprint Review/Demo: Show working software to stakeholders, get feedback. Updates Product Backlog based on feedback. Sprint Retrospective: What went well, what didn't, what to improve. Produces action items for the next sprint. The retrospective is often the most valuable ceremony — it's how teams continuously improve.

•

Q4: What is the difference between CI, CD (Delivery), and CD (Deployment)?

CI (Continuous Integration)CD (Continuous Delivery)CD (Continuous Deployment)

A: CI (Continuous Integration): Developers merge frequently (at least daily), each merge triggers automated build and tests. Goal: detect integration issues early. CD (Continuous Delivery): Code is always in a deployable state — deploying to production requires a manual approval. CD (Continuous Deployment): Every change that passes automated tests is automatically deployed to production — no human gate. Progression: CI → Continuous Delivery → Continuous Deployment. Most teams are at Continuous Delivery; Continuous Deployment requires very mature test suites and monitoring.

•

Q5: How does SDLC differ for ML projects compared to traditional software?

Data dependencyNon-determinismContinuous degradationVersioning complexityExperimentation

A: ML projects have unique challenges: (1) Data dependency: ML quality depends on data quality — SDLC must include data collection, validation, and versioning phases. (2) Non-determinism: Testing is probabilistic (metric thresholds instead of pass/fail). (3) Continuous degradation: Models degrade over time due to data drift — requires continuous monitoring and retraining loops. (4) Versioning complexity: Must version code + data + model artifacts + training config. (5) Experimentation: Before deployment, extensive experimentation phase (CRISP-DM) that doesn't exist in traditional SDLC. Frameworks like CRISP-DM and MLOps practices bridge this gap.

•

Q6: Explain branching strategies. Which one do you prefer?

Git FlowGitHub FlowTrunk-Based

A: Git Flow: Feature branches → develop → release → main. Good for versioned releases but complex. GitHub Flow: Feature branches → main. Simple, always-deployable main branch. Trunk-Based: Everyone commits to main with feature flags. Fastest iteration but requires mature CI/CD. I prefer GitHub Flow for most teams — it balances simplicity with safety. For mature teams doing continuous deployment, trunk-based is ideal. Git Flow is best when you need parallel release maintenance (e.g., v1.x and v2.x simultaneously).

•

Q7: What is Definition of Done (DoD)?

A: DoD is a shared checklist that defines when a user story is truly "done" — not just "code complete." Typical DoD: (1) Code written and passes all linters, (2) Unit tests written with >80% coverage on new code, (3) Code reviewed and approved by at least one peer, (4) Integration tests passing, (5) Documentation updated, (6) No known defects, (7) Deployed to staging and smoke tested, (8) Acceptance criteria verified by PO. DoD prevents "90% done" stories that linger. It's agreed upon by the team and applied consistently.

•

Q8: How do you handle technical debt?

Make it visibleAllocate capacityPrioritize by impactPrevent accumulationCommunicate business impact

A: Technical debt is the implied cost of future rework caused by short-term shortcuts. Management strategy: (1) Make it visible: Track tech debt items in the backlog with clear impact descriptions. (2) Allocate capacity: Reserve 10-20% of each sprint for debt reduction. (3) Prioritize by impact: Fix debt that slows down current feature development first. (4) Prevent accumulation: Strong code reviews, DoD, and "Boy Scout Rule" (leave code cleaner than you found it). (5) Communicate business impact: Frame debt in terms stakeholders understand — "This refactoring will reduce bug-fix time from 3 days to 4 hours." Never ask "permission" to fix tech debt — it's part of professional engineering.

•

Q9: Explain the Testing Pyramid. Why is it shaped that way?

Unit testsIntegration testsE2E/UI tests

A: The pyramid has three layers — bottom to top: Unit tests (many, fast, cheap), Integration tests (moderate count, slower, test component interactions), E2E/UI tests (few, slowest, most expensive to maintain). It's shaped this way because: (1) Unit tests give fastest feedback — seconds to run, easy to debug failures. (2) Integration tests catch miscommunication between services. (3) E2E tests are fragile, slow, and expensive but catch user-facing issues. Anti-pattern: "Ice cream cone" — mostly manual/E2E tests, few unit tests. This leads to slow CI, flaky tests, and late bug detection. The goal is to catch 70-80% of bugs at the unit level.

•

Q10: What would you do if requirements change mid-sprint?

Minor changesMajor changesProcess fix

A: In Scrum: (1) Minor changes: Discuss with PO — can they fit within the Sprint Goal without jeopardizing committed work? If yes, swap in the new item and remove an equally-sized uncommitted item. (2) Major changes: If the Sprint Goal is invalidated, the PO can cancel the sprint (rare). Start a new sprint planning. (3) Process fix: If this happens frequently, it signals a problem — either the backlog isn't groomed properly, stakeholders aren't engaged in planning, or sprint length is too long. Discuss in retrospective. The Agile principle is "welcome changing requirements" — but within a structured change management process, not chaotic context-switching.

SDLC is not just a process — it's a mindset. The goal is to build software that works, is maintainable, and delivers value. The specific methodology matters less than the discipline of planning, iterating, testing, and reflecting. Choose the simplest process that gives your team enough structure without slowing them down.
