Running a model you rent: prompts and indexes as artefacts, eval gates, canarying a prompt, and the two SLIs MLOps never had

LLMOps — Operating an LLM System in Production

Scope: What changes when the model in production is one you rent instead of one you trained — the artefacts you version, the gate that replaces the accuracy check, the two SLIs MLOps never had, and the failure modes that only appear once real users are typing.

•

Overview

LLMOps is not a second discipline that replaces MLOps. It is the same lifecycle with the training step taken away and four new versioned artefacts put in its place.

That single sentence is worth memorising, because it is the honest framing and it is what an interviewer is listening for. Everything you already know about CI/CD, containers, canary releases, rollback, and monitoring carries over untouched. What is new is that the things which decide your output quality — the prompt, the retrieved context, the model version, and the token bill — were never artefacts before, so most teams do not version, test, or budget them at all.

The result is a specific and very common failure: a system that was excellent in a demo, drifts quietly for six weeks, and nobody can say what changed — because the thing that changed was a prompt someone edited in a dashboard.

Key Definitions (read first)

LLMOpsPrompt registryGolden setLLM-as-a-judgeEval gateTTFT / TPOT
Term Plain-language definition
LLMOps The practices for shipping and running systems built on a large language model you did not train: prompt and context management, evaluation, rollout, observability, and cost control.
Prompt registry A versioned store of prompts, treated like code — reviewed, diffed, tagged, and rolled back. The alternative is a string edited in a UI with no history.
Golden set A fixed, curated set of inputs with known-good outputs (or rubrics), run on every change. The LLM equivalent of a test suite.
LLM-as-a-judge Using a model to score another model's output against a rubric, because there is no single correct string to compare against.
Eval gate A CI step that blocks a release when scores on the golden set fall below a threshold. It replaces the accuracy check MLOps had.
TTFT / TPOT Time to first token — how long before the user sees anything. Time per output token — how fast the rest streams. Together they explain nearly all perceived latency.
Prompt caching Provider-side reuse of an unchanged prefix (system prompt, few-shot block, tool schemas) at a fraction of the input price.
Model pinning Naming an exact model version in config rather than a moving alias, so the provider cannot change your system's behaviour without you deploying.
Shadow traffic Sending a copy of live requests to a new prompt/model and scoring the output without returning it to users.
Trace / span One end-to-end request, and each step inside it (retrieve, rerank, generate, tool call). The unit of debugging in an LLM system.

1. The one-line definition, and what actually changes

code, data, model weightsPromptyouRetrieved context / indexModel version + paramsyou, in config

Classic MLOps has three artefacts: code, data, model weights. You own all three, and a deploy is reproducible when all three are pinned together.

In an LLM system you own a different set:

Artefact Who owns it in MLOps Who owns it in LLMOps Versioned by most teams?
Code you you yes
Training data you the provider n/a
Model weights you the provider no — you pin a version string
Prompt did not exist you usually not
Retrieved context / index did not exist you usually not
Model version + params implicit in the weights you, in config usually not
Token spend not a thing you, per request usually not

The risk moves outward. In MLOps the scary question is "did the data drift?". In LLMOps the scary question is "what changed?" — and if prompts and indexes are not versioned, there is no answer.

Rule of thumb: if changing it changes the output a user sees, it is a deployable. Prompts and indexes change the output. Therefore they are deployables, and everything you do for code applies to them.

2. MLOps vs LLMOps, side by side

TestUnit cost 
              MLOps                                LLMOps
              ─────                                ──────
  build       train a model on your data     →     pick a model, write a prompt
  test        accuracy / F1 on a holdout     →     rubric scores on a golden set
  artefact    code + data + weights          →     code + prompt + index + model pin
  deploy      ship the weights               →     ship a config (prompt + version)
  monitor     input drift, accuracy          →     input drift, quality, tokens, cost
  retrain     new data → new weights         →     new eval data → new prompt / RAG fix
  rollback    previous model file            →     previous prompt version
  unit cost   GPU hours (fixed-ish)          →     tokens (varies with the user)

Two rows deserve attention because they are where teams get hurt.

Test. There is no single correct output, so there is no accuracy. You replace it with a scored suite — and scores are noisy, which means you need to know your own noise floor before you can call a change a regression (see §5).

Unit cost. A GPU costs the same whether the request was easy or hard. A token bill does not. A user who pastes a 40-page PDF costs 30× a user who asks a one-line question, and nothing in your infrastructure stops them.

3. Prompts are artifacts, not strings

What "versioned" has to meanWhy a content hash rather than v3What to record on every request

The single highest-value practice in LLMOps, and the one most often missing.

What "versioned" has to mean:

  • the prompt lives in the repo (or a registry backed by one), not in a console
  • every change goes through review, with a diff a human can read
  • each version has an immutable id, and the id is recorded on every request that used it
  • rolling back is one config change, and it has been rehearsed

That last bullet is the one that pays for the other three. When quality drops on a Tuesday, the question is "which version were those bad answers generated by?" — and you can only answer it if the version id was written into the trace.

# prompt_registry.py — a prompt registry small enough to actually adopt.
# Prompts live in files; the hash is the version. Nothing to run, nothing to host.
import hashlib
import pathlib

PROMPTS = pathlib.Path(__file__).parent / "prompts"


class Prompt:
    def __init__(self, name: str, text: str):
        self.name = name
        self.text = text
        # short content hash: two identical prompts always get the same id, and any
        # edit — including a stray trailing space — gets a new one
        self.version = hashlib.sha256(text.encode("utf-8")).hexdigest()[:12]

    def render(self, **kw) -> str:
        return self.text.format(**kw)

    def __repr__(self):
        return "Prompt(%s@%s)" % (self.name, self.version)


def load(name: str) -> Prompt:
    return Prompt(name, (PROMPTS / (name + ".md")).read_text(encoding="utf-8"))


# usage: the version id travels with the request, into the trace and the log line
p = load("support_answer")
messages = [{"role": "system", "content": p.render(tone="concise")}]
log_fields = {"prompt_name": p.name, "prompt_version": p.version}

Why a content hash rather than v3: hand-maintained numbers drift from reality the first time somebody edits without bumping. A hash cannot lie about whether the text changed.

What to record on every request: prompt name and version, model id, temperature and the other sampling params, the retrieval config (index version, k, reranker), and the token counts. Those seven fields answer almost every "what changed?" question you will be asked.

4. The context layer — your index is a deployable

fullThe operational rules that followVersion the indexNever re-embed in placeTrack freshness as an SLIWarning

For a RAG system, the retrieved context decides the answer at least as much as the prompt does. Which means every one of these is a release:

Change Why it is a release, not a chore
Re-chunking (size or overlap) every neighbourhood shifts; answers change wholesale
Swapping the embedding model old and new vectors are not comparable — a full re-index, not an update
Changing k or adding a reranker different evidence reaches the model
A bulk document import new content can outrank the pages that used to win
Deleting stale documents fixes staleness, and silently removes answers people relied on

The operational rules that follow:

  • Version the index the way you version a model: docs-2026-08-14-e5large-c512-o64 tells you the corpus date, the embedding model, the chunk size and the overlap.
  • Never re-embed in place. Build the new index alongside, evaluate against it, then switch the pointer. This is a blue/green deploy, and it gives you a rollback.
  • Track freshness as an SLI. "P95 document age" catches the pipeline that quietly stopped ingesting three weeks ago — the most common RAG incident there is, and invisible to every application metric.
  • Evaluate retrieval separately from generation. If recall@k is 0.55, no prompt engineering will save the answer, and time spent on the prompt is wasted.

Warning: the failure mode here is silent by construction. A broken ingestion pipeline does not raise errors — it serves confident answers from a stale corpus, and nobody notices until a customer quotes last quarter's price back at you.

See RAG and Vector Stores for the retrieval mechanics themselves.

5. Evaluation — the gate that replaces the accuracy check

AssertionsGolden set + judgeHuman reviewBuilding the golden set2 pp1.15 SE

You cannot compute accuracy on free text, so you build a suite and gate on it. Three layers, cheapest first:

Layer What it catches Cost Run it
Assertions schema violations, missing citations, banned phrases, length ~free every request, and in CI
Golden set + judge quality and faithfulness regressions cents per run every pull request
Human review the things a judge is wrong about expensive weekly sample, and before a big release

Building the golden set: take real traces, not invented questions. 150–300 items is enough to be useful; stratify by intent so a regression in one intent cannot hide inside an average. Every production incident adds an item — that is how the suite earns its keep over time.

Knowing your noise floor before you call something a regression. This is the step almost everyone skips.

With a golden set of n = 300 and a pass rate around p = 0.90, the standard error on that rate is:

SE = sqrt(p(1-p)/n) = sqrt(0.90 × 0.10 / 300) = sqrt(0.0003) = 0.0173  →  ±1.7 pp

So:

  • a 2 pp drop (0.90 → 0.88) is 1.15 SE — noise. Do not block a release on it.
  • a 4 pp drop (0.90 → 0.86) is 2.31 SE — real. Block it.

Set the gate threshold from that arithmetic, not from a feeling. A gate tuned tighter than your noise floor fails randomly, and a gate everyone learns to override is not a gate.

# eval_gate.py — the CI step. Exits non-zero, which is the whole point.
import json
import statistics
import sys

BASELINE = 0.90          # last released score on the golden set
MIN_DELTA = 0.03         # ~1.7 SE at n=300: below this, it is noise


def gate(results_path: str) -> int:
    rows = [json.loads(l) for l in open(results_path, encoding="utf-8")]
    score = statistics.fmean(r["passed"] for r in rows)
    n = len(rows)
    se = (score * (1 - score) / n) ** 0.5
    print("golden set n=%d  score=%.3f  SE=%.3f  baseline=%.3f" % (n, score, se, BASELINE))

    # a per-intent floor as well as an overall one: an average hides a slice that broke
    by_intent = {}
    for r in rows:
        by_intent.setdefault(r["intent"], []).append(r["passed"])
    for intent, vals in sorted(by_intent.items()):
        s = statistics.fmean(vals)
        flag = "  <-- REGRESSED" if s < BASELINE - 2 * MIN_DELTA else ""
        print("   %-22s %.3f  (n=%d)%s" % (intent, s, len(vals), flag))

    if score < BASELINE - MIN_DELTA:
        print("FAIL: %.3f is more than %.0f pp below baseline" % (score, MIN_DELTA * 100))
        return 1
    print("PASS")
    return 0


if __name__ == "__main__":
    sys.exit(gate(sys.argv[1]))

The judge needs evaluating too. Sample 50 items, have a human label them, and measure agreement with the judge. Below ~80% agreement the judge is measuring its own preferences and your gate is theatre. Details in LLM Metrics and LLM as Judge.

6. Rollout — canary a prompt the way you canary a model

The ordering that worksOfflineShadowCanaryRamp

Everything you know about progressive delivery applies, with the prompt version as the thing being rolled out.

   1% ──► 10% ──► 50% ──► 100%
    │       │       │
    └───────┴───────┴──► automatic rollback on: quality score, error rate,
                          p95 latency, or cost per request breaching its budget

The ordering that works:

  1. Offlinegolden set in CI. Blocks the merge.
  2. Shadowreal traffic, scored, output discarded. Catches the inputs your golden set never imagined, at no user risk.
  3. Canary1% of users, with automatic rollback wired to all four signals above.
  4. Ramp10%, 50%, 100%, holding long enough at each step to see the metric move.

What is different from a model rollout: the change is instant and cheap, which makes it tempting to skip the ladder. Resist that — cheap to deploy is not the same as cheap to get wrong, and a prompt change can alter behaviour far more sharply than a retrained model ever does.

# canary.py — deterministic assignment, so one user does not flip between
# versions mid-conversation and see the personality change
import hashlib

def variant(user_id: str, canary_pct: int) -> str:
    bucket = int(hashlib.sha256(user_id.encode()).hexdigest()[:8], 16) % 100
    return "canary" if bucket < canary_pct else "stable"

Hashing the user id (not the request) is the detail that matters: a per-request coin flip gives a user two different assistants in the same session.

7. Observability — traces, spans, and token accounting

traceWhat every span should carryThe four metrics worth alerting onQualityCost per requestRefusal / fallback rate

The unit of debugging is the trace: one user request, with a span for every step — retrieve, rerank, build prompt, generate, tool call, retry.

Aggregate dashboards cannot debug an LLM system, because the failure is almost always in one request's context, not in the average. What you need is the ability to open the specific bad answer and see exactly what the model was shown.

What every span should carry:

Field Why
prompt name + version "what changed?"
model id + sampling params provider-side change detection
index version, k, retrieved doc ids was the evidence even there?
input / output token counts cost attribution, and the drift of length
latency split (TTFT, total) where the time went
judge score, when sampled quality trend over time
user or session id (hashed) complaint → trace, in one lookup

The four metrics worth alerting on:

  1. Qualityrolling judge score on a sampled slice of production traffic
  2. Cost per requestthe token bill divided by requests, watched like latency
  3. Refusal / fallback ratea spike means an upstream change, a guardrail misfiring, or an attack
  4. Retrieval recall proxyshare of answers where no retrieved document was cited

The deeper treatment, including a worked incident, is in LLM Observability and Tracing.

8. Cost — the SLI that MLOps never had

first-class reliability signalThe formulaWorked exampleCost per request$0.0075Per day

Cost per request is a first-class reliability signal, because it moves with what users type, and it can double overnight without a single deploy.

The formula: 

cost_per_request = (T_in × P_in + T_out × P_out) / 1,000,000
daily_cost       = requests_per_day × cost_per_request

Worked example. 200,000 requests/day, averaging 1,400 input and 220 output tokens, at $3.00 / 1M input and $15.00 / 1M output:

Term Calculation Result
Input per request 1,400 × 3.00 / 1e6 $0.0042
Output per request 220 × 15.00 / 1e6 $0.0033
Cost per request sum $0.0075
Input per day 200,000 × $0.0042 $840
Output per day 200,000 × $0.0033 $660
Per day $1,500
Per 30 days $45,000

Note what the split tells you: output is only 14% of the tokens but 44% of the bill, because output tokens cost 5× input. Shortening answers is a cost lever, not just a latency one.

Now cache the prefix. Suppose 900 of those 1,400 input tokens are a fixed system prompt, few-shot block and tool schemas — identical on every request — and cached reads bill at 10% of the input price ($0.30 / 1M):

Term Calculation Result
Cached prefix 900 × 0.30 / 1e6 $0.00027
Fresh input 500 × 3.00 / 1e6 $0.00150
Output 220 × 15.00 / 1e6 $0.00330
Cost per request sum $0.00507
Per day 200,000 × $0.00507 $1,014
Saved $1,500 − $1,014 $486/day = $14,580/month (−32%)

One structural change — putting the static part of the prompt first so it can be cached — took a third off the bill and changed nothing a user sees.

The levers, in the order worth trying:

Lever Typical saving Cost to you
Cache the static prefix 20–40% reorder the prompt; free
Shorten the output (max_tokens, "be concise") 10–30% may lose detail
Route easy requests to a small model 30–70% a router, and its own eval
Semantic cache on repeated questions 10–30% staleness risk; needs invalidation
Trim retrieved context (better reranking) 10–25% recall risk if k goes too low

Tip: put a hard budget per request and per tenant in the code, not in a spreadsheet. Truncate or reject beyond it. Without one, a single user pasting a book is an incident.

9. Latency — TTFT, TPOT, and the biggest lever

Worked example5,298 ms (5.3 s)3,098 ms (3.1 s)2,200 ms — 41% of the wall clockGeneration65%

Generation is sequential, so end-to-end latency is:

total ≈ TTFT + (output_tokens − 1) × TPOT

Worked example. TTFT = 480 ms, TPOT = 22 ms/token:

Output length Calculation Total Perceived (streaming)
220 tokens 480 + 219 × 22 5,298 ms (5.3 s) 480 ms
120 tokens 480 + 119 × 22 3,098 ms (3.1 s) 480 ms

Cutting the answer from 220 to 120 tokens removes 2,200 ms — 41% of the wall clock. No infrastructure change comes close to that, which is why "make the answer shorter" is the first latency lever, not the last.

And streaming changes the question entirely. With streaming, the user waits 480 ms, not 5.3 s. Optimising TTFT (cache the prefix, retrieve in parallel, keep the system prompt short) improves the experience far more than shaving TPOT does.

Where the time goes in a RAG request — measure it, because the intuition is usually wrong:

Stage Typical share First thing to try
Embedding the query 5% cache repeated queries
Vector search 10% tune ef_search / index params
Reranking 15% rerank fewer candidates
Generation 65% shorten output, stream, smaller model
Post-processing 5% usually not worth touching

10. Reliability — the model is a dependency you do not control

Pin the versionA degraded mode that is honest

A hosted model is a third-party dependency with an availability number worse than your database, rate limits you can hit without warning, and a version that can be deprecated on the provider's schedule.

The four things to have in place before you need them:

  1. Pin the version. Use the dated model id, never a moving alias. An alias means the provider can change your behaviour without your deploy, and your evals will not have seen it.
  2. A fallback model, already evaluated. Not "we'll switch if it breaks" — a second provider or a smaller model that has been run against the golden set, so you know what you are degrading to.
  3. Timeouts, retries with jitter, and a circuit breaker. Retrying a rate-limited provider without backoff turns their bad minute into your bad hour.
  4. A degraded mode that is honest. Cached answer, retrieval-only extract, or a plain "I can't answer right now" — all three beat a confident hallucination produced by a fallback nobody tested.
# resilient_call.py — timeout, jittered backoff, and a fallback that was evaluated
import random
import time

def call_with_fallback(client, fallback, messages, attempts=3, timeout=20.0):
    for i in range(attempts):
        try:
            return client.generate(messages, timeout=timeout)
        except RateLimited:
            # full jitter: without it, every retry in the fleet fires together
            time.sleep(random.uniform(0, min(8.0, 2 ** i)))
        except (Timeout, ProviderError):
            break
    return fallback.generate(messages, timeout=timeout)   # scored on the golden set too

Deprecation is a scheduled outage you are told about in advance and still miss. Keep a register of every model id in use with its retirement date, and re-run the eval suite against the successor before the deadline, not after. See Model Deprecation and Migration.

11. Guardrails in the pipeline

InputRetrievalOutputPost-hoc

Guardrails are not a moderation setting — they are pipeline stages, with latency and failure modes of their own.

Stage Checks On failure
Input prompt injection, PII, off-topic, size limit reject or strip, and log
Retrieval permission filter applied per user fail closed — never widen
Output schema, citations present, banned content, leaked secrets repair once, then refuse
Post-hoc sampled judge scoring feeds the quality metric

The two operational facts people miss:

  • Every guardrail is latency and cost. A moderation call before and after generation can add 200–400 ms and a second bill. Run cheap deterministic checks (regex, schema, length) before expensive model-based ones, and run independent checks in parallel.
  • Fail closed on the permission filter. An input guardrail that errors open leaks. Of all the stages, retrieval permissions are the one where an exception must mean "return nothing", not "return everything".

12. The feedback loop — traces become eval sets become training data

How the loop is actually runKey ideaprompt → retrieval → fine-tune

This is the arrow that turns a launch into a lifecycle, and it is the one most teams never close.

production traces
       │
       ├──► sampled + judged ────► the quality metric you alert on
       │
       ├──► thumbs-down + escalations ──► new golden-set items ──► the eval gate
       │
       └──► accepted answers, curated ──► few-shot examples ──► fine-tuning set

How the loop is actually run:

  • Sample production traffic continuously (1–5% is plenty) and score it. That sample is your quality metric.
  • Every complaint and every incident becomes a golden-set item the same week. This is what stops the same regression shipping twice.
  • Only after prompt and retrieval work has plateaued does fine-tuning become the right answer — and then the training set comes from these curated traces, which is why collecting them properly from day one matters.

Key idea: the order is prompt → retrieval → fine-tune, and the reason is operational, not technical. The first two are a config change with a one-minute rollback. The third is a build, a version, and a new artefact to maintain forever.

15. Interview deep dive

How do you control cost?When would you fine-tune?

What is LLMOps, and how is it different from MLOps?

MLOps is DevOps plus two things that drift: data and the model. LLMOps is MLOps with the training loop removed and four new versioned artefacts put in its place — the prompt, the retrieval index, the model version you pinned, and the token budget. CI/CD, containers, canary and monitoring all carry over unchanged. What is new is that the things deciding output quality were never artefacts before, so most teams do not version, test or budget them.

How do you test something with no correct answer?

Three layers. Cheap deterministic assertions (schema, citations present, length, banned phrases) on every request. A golden set of 150–300 real traced inputs scored by rubric or judge on every pull request, gating the merge. Human review weekly and before big releases. And I calibrate the gate against the noise floor: at n=300 and p=0.90 the standard error is 1.7 points, so a 2-point drop is noise and a 4-point drop is 2.3 SE and worth blocking on.

Quality dropped last week and nobody deployed. How do you investigate?

I would look at the seven fields I record on every request. If model id is a moving alias, the provider probably changed it — that is the most common cause of a change with no deploy. If prompt version differs across the bad window, somebody edited outside the pipeline. If index version changed, an ingestion job ran. If none changed, I compare input distributions — usually the users changed, not the system. Not being able to run that check is itself the finding, and the fix is putting those fields into the traces.

How do you control cost?

Treat cost per request as an SLI with a budget. Then the levers in order of return: cache the static prefix, which on a typical 1,400-token prompt with a 900-token fixed prefix took a $1,500/day bill to $1,014 — a third, for a prompt reordering. Cap and shorten outputs, since output tokens cost five times input and dominate the bill at only 14% of the volume. Route easy requests to a smaller model, with its own eval. Then semantic caching and context trimming. And a hard per-request and per-tenant budget in code, because one user pasting a book is otherwise an incident.

A prompt change is one line. Why not just ship it?

Because cheap to deploy is not cheap to get wrong. A prompt change can shift behaviour more sharply than a retrained model, and it reaches 100% of users instantly. It goes through the same ladder as any other artefact: eval gate in CI, shadow traffic, 1% canary with automatic rollback on quality, errors, latency and cost, then ramp.

When would you fine-tune?

Only after prompt and retrieval work has plateaued. Fine-tuning is good at form — tone, format, a house style — and bad at facts, which belong in retrieval. Operationally it is also the expensive choice: prompt and retrieval changes are config with a one-minute rollback, while a fine-tune is a build, a version and an artefact to maintain across every future base-model migration.

What would you put in place first on a team with none of this?

Tracing with the seven fields, then the prompt registry. Everything else — evals, budgets, canaries — depends on being able to answer "what changed?", and neither costs much to add.
