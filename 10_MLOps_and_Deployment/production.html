Production Issue #1: Model Drift & Degradation

Scope: Model Drift & Degradation — detection, diagnosis, resolution strategies, and production patterns.

•

Overview

One-sentence ideaquietlymonitoringtestingafter

One-sentence idea: A model learns patterns from yesterday's data. When the world changes, those patterns stop matching reality — and the model gets quietly worse while still happily returning confident predictions.

The dangerous word is quietly. Model drift doesn't crash the service or throw an error. The model keeps returning answers that are increasingly wrong. That is exactly why drift needs monitoring (watching live data) and not just testing (checking once before launch).

Why drift is a production problem, not a training problem: Offline, your test set is drawn from the same distribution as your training set — so accuracy looks great forever. Drift only lives in the gap between when you trained and now, and that gap only opens up after deployment.

•

Running Example: A Loan-Approval Model 🏦

2023approvereject94% accuracy

We'll use one example through the whole doc so the drift types aren't abstract.

You train a model in 2023 to predict "will this person repay a loan?". It learns rules like: - Income ~$60k, stable job, debt-to-income < 30% → approve - Low income + high existing debt → reject

It scores 94% accuracy, you ship it, and then the world starts moving. The sections below show each drift type happening to this same model.

•

Types of Drift

Mental modelData driftConcept driftLabel driftFeature driftWhat

Mental model: every drift type is "something in the joint distribution P(X, Y) changed." Which piece changed tells you what to fix.

TypeWhat changedAnalogy
Data driftP(X) — the inputsSame exam, different students
Concept driftP(Y\|X) — the ruleSame students, the answer key changed
Label driftP(Y) — the target mixMore of one answer than before
Feature driftthe pipelineSomeone swapped the exam's units

1. Data Drift (Covariate Shift) — P(X) changes

  • WhatInput feature distributions change; the input→output rule still holds.
  • Loan exampleA recession hits. The kind of people applying shifts — avg income drops $60k → $42k, avg debt-to-income rises 28% → 45%. "Low debt → repays" is still true, but the model has barely seen 2024's applicants, so it's extrapolating into unfamiliar territory. Same exam, different students.
  • Other exampleE-commerce model trained on pre-COVID shopping data sees entirely different patterns post-COVID.
  • DetectionKS test, PSI (Population Stability Index), KL divergence on feature distributions

2. Concept Drift — P(Y|X) changes

  • WhatThe relationship between inputs and outputs changes. This is the nastiest type, because the inputs can look completely normal — only the outcomes reveal it.
  • Loan exampleA loan-forgiveness program passes. People who look risky (high debt) now do repay, because their debt got wiped. Inputs are unchanged, but the meaning flipped:
2023:  high debt  →  likely default
2024:  high debt  →  likely repays   ← the relationship inverted
  • Other exampleFraud patterns evolve — behavior that was legitimate yesterday is fraudulent today.
  • DetectionMonitor prediction accuracy vs. delayed ground truth (the catch: ground truth arrives late — you may not know a 5-year loan defaulted for years).

3. Label Drift (Prior Probability Shift) — P(Y) changes

  • WhatDistribution of the target variable changes (more "approves" than "rejects" than before), even if each input→output rule is stable.
  • Loan exampleAfter the recession the true repayment rate drops from 85% → 60%. A model calibrated to an 85% base rate now over-approves.
  • Other exampleDisease prevalence changes seasonally, affecting a diagnostic model.
  • DetectionTrack prediction distribution over time

4. Feature Drift — the pipeline changes

  • WhatUpstream data pipeline changes alter feature values. This isn't the world changing — it's your plumbing changing, which is why it causes sudden catastrophic drops rather than a slow bleed.
  • Loan exampleA vendor API changes annual_income from dollars (60000) to thousands (60). The model now sees everyone earning $60/year and rejects the entire planet overnight.
  • Other exampleA partner API changes units from meters to feet.
  • DetectionSchema validation, range checks, Great Expectations

Detection Methods

bucket-by-bucketwayinputs alone

1. Population Stability Index (PSI)

import numpy as np

def calculate_psi(expected, actual, bins=10):
    """
    PSI < 0.1  → No significant shift
    PSI 0.1-0.25 → Moderate shift (investigate)
    PSI > 0.25 → Major shift (retrain)
    """
    expected_perc = np.histogram(expected, bins=bins)[0] / len(expected)
    actual_perc = np.histogram(actual, bins=bins)[0] / len(actual)
    
    # Avoid division by zero
    expected_perc = np.clip(expected_perc, 1e-4, None)
    actual_perc = np.clip(actual_perc, 1e-4, None)
    
    psi = np.sum((actual_perc - expected_perc) * np.log(actual_perc / expected_perc))
    return psi

# Usage
training_scores = np.random.normal(0.7, 0.1, 10000)
production_scores = np.random.normal(0.65, 0.15, 10000)  # shifted
print(f"PSI: {calculate_psi(training_scores, production_scores):.4f}")

PSI worked by hand (so the formula isn't a black box)

PSI compares two distributions bucket-by-bucket. Bin our loan applicants' debt-to-income into 3 buckets and compare training vs. production proportions:

BucketTraining % (E)Production % (A)
Low (<30%)0.600.30
Mid (30–40%)0.300.30
High (>40%)0.100.40

Per-bucket term is (A − E) × ln(A / E), then sum:

Low :  (0.30 − 0.60) × ln(0.30/0.60) = (−0.30) × ln(0.5) = (−0.30)(−0.693) = 0.208
Mid :  (0.30 − 0.30) × ln(0.30/0.30) = ( 0.00) × ln(1.0) = ( 0.00)( 0.000) = 0.000
High:  (0.40 − 0.10) × ln(0.40/0.10) = ( 0.30) × ln(4.0) = ( 0.30)( 1.386) = 0.416
                                                                    ──────────────
                                                              PSI = 0.624

0.624 is way past the 0.25 retrain threshold → the applicant population has shifted hard toward high-debt borrowers. The alarm fires on the inputs alone, before accuracy tanks — which is the whole point: PSI catches drift without waiting for slow ground-truth labels.

Alerting Pipeline

def monitor_model(model_name, predictions, features, reference_data):
    alerts = []
    
    # 1. Check prediction distribution
    psi = calculate_psi(reference_data["predictions"], predictions)
    if psi > 0.25:
        alerts.append({"severity": "CRITICAL", "type": "prediction_drift", "psi": psi})
    elif psi > 0.1:
        alerts.append({"severity": "WARNING", "type": "prediction_drift", "psi": psi})
    
    # 2. Check feature distributions
    for col in features.columns:
        feat_psi = calculate_psi(reference_data[col], features[col])
        if feat_psi > 0.25:
            alerts.append({"severity": "HIGH", "type": "feature_drift", "feature": col, "psi": feat_psi})
    
    # 3. Check for nulls
    null_rates = features.isnull().mean()
    high_null = null_rates[null_rates > 0.05]
    for col, rate in high_null.items():
        alerts.append({"severity": "HIGH", "type": "missing_data", "feature": col, "rate": rate})
    
    return alerts

def weighted_ensemble(old_model, new_model, recency_weight=0.7):
    def predict(X):
        old_pred = old_model.predict(X)
        new_pred = new_model.predict(X)
        return recency_weight * new_pred + (1 - recency_weight) * old_pred
    return predict

Production Issue #2: Latency & Performance Bottlenecks

Scope: Latency & Performance Bottlenecks — detection, diagnosis, resolution strategies, and production patterns.

•

Overview

ML models that work perfectly in notebooks often fail performance requirements in production. Latency spikes, high memory usage, and throughput limitations can make a model unusable.

•

Key Definitions (read first)

LatencyoneThroughputper secondP50 / P95 / P99P99 = 200 ms
TermPlain-language definition
LatencyTime to serve one request, end to end (e.g. 45 ms). "How long does the user wait?"
ThroughputHow many requests you serve per second (QPS/RPS). "How many users at once?"
P50 / P95 / P99Percentiles of latency. P99 = 200 ms means 99% of requests finish under 200 ms and the slowest 1% are worse. Averages hide the slow tail; percentiles expose it.
Tail latencyThe slow end (P99/P99.9). A few slow requests that hurt the worst-case experience even when the average looks fine.
Cold startThe first request after a deploy/scale-up is slow because the model still has to be loaded into memory. Later requests are fast (model already resident).
Memory leakMemory that is allocated but never released, so usage climbs forever. In Python it's usually an unbounded collection or global that keeps growing (not the garbage collector failing). It ends in an OOM kill.
OOM (Out Of Memory)The process asked for more RAM/VRAM than allowed, so the OS/Kubernetes kills it → restart → downtime.
QuantizationStoring model weights in lower precision (FP32 → INT8) to shrink size and speed up inference, trading a little accuracy.
DistillationTraining a small "student" model to imitate a large "teacher" — most of the quality at a fraction of the cost.
BatchingGrouping several requests so the GPU processes them in one pass — higher throughput, slightly higher latency per request.
GC pauseA "stop-the-world" moment when the garbage collector reclaims memory; a common cause of sudden P99 spikes.

3. Memory Leaks

Definition: A memory leak is memory your program holds onto but never frees, so RAM usage rises steadily until the process is OOM-killed. The tell-tale sign is a sawtooth that never resets: memory climbs with traffic and doesn't fall when traffic drops. In Python the cause is almost always logical — an ever-growing list/dict/cache or global state — not the garbage collector failing. A restart "fixes" it temporarily, which is the classic symptom.

# BAD: Memory leak — accumulating data in global state
predictions_history = []  # Grows forever!

def predict(data):
    result = model.predict(data)
    predictions_history.append(result)  # ← LEAK
    return result

# GOOD: Use bounded collection
from collections import deque
predictions_history = deque(maxlen=10000)

3. Model Distillation

# Train a smaller "student" model to mimic a larger "teacher"
def distillation_loss(student_logits, teacher_logits, labels, temperature=4.0, alpha=0.7):
    soft_loss = F.kl_div(
        F.log_softmax(student_logits / temperature, dim=1),
        F.softmax(teacher_logits / temperature, dim=1),
        reduction="batchmean"
    ) * temperature ** 2
    hard_loss = F.cross_entropy(student_logits, labels)
    return alpha * soft_loss + (1 - alpha) * hard_loss

4. Caching

import hashlib
from functools import lru_cache
import redis

# In-memory caching
@lru_cache(maxsize=10000)
def predict_cached(features_tuple):
    return model.predict([list(features_tuple)])[0]

# Redis caching for distributed
redis_client = redis.Redis(host="redis", port=6379)

def predict_with_cache(features, ttl=3600):
    cache_key = hashlib.md5(str(features).encode()).hexdigest()
    cached = redis_client.get(cache_key)
    if cached:
        return float(cached)
    result = model.predict([features])[0]
    redis_client.setex(cache_key, ttl, str(result))
    return result

5. Batching

import asyncio
from collections import deque

class DynamicBatcher:
    def __init__(self, model, max_batch=32, max_wait_ms=50):
        self.model = model
        self.max_batch = max_batch
        self.max_wait = max_wait_ms / 1000
        self.queue = deque()
    
    async def predict(self, features):
        future = asyncio.Future()
        self.queue.append((features, future))
        
        if len(self.queue) >= self.max_batch:
            await self._process_batch()
        else:
            await asyncio.sleep(self.max_wait)
            if self.queue:
                await self._process_batch()
        
        return await future
    
    async def _process_batch(self):
        batch = []
        futures = []
        while self.queue and len(batch) < self.max_batch:
            features, future = self.queue.popleft()
            batch.append(features)
            futures.append(future)
        
        results = self.model.predict(batch)
        for future, result in zip(futures, results):
            future.set_result(result)

Production Issue #3: Training-Serving Skew

Scope: Training-Serving Skew — detection, diagnosis, resolution strategies, and production patterns.

•

Overview

Training-serving skew occurs when the model behaves differently in production than during training, even though the model artifact is identical. The difference comes from inconsistencies in data processing, feature engineering, or environment.

•

Key Definitions (read first)

Training-serving skewone way during trainingdifferent way during servingFeatureFeature leakage (target leakage)future
TermPlain-language definition
Training-serving skewThe model sees data prepared one way during training and a different way during serving, so it silently underperforms in production — even though the model file is byte-identical. The bug is in the preprocessing, not the model.
FeatureA single input signal the model uses (e.g. age_normalized). "Feature engineering" is the code that computes it from raw data.
Feature leakage (target leakage)A feature accidentally contains information from the future or from the label itself. It inflates offline accuracy but isn't available at serving time → the model collapses in production.
Feature storeA central service that computes and serves features the same way for training (offline/batch) and serving (online/low-latency) — the main cure for skew.
Point-in-time correctnessWhen building training data, joining each label with the feature values as they were at that moment — not today's values. Prevents leakage.
Golden testA fixed set of known inputs → known expected outputs, run on every deploy to catch silent behavior changes.
Environment pinningLocking exact library/CUDA versions (via requirements.txt + Docker) so training and serving compute identically.
•

# Split large model across multiple GPUs
import torch

def shard_model(model, num_gpus):
    """Simple pipeline parallelism."""
    layers = list(model.children())
    layers_per_gpu = len(layers) // num_gpus
    
    shards = []
    for i in range(num_gpus):
        start = i * layers_per_gpu
        end = start + layers_per_gpu if i < num_gpus - 1 else len(layers)
        shard = torch.nn.Sequential(*layers[start:end]).to(f"cuda:{i}")
        shards.append(shard)
    
    def forward(x):
        for i, shard in enumerate(shards):
            x = x.to(f"cuda:{i}")
            x = shard(x)
        return x
    
    return forward

class CanaryDeployment:
    def __init__(self, old_model, new_model, canary_pct=5):
        self.old_model = old_model
        self.new_model = new_model
        self.canary_pct = canary_pct
        self.metrics = {"old": [], "new": []}
    
    def predict(self, features, request_id):
        use_canary = hash(request_id) % 100 < self.canary_pct
        
        if use_canary:
            result = self.new_model.predict(features)
            self.metrics["new"].append(result)
        else:
            result = self.old_model.predict(features)
            self.metrics["old"].append(result)
        
        return result
    
    def evaluate_canary(self):
        """Check if canary is safe to promote."""
        if len(self.metrics["new"]) < 100:
            return "INSUFFICIENT_DATA"
        
        # Compare error rates, latency, etc.
        old_error_rate = self.calculate_error_rate(self.metrics["old"])
        new_error_rate = self.calculate_error_rate(self.metrics["new"])
        
        if new_error_rate > old_error_rate * 1.1:  # 10% worse
            return "ROLLBACK"
        return "PROMOTE"

def rollback_model(model_name, target_version=None):

    def __init__(self, base_path, model_name):
        self.base_path = Path(base_path) / model_name
        self.base_path.mkdir(parents=True, exist_ok=True)

        if version is None:
            version = self.get_next_version()
        
        version_path = self.base_path / f"v{version}"
        version_path.mkdir(exist_ok=True)
        
        # Save model
        with open(version_path / "model.pkl", "wb") as f:
            pickle.dump(model, f)
        
        # Save metadata
        metadata.update({
            "version": version,
            "saved_at": datetime.now().isoformat(),
            "model_type": type(model).__name__,
        })
        with open(version_path / "metadata.json", "w") as f:
            json.dump(metadata, f, indent=2)
        
        # Save feature config
        if hasattr(model, "feature_names_in_"):
            with open(version_path / "features.json", "w") as f:
                json.dump(list(model.feature_names_in_), f)
        
        # Create "latest" symlink
        latest_path = self.base_path / "latest"
        if latest_path.exists():
            latest_path.unlink()
        latest_path.symlink_to(version_path)
        
        return version_path
    
    def load_artifacts(self, version="latest"):
        version_path = self.base_path / (f"v{version}" if version != "latest" else "latest")
        
        with open(version_path / "model.pkl", "rb") as f:
            model = pickle.load(f)
        with open(version_path / "metadata.json", "r") as f:
            metadata = json.load(f)
        
        return model, metadata
    
    def get_next_version(self):
        existing = [
            int(p.name[1:]) for p in self.base_path.iterdir()
            if p.is_dir() and p.name.startswith("v") and p.name[1:].isdigit()

from scipy import stats
import numpy as np
from collections import defaultdict

class DataMonitor:
    """Monitor input data distributions in production."""
    
    def __init__(self, reference_data):
        self.reference_stats = self.compute_stats(reference_data)
        self.alerts = []
    
    def compute_stats(self, data):
        stats_dict = {}
        for col in data.columns:
            if data[col].dtype in ['float64', 'int64']:
                stats_dict[col] = {
                    "mean": data[col].mean(),
                    "std": data[col].std(),
                    "min": data[col].min(),
                    "max": data[col].max(),
                    "median": data[col].median(),
                    "q25": data[col].quantile(0.25),
                    "q75": data[col].quantile(0.75),
                    "null_pct": data[col].isnull().mean(),
                    "distribution": np.histogram(data[col].dropna(), bins=50),
                }
            else:
                stats_dict[col] = {
                    "unique_count": data[col].nunique(),
                    "top_values": data[col].value_counts().head(20).to_dict(),
                    "null_pct": data[col].isnull().mean(),
                }
        return stats_dict
    
    def check_batch(self, new_data, alert_threshold=0.05):
        """Check a batch of new data against reference."""
        results = {}
        
        for col in new_data.columns:
            if col not in self.reference_stats:
                self.alerts.append(f"NEW_COLUMN: {col} not in reference")
                continue
            
            ref = self.reference_stats[col]
            
            if new_data[col].dtype in ['float64', 'int64']:
                # KS test for distribution shift
                ks_stat, p_value = stats.ks_2samp(
                    new_data[col].dropna().values[:5000],
                    np.random.choice(
                        ref["distribution"][1][:-1],
                        size=5000,
                        p=ref["distribution"][0] / ref["distribution"][0].sum()
                    )
                )
                
                # Null rate change
                null_change = abs(new_data[col].isnull().mean() - ref["null_pct"])
                
                results[col] = {
                    "ks_statistic": ks_stat,
                    "p_value": p_value,
                    "drift_detected": p_value < alert_threshold,
                    "null_rate_change": null_change,
                    "current_mean": new_data[col].mean(),
                    "reference_mean": ref["mean"],
                }
                
                if p_value < alert_threshold:
                    self.alerts.append(
                        f"DRIFT: {col} distribution shifted (p={p_value:.4f})"
                    )
        
        return results

class DelayedMetricsTracker:
    """Track metrics when ground truth arrives with delay."""
    
    def __init__(self, window_size=10000):
        self.predictions = {}  # request_id -> prediction
        self.window_size = window_size
        self.metrics_history = []
    
    def log_prediction(self, request_id, prediction, timestamp):
        self.predictions[request_id] = {
            "prediction": prediction,
            "timestamp": timestamp,
        }
        # Evict old entries
        if len(self.predictions) > self.window_size * 2:
            self.cleanup()
    
    def log_ground_truth(self, request_id, actual):
        if request_id not in self.predictions:
            return  # Prediction already evicted
        
        pred_info = self.predictions.pop(request_id)
        
        self.metrics_history.append({
            "prediction": pred_info["prediction"],
            "actual": actual,
            "delay_seconds": (
                datetime.now() - pred_info["timestamp"]
            ).total_seconds(),
        })
    
    def compute_metrics(self, last_n=1000):
        recent = self.metrics_history[-last_n:]
        if not recent:
            return {}
        
        preds = [r["prediction"] for r in recent]
        actuals = [r["actual"] for r in recent]
        
        return {
            "accuracy": sum(p == a for p, a in zip(preds, actuals)) / len(preds),
            "sample_size": len(preds),
            "avg_delay_hours": np.mean([r["delay_seconds"] for r in recent]) / 3600,
        }

class SmartAlerter:
    """Prevent alert fatigue with intelligent grouping and suppression."""
    
    def __init__(self, cooldown_seconds=3600):
        self.cooldown = cooldown_seconds
        self.last_fired = {}
        self.alert_counts = defaultdict(int)
    
    def should_alert(self, alert_name, severity="warning"):
        now = time.time()
        
        # Check cooldown
        if alert_name in self.last_fired:
            elapsed = now - self.last_fired[alert_name]
            if elapsed < self.cooldown:
                self.alert_counts[alert_name] += 1
                return False
        
        # Fire alert
        self.last_fired[alert_name] = now
        suppressed = self.alert_counts.get(alert_name, 0)
        self.alert_counts[alert_name] = 0
        
        return {
            "fire": True,
            "suppressed_count": suppressed,
            "message": f"{alert_name} ({suppressed} similar suppressed)",
        }
    
    def get_summary(self):
        """Get overview of all alert states."""
        return {
            name: {
                "last_fired": self.last_fired.get(name),
                "suppressed": count,
            }
            for name, count in self.alert_counts.items()
        }

Production Issue #16: A/B Testing & Experimentation for ML

Scope: A/B Testing & Experimentation — how to know a model/prompt change actually helped, not just "felt better." Overview

One-sentence ideacontrolled online experimentcausalPeekingUnderpowering

One-sentence idea: Offline metrics tell you a new model is different; only a controlled online experiment tells you it's better for users. A/B testing is how you get a causal estimate of impact — randomize users into control (old) vs treatment (new), and compare. Skip the statistics and you'll ship changes that look like wins but are just noise.

The trap this prevents: "AUC went up 0.3% offline, so we shipped it" — and engagement actually dropped, because offline AUC isn't the business metric and the offline test set didn't reflect live behavior. The two most common ways teams fool themselves: 1. Peeking — stopping the test the moment it looks significant (massively inflates false positives). 2. Underpowering — too few samples to detect the effect, so a real win looks like "no difference."

How an A/B Test Works (and why randomization matters)

                 ┌─ 50% CONTROL  → old model  → measure metric ─┐
all users ─ randomize ─                                          ├─ compare → significant?
                 └─ 50% TREATMENT → new model → measure metric ─┘

Random assignment makes the two groups statistically identical except for the change — so any metric difference is caused by the change, not by confounders (time of day, user type, seasonality). That causal claim is the entire point; without randomization you only have correlation.

Step 1: Sample Size & Power (do this BEFORE running)

Worked examplerelative2 / (p2 - p1)

You must compute how many users you need before starting — otherwise you can't interpret the result. The drivers: baseline rate, MDE, α (5%), power (80%).

Worked example. Baseline conversion = 10%; you want to detect a relative +5% lift (10% → 10.5%, so absolute MDE = 0.5%).

import math
from scipy import stats

def sample_size_per_arm(baseline, mde_abs, alpha=0.05, power=0.80):
    p1 = baseline
    p2 = baseline + mde_abs
    z_a = stats.norm.ppf(1 - alpha / 2)     # 1.96 for 5% two-sided
    z_b = stats.norm.ppf(power)             # 0.84 for 80% power
    p_bar = (p1 + p2) / 2
    n = (z_a * math.sqrt(2 * p_bar * (1 - p_bar)) +
         z_b * math.sqrt(p1 * (1 - p1) + p2 * (1 - p2))) ** 2 / (p2 - p1) ** 2
    return math.ceil(n)

n = sample_size_per_arm(0.10, 0.005)   # ≈ 58,000 PER ARM  (~116k total)

The key intuition — smaller effects cost dramatically more samples (n scales with 1/MDE²):

Relative lift to detectAbsolute MDE~n per arm
+20% (10% → 12%)0.020~3,800
+10% (10% → 11%)0.010~14,700
+5% (10% → 10.5%)0.005~58,000
+2% (10% → 10.2%)0.002~365,000

If you don't have the traffic to reach n, you cannot reliably detect your MDE — full stop. Either accept a larger MDE, run longer, or reduce variance (CUPED). Running underpowered and "eyeballing" is how real wins get discarded as noise.

Step 2: The Peeking Problem (the #1 mistake)

extra chancesFixeswithout

Every time you check a running test and stop as soon as p < 0.05, you get extra chances to cross the line by luck. The stated 5% false-positive rate becomes much higher.

Check once at the planned end:           ~5%  false-positive rate ✅
Peek continuously and stop at p<0.05:   ~25-40% false-positive rate ❌
→ You "find" significant wins that are pure noise, ship them, and wonder why
  the aggregate metric never moves.

Fixes: - Fix the sample size up front and only decide at the end (classic fixed-horizon test). The simplest correct approach. - Sequential testing / always-valid p-values (group sequential, mSPRT, Bayesian) — designed to let you monitor continuously and stop early without inflating error. Use these if you need early stopping. (Optimizely/Statsig-style "always-valid" inference.) - Don't stop on the primary metric just because a guardrail looks fine, and vice versa.

# Fixed-horizon discipline: compute n first, then judge ONCE at n.
def decide(control, treatment, n_planned):
    if len(control) < n_planned:
        return "KEEP RUNNING — do not peek-and-stop"   # resist the temptation
    stat, p = stats.ttest_ind(treatment, control)
    return {"significant": p < 0.05, "p": round(p, 4),
            "lift": (treatment.mean() - control.mean())}

Step 3: Sanity Checks Before Trusting a Result

something is brokenfadeRun long enoughnew vs returningWeekly seasonalityMultiple comparisons

Sample Ratio Mismatch (SRM)

If you split 50/50 but observe 48/52 with large N, something is broken (a logging bug, a redirect that drops one arm, a crash hitting one variant). A failed SRM check invalidates the whole experiment — fix it, don't interpret it.

def srm_check(n_control, n_treatment, expected=0.5):
    from scipy import stats
    total = n_control + n_treatment
    stat, p = stats.chisquare([n_control, n_treatment],
                              [total * expected, total * (1 - expected)])
    return {"srm_detected": p < 0.001, "p": p}   # p<0.001 → broken assignment, STOP

Novelty & primacy effects

Users react to change itself: a shiny new UI gets clicks from curiosity (novelty), or a changed ranking annoys regulars at first (primacy). Both fade, so an early result misleads. - Run long enough to outlast the effect (often 1–2+ weeks; cover weekly cycles). - Segment new vs returning users; look at the trend, not just the average.

Other traps

  • Weekly seasonalityrun in whole-week multiples; weekday ≠ weekend behavior.
  • Multiple comparisonstesting 20 metrics, one will be "significant" by chance; correct (Bonferroni/FDR) or pre-register the primary metric.
  • Interference / network effectsin social/marketplace/ride-share, treatment users affect control users; user-level randomization breaks. Use cluster/geo randomization.

ML-Specific Experimentation

The offline↔online gap

Offline metric ↑ does not guarantee online metric ↑. Reasons: offline test set isn't live traffic; the metric (AUC, NDCG) isn't the business KPI; feedback loops; the model changes user behavior. Always confirm an offline win with an online test before full rollout.

Testing models — connect to the deploy pipeline

A/B testing is the canary/champion-challenger step from Scaling and Infrastructure: route a slice of traffic to the challenger, compare primary + guardrail metrics, promote or roll back.

Interleaving (for ranking/search/recsys)

Instead of splitting users, mix results from both models into one list per query and see which model's items get clicked. Far more sensitive (needs ~10–100× less traffic) because each user compares both models directly — great for ranking changes.

Long-term vs short-term metrics

A model that maximizes clicks today may hurt retention next month (clickbait effect). Watch guardrail and long-term metrics (retention, complaints, unsubscribes), not just the immediate OEC. Consider holdback groups (a small % never gets the change) to measure long-term cumulative impact.

Counterfactual / off-policy evaluation

For recommenders/bandits you can sometimes estimate a new policy's value from logged data (inverse propensity weighting) to pre-screen candidates before spending live traffic — but still confirm online.

Model Drift & Degradation
•

Q1: What is model drift and how do you detect it?

Data driftConcept drift

A: Model drift is the degradation of model performance over time in production. Two types: Data drift — input distribution changes (e.g., new user demographics). Concept drift — the relationship between features and target changes (e.g., pandemic changes buying behavior). Detection: (1) Monitor prediction distribution (PSI — Population Stability Index). PSI > 0.2 → significant drift. (2) Monitor feature distributions (KS test, KL divergence per feature). (3) Track model performance metrics if ground truth is available (with a lag). (4) Use Evidently AI, NannyML, or custom dashboards. Response: Trigger retraining when drift exceeds thresholds.

•

Q2: How do you handle concept drift vs data drift differently?

Data driftConcept drift

A: Data drift: Input distribution shifts but the underlying relationship is stable. Solution: Retrain on recent data or use domain adaptation. Example: seasonal shifts in e-commerce. Concept drift: The true mapping f(X)→Y changes. This is more dangerous because even retraining may not help if you don't account for the shift. Types: sudden (regime change), gradual (slow shift), recurring (seasonal). Solution: Use online learning, sliding window retraining, or ensemble of models from different time periods weighted by recency. Detection: Data drift detectors may miss concept drift if the input distribution doesn't change.

•

Q3: What is PSI and how do you interpret it?

A: Population Stability Index measures how much a variable's distribution has shifted between two time periods. Formula: PSI = ∑ (Pi − Qi) · ln(Pi / Qi) where P and Q are the proportions in each bin. Interpretation: PSI < 0.1 → no significant shift. 0.1-0.2 → moderate shift, monitor closely. PSI > 0.2 → significant shift, investigate and likely retrain. Compute PSI for both input features and prediction scores. A sudden PSI spike in prediction scores without feature drift may indicate concept drift.

Q4: Your model's P99 latency increased from 50ms to 200ms. How do you debug?

A: Systematic approach: (1) Reproduce: Identify if it's all requests or specific patterns (large inputs, specific features). (3) Check infrastructure: CPU/GPU utilization, memory pressure, disk I/O, network latency, GC pauses. (4) Check data: Are input sizes growing? Feature store latency? Cold cache? Q5: How would you reduce model serving latency from 100ms to 20ms?

ModelServingFeaturesInfrastructureArchitecture

A: Layer the optimizations: (1) Model: Quantize FP32→INT8 (2-4x), prune (1.5x), distill to smaller model. (2) Serving: Use batching (dynamic batching in Triton), cache frequent predictions, use ONNX Runtime or TensorRT. (3) Features: Pre-compute features, use feature store with in-memory cache, minimize feature count. (4) Infrastructure: Right-size GPU (A10G may suffice over A100), co-locate model with feature store, use gRPC instead of REST. (5) Architecture: Separate heavy/light models — light model for fast path, heavy model for uncertain cases only.

Q6: What is the difference between throughput and latency? How do you optimize each?

LatencyThroughput

A: Latency: Time for a single request (P50, P95, P99). Optimize: smaller model, GPU, caching, reduced preprocessing. Throughput: Requests per second. Optimize: batching, horizontal scaling, async processing, efficient data loading. Tension: batching improves throughput (GPU utilization) but increases latency (waiting for batch to fill). Solution: dynamic batching with a max wait time (e.g., 10ms or batch_size=32, whichever comes first). Real-time serving: optimize latency. Batch scoring: optimize throughput.

Training-Serving Skew
•

Q10: What is training-serving skew and how do you prevent it?

Feature computation differencesData leakage in trainingPreprocessing mismatchStale features

A: Training-serving skew occurs when the model sees different data in production than during training, causing silent accuracy degradation. Common causes: (1) Feature computation differences: Python (training) vs Java (serving) implement feature logic differently. (2) Data leakage in training: Features computed using future information not available at serving time. (3) Preprocessing mismatch: Different normalization parameters, tokenizers, or encoding. (4) Stale features: Feature store returns cached/old values. Prevention: (1) Share feature computation code between training and serving (feature store pattern). (2) Log serving-time features, replay through training pipeline, compare. (3) Use the same preprocessing pipeline (save with the model via sklearn Pipeline). (4) Integration tests comparing training and serving outputs.

•

Q11: How does a feature store help prevent training-serving skew?

Single source of truthPoint-in-time correctOnline/offline consistencyFeature versioningMonitoring

A: A feature store (Feast, Tecton, Hopsworks) centralizes feature computation and serving: (1) Single source of truth: Same feature logic for training and serving — eliminates divergent implementations. (2) Point-in-time correct: Training data joins use historical feature values (as-of timestamps), preventing leakage. (3) Online/offline consistency: Offline store (batch, for training) and online store (low-latency, for serving) compute features identically. (4) Feature versioning: Track feature definition changes and their impact. (5) Monitoring: Feature store can monitor input distributions and alert on drift.

Scaling & Infrastructure

Q12: Your model serves 100 QPS. Now traffic jumps to 10K QPS. What do you do?

ImmediateCachingBatchingModel optimizationArchitectureCost

A: Multi-layer scaling: (1) Immediate: Horizontal pod autoscaling (HPA) with CPU/GPU utilization triggers. Pre-warm spare replicas. (2) Caching: Cache predictions for frequent/repeated inputs (Redis/Memcached). If 80% of queries are top 1000 items, cache hit rate is huge. Q13: How do you handle GPU failures in production?

(4) Auto-recovery: Kubernetes restarts failed pods automatically. Node auto-repair in cloud environments. (5) Monitoring: Track GPU temperature, memory utilization, ECC errors, NVML health metrics. Q16: How do you protect against adversarial attacks on ML models?

Input validationAdversarial trainingInput preprocessingModel ensembleMonitoringRate limiting

A: (1) Input validation: Bound input ranges, reject out-of-distribution inputs, sanitize text inputs. (2) Adversarial training: Include adversarial examples (FGSM, PGD) during training to build robustness. Q17: What is model extraction and how do you prevent it?

A: Model extraction (model stealing) involves querying a production model repeatedly to build a copy. Prevention: (1) Rate limiting per API key/IP. (2) Return only top-k predictions (not full probability distributions). (3) Add calibrated noise to output probabilities. (4) Watermark model outputs to detect stolen copies. (5) Monitor query patterns — extraction attacks show unusual query distributions (systematic feature space exploration). (6) Differential privacy in training to limit memorization.

Q30: How do you maintain multiple models in production simultaneously?

Model registryA/B testing infrastructureShared serving platformResource isolationCentralized monitoringAutomated promotion

A: Multi-model architecture: (1) Model registry: Version, stage (dev/staging/prod), metadata for each model. (2) A/B testing infrastructure: Traffic splitting by user/session. (3) Shared serving platform: Triton, Seldon, or KServe with multi-model support. (4) Resource isolation: Separate resource pools to prevent one model from starving others. (5) Centralized monitoring: Dashboard showing all model versions' metrics side by side. (6) Automated promotion: Champion/challenger pattern — new model auto-promoted if it outperforms current champion over evaluation window.

Q31: What's the biggest risk of automating model retraining?

A: Silently deploying a degraded model. An automated pipeline might retrain on corrupted data, pass basic validation (overall accuracy acceptable), but fail on critical segments. Solution: Multi-level validation gates — data quality, overall metrics, per-segment metrics, prediction distribution comparison with the current production model. Human approval for models affecting revenue-critical paths.

Q32: How do you handle feature store latency spikes?

A: (1) Use cached fallback values (stale-while-revalidate pattern). (2) Pre-compute features in batch for frequent entities. (3) Implement circuit breaker — if feature store latency > threshold, use default feature values or a simpler model that doesn't need the feature store. (4) Monitor and alert on P99 feature store latency.

Q33: What is a model card and why is it important in production?

A: A model card documents: model description, intended use, training data, evaluation metrics (overall + per-segment), limitations, ethical considerations, and maintenance ownership. Important because: (1) Regulatory compliance (EU AI Act). (2) Handoff between teams. (3) Incident response — knowing a model's limitations helps debug production issues faster. (4) Bias and fairness tracking.

•

Q34: How do you handle ML pipeline idempotency?

A: Idempotent pipelines produce the same result when run multiple times with the same input. Key practices: (1) Use deterministic data loading (sorted, deduplicated). (2) Set random seeds. (3) Write outputs to versioned paths (not overwrite). (4) Use checksums to detect duplicate runs. (5) Design Airflow/Prefect tasks with idempotent semantics. Why it matters: pipeline retries after failures shouldn't produce different/duplicate results.

Q35: What metrics would you track for an LLM in production?

QualitySafetyCostUser satisfactionOperationalGuardrails

A: Beyond standard latency/throughput: (1) Quality: Human evaluation scores (sampled), automated eval (BLEU, ROUGE, exact match). (2) Safety: Toxicity rate, PII leak rate, hallucination rate (NLI-based). (3) Cost: Tokens per request, cost per query. (4) User satisfaction: Thumbs up/down, conversation completion rate, retry rate. (5) Operational: Time to first token (TTFT), tokens per second (TPS), cache hit rate. (6) Guardrails: Block rate (how often guardrails triggered), false positive rate of safety filters.

Q26: A pod keeps restarting every few minutes. How do you investigate?

kubectl describe podkubectl logs <pod> --previousOOMKilled?Failing probes?Crash on startupExit code

A: Get the restart reason, then the cause:

  1. kubectl describe podEvents + last state. Look at Reason: OOMKilled, CrashLoopBackOff, Error, exit code; restart count.
  2. kubectl logs <pod> --previouslogs from the crashed container (the previous instance), where the actual error/stack trace lives.
  3. OOMKilled? Memory limit too low or a leak (Q32/Q35) — raise limits or fix the leak; check memory limit vs. actual usage.
  4. Failing probes? Liveness probe too aggressive (short timeout / app slow to start) → K8s kills a healthy-but-slow pod. Tune initialDelaySeconds, use a startupProbe.
  5. Crash on startupbad config/secret/env, missing dependency, failed migration, unreachable DB.
  6. Exit code137 = SIGKILL (OOM/timeout), 1/app error, 139 = segfault.
  7. Resource starvation / node issueskubectl get events, node pressure, evictions.

Key takeaway: describe pod for the restart reason + logs --previous for the crash trace. Most cases are OOMKilled (limits/leak) or an over-aggressive liveness probe killing a slow-starting app — distinguish those first.

Q27: A deployment succeeded but users still get errors. Why?

Readiness liesBad config/secret/envDownstream dependencyFailed/incomplete migrationImage/version mismatchRouting

A: "Rollout succeeded" only means pods are Running/Ready — not that the app works. Likely causes:

  • Readiness lies. Readiness probe returns 200 before the app can actually serve (deps not warmed) → traffic hits a not-ready pod.
  • Bad config/secret/env for this environment — pods start but mis-behave (wrong DB URL, missing key).
  • Downstream dependency broken — DB migration not applied, a service it calls is down, network policy blocking it.
  • Failed/incomplete migrationschema mismatch between new code and DB.
  • Image/version mismatchold image cached, or only some replicas updated (partial rollout).
  • RoutingService selector/labels wrong, Ingress misconfigured, traffic going to old pods.
  • Resource limitspods throttled/OOM under real load though they passed health checks.
  • Client-side caching / stale frontend assets.

Diagnose: check actual app logs + error rate per pod version, hit the service directly, verify config/secrets, confirm migrations and downstream health.

Key takeaway: A green rollout ≠ working app. Look past pod status at real error logs, config/secrets, migrations, downstream deps, and routing — and make readiness probes test genuine serving capability, not just process liveness.

Q28: How do you perform a zero-downtime deployment?

Rolling updatereadinessGraceful shutdownBlue-greenCanaryBackward-compatible changes

A: Replace instances gradually while always keeping healthy capacity serving:

  1. Rolling update (K8s default) with maxUnavailable: 0 / maxSurge — spin up new pods, wait for readiness, then retire old ones. Accurate readiness probes are essential (Q27).
  2. Graceful shutdown. Handle SIGTERM: stop accepting new requests, drain in-flight ones, then exit. Set terminationGracePeriodSeconds; use a preStop hook so the pod leaves the load-balancer rotation before dying.
  3. Blue-greenfull new stack alongside old; flip the router once validated; instant rollback by flipping back.
  4. Canaryroute a small % to the new version, watch error/latency metrics, ramp up or auto-rollback.
  5. Backward-compatible changesespecially DB: expand/contract migrations so old and new code both work during the overlap (never break the running version's schema).
  6. PodDisruptionBudget to keep a minimum available during the roll.

Key takeaway: Rolling/blue-green/canary with accurate readiness probes, graceful SIGTERM draining (preStop + grace period), and backward-compatible (expand/contract) schema changes. The overlap window is what makes it zero-downtime — both versions must coexist safely.

Q29: What happens if a pod dies during a long-running workflow?

anything not persisted is goneWith checkpointing (Q1, Q4)resumesWithout checkpointingSide-effects in flightdurable orchestrator

A: The in-memory progress is lost and K8s reschedules a replacement — anything not persisted is gone. Whether that's fine depends on durability:

  • With checkpointing (Q1, Q4): the new pod loads the last checkpoint and resumes from the last completed step. In-flight step may re-run — fine if idempotent.
  • Without checkpointing: the workflow restarts from scratch (or is simply lost). Bad for 40-step / long jobs.
  • Side-effects in flight may have partially applied — idempotency (Q2, Q60) prevents double-execution on resume.

Make long workflows pod-death-tolerant: - Don't run long workflows in a request/ephemeral pod — drive them from a durable orchestrator (Temporal, Step Functions, a job queue) with persisted state. - Checkpoint after each step; key by a stable run_id. - Graceful shutdown on SIGTERM: checkpoint and stop cleanly when the pod is being evicted/rolled. - Use a queue with visibility timeout / at-least-once so an unacked work item is redelivered to another worker.

Key takeaway: A dying pod loses all in-memory state; survival requires external checkpoints + idempotent steps so a replacement pod resumes rather than restarts. Don't anchor long workflows to ephemeral pod lifetimes — use a durable orchestrator/queue.

Q30: How do you autoscale LLM workers?

Scale on the right metricKEDAcustom/external metricsQueue-based decouplingGPU realitiesPre-warm

A: LLM serving is GPU-bound and latency-sensitive, so default CPU-based HPA is the wrong signal:

  1. Scale on the right metric. Queue depth / pending requests, GPU utilization, batch wait time, or tokens-in-flight — not CPU. Use KEDA (scale on queue length) or HPA on custom/external metrics.
  2. Queue-based decoupling. Put requests on a queue; scale workers to keep queue latency under SLO. Smooths bursts and gives a clean scaling signal.
  3. GPU realities. Pods take minutes to schedule (node provisioning, large image/model pull, model load into VRAM). Pre-warm a buffer of replicas and use provisioned headroom; cold-start can't keep up with a sudden spike.
  4. Batching. Continuous/dynamic batching (vLLM, TGI, Triton) raises throughput per GPU before you add more GPUs — scale up batching efficiency first.
  5. Scale-to-zero carefully for spiky/dev workloads (KEDA), accepting cold-start latency; keep min replicas > 0 for prod SLOs.
  6. Cost controls. Spot/preemptible GPUs for non-critical, mixed instance types, scale down off-peak.
  7. Cluster Autoscaler / Karpenter to add GPU nodes when pods can't be scheduled.

Key takeaway: Scale LLM workers on queue depth / GPU utilization (not CPU) via KEDA/custom-metric HPA, pre-warm replicas to hide multi-minute GPU cold starts, and exploit continuous batching before adding GPUs. Pair pod autoscaling with node autoscaling (Karpenter/Cluster Autoscaler).

Q41: A workflow failed overnight. How do you identify the root cause?

Find the failed runsteperror + stack traceTrace the requestCorrelate timingInputs

A: Reconstruct the timeline from your telemetry:

  1. Find the failed run by run_id/trace_id; get its status, which step failed, and the error + stack trace from structured logs.
  2. Trace the request (Q43) across services/steps — the span that errored and what it was doing (inputs, downstream call).
  3. Correlate timing. What else happened at that timestamp? A deploy, a dependency outage, a traffic/cost spike, a DB incident (Q16/Q17), rate limits (Q6)? Check dashboards/alerts around that time.
  4. Inputs. Capture the input that triggered it — was it a poison/edge-case payload (Q24)?
  5. Reproduce with the captured inputs in a safe env.
  6. Check retries/idempotencydid it loop (Q3) or partially apply side-effects?

This requires correlation IDs threaded through every step + structured logs + traces beforehand — without them, overnight debugging is guesswork.

Key takeaway: Use run_id/trace_id to locate the failed step, read its structured error + trace span, and correlate the timestamp with deploys/dependency incidents/inputs — then reproduce. The whole approach depends on having correlation IDs and structured logs/traces in place before the failure.

Q42: What logs would you capture for an LLM application?

structured (JSON)Request contextPrompt & responseTokens & costLatency breakdownRetrieval (RAG)

A: Enough to debug, audit, and measure quality — structured (JSON) and correlated by request_id/trace_id:

  • Request context: request/trace/user/session ids, route, timestamp, model + version, parameters (temperature, max_tokens).
  • Prompt & response: the rendered prompt (or a hash/reference if it contains sensitive data — Q39), system prompt version, the completion, finish_reason.
  • Tokens & cost: prompt/completion/total tokens, estimated cost.
  • Latency breakdown: queue wait, time-to-first-token, total generation time.
  • Retrieval (RAG): query, retrieved chunk ids + scores, which chunks were actually used/cited (Q44).
  • Tool/agent steps: each tool call, args, result, errors, number of iterations.
  • Outcome & quality: errors/retries/fallbacks, guardrail triggers, validation failures (Q9), user feedback (thumbs up/down), eval scores.
  • Safety: guardrail/PII-redaction events, refusals, injection-detection hits.

Caveats: redact PII/secrets, sample high-volume logs, and respect retention/privacy. Avoid logging raw sensitive prompt contents.

Key takeaway: Capture structured, trace-correlated logs of model+params, prompt/response (redacted), tokens/cost, latency breakdown (incl. TTFT), retrieved+used chunks, tool steps, and outcome/quality/guardrail signals. These power debugging, cost control, and quality eval — but redact PII and sample volume.

Q43: How do you trace a request across 10 microservices?

Distributed tracingOpenTelemetryTrace + span IDspropagatedand async/queue boundariesspan

A: Distributed tracing with a propagated trace context:

  1. OpenTelemetry (vendor-neutral standard) to instrument each service; export to Jaeger / Tempo / Honeycomb / Datadog.
  2. Trace + span IDs. A trace_id is generated at the edge and propagated through every hop via headers (W3C traceparent) — across HTTP, gRPC, and async/queue boundaries (inject context into message headers). Each service/operation creates a span with parent linkage.
  3. Result: one waterfall showing every hop, its duration, and where time/errors concentrate (Q31) — so you see which of the 10 services is the bottleneck or failure.
  4. Add baggage/attributes (user id, model, route) and correlate logs by embedding trace_id in every log line (Q42) — jump from a trace to its logs.
  5. Sampling (head/tail) to control volume while keeping error/slow traces.

Key takeaway: Propagate a W3C trace context through all 10 services (including async/queue hops) using OpenTelemetry; each emits spans that assemble into one end-to-end waterfall, and embedding the trace_id in logs ties traces to logs. That's how you pinpoint the slow/failing hop.

Q44: What metrics would you monitor for a production RAG system?

System / opscost per queryRetrieval qualityGeneration qualityfaithfulness/groundednesshallucination/abstention rate

A: Across system, retrieval, generation, and business:

  • System / ops: end-to-end latency (P50/P95/P99) broken into retrieval vs. generation, QPS, error rate, vector-DB latency (Q13), token usage & cost per query, cache hit rate.
  • Retrieval quality: Recall@k / MRR / nDCG on a labeled set, retrieval score distributions, % queries with low top-score (potential "no good context"), index freshness/coverage.
  • Generation quality: faithfulness/groundedness (answer supported by context), answer relevance, hallucination/abstention rate, citation correctness — measured with an LLM-judge / RAGAS on samples.
  • Drift: query distribution drift, embedding/data drift, OOD-query rate (questions the corpus can't answer).
  • User signals: thumbs up/down, follow-up/regenerate rate, deflection/resolution, escalation to human.
  • Guardrails: injection detections, PII-redaction events, refusal rate.

Key takeaway: Monitor split latency (retrieval vs generation), cost/tokens, retrieval quality (Recall@k/MRR) and answer faithfulness/hallucination rate (LLM-judge/RAGAS on samples), plus query drift and user feedback. RAG needs quality metrics, not just system metrics — most failures are silent relevance/grounding regressions.

Q45: How would you set up alerts for workflow failures?

Tier by severity → channelerror-budget burnSymptom-based + key signalsqueue depth/lagDLQ depthEvery alert has a runbook

A: Actionable, tiered, low-noise:

  1. Tier by severity → channel. Critical (workflow engine down, failure rate spikes, all retries exhausted) → page/PagerDuty. Warning (elevated retry rate, latency creeping, DLQ filling — Q24) → Slack. Info → dashboard/daily digest.
  2. Alert on rates & SLOs, not single events. "Failure rate > 5% over 5 min" or error-budget burn, not every individual failure (avoids fatigue). Single-event paging only for truly critical/rare conditions.
  3. Symptom-based + key signals: failure rate, p99 latency, queue depth/lag (Q23), DLQ depth (Q24), stuck/long-running runs (Q3), dependency error rates (LLM 429/5xx — Q6/Q8), checkpoint-store health (Q5).
  4. Every alert has a runbook and points at the trace/log to start from (Q41).
  5. Reduce noise: dedup, group, set sensible thresholds + for durations, suppress during maintenance, composite conditions (multiple signals together).
  6. Catch silence too"no successful runs in N min" / heartbeat alerts catch a stalled scheduler that emits no errors.

Key takeaway: Tier alerts by severity to the right channel, fire on rates/SLO-burn (not single events) plus key signals (failure rate, latency, queue/DLQ depth, stuck runs, dependency errors), attach a runbook to each, and add heartbeat alerts for silent stalls. Optimize for actionability over coverage.
