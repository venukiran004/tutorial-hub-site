Google ADK — Agent Development Kit, End to End

Google's open-source, code-first framework for building and shipping AI agents. This file is the whole thing in one place: install, the agent model, graph workflows, tools, session and memory, callbacks, multi-agent and A2A, MCP, evaluation, deployment, and the 1.x → 2.x break.

Everything below was checked against a real install of google-adk 2.8.0 (released 26 Aug 2026, Python ≥ 3.10). Where you see an Output block, that is stdout from actually running the code on this machine — the graph, state and tool-schema examples need no API key, so they are reproducible offline. API surfaces (field lists, CLI commands) came from introspecting the installed package, not from memory.

1. What ADK is, and where it sits

ADK is a Python/Java/Go library for building agents, plus a CLI (adk) that runs, tests, evaluates and deploys them. It is the framework behind Google's own agent products, released as open source, and it is deliberately code-first: an agent is a Python object in a file you own, not a configuration in someone's console.

Three things it gives you that a bare model SDK does not:

Concern What ADK provides
Orchestration A graph runtime — nodes and edges, deterministic routing, loops, parallelism
State Sessions, scoped state (app:/user:/temp:), cross-session memory
Operations A dev UI, an eval harness, tracing, and one-command deploy to Cloud Run / Agent Engine / GKE

Where it sits relative to things you already know:

  • vs. calling Gemini directlyADK adds the loop, the tool plumbing, and the state. If your app is one prompt and one response, you do not need ADK.
  • vs. LangGraphthe closest comparison. Both are graph orchestrators over LLM calls. ADK is Google-native (Gemini, Vertex, Agent Engine) and ships the ops story in the box; LangGraph is model-agnostic with a larger ecosystem. See §17.
  • vs. MCPnot competitors. MCP is a protocol for exposing tools; ADK is a framework that consumes MCP servers as tools (§12) and speaks A2A to other agents (§11). See 01_MCP_Notes.md.
2. Install and your first agent 
pip install google-adk                    # 2.8.0 at the time of writing, needs Python >= 3.10

Optional extras, declared by the package itself — install only what you use:

a2a  agent-identity  all  antigravity  benchmark  bigquery-analytics  community  daytona
db  dev  docs  e2b  eval  extensions  gcp  mcp  oci  otel-gcp  redis  slack  test  toolbox  tools

So MCP support is pip install "google-adk[mcp]", agent-to-agent is [a2a], the eval harness is [eval]. This bites people: McpToolset and RemoteA2aAgent are importable only with their extra installed — without it you get ModuleNotFoundError: No module named 'mcp' (or 'a2a'), which looks like an ADK bug and is not.

The scaffold

adk create my_app --model gemini-2.5-flash --api_key $GOOGLE_API_KEY

That writes exactly four files:

my_app/
├── .env
├── .gitignore
├── __init__.py        # from . import agent
└── agent.py           # must define a module-level `root_agent`

agent.py, verbatim from the generator:

from google.adk.agents.llm_agent import Agent

root_agent = Agent(
    model='gemini-2.5-flash',
    name='root_agent',
    description='A helpful assistant for user questions.',
    instruction='Answer user questions to the best of your knowledge',
)

The root_agent name is a contract — adk web, adk run and the deployers all look for that symbol. Rename it and the tooling stops finding your agent.

Two backends, one switch

adk create writes a different .env depending on whether you passed --api_key or --project/--region:

# Google AI Studio: an API key, no cloud project
GOOGLE_GENAI_USE_ENTERPRISE=0
GOOGLE_API_KEY=...

# Vertex AI: a project, ADC for credentials, no key
GOOGLE_GENAI_USE_ENTERPRISE=1
GOOGLE_CLOUD_PROJECT=my-proj
GOOGLE_CLOUD_LOCATION=us-central1

Same agent code either way. Start on the key, move to Vertex when you need VPC-SC, quotas, or the managed session and memory services.

3. The three ways to build

This is the thing to get straight before writing anything, because ADK offers three orchestration styles and they compose:

Style You get Use when
A single Agent The model decides everything — which tool, when to stop The task is genuinely open-ended
Workflow agents (SequentialAgent, ParallelAgent, LoopAgent) Fixed control flow, agents as steps You know the shape of the pipeline
Graph Workflow (2.x) Nodes and edges, conditional routes, plain functions as nodes You want determinism and branching

All three still exist in 2.8.0 — I checked google.adk.agents, and SequentialAgent, ParallelAgent and LoopAgent are all still exported. The graph Workflow is the 2.x addition, not a replacement.

The judgement call: every step you hand to the model is a step that can go wrong in a way you cannot unit-test. Push as much as you can into deterministic edges and plain Python nodes, and keep the model for the parts that genuinely need language.

4. LlmAgent — the full surface

Agent is an alias for LlmAgent. Introspecting the class on 2.8.0 gives 33 fields. Grouped by what they are for:

Identity and behaviour

Field Notes
name Required, unique. Used for delegation and in traces
model str (e.g. "gemini-2.5-flash") or a BaseLlm instance
description How other agents decide to route to this one — write it for that reader
instruction str, or a callable taking ReadonlyContext. Supports {state_key} templating
static_instruction Instruction content that never varies — cache-friendly
global_instruction Applied across the agent tree
mode 'chat' \| 'task' \| 'single_turn' — the 2.x collaboration modes

Input and output

Field Notes
tools List of functions, BaseTools, or toolsets
input_schema / output_schema Pydantic models. output_schema forces structured JSON
output_key Writes the final response into session state under this key
state_schema Pydantic model constraining session state
include_contents 'default' or 'none' — 'none' makes the agent stateless per turn
generate_content_config Temperature, max tokens, safety settings

Control

Field Notes
sub_agents Children this agent may delegate to
disallow_transfer_to_parent / disallow_transfer_to_peers Fence the delegation graph
planner BuiltInPlanner or PlanReActPlanner
code_executor Lets the agent run generated code
retry_config, timeout, rerun_on_resume, wait_for_output, parallel_worker 2.x execution controls

Callbacks — eight of them: before_agent_callback, after_agent_callback, before_model_callback, after_model_callback, before_tool_callback, after_tool_callback, plus on_model_error_callback and on_tool_error_callback. See §10.

description vs instruction. instruction tells this agent how to behave. description tells the parent what this agent is for. A vague description is the single most common cause of a coordinator routing to the wrong specialist.

5. Graph workflows

The 2.x model: nodes are agents, tools or plain Python functions; edges describe flow. "START" is the entry point. A tuple of nodes is a sequential chain; a dict maps a route label to the next node.

Here is a complete, runnable workflow with a conditional branch. It uses no model, so it needs no API key:

"""ADK 2.x graph workflow using only plain-Python nodes - no model, no API key."""
import asyncio
from google.adk import Workflow, Event, Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types


def classify(node_input: str):
    """Router node: pick a branch and pass the text along."""
    text = node_input or ""
    route = "SHOUT" if text.isupper() else "WHISPER"
    return Event(output=text, route=route, state={"classified_as": route})


def shout(node_input: str):
    return Event(output=f"{node_input}!!!", message=f"shouting: {node_input}!!!")


def whisper(node_input: str):
    return Event(output=node_input.lower(), message=f"whispering: {node_input.lower()}")


root_agent = Workflow(
    name="tone_router",
    description="Routes text to a shout or whisper node.",
    edges=[
        ("START", classify),
        (classify, {"SHOUT": shout, "WHISPER": whisper}),
    ],
)


async def main():
    session_service = InMemorySessionService()
    runner = Runner(agent=root_agent, app_name="demo", session_service=session_service)
    for text in ("HELLO THERE", "Hello There"):
        session = await session_service.create_session(app_name="demo", user_id="u1")
        msg = types.Content(role="user", parts=[types.Part(text=text)])
        print("input: %r" % text)
        async for event in runner.run_async(user_id="u1", session_id=session.id,
                                            new_message=msg):
            if event.output is not None:
                print("   %-10s output=%r route=%r" % (event.author, event.output,
                                                       event.actions.route))
        final = await session_service.get_session(app_name="demo", user_id="u1",
                                                  session_id=session.id)
        print("   final state:", dict(final.state))
        print()

asyncio.run(main())

Output 

input: 'HELLO THERE'
   tone_router output='HELLO THERE' route='SHOUT'
   tone_router output='HELLO THERE!!!' route=None
   final state: {'classified_as': 'SHOUT'}

input: 'Hello There'
   tone_router output='Hello There' route='WHISPER'
   tone_router output='hello there' route=None
   final state: {'classified_as': 'WHISPER'}

Three things that output proves:

  1. A plain function is a node. No decorator, no wrapper class — put it in edges and ADK adapts it.
  2. Routing is data, not control flow. classify does not call the next node; it returns a label and the runtime dispatches. That is what makes the graph inspectable and testable.
  3. route is None on the terminal node's event — routing metadata belongs to the decision, not the result.

Workflow fields

From the installed class: name, description, edges, graph, input_schema, output_schema, state_schema, max_concurrency, retry_config, timeout, rerun_on_resume, wait_for_output.

The older workflow agents

Still fully supported, and simpler when the flow is fixed:

from google.adk.agents import SequentialAgent, LlmAgent

writer = LlmAgent(name="Writer", model="gemini-2.5-flash",
                  instruction="Write a Python function for the request.",
                  output_key="generated_code")

reviewer = LlmAgent(name="Reviewer", model="gemini-2.5-flash",
                    instruction="Review this code:\n```python\n{generated_code}\n```",
                    output_key="review_comments")

pipeline = SequentialAgent(name="CodePipeline", sub_agents=[writer, reviewer])

Note the pattern: output_key writes to state, and the next agent's instruction reads it back with {generated_code}. That is how workflow agents pass data — through state, not arguments.

6. Moving data between nodes

An Event carries four things you will use constantly:

Kwarg Where it lands Meaning
output event.output Value handed to the next node as node_input
message event.message User-facing text
state event.actions.state_delta Merged into session state
route event.actions.route Branch label for conditional edges

route and state are convenience kwargs, not fields. A before validator folds them into actions. Worth knowing because Event is configured extra='ignore' — a typo'd kwarg is silently dropped rather than raising:

>>> Event(route="RUN_TASK_C").actions.route
'RUN_TASK_C'
>>> Event(state={"attempts": 3}).actions.state_delta
{'attempts': 3}
>>> Event(rout="typo").actions.route     # note the typo
None

Nodes declare what they need as parameters and the runtime supplies it — node_input for the previous node's output, and any state key by name:

def start(node_input: str):
    return Event(output=node_input, state={"steps": ["start"]})


def add_tax(node_input: str, steps: list):
    total = round(float(node_input) * 1.18, 2)
    return Event(output=str(total), state={"steps": steps + ["tax"], "with_tax": total})


def add_shipping(node_input: str, steps: list):
    total = round(float(node_input) + 4.99, 2)
    return Event(output=str(total), state={"steps": steps + ["shipping"]},
                 message=f"total is {total}")


pipeline = Workflow(name="checkout", edges=[("START", start, add_tax, add_shipping)])

Output (driven by a Runner over InMemorySessionService, input "100.00")

   node output: 100.00
   node output: 118.0
   node output: 122.99
   final state: {'steps': ['start', 'tax', 'shipping'], 'with_tax': 118.0}

steps was never passed explicitly — each node asked for it by parameter name and the runtime injected the current state value.

7. Tools

A function is a tool

ADK reads the signature, type hints and docstring and generates the schema the model sees. There is no decorator:

def get_weather(city: str, unit: str = "celsius") -> dict:
    """Look up the current weather for a city.

    Args:
        city: The city to look up, e.g. "Hyderabad".
        unit: Either "celsius" or "fahrenheit".
    """
    return {"status": "ok", "city": city, "temp": 31, "unit": unit}

agent = Agent(name="w", model="gemini-2.5-flash", tools=[get_weather])

What the model actually receives, printed from FunctionTool(func=get_weather)._get_declaration():

Output 

tool name        : get_weather
tool description : Look up the current weather for a city.
parameters       : {
  "properties": {
    "city": {
      "title": "City",
      "type": "string"
    },
    "unit": {
      "default": "celsius",
      "title": "Unit",
      "type": "string"
    }
  },
  "required": [
    "city"
  ],
  "title": "get_weatherParams",
  "type": "object"
}

So: the docstring is the tool description the model reasons over, type hints become the JSON schema, and defaults make parameters optional. A missing docstring means the model is guessing.

Return a dict, not a bare string. The keys give the model structure to reason about; a {"status": ...} field in particular lets it distinguish success from a handled failure.

ToolContext — reaching the session from inside a tool

from google.adk.tools import ToolContext

def remember_city(city: str, tool_context: ToolContext) -> dict:
    tool_context.state["user:home_city"] = city          # survives the session
    return {"status": "saved", "city": city}

ADK detects the parameter by its type annotation, not its name, and hides it from the schema the model sees. Through it you get state, actions (including transfer_to_agent, escalate, skip_summarization), and artifact load/save.

The rest of the tool catalogue

Kind Import / usage
Wrapped function FunctionTool(func=...) — explicit form of the above
Long-running LongRunningFunctionTool(func=...) — returns a ticket, agent resumes later
Agent as tool AgentTool(agent=...) — call another agent and get its answer back
Built-in google_search, code execution, Vertex AI Search
Memory load_memory — search across past sessions
Loop control exit_loop — break out of a LoopAgent
MCP McpToolset (§12)
OpenAPI Generate tools from a spec
Third party LangChain and CrewAI tool adapters

AgentTool vs sub_agents — the distinction interviewers probe. AgentTool is a call: the child answers and control returns, like a function. sub_agents is a handoff: the child takes over the conversation. Use AgentTool when you want an answer, sub_agents when you want a specialist to own the next few turns.

8. Session, state and memory

Three different things, routinely confused:

Concept Scope Analogy
Session One conversation thread The chat window
State Key–value data attached to a session Variables in that window
Memory Searchable store across sessions What the agent remembers about you

State scoping is a prefix

Verified constants: State.APP_PREFIX = 'app:', State.USER_PREFIX = 'user:', State.TEMP_PREFIX = 'temp:'.

svc = InMemorySessionService()
s1 = await svc.create_session(app_name="demo", user_id="u1", state={
    "app:tier": "free", "user:name": "Venu", "cart": ["book"], "temp:scratch": 1})
s2 = await svc.create_session(app_name="demo", user_id="u1")

Output 

   State.APP_PREFIX ='app:'  State.USER_PREFIX='user:'  State.TEMP_PREFIX='temp:'
   session 1 state: {'cart': ['book'], 'app:tier': 'free', 'user:name': 'Venu'}
   session 2 sees : {'app:tier': 'free', 'user:name': 'Venu'}
   -> app: and user: values follow the user; plain keys do not

Two facts that output settles:

  • temp:scratch is not in session 1's state at all. temp: values live for one invocation and are never persisted — do not use them to pass data between turns.
  • A brand-new session already has app: and user: values. The prefix, not the API call, is what decides scope.

Service implementations

Session Memory
InMemorySessionService — dev only, lost on restart InMemoryMemoryService — dev only
DatabaseSessionService — any SQLAlchemy URL VertexAiMemoryBankService — managed, persistent
VertexAiSessionService — managed on Vertex

Swapping the service does not change your agent code. Build on in-memory, move to a database when you need to survive a restart, move to Vertex when you want it managed.

9. Runner — driving an agent from your own code

adk web and adk run are conveniences. In your own service you drive a Runner:

from google.adk import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types

session_service = InMemorySessionService()
runner = Runner(agent=root_agent, app_name="demo", session_service=session_service)

session = await session_service.create_session(app_name="demo", user_id="u1")
msg = types.Content(role="user", parts=[types.Part(text="hello")])

async for event in runner.run_async(user_id="u1", session_id=session.id, new_message=msg):
    if event.is_final_response() and event.content and event.content.parts:
        print(event.content.parts[0].text)

Runner.__init__ is keyword-only: app, app_name, agent, node, plugins, artifact_service, session_service (required), memory_service, credential_service. Methods: run, run_async, run_debug, run_live (bidirectional audio/video), rewind_async, close.

Two easy mistakes:

  • create_session is async — await it. Passing a coroutine as a session is a confusing ValueError later.
  • run_async yields many events (tool calls, partials, state deltas). Filter with event.is_final_response() unless you are streaming.
10. Callbacks and plugins

Six interception points, plus two error hooks. The pattern is uniform: return None to continue, return an object to override.

Callback Return None Return a value
before_agent_callback Run the agent Content — skip the agent entirely
after_agent_callback Keep output Content — appended as an extra event
before_model_callback Call the LLM LlmResponse — skip the call (cache, guardrail)
after_model_callback Keep response LlmResponse — replace it (redaction)
before_tool_callback Run the tool dict — skip the tool (mock, deny)
after_tool_callback Keep result dict — replace the result 
def block_pii(callback_context, llm_request):
    """Refuse outright rather than letting the prompt reach the model."""
    text = str(llm_request.contents[-1])
    if "ssn" in text.lower():
        from google.adk.models import LlmResponse
        from google.genai import types
        return LlmResponse(content=types.Content(
            role="model", parts=[types.Part(text="I can't process that.")]))
    return None

agent = Agent(name="safe", model="gemini-2.5-flash", before_model_callback=block_pii)

before_model_callback returning a cached LlmResponse is the cheapest caching layer you will ever write, and before_tool_callback returning a dict is how you build a deny-list without touching tool code.

Plugins (Runner(plugins=[...])) are the same hooks applied across every agent in the app — use them for tracing, cost accounting and global guardrails instead of copying callbacks onto every agent.

11. Multi-agent and A2A

In-process: coordinator and specialists

billing = Agent(name="billing", model="gemini-2.5-flash",
                description="Handles invoices, refunds and payment failures.")
tech = Agent(name="tech", model="gemini-2.5-flash",
             description="Handles login problems, errors and outages.")

coordinator = Agent(
    name="coordinator", model="gemini-2.5-flash",
    instruction="Route the user to the right specialist.",
    sub_agents=[billing, tech],
)

Routing is driven by the sub-agents' description fields. Fence it with disallow_transfer_to_parent / disallow_transfer_to_peers when you do not want a specialist handing control sideways.

The 2.x mode field ('chat' | 'task' | 'single_turn') controls how a delegated agent behaves — task mode runs the specialist to completion and returns control to the coordinator, with its own isolated history.

Across processes: A2A

Agent2Agent is the open protocol for one agent calling another over HTTP. Needs pip install "google-adk[a2a]".

from google.adk.agents.remote_a2a_agent import (
    AGENT_CARD_WELL_KNOWN_PATH, RemoteA2aAgent)

prime_agent = RemoteA2aAgent(
    name="prime_agent",
    description="Agent that handles checking if numbers are prime.",
    agent_card=f"http://localhost:8001/a2a/check_prime_agent{AGENT_CARD_WELL_KNOWN_PATH}",
)

root_agent = Agent(model="gemini-2.5-flash", name="root_agent",
                   sub_agents=[roll_agent, prime_agent])

A remote agent is used exactly like a local sub-agent — the transport is the only difference. Expose your own with adk api_server --a2a, which serves the agent card (capabilities, skills, endpoint) at the well-known path so callers can discover it.

MCP vs A2A, the one-liner: MCP connects an agent to tools; A2A connects an agent to other agents. ADK speaks both.

12. MCP inside ADK

pip install "google-adk[mcp]", then any MCP server becomes a toolset:

from google.adk.agents import LlmAgent
from google.adk.tools.mcp_tool.mcp_toolset import McpToolset
from google.adk.tools.mcp_tool.mcp_session_manager import StdioConnectionParams
from mcp import StdioServerParameters

root_agent = LlmAgent(
    model='gemini-2.5-flash',
    name='fs_agent',
    instruction='Help users with file management.',
    tools=[
        McpToolset(
            connection_params=StdioConnectionParams(
                server_params=StdioServerParameters(
                    command='npx',
                    args=["-y", "@modelcontextprotocol/server-filesystem", "/path/to/folder"],
                ),
            ),
            tool_filter=['list_directory', 'read_file'],
        )
    ],
)

Remote servers use StreamableHTTPConnectionParams(url=..., headers=...) instead.

Always set tool_filter. A toolset injects every tool the server advertises into the model's context — an unfiltered server is a silent token bill and a larger attack surface.

13. Human in the loop

Two mechanisms, for two different shapes of pause:

Long-running tools — the tool returns a ticket immediately and the run suspends:

from google.adk.tools import LongRunningFunctionTool

def ask_for_approval(purpose: str, amount: float) -> dict:
    """Ask a human to approve a reimbursement."""
    return {'status': 'pending', 'approver': 'Sean Zhou', 'ticket-id': 'approval-ticket-1'}

approval_tool = LongRunningFunctionTool(func=ask_for_approval)

Your application watches for the pending status, gets a human decision out of band, and resumes the run with the result.

Tool confirmation — 2.x has first-class confirmation, surfaced on event.actions.requested_tool_confirmations. The runtime pauses before executing a tool marked as requiring confirmation and waits for an explicit approval.

Related fields on EventActions worth knowing: escalate (bubble up to the parent agent), transfer_to_agent, skip_summarization, rewind_before_invocation_id.

14. Evaluation

Agents fail differently from functions: the same input can produce a different route on a different day. ADK evaluates both the trajectory and the answer.

File Purpose
*.test.json One session, a few turns — unit-test scale, run during development
*.evalset.json Many sessions, multi-turn — integration scale, run in CI

Both are Pydantic-backed (EvalSet, EvalCase) and record the user query, the expected tool trajectory, intermediate responses and a reference final response.

adk eval path/to/agent path/to/agent/my_evalset.evalset.json
# in pytest
from google.adk.evaluation import AgentEvaluator

async def test_agent():
    await AgentEvaluator.evaluate(agent_module="my_app",
                                  eval_dataset_file_path_or_dir="tests/basic.test.json")

Default metrics:

  • tool_trajectory_avg_scoredefault threshold 1.0, an exact match on the sequence of tool calls. Strict on purpose: if the agent reached the right answer by the wrong route, you want to know.
  • response_match_scoredefault 0.8, ROUGE-style similarity, because natural language will not match exactly.

adk web has an Eval tab for building cases from a live conversation, which is by far the fastest way to turn "it did something weird just now" into a regression test.

15. Deployment

Three targets, verified from adk deploy --help:

adk deploy agent_engine ...     # fully managed Vertex AI Agent Engine
adk deploy cloud_run ...        # serverless container
adk deploy gke ...              # your own Kubernetes

Cloud Run, with the flags that matter:

adk deploy cloud_run \
  --project=$GOOGLE_CLOUD_PROJECT \
  --region=$GOOGLE_CLOUD_LOCATION \
  --service_name=$SERVICE_NAME \
  --app_name=$APP_NAME \
  --with_ui \
  $AGENT_PATH

Also available: --session_service_uri, --artifact_service_uri, --port (default 8000).

If you want your own container and full control of the FastAPI app:

from google.adk.cli.fast_api import get_fast_api_app

app: FastAPI = get_fast_api_app(
    agents_dir=AGENT_DIR,
    session_service_uri=SESSION_SERVICE_URI,
    allow_origins=ALLOWED_ORIGINS,
    web=SERVE_WEB_INTERFACE,
)

The one production decision people get wrong: deploying with InMemorySessionService. It works in staging and then loses every conversation on the first scale-to-zero or redeploy. Set --session_service_uri (or a DatabaseSessionService) before you take traffic.

Target Pick it when
Agent Engine You want sessions, memory, tracing and scaling managed for you
Cloud Run You want a container, scale-to-zero, and your own dependencies
GKE You already run Kubernetes and need VPC/sidecar/GPU control
16. ADK 1.x → 2.x

ADK 2.0 went stable on 19 May 2026. The headline change is that execution became a graph.

Area 1.x 2.x
Orchestration Hierarchical agents, workflow agents Graph runtime: nodes + edges, plus the old workflow agents
Event schema — New node_info and output fields
Context Separate ToolContext, CallbackContext Unified Context (exported at google.adk.Context)
Delegation transfer_to_agent Task API, plus mode='task' collaboration agents
HITL Long-running tools Long-running tools and first-class tool confirmation
Config Code Code, or AgentConfig YAML for no-code assembly

What this means in practice:

  • Your 1.x agents mostly still work. Agent, SequentialAgent, ParallelAgent and LoopAgent are all still there in 2.8.0.
  • Custom session storage needs attention. If you persist events yourself and validate with a strict JSON schema, the new node_info/output fields will fail validation until you update it.
  • Beware broad except blocks. 2.x retries automatically; a bare except around agent execution swallows failures the retry machinery is trying to surface.
  • adk migrate exists to help with the mechanical parts.

A note on sources: much of the 2.0 "breaking changes" writing online is about ADK Go. Go-only details (BaseAgent → BaseNode, context.Context as a first argument) do not apply to Python. I checked the Python package directly; the Python break is narrower than the blogs imply.

17. ADK vs LangGraph vs CrewAI
Google ADK LangGraph CrewAI
Model Graph of nodes/edges Graph of nodes/edges Roles and tasks
Determinism High — explicit edges High — explicit edges Lower — role-driven
Models Gemini first; others via LiteLLM Any Any
State Sessions + scoped state + memory services Checkpointers Lighter
Tools Functions, MCP, OpenAPI, A2A LangChain ecosystem LangChain-compatible
Eval Built in (adk eval, trajectory metric) LangSmith (separate product) Limited
Deploy adk deploy → Agent Engine / Cloud Run / GKE Bring your own / LangGraph Platform Bring your own

The honest summary: ADK and LangGraph solve the same problem with very similar shapes. Choose ADK when you are already on Google Cloud and value the eval + deploy story being in the box; choose LangGraph when portability across providers matters more. Both beat CrewAI when correctness and testability matter, because both let you write the control flow down explicitly.

18. Interview questions
•

Q1. What problem does ADK solve that the Gemini SDK does not?

Orchestration, state and operations. The SDK gives you one call; ADK gives you the loop (multi-step, multi-tool), scoped session state and cross-session memory, and the surrounding machinery — dev UI, trajectory-aware eval, tracing, one-command deploy.

•

Q2. When would you use a graph Workflow over a single Agent?

Whenever the control flow is knowable. Every decision delegated to the model is a decision you cannot unit-test and that costs tokens. Deterministic edges for the parts you know, the model for the parts that genuinely need language.

•

Q3. AgentTool or sub_agents?

AgentTool is a call — the child answers, control returns. sub_agents is a handoff — the child owns the conversation. Use the first for "compute this for me", the second for "this specialist should take over".

•

Q4. How does a Python function become a tool?

ADK introspects the signature. Type hints become the JSON schema, defaults make parameters optional, and the docstring becomes the description the model reasons over. Return a dict so the model gets structure. No decorator involved.

•

Q5. Explain the state prefixes.

No prefix = this session. user: = follows the user across sessions. app: = shared by every user of the app. temp: = this invocation only and never persisted. The prefix alone determines scope — there is no separate API.

•

Q6. Session vs memory?

A session is one conversation with its state; memory is a searchable store across sessions. Session is what the agent has; memory is what it can look up, via the load_memory tool.

•

Q7. How do you evaluate an agent?

Two axes. tool_trajectory_avg_score checks the agent took the right route (default threshold 1.0, exact). response_match_score checks the final answer (default 0.8, similarity-based). Cases live in .test.json / .evalset.json and run from adk eval or pytest via AgentEvaluator.

•

Q8. How do you stop an agent leaking PII to the model?

before_model_callback. Returning an LlmResponse short-circuits the call entirely, so the prompt never leaves your process. The same hook returning a cached response is also the cheapest caching layer available.

•

Q9. MCP and A2A — how do they differ, and how does ADK use both?

MCP connects an agent to tools; A2A connects an agent to other agents. ADK consumes MCP servers via McpToolset and both consumes and exposes A2A agents via RemoteA2aAgent and adk api_server --a2a.

•

Q10. What breaks when you deploy an ADK agent to Cloud Run?

Usually InMemorySessionService. It survives staging and then loses every conversation on the first scale-to-zero. Point --session_service_uri at a real database before taking traffic.

•

Q11. How do you implement human approval?

A LongRunningFunctionTool that returns a pending ticket and suspends the run, or 2.x tool confirmation surfaced on event.actions.requested_tool_confirmations. Either way the human decision arrives out of band and the run resumes.

•

Q12. What changed in ADK 2.0?

Execution became a graph (nodes, edges, node_info/output on events), contexts unified into one Context, the Task API and mode='task' collaboration agents landed, and tool confirmation became first-class. The older workflow agents still work.

19. Gotchas
  1. Extras are not optional in practice. McpToolset needs [mcp], RemoteA2aAgent needs [a2a]. Without them you get ModuleNotFoundError: No module named 'mcp', which reads like a framework bug.
  2. root_agent is a magic name. adk web, adk run and the deployers look for that exact module-level symbol.
  3. Event ignores unknown kwargs. It is configured extra='ignore', so Event(rout="X") silently does nothing. Check event.actions.route, not event.route — route and state are convenience kwargs folded into actions.
  4. temp: state does not persist. Not even to the next turn of the same session.
  5. create_session is async. Forgetting await produces a confusing error later, not at the call site.
  6. run_async yields a lot. Tool calls, partials, state deltas. Filter on event.is_final_response() unless you are deliberately streaming.
  7. A missing docstring silently degrades tool use. The model has nothing to reason about, so it guesses or ignores the tool.
  8. description drives routing. A vague sub-agent description is the usual cause of a coordinator picking the wrong specialist — instruction will not save you.
  9. Unfiltered McpToolset injects every tool the server offers into context. Set tool_filter.
  10. adk web is a dev server. Do not deploy it as your API.
  11. Don't wrap agent execution in a bare except on 2.x. The framework retries; a broad catch hides the failures it is signalling.
  12. Most "ADK 2.0 breaking changes" posts are about Go. Verify against the Python package before rewriting anything.
