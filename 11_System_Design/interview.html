Architect Interview Guide — Staff/Principal Level System Design

Scope: Comprehensive interview preparation for Staff, Principal, and Distinguished Engineer system design interviews. Frameworks for structured thinking, trade-off analysis, architecture decision records, and end-to-end design walkthroughs.

•

Key Definitions (read first)

Term Plain-language definition
Functional vs non-functional requirements What the system does vs how well (scale, latency, availability).
NFRs The "-ilities": scalability, availability, latency, durability, consistency, security.
Capacity estimation Back-of-the-envelope math for QPS, storage, bandwidth to size the system.
QPS Queries per second — the core load number you estimate first.
Availability (the "9s") Uptime target: 99.9% ≈ 8.7h down/yr, 99.99% ≈ 52min/yr.
Latency budget Total response-time target split across components.
Trade-off analysis Explicitly weighing options (consistency vs availability, cost vs latency) — the core Staff+ signal.
ADR Architecture Decision Record — short doc capturing a decision + context + consequences.
Bottleneck The component that caps overall throughput — find it before optimizing.
Single point of failure (SPOF) A component whose failure takes the whole system down — design it out.
Estimation anchors Reusable numbers (cache 0.5ms, SSD 150µs, cross-DC RTT ~50ms) for fast sizing.
Staff+ signal / red flags Driving the design, owning trade-offs (good) vs jumping to solutions, ignoring scale (bad).

1. Interview Framework

  │   Designs systems that scale + operate well              │
  │   Drives the conversation (interviewer is stakeholder)   │

  │   Identifies risks and mitigations proactively           │
  │                                                          │

2. The 4-Step Design Process

STEP 1: REQUIREMENTS & SCOPE (5 min)
  ┌──────────────────────────────────────────────────────────┐
  │ FUNCTIONAL:                                              │
  │   "What are the core use cases?"                         │
  │   "Who are the users? What do they do?"                  │
  │   "What are the inputs and outputs?"                     │
  │                                                          │
  │ NON-FUNCTIONAL:                                          │
  │   "What scale are we designing for?"                     │
  │   "What's the latency requirement?"                      │
  │   "What's more important: consistency or availability?"  │
  │   "Any compliance requirements? (GDPR, HIPAA)"           │
  │                                                          │
  │ CONSTRAINTS:                                             │
  │   "Existing tech stack?"                                 │
  │   "Team size and expertise?"                             │
  │   "Budget constraints?"                                  │
  │   "Timeline — MVP vs full system?"                       │
  │                                                          │
  │ PRO TIP: Write requirements on whiteboard/doc.           │
  │ Refer back to them during design decisions.              │
  └──────────────────────────────────────────────────────────┘

STEP 2: HIGH-LEVEL DESIGN (10 min)
  ┌──────────────────────────────────────────────────────────┐
  │ Draw the main components:                                │
  │   Client → Load Balancer → API Gateway →                 │
  │   Services → Database / Cache / Queue                    │
  │                                                          │
  │ Define APIs:                                             │
  │   POST /api/v1/resource { body }                         │
  │   GET  /api/v1/resource/{id}                             │
  │                                                          │
  │ Data model:                                              │
  │   Key entities, relationships, access patterns           │
  │                                                          │
  │ Data flow:                                               │
  │   Walk through a request end-to-end                      │
  │   "User clicks submit → request hits LB → ..."           │
  │                                                          │
  │ STAFF+ TIP: Propose 2-3 approaches briefly, then pick    │
  │ one with clear reasoning.                                │
  └──────────────────────────────────────────────────────────┘

STEP 3: DETAILED DESIGN (15 min)
  ┌──────────────────────────────────────────────────────────┐
  │ Deep dive into 2-3 critical components:                  │
  │   (Ask interviewer: "Which area should we dig into?")    │
  │                                                          │
  │ For each component:                                      │
  │   - Data storage: schema, partitioning, replication      │
  │   - Algorithms: ranking, matching, deduplication         │
  │   - Scaling: how does this handle 10x, 100x traffic?     │
  │   - Failure modes: what happens when X fails?            │
  │                                                          │
  │ STAFF+ TIP: Proactively address:                         │
  │   - Hot spots and bottlenecks                            │
  │   - Data consistency challenges                          │
  │   - Race conditions and edge cases                       │
  └──────────────────────────────────────────────────────────┘

STEP 4: WRAP-UP (5 min)
  ┌──────────────────────────────────────────────────────────┐
  │ Scaling plan: "As we grow 10x, we'd need to..."          │
  │ Monitoring: "Key metrics I'd track: ..."                 │
  │ Known limitations: "This design doesn't handle..."       │
  │ Future improvements: "Next iteration would add..."       │
  │                                                          │
  │ STAFF+ TIP: Discuss operational readiness:               │
  │   - Deployment strategy (canary, blue-green)             │
  │   - Alerting and on-call implications                    │
  │   - Cost estimate and optimization path                  │
  │   - Team structure to build and operate this             │
  └──────────────────────────────────────────────────────────┘

3. Capacity Estimation Cheat Sheet

KEY NUMBERS TO MEMORIZE:
  ┌──────────────────────────────────────────────────────────┐
  │ LATENCY:                                                 │
  │   L1 cache:          0.5 ns                              │
  │   L2 cache:          7 ns                                │
  │   Main memory:       100 ns                              │
  │   SSD random read:   150 μs                              │
  │   HDD random read:   10 ms                               │
  │   Same datacenter RT: 0.5 ms                             │
  │   Cross-continent RT: 150 ms                             │
  │                                                          │
  │ THROUGHPUT:                                              │
  │   SSD sequential:    1 GB/s                              │
  │   HDD sequential:    100 MB/s                            │
  │   1 Gbps network:    125 MB/s                            │
  │   10 Gbps network:   1.25 GB/s                           │
  │                                                          │
  │ STORAGE:                                                 │
  │   1 char = 1 byte (ASCII) / 2-4 bytes (UTF-8)            │
  │   UUID = 16 bytes (128 bits)                             │
  │   Typical tweet = 140 bytes                              │
  │   Average web page = 2 MB                                │
  │   Average photo = 200 KB (compressed)                    │
  │   1080p video minute = 150 MB                            │
  │                                                          │
  │ SCALE:                                                   │
  │   86,400 seconds/day ≈ 100K                              │
  │   2.5M seconds/month ≈ 2.5M                              │
  │   1M requests/day ≈ 12 requests/second                   │
  │   1B requests/day ≈ 12K requests/second                  │
  └──────────────────────────────────────────────────────────┘

  BACK-OF-ENVELOPE CALCULATION TEMPLATE:
  ┌──────────────────────────────────────────────────────────┐
  │ Given: 100M DAU, each user does 10 actions/day           │
  │                                                          │
  │ QPS: 100M × 10 / 86,400 ≈ 12,000 QPS                     │
  │ Peak QPS: 12,000 × 3 (peak factor) = 36,000 QPS          │
  │                                                          │
  │ Storage (per year):                                      │
  │ 100M × 10 × 365 × 500 bytes/action = 182 TB/year         │
  │                                                          │
  │ Bandwidth:                                               │
  │ 36,000 QPS × 500 bytes = 18 MB/s (negligible)            │
  │                                                          │
  │ TIP: Round aggressively. Precision doesn't matter.       │
  │ 86,400 ≈ 100,000. Goal is order of magnitude.            │
  └──────────────────────────────────────────────────────────┘

  DATABASE QPS BENCHMARKS:
  ┌──────────────────────────────────────────────────────────┐
  │ MySQL/PostgreSQL:   ~5K-10K QPS (single node)            │
  │ Redis:              ~100K QPS (single node)              │
  │ Cassandra:          ~10K-50K writes/s per node           │
  │ DynamoDB:           ~25K RCU/WCU default (auto-scales)   │
  │ Elasticsearch:      ~10K queries/s per node              │
  │ Kafka:              ~1M messages/s per broker            │
  └──────────────────────────────────────────────────────────┘

4. Trade-Off Analysis Framework

THE TRADE-OFF MATRIX:

  For every design decision, explicitly state:
  ┌──────────────────────────────────────────────────────────┐
  │ OPTION A vs OPTION B:                                    │
  │                                                          │
  │ Criteria      │ Option A        │ Option B               │
  │ ──────────────│─────────────────│──────────────────────  │
  │ Consistency   │ Strong          │ Eventual               │
  │ Availability  │ Lower (pauses)  │ Higher (always up)     │
  │ Latency       │ Higher (sync)   │ Lower (async)          │
  │ Complexity    │ Lower           │ Higher                 │
  │ Cost          │ Higher          │ Lower                  │
  │ Ops burden    │ Lower           │ Higher                 │
  │                                                          │
  │ Decision: Option B because our requirements prioritize   │
  │ availability and latency over strict consistency.        │
  │ Mitigation: Add reconciliation job for eventual          │
  │ consistency gaps.                                        │
  └──────────────────────────────────────────────────────────┘

  COMMON TRADE-OFFS:
  ┌──────────────────────────────────────────────────────────┐
  │ 1. SQL vs NoSQL                                          │
  │    SQL: ACID, joins, flexible queries, schema enforced   │
  │    NoSQL: Scale horizontally, flexible schema, fast      │
  │    Decision driver: query patterns + consistency needs   │
  │                                                          │
  │ 2. Push vs Pull (fan-out write vs read)                  │
  │    Push: Fast reads, slow writes, more storage           │
  │    Pull: Slow reads, fast writes, less storage           │
  │    Decision driver: read/write ratio                     │
  │                                                          │
  │ 3. Sync vs Async communication                           │
  │    Sync: Simple, immediate response, tight coupling      │
  │    Async: Decoupled, resilient, complex debugging        │
  │    Decision driver: latency requirement + failure modes  │
  │                                                          │
  │ 4. Monolith vs Microservices                             │
  │    Monolith: Simple, fast dev, single deploy             │
  │    Micro: Independent scaling, team autonomy, complex    │
  │    Decision driver: team size + org structure            │
  │                                                          │
  │ 5. Cache aside vs Write-through                          │
  │    Aside: Simple, stale reads possible                   │
  │    Write-through: Consistent, write latency higher       │
  │    Decision driver: consistency requirement              │
  │                                                          │
  │ 6. CP vs AP (CAP theorem)                                │
  │    CP: Consistent reads, unavailable during partitions   │
  │    AP: Always available, stale reads during partitions   │
  │    Decision driver: business impact of stale vs down     │
  │                                                          │
  │ 7. Batch vs Stream processing                            │
  │    Batch: Higher throughput, higher latency (hours)      │
  │    Stream: Lower latency (seconds), more complex         │
  │    Decision driver: freshness requirement                │
  └──────────────────────────────────────────────────────────┘

5. Architecture Decision Records

ADR TEMPLATE:
  ┌──────────────────────────────────────────────────────────┐
  │ ADR-001: Use PostgreSQL as Primary Database              │
  │                                                          │
  │ Status: Accepted                                         │
  │ Date: 2024-01-15                                         │
  │ Decision Makers: Team leads + Architect                  │
  │                                                          │
  │ Context:                                                 │
  │   We need a primary data store for our order service.    │
  │   Requirements: ACID transactions for financial data,    │
  │   complex queries for reporting, moderate write volume   │
  │   (~5K writes/sec).                                      │
  │                                                          │
  │ Decision:                                                │
  │   Use PostgreSQL with read replicas for reporting.       │
  │                                                          │
  │ Alternatives Considered:                                 │
  │   1. MySQL: Similar but weaker JSON support, less        │
  │      extensible. Our team has more PostgreSQL expertise. │
  │   2. DynamoDB: Better write scaling but no joins, no     │
  │      ACID across items. Reporting would require ETL.     │
  │                                                          │
  │ Consequences:                                            │
  │   + Strong consistency for financial data                │
  │   + Rich query capability for reporting                  │
  │   + Team expertise exists                                │
  │   - Vertical scaling limits (~50K QPS max)               │
  │   - Need to shard if we exceed 10TB                      │
  │   Mitigation: If we outgrow single node, evaluate        │
  │   Citus (distributed PostgreSQL) or CQRS with read store │
  └──────────────────────────────────────────────────────────┘

  │ Demonstrates you consider alternatives                   │
  │ Proves you think about consequences                      │
  │ Signals experience with real-world architecture          │
  │                                                          │
  │ When interviewer asks "Why X?", answer in ADR format:    │
  │ Context → Alternatives → Decision → Reasoning            │

9. Design Walkthrough: URL Shortener

STEP 1: REQUIREMENTS
  ┌──────────────────────────────────────────────────────────┐
  │ Functional:                                              │
  │   - Shorten URL: long URL → short URL                    │
  │   - Redirect: short URL → 301/302 to long URL            │
  │   - Custom aliases (optional)                            │
  │   - Analytics (click count, geo)                         │
  │                                                          │
  │ Non-functional:                                          │
  │   - 100M URLs created/day                                │
  │   - Read-heavy (100:1 read/write ratio)                  │
  │   - Low latency redirect (< 50ms)                        │
  │   - High availability (99.99%)                           │
  │   - URLs expire after configurable TTL                   │
  │                                                          │
  │ Capacity:                                                │
  │   Write: 100M/day ≈ 1,200/sec                            │
  │   Read: 10B/day ≈ 120,000/sec                            │
  │   Storage: 100M × 365 × 5 years × 500 bytes = 91 TB      │
  └──────────────────────────────────────────────────────────┘

STEP 2: HIGH-LEVEL DESIGN
  ┌──────────────────────────────────────────────────────────┐
  │                                                          │
  │   Client → LB → API Servers → Database                   │
  │                      │                                   │
  │                      ├── Cache (Redis)                   │
  │                      └── Analytics (Kafka → OLAP)        │
  │                                                          │
  │   APIs:                                                  │
  │   POST /api/v1/shorten { url, custom_alias?, ttl? }      │
  │   GET  /{short_code} → 301 Redirect                      │
  │   GET  /api/v1/stats/{short_code} → analytics            │
  │                                                          │
  │   Data model:                                            │
  │   urls: { short_code (PK), long_url, user_id,            │
  │           created_at, expires_at }                       │
  └──────────────────────────────────────────────────────────┘

STEP 3: DETAILED DESIGN

  SHORT CODE GENERATION:
  ┌──────────────────────────────────────────────────────────┐
  │ Option A: Hash (MD5/SHA256) + Base62                     │
  │   MD5(long_url) → take first 7 chars → base62            │
  │   Problem: collisions, must check DB                     │
  │                                                          │
  │ Option B: Counter-based (RECOMMENDED)                    │
  │   Auto-increment counter → Base62 encode                 │
  │   7 chars of base62 = 62^7 = 3.5 trillion combinations   │
  │   No collisions!                                         │
  │                                                          │
  │ Counter approach:                                        │
  │   Snowflake ID or distributed counter (ZooKeeper ranges) │
  │   Each server gets a range: Server1 [1-1M],              │
  │   Server2 [1M-2M]. No coordination needed.               │
  │                                                          │
  │ Base62: [0-9a-zA-Z] = 62 characters                      │
  │   7 chars: enough for 3.5T URLs                          │
  └──────────────────────────────────────────────────────────┘

  REDIRECT FLOW:
  ┌──────────────────────────────────────────────────────────┐
  │ GET /abc1234                                             │
  │   → Check Redis cache                                    │
  │   → Cache hit: 301 redirect (cached long URL)            │
  │   → Cache miss: query DB → cache result → 301 redirect   │
  │                                                          │
  │ 301 vs 302:                                              │
  │   301 (Permanent): Browser caches, less server load      │
  │   302 (Temporary): Every request hits server, better for │
  │                     analytics tracking                   │
  │   Decision: 302 if analytics matter, 301 otherwise       │
  └──────────────────────────────────────────────────────────┘

STEP 4: SCALING & OPERATIONS
  ┌──────────────────────────────────────────────────────────┐
  │ Database: Shard by short_code hash                       │
  │ Cache: 80/20 rule — cache top 20% URLs (serve 80% reads) │
  │ Read replicas for read-heavy load                        │
  │ CDN for static redirects (most popular URLs)             │
  │ Analytics: async via Kafka (don't slow redirect path)    │
  │ Monitoring: redirect latency P99, cache hit rate, QPS    │
  └──────────────────────────────────────────────────────────┘

0. System Design Glossary — Key Definitions
Term Definition
API (Application Programming Interface) A contract that defines how two software components communicate. Specifies endpoints, request/response formats, and protocols (REST, gRPC, GraphQL). The "door" through which clients access server functionality.
Load Balancer A device or software that distributes incoming network traffic across multiple servers to ensure no single server is overwhelmed. Improves availability, throughput, and fault tolerance.
Caching Storing frequently accessed data in a fast-access layer (memory) to reduce latency and database load. Data is served from cache instead of recomputing or fetching from the source.
CDN (Content Delivery Network) A geographically distributed network of edge servers that cache and serve static content (images, CSS, JS, videos) from locations closest to the user, reducing latency.
Database Indexing A data structure (typically B-tree or hash) that speeds up data retrieval by creating a sorted reference to rows. Like a book's index — look up a term to find the page, instead of scanning every page.
Pagination Technique to divide large result sets into smaller pages (chunks) so clients receive manageable amounts of data per request instead of millions of rows at once.
Rate Limiting Controlling the number of requests a client can make within a time window. Protects servers from abuse, DoS attacks, and ensures fair resource usage.
Idempotency A property where performing the same operation multiple times produces the same result as performing it once. Critical for safe retries in distributed systems (e.g., charging a credit card exactly once).
Replication Copying data across multiple servers (replicas) so if one server dies, others have the same data. Improves read performance (read from replicas) and fault tolerance.
Sharding (Partitioning) Splitting data across multiple databases/servers so each holds a subset. Enables horizontal scaling — no single database stores all data.
Message Queue A middleware that decouples producers from consumers. Producer sends messages to a queue; consumer processes them asynchronously. Enables async processing, load leveling, and fault tolerance.
Kafka A distributed event streaming platform. Unlike traditional queues, Kafka retains messages in a persistent log. Multiple consumers can read independently, and messages can be replayed.
Microservices An architecture where an application is built as a collection of small, independent services, each owning its data and deployable separately. Opposite of monolith.
Distributed Locking A mechanism to ensure only one process/service can access a shared resource at a time across multiple servers. Prevents race conditions in distributed systems.
Consistent Hashing A technique to distribute data across nodes such that adding/removing a node only requires moving a small fraction of data, not reshuffling everything.
Circuit Breaker A pattern that stops calling a failing service after repeated failures, returning a fallback response instead. Prevents cascading failures across services.
Backpressure A mechanism where a overwhelmed downstream service signals upstream to slow down, preventing system overload.
Eventual Consistency A consistency model where reads may temporarily return stale data, but all replicas will converge to the same value eventually (typically within milliseconds to seconds).
Strong Consistency A consistency model where every read returns the most recent write. All clients see the same data at the same time. Requires coordination (slower).
CAP Theorem In a distributed system experiencing a network partition, you must choose between Consistency (all nodes see same data) and Availability (every request gets a response). You cannot have both during a partition.
ACID Properties of reliable database transactions: Atomicity (all or nothing), Consistency (valid state transitions), Isolation (concurrent transactions don't interfere), Durability (committed data survives crashes).
BASE Properties of NoSQL systems: Basically Available (system always responds), Soft state (state may change over time), Eventually consistent (replicas converge). Trade-off: weaker guarantees for higher availability.
SLA / SLO / SLI SLA (Service Level Agreement): contractual uptime promise. SLO (Service Level Objective): internal target (e.g., 99.9% uptime). SLI (Service Level Indicator): actual measured metric (e.g., error rate).
Fan-out The process of distributing a single event to multiple recipients. Fan-out on write: pre-compute at write time. Fan-out on read: compute at read time.
Saga Pattern Managing distributed transactions as a sequence of local transactions, each with a compensating action for rollback. Used when you can't do ACID across services.
Outbox Pattern Writing business data and events in the same database transaction (to an "outbox" table), then publishing events separately. Guarantees consistency between data and events.
Dead Letter Queue (DLQ) A queue where messages that can't be processed after multiple retries are sent. Allows debugging failed messages without blocking the main queue.
Quorum The minimum number of nodes that must agree for a distributed operation to succeed. Typically: W + R > N ensures consistency (W=write quorum, R=read quorum, N=replicas).
WAL (Write-Ahead Log) Before modifying data, write the intended change to a log file first. If the system crashes, replay the log to recover. Foundation of database durability.
Tombstone A marker indicating deleted data in systems that don't immediately remove records (e.g., Cassandra, LSM-trees). Actual deletion happens during compaction.
Hot Spot / Hot Key A partition or key that receives disproportionately high traffic, causing that server to become a bottleneck while others sit idle.
Thundering Herd When many clients simultaneously retry or request the same resource (e.g., cache expires → thousands of DB queries at once). Mitigate with jitter, locking, or staggered TTLs.

Q3. Explain the CAP theorem.

In a distributed system, you can only guarantee 2 of 3: Consistency (all nodes see same data), Availability (every request gets a response), Partition Tolerance (system works despite network failures). In practice, P is always present, so choose between CP (strong consistency) and AP (high availability).

•

Q4. What is consistent hashing?

Distributes data across nodes on a virtual ring. Adding/removing a node only affects neighbors, not all data. Used in: distributed caches (Memcached), databases (Cassandra), CDNs. Virtual nodes improve balance.

•

Q5. Explain the difference between latency and throughput.

Latency: time to complete one request. Throughput: requests per second. Often tradeoffs: batching increases throughput but increases latency. Optimize for whichever your SLA requires.

•

Q6. What is a reverse proxy?

Sits between clients and servers. Functions: load balancing, SSL termination, caching, compression, rate limiting, security. Examples: Nginx, HAProxy, Envoy.

•

Q7. Explain stateless vs stateful services.

Q11. Explain rate limiting strategies in detail.

Rate limiting controls how many requests a client can make in a given time window. Protects against abuse, DDoS, and ensures fair usage.

STRATEGIES EXPLAINED:

1. TOKEN BUCKET (most popular — used by Stripe, AWS):
   Bucket holds max N tokens. Tokens refill at rate R/sec.
   Each request takes 1 token. Empty bucket = rejected (429).
   ✓ Allows bursts (up to bucket size)
   ✓ Smooth average rate over time

   Time 0: [T][T][T][T][T]  (5 tokens, bucket full)
   Req 1:  [T][T][T][T][ ]  (4 tokens left)
   Req 2:  [T][T][T][ ][ ]  (3 tokens left)
   +1 sec: [T][T][T][T][ ]  (refilled 1 token)

2. LEAKY BUCKET:
   Requests enter a queue (bucket). Processed at fixed rate.
   If queue full, new requests are dropped.
   ✓ Perfectly smooth output rate
   ✗ Cannot handle bursts at all

3. FIXED WINDOW:
   Count requests in fixed time windows (e.g., per minute).
   Window 12:00-12:01: max 100 requests.
   ✗ Problem: 100 requests at 12:00:59 + 100 at 12:01:00
     = 200 requests in 2 seconds (boundary burst)

4. SLIDING WINDOW LOG:
   Track timestamp of each request. Count requests in
   last N seconds. Most precise but memory-heavy.
   ✓ No boundary burst problem
   ✗ Stores every request timestamp

5. SLIDING WINDOW COUNTER:
   Weighted average of current + previous window.
   requests = prev_window_count * overlap% + current_count
   ✓ Low memory, smooth limiting
   ✓ Best balance of accuracy and efficiency

Python Implementation — Token Bucket (RPM + TPM Rate Limiter): 

import time
import threading


class TokenBucketRateLimiter:
    """
    Rate limiter using Token Bucket algorithm.
    Supports both RPM (requests per minute) and TPM (tokens per minute).
    Thread-safe for production use.
    """

    def __init__(self, max_tokens: int, refill_rate: float):
        """
        Args:
            max_tokens: Maximum tokens in the bucket (burst capacity)
            refill_rate: Tokens added per second
        """
        self.max_tokens = max_tokens
        self.refill_rate = refill_rate
        self.tokens = max_tokens
        self.last_refill = time.monotonic()
        self.lock = threading.Lock()

    def _refill(self):
        """Add tokens based on elapsed time since last refill."""
        now = time.monotonic()
        elapsed = now - self.last_refill
        tokens_to_add = elapsed * self.refill_rate
        self.tokens = min(self.max_tokens, self.tokens + tokens_to_add)
        self.last_refill = now

    def consume(self, tokens: int = 1) -> bool:
        """
        Try to consume tokens. Returns True if allowed, False if rate limited.

        Args:
            tokens: Number of tokens to consume (1 for RPM, N for TPM)
        """
        with self.lock:
            self._refill()
            if self.tokens >= tokens:
                self.tokens -= tokens
                return True
            return False

    def wait_and_consume(self, tokens: int = 1, timeout: float = 60.0) -> bool:
        """
        Block until tokens are available, then consume.
        Returns False if timeout exceeded.
        """
        deadline = time.monotonic() + timeout
        while time.monotonic() < deadline:
            if self.consume(tokens):
                return True
            # Sleep until at least 1 token is available
            with self.lock:
                self._refill()
                wait_time = max(0, (tokens - self.tokens) / self.refill_rate)
            time.sleep(min(wait_time + 0.01, deadline - time.monotonic()))
        return False

class DualRateLimiter:
    """
    Enforces BOTH RPM and TPM limits (like OpenAI API).
    A request must pass BOTH limiters to proceed.
    """

    def __init__(self, rpm: int, tpm: int):
        self.rpm_limiter = TokenBucketRateLimiter(
            max_tokens=rpm,
            refill_rate=rpm / 60
        )
        self.tpm_limiter = TokenBucketRateLimiter(
            max_tokens=tpm,
            refill_rate=tpm / 60
        )

    def consume(self, token_count: int = 1) -> dict:
        rpm_ok = self.rpm_limiter.consume(tokens=1)       # 1 request
        tpm_ok = self.tpm_limiter.consume(tokens=token_count)  # N tokens

        allowed = rpm_ok and tpm_ok
        if not allowed:
            # Refund if one passed but other didn't
            if rpm_ok and not tpm_ok:
                self.rpm_limiter.tokens += 1  # refund the request
            if tpm_ok and not rpm_ok:
                self.tpm_limiter.tokens += token_count  # refund tokens

        return {
            "allowed": allowed,
            "rpm_ok": rpm_ok,
            "tpm_ok": tpm_ok,
            "reason": "OK" if allowed else
                      ("RPM exceeded" if not rpm_ok else "TPM exceeded")
        }

Redis-based Distributed Rate Limiter (Sliding Window): 

import time
import redis

r = redis.Redis(host='localhost', port=6379)

def is_rate_limited(user_id: str, max_requests: int = 60,
                    window_seconds: int = 60) -> bool:
    """
    Sliding window rate limiter using Redis sorted sets.
    Returns True if the request should be BLOCKED.
    """
    key = f"rate_limit:{user_id}"
    now = time.time()
    window_start = now - window_seconds

    pipe = r.pipeline()
    pipe.zremrangebyscore(key, 0, window_start)  # Remove old entries
    pipe.zadd(key, {f"{now}": now})               # Add current request
    pipe.zcard(key)                                # Count requests in window
    pipe.expire(key, window_seconds)               # Auto-cleanup
    results = pipe.execute()

    request_count = results[2]
    return request_count > max_requests

# Usage:
if is_rate_limited("user_123", max_requests=60, window_seconds=60):
    print("429 Too Many Requests")
else:
    print("200 OK")

Q51. Name the caching strategies and explain when to use each.

Cache Eviction PoliciesLRULFUFIFOTTLRandom

Caching stores frequently accessed data in a fast-access layer (usually RAM) to reduce latency and database load. Instead of computing or fetching from disk, serve from memory.

CACHE-ASIDE (Lazy Loading) — Most Common:
  App ──► Check Cache ──► HIT? → Return cached data (1ms)
                       └─► MISS? → Query DB (50ms) → Write to cache → Return

  ✓ Only caches what's actually requested (no wasted memory)
  ✓ Cache failure doesn't break the app (falls back to DB)
  ✗ First request is always slow (cache miss)
  ✗ Data can become stale (mitigate with TTL)
  When: Most read-heavy workloads. Default choice.

WRITE-THROUGH:
  App ──► Write to Cache ──► Cache writes to DB ──► Return

  ✓ Cache is always up-to-date (strong consistency)
  ✗ Higher write latency (write to 2 places)
  ✗ May cache data that's never read (wasted memory)
  When: Read-heavy + consistency required. E-commerce product catalog.

WRITE-BEHIND (Write-Back):
  App ──► Write to Cache ──► Return immediately
                               (async) ──► Cache writes to DB later

  ✓ Fastest writes (no DB wait)
  ✓ Batches DB writes (reduces DB load)
  ✗ Risk: data loss if cache crashes before DB write
  When: Write-heavy, loss-tolerant. Analytics, view counters.

READ-THROUGH:
  App ──► Read from Cache ──► Cache auto-loads from DB on miss ──► Return

  Like cache-aside but the cache library handles DB loading.
  When: Simpler application code. Used with Hibernate, ORM caches.

REFRESH-AHEAD:
  Cache proactively refreshes entries BEFORE they expire.
  Monitor access patterns, pre-fetch popular keys.
  When: Hot data that must always be warm (e.g., homepage feed).

Cache-Aside Eventual Normal Fast (after warm) None
Write-Through Strong Slow Always fast None
Write-Behind Eventual Fastest Always fast Yes (cache crash)

Q72. When would you use Kafka? How does it work internally?

When to use KafkaWhen NOT to use

Kafka is a distributed event streaming platform — a persistent, ordered, replayable log of events.

KAFKA ARCHITECTURE:

  Producer ──► Topic: "orders" ──► Consumer Group A (Order Service)
                  │                ──► Consumer Group B (Analytics)
                  │                ──► Consumer Group C (Notification)
                        │
            ┌─────┴─────┐
            │ Partitions│
            │ P0: [1][2][3][4]  ◄─ ordered within partition
            │ P1: [1][2][3]     ◄─ partition key = order_id hash
            │ P2: [1][2][3][4][5]
            └───────────┘

KEY CONCEPTS:
  Topic:     Category of messages (like a DB table name)
  Partition: Ordered, immutable sequence of messages. Unit of parallelism.
  Offset:    Unique ID of a message within a partition (auto-incrementing)
  Consumer Group: Consumers that share the work. Each partition consumed by
                  exactly ONE consumer in a group. More partitions = more parallelism.
  Broker:    A Kafka server. Cluster = multiple brokers. Partitions replicated across brokers.
  Retention: Messages kept for configurable period (default 7 days) or forever.

When to use Kafka: High-throughput event streaming, log aggregation, real-time analytics, CDC (change data capture), event sourcing, microservice communication backbone. When you need: message replay, multiple consumers, ordered processing, durable storage. When NOT to use: Simple task queues (use SQS), low-throughput with few consumers (overkill), request-reply patterns (use gRPC/REST).

Q73. Explain pub-sub pattern.

Publisher sends messages to a topic. Multiple subscribers receive all messages on that topic. Decouples producers from consumers. Used in: notifications, event-driven systems, fan-out pattern.

•

Q74. What is exactly-once delivery? Is it achievable?

Guarantee: each message processed exactly once. Hard in distributed systems. Strategies: idempotent consumers + at-least-once delivery, transactional outbox pattern, Kafka transactions.

•

Q75. How to handle message ordering?

Kafka: ordered within a partition (use same key for related messages). SQS FIFO: ordered within message group. Global ordering: single partition/queue (limits throughput).

•

Q76. Explain the outbox pattern.

Store events in an 'outbox' table within the same transaction as business logic. Separate process reads outbox and publishes to message broker. Ensures atomicity between DB change and event publication.

Q92. How to design RESTful APIs?

REST (Representational State Transfer) uses HTTP methods on resource URLs.

RESTful API DESIGN RULES:

  Resources are NOUNS (not verbs):
  ✓ GET    /api/v1/users              → List users
  ✓ POST   /api/v1/users              → Create user
  ✓ GET    /api/v1/users/123          → Get user 123
  ✓ PUT    /api/v1/users/123          → Replace user 123
  ✓ PATCH  /api/v1/users/123          → Partial update user 123
  ✓ DELETE /api/v1/users/123          → Delete user 123
  ✗ POST   /api/v1/getUser            → BAD (verb in URL)
  ✗ GET    /api/v1/deleteUser/123     → BAD (verb + wrong method)

  Nested resources for relationships:
  GET /api/v1/users/123/orders         → Orders belonging to user 123
  GET /api/v1/users/123/orders/456     → Specific order of user 123

  HTTP STATUS CODES:
  200 OK              → Successful GET/PUT/PATCH
  201 Created         → Successful POST (include Location header)
  204 No Content      → Successful DELETE
  400 Bad Request     → Invalid input (validation error)
  401 Unauthorized    → Not authenticated (no/bad token)
  403 Forbidden       → Authenticated but not authorized
  404 Not Found       → Resource doesn't exist
  409 Conflict        → Resource state conflict (duplicate)
  429 Too Many Req    → Rate limited
  500 Internal Error  → Server bug (never expose stack traces!)

  FILTERING, SORTING, PAGINATION:
  GET /api/v1/users?status=active&sort=-created_at&limit=20&cursor=abc123

Q94. What is the API gateway pattern?

Single entry point for all client requests. Handles cross-cutting concerns so individual services don't have to.

Client ──► API GATEWAY ──┬─► User Service
                       ├─► Order Service
                       ├─► Payment Service
                       └─► Notification Service

  Gateway handles:
  ✓ Routing:          /api/users → User Service, /api/orders → Order Service
  ✓ Authentication:   Validate JWT before forwarding
  ✓ Rate Limiting:    100 req/min per API key
  ✓ SSL Termination:  HTTPS → HTTP internally
  ✓ Request Transform: Add headers, modify body
  ✓ Response Aggregation: Merge responses from multiple services
  ✓ Circuit Breaking: Stop calling failing service
  ✓ Logging/Metrics:  Centralized request tracking

  Examples: Kong, AWS API Gateway, Envoy, Nginx, Traefik

Q96. Explain the saga pattern in detail.

Manages distributed transactions across multiple services when you can't use a single ACID transaction.

PROBLEM: E-commerce checkout needs:
  1. Reserve inventory (Inventory Service)
  2. Charge payment (Payment Service)
  3. Ship order (Shipping Service)
  These are 3 different databases. No single ACID transaction possible!

SAGA = sequence of local transactions + compensating actions:

  CHOREOGRAPHY (event-driven, no coordinator):
  Inventory ── Reserved ──► Payment ── Charged ──► Shipping ── Shipped
       │                        │                       │
       ◄── UnReserve ──────── ◄── Refund ─────────── (if failure)
  (compensating actions roll back on failure)

  ORCHESTRATION (central coordinator):
  Saga Orchestrator ─► Step 1: Reserve Inventory
                    ─► Step 2: Charge Payment
                    ─► Step 3: Ship Order
                    If Step 2 fails: call compensate Step 1 (unreserve)

  Choreography: simpler for few steps, decoupled. Hard to debug.
  Orchestration: clearer flow, easier debugging. Single point of failure.

Q97. How to handle distributed tracing?

In microservices, one user request may hit 10+ services. When something is slow, which service is the bottleneck?

DISTRIBUTED TRACING:

  User request → API Gateway → User Service → Order Service → DB
       |           12ms          45ms           30ms          5ms
       |───────────────────── Total: 92ms ─────────────────|

  HOW IT WORKS:
  1. Gateway generates Trace ID: "abc-123" + Span ID: "span-1"
  2. Passes in header: X-Trace-Id: abc-123
  3. Each service creates child span with parent reference
  4. All spans collected and assembled into a trace tree

  TOOLS: Jaeger, Zipkin, OpenTelemetry (standard), Datadog APM
  STANDARD: OpenTelemetry (vendor-neutral, industry standard)
    - Traces (request flow)
    - Metrics (counters, gauges, histograms)
    - Logs (correlated with trace IDs)

Program 901: Observer Pattern — ML Training Monitor

Subject broadcasts events to many observers; it doesn't know what each one does. 

            Subject (TrainingMonitor)
          notify(event, data)
        ┌─────────────┼──────────────┐
        ▼             ▼              ▼
     Logger      Checkpoint      "complete!"
   (epoch_end)  (acc>0.8 →save)  (train_end)
   → add/remove observers freely; Subject stays unchanged
class TrainingMonitor:
    def __init__(self):
        self.observers = []
    
    def subscribe(self, observer):
        self.observers.append(observer)
    
    def notify(self, event, data):
        for obs in self.observers:
            obs(event, data)
    
    def train(self, epochs=5):
        for epoch in range(1, epochs + 1):
            loss = 1.0 / epoch
            acc = 1 - loss
            self.notify("epoch_end", {"epoch": epoch, "loss": loss, "accuracy": acc})
        self.notify("train_end", {"total_epochs": epochs})

monitor = TrainingMonitor()
monitor.subscribe(lambda e, d: print(f"  Logger: {e} → {d}") if e == "epoch_end" else None)
monitor.subscribe(lambda e, d: print(f"  Checkpoint: Saving model") if e == "epoch_end" and d.get("accuracy", 0) > 0.8 else None)
monitor.subscribe(lambda e, d: print(f"  ✓ Training complete!") if e == "train_end" else None)
monitor.train(5)

Program 902: Strategy Pattern — Model Selection

        ModelStrategy (context)

            │ selects one at runtime
       ┌────┴─────┐

class ModelStrategy:

        self.strategies = {}

Program 903: Factory Pattern — Data Loader

   create("csv")    ─┐
   create("json")   ─┤►  DataLoaderFactory  ──►  CSVLoader / JSONLoader / ParquetLoader
   create("parquet")─┘     (registry: name→class)        (concrete product)

class DataLoaderFactory:
    _loaders = {}
    
    @classmethod
    def register(cls, format_name, loader_class):
        cls._loaders[format_name] = loader_class
    
    @classmethod
    def create(cls, format_name, **kwargs):
        if format_name not in cls._loaders:
            raise ValueError(f"Unknown format: {format_name}")
        return cls._loaders[format_name](**kwargs)

Program 905: Decorator Pattern — Pipeline Steps

Wrap an object to add behavior while keeping the same interface. 

   Normalization( OutlierRemoval( LogTransform( data ) ) )
        outer ──────────► inner ──────────► innermost
   process() flows inward →, each layer adds one transform on the way out ←
   → stack/reorder transforms without changing any class
class PipelineStep:
    def process(self, data):
        return data

class NormalizationStep(PipelineStep):
    def __init__(self, wrapped=None):
        self.wrapped = wrapped
    def process(self, data):
        if self.wrapped:
            data = self.wrapped.process(data)
        mean = sum(data) / len(data)
        std = (sum((x - mean)**2 for x in data) / len(data)) ** 0.5
        return [(x - mean) / (std + 1e-8) for x in data]

class OutlierRemovalStep(PipelineStep):
    def __init__(self, wrapped=None, threshold=2):
        self.wrapped = wrapped
        self.threshold = threshold
    def process(self, data):
        if self.wrapped:
            data = self.wrapped.process(data)
        mean = sum(data) / len(data)
        std = (sum((x - mean)**2 for x in data) / len(data)) ** 0.5
        return [x for x in data if abs(x - mean) <= self.threshold * std]

class LogTransformStep(PipelineStep):
    def __init__(self, wrapped=None):
        self.wrapped = wrapped
    def process(self, data):
        if self.wrapped:
            data = self.wrapped.process(data)
        import math
        return [math.log(x + 1) for x in data]

# Chain decorators
pipeline = NormalizationStep(OutlierRemovalStep(LogTransformStep()))
data = [1, 2, 3, 100, 4, 5, 6, 200, 7, 8]
result = pipeline.process(data)
print(f"Input:  {data}")
print(f"Output: {[round(x, 4) for x in result]}")

Program 907: Proxy Pattern — Model Cache

A stand-in with the same interface that controls access (here: caching + lazy load). 

   client.predict() ─►  ModelProxy  ─►  cache fresh?  ─yes─►  cached_model
                            │                └──no──►  load model → store → use
   → caller sees the real model's API; proxy adds caching/TTL transparently
import time

class ModelProxy:
    def __init__(self, model_loader, cache_ttl=60):
        self.model_loader = model_loader
        self.cache_ttl = cache_ttl
        self.cached_model = None
        self.load_time = 0
        self.request_count = 0
    
    def _get_model(self):
        if self.cached_model is None or time.time() - self.load_time > self.cache_ttl:
            print("  Loading model...")
            self.cached_model = self.model_loader()
            self.load_time = time.time()
        return self.cached_model
    
    def predict(self, X):
        self.request_count += 1
        model = self._get_model()
        return model(X)

proxy = ModelProxy(
    lambda: (lambda X: [x * 2 for x in X]),
    cache_ttl=300

Program 908: Command Pattern — Experiment Tracker

Encapsulate an action (and its undo) as an object — so you can log, queue, replay, undo. 

   ExperimentCommand{ execute_fn, undo_fn, params }
              │ tracker.run(cmd)
   Tracker ─► cmd.execute() ─► history[] ──undo_last()──► cmd.undo()
   → actions become first-class data, not just function calls
class ExperimentCommand:
    def __init__(self, name, params, execute_fn, undo_fn=None):
        self.name = name
        self.params = params
        self.execute_fn = execute_fn
        self.undo_fn = undo_fn
        self.result = None
    
    def execute(self):
        self.result = self.execute_fn(self.params)
        return self.result
    
    def undo(self):
        if self.undo_fn:
            self.undo_fn(self.params)

class ExperimentTracker:
    def __init__(self):
        self.history = []
    
    def run(self, command):
        result = command.execute()
        self.history.append(command)
        print(f"  Ran: {command.name} → {result}")
        return result
    
    def undo_last(self):
        if self.history:
            cmd = self.history.pop()
            cmd.undo()
            print(f"  Undone: {cmd.name}")
    
    def report(self):
        return [{"name": c.name, "params": c.params, "result": c.result} for c in self.history]

tracker = ExperimentTracker()
tracker.run(ExperimentCommand("train_lr_0.001", {"lr": 0.001}, lambda p: {"acc": 0.85, **p}))
tracker.run(ExperimentCommand("train_lr_0.01", {"lr": 0.01}, lambda p: {"acc": 0.92, **p}))
print(f"Experiments: {tracker.report()}")

Program 909: Chain of Responsibility — Data Validator

Pass the request along a chain until a handler deals with it. 

   data ─► TypeValidator ─► RequiredFields ─► RangeValidator ─► ✓ valid
              │ fail            │ fail            │ fail
              └── return error (stop)   each handler: handle, or pass to .next
   → add/remove/reorder checks without touching the others
class ValidationHandler:
    def __init__(self):
        self.next = None
    
    def set_next(self, handler):
        self.next = handler
        return handler
    
    def handle(self, data):
        result = self.validate(data)
        if result is not None:
            return result
        if self.next:
            return self.next.handle(data)
        return None
    
    def validate(self, data):
        raise NotImplementedError

class TypeValidator(ValidationHandler):
    def validate(self, data):
        if not isinstance(data, dict):

Program 911: Composite Pattern — Feature Engineering

Treat a single item and a group of items the same way (a tree). 

   FeaturePipeline (composite)
     ├─ NormalizeFeature (leaf)
     └─ BinFeature       (leaf)
   transform() on the pipeline calls transform() on each child — same interface

class FeatureTransform:
    def transform(self, data):
        raise NotImplementedError
    def __repr__(self):
        return self.__class__.__name__

class NormalizeFeature(FeatureTransform):
    def transform(self, data):
        mean = sum(data) / len(data)
        std = max((sum((x-mean)**2 for x in data)/len(data))**0.5, 1e-8)
        return [round((x-mean)/std, 4) for x in data]

class BinFeature(FeatureTransform):
    def __init__(self, bins=4):
        self.bins = bins
    def transform(self, data):
        mn, mx = min(data), max(data)
        width = (mx - mn) / self.bins
        return [min(int((x-mn)/width), self.bins-1) for x in data]

        self.name = name
        self.steps = []
    def add(self, step):
        self.steps.append(step)
        return self
    def transform(self, data):
        for step in self.steps:
            data = step.transform(data)
        return data

Program 913: Producer-Consumer Pattern

Decouple fast/slow parties through a bounded queue (backpressure built in). 

   Producer ──put──► [ Queue(maxsize=5) ] ──get──► Consumer 1
                            (buffer)         └─get─► Consumer 2
   → each runs at its own pace; full queue blocks the producer (backpressure)

import threading
import time

def producer(q, items):
    for item in items:
        q.put(item)
        print(f"  Produced: {item}")

def consumer(q, name):
    results = []
    while True:
        item = q.get()
        if item is None:
            q.put(None)  # Pass sentinel to next consumer
            break
        result = item ** 2
        results.append(result)
        print(f"  {name} consumed {item} → {result}")
    return results

class Specification:
    def is_satisfied(self, item):
        raise NotImplementedError
    def __and__(self, other):
        return AndSpec(self, other)
    def __or__(self, other):
        return OrSpec(self, other)
    def __invert__(self):
        return NotSpec(self)

    def __init__(self, *specs):
        self.specs = specs
    def is_satisfied(self, item):

    def __init__(self, *specs):

Program 918: Saga Pattern — Distributed Transaction

No global lock — each step has a compensating action that undoes it. 

   Step1 ✓ ─► Step2 ✓ ─► Step3 ✗ (fail)
     │           │
     └───────────┴── compensate in REVERSE: undo Step2, then undo Step1
   → eventual consistency across services without a 2-phase-commit lock
class Saga:
    def __init__(self):
        self.steps = []
        self.compensations = []
    
    def add_step(self, execute, compensate):
        self.steps.append(execute)
        self.compensations.append(compensate)
        return self
    
    def execute(self):
        completed = []
        try:
            for i, step in enumerate(self.steps):
                result = step()
                completed.append(i)
                print(f"  Step {i+1}: {result}")
            return True
        except Exception as e:
            print(f"  Failed at step {len(completed)+1}: {e}")
            # Compensate in reverse order
            for i in reversed(completed):
                self.compensations[i]()
                print(f"  Compensated step {i+1}")
            return False

Program 919: Circuit Breaker with Health Metrics

Stop hammering a failing dependency — fail fast, then probe for recovery. 

   CLOSED ──failure rate ≥ threshold──► OPEN ──cooldown elapsed──► HALF_OPEN
     ▲                                  (fail fast)                    │
     └───────────────── success ◄──────────────────────────── trial call
   → protects the caller and gives the sick service room to recover
import time
from collections import deque

class AdvancedCircuitBreaker:
    def __init__(self, failure_rate_threshold=0.5, window_size=10, cooldown=5):
        self.failure_rate_threshold = failure_rate_threshold
        self.window_size = window_size
        self.cooldown = cooldown
        self.results = deque(maxlen=window_size)
        self.state = "closed"
        self.open_time = None
    
    def _failure_rate(self):
        if not self.results:
            return 0.0
        return sum(1 for r in self.results if not r) / len(self.results)
    
    def call(self, func, *args):
        if self.state == "open":
            if time.time() - self.open_time > self.cooldown:
                self.state = "half_open"
            else:
                raise RuntimeError(f"Circuit OPEN (failure rate: {self._failure_rate():.0%})")
        
        try:
            result = func(*args)
            self.results.append(True)
            if self.state == "half_open":
                self.state = "closed"
            return result
        except Exception as e:
            self.results.append(False)
            if self._failure_rate() >= self.failure_rate_threshold:
                self.state = "open"
                self.open_time = time.time()
            raise
    
    def metrics(self):
        return {
            "state": self.state,
            "failure_rate": f"{self._failure_rate():.0%}",
            "window": len(self.results)
        }

        else:
            cb.call(lambda: "ok")
    except Exception as e:
        pass
    print(f"  Call {i+1}: {cb.metrics()}")

Program 920: Pub/Sub with Topic Filtering

Publishers and subscribers are decoupled; the broker routes by topic pattern. 

   publish("model.trained") ─►  broker matches patterns  ─►  subs of "model.*"
                                                          └►  subs of "model.trained"
   → publishers don't know who listens; subscribe/unsubscribe at will
import re
from collections import defaultdict

class PubSub:
    def __init__(self):
        self.subscribers = defaultdict(list)
    
    def subscribe(self, pattern, callback):
        self.subscribers[pattern].append(callback)
    
    def publish(self, topic, data):
        for pattern, callbacks in self.subscribers.items():
            if re.match(pattern.replace('*', '.*'), topic):
                for cb in callbacks:
                    cb(topic, data)
    
    def unsubscribe(self, pattern, callback=None):
        if callback:
            self.subscribers[pattern].remove(callback)
        else:
            del self.subscribers[pattern]

class WriteAheadLog:
    def __init__(self):
        self.log = []
        self.committed = set()
    def write(self, tx_id, operation, data):
        entry = {"tx_id": tx_id, "op": operation, "data": data, "status": "pending"}
        self.log.append(entry)
        return len(self.log) - 1

        for entry in self.log:
            if entry["tx_id"] == tx_id:
                entry["status"] = "committed"
    def recover(self):
        uncommitted = [e for e in self.log if e["status"] == "pending"]
        return uncommitted

import hashlib
class ScalableBloomFilter:
    def __init__(self, expected_items=1000, fp_rate=0.01):
        import math
        self.size = int(-expected_items * math.log(fp_rate) / (math.log(2)**2))
        self.num_hashes = int(self.size / expected_items * math.log(2))
        self.bits = bytearray(self.size // 8 + 1)
    def _hashes(self, item):
        for i in range(self.num_hashes):
            h = int(hashlib.sha256(f"{item}:{i}".encode()).hexdigest(), 16) % self.size
            yield h
    def add(self, item):
        for h in self._hashes(item):
            self.bits[h // 8] |= (1 << (h % 8))
    def __contains__(self, item):
        return all(self.bits[h // 8] & (1 << (h % 8)) for h in self._hashes(item))

import threading, time
class DistributedLock:
    def __init__(self):
        self.locks = {}
        self._lock = threading.Lock()
    def acquire(self, resource, owner, ttl=10):
        with self._lock:
            if resource in self.locks:
                lock_info = self.locks[resource]
                if time.time() - lock_info["acquired_at"] > lock_info["ttl"]:
                    pass  # Lock expired
                elif lock_info["owner"] != owner:
                    return False
            self.locks[resource] = {"owner": owner, "acquired_at": time.time(), "ttl": ttl}
            return True
    def release(self, resource, owner):
        with self._lock:
            if self.locks.get(resource, {}).get("owner") == owner:
                del self.locks[resource]
                return True
            return False

        self.dlq = []
        self.max_retries = 3

class OnlineLearner:
    def __init__(self):
        self.weights = None
        self.lr = 0.01
        self.samples_seen = 0
    def partial_fit(self, x, y):
        if self.weights is None:
            self.weights = [0.0] * len(x)
        pred = sum(w*xi for w, xi in zip(self.weights, x))
        error = y - pred
        self.weights = [w + self.lr * error * xi for w, xi in zip(self.weights, x)]
        self.samples_seen += 1
        return pred

import random
class WorkStealer:
    def __init__(self, num_workers):
        self.queues = {i: [] for i in range(num_workers)}
    def submit(self, task, worker=None):
        target = worker if worker is not None else random.randint(0, len(self.queues)-1)
        self.queues[target].append(task)
    def steal(self, idle_worker):
        for w, q in self.queues.items():
            if w != idle_worker and len(q) > 1:
                stolen = q.pop()
                self.queues[idle_worker].append(stolen)
                return True
        return False
    def status(self):
        return {w: len(q) for w, q in self.queues.items()}

def parallel_stages(num_workers, stages):

            result = stage(worker_id)

class RingBuffer:

        self.buffer = [None] * capacity
        self.head = 0
        self.size = 0
        self.capacity = capacity

        idx = (self.head + self.size) % self.capacity
        self.buffer[idx] = item
        if self.size < self.capacity:
            self.size += 1
        else:
            self.head = (self.head + 1) % self.capacity

        return [self.buffer[(self.head + i) % self.capacity] for i in range(self.size)]

class ChaosTest:

        self.system_fn = system_fn
    def inject_latency(self, request, delay=0.5):
        time.sleep(delay * 0.001)

        if random.random() < rate:
            raise RuntimeError("Chaos: Injected failure!")
        return self.system_fn(request)
    def run_test(self, requests, failure_rate=0.2):
        successes = 0
        for req in requests:
            try:
                self.inject_failure(req, failure_rate)
                successes += 1
            except RuntimeError:
                pass
        return {"total": len(requests), "success": successes, "rate": successes/len(requests)}

# 996: Migration runner
class MigrationRunner:
    def __init__(self):
        self.migrations = []
        self.applied = set()
    def add(self, version, up_fn, down_fn):
        self.migrations.append({"version": version, "up": up_fn, "down": down_fn})
    def migrate(self):
        for m in sorted(self.migrations, key=lambda x: x["version"]):
            if m["version"] not in self.applied:
                m["up"]()
                self.applied.add(m["version"])
                print(f"  Applied: v{m['version']}")
    def rollback(self, to_version):
        for m in sorted(self.migrations, key=lambda x: -x["version"]):
            if m["version"] > to_version and m["version"] in self.applied:
                m["down"]()
                self.applied.discard(m["version"])
                print(f"  Rolled back: v{m['version']}")
mr = MigrationRunner()
mr.add(1, lambda: None, lambda: None)
mr.add(2, lambda: None, lambda: None)
mr.add(3, lambda: None, lambda: None)
mr.migrate()
mr.rollback(1)

def generate_release_notes(commits):
    categories = {"feat": [], "fix": [], "docs": [], "refactor": [], "other": []}
    for commit in commits:
        for cat in categories:
            if commit.startswith(cat):
                categories[cat].append(commit)
                break
        else:
            categories["other"].append(commit)
    notes = "# Release Notes\n\n"
    labels = {"feat": "Features", "fix": "Bug Fixes", "docs": "Documentation", "refactor": "Refactoring"}
    for cat, items in categories.items():
        if items and cat != "other":
            notes += f"## {labels.get(cat, cat)}\n"
            for item in items:
                notes += f"- {item}\n"
            notes += "\n"
    return notes
