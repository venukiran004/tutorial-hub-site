2. SOLID Principles

ProblemReal-world analogy

SOLID is the most important set of OOP design principles, coined by Robert C. Martin (Uncle Bob).

S — Single Responsibility Principle (SRP)

A class should have only one reason to change.

Bad Example ❌

class Employee:
    def __init__(self, name, salary):
        self.name = name
        self.salary = salary
    
    def calculate_pay(self):
        """Business logic — HR department"""
        return self.salary * 12
    
    def save_to_database(self):
        """Persistence — DBA department"""
        db.execute(f"INSERT INTO employees VALUES ('{self.name}', {self.salary})")
    
    def generate_report(self):
        """Reporting — Management department"""
        return f"Employee Report: {self.name} earns {self.salary}/month"

Problem: Three reasons to change (pay rules, DB schema, report format). Three different departments could request changes.

Good Example ✅

class Employee:
    """Only holds employee data"""
    def __init__(self, name: str, salary: float):
        self.name = name
        self.salary = salary

class PayCalculator:
    """Handles pay calculations — HR"""
    def calculate_annual_pay(self, employee: Employee) -> float:
        return employee.salary * 12

class EmployeeRepository:
    """Handles persistence — DBA"""
    def __init__(self, db):
        self.db = db
    
    def save(self, employee: Employee):
        self.db.execute(
            "INSERT INTO employees (name, salary) VALUES (?, ?)",
            (employee.name, employee.salary)
        )

class ReportGenerator:
    """Handles reporting — Management"""
    def generate(self, employee: Employee) -> str:
        return f"Employee Report: {employee.name} earns {employee.salary}/month"

Real-world analogy: A chef should cook. A waiter should serve. A cashier should bill. One person doing all three = chaos.

O — Open/Closed Principle (OCP)

Open for extension, closed for modification.

Bad Example ❌

class DiscountCalculator:
    def calculate(self, customer_type: str, amount: float) -> float:
        if customer_type == "regular":
            return amount * 0.1
        elif customer_type == "premium":
            return amount * 0.2
        elif customer_type == "vip":
            return amount * 0.3
        # Adding new type? Must modify this class!
        # What if someone breaks existing logic?

Good Example ✅

from abc import ABC, abstractmethod

class DiscountStrategy(ABC):
    @abstractmethod
    def calculate(self, amount: float) -> float:
        pass

class RegularDiscount(DiscountStrategy):
    def calculate(self, amount: float) -> float:
        return amount * 0.1

class PremiumDiscount(DiscountStrategy):
    def calculate(self, amount: float) -> float:
        return amount * 0.2

class VIPDiscount(DiscountStrategy):
    def calculate(self, amount: float) -> float:
        return amount * 0.3

# Adding new type? Just create a new class — no existing code modified!
class EmployeeDiscount(DiscountStrategy):
    def calculate(self, amount: float) -> float:
        return amount * 0.4

class DiscountCalculator:
    def __init__(self, strategy: DiscountStrategy):
        self.strategy = strategy
    
    def apply_discount(self, amount: float) -> float:
        return self.strategy.calculate(amount)

# Usage
calc = DiscountCalculator(VIPDiscount())
print(calc.apply_discount(1000))  # 300.0

L — Liskov Substitution Principle (LSP)

Subtypes must be substitutable for their base types without breaking the program.

Bad Example ❌ (Classic: Rectangle/Square)

class Rectangle:
    def __init__(self, width, height):
        self._width = width
        self._height = height
    
    @property
    def width(self):
        return self._width
    
    @width.setter
    def width(self, value):
        self._width = value
    
    @property
    def height(self):
        return self._height
    
    @height.setter
    def height(self, value):
        self._height = value
    
    def area(self):
        return self._width * self._height

class Square(Rectangle):
    def __init__(self, side):
        super().__init__(side, side)
    
    @Rectangle.width.setter
    def width(self, value):
        self._width = value
        self._height = value  # Breaks LSP! Changing width also changes height
    
    @Rectangle.height.setter
    def height(self, value):
        self._width = value
        self._height = value

# This function works with Rectangle but BREAKS with Square
def double_width(rect: Rectangle):
    rect.width = rect.width * 2
    # For Rectangle(3,4): area should be 6*4=24 ✓
    # For Square(3):      area becomes 6*6=36 ✗ (unexpected!)

Good Example ✅

from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self) -> float:
        pass

class Rectangle(Shape):
    def __init__(self, width: float, height: float):
        self.width = width
        self.height = height
    
    def area(self) -> float:
        return self.width * self.height

class Square(Shape):
    def __init__(self, side: float):
        self.side = side
    
    def area(self) -> float:
        return self.side ** 2

# Both can be used wherever Shape is expected
def print_area(shape: Shape):
    print(f"Area: {shape.area()}")  # Works correctly for all shapes

print_area(Rectangle(3, 4))  # Area: 12
print_area(Square(5))        # Area: 25

I — Interface Segregation Principle (ISP)

Clients should not be forced to depend on interfaces they don't use.

Bad Example ❌

from abc import ABC, abstractmethod

class Worker(ABC):
    @abstractmethod
    def work(self): pass
    
    @abstractmethod
    def eat(self): pass
    
    @abstractmethod
    def sleep(self): pass

class Robot(Worker):
    def work(self):
        print("Robot working")
    
    def eat(self):
        pass  # Robots don't eat! Forced to implement useless method
    
    def sleep(self):
        pass  # Robots don't sleep! Forced to implement useless method

Good Example ✅

from abc import ABC, abstractmethod

class Workable(ABC):
    @abstractmethod
    def work(self): pass

class Eatable(ABC):
    @abstractmethod
    def eat(self): pass

class Sleepable(ABC):
    @abstractmethod
    def sleep(self): pass

class Human(Workable, Eatable, Sleepable):
    def work(self):
        print("Human working")
    def eat(self):
        print("Human eating")
    def sleep(self):
        print("Human sleeping")

class Robot(Workable):  # Only implements what it needs
    def work(self):
        print("Robot working")

D — Dependency Inversion Principle (DIP)

High-level modules should not depend on low-level modules. Both should depend on abstractions.

Bad Example ❌

class MySQLDatabase:
    def connect(self):
        return "Connected to MySQL"
    def query(self, sql):
        return f"MySQL result for: {sql}"

class UserService:
    def __init__(self):
        self.db = MySQLDatabase()  # Tightly coupled to MySQL!
    
    def get_user(self, user_id):
        return self.db.query(f"SELECT * FROM users WHERE id={user_id}")

# What if we want PostgreSQL? Must modify UserService!

Good Example ✅

from abc import ABC, abstractmethod

class Database(ABC):
    @abstractmethod
    def connect(self): pass
    
    @abstractmethod
    def query(self, sql: str): pass

class MySQLDatabase(Database):
    def connect(self):
        return "Connected to MySQL"
    def query(self, sql):
        return f"MySQL: {sql}"

class PostgreSQLDatabase(Database):
    def connect(self):
        return "Connected to PostgreSQL"
    def query(self, sql):
        return f"PostgreSQL: {sql}"

class UserService:
    def __init__(self, db: Database):  # Depends on abstraction!
        self.db = db
    
    def get_user(self, user_id):
        return self.db.query(f"SELECT * FROM users WHERE id={user_id}")

# Easy to swap!
service_mysql = UserService(MySQLDatabase())
service_pg = UserService(PostgreSQLDatabase())

3. DRY — Don't Repeat Yourself

Importantknowledge duplication

Every piece of knowledge must have a single, unambiguous representation in the system.

DRY in practice

Bad Example ❌

def calculate_employee_tax(salary):
    if salary <= 50000:
        return salary * 0.1
    elif salary <= 100000:
        return salary * 0.2
    else:
        return salary * 0.3

def calculate_contractor_tax(payment):
    if payment <= 50000:
        return payment * 0.1    # Same logic duplicated!
    elif payment <= 100000:
        return payment * 0.2
    else:
        return payment * 0.3

Good Example ✅

def calculate_tax(income: float) -> float:
    """Single source of truth for tax calculation"""
    TAX_BRACKETS = [
        (50_000, 0.1),
        (100_000, 0.2),
        (float('inf'), 0.3),
    ]
    for threshold, rate in TAX_BRACKETS:
        if income <= threshold:
            return income * rate

# Reused everywhere
employee_tax = calculate_tax(salary=75000)
contractor_tax = calculate_tax(income=75000)

DRY ≠ No Duplication

Important: DRY is about knowledge duplication, not code duplication. Two functions may look the same but represent different business concepts — that's OK!

# These LOOK similar but are DIFFERENT concepts — NOT a DRY violation
def validate_username(name: str) -> bool:
    return 3 <= len(name) <= 20  # Business rule: usernames

def validate_product_name(name: str) -> bool:
    return 3 <= len(name) <= 20  # Business rule: product names
    # These rules may diverge later!

4. KISS — Keep It Simple, Stupid

Simplicity is the ultimate sophistication.

KISS in practice

Bad Example ❌

# Over-engineered
def is_even(n):
    return not bool(n & 1) if isinstance(n, int) else (
        True if float(n) == int(float(n)) and not bool(int(float(n)) & 1) 
        else False
    )

Good Example ✅

def is_even(n: int) -> bool:
    return n % 2 == 0

Bad Example ❌ (Over-abstraction)

class NumberCheckerFactory:
    @staticmethod
    def create_checker(check_type):
        if check_type == "even":
            return EvenChecker()
        elif check_type == "odd":
            return OddChecker()

class EvenChecker:
    def check(self, n):
        return n % 2 == 0

class OddChecker:
    def check(self, n):
        return n % 2 != 0

# Usage (way too complex for the task)
checker = NumberCheckerFactory.create_checker("even")
result = checker.check(42)

Good Example ✅

def is_even(n: int) -> bool:
    return n % 2 == 0

def is_odd(n: int) -> bool:
    return n % 2 != 0
•

5. YAGNI — You Aren't Gonna Need It

Don't implement something until it is actually needed.

YAGNI in practice

Bad Example ❌

class UserService:
    def create_user(self, data):
        pass
    
    def delete_user(self, user_id):
        pass
    
    # "We might need these later..."
    def export_users_to_csv(self):
        pass  # Not in any requirement
    
    def import_users_from_xml(self):
        pass  # No one asked for this
    
    def merge_duplicate_users(self):
        pass  # Maybe someday...
    
    def predict_user_churn(self):
        pass  # Definitely not now

Good Example ✅

class UserService:
    """Only implements what's needed NOW"""
    def create_user(self, data: dict) -> User:
        ...
    
    def delete_user(self, user_id: int) -> bool:
        ...
    
    # Add new methods when requirements arrive,
    # not when you imagine they might be needed

YAGNI vs Planning Ahead

YAGNI says:              Planning says:
──────────               ──────────────
Don't build features     DO design for extensibility
you don't need yet       (OCP, DIP)

Don't write code         DO write clean interfaces
for imaginary use cases  that allow future extension

Don't optimize           DO choose the right
prematurely              data structures

6. Separation of Concerns (SoC)

Each module/function/class should address a separate concern.

SoC in practice

Web Application Example

┌─────────────────────────────────────────────────────────┐
│                     PRESENTATION                         │
│  (HTML, CSS, JavaScript, Templates)                      │
│  Concern: How things LOOK                                │
├─────────────────────────────────────────────────────────┤
│                     BUSINESS LOGIC                        │
│  (Services, Use Cases, Domain Models)                    │
│  Concern: WHAT the app does                              │
├─────────────────────────────────────────────────────────┤
│                     DATA ACCESS                           │
│  (Repositories, ORM, SQL)                                │
│  Concern: WHERE/HOW data is stored                       │
└─────────────────────────────────────────────────────────┘

Bad Example ❌

@app.post("/register")
def register(request):
    # Validation (concern 1)
    if not request.email or "@" not in request.email:
        return {"error": "Invalid email"}
    
    # Business logic (concern 2)
    hashed_password = bcrypt.hash(request.password)
    
    # Database (concern 3)
    db.execute("INSERT INTO users ...", (request.email, hashed_password))
    
    # Email (concern 4)
    smtp.send_mail(request.email, "Welcome!", "Thanks for registering")
    
    # Logging (concern 5)
    logger.info(f"New user: {request.email}")
    
    return {"message": "Registered"}

Good Example ✅

# validators.py
class UserValidator:
    def validate_registration(self, data: dict) -> bool:
        if not data.get("email") or "@" not in data["email"]:
            raise ValidationError("Invalid email")

# services.py
class UserService:
    def __init__(self, repo, email_service, logger):
        self.repo = repo
        self.email_service = email_service
        self.logger = logger
    
    def register(self, data: dict) -> User:
        user = User(email=data["email"], password=hash_password(data["password"]))
        self.repo.save(user)
        self.email_service.send_welcome(user.email)
        self.logger.info(f"New user: {user.email}")
        return user

# routes.py
@app.post("/register")
def register(request, service: UserService = Depends()):
    validator.validate_registration(request.dict())
    user = service.register(request.dict())
    return {"message": "Registered", "id": user.id}

7. Composition Over Inheritance

Favor composing objects over inheriting from a base class.

Composition in practice

Bad Example ❌ (Deep Inheritance)

class Animal:
    def eat(self): print("Eating")

class Bird(Animal):
    def fly(self): print("Flying")

class Duck(Bird):
    def swim(self): print("Swimming")

class RubberDuck(Duck):  # Inherits fly(), eat() — rubber ducks don't fly or eat!
    def squeak(self): print("Squeak!")

Good Example ✅ (Composition)

class EatAbility:
    def eat(self): print("Eating")

class FlyAbility:
    def fly(self): print("Flying")

class SwimAbility:
    def swim(self): print("Swimming")

class SqueakAbility:
    def squeak(self): print("Squeak!")

class Duck:
    def __init__(self):
        self.eating = EatAbility()
        self.flying = FlyAbility()
        self.swimming = SwimAbility()

class RubberDuck:
    def __init__(self):
        self.swimming = SwimAbility()
        self.squeaking = SqueakAbility()
        # No eating, no flying — makes sense!

duck = Duck()
duck.eating.eat()       # Eating
duck.flying.fly()       # Flying

rubber = RubberDuck()
rubber.squeaking.squeak()  # Squeak!
# rubber.flying → AttributeError (correct behavior!)

When to Use Inheritance vs Composition

Use INHERITANCE when:              Use COMPOSITION when:
─────────────────────              ──────────────────────
True "is-a" relationship           "has-a" relationship
Dog IS an Animal                   Car HAS an Engine
Shared behavior won't diverge      Behaviors vary independently
Shallow hierarchy (2-3 levels)     Would create deep hierarchies
•

8. Law of Demeter (LoD)

"Don't talk to strangers." — An object should only call methods on: itself, its parameters, objects it creates, its direct components.

LoD in practice

Bad Example ❌

# Chain of method calls — reaching deep into object graph
customer.get_wallet().get_credit_card().charge(amount)
order.get_customer().get_address().get_city()

Good Example ✅

# Tell, don't ask
customer.charge(amount)  # Customer handles the details internally

class Customer:
    def charge(self, amount: float):
        self.wallet.charge(amount)

class Wallet:
    def charge(self, amount: float):
        self.credit_card.charge(amount)

9. Encapsulation

Hide internal state and require all interaction through public methods.

class BankAccount:
    def __init__(self, owner: str, balance: float = 0):
        self._owner = owner
        self.__balance = balance  # Private
    
    @property
    def balance(self) -> float:
        return self.__balance
    
    def deposit(self, amount: float):
        if amount <= 0:
            raise ValueError("Deposit must be positive")
        self.__balance += amount
    
    def withdraw(self, amount: float):
        if amount > self.__balance:
            raise ValueError("Insufficient funds")
        if amount <= 0:
            raise ValueError("Withdrawal must be positive")
        self.__balance -= amount

# Usage
account = BankAccount("Alice", 1000)
account.deposit(500)
account.withdraw(200)
print(account.balance)  # 1300
# account.__balance = -9999  # Won't work! (name mangling)
•

10. Abstraction

Expose only what's necessary, hide complexity.

# User sees this simple interface:
class EmailService:
    def send(self, to: str, subject: str, body: str) -> bool:
        """Simple API — hides SMTP complexity"""
        ...

# Internally:
class EmailService:
    def send(self, to: str, subject: str, body: str) -> bool:
        connection = self._connect_to_smtp()        # Hidden
        message = self._build_mime_message(...)      # Hidden
        self._authenticate(connection)               # Hidden
        self._send_raw(connection, message)          # Hidden
        self._close_connection(connection)           # Hidden
        return True

11. Coupling & Cohesion

CouplingCohesion

Coupling (Low is better)

Coupling = degree of interdependence between modules.

Tight Coupling (Bad):              Loose Coupling (Good):
─────────────────────              ──────────────────────
Module A ←──────→ Module B         Module A ←→ Interface ←→ Module B
Change A → must change B           Change A → B unaffected
Hard to test in isolation          Easy to mock and test

Cohesion (High is better)

Cohesion = degree to which elements within a module belong together.

Low Cohesion (Bad):                High Cohesion (Good):
───────────────────                ────────────────────
class Utils:                       class FileHandler:
    send_email()                       read_file()
    parse_json()                       write_file()
    validate_user()                    delete_file()
    resize_image()                     list_files()
    (unrelated methods)                (all related to files)
•

12. Inversion of Control (IoC) & Dependency Injection (DI)

# WITHOUT DI — class creates its own dependencies
class OrderService:
    def __init__(self):
        self.db = PostgresDatabase()     # Creates dependency
        self.emailer = SMTPEmailer()     # Creates dependency
        self.logger = FileLogger()       # Creates dependency

# WITH DI — dependencies are injected from outside
class OrderService:
    def __init__(self, db: Database, emailer: Emailer, logger: Logger):
        self.db = db
        self.emailer = emailer
        self.logger = logger

# Now we can inject anything!
# Production:
service = OrderService(PostgresDatabase(), SMTPEmailer(), FileLogger())

# Testing:
service = OrderService(MockDatabase(), MockEmailer(), MockLogger())

FastAPI DI Example

from fastapi import Depends

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

@app.get("/users")
def list_users(db: Session = Depends(get_db)):
    return db.query(User).all()

13. Fail Fast Principle

If something is going to fail, fail immediately and clearly.

# BAD: Fails silently, causes problems later
def process_order(order):
    if order.total < 0:
        order.total = 0  # Silently "fixing" bad data
    # ... continues processing with wrong data

# GOOD: Fails fast with clear error
def process_order(order):
    if order.total < 0:
        raise ValueError(f"Invalid order total: {order.total}")
    if not order.customer:
        raise ValueError("Order must have a customer")
    # ... continues only with valid data

14. Convention Over Configuration

Provide sensible defaults; only require configuration for the unconventional.

# Django: Convention — models.py, views.py, urls.py
# FastAPI: Convention — response_model auto-generates docs
# SQLAlchemy: Convention — table name = class name (lowercase)

class User(Base):
    __tablename__ = "user"  # Convention: auto-derived from class name
    id = Column(Integer, primary_key=True)
    name = Column(String)  # Column name = attribute name by convention

16. Creational Patterns

16.1 Singleton — One instance only

class DatabaseConnection:
    _instance = None
    
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance.connection = cls._create_connection()
        return cls._instance
    
    @staticmethod
    def _create_connection():
        return "Connected to DB"

# Usage
db1 = DatabaseConnection()
db2 = DatabaseConnection()
print(db1 is db2)  # True — same instance

# Pythonic Singleton (using module)
# db.py
connection = create_connection()  # Module-level = singleton by default

16.2 Factory — Create objects without specifying exact class

from abc import ABC, abstractmethod

class Notification(ABC):
    @abstractmethod
    def send(self, message: str): pass

class EmailNotification(Notification):
    def send(self, message):
        print(f"📧 Email: {message}")

class SMSNotification(Notification):
    def send(self, message):
        print(f"📱 SMS: {message}")

class PushNotification(Notification):
    def send(self, message):
        print(f"🔔 Push: {message}")

class NotificationFactory:
    @staticmethod
    def create(channel: str) -> Notification:
        factories = {
            "email": EmailNotification,
            "sms": SMSNotification,
            "push": PushNotification,
        }
        if channel not in factories:
            raise ValueError(f"Unknown channel: {channel}")
        return factories[channel]()

# Usage
notif = NotificationFactory.create("email")
notif.send("Hello!")  # 📧 Email: Hello!

16.3 Builder — Construct complex objects step by step

class QueryBuilder:
    def __init__(self):
        self._table = ""
        self._conditions = []
        self._order = ""
        self._limit = None
    
    def table(self, name: str):
        self._table = name
        return self  # Enable chaining
    
    def where(self, condition: str):
        self._conditions.append(condition)
        return self
    
    def order_by(self, field: str):
        self._order = field
        return self
    
    def limit(self, n: int):
        self._limit = n
        return self
    
    def build(self) -> str:
        query = f"SELECT * FROM {self._table}"
        if self._conditions:
            query += " WHERE " + " AND ".join(self._conditions)
        if self._order:
            query += f" ORDER BY {self._order}"
        if self._limit:
            query += f" LIMIT {self._limit}"
        return query

    .where("active = true")
    .order_by("name")
    .limit(10)
    .build()

17.2 Decorator — Add behavior dynamically

# Python's built-in decorator pattern
import functools
import time

def timer(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = time.time()
        result = func(*args, **kwargs)
        elapsed = time.time() - start
        print(f"{func.__name__} took {elapsed:.4f}s")
        return result
    return wrapper

def retry(max_attempts=3):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(max_attempts):
                try:
                    return func(*args, **kwargs)
                except Exception as e:
                    if attempt == max_attempts - 1:
                        raise
                    print(f"Retry {attempt + 1}/{max_attempts}: {e}")
        return wrapper
    return decorator

@timer
@retry(max_attempts=3)
def fetch_data(url: str):
    # Simulate API call
    return {"data": "result"}

18. Behavioral Patterns

18.1 Strategy — Swap algorithms at runtime

from abc import ABC, abstractmethod

class SortStrategy(ABC):
    @abstractmethod
    def sort(self, data: list) -> list: pass

class BubbleSort(SortStrategy):
    def sort(self, data):
        print("Bubble sort (small datasets)")
        return sorted(data)

class QuickSort(SortStrategy):
    def sort(self, data):
        print("Quick sort (large datasets)")
        return sorted(data)

class Sorter:
    def __init__(self, strategy: SortStrategy):
        self._strategy = strategy
    
    def set_strategy(self, strategy: SortStrategy):
        self._strategy = strategy
    
    def sort(self, data: list) -> list:
        return self._strategy.sort(data)

# Usage
sorter = Sorter(BubbleSort())
sorter.sort([3, 1, 2])            # Bubble sort

sorter.set_strategy(QuickSort())
sorter.sort([3, 1, 2])            # Quick sort

18.2 Observer — Publish-Subscribe

class EventManager:
    def __init__(self):
        self._subscribers: dict[str, list] = {}
    
    def subscribe(self, event: str, callback):
        self._subscribers.setdefault(event, []).append(callback)
    
    def unsubscribe(self, event: str, callback):
        self._subscribers.get(event, []).remove(callback)
    
    def notify(self, event: str, data=None):
        for callback in self._subscribers.get(event, []):
            callback(data)

# Usage
events = EventManager()

def send_welcome_email(user):
    print(f"📧 Welcome email to {user}")

def log_registration(user):
    print(f"📝 Logged: {user} registered")

def award_bonus(user):
    print(f"🎁 Bonus awarded to {user}")

events.subscribe("user_registered", send_welcome_email)
events.subscribe("user_registered", log_registration)
events.subscribe("user_registered", award_bonus)

events.notify("user_registered", "Alice")
# 📧 Welcome email to Alice
# 📝 Logged: Alice registered
# 🎁 Bonus awarded to Alice

18.3 Chain of Responsibility

from abc import ABC, abstractmethod

class Handler(ABC):
    def __init__(self):
        self._next: Handler = None
    
    def set_next(self, handler: "Handler") -> "Handler":
        self._next = handler
        return handler
    
    def handle(self, request: dict):
        if self._next:
            return self._next.handle(request)
        return None

class AuthHandler(Handler):
    def handle(self, request):
        if not request.get("token"):
            return "❌ Authentication failed"
        print("✅ Authenticated")
        return super().handle(request)

class RateLimitHandler(Handler):
    def handle(self, request):
        if request.get("requests_count", 0) > 100:
            return "❌ Rate limit exceeded"
        print("✅ Rate limit OK")
        return super().handle(request)

class ValidationHandler(Handler):
    def handle(self, request):
        if not request.get("data"):
            return "❌ Validation failed"
        print("✅ Validated")
        return super().handle(request)

# Build chain
auth = AuthHandler()
rate_limit = RateLimitHandler()
validation = ValidationHandler()
auth.set_next(rate_limit).set_next(validation)

# Process request
result = auth.handle({"token": "abc123", "requests_count": 5, "data": "hello"})
# ✅ Authenticated
# ✅ Rate limit OK
# ✅ Validated

SOLID

Q1: Explain SOLID principles in one sentence each.

  • SRP: One class = one responsibility = one reason to change.
  • OCP: Open for extension (new classes), closed for modification (existing code).
  • LSP: Subclasses must be drop-in replacements for their parent class.
  • ISP: Many small interfaces are better than one large interface.
  • DIP: Depend on abstractions (interfaces), not concrete implementations.

Q2: Give a real-world violation of SRP.

A UserController class that handles HTTP request parsing, business logic validation, database queries, email sending, and logging. It has 5 reasons to change. Should be split into Controller, Validator, Service, Repository, EmailService, and Logger.

Q3: How does OCP relate to the Strategy pattern?

Instead of if/elif chains for different behaviors, you define a strategy interface and create concrete strategies. To add new behavior, you create a new class (extension) without modifying existing ones (closed for modification).

Q4: Why is Liskov Substitution important for polymorphism?

If subclasses can't fully replace their parent, polymorphism breaks. Code expecting a base type may crash or behave incorrectly with a subtype, defeating the purpose of inheritance.

Design Patterns

Q5: What's the difference between Factory and Abstract Factory?

  • FactoryCreates objects of a single family (e.g., NotificationFactory → Email, SMS, Push).
  • Abstract FactoryCreates objects of multiple related families (e.g., UIFactory → creates Button + Checkbox + Menu for Windows or Mac).

Q6: When would you use the Builder pattern?

When constructing objects with many optional parameters (avoid telescoping constructors), when construction has multiple steps, or when the same construction process should create different representations (e.g., SQL query builder, HTML builder, meal builder).

Both wrap an object, but the intent differs.

Q13: When would you use composition over inheritance?

  • When multiple inheritance causes the "diamond problem"

System design is the process of architecting large-scale distributed systems that balance reliability, scalability, and maintainability. Understanding these fundamentals—including back-of-the-envelope estimations—is essential for making informed infrastructure decisions during interviews and real-world engineering.

SYSTEM DESIGN = Designing large-scale distributed systems that are:

  Maintainable: Easy to operate and evolve

2. Scalability

Scalability is a system's ability to handle increasing workload by adding resources, either vertically (bigger machines) or horizontally (more machines). Choosing the right scaling strategy is critical because it directly impacts cost, fault tolerance, and operational complexity.

VERTICAL SCALING (Scale Up):
  Bigger machine: more CPU, RAM, SSD
  Pros: Simple, no code changes
  Cons: Hardware limits, single point of failure
  
HORIZONTAL SCALING (Scale Out):
  More machines behind a load balancer
  Pros: Virtually unlimited, fault-tolerant
  Cons: Distributed systems complexity, data consistency
  
  SCALING DIMENSIONS:
  ┌─────────────────────────────────────────────┐
  │  Stateless services: Scale horizontally     │
  │  (API servers, web servers)                 │
  ├─────────────────────────────────────────────┤
  │  Databases: Replicas (read) + Sharding      │
  ├─────────────────────────────────────────────┤
  │  Caching: Redis cluster, CDN                │
  ├─────────────────────────────────────────────┤
  │  Async work: Message queues + workers       │
  └─────────────────────────────────────────────┘

3. Load Balancing

A load balancer distributes incoming network traffic across multiple servers to ensure no single server becomes a bottleneck. It improves availability and fault tolerance by routing requests only to healthy backend instances.

ALGORITHMS:
  Round Robin:       Equal distribution (default)
  Weighted RR:       Based on server capacity
  Least Connections: Route to server with fewest active connections
  IP Hash:           Sticky sessions (same client → same server)
  
LAYERS:
  L4 (Transport):  TCP/UDP level, fast, no content inspection
  L7 (Application): HTTP level, can route by path/header, SSL termination
  
TOOLS:
  Nginx, HAProxy, AWS ALB/NLB, Envoy
  
HEALTH CHECKS:
  Active: LB pings /health endpoint periodically
  Passive: LB detects failures from actual traffic
  
  Unhealthy server → removed from pool → health check recovers → added back
•

4. Caching

Caching stores frequently accessed data in a fast-access layer (such as memory) to reduce latency and backend load. Selecting the right caching strategy and eviction policy is crucial for maintaining data consistency while maximizing performance gains.

CACHE STRATEGIES:
  Cache-Aside (Lazy):     App checks cache → miss → read DB → write cache
  Write-Through:          App writes cache + DB simultaneously
  Write-Behind:           App writes cache → async write to DB (risky)
  Read-Through:           Cache transparently fetches from DB on miss

CACHE EVICTION:
  LRU (Least Recently Used): Most common
  LFU (Least Frequently Used): For stable hotspots  
  TTL (Time-To-Live): Expire after duration

CACHING LAYERS:
  Browser cache → CDN → API gateway cache → App cache (Redis) → DB cache

REDIS PATTERNS:
  Strings:      Simple key-value, counters
  Hashes:       User profiles, session data
  Lists:        Recent activity feed, message queues
  Sets:         Tags, unique visitors
  Sorted Sets:  Leaderboards, rate limiting
  
CACHE PROBLEMS:
  Thundering herd: Many requests hit DB when cache expires
    → Solution: Lock + single-flight (one request populates cache)
  Cache penetration: Query for non-existent data always misses
    → Solution: Cache null values, Bloom filter
  Cache avalanche: Many keys expire simultaneously
    → Solution: Random TTL jitter
•

5. Database Design

Database design involves choosing the appropriate data model (SQL vs NoSQL) and indexing strategy based on the application's query patterns, consistency requirements, and scalability needs. Sound database design decisions are foundational to building performant and reliable systems.

SQL vs NoSQL:
  SQL (PostgreSQL, MySQL):
    Structured data, ACID, joins, complex queries
    Best for: Transactions, relational data, consistency-critical

  NoSQL:
    Document (MongoDB):   Flexible schema, nested data
    Key-Value (Redis, DynamoDB): Simple lookups, sessions, caching
    Wide-Column (Cassandra): Time-series, IoT, write-heavy
    Graph (Neo4j):        Relationships, social networks

INDEXING:
  B-Tree:      Default, good for range queries, O(log n)
  Hash:        Equality lookups only, O(1)
  GIN:         Full-text search, array containment
  Composite:   Multi-column (order matters: leftmost prefix)
  
  RULE: Index columns in WHERE, JOIN, ORDER BY clauses
  COST: Faster reads, slower writes, more storage

6. Database Scaling

Database scaling extends a single database's capacity through read replicas, sharding, or vertical partitioning to handle growing data volumes and query loads. Each strategy introduces trade-offs between consistency, query complexity, and operational overhead.

READ REPLICAS:
  Primary (writes) → Replica 1 (reads)
                   → Replica 2 (reads)
  Replication lag: Eventual consistency (0.1-1s)

SHARDING (Horizontal Partitioning):
  Split data across multiple DB instances by a shard key
  
  Range-based:  user_id 1-1M → Shard 1, 1M-2M → Shard 2
    Pros: Range queries easy  Cons: Hotspots
  Hash-based:   hash(user_id) % N → Shard N
    Pros: Even distribution  Cons: Range queries across shards
  
  CHALLENGES:
  - Cross-shard joins (avoid — denormalize instead)
  - Rebalancing when adding/removing shards
  - Auto-increment IDs (use UUIDs or Snowflake IDs)

VERTICAL PARTITIONING:
  Split columns: users table → users_core + users_profile
  Useful when some columns queried much more than others
•

7. CAP, ACID, BASE

The CAP theorem, ACID properties, and BASE semantics define the fundamental consistency and availability trade-offs in distributed data systems. Understanding these theoretical foundations is essential for choosing the right database architecture for a given use case.

CAP THEOREM:
  In a distributed system, you can only guarantee 2 of 3:
  Consistency:    Every read returns the most recent write
  Availability:   Every request gets a response
  Partition Tolerance: System works despite network failures
  
  In real systems, P is unavoidable → choose CP or AP
  CP: PostgreSQL, MongoDB (strong consistency, may reject requests)
  AP: Cassandra, DynamoDB (always available, eventual consistency)

ACID (traditional SQL):
  Atomicity:   All or nothing
  Consistency:  Valid state to valid state
  Isolation:    Transactions don't interfere
  Durability:   Committed data survives crashes

BASE (NoSQL trade-off):
  Basically Available: System always responds
  Soft state: State may change without input (eventual propagation)
  Eventual consistency: Will become consistent eventually
•

8. Consistent Hashing

Consistent hashing is a technique that distributes data across a dynamic set of servers while minimizing key redistribution when nodes are added or removed. It is widely used in distributed caches, databases, and CDNs to achieve even load distribution.

PROBLEM: hash(key) % N → Adding/removing a server reshuffles ALL keys

CONSISTENT HASHING:
  Place servers on a hash ring (0 to 2³²)
  hash("server1") → position on ring
  hash(key) → find next server clockwise
  
  Adding server: Only keys between new server and its predecessor move
  Removing server: Only that server's keys move to the next server
  
  VIRTUAL NODES: Each physical server gets multiple positions on ring
    → More even distribution, smoother rebalancing
  
  USED BY: DynamoDB, Cassandra, Redis Cluster, CDN routing
•

9. Message Queues

Message queues decouple producers from consumers by buffering messages asynchronously, enabling resilient and scalable inter-service communication. They are essential for handling burst traffic, event-driven architectures, and maintaining system reliability under load.

PATTERNS:
  Point-to-Point: 1 producer → Queue → 1 consumer (task queue)
  Pub/Sub: 1 producer → Topic → Multiple consumers (event streaming)

COMPARISON:
  Queue         │ Type    │ Ordering │ Persistence │ Throughput
  ──────────────┼─────────┼──────────┼─────────────┼──────────
  Kafka         │ Log     │ Per-part │ Disk (days)  │ Very High
  RabbitMQ      │ Queue   │ FIFO     │ Optional    │ Medium
  Redis Streams │ Log     │ Per-key  │ Memory+disk │ High
  SQS           │ Queue   │ Best-eff │ 14 days     │ High
  
  Kafka: Event streaming, high throughput, replay capability
  RabbitMQ: Task queues, routing, lower latency
  SQS: Serverless, managed, simple queue

USE CASES:
  Decoupling:     Service A → Queue → Service B (async)
  Load leveling:  Burst traffic → Queue → Steady processing
  Event sourcing: All events in Kafka → replay to rebuild state
•

10. API Design

API design defines the contract between clients and servers, determining how data is requested, structured, and transmitted. Choosing between REST, GraphQL, and gRPC involves trade-offs in flexibility, performance, and developer experience.

REST:
  GET /users/123         → Read user 123
  POST /users            → Create user
  PUT /users/123         → Update user 123 (full)
  PATCH /users/123       → Update user 123 (partial)
  DELETE /users/123      → Delete user 123
  
  Pagination: GET /users?page=2&limit=20
  Filtering:  GET /users?status=active&role=admin
  Versioning: /v1/users or Accept: application/vnd.api.v1+json

GraphQL:
  Single endpoint, client specifies exact fields needed

gRPC:

  Pros: Very fast, streaming, code generation
  Cons: Not browser-friendly, harder to debug
  Best for: Internal microservice communication

11. Microservices

Microservices is an architectural pattern where an application is decomposed into small, independently deployable services, each owning its own data store. While enabling independent scaling and deployment, it introduces challenges around distributed transactions and operational complexity.

MICROSERVICES vs MONOLITH:
  Monolith:      Single deployable unit
    Pros: Simple, easy debugging, ACID transactions
    Cons: Scaling is all-or-nothing, deployment risk
    
  Microservices:  Independent services, own DB each
    Pros: Independent scaling, deployment, technology choice
    Cons: Distributed complexity, eventual consistency, debugging
    
  RULE: Start monolith → extract microservices when needed
  
SERVICE COMMUNICATION:
  Synchronous:  REST, gRPC (request-response)
  Asynchronous: Message queues (event-driven)
  
  Prefer async for: non-blocking operations, eventual consistency OK
  Use sync for: immediate response needed, strong consistency
•

12. Rate Limiting

Rate limiting controls the number of requests a client can make to an API within a given time window, protecting services from abuse and ensuring fair resource allocation. Common algorithms include token bucket and sliding window, typically implemented via Redis or API gateways.

ALGORITHMS:
  Token Bucket:     Tokens added at fixed rate, request consumes token
  Sliding Window:   Count requests in rolling time window
  Fixed Window:     Count requests per fixed time interval
  Leaky Bucket:     Requests processed at fixed rate, excess queued
  
  Token Bucket: Most flexible, allows bursts up to bucket capacity
  Sliding Window: Most accurate, more memory
  
IMPLEMENTATION:
  Redis + Lua script (atomic operations)
  API Gateway level (Kong, AWS API Gateway)
  Application level (middleware)
  
  Response headers:
    X-RateLimit-Limit: 100
    X-RateLimit-Remaining: 42
    X-RateLimit-Reset: 1640995200
    
  Exceeded → HTTP 429 Too Many Requests
•

13. Distributed Patterns

Distributed patterns are reusable architectural solutions—such as circuit breakers, event sourcing, CQRS, and sagas—that address common challenges in distributed systems. These patterns help manage failures, maintain data consistency, and coordinate transactions across services.

CIRCUIT BREAKER:
  Closed (normal) → calls succeed
  → Failures exceed threshold → Open (all calls fail fast)
  → After timeout → Half-Open (allow one test call)
  → Success → Closed  |  Failure → Open
  
  Prevents cascading failures when downstream service is down

EVENT SOURCING:
  Store all state changes as immutable events (not just current state)
  Events: UserCreated, OrderPlaced, PaymentProcessed
  Rebuild current state by replaying events
  Benefits: Full audit trail, time travel, event replay

CQRS (Command Query Responsibility Segregation):
  Separate write model (commands) from read model (queries)
  Write → normalized DB | Read → denormalized/materialized views
  Often combined with Event Sourcing

SAGA PATTERN (Distributed Transactions):
  Choreography: Each service publishes events → next service reacts
  Orchestration: Central coordinator manages the transaction steps
  Compensation: If step 3 fails → undo steps 2 and 1

IDEMPOTENCY:
  Same request sent multiple times → same result
  Use idempotency key (client-generated UUID)
  Critical for: payment processing, order creation, retries
•

14. Observability

Observability is the ability to understand a system's internal state through its external outputs—metrics, logs, and distributed traces. It is essential for debugging, performance tuning, and ensuring reliability in microservice architectures.

THREE PILLARS:
  Metrics:   Quantitative measurements (QPS, latency, error rate)
             Tools: Prometheus, Datadog, CloudWatch
  Logs:      Event records with context
             Tools: ELK, Loki, CloudWatch Logs
  Traces:    Request path across services (distributed tracing)
             Tools: Jaeger, Zipkin, OpenTelemetry

TRACING:
  Request → Service A (trace_id: abc, span: 1)
         → Service B (trace_id: abc, span: 2)
         → Service C (trace_id: abc, span: 3)
  
  Trace ID propagated through all services → end-to-end visibility
•

15. Common Design Problems

Common design problems are frequently asked system design interview scenarios—such as URL shorteners, chat systems, and news feeds—that test a candidate's ability to apply fundamental concepts under constraints. Mastering estimation shortcuts and standard solution patterns accelerates both interview performance and real-world architecture work.

DESIGN PATTERNS FOR COMMON SYSTEMS:
  URL Shortener:     Hash → base62 encode → redirect
  Rate Limiter:      Token bucket + Redis
  Chat System:       WebSockets + message queue + fan-out
  News Feed:         Fan-out on write (push) vs fan-out on read (pull)
  Notification:      Queue per channel (email, SMS, push)
  Search Engine:     Inverted index + ranking (TF-IDF, BM25)
  Video Streaming:   CDN + adaptive bitrate + transcoding pipeline
  Payment System:    Idempotency + ACID + event sourcing + reconciliation
  
ESTIMATION SHORTCUTS:
  1 million = 10⁶
  1 billion = 10⁹
  QPS from DAU: DAU × avg_requests / 86400
  Storage: records × avg_size × retention_period
  Bandwidth: QPS × avg_response_size

16. Interview Framework

The interview framework provides a structured approach for tackling system design interviews within a 45–60 minute window. Following this step-by-step process—requirements, estimation, high-level design, deep dive, and scaling—ensures comprehensive coverage and clear communication of trade-offs.

SYSTEM DESIGN INTERVIEW (45-60 min):
  1. REQUIREMENTS (5 min):
     Functional: What does the system do?
     Non-functional: Scale, latency, availability, consistency
     
  2. ESTIMATION (5 min):
     Users, QPS, storage, bandwidth
     
  3. HIGH-LEVEL DESIGN (10 min):
     Draw components: clients, LB, API servers, DB, cache, queue
     
  4. DEEP DIVE (20 min):
     Pick 2-3 components to detail
     Discuss trade-offs for each decision
     
  5. SCALING & TRADE-OFFS (10 min):
     Bottlenecks, single points of failure
     How to scale each component
     
  KEY: Drive the conversation, state trade-offs explicitly,
  ask clarifying questions, don't jump to solutions

17. Interview Deep Dive

RequirementsAPIKey decisionsNumbersAlgorithmImplementation

Q1: Design a URL shortener.

A: Requirements: Shorten long URLs, redirect, analytics, high availability. API: POST /shorten {url} → {short_url}, GET /{code} → 301 redirect. Key decisions: (1) Generate 7-char code: base62(auto_increment_id) or hash(url)[:7] with collision handling. (2) Storage: SQL (PostgreSQL) for strong consistency, index on short_code. (3) Scale reads: Redis cache (code → URL), 80%+ cache hit rate. (4) Scale writes: Range-based ID assignment to avoid contention. (5) Analytics: Async event logging to Kafka → batch processing. Numbers: 100M URLs/month = ~40 QPS writes, 4000 QPS reads → single server + Redis handles it.

Q2: How would you design a rate limiter?

A: Algorithm: Token bucket (allows bursts, simple). Implementation: Redis with Lua script for atomicity. Per key (user_id or IP): store {tokens, last_refill_time}. On request: calculate tokens to add since last refill, subtract 1 if available, reject if 0. Distributed: Use Redis cluster (shared state). Levels: Per-user, per-IP, per-API-key, global. Response: 429 with Retry-After header. Edge cases: Clock skew across servers (use Redis time), race conditions (Lua script is atomic), sliding window for bursty traffic.

Q3: Explain CAP theorem with examples.

A: In a distributed system during a network partition (P), you must choose Consistency (C) or Availability (A). CP (PostgreSQL, MongoDB): During partition, reject writes to maintain consistency. Bank transactions — wrong balance is worse than downtime. AP (Cassandra, DynamoDB): During partition, accept writes with eventual consistency. Social media — showing a slightly stale post is better than being unavailable. In practice: P is rare. Most systems are CA during normal operation. CAP is about behavior DURING partitions.

Q4: When would you use a message queue?

A: (1) Decoupling: Service A doesn't need to know about Service B. (2) Load leveling: Absorb traffic spikes (producers add faster than consumers process). (3) Async processing: User gets instant response, heavy work happens later (email, report generation). (4) Fan-out: One event → multiple consumers (order placed → notify, ship, bill). (5) Retry/resilience: Failed processing → re-queue. Choose Kafka for: high throughput, event streaming, replay. Choose RabbitMQ for: task queues, complex routing. Choose SQS for: serverless, simple queuing.

Q5: Design a notification system.

A: Components: API Gateway → Notification Service → Channel-specific queues (email, SMS, push) → Delivery services → Status tracker. Key decisions: (1) Use message queue per channel (Kafka/SQS) for decoupling and retry. (2) Template service for message formatting. (3) Priority queue for urgent notifications. (4) Rate limiting per user (don't spam). (5) Idempotency (notification_id as dedup key). (6) Status tracking: pending → sent → delivered → read. (7) User preferences (channels, quiet hours, opt-out). Scale: async processing, independent channel scaling.

Q6: How do you handle distributed transactions?

A: Don't use distributed transactions when possible — design for eventual consistency. When needed: Saga Pattern: Chain of local transactions with compensating actions. Two types: (1) Choreography: Services publish events, next service reacts. Simple but hard to debug. (2) Orchestration: Central coordinator manages steps. Easier to reason about. Example (order): Create Order → Reserve Inventory → Process Payment. If payment fails → compensate: Release Inventory → Cancel Order. Key: Each step must be idempotent, each has a compensation action.

Q7: Explain consistent hashing.

A: Regular hashing: hash(key) % N — adding/removing a server remaps ALL keys. Consistent hashing: Place servers on a hash ring (0 to 2³²). Each key is assigned to the next server clockwise on the ring. Adding server S: only keys between S and its predecessor move to S. Removing S: its keys go to the next server. With virtual nodes (each server has 100-200 positions): more even distribution. Used by: DynamoDB, Cassandra, CDN routing, load balancers.

Q8: What is the circuit breaker pattern?

A: Prevents cascading failures when a downstream service is failing. Three states: Closed (normal, calls pass through, track failures). Open (failures exceeded threshold, all calls fail immediately without reaching the service — fast failure). Half-Open (after timeout, allow ONE test call — success → Closed, failure → Open). Implementation: Track failure count/rate in a sliding window. Threshold example: 5 failures in 60 seconds → open for 30 seconds. Tools: resilience4j (Java), Polly (.NET), tenacity (Python). Essential for microservices.
