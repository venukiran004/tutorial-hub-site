Distributed Systems Deep Dive — Architect-Level Reference

Scope: Consensus protocols (Raft, Paxos, ZAB), distributed clocks (Lamport, vector, hybrid logical), leader election, gossip protocols, failure detection, membership protocols, distributed locking, linearizability, quorum systems, split-brain handling, Byzantine fault tolerance, CRDTs, distributed snapshots, exactly-once semantics, backpressure, and production war stories.

1. Why Distributed Systems Are Hard

THE FUNDAMENTAL CHALLENGES:

  1. PARTIAL FAILURE
     ┌────────────────────────────────────────────────────────┐
     │ In a single machine: either everything works or       │
     │ everything fails. In distributed systems: some parts  │
     │ can fail while others continue, and you can't even    │
     │ TELL which parts have failed.                         │
     └────────────────────────────────────────────────────────┘

  2. UNRELIABLE NETWORKS
     - Messages can be lost, delayed, duplicated, or reordered
     - No upper bound on message delivery time
     - You can't distinguish "slow" from "dead"

  3. NO GLOBAL CLOCK
     - Each machine has its own clock (clock drift: 10-100 ppm)
     - NTP can synchronize to ~1ms but not perfectly
     - "Event A happened before B" is often UNDEFINED

  4. UNBOUNDED DELAYS
     - Process pauses (GC, page faults, context switches)
     - Network congestion
     - Disk I/O delays

  THE IMPOSSIBILITY RESULTS:
  ┌──────────────────────────────────────────────────────────────────┐
  │ FLP Impossibility (1985):                                       │
  │   No deterministic consensus protocol can guarantee agreement   │
  │   in an async system with even ONE faulty process.              │
  │                                                                 │
  │ CAP Theorem (2000):                                             │
  │   Cannot simultaneously guarantee Consistency, Availability,    │
  │   and Partition tolerance. (In practice: choose CP or AP)       │
  │                                                                 │
  │ PACELC (extension of CAP):                                      │
  │   Even when no Partition: choose between Latency and            │
  │   Consistency. Full: if P then (A or C), Else (L or C)         │
  └──────────────────────────────────────────────────────────────────┘

2. Failure Models

FAILURE HIERARCHY (least severe → most severe):

  ┌────────────────────────────────────────────────────────────┐
  │ 1. CRASH-STOP                                             │
  │    Node stops and never recovers                          │
  │    Easiest to handle. Node is "dead" forever.             │
  ├────────────────────────────────────────────────────────────┤
  │ 2. CRASH-RECOVERY                                         │
  │    Node crashes, then restarts with persistent state      │
  │    Most common in practice (server reboot, container      │
  │    restart). Must handle: stale state, message replays.   │
  ├────────────────────────────────────────────────────────────┤
  │ 3. OMISSION                                               │
  │    Node fails to send or receive messages                 │
  │    Send omission: node processes but doesn't respond      │
  │    Receive omission: node drops incoming messages         │
  ├────────────────────────────────────────────────────────────┤
  │ 4. TIMING / PERFORMANCE                                   │
  │    Node responds too slowly (beyond timeout)              │
  │    Most insidious: system "works" but degrades            │
  │    Cascading slowdowns can bring down entire clusters     │
  ├────────────────────────────────────────────────────────────┤
  │ 5. BYZANTINE                                              │
  │    Node behaves arbitrarily (send wrong data, lie)        │
  │    Could be malicious or due to bugs/corruption           │
  │    Hardest to handle. Requires 3f+1 nodes for f faults.  │
  └────────────────────────────────────────────────────────────┘

  PRACTICAL FAILURE CATEGORIES:
  ┌──────────────────┬────────────────────────────────────────┐
  │ Hardware         │ Disk failure, memory corruption,       │
  │                  │ NIC failure, power outage              │
  ├──────────────────┼────────────────────────────────────────┤
  │ Software         │ OOM, deadlocks, infinite loops,        │
  │                  │ config errors, dependency failures     │
  ├──────────────────┼────────────────────────────────────────┤
  │ Network          │ Partition, congestion, DNS failure,    │
  │                  │ cable cut, switch failure              │
  ├──────────────────┼────────────────────────────────────────┤
  │ Human            │ Misconfig (leading cause!), bad deploy,│
  │                  │ wrong command, capacity oversight      │
  └──────────────────┴────────────────────────────────────────┘

  GRAY FAILURES (hardest to debug):
  - System is partially working (some requests succeed, some fail)
  - Flapping: node alternates between healthy and unhealthy
  - Silent data corruption: wrong results without errors
  - Performance degradation without clear threshold breach

3. Time and Ordering

WHY TIME MATTERS:
  - Determining causality: Did event A cause event B?
  - Conflict resolution: Which write is "most recent"?
  - Lease expiry: Is this lock still valid?
  - Debugging: Correlating logs across services

PHYSICAL CLOCKS:
  ┌──────────────────────────────────────────────────────────┐
  │ Each machine has a quartz oscillator (drifts 10-100 ppm) │
  │ 100 ppm = 8.6 seconds per day of drift                  │
  │                                                          │
  │ NTP (Network Time Protocol):                             │
  │   Synchronizes to ~1-50ms accuracy                       │
  │   Can jump forward or backward                           │
  │   NOT reliable for ordering events                       │
  │                                                          │
  │ Google TrueTime (Spanner):                               │
  │   GPS + atomic clocks → bounded uncertainty [earliest,   │
  │   latest]. Wait out uncertainty before commit.           │
  │   Accuracy: ~1-7ms uncertainty interval                  │
  │   Enables globally consistent transactions               │
  └──────────────────────────────────────────────────────────┘

LAMPORT CLOCKS (Logical):
  ┌──────────────────────────────────────────────────────────┐
  │ Each process maintains a counter C                       │
  │                                                          │
  │ Rules:                                                   │
  │   1. Before any event: C = C + 1                         │
  │   2. Send message: attach C to message                   │
  │   3. Receive message(C_msg): C = max(C, C_msg) + 1      │
  │                                                          │
  │ Property: If A → B (A causally precedes B), then C(A) < C(B)│
  │ BUT: C(A) < C(B) does NOT imply A → B (concurrent events)│
  │                                                          │
  │ Example:                                                 │
  │   Process P1:  [1] ──send──→ [2]           [5]          │
  │   Process P2:         [1] [2] ──recv──→ [3] ──send──→[4]│
  │   Process P3:              [1]        [2]   ──recv──→[5] │
  └──────────────────────────────────────────────────────────┘

VECTOR CLOCKS:
  ┌──────────────────────────────────────────────────────────┐
  │ Each process maintains a vector of counters              │
  │ (one entry per process in the system)                    │
  │                                                          │
  │ Rules:                                                   │
  │   1. Before event: increment own entry                   │
  │   2. Send: attach entire vector                          │
  │   3. Receive: take element-wise max, then increment own  │
  │                                                          │
  │ Property: Can detect CONCURRENT events                   │
  │   V(A) < V(B): A happened before B                      │
  │   V(A) || V(B): A and B are concurrent (conflict!)      │
  │                                                          │
  │ Example (3 processes):                                   │
  │   P1: [1,0,0] → send → [2,0,0]                         │
  │   P2: [0,1,0] → recv → [2,2,0] → send → [2,3,0]       │
  │   P3: [0,0,1] → recv → [2,3,2]                         │
  │                                                          │
  │ Problem: Vector size grows with # processes              │
  │ Used by: DynamoDB, Riak (for conflict detection)         │
  └──────────────────────────────────────────────────────────┘

HYBRID LOGICAL CLOCKS (HLC):
  ┌──────────────────────────────────────────────────────────┐
  │ Combines physical time with logical counter              │
  │ HLC = (physical_time, logical_counter)                   │
  │                                                          │
  │ Benefits:                                                │
  │   - Bounded drift from physical time                     │
  │   - Captures causality like Lamport clocks               │
  │   - Fixed size (not like vector clocks)                  │
  │   - Can be used for snapshot reads                       │
  │                                                          │
  │ Used by: CockroachDB, YugabyteDB, MongoDB               │
  └──────────────────────────────────────────────────────────┘

VERSION VECTORS (for replicated data):
  - Like vector clocks but track data versions, not events
  - Each replica increments its entry on write
  - On sync: compare vectors to detect conflicts
  - Used by: DynamoDB, Cassandra (lightweight version)

4. Consensus Protocols

CONSENSUS: Getting N nodes to agree on a value even when some fail.

  REQUIREMENTS:
  1. Agreement:   All correct nodes decide the same value
  2. Validity:    The decided value was proposed by some node
  3. Termination: All correct nodes eventually decide
  4. Integrity:   Each node decides at most once

═══════════════════════════════════════════════════════════════
RAFT PROTOCOL (most practical, easy to understand)
═══════════════════════════════════════════════════════════════

  STATES:
  ┌──────────┐    timeout    ┌───────────┐   majority    ┌────────┐
  │ Follower │──────────────→│ Candidate │──────────────→│ Leader │
  └──────────┘               └───────────┘               └────────┘
       ↑                          │                           │
       │                          │ higher term               │ higher term
       │                          ↓                           ↓
       └──────────────────────────────────────────────────────┘

  KEY CONCEPTS:
  Term:    Logical time period. Monotonically increasing.
           Each term has at most one leader.
  Log:     Ordered sequence of commands. Replicated to all nodes.
  Commit:  Entry is committed when replicated to majority.

  LEADER ELECTION:
  1. Follower's election timeout expires (150-300ms random)
  2. Becomes Candidate, increments term, votes for itself
  3. Sends RequestVote RPCs to all other nodes
  4. Wins if receives majority votes (term must be ≥ voter's term,
     candidate's log must be at least as up-to-date as voter's)
  5. Becomes Leader, sends heartbeats to prevent new elections

  LOG REPLICATION:
  1. Client sends command to Leader
  2. Leader appends to local log
  3. Leader sends AppendEntries RPCs to all Followers
  4. When majority acknowledges → Leader commits
  5. Leader responds to client
  6. Leader notifies Followers of commit in next heartbeat
  7. Followers apply committed entries to state machine

  SAFETY GUARANTEES:
  - Election Safety: At most one leader per term
  - Leader Append-Only: Leader never overwrites its log
  - Log Matching: If two logs contain entry with same index
    and term, all preceding entries are identical
  - Leader Completeness: If an entry is committed, it appears
    in all future leaders' logs
  - State Machine Safety: If a server applies an entry at a
    given index, no other server applies a different entry

  JOINT CONSENSUS (membership changes):
  - Can't just add/remove nodes (could have two majorities!)
  - Raft uses two-phase approach:
    Phase 1: Leader creates C_old,new config (both majorities needed)
    Phase 2: Leader creates C_new config (only new majority needed)

  RAFT IN PRODUCTION:
  - etcd (Kubernetes): Raft for metadata consensus
  - CockroachDB: Multi-Raft (one Raft group per range)
  - TiKV: Raft for distributed KV store
  - Consul: Raft for service discovery

═══════════════════════════════════════════════════════════════
PAXOS PROTOCOL (theoretical foundation)
═══════════════════════════════════════════════════════════════

  ROLES:
  Proposer:  Proposes values
  Acceptor:  Votes on proposals
  Learner:   Learns decided value

  BASIC PAXOS (single value):
  Phase 1 — PREPARE:
    Proposer sends Prepare(n) to majority of Acceptors
    Acceptor: if n > highest seen → promise to not accept < n
              return any previously accepted (n_a, v_a)

  Phase 2 — ACCEPT:
    If Proposer gets majority promises:
      If any acceptor returned (n_a, v_a): use highest v_a
      Else: use proposer's own value
      Send Accept(n, v) to majority
    Acceptor: if n ≥ highest promised → accept

  MULTI-PAXOS:
    Elect a stable leader (skip Phase 1 for subsequent proposals)
    Leader can directly do Phase 2 → much faster
    Essentially becomes Raft-like

  WHY RAFT OVER PAXOS:
  - Raft: designed for understandability
  - Paxos: minimal protocol, many gaps for implementation
  - Raft: specifies leader election, log replication, membership
  - Paxos: only specifies single-value agreement

═══════════════════════════════════════════════════════════════
ZAB (ZooKeeper Atomic Broadcast)
═══════════════════════════════════════════════════════════════

  - Used by Apache ZooKeeper
  - Similar to Raft but:
    - Uses epochs (like terms)
    - Recovery phase resyncs follower logs
    - Guarantees total order of all state changes
  - Primary-backup model with ordered broadcasts
  
  PHASES:
  1. Discovery: Find latest epoch and transaction
  2. Synchronization: New leader syncs with followers  
  3. Broadcast: Leader proposes, followers ack, leader commits

═══════════════════════════════════════════════════════════════
VIEWSTAMPED REPLICATION
═══════════════════════════════════════════════════════════════

  - Predecessor to Raft
  - View change protocol for leader failure
  - Normal operation similar to Raft
  - Historical importance, less used in practice

5. Leader Election

LEADER ELECTION PATTERNS:

  1. RAFT-BASED (most common):
     Random election timeout → candidate → majority votes → leader
     Used by: etcd, CockroachDB, Consul

  2. BULLY ALGORITHM:
     Highest-ranked live node becomes leader
     Election: node sends ELECTION to higher-ranked nodes
     If no response → declare self as leader
     If response → wait for COORDINATOR from higher node
     Simple but may elect least-optimal node

  3. RING ALGORITHM:
     Nodes arranged in logical ring
     Election message circulates, collecting candidates
     Highest ID in message becomes leader
     Used in: some peer-to-peer systems

  4. ZOOKEEPER-BASED:
     Ephemeral sequential znodes in /election/
     Smallest sequence number = leader
     Each node watches its predecessor (herd avoidance)
     Used by: Kafka (controller election), HBase

  5. ETCD-BASED LEASE:
     Campaign for leadership using etcd lease
     Leader must periodically renew lease
     If lease expires → new election
     Used by: Kubernetes (controller manager, scheduler)

  LEADER ELECTION CHALLENGES:
  ┌───────────────────────────────────────────────────────────┐
  │ Split Brain:  Two nodes think they're leader             │
  │ → Use fencing tokens (monotonically increasing token     │
  │   issued with each leadership term; resource rejects     │
  │   requests with stale tokens)                            │
  │                                                          │
  │ Thundering Herd: All nodes try to become leader at once  │
  │ → Random backoff, watch predecessor pattern              │
  │                                                          │
  │ Network Partition: Old leader in minority partition      │
  │ → Leader must be able to reach majority to remain leader │
  │ → Old leader steps down if cannot reach quorum           │
  └───────────────────────────────────────────────────────────┘

  LEADERLESS ALTERNATIVE:
  - Some systems avoid leaders entirely
  - All nodes are equal (symmetric)
  - Use quorum reads/writes (W + R > N)
  - Examples: Cassandra, DynamoDB
  - Trade-off: no single-point coordination, but weaker consistency

6. Gossip Protocols

GOSSIP (EPIDEMIC) PROTOCOLS:
  Each node periodically shares state with random peers
  Information spreads exponentially like an epidemic

  HOW IT WORKS:
  ┌────────────────────────────────────────────────────────────┐
  │ Every T seconds:                                          │
  │   1. Node A picks random node B                           │
  │   2. A sends its state digest to B                        │
  │   3. B compares with own state                            │
  │   4. B sends back differences                             │
  │   5. Both update their state                              │
  │                                                           │
  │ Convergence: O(log N) rounds for N nodes                  │
  │ (1000 nodes converge in ~10 rounds!)                      │
  └────────────────────────────────────────────────────────────┘

  GOSSIP STYLES:
  Push:       Send your updates to random peer
  Pull:       Ask random peer for their updates  
  Push-Pull:  Exchange updates bidirectionally (fastest convergence)

  APPLICATIONS:
  ┌────────────────────┬──────────────────────────────────────┐
  │ Membership         │ Track which nodes are alive          │
  │                    │ (Cassandra, DynamoDB)                │
  ├────────────────────┼──────────────────────────────────────┤
  │ Failure Detection  │ Heartbeats via gossip               │
  │                    │ (SWIM protocol)                     │
  ├────────────────────┼──────────────────────────────────────┤
  │ State Dissemination│ Spread config/metadata               │
  │                    │ (Consul, Serf)                      │
  ├────────────────────┼──────────────────────────────────────┤
  │ Aggregate Queries  │ Distributed counts, averages        │
  │                    │ (monitoring systems)                │
  └────────────────────┴──────────────────────────────────────┘

  SWIM PROTOCOL (Scalable Weakly-consistent Infection-style
                  Membership):
  - Direct probe: Ping node, expect ACK
  - Indirect probe: If no ACK, ask K random nodes to ping target
  - If still no ACK → suspect → after timeout → declare dead
  - Piggybacking: Attach membership updates on protocol messages
  - O(1) per-node communication overhead!
  - Used by: Consul (Serf library), Memberlist (HashiCorp)

  CRDT GOSSIP (state-based):
  - Replicas gossip their CRDT state
  - Merge function is commutative, associative, idempotent
  - Guaranteed eventual convergence without coordination

7. Failure Detection

FAILURE DETECTION STRATEGIES:

  HEARTBEAT-BASED:
  ┌────────────────────────────────────────────────────────────┐
  │ Node sends periodic "I'm alive" messages                  │
  │ If no heartbeat within timeout → suspect failure          │
  │                                                           │
  │ Challenges:                                               │
  │   - Timeout too short → false positives (healthy node     │
  │     declared dead due to network blip)                    │
  │   - Timeout too long → slow detection                    │
  │   - GC pauses can cause missed heartbeats                │
  └────────────────────────────────────────────────────────────┘

  PHI ACCRUAL FAILURE DETECTOR:
  ┌────────────────────────────────────────────────────────────┐
  │ Instead of binary alive/dead → outputs suspicion level φ  │
  │                                                           │
  │ Tracks heartbeat arrival times, builds distribution       │
  │ φ = -log₁₀(P(heartbeat_delay ≥ time_since_last))        │
  │                                                           │
  │ φ = 1 → 10% chance of being wrong                       │
  │ φ = 2 → 1% chance                                       │
  │ φ = 3 → 0.1% chance                                     │
  │                                                           │
  │ Application sets threshold based on tolerance             │
  │ Adapts to network conditions automatically                │
  │ Used by: Cassandra, Akka                                 │
  └────────────────────────────────────────────────────────────┘

  SWIM-BASED DETECTION:
  - Direct probe + indirect probe (via random intermediaries)
  - Suspect → Alive (if probe succeeds) or Dead (after timeout)
  - Bounded completeness: every failed node is eventually detected
  - Low false positive rate through indirect probing

  PRACTICAL CONSIDERATIONS:
  ┌───────────────────────────────────────────────────────────┐
  │ 1. Differentiate: crash vs slow vs network partition     │
  │ 2. Use multiple detection mechanisms in parallel         │
  │ 3. Require multiple detectors to agree before action     │
  │ 4. Implement graceful degradation (suspect state)        │
  │ 5. Consider asymmetric partitions (A→B works, B→A fails)│
  │ 6. Log and alert on detection events for debugging       │
  └───────────────────────────────────────────────────────────┘

8. Distributed Locking

DISTRIBUTED LOCKS: Coordinate access to shared resources across nodes.

  WHY IT'S HARD:
  - Lock holder can crash while holding lock
  - Network partition can isolate lock holder
  - GC pauses can delay lock release check
  - Clock skew can cause lease to seem valid when expired

═══════════════════════════════════════════════════════════════
REDIS-BASED LOCKING
═══════════════════════════════════════════════════════════════

  SIMPLE (single Redis):
    LOCK:   SET lock_key unique_value NX PX 30000
    UNLOCK: if GET lock_key == unique_value then DEL lock_key
            (Lua script for atomicity)

  REDLOCK (Martin Kleppmann's critique applies):
    1. Get current time
    2. Try to acquire lock on N/2+1 Redis instances
    3. Lock acquired if majority succeed within timeout
    4. Lock validity = TTL - elapsed_time
    5. If failed, unlock all instances

  PROBLEMS WITH REDLOCK (Kleppmann):
    - Clock jumps can cause lock expiry before expected
    - GC pause after acquiring lock → lock expires →
      another client gets lock → split-brain!
    - Solution: Use fencing tokens

═══════════════════════════════════════════════════════════════
ZOOKEEPER-BASED LOCKING (recommended for correctness)
═══════════════════════════════════════════════════════════════

  1. Create ephemeral sequential node: /locks/resource-000001
  2. Get all children of /locks/
  3. If your node has smallest sequence → you have the lock
  4. Otherwise, watch the node with next-smallest sequence
  5. When that node is deleted → re-check if you're smallest
  6. Auto-release: ephemeral nodes deleted on session timeout

  BENEFITS:
  - Ephemeral nodes auto-cleanup on failure
  - Watch mechanism avoids polling
  - Herd avoidance (only watch predecessor)
  - Session semantics tied to ZK connection

═══════════════════════════════════════════════════════════════
ETCD-BASED LOCKING
═══════════════════════════════════════════════════════════════

  - Uses lease-based approach
  - Create key with lease → key auto-deleted when lease expires
  - Leader election + locking via etcd concurrency package
  - Used by: Kubernetes controllers

═══════════════════════════════════════════════════════════════
FENCING TOKENS (critical safety mechanism)
═══════════════════════════════════════════════════════════════

  Problem: Client A gets lock, pauses (GC), lock expires,
           Client B gets lock, Client A resumes → BOTH think
           they hold the lock!

  Solution:
  ┌────────────────────────────────────────────────────────────┐
  │ Lock service issues monotonically increasing FENCING TOKEN│
  │ with each lock grant.                                     │
  │                                                           │
  │ Client A gets lock (token=33)                             │
  │ Client A pauses... lock expires...                        │
  │ Client B gets lock (token=34)                             │
  │ Client A resumes, sends write with token=33               │
  │ Storage server: 34 > 33 → REJECT Client A's write!       │
  │                                                           │
  │ Requires: storage/resource server to check fencing token  │
  └────────────────────────────────────────────────────────────┘

  ARCHITECT GUIDANCE:
  ┌───────────────────────────────────────────────────────────┐
  │ • If lock is for EFFICIENCY (prevent duplicate work):    │
  │   Redis lock is fine (occasional duplicate is OK)        │
  │ • If lock is for CORRECTNESS (prevent data corruption):  │
  │   Use ZooKeeper/etcd + fencing tokens                    │
  │ • NEVER rely on lock timing for safety                   │
  │ • Always have a TTL to prevent deadlocks                 │
  │ • Make protected operations idempotent when possible     │
  └───────────────────────────────────────────────────────────┘

9. Consistency Models Deep Dive

CONSISTENCY SPECTRUM (weakest → strongest):

  Eventual ──→ Causal ──→ Sequential ──→ Linearizable
  (weakest)                                (strongest)

═══════════════════════════════════════════════════════════════
EVENTUAL CONSISTENCY
═══════════════════════════════════════════════════════════════
  - If no new writes, all replicas converge to same value
  - No guarantee on WHEN convergence happens
  - Reads may return stale data
  - Used by: DNS, Cassandra (tunable), DynamoDB (default)
  - Suitable for: social media feeds, product catalogs

═══════════════════════════════════════════════════════════════
CAUSAL CONSISTENCY  
═══════════════════════════════════════════════════════════════
  - If operation A causally precedes B, everyone sees A before B
  - Concurrent operations can be seen in different orders
  - Preserves "makes sense" ordering without global synchronization
  - Implementation: vector clocks, dependency tracking
  - Used by: MongoDB (causal sessions), COPS
  - Suitable for: comments/replies, collaborative editing

═══════════════════════════════════════════════════════════════
SEQUENTIAL CONSISTENCY
═══════════════════════════════════════════════════════════════
  - All processes see operations in SOME total order
  - That order is consistent with each process's local order
  - But NOT necessarily real-time order
  - Used by: ZooKeeper (within a session)
  - Suitable for: event logs, audit trails

═══════════════════════════════════════════════════════════════
LINEARIZABILITY (strongest)
═══════════════════════════════════════════════════════════════
  - Operations appear to execute atomically at some point
    between their invocation and completion
  - Real-time ordering: if op A completes before op B starts,
    everyone sees A before B
  - "Behaves like a single copy of data"
  - Used by: etcd, Spanner, CockroachDB
  - Suitable for: leader election, distributed locks, counters

  LINEARIZABILITY vs SERIALIZABILITY:
  ┌────────────────────────────────────────────────────────────┐
  │ Linearizability: Single-object, real-time ordering        │
  │ Serializability: Multi-object (transactions), any serial  │
  │                  order is acceptable                       │
  │ Strict Serializability = Linearizable + Serializable      │
  │ (what Spanner provides)                                   │
  └────────────────────────────────────────────────────────────┘

SESSION GUARANTEES (practical middle ground):
  Read Your Writes:   See your own recent writes
  Monotonic Reads:    Never see older data after seeing newer
  Monotonic Writes:   Writes are applied in order per client
  Writes Follow Reads: Write is ordered after prior reads

  These can be provided even with eventual consistency!
  Implementation: route client to same replica, or track
  client's read/write versions.

10. Quorum Systems

QUORUM: The minimum number of nodes that must participate
        in an operation for it to be valid.

  BASIC QUORUM:
  N = total replicas
  W = write quorum (nodes that must acknowledge a write)
  R = read quorum (nodes that must respond to a read)

  RULE: W + R > N → at least one node has the latest value

  EXAMPLES:
  ┌─────────────┬─────────────┬─────────────┬──────────────────┐
  │ Config       │ N=3, W=2,  │ N=3, W=1,  │ N=5, W=3,       │
  │             │ R=2         │ R=3          │ R=3              │
  ├─────────────┼─────────────┼─────────────┼──────────────────┤
  │ Consistency │ Strong      │ Strong       │ Strong           │
  │ Write avail │ Tolerate 1  │ Tolerate 2  │ Tolerate 2       │
  │ Read avail  │ Tolerate 1  │ Tolerate 0  │ Tolerate 2       │
  │ Use case    │ Balanced    │ Write-heavy  │ High availability│
  └─────────────┴─────────────┴─────────────┴──────────────────┘

  SLOPPY QUORUM (DynamoDB):
  - During partition, write to ANY N healthy nodes (not just designated)
  - "Hinted handoff": temporary holder forwards data when original recovers
  - Provides higher availability but weaker consistency
  - Not a true quorum — W + R > N doesn't guarantee latest value

  READ REPAIR:
  - During quorum read, if some nodes have stale data
  - Coordinator sends latest value to stale nodes
  - Background process (anti-entropy) also repairs periodically

  WITNESS REPLICAS:
  - Lightweight replicas that participate in quorum but don't
    store full data — only enough to determine which write is latest
  - Reduces storage cost for high-replication setups

11. CRDTs — Conflict-Free Replicated Data Types

CRDT: Data structures that can be replicated across nodes and
      merged automatically without coordination or conflicts.

  WHY CRDTs:
  - No coordination needed (no consensus, no locking)
  - Always available (AP in CAP)
  - Mathematically guaranteed convergence
  - Trade-off: limited data structure types, eventual consistency

  TWO TYPES:
  ┌──────────────────────────────────────────────────────────┐
  │ State-based (CvRDT):                                    │
  │   Replicas send full state, merge with join function     │
  │   Merge must be: commutative, associative, idempotent    │
  │   Higher bandwidth, simpler to implement                 │
  │                                                          │
  │ Operation-based (CmRDT):                                 │
  │   Replicas send operations, apply in any order           │
  │   Requires reliable broadcast (at-least-once delivery)   │
  │   Lower bandwidth, more complex                          │
  └──────────────────────────────────────────────────────────┘

  COMMON CRDTs:
  ┌───────────────────┬──────────────────────────────────────┐
  │ G-Counter         │ Grow-only counter (each node has own │
  │                   │ count, total = sum of all)           │
  ├───────────────────┼──────────────────────────────────────┤
  │ PN-Counter        │ Positive-Negative counter (G-Counter │
  │                   │ for increments + G-Counter for       │
  │                   │ decrements, value = P - N)           │
  ├───────────────────┼──────────────────────────────────────┤
  │ G-Set             │ Grow-only set (only additions)       │
  ├───────────────────┼──────────────────────────────────────┤
  │ OR-Set            │ Observed-Remove set (add + remove    │
  │ (Add-Wins)        │ with unique tags; add wins conflicts)│
  ├───────────────────┼──────────────────────────────────────┤
  │ LWW-Register      │ Last-Writer-Wins register            │
  │                   │ (timestamp-based conflict resolution) │
  ├───────────────────┼──────────────────────────────────────┤
  │ MV-Register       │ Multi-Value register (keeps all      │
  │                   │ concurrent values — app resolves)     │
  ├───────────────────┼──────────────────────────────────────┤
  │ LWW-Element-Graph │ For graph structures (edges + nodes  │
  │                   │ with LWW semantics)                  │
  ├───────────────────┼──────────────────────────────────────┤
  │ RGA              │ Replicated Growable Array             │
  │                   │ (ordered list for collaborative edit)│
  └───────────────────┴──────────────────────────────────────┘

  REAL-WORLD USAGE:
  - Redis CRDB (conflict-free replicated database)
  - Riak (all data types are CRDTs)
  - Apple Notes (collaborative editing)
  - Figma (collaborative design)
  - Phoenix LiveView (distributed presence)

  LIMITATIONS:
  - Cannot express all operations (no "check-then-act")
  - Metadata overhead (tombstones, version vectors)
  - Garbage collection of tombstones is complex
  - Some operations are unintuitive (remove + re-add)

12. Distributed Snapshots

DISTRIBUTED SNAPSHOT: Capture consistent global state of a
distributed system without stopping it.

  CHANDY-LAMPORT ALGORITHM:
  ┌────────────────────────────────────────────────────────────┐
  │ 1. Initiator saves its own state                          │
  │ 2. Sends MARKER on all outgoing channels                  │
  │ 3. On receiving MARKER (first time on a channel):         │
  │    a. Save own state                                      │
  │    b. Record channel state = messages received between     │
  │       own snapshot and marker on that channel              │
  │    c. Send MARKER on all outgoing channels                │
  │ 4. On receiving MARKER (subsequent times):                │
  │    Stop recording that channel's state                    │
  │ 5. Snapshot complete when all channels have received MARKER│
  └────────────────────────────────────────────────────────────┘

  REQUIREMENTS:
  - FIFO channels (messages arrive in order)
  - Reliable delivery (no message loss)

  USE CASES:
  - Checkpointing for fault tolerance (Flink, Spark)
  - Deadlock detection
  - Garbage collection across distributed heap
  - Debugging (capture system state at point in time)

  APACHE FLINK CHECKPOINTING:
  - Based on Chandy-Lamport
  - Barrier alignment: barriers flow through the stream graph
  - On barrier receipt: operator snapshots state to durable storage
  - Enables exactly-once processing with checkpoints
  - Unaligned checkpoints: barriers can overtake data records
    (reduces checkpoint latency at cost of state size)

13. Exactly-Once Semantics

DELIVERY GUARANTEES:
  At-Most-Once:  Send and forget. May lose messages.
  At-Least-Once: Retry until acknowledged. May duplicate.
  Exactly-Once:  Each message processed exactly once.

  THE TRUTH: Exactly-once DELIVERY is impossible in theory.
  But exactly-once PROCESSING is achievable!

  HOW TO ACHIEVE EXACTLY-ONCE PROCESSING:
  ┌────────────────────────────────────────────────────────────┐
  │ At-Least-Once Delivery + Idempotent Processing            │
  │                         = Exactly-Once Semantics           │
  └────────────────────────────────────────────────────────────┘

  IDEMPOTENCY STRATEGIES:
  ┌───────────────────┬──────────────────────────────────────┐
  │ Natural idempotent│ SET x = 5 (repeating has no effect)  │
  │                   │ vs SET x = x + 1 (NOT idempotent)   │
  ├───────────────────┼──────────────────────────────────────┤
  │ Deduplication ID  │ Store processed message IDs          │
  │                   │ Reject if ID already processed       │
  │                   │ Client generates UUID for each op    │
  ├───────────────────┼──────────────────────────────────────┤
  │ Conditional write │ UPDATE ... WHERE version = N         │
  │                   │ Only succeeds if version matches     │
  ├───────────────────┼──────────────────────────────────────┤
  │ Outbox pattern    │ Write event + business data in same  │
  │                   │ transaction. Separate publisher      │
  │                   │ reads outbox and publishes.          │
  └───────────────────┴──────────────────────────────────────┘

  KAFKA EXACTLY-ONCE:
  ┌────────────────────────────────────────────────────────────┐
  │ Producer:                                                 │
  │   Idempotent producer (enable.idempotence=true)           │
  │   Assigns sequence number per partition                   │
  │   Broker deduplicates by (producer_id, sequence)          │
  │                                                           │
  │ Transactional producer:                                   │
  │   Atomic writes across multiple partitions                │
  │   begin_transaction() → produce() → commit()             │
  │                                                           │
  │ Consumer:                                                 │
  │   Read committed isolation (read_committed)               │
  │   Only see committed transactional messages               │
  │   Consume-transform-produce pattern:                      │
  │   read → process → write output + offset in SAME txn     │
  └────────────────────────────────────────────────────────────┘

14. Split-Brain and Network Partitions

SPLIT-BRAIN: Two or more parts of a distributed system
operate independently, each believing it is the sole authority.

  CAUSES:
  - Network partition between data centers
  - Switch/router failure
  - Firewall misconfiguration
  - DNS failure causing one-way communication

  CONSEQUENCES:
  - Two leaders accepting writes → data divergence
  - Conflicting decisions → data corruption
  - Resource contention → wasted compute

  PREVENTION STRATEGIES:
  ┌────────────────────────────────────────────────────────────┐
  │ 1. QUORUM-BASED                                           │
  │    Require majority (N/2+1) to make progress              │
  │    Minority partition automatically becomes read-only      │
  │    Used by: Raft, Paxos, ZooKeeper                       │
  │                                                           │
  │ 2. FENCING (STONITH)                                      │
  │    "Shoot The Other Node In The Head"                     │
  │    If node can't reach peers → power off the old leader   │
  │    Or: use fencing tokens (see distributed locking)       │
  │    Used by: Pacemaker/Corosync, cloud VMs (API kill)     │
  │                                                           │
  │ 3. EXTERNAL ARBITER                                       │
  │    Third-party witness node breaks ties                   │
  │    Must be in separate failure domain                     │
  │    Cloud: use a different AZ or region for witness        │
  │                                                           │
  │ 4. LEASE-BASED LEADERSHIP                                 │
  │    Leader must renew lease periodically                   │
  │    If lease expires, leader steps down                    │
  │    New election only after lease timeout                  │
  │    Clock skew risk: use conservative lease duration       │
  └────────────────────────────────────────────────────────────┘

  CONFLICT RESOLUTION (when split-brain has occurred):
  - Last-Writer-Wins (LWW): Simple but loses data
  - Merge: Application-specific merge logic
  - CRDTs: Automatic conflict-free merging
  - Human resolution: Flag conflicts for manual review
  - Version vectors: Detect concurrent writes, present to app

15. Byzantine Fault Tolerance

BYZANTINE FAILURE: Node sends different, potentially malicious
information to different peers. Named after the Byzantine
Generals Problem (Lamport, 1982).

  WHEN TO CARE:
  - Blockchain / cryptocurrency networks
  - Multi-organization systems (no mutual trust)
  - Safety-critical systems (aerospace, medical)
  - NOT typical for: internal datacenter systems

  REQUIREMENTS:
  3f + 1 nodes needed to tolerate f Byzantine faults
  (f = 1 → need 4 nodes; f = 2 → need 7 nodes)

  PBFT (Practical Byzantine Fault Tolerance):
  ┌────────────────────────────────────────────────────────────┐
  │ 1. Pre-prepare: Primary broadcasts request with sequence  │
  │ 2. Prepare: Each replica broadcasts PREPARE to all others │
  │ 3. Commit: After 2f+1 PREPAREs, broadcast COMMIT         │
  │ 4. Reply: After 2f+1 COMMITs, execute and reply to client│
  │                                                           │
  │ Complexity: O(N²) messages per operation                  │
  │ Practical for: small clusters (4-20 nodes)               │
  └────────────────────────────────────────────────────────────┘

  BLOCKCHAIN CONSENSUS:
  - Proof of Work (Bitcoin): computational puzzle
  - Proof of Stake (Ethereum 2.0): stake-based voting
  - Tendermint/Cosmos: BFT-based for permissioned chains

  FOR ARCHITECTS:
  Most internal systems assume crash-fault model, not Byzantine.
  Use checksums + TLS + authentication to prevent most
  "Byzantine-like" issues in datacenter environments.

16. Backpressure and Flow Control

BACKPRESSURE: When a downstream service cannot keep up with
upstream traffic, signal the upstream to slow down.

  WITHOUT BACKPRESSURE:
  ┌────────────────────────────────────────────────────────────┐
  │ Producer (fast) → Consumer (slow)                         │
  │                                                           │
  │ Buffer grows → OOM → crash                               │
  │ OR: Drop messages → data loss                            │
  │ OR: Cascading failures → system-wide outage              │
  └────────────────────────────────────────────────────────────┘

  BACKPRESSURE STRATEGIES:
  ┌──────────────────┬───────────────────────────────────────┐
  │ Drop             │ Discard excess messages               │
  │                  │ (metrics, logs — acceptable loss)     │
  ├──────────────────┼───────────────────────────────────────┤
  │ Buffer           │ Queue messages temporarily            │
  │                  │ (bounded buffer + drop oldest/newest) │
  ├──────────────────┼───────────────────────────────────────┤
  │ Block            │ Stop accepting new requests           │
  │                  │ (TCP flow control, sync APIs)        │
  ├──────────────────┼───────────────────────────────────────┤
  │ Signal           │ Tell producer to slow down            │
  │                  │ (HTTP 429, Kafka consumer lag metric) │
  ├──────────────────┼───────────────────────────────────────┤
  │ Auto-scale       │ Scale consumers to match load         │
  │                  │ (K8s HPA, Lambda concurrency)        │
  └──────────────────┴───────────────────────────────────────┘

  REACTIVE STREAMS SPECIFICATION:
  - Publisher → Subscriber with demand-driven flow
  - Subscriber requests N items (backpressure signal)
  - Publisher sends at most N items
  - Frameworks: Project Reactor, RxJava, Akka Streams

  PRACTICAL PATTERNS:
  - Rate limiting at API gateway (prevent overload)
  - Circuit breaker (fast-fail when downstream is slow)
  - Load shedding (drop low-priority requests under pressure)
  - Admission control (reject requests above capacity)
  - Queue depth monitoring + auto-scaling

18. Production War Stories and Lessons

LESSON 1: THE GC PAUSE THAT CAUSED SPLIT-BRAIN
  Scenario: ZooKeeper leader had 15-second GC pause
  Impact: Followers elected new leader. Old leader resumed,
          sent stale data to clients.
  Fix: Fencing tokens, shorter ZK session timeouts,
       tuned GC (shorter, more frequent collections)

LESSON 2: THE CASCADE FAILURE
  Scenario: One service slowed down due to DB query.
  Impact: Thread pools exhausted in callers → they slowed →
          their callers slowed → entire system froze.
  Fix: Circuit breakers, bulkheads (separate thread pools),
       timeout on every inter-service call, load shedding.

LESSON 3: THE THUNDERING HERD
  Scenario: Cache expired for popular key. 10,000 concurrent
           requests all hit the database simultaneously.
  Impact: Database CPU 100%, cascading failures.
  Fix: Single-flight pattern (only one request populates cache),
       staggered TTLs, cache warming before expiry.

LESSON 4: THE CLOCK SKEW INCIDENT
  Scenario: TTL-based cache used wall-clock time.
           One server's clock was 30 minutes ahead.
  Impact: That server's cache entries expired 30 min early,
          causing constant cache misses → DB overload.
  Fix: Use monotonic clocks for durations, NTP monitoring,
       alerting on clock skew > threshold.

LESSON 5: THE RETRY STORM
  Scenario: Service returned 503 under load.
  Impact: All clients retried immediately → 3× load → more
          503s → more retries → exponential load growth.
  Fix: Exponential backoff with jitter, circuit breakers,
       server-side retry budgets, client-side retry limits.

LESSON 6: THE METADATA STORE BOTTLENECK
  Scenario: All services queried a single config/metadata service.
  Impact: Metadata service became SPOF. Any slowdown
          cascaded to entire infrastructure.
  Fix: Cache metadata locally with TTL, use gossip for
       propagation, multiple read replicas, graceful
       degradation with stale config.

ARCHITECT TAKEAWAYS:
  ┌────────────────────────────────────────────────────────────┐
  │ 1. EVERY timeout is a design decision — choose carefully  │
  │ 2. Retries without backoff+jitter = self-DDoS             │
  │ 3. Shared dependencies are hidden SPOFs                   │
  │ 4. GC pauses are equivalent to network partitions         │
  │ 5. Monitor everything, but especially tail latencies      │
  │ 6. Design for failure: test it (chaos engineering)        │
  │ 7. Keep blast radius small (bulkheads, failure domains)   │
  │ 8. Humans are the leading cause of outages (automate)     │
  └────────────────────────────────────────────────────────────┘

20. Interview Deep Dive

LinearizabilitySerializabilityStrict serializabilityCRDTsConsensusChallenge

Q1: Explain the difference between linearizability and serializability.

A: Linearizability is a single-object guarantee — each operation appears to take effect atomically at some point between its invocation and response, respecting real-time order. Serializability is a multi-object (transaction) guarantee — the result is equivalent to some serial execution of transactions, but doesn't require real-time ordering. Strict serializability = both combined. Spanner achieves this using TrueTime. In practice: use linearizable reads for leader election (etcd), serializable transactions for banking (PostgreSQL).

Q2: How does Raft handle a network partition?

A: If the leader is in the majority partition, it continues normally. Nodes in the minority cannot form a quorum, so they can't elect a new leader or commit writes — they effectively become read-only (stale). If the leader is in the minority, it can't commit any new entries (can't get majority ACKs). The majority partition's followers time out and elect a new leader. When the partition heals, the old leader discovers a higher term, steps down to follower, and its uncommitted log entries are overwritten by the new leader's log.

Q3: When would you use CRDTs vs consensus?

A: CRDTs when: (1) You need always-available writes (AP). (2) Data types fit CRDT models (counters, sets, registers). (3) Conflict resolution semantics are acceptable. (4) Multi-datacenter with unreliable links. Examples: collaborative editing, distributed counters, shopping carts. Consensus when: (1) Strong consistency required (CP). (2) Exactly-one leader decisions. (3) Configuration management, leader election. (4) Financial transactions. Trade-off: CRDTs = no coordination overhead but limited data models; consensus = stronger guarantees but higher latency and lower availability during partitions.

Q4: Design a distributed rate limiter for a global API gateway.

A: Challenge: Rate limiting across multiple geographically distributed nodes. Approach 1 — Local + Gossip: Each node enforces local limits, gossip-propagates counters. Allows temporary over-limit but converges. Simple, highly available. Approach 2 — Centralized Redis: All nodes check a shared Redis. Accurate but adds latency and introduces SPOF. Approach 3 — Token bucket per region + global sync: Each region gets allocated portion of global rate. Periodic sync adjusts allocation. Under-utilized regions donate tokens. Architecture: API Gateway → local sliding window → async sync to global counter (Redis Cluster). Allow 10% burst over limit for availability. Use client ID + consistent hashing to route to same counter node.

Q5: Explain the Saga pattern. When would you use choreography vs orchestration?

A: Saga: A sequence of local transactions where each step has a compensating action for rollback. Used instead of distributed transactions (2PC). Choreography: Services publish events, next service reacts. Pros: decoupled, no single point of failure. Cons: hard to debug (no central view), cyclic dependencies possible, difficult to understand flow. Best for: simple sagas with few steps, loosely coupled teams. Orchestration: Central coordinator directs each step. Pros: easy to understand flow, centralized monitoring, simpler error handling. Cons: coordinator is a potential SPOF, tighter coupling to coordinator. Best for: complex sagas with many steps, when visibility is important. My preference for most production systems: Orchestration with the Temporal workflow engine — gives durability, visibility, and retry semantics out of the box.

Q6: How would you design a system that needs to be consistent across 3 data centers?

A: Option 1 — Synchronous Raft across DCs (Spanner-like): Raft group spans 3 DCs, leader in one DC. Writes require majority (2 of 3 DCs). Latency = cross-DC RTT (~50-150ms per write). Best for: banking, inventory. Option 2 — Async replication + conflict resolution: Primary DC handles writes, async replicate. On failover, resolve conflicts (LWW or CRDTs). Lower write latency but eventual consistency. Option 3 — Partitioned by geography: Each DC is primary for its region's data. Cross-region reads go to nearest replica. Best for: user data with geographic locality. My recommendation: Start with Option 3 (locality-based partitioning). For globally consistent data (e.g., usernames, billing), use Option 1 with a small, critical Raft group. For the rest, use Option 2 with CRDTs where possible.

Q7: What is the thundering herd problem? Give three solutions.

A: When a popular cache key expires, thousands of concurrent requests simultaneously hit the database to repopulate it, potentially crashing the DB. Solutions: (1) Single-flight / request coalescing: Only one request fetches from DB; others wait for its result. Implement with a mutex or promise per key. (2) Staggered TTLs with jitter: Instead of TTL=3600, use TTL=3600 + random(0,600). Keys expire at different times. (3) Probabilistic early recomputation: Each request has a small probability of refreshing the cache BEFORE expiry. Higher probability as TTL approaches. (4) Cache warming: Background job refreshes hot keys before they expire based on access frequency tracking.

Q8: Explain fencing tokens and why they matter.

A: Fencing tokens solve the problem of stale lock holders. When a distributed lock service grants a lock, it also issues a monotonically increasing integer (fencing token). The lock holder includes this token with every operation on the protected resource. The resource server tracks the highest token it has seen and rejects any request with a lower token. This prevents a scenario where Client A gets lock (token=33), pauses (GC), lock expires, Client B gets lock (token=34), Client A resumes and tries to write — the resource rejects token=33 because it has seen 34. Critical for any system where lock-protected operations must be linearizable. ZooKeeper's sequential znodes naturally provide fencing tokens.

2. B-Tree Storage

B-TREE: Balanced tree structure. The most widely used
index type in databases for 40+ years.

  STRUCTURE:
  ┌────────────────────────────────────────────────────────────┐
  │                  [Root Page]                               │
  │                  [10 | 20 | 30]                           │
  │                 /    |     |    \                          │
  │        [1-9]    [10-19] [20-29] [30-39]                   │
  │        /  \       / \     / \     / \                     │
  │    [leaf] [leaf] [leaf] [leaf] [leaf] [leaf]               │
  │    pages  pages  pages  pages  pages  pages               │
  │                                                           │
  │ Leaf pages contain actual data pointers (or data itself)  │
  │ Each page = fixed size (typically 4KB-16KB)               │
  │ Branching factor: ~100-500 keys per page                  │
  │ Depth: 3-4 levels covers billions of rows                 │
  └────────────────────────────────────────────────────────────┘

  OPERATIONS:
  READ:  Traverse root → internal → leaf = O(log_b N)
         b = branching factor (100-500)
         4 levels with b=500: 500^4 = 62.5 billion keys!
         Practically: 3-4 disk reads max

  WRITE: Find correct leaf page → update in place
         If page full → split into two pages → update parent
         Write-ahead log (WAL) for crash recovery

  B+ TREE (what databases actually use):
  ┌────────────────────────────────────────────────────────────┐
  │ - Only leaf nodes contain data/pointers                   │
  │ - Internal nodes only contain keys for routing            │
  │ - Leaf nodes linked as doubly-linked list                 │
  │ - Enables efficient range scans (follow leaf links)       │
  │ - Higher branching factor (more keys per internal page)  │
  └────────────────────────────────────────────────────────────┘

  PERFORMANCE CHARACTERISTICS:
  ┌──────────────────┬──────────────────────────────────────────┐
  │ Point lookup     │ O(log N) — excellent                    │
  │ Range scan       │ O(log N + K) — excellent (K = results) │
  │ Insert           │ O(log N) — good, but page splits costly │
  │ Update           │ O(log N) — in-place update              │
  │ Delete           │ O(log N) — mark deleted, later compact  │
  │ Space amplification│ ~1.0-1.5× (fragmentation)            │
  │ Write amplification│ 1-2× (WAL + page write)              │
  └──────────────────┴──────────────────────────────────────────┘

  FRAGMENTATION:
  - Deletes leave holes in pages
  - Page splits create half-full pages
  - Over time: wasted space, slower sequential scans
  - Fix: VACUUM (PostgreSQL), OPTIMIZE TABLE (MySQL)
•

3. LSM-Tree Storage

LSM-TREE (Log-Structured Merge-Tree):
Optimize writes by buffering in memory, then flushing
sorted runs to disk. Background compaction merges runs.

  ARCHITECTURE:
  ┌────────────────────────────────────────────────────────────┐
  │                                                           │
  │  Write → MemTable (in-memory sorted tree, e.g., red-black)│
  │              │                                            │
  │              │ (when full, ~64MB)                         │
  │              ↓                                            │
  │         Flush to disk as SSTable (Sorted String Table)    │
  │              │                                            │
  │              ↓                                            │
  │  Level 0: [SST-1] [SST-2] [SST-3] (may overlap)         │
  │              │                                            │
  │              │ (compaction merges)                        │
  │              ↓                                            │
  │  Level 1: [SST-A] [SST-B] [SST-C] (non-overlapping)     │
  │              │                                            │
  │              │ (compaction merges)                        │
  │              ↓                                            │
  │  Level 2: [SST-X] [SST-Y] [SST-Z] (larger, non-overlap) │
  │                                                           │
  │  Each level is ~10× larger than the previous             │
  └────────────────────────────────────────────────────────────┘

  SSTABLE (Sorted String Table):
  ┌────────────────────────────────────────────────────────────┐
  │ - Immutable file on disk                                  │
  │ - Keys sorted within the file                             │
  │ - Contains: data blocks + index block + bloom filter      │
  │ - Bloom filter: quickly check "is key POSSIBLY here?"    │
  │   (false positives possible, false negatives impossible)  │
  │ - Once written, never modified (append-only)              │
  └────────────────────────────────────────────────────────────┘

  WRITE PATH:
  1. Write to WAL (crash recovery)
  2. Write to MemTable (in-memory)
  3. When MemTable full → become immutable, new MemTable starts
  4. Background flush: immutable MemTable → SSTable on disk
  5. Background compaction: merge SSTables, remove duplicates

  READ PATH:
  1. Check MemTable (in-memory)
  2. Check immutable MemTables
  3. Check Level 0 SSTables (bloom filter first)
  4. Check Level 1 → Level 2 → ... (bloom filter first)
  5. Binary search within SSTable if bloom filter positive

  COMPACTION STRATEGIES:
  ┌──────────────────┬──────────────────────────────────────────┐
  │ Size-Tiered      │ Merge similarly-sized SSTables           │
  │ (STCS)           │ Good write throughput, more space        │
  │                  │ Used by: Cassandra (default), HBase      │
  ├──────────────────┼──────────────────────────────────────────┤
  │ Leveled          │ Each level has fixed size, merge into    │
  │ (LCS)            │ next level. Better read performance.     │
  │                  │ Higher write amplification.              │
  │                  │ Used by: RocksDB, LevelDB                │
  ├──────────────────┼──────────────────────────────────────────┤
  │ FIFO             │ Delete oldest SSTables (time-series)     │
  │                  │ No merge, very fast writes               │
  │                  │ Used for: TTL-based data (metrics)       │
  └──────────────────┴──────────────────────────────────────────┘

  PERFORMANCE CHARACTERISTICS:
  ┌──────────────────┬──────────────────────────────────────────┐
  │ Point lookup     │ O(L × log N) — bloom filters help       │
  │ Range scan       │ Merge across levels — slower than B-tree│
  │ Write            │ O(1) amortized — sequential I/O         │
  │ Space amplification│ 1.1-2.0× (compaction overhead)       │
  │ Write amplification│ 10-30× (data rewritten in compaction)│
  │ Read amplification│ 1-5× (check multiple levels)          │
  └──────────────────┴──────────────────────────────────────────┘

  B-TREE vs LSM-TREE DECISION:
  ┌──────────────────┬──────────────────┬──────────────────────┐
  │                  │ B-Tree           │ LSM-Tree             │
  ├──────────────────┼──────────────────┼──────────────────────┤
  │ Read-heavy       │ ✓ Better         │                      │
  │ Write-heavy      │                  │ ✓ Better             │
  │ Range scans      │ ✓ Better         │                      │
  │ Write throughput │                  │ ✓ Much better        │
  │ Predictable perf │ ✓ Better         │ (compaction spikes)  │
  │ Space efficiency │                  │ ✓ (with compaction)  │
  │ Transactions     │ ✓ Easier (locks) │ Harder (MVCC needed) │
  │ SSD-friendly     │ Good             │ ✓ Sequential writes  │
  └──────────────────┴──────────────────┴──────────────────────┘

4. Write-Ahead Log (WAL)

WAL: Before modifying actual data, write the change
to a sequential log file. If crash occurs, replay log.

  WHY WAL:
  ┌────────────────────────────────────────────────────────────┐
  │ Problem: Database crash mid-write → corrupted data        │
  │                                                           │
  │ Solution:                                                 │
  │ 1. Write change to WAL (sequential, fast)                │
  │ 2. Respond to client (durable)                           │
  │ 3. Apply change to actual data pages (async/background)  │
  │                                                           │
  │ On crash recovery:                                        │
  │ 1. Read WAL from last checkpoint                         │
  │ 2. Replay any committed but unapplied changes            │
  │ 3. Rollback any uncommitted changes                      │
  └────────────────────────────────────────────────────────────┘

  WAL USES BEYOND CRASH RECOVERY:
  ┌──────────────────┬──────────────────────────────────────────┐
  │ Replication      │ Ship WAL to replicas (PostgreSQL        │
  │                  │ streaming replication, MySQL binlog)     │
  ├──────────────────┼──────────────────────────────────────────┤
  │ CDC              │ Read WAL for change data capture        │
  │                  │ (Debezium reads PostgreSQL WAL)         │
  ├──────────────────┼──────────────────────────────────────────┤
  │ Point-in-time    │ Base backup + replay WAL to any point   │
  │ recovery         │ in time (PITR)                          │
  ├──────────────────┼──────────────────────────────────────────┤
  │ Consensus        │ Raft log is essentially a WAL           │
  │                  │ (replicated state machine)              │
  └──────────────────┴──────────────────────────────────────────┘

  WAL PERFORMANCE:
  - Sequential writes → optimal for both HDD and SSD
  - Can be batched (group commit): multiple transactions
    committed together → amortize fsync cost
  - Compression: WAL can be compressed to reduce I/O
  - WAL segment rotation: old segments archived or deleted

5. Transaction Isolation Levels

ISOLATION LEVELS define what anomalies a transaction
can see from concurrent transactions.

  ANOMALIES:
  ┌────────────────────────────────────────────────────────────┐
  │ DIRTY READ:                                               │
  │   T1 writes A = 100                                       │
  │   T2 reads A = 100                                        │
  │   T1 rolls back (A reverts to 50)                         │
  │   T2 used A = 100 (which was never committed!)           │
  │                                                           │
  │ NON-REPEATABLE READ:                                      │
  │   T1 reads A = 50                                         │
  │   T2 updates A = 100, commits                             │
  │   T1 reads A = 100 (different from first read!)          │
  │                                                           │
  │ PHANTOM READ:                                             │
  │   T1 reads: SELECT * WHERE age > 25 → 10 rows            │
  │   T2 inserts a row with age = 30, commits                 │
  │   T1 reads same query → 11 rows (new row appeared!)      │
  │                                                           │
  │ WRITE SKEW:                                               │
  │   Constraint: at least 1 doctor on call                   │
  │   T1: reads 2 doctors on call, removes self              │
  │   T2: reads 2 doctors on call, removes self              │
  │   Result: 0 doctors on call! (both committed)            │
  │   Neither saw the other's write.                         │
  └────────────────────────────────────────────────────────────┘

  ISOLATION LEVELS:
  ┌────────────────────┬────────┬──────────┬─────────┬────────┐
  │ Level              │ Dirty  │ Non-Rep  │ Phantom │ Write  │
  │                    │ Read   │ Read     │ Read    │ Skew   │
  ├────────────────────┼────────┼──────────┼─────────┼────────┤
  │ Read Uncommitted   │ ✗ Yes  │ ✗ Yes    │ ✗ Yes   │ ✗ Yes  │
  │ Read Committed     │ ✓ No   │ ✗ Yes    │ ✗ Yes   │ ✗ Yes  │
  │ Repeatable Read    │ ✓ No   │ ✓ No     │ ✗ Yes*  │ ✗ Yes  │
  │ Serializable       │ ✓ No   │ ✓ No     │ ✓ No    │ ✓ No   │
  └────────────────────┴────────┴──────────┴─────────┴────────┘
  * PostgreSQL RR actually prevents phantoms too (MVCC snapshot)

  DATABASE DEFAULTS:
  ┌────────────────────┬───────────────────────────────────────┐
  │ PostgreSQL         │ Read Committed (default)              │
  │                    │ Repeatable Read (MVCC snapshot)       │
  │                    │ Serializable (SSI — no locks!)       │
  ├────────────────────┼───────────────────────────────────────┤
  │ MySQL (InnoDB)     │ Repeatable Read (default)             │
  │                    │ Uses gap locks to prevent phantoms    │
  ├────────────────────┼───────────────────────────────────────┤
  │ SQL Server         │ Read Committed (default, locking)     │
  │                    │ Read Committed Snapshot (MVCC option) │
  ├────────────────────┼───────────────────────────────────────┤
  │ Oracle             │ Read Committed (default)              │
  │                    │ Serializable (MVCC-based)             │
  └────────────────────┴───────────────────────────────────────┘

  SERIALIZABLE SNAPSHOT ISOLATION (SSI):
  ┌────────────────────────────────────────────────────────────┐
  │ PostgreSQL's serializable uses SSI (no locks!):           │
  │                                                           │
  │ 1. Each transaction gets a snapshot (like MVCC)           │
  │ 2. Track read/write dependencies between transactions    │
  │ 3. If a dangerous cycle is detected → abort one tx       │
  │ 4. Optimistic: assumes no conflict, aborts if detected   │
  │                                                           │
  │ Benefits vs 2PL (two-phase locking):                      │
  │ - No blocking: readers never block writers               │
  │ - No deadlocks: just abort and retry                     │
  │ - Better performance for read-heavy workloads            │
  │                                                           │
  │ Cost: Occasional aborts (must retry transactions)        │
  └────────────────────────────────────────────────────────────┘

6. MVCC — Multi-Version Concurrency Control

MVCC: Keep multiple versions of each row. Readers see
a snapshot from their transaction start time.
Writers create new versions instead of updating in place.

  HOW IT WORKS (PostgreSQL):
  ┌────────────────────────────────────────────────────────────┐
  │ Each row has:                                             │
  │   xmin: Transaction ID that created this version          │
  │   xmax: Transaction ID that deleted/updated this version  │
  │                                                           │
  │ INSERT: Create row with xmin=current_txid, xmax=null     │
  │ UPDATE: Set xmax on old row, create new row with new xmin│
  │ DELETE: Set xmax on the row                               │
  │                                                           │
  │ READ: Only see rows where:                                │
  │   xmin is committed AND before my snapshot                │
  │   xmax is not set OR xmax is not committed                │
  │   OR xmax is after my snapshot                            │
  │                                                           │
  │ Result: Readers never block writers!                      │
  │ Writers never block readers!                              │
  └────────────────────────────────────────────────────────────┘

  EXAMPLE:
  ┌────────────────────────────────────────────────────────────┐
  │ Time   T1 (snapshot at t=5)     T2                        │
  │ t=1    BEGIN                                              │
  │ t=2    SELECT balance → 100                               │
  │ t=3                              BEGIN                    │
  │ t=4                              UPDATE balance=200       │
  │ t=5                              COMMIT                   │
  │ t=6    SELECT balance → 100     (T1 still sees old value!)│
  │ t=7    COMMIT                                             │
  │                                                           │
  │ T1's snapshot was taken before T2 committed, so T1        │
  │ sees the version from before T2's update.                │
  └────────────────────────────────────────────────────────────┘

  VACUUM (PostgreSQL):
  - Dead rows (old versions) accumulate
  - VACUUM reclaims space from dead rows
  - autovacuum runs automatically (configure thresholds)
  - Without VACUUM: table bloat, index bloat, wraparound risk
  - Monitor: pg_stat_user_tables.n_dead_tup

  MYSQL INNODB MVCC:
  - Uses undo log instead of multiple row versions
  - Read view: list of active transaction IDs at snapshot
  - Undo log chained backward: follow chain to find visible version
  - Purge thread: clean up old undo records

7. Replication Protocols

REPLICATION: Keeping copies of data on multiple nodes.

  REPLICATION MODES:
  ┌────────────────────────────────────────────────────────────┐
  │ SYNCHRONOUS:                                              │
  │   Primary waits for ALL replicas to acknowledge           │
  │   + Strong consistency                                    │
  │   - Higher write latency                                  │
  │   - Single slow replica blocks all writes                 │
  │   Used by: Spanner, CockroachDB (Raft-based)             │
  │                                                           │
  │ ASYNCHRONOUS:                                             │
  │   Primary responds to client immediately                  │
  │   Replicas apply changes later                            │
  │   + Low write latency                                     │
  │   - Data loss risk (committed but not replicated)         │
  │   - Replication lag (reads from replica may be stale)     │
  │   Used by: PostgreSQL (default), MySQL (default)          │
  │                                                           │
  │ SEMI-SYNCHRONOUS:                                         │
  │   Primary waits for at least ONE replica to acknowledge   │
  │   + Balance of consistency and performance                │
  │   - If that one replica is slow, writes are slow         │
  │   Used by: PostgreSQL (synchronous_standby_names),        │
  │            MySQL (semi-sync replication)                   │
  └────────────────────────────────────────────────────────────┘

  REPLICATION TOPOLOGIES:
  ┌────────────────────────────────────────────────────────────┐
  │ SINGLE-LEADER (Primary-Replica):                          │
  │   All writes → Primary → Replicate to Replicas            │
  │   Reads from any replica (eventual consistency)           │
  │   Simplest. Used by: PostgreSQL, MySQL, MongoDB           │
  │                                                           │
  │ MULTI-LEADER:                                             │
  │   Writes to any leader → replicate to others              │
  │   Conflict resolution needed (LWW, merge, CRDT)          │
  │   Used by: CockroachDB, multi-DC setups                  │
  │                                                           │
  │ LEADERLESS:                                               │
  │   Write to any N nodes, read from R nodes                 │
  │   W + R > N → guaranteed to see latest write              │
  │   Used by: Cassandra, DynamoDB, Riak                     │
  └────────────────────────────────────────────────────────────┘

  REPLICATION LAG EFFECTS:
  ┌────────────────────────────────────────────────────────────┐
  │ 1. Read-your-writes violation:                            │
  │    User writes → reads from stale replica → doesn't see  │
  │    their own write!                                       │
  │    Fix: Route reads to primary for recently-written data  │
  │         or track "last_write_timestamp" per user          │
  │                                                           │
  │ 2. Monotonic reads violation:                             │
  │    User reads from replica A (fresh) → reads from        │
  │    replica B (stale) → time goes backward!               │
  │    Fix: Sticky sessions (route user to same replica)     │
  │                                                           │
  │ 3. Consistent prefix violation:                           │
  │    Causally related writes appear out of order            │
  │    Fix: Causal ordering guarantees, partition-level order │
  └────────────────────────────────────────────────────────────┘

  MONITORING REPLICATION LAG:
  - PostgreSQL: pg_stat_replication.replay_lag
  - MySQL: SHOW SLAVE STATUS → Seconds_Behind_Master
  - Alert threshold: > 1 second for most systems
  - Critical: > 10 seconds (risk of serving very stale data)

8. Partitioning Strategies

PARTITIONING: Split data across multiple nodes/tables
for scalability and manageability.

  HORIZONTAL PARTITIONING (SHARDING):
  Split rows across nodes by a partition/shard key.

  ┌──────────────────┬──────────────────────────────────────────┐
  │ HASH PARTITIONING│                                         │
  │                  │ hash(key) % N → shard assignment        │
  │                  │ + Even distribution                     │
  │                  │ - Range queries across all shards        │
  │                  │ - Adding shards requires reshuffling    │
  │                  │ Fix: Consistent hashing                 │
  ├──────────────────┼──────────────────────────────────────────┤
  │ RANGE PARTITIONING│                                        │
  │                  │ key < 1000 → S1, 1000-2000 → S2        │
  │                  │ + Range queries efficient               │
  │                  │ - Hotspots (all recent data in one)     │
  │                  │ Fix: Add prefix/suffix to key           │
  ├──────────────────┼──────────────────────────────────────────┤
  │ LIST PARTITIONING│                                         │
  │                  │ country=US → S1, country=EU → S2        │
  │                  │ + Logical grouping                       │
  │                  │ - Uneven distribution possible           │
  ├──────────────────┼──────────────────────────────────────────┤
  │ COMPOSITE        │                                         │
  │                  │ Hash by user_id, then range by date     │
  │                  │ Multi-level partitioning                │
  └──────────────────┴──────────────────────────────────────────┘

  PARTITION KEY SELECTION (most critical decision):
  ┌────────────────────────────────────────────────────────────┐
  │ GOOD partition key:                                       │
  │ - High cardinality (many distinct values)                │
  │ - Even distribution (no hotspots)                        │
  │ - Matches primary access pattern (query hits one shard)  │
  │                                                           │
  │ Examples:                                                 │
  │ - user_id: Good for user-centric queries                 │
  │ - order_id: Good for order lookups                       │
  │ - timestamp: BAD (all recent writes to one partition)    │
  │ - country: BAD if 50% of users are in US                │
  │                                                           │
  │ RULE: Design queries to include partition key             │
  │ Cross-partition queries = scatter-gather = slow           │
  └────────────────────────────────────────────────────────────┘

  REBALANCING:
  ┌────────────────────────────────────────────────────────────┐
  │ Fixed number of partitions:                               │
  │   Pre-create 1000 partitions, distribute across N nodes   │
  │   Adding node: move some partitions to new node          │
  │   Used by: Elasticsearch, Cassandra, Riak                │
  │                                                           │
  │ Dynamic partitioning:                                     │
  │   Partition splits when too large, merges when too small │
  │   Like B-tree splits but for data partitions             │
  │   Used by: HBase, MongoDB, CockroachDB                  │
  │                                                           │
  │ Key-count-based:                                         │
  │   Split when partition has too many keys                  │
  │   Ensures bounded partition size                         │
  └────────────────────────────────────────────────────────────┘

  SECONDARY INDEXES WITH PARTITIONING:
  ┌────────────────────────────────────────────────────────────┐
  │ LOCAL INDEX (document-partitioned):                       │
  │   Each partition has its own secondary index              │
  │   Write: update index on one partition                   │
  │   Read by secondary key: scatter-gather ALL partitions   │
  │   Used by: MongoDB, Cassandra                            │
  │                                                           │
  │ GLOBAL INDEX (term-partitioned):                         │
  │   Secondary index is itself partitioned separately        │
  │   Write: update multiple index partitions (slow writes)  │
  │   Read by secondary key: query one index partition (fast)│
  │   Used by: DynamoDB (GSI), CockroachDB                  │
  └────────────────────────────────────────────────────────────┘

9. Change Data Capture (CDC)

CDC: Capture row-level changes from a database and stream
them to other systems in real-time.

  WHY CDC:
  ┌────────────────────────────────────────────────────────────┐
  │ 1. Keep read replicas/caches in sync without dual-writes │
  │ 2. Build materialized views / search indexes              │
  │ 3. Feed data pipelines / data warehouse                   │
  │ 4. Enable event-driven architecture from existing DB      │
  │ 5. Cross-service data sync without tight coupling         │
  └────────────────────────────────────────────────────────────┘

  CDC APPROACHES:
  ┌──────────────────┬──────────────────────────────────────────┐
  │ LOG-BASED        │ Read database WAL/binlog                 │
  │ (recommended)    │ + No schema changes needed               │
  │                  │ + Captures all changes (including DELETEs)│
  │                  │ + Low overhead on source DB              │
  │                  │ - DB-specific implementation              │
  ├──────────────────┼──────────────────────────────────────────┤
  │ TRIGGER-BASED    │ DB triggers write changes to outbox table│
  │                  │ + Works with any DB                      │
  │                  │ - Performance impact on source DB        │
  │                  │ - Must maintain trigger code             │
  ├──────────────────┼──────────────────────────────────────────┤
  │ QUERY-BASED      │ Poll table periodically for changes     │
  │                  │ (WHERE updated_at > last_poll)           │
  │                  │ + Simplest to implement                  │
  │                  │ - Can't capture DELETEs (use soft delete)│
  │                  │ - Higher latency, higher DB load        │
  ├──────────────────┼──────────────────────────────────────────┤
  │ OUTBOX PATTERN   │ Application writes event to outbox table │
  │                  │ in same transaction as business data     │
  │                  │ CDC reads outbox → publishes to broker  │
  │                  │ + Guarantees exactly-once semantics      │
  │                  │ - Application must write to outbox      │
  └──────────────────┴──────────────────────────────────────────┘

  DEBEZIUM (most popular CDC tool):
  ┌────────────────────────────────────────────────────────────┐
  │ Source DB ──(WAL/binlog)──→ Debezium ──→ Kafka ──→ Sink  │
  │                                                           │
  │ Supported sources:                                        │
  │   PostgreSQL (logical decoding)                           │
  │   MySQL (binlog)                                          │
  │   MongoDB (change streams)                                │
  │   SQL Server (CT)                                         │
  │   Oracle (LogMiner)                                       │
  │                                                           │
  │ Sink connectors:                                          │
  │   Elasticsearch, Redis, S3, Snowflake, etc.              │
  │                                                           │
  │ Event format: {before, after, source, op, ts_ms}         │
  │   op: c (create), u (update), d (delete), r (read/snaps) │
  └────────────────────────────────────────────────────────────┘

  CDC ARCHITECTURE PATTERN:
  ┌────────────────────────────────────────────────────────────┐
  │                                                           │
  │  Microservice ──write──→ PostgreSQL                       │
  │                              │                            │

  │                           Kafka                           │

10. Stream Processing Internals

STREAM PROCESSING: Continuous computation on unbounded
data as it arrives, rather than batch processing.

  KAFKA INTERNALS:
  ┌────────────────────────────────────────────────────────────┐
  │ TOPIC:                                                    │
  │   Logical channel for messages                            │
  │   Partitioned for parallelism                             │
  │                                                           │
  │ PARTITION:                                                │
  │   Ordered, immutable log of records                       │
  │   Each record has an offset (position in the log)         │
  │   Replicated across brokers (leader + followers)          │
  │                                                           │
  │ PRODUCER:                                                 │
  │   Writes to partition based on key hash                   │
  │   Same key always → same partition → ordering guarantee  │
  │   Acks: 0 (fire-forget), 1 (leader), all (ISR replicas) │
  │                                                           │
  │ CONSUMER GROUP:                                           │
  │   Each partition assigned to exactly ONE consumer in group│
  │   Consumers in same group: load balance                   │
  │   Different groups: each gets all messages (pub-sub)     │
  │   Consumer commits offset → tracks progress               │
  │                                                           │
  │ RETENTION:                                                │
  │   Time-based (default 7 days) or size-based               │
  │   Compacted topics: keep latest value per key            │
  │   (perfect for changelog/CDC topics)                     │
  └────────────────────────────────────────────────────────────┘

  STREAM PROCESSING PATTERNS:
  ┌──────────────────┬──────────────────────────────────────────┐
  │ Stateless        │ Filter, map, transform each record      │
  │                  │ No state between records                │
  ├──────────────────┼──────────────────────────────────────────┤
  │ Stateful         │ Aggregation, joins, windowing           │
  │                  │ State stored locally + checkpointed     │
  ├──────────────────┼──────────────────────────────────────────┤
  │ Windowing        │ Group events by time window             │
  │                  │ Tumbling: [0-5min][5-10min] (no overlap)│
  │                  │ Sliding: [0-5][1-6][2-7] (overlapping)  │
  │                  │ Session: gap-based per user              │
  ├──────────────────┼──────────────────────────────────────────┤
  │ Stream-Table     │ Join streaming events with table         │
  │ Join             │ (KTable in Kafka Streams)               │
  │                  │ Enrich events with reference data       │
  ├──────────────────┼──────────────────────────────────────────┤
  │ Stream-Stream    │ Join two streams by time window          │
  │ Join             │ Match events from different sources     │
  └──────────────────┴──────────────────────────────────────────┘

  FLINK INTERNALS:
  ┌────────────────────────────────────────────────────────────┐
  │ Dataflow graph: Source → Operators → Sink                 │
  │ State backends: RocksDB (large state) or Heap (fast)      │
  │ Checkpointing: Chandy-Lamport algorithm                   │
  │   - Barriers flow through the dataflow graph              │
  │   - On barrier: operator snapshots state to durable store │
  │   - Enables exactly-once processing                       │
  │ Watermarks: Track event time progress                     │
  │   - Handle late-arriving events                           │
  │   - W(t) = "all events with timestamp ≤ t have arrived"  │
  │   - Late data: side output or allowed lateness            │
  │ Savepoints: Manual checkpoint for upgrades/migration     │
  └────────────────────────────────────────────────────────────┘

  BATCH vs STREAMING vs UNIFIED:

  │ Batch + Stream    │ Stream only      │ (Flink, Spark)       │
  │ layers separately │ reprocess via    │ Same code for both   │

Q1: Explain B-tree vs LSM-tree. When would you choose each?

A: B-tree: Data stored in sorted pages, updates are in-place. Excellent for reads (O(log N) with high branching factor — 3-4 disk reads for billions of keys). Good for workloads with lots of point lookups and range scans. Downsides: random I/O on writes (page splits), write amplification from WAL + page write. LSM-tree: Writes go to in-memory MemTable, flushed as sorted SSTables, merged via compaction. Excellent write throughput (sequential I/O). Downsides: read amplification (check multiple levels), compaction can cause latency spikes. Choose B-tree: OLTP with balanced read/write, transactions (PostgreSQL, MySQL). Choose LSM-tree: Write-heavy (logging, metrics, IoT), append-heavy (Cassandra, RocksDB). In practice, CockroachDB and TiKV use RocksDB (LSM) underneath but provide SQL/transaction semantics on top.

Q2: What happens when you run a PostgreSQL transaction at Serializable isolation?

A: PostgreSQL uses Serializable Snapshot Isolation (SSI), not traditional two-phase locking. Each transaction gets an MVCC snapshot at start — it sees a consistent view of the database at that moment. As the transaction executes, PostgreSQL tracks read-write dependencies between concurrent transactions. If it detects a "dangerous structure" (a cycle in the dependency graph that could lead to a serialization anomaly like write skew), it aborts one of the transactions with a serialization failure. The application must then retry. Key benefits: readers never block writers, no deadlocks (just aborts), good performance for read-heavy workloads. Trade-off: occasional aborts require retry logic. This is why PostgreSQL's Serializable is actually practical, unlike traditional lock-based serializability.

Q3: How would you design a CDC pipeline for real-time analytics?

A: Source: PostgreSQL with logical replication enabled. Capture: Debezium connector reads PostgreSQL WAL, publishes change events to Kafka. Each table gets a topic. Schema: Use Avro with Confluent Schema Registry for schema evolution. Processing: Flink reads from Kafka, performs transformations (enrichment, aggregation, windowing). Exactly-once via Flink checkpointing. Sink: Write to Iceberg table on S3 for the data lakehouse. Also maintain real-time materialized views in Redis for dashboards. Monitoring: Track Debezium connector lag, Kafka consumer lag, Flink checkpoint duration. Alert if CDC lag > 30 seconds. Key considerations: (1) Handle schema changes gracefully (Debezium captures DDL). (2) Ensure ordering within partition (same table, same key). (3) Handle deletes (soft delete marker in change event). (4) Backfill: initial snapshot before streaming changes.

Q4: Explain partition key selection for DynamoDB.

A: DynamoDB partitions by hash of the partition key. Good key: High cardinality, even distribution, matches access pattern. For an e-commerce app: user_id as PK for user data (each user is a hot partition, but distributed across many). order_id for orders. Bad key: date (all today's orders in one partition — hot partition). country (US = 50% of traffic, one partition overloaded). Composite key (PK + Sort Key): PK=user_id, SK=order_date#order_id — efficient range query for user's orders by date. GSI (Global Secondary Index): Additional access patterns. GSI PK=product_id, SK=order_date for queries by product. Hot partition mitigation: Write sharding — add random suffix to PK, scatter-gather on read. Or use DynamoDB Adaptive Capacity (automatic).

Q5: Compare Kafka vs Flink for stream processing.

A: Kafka Streams: Library (not a cluster), runs in your JVM, stateful processing, changelog-backed state stores (RocksDB), exactly-once via Kafka transactions. Best for: Kafka-centric architectures, simpler topologies, when you don't want to operate a separate cluster. Limitations: JVM only, Kafka-to-Kafka only, harder for complex event processing. Flink: Distributed runtime (cluster), multiple source/sinks, sophisticated windowing (event time, watermarks), exactly-once via Chandy-Lamport checkpointing, SQL support. Best for: Complex event processing, multi-source, precise event-time processing, when you need advanced windowing or stream-stream joins. My recommendation: Kafka Streams for service-level stream processing (simple transformations, aggregations within a microservice). Flink for platform-level stream processing (cross-source joins, complex analytics, data pipeline backbone).
