1. Load Balancing

DefinitionPick it whenTrade-offstatelessReal-world example — Google MaglevAWS ALB/ELB

Definition. A load balancer sits in front of a pool of identical servers and spreads incoming requests across them so no single server is overwhelmed. It also removes unhealthy servers from rotation, improving availability.

  • Pick it when: traffic exceeds what one server can handle.
  • Trade-off: backends must be stateless (or you need sticky sessions / a shared session store), otherwise a user's requests landing on different servers lose their session.

Real-world example — Google Maglev. Google fronts services like Search and Gmail with Maglev, a software network load balancer running on ordinary servers. A cluster of Maglev machines advertises a single virtual IP (VIP) to the internet and spreads the incoming packet flood across hundreds of backend servers, with each Maglev box able to saturate a 10 Gbps link. It uses consistent hashing on the connection's 5-tuple so that when a backend is added or removed, existing TCP connections stay pinned to the same server instead of being reset. Because the backends are stateless web servers (session state lives in a shared store — the exact precondition this pattern demands), any backend can answer any request, so Google can lose individual backends, or even whole Maglev nodes, without users noticing. The same idea in smaller form is what AWS ALB/ELB and Nginx/HAProxy do for ordinary web apps.

            ┌──────────────┐
client ───► │ Load Balancer │──► Server A   (Round Robin: A, B, C, A, B, C…)
            │  (health      │──► Server B   (Least-Conn: pick fewest active)
            │   checks)     │──► Server C   (IP Hash: same client → same server)
            └──────────────┘
from itertools import cycle

class RoundRobinLB:
    """Distribute requests evenly, skipping unhealthy backends."""
    def __init__(self, servers):
        self.servers = servers
        self.healthy = set(servers)
        self._ring = cycle(servers)

    def mark_down(self, server): self.healthy.discard(server)
    def mark_up(self, server):   self.healthy.add(server)

    def route(self):
        for _ in range(len(self.servers)):       # at most one full loop
            s = next(self._ring)
            if s in self.healthy:
                return s
        raise RuntimeError("no healthy backend")

class LeastConnectionsLB:
    """Route to the backend with the fewest in-flight requests."""
    def __init__(self, servers):
        self.active = {s: 0 for s in servers}

    def route(self):
        s = min(self.active, key=self.active.get)
        self.active[s] += 1
        return s

    def release(self, server):
        self.active[server] = max(0, self.active[server] - 1)

lb = RoundRobinLB(["A", "B", "C"])
print([lb.route() for _ in range(5)])   # ['A', 'B', 'C', 'A', 'B']
lb.mark_down("B")
print([lb.route() for _ in range(4)])   # ['C', 'A', 'C', 'A']  (B skipped)

Interview Q&A - Q: L4 vs L7 load balancing? L4 (transport) routes on IP/port — fast, protocol-agnostic, no payload inspection. L7 (application) understands HTTP, so it can route by URL path/header, terminate TLS, and do content-based routing — at higher CPU cost. - Q: How do you keep sessions working behind a round-robin LB? Make servers stateless and store session state externally (Redis/DB) so any server can serve any request; or use sticky sessions (IP/cookie hash) as a weaker fallback that hurts even distribution and breaks on scale-down. - Q: Active vs passive health checks? Active = LB periodically pings /health. Passive = LB infers failure from real traffic errors/timeouts. Production uses both.

2. Horizontal Scaling

Definitionmore machinesstatelessPick it whenTrade-offInterview Q&A

Definition. Handle more load by adding more machines (scale out) rather than a bigger machine (scale up). Works cleanly only for stateless units that can run in parallel behind a load balancer; shared state must move to an external store.

  • Pick it when: load keeps growing past a single box, and you want fault tolerance.
  • Trade-off: coordination complexity — data consistency, distributed caching, deployments, and observability across N nodes.

Real-world example — Netflix on AWS. Netflix serves hundreds of millions of subscribers, and its traffic is extremely peaky: quiet in the morning, then a massive ramp every evening as people get home to watch. Instead of one giant server, Netflix runs its API and streaming-control tiers as thousands of small, stateless instances inside AWS Auto Scaling Groups. Scaling policies watch CPU and request-rate metrics and automatically launch more instances as load climbs, then terminate them overnight to save money — the fleet literally breathes with demand. Because instances hold no per-user state (it lives in Cassandra and the EVCache caching tier), the load balancer can route any request to any instance and a dead instance is simply replaced. The coordination cost is real and is the pattern's trade-off: to run a fleet that large Netflix had to build heavy supporting tooling — Eureka for service discovery, Hystrix for resilience, and Chaos Monkey to constantly prove the system survives lost instances.

Vertical (scale up)1 node, more CPU/RAM→hardware ceiling, SPOF
Horizontal (scale out)N nodes + LB + shared DB→near-unlimited, fault-tolerant 
import hashlib

class StatelessWorker:
    def handle(self, req):          # no per-worker state — safe to replicate
        return f"{self.name}: processed {req}"

class WorkerPool:
    """Add/remove identical workers at will; capacity scales with count."""
    def __init__(self): self.workers = []
    def scale_to(self, n):
        self.workers = [self._make(i) for i in range(n)]
    def _make(self, i):
        w = StatelessWorker(); w.name = f"worker-{i}"; return w
    def dispatch(self, req):
        # any worker can serve any request because state is external
        idx = int(hashlib.md5(req.encode()).hexdigest(), 16) % len(self.workers)
        return self.workers[idx].handle(req)

pool = WorkerPool()
pool.scale_to(2); print(pool.dispatch("req-1"))   # worker-0 or worker-1
pool.scale_to(5); print(pool.dispatch("req-1"))   # capacity grew, no code change

Interview Q&A - Q: What blocks horizontal scaling? Local state (in-memory sessions, sticky files), single-writer databases, and shared mutable resources. Externalize state, then nodes become interchangeable. - Q: Vertical vs horizontal? Vertical is simplest (no code change) but has a hardware ceiling and a single point of failure. Horizontal is effectively unlimited and fault-tolerant but introduces distributed-systems complexity. - Q: How do stateless services keep user sessions? Token-based auth (JWT) or a shared session store (Redis) — never local memory.

3. Database Sharding

Definitiondisjoint subsetshard keyPick it whenTrade-offReal-world example — Instagram

Definition. Split one logical database into many physical shards, each holding a disjoint subset of rows selected by a shard key. Each shard handles its own reads and writes, so total write throughput scales with the number of shards.

  • Pick it when: a single DB can no longer handle the write volume or dataset size.
  • Trade-off: cross-shard queries/joins and transactions become hard; rebalancing and global IDs need planning.

Real-world example — Instagram. When Instagram outgrew a single PostgreSQL box, they split user data across many database servers, and then further across thousands of logical shards so they could later move shards between physical machines without changing application code. The shard that owns a row is derived from the object's ID, and they cleverly encode the shard ID directly inside their 64-bit IDs (a custom scheme of timestamp + shard id + per-shard sequence), so given any ID the app instantly knows which shard to hit — no lookup table. This lets writes scale roughly linearly: each shard absorbs only its slice of the insert load, so doubling shards roughly doubles write capacity. The price is the pattern's classic trade-off: a query needing data across many users (a global aggregate) has to fan out to every shard and merge results, so Instagram designs access patterns to stay within a single shard whenever possible. YouTube solves the same problem on MySQL using Vitess, which transparently shards and routes queries.

hash(user_id) % 3→Shard 0 | Shard 1 | Shard 2
range→[0–1M)→S0 [1M–2M)→S1 [2M–3M)→S2range queries easy, hotspots risk 
class ShardedStore:
    """Hash-based sharding: shard = hash(key) % num_shards."""
    def __init__(self, num_shards):
        self.shards = [dict() for _ in range(num_shards)]

    def _shard(self, key):
        return self.shards[hash(key) % len(self.shards)]

    def put(self, key, value): self._shard(key)[key] = value
    def get(self, key):        return self._shard(key).get(key)

    def scatter_gather(self, predicate):
        # cross-shard query = query every shard, then merge (expensive!)
        return [v for shard in self.shards for v in shard.values() if predicate(v)]

db = ShardedStore(num_shards=3)
for uid in range(6):
    db.put(f"user:{uid}", {"id": uid, "tier": "pro" if uid % 2 else "free"})
print(db.get("user:4"))                                   # routed to one shard
print(db.scatter_gather(lambda v: v["tier"] == "pro"))    # hits ALL shards

Interview Q&A - Q: How do you choose a shard key? High cardinality + even access distribution + present in most queries. Bad keys (e.g. country) create hotspots; keys tied to a single tenant let you route a query to one shard. - Q: Range vs hash sharding? Range keeps ordered data together (great for range scans) but causes hotspots on sequential keys. Hash spreads load evenly but makes range queries fan out to all shards. - Q: How do you avoid auto-increment ID collisions across shards? Use UUIDs or a coordination-free scheme like Snowflake IDs (timestamp + machine id + sequence).

4. Read Replicas

Definitionprimaryread-only replicasPick it whenTrade-offreplication lag

Definition. Keep one primary for writes and replicate its data to one or more read-only replicas. Send reads to replicas to scale read throughput while writes stay on the primary.

  • Pick it when: reads vastly outnumber writes.
  • Trade-off: replication laga replica may briefly return stale data (eventual consistency).

Real-world example — Wikipedia. Wikipedia is overwhelmingly a read workload — billions of article views against a comparatively tiny number of edits. They run MySQL with one primary that accepts all writes (edits) and a fleet of replicas that serve the reads, with traffic load-balanced across the replicas. A normal page view is answered from a replica (and usually from a Varnish/cache layer in front of it), so the write primary is never the bottleneck for read traffic and you can scale reads just by adding replicas. The trade-off appears immediately after you click "Save": replication lag means a replica might be a fraction of a second behind the primary. MediaWiki handles this by deliberately routing your own reads to the primary for a short window after you edit, so you always see your own change — the standard "read-your-writes" workaround for replica staleness.

write ─► PRIMARY ──async replicate──► REPLICA 1 ─► reads
                  └────────────────► REPLICA 2 ─► reads   (lag: 0.1–1s)
import time
from itertools import cycle

class PrimaryReplica:
    def __init__(self, num_replicas=2, lag=0.0):
        self.primary = {}
        self.replicas = [dict() for _ in range(num_replicas)]
        self._rr = cycle(range(num_replicas))
        self.lag = lag

    def write(self, key, value):
        self.primary[key] = value
        self._replicate(key, value)         # async in real systems

    def _replicate(self, key, value):
        time.sleep(self.lag)                 # simulate replication delay
        for r in self.replicas: r[key] = value

    def read(self, key, consistent=False):
        if consistent:                       # read-your-writes → hit primary
            return self.primary.get(key)
        return self.replicas[next(self._rr)].get(key)   # load-balanced reads

db = PrimaryReplica()
db.write("balance:alice", 100)
print(db.read("balance:alice"))                  # 100 (read from a replica)
print(db.read("balance:alice", consistent=True)) # 100 (forced to primary)

Interview Q&A - Q: How do you handle "read-your-own-writes" with replicas? Route a user's reads to the primary for a short window after they write, or pin them to the primary until the replica catches up (track replication position). - Q: What's replication lag and why does it matter? The delay between a write committing on the primary and appearing on a replica. It breaks read-after-write expectations (e.g., user posts a comment, refreshes, doesn't see it). - Q: Synchronous vs asynchronous replication? Sync replicas guarantee no data loss but add write latency and reduce availability if a replica is slow. Async is fast but can lose recent writes on primary failure.

5. Consistent Hashing

Definitionfirst server clockwisePick it whenTrade-offvirtual nodesDiscord

Definition. A hashing scheme that maps both keys and servers onto a ring (0…2³²). A key belongs to the first server clockwise from its position. When a node joins or leaves, only the keys in its arc move — not the entire keyspace (unlike hash(key) % N).

  • Pick it when: nodes frequently join/leave (caches, DHTs, sharded caches).
  • Trade-off: more complex routing; needs virtual nodes for even distribution.

Real-world example — DynamoDB / Cassandra / Discord. DynamoDB (and its open-source cousin Cassandra, both descending from Amazon's original Dynamo paper) places every storage node on a hash ring and assigns each row to the node owning its key's position. The crucial payoff is elasticity: when you add a node to handle growth, only the keys in the arc between the new node and its predecessor move — roughly 1/N of the data — instead of the near-total reshuffle that hash(key) % N would cause. Each physical node is given many virtual nodes (token ranges) around the ring, so load stays even and a departing node's data is redistributed across many survivors rather than dumped entirely on one neighbor. Discord runs large Cassandra (and later ScyllaDB) clusters this way to store trillions of messages, adding capacity without downtime. The cost is routing complexity: clients or coordinator nodes must know the ring topology to find which node owns a given key.

Problem: hash(key) % N → change N → ~ALL keys remap (cache stampede)

Ring:   ...── S1 ──── k1 ── S2 ──── k2 ── S3 ──...   key → next server clockwise
Add S4 between S1 and S2 → only keys in (S1, S4] move. Everything else untouched.
import hashlib, bisect

class ConsistentHashRing:
    def __init__(self, vnodes=100):
        self.vnodes = vnodes        # virtual nodes per server → even spread
        self.ring = {}              # hash position -> server
        self.sorted_keys = []

    def _hash(self, s):
        return int(hashlib.md5(s.encode()).hexdigest(), 16)

    def add(self, server):
        for i in range(self.vnodes):
            h = self._hash(f"{server}#{i}")
            self.ring[h] = server
            bisect.insort(self.sorted_keys, h)

    def remove(self, server):
        for i in range(self.vnodes):
            h = self._hash(f"{server}#{i}")
            del self.ring[h]
            self.sorted_keys.remove(h)

    def get_node(self, key):
        if not self.ring: return None
        h = self._hash(key)
        idx = bisect.bisect(self.sorted_keys, h) % len(self.sorted_keys)
        return self.ring[self.sorted_keys[idx]]

ring = ConsistentHashRing()
for s in ["cache-A", "cache-B", "cache-C"]: ring.add(s)
before = {k: ring.get_node(k) for k in [f"key{i}" for i in range(1000)]}
ring.add("cache-D")
after = {k: ring.get_node(k) for k in before}
moved = sum(before[k] != after[k] for k in before)
print(f"{moved}/1000 keys moved when adding a 4th node")  # ~290 (≈1/N), not ~1000

Interview Q&A - Q: Why virtual nodes? With few physical nodes the ring is uneven, causing load skew. Giving each server many positions averages out the arcs and also spreads a departing node's load across many survivors. - Q: What does consistent hashing buy you over modulo hashing? Adding/removing a node remaps only ~1/N of keys instead of nearly all, avoiding a full cache miss storm. - Q: Who uses it? DynamoDB, Cassandra, Redis Cluster, memcached clients, and CDN/request routing.

6. Cache-Aside

DefinitionmissinvalidatePick it whenTrade-offInterview Q&A

Definition. (a.k.a. lazy loading) The application owns the cache. On read: check cache → on miss, load from DB and populate the cache. On write: update the DB and invalidate the cached entry.

  • Pick it when: read-heavy workloads where only a subset of data is hot.
  • Trade-off: stale-cache risk and a cold-start miss penalty; first request for each key always misses.

Real-world example — Facebook + Memcached. Facebook's social graph is read-dominated: every page load fetches a user's friends, their recent posts, likes, and comments, so they run one of the world's largest Memcached deployments in front of MySQL. On a read the web tier asks Memcached first; on a miss it reads MySQL and writes the value back into the cache for next time — textbook cache-aside. On a write they delete the cached key rather than update it, so the next reader repopulates from the source of truth and two concurrent writers can't race to leave a stale value behind. At their scale this absorbs the overwhelming majority of reads and is the only reason MySQL load stays survivable. The famous hard problems Facebook had to solve are exactly this pattern's trade-offs: the "thundering herd" when a hot key expires and thousands of requests stampede the database at once, and keeping caches coherent across multiple data centers.

READ:  cache.get(k) ─hit─► return
                    └miss─► db.get(k) → cache.set(k) → return
WRITE: db.put(k,v) → cache.delete(k)        (invalidate, repopulate on next read)
class CacheAside:
    def __init__(self, db):
        self.cache, self.db = {}, db
        self.hits = self.misses = 0

    def get(self, key):
        if key in self.cache:
            self.hits += 1
            return self.cache[key]
        self.misses += 1
        value = self.db.get(key)            # slow path
        if value is not None:
            self.cache[key] = value         # populate for next time
        return value

    def put(self, key, value):
        self.db[key] = value
        self.cache.pop(key, None)           # invalidate, don't update

db = {"user:1": "Alice"}
c = CacheAside(db)
print(c.get("user:1"))   # miss → DB → cached
print(c.get("user:1"))   # hit
c.put("user:1", "Alicia")
print(c.get("user:1"))   # miss (invalidated) → DB → "Alicia"
print(c.hits, c.misses)  # 1 2

Interview Q&A - Q: Why invalidate instead of update the cache on write? Updating risks races (two writers interleave and leave a stale value). Deleting forces the next reader to repopulate from the source of truth. - Q: How do you prevent a thundering herd when a hot key expires? Single-flight locking (one request rebuilds while others wait), request coalescing, or staggered/early refresh. - Q: Cache penetration / avalanche fixes? Penetration (queries for nonexistent keys): cache negative results or use a Bloom filter. Avalanche (many keys expire together): add random TTL jitter.

7. Write-Through Cache

DefinitionPick it whenTrade-offInterview Q&AQ: Write-through vs cache-aside?

Definition. Every write goes to the cache and the database synchronously in the same operation. The cache is always consistent with the DB, so reads after writes are guaranteed fresh.

  • Pick it when: data must always be fresh and reads must never see stale values.
  • Trade-off: slower writes (two synchronous hops) and you cache data that may never be read.

Real-world example — pricing & feature-flag systems. Picture an e-commerce checkout that must never show a stale price after the merchandising team changes it. A write-through cache writes the new price to both the cache and the database in one synchronous operation, so the instant the write returns, the next read — which is served from cache — already reflects the new value, with zero staleness window. This is the right choice when correctness-on-read matters more than write speed: you accept that every write now pays two hops (cache + DB) and that you may cache keys nobody ever reads, in exchange for a hard guarantee that the cache is never behind the database. In practice it's paired with a TTL and a read-through fallback so cold keys still load lazily on first access. Contrast this with cache-aside, where there is a brief window between the DB write and the cache being repopulated during which a stale value can be served — unacceptable for prices, fine for a profile bio.

WRITE: app ─► cache.set(k,v) ─► db.put(k,v)   (both succeed before ack)
READ:  always a cache hit for written keys (no staleness)
class WriteThroughCache:
    def __init__(self, db):
        self.cache, self.db = {}, db

    def put(self, key, value):
        self.cache[key] = value     # 1) write cache
        self.db[key] = value        # 2) write DB synchronously → consistent
        return "ok"

    def get(self, key):
        if key in self.cache:
            return self.cache[key]
        v = self.db.get(key)        # cold cache fallback
        if v is not None: self.cache[key] = v
        return v

db = {}
c = WriteThroughCache(db)
c.put("config:flag", True)
print(c.get("config:flag"), db["config:flag"])  # True True  (never stale)

Interview Q&A - Q: Write-through vs cache-aside? Write-through keeps the cache authoritative and always fresh at the cost of write latency; cache-aside is lazier (populate on read) and tolerates staleness for cheaper writes. - Q: Downside of write-through alone? You write data that may never be read, and writes pay the double-hop latency. Often paired with a read-through cache and TTLs. - Q: How do you guarantee both writes succeed? Wrap them so a DB failure rolls back / evicts the cache entry; otherwise the cache can hold a value the DB rejected.

8. Write-Behind Cache

Definitioncache immediatelyasynchronously flushesPick it whenTrade-offdata loss

Definition. (a.k.a. write-back) Writes go to the cache immediately and are acknowledged; the cache asynchronously flushes to the database in the background (often batched). This makes writes very fast.

  • Pick it when: ultra-fast writes are needed and brief durability gaps are acceptable (metrics, counters, view counts).
  • Trade-off: potential data loss if the cache crashes before flushing; the DB is temporarily behind.

Real-world example — view / like counters. High-frequency counters — YouTube video views, Reddit upvotes, Medium claps, post likes — are the canonical write-behind case. If every click wrote straight to a relational database you would melt it, because the same row gets hammered thousands of times a second and each write contends for the same lock. Instead the increment lands in a fast in-memory store (usually Redis), is acknowledged immediately, and a background job periodically flushes the accumulated total to the durable database — and critically, the many increments to one key between flushes collapse into a single DB write. That batching/coalescing is what makes ultra-high write rates affordable. The accepted risk is the pattern's defining trade-off: if the cache node dies before a flush, you lose the last few seconds of counts. That's perfectly tolerable for a view counter (nobody cares if a video shows 1,000,012 vs 1,000,000 views), which is exactly why it's used there and never for a bank balance.

WRITE: app ─► cache.set(k,v) ──ack (fast)
                  │
                  └─ buffer → [async/batched] → db.put(...)   (flush later)
import queue, threading, time

class WriteBehindCache:
    def __init__(self, db, flush_interval=0.1):
        self.cache, self.db = {}, db
        self.dirty = queue.Queue()
        self._stop = False
        threading.Thread(target=self._flusher, args=(flush_interval,),
                         daemon=True).start()

    def put(self, key, value):
        self.cache[key] = value         # instant ack
        self.dirty.put(key)             # schedule background write
        return "ok"

    def get(self, key): return self.cache.get(key)

    def _flusher(self, interval):
        while not self._stop:
            time.sleep(interval)
            while not self.dirty.empty():
                k = self.dirty.get()
                self.db[k] = self.cache[k]   # batched persist

    def stop(self): self._stop = True

db = {}

c.stop()

Mitigate with a write-ahead log/replicated cache, bounded flush intervals, and using it only where small loss is tolerable. - Q: Why is it faster than write-through? The DB write is removed from the request path and writes are batched/coalesced (many updates to the same key collapse to one DB write). - Q: Good use cases? Counters, leaderboards, analytics, session updates — high write rate, loss-tolerant.

9. CDN

Definitionedge cachesPick it whenTrade-offCloudflare, Akamai, CloudFrontInterview Q&A

Definition. A Content Delivery Network is a geographically distributed set of edge caches. Clients fetch from the nearest edge; on a miss the edge pulls from origin and caches it with a TTL, cutting latency and origin load for static (and cacheable dynamic) content.

  • Pick it when: you need global, low-latency delivery of static/large assets (images, video, JS/CSS).
  • Trade-off: content can be stale until TTL expiry or explicit purge; cache invalidation across edges is the hard part.

Real-world example — Netflix Open Connect. Video is enormous and latency-sensitive, so Netflix doesn't stream from a central data center — it built its own CDN, Open Connect, and places cache appliances inside ISP networks and at internet exchange points, physically close to viewers. During off-peak hours it proactively pushes the titles it predicts will be popular onto those edge boxes, so when you press play the bytes come from a server a few network hops away instead of from across the country. This is how Netflix can be responsible for a large share of all internet traffic without saturating expensive long-haul links, and why playback starts almost instantly. The trade-offs are freshness and operations: edges serve cached copies, so pushing a new encode means re-distributing it to thousands of appliances, and Netflix must operate that whole global fleet. General-purpose CDNs (Cloudflare, Akamai, CloudFront) apply the identical idea to images, JS/CSS, and even cacheable API responses for everyone else.

                     └miss─► ORIGIN (us-east) → cache@edge w/ TTL → serve
import time

class EdgeNode:
    def __init__(self, name, origin):
        self.name, self.origin, self.store = name, origin, {}

    def get(self, path, ttl=2.0):
        now = time.time()
        if path in self.store:
            value, expires = self.store[path]
            if now < expires:
                return f"{self.name} HIT: {value}"
        value = self.origin.fetch(path)          # miss → origin
        self.store[path] = (value, now + ttl)
        return f"{self.name} MISS→origin: {value}"

    def purge(self, path): self.store.pop(path, None)

class Origin:
    def __init__(self): self.assets = {"/logo.png": "v1-bytes"}
    def fetch(self, path): return self.assets[path]

origin = Origin()
edge = EdgeNode("edge-EU", origin)
print(edge.get("/logo.png"))   # MISS→origin
print(edge.get("/logo.png"))   # HIT (served from edge)
origin.assets["/logo.png"] = "v2-bytes"; edge.purge("/logo.png")
print(edge.get("/logo.png"))   # MISS→origin: v2-bytes  (after purge)

Yes with care — vary on cache keys (headers/cookies), use short TTLs or stale-while-revalidate, and keep truly personalized responses uncacheable. - Q: Push vs pull CDN? 10. Materialized Views

DefinitionrefreshedPick it whenTrade-offInterview Q&AQ: Refresh strategies?

Definition. A precomputed, stored result of an expensive query (joins/aggregations). Reads hit the cheap precomputed table instead of recomputing; the view is refreshed periodically or on data change.

  • Pick it when: the same expensive query runs often and slightly stale results are acceptable.
  • Trade-off: refresh lag (view trails the base data) and extra storage + refresh cost.

Real-world example — Twitter/X home timeline. Building a home timeline by querying "all recent tweets from everyone I follow, merged and ranked" at read time would be ruinously expensive for someone following thousands of accounts, and timelines are read constantly. So for most users the timeline is effectively a materialized view: when you tweet, your post is fanned out on write into your followers' precomputed timeline lists (in Redis), and a read just pulls the ready-made list instead of re-aggregating from scratch. Leaderboards and BI dashboards use the same trick — an expensive GROUP BY is computed ahead of time and stored for cheap reads. The trade-off is refresh lag and storage: the view trails the base data between refreshes. Twitter also hit the limit of pure precompute — fanning a celebrity's tweet out to 100M follower lists is wasteful — so they use a hybrid, computing those few high-fan-out accounts at read time and merging them in (the classic "fan-out on write vs. fan-out on read" decision).

class MaterializedView:

11. Event Sourcing

DefinitionreplayingPick it whenTrade-offInterview Q&Asnapshots

Definition. Instead of storing only current state, store the full ordered log of state-changing events. Current state is derived by replaying events from the start (or from a snapshot). The event log is the source of truth.

  • Pick it when: you need a complete audit trail, time-travel/debugging, or the ability to rebuild state and projections.
  • Trade-off: replay complexity, schema/versioning of events, and the log grows forever (needs snapshots).

Real-world example — bank ledgers & Git. A bank ledger never overwrites your balance; it appends immutable transactions (deposits, withdrawals, transfers), and your current balance is the fold over that history. That is event sourcing, and it's effectively mandatory in finance because you need a complete, tamper-evident audit trail and the ability to reconstruct the exact state at any past moment ("what was the balance on March 3rd?"). Git is the same idea made tangible: each commit is an immutable event, the working tree you check out is the replay of the commit chain, and git log is literally the event store you can travel through. The trade-off the bank has to manage is replay cost — folding millions of events is slow — so they periodically write balance snapshots and only replay events recorded after the latest snapshot, and they must carefully version event schemas as the business evolves so old events still replay correctly.

events: [AccountOpened, Deposited(100), Withdrew(30)]
replay:  0 → +100 → -30  →  balance = 70   (state is a fold over events)
class EventSourcedAccount:
    def __init__(self):
        self.events = []                 # append-only log = source of truth

    # commands append events (never mutate state directly)
    def open(self):            self.events.append(("Opened", 0))
    def deposit(self, amt):    self.events.append(("Deposited", amt))
    def withdraw(self, amt):
        if self.balance() < amt: raise ValueError("insufficient funds")
        self.events.append(("Withdrew", amt))

    def balance(self):                   # rebuild state by folding events
        bal = 0
        for kind, amt in self.events:
            bal += amt if kind in ("Opened", "Deposited") else -amt
        return bal

acct = EventSourcedAccount()
acct.open(); acct.deposit(100); acct.withdraw(30)
print(acct.balance())          # 70
print(acct.events)             # full history → audit/time-travel

Interview Q&A - Q: How do you avoid replaying millions of events? Periodic snapshots of state at a known version; replay only events after the latest snapshot. - Q: How do you query current state efficiently? Build read-model projections (often via CQRS) updated as events arrive, instead of folding the log on every read. - Q: What happens when the event schema changes? Version events and use upcasters that transform old event shapes into new ones during replay.

12. CQRS

Definitionwrite modelread modelPick it whenTrade-offElasticsearch

Definition. Command Query Responsibility Segregation splits the model in two: a write model (commands that change state) and a separate read model (queries), often with different storage shapes. The read side is kept in sync via events/projections.

  • Pick it when: read and write workloads differ greatly (e.g., complex writes, denormalized fast reads) and you want to scale/optimize them independently.
  • Trade-off: more moving parts and eventual consistency between write and read models.

Real-world example — e-commerce search. An online store has two very different shapes of work. Writes — placing orders, decrementing inventory — need transactional integrity in a normalized relational database. Reads — browsing, faceted/full-text search, "products like this" — need fast, denormalized queries that a relational schema is bad at. CQRS splits them: orders are written to the SQL system of record, and an event pipeline projects product data into a denormalized Elasticsearch index built purely for querying. Browsing traffic, which is the vast majority of requests, hits Elasticsearch and never touches the order database, and each side can be scaled and tuned independently (more search replicas without touching the order DB). The trade-off is eventual consistency and extra moving parts: there's a short delay before a catalog edit appears in search — totally fine for browsing, but you would not serve the order total at checkout from the lagging read model.

command ─► WRITE model (normalized) ─emits event─► projection ─► READ model (denormalized)
query   ─────────────────────────────────────────────────────► READ model
class CQRS:
    def __init__(self):
        self.write_store = {}     # normalized source of truth
        self.read_store = {}      # denormalized, query-optimized

    # ---- command side (mutations) ----
    def create_order(self, oid, user, amount):
        self.write_store[oid] = {"user": user, "amount": amount}
        self._project(user, amount)            # update read model

    # ---- projection keeps read model in sync ----
    def _project(self, user, amount):
        r = self.read_store.setdefault(user, {"orders": 0, "spent": 0})
        r["orders"] += 1
        r["spent"] += amount

    # ---- query side (reads) ----
    def user_summary(self, user):
        return self.read_store.get(user)       # O(1), no joins/aggregation

c = CQRS()
c.create_order("o1", "alice", 30)
c.create_order("o2", "alice", 20)
print(c.user_summary("alice"))   # {'orders': 2, 'spent': 50} — precomputed read

Interview Q&A - Q: When is CQRS overkill? For simple CRUD with similar read/write shapes — the extra projections and eventual consistency aren't worth it. - Q: CQRS vs event sourcing — related? Independent but synergistic. CQRS separates read/write models; event sourcing is one way to feed projections. You can do either alone. - Q: How do you handle the read model lagging the write model? Accept eventual consistency, surface "pending" states in UI, or read from the write model for the rare strongly-consistent query.

13. Data Partitioning

DefinitionHorizontalverticalPick it whenTrade-offPrometheus

Definition. Divide a dataset into partitions so each can be stored/processed independently. Horizontal partitioning splits rows (the basis of sharding); vertical partitioning splits columns. Partitioning by key, range, or hash improves parallelism and manageability.

  • Pick it when: datasets are too large for one node or you want parallel processing.
  • Trade-off: rebalancing when partitions grow unevenly, and queries that span partitions get complex.

Real-world example — Kafka topic partitions. A Kafka topic is split into partitions, and that partition count is the unit of parallelism: each partition is an independent, strictly-ordered log read by exactly one consumer within a consumer group, so a 12-partition topic can be processed by up to 12 workers at once. Producers pick a partition by hashing a message key (say user_id), which guarantees all events for one user land on the same partition and stay in order, while different users spread across partitions for throughput — partitioning applied to a stream rather than a table. This is how Kafka scales to millions of messages per second. The trade-offs are the pattern's own: you can't easily change the partition count later without disturbing the key→partition mapping (and thus per-key ordering), and ordering is only guaranteed within a partition, never across the whole topic. Time-series databases like Prometheus and InfluxDB partition by time range for the same parallelism/manageability reasons.

Hashhash(k)%N→even spreadno hotspots, range scans fan out

class RangePartitioner:
    """Assign keys to partitions by sorted boundaries (e.g. A–M, N–Z)."""
    def __init__(self, boundaries):       # boundaries=['M'] → 2 partitions
        self.boundaries = boundaries
        self.partitions = [dict() for _ in range(len(boundaries) + 1)]

    def _index(self, key):
        i = 0
        while i < len(self.boundaries) and key[0].upper() > self.boundaries[i]:
            i += 1
        return i

    def put(self, key, value): self.partitions[self._index(key)][key] = value
    def get(self, key):        return self.partitions[self._index(key)].get(key)

p = RangePartitioner(boundaries=["M"])
for name in ["Alice", "Zoe", "Bob", "Nina"]:
    p.put(name, f"{name}'s data")
print([sorted(part) for part in p.partitions])
# [['Alice', 'Bob'], ['Nina', 'Zoe']]  → A–M in P0, N–Z in P1

Interview Q&A - Q: Partitioning vs sharding? Partitioning is the general concept of splitting data (can be within one DB). Sharding specifically distributes partitions across separate machines for scale-out. - Q: How do you rebalance hot partitions? Split the hot partition, use consistent hashing to limit movement, or add salt to the key to spread a hot value. - Q: Horizontal vs vertical partitioning? Horizontal splits rows (scale data volume/throughput). Vertical splits columns (separate hot from cold/large columns, e.g. blobs).

14. Distributed Transactions

Definitionall commit or all abortTwo-Phase Commit (2PC)Pick it whenTrade-offInterview Q&A

Definition. Coordinate a single atomic transaction across multiple independent resources (services/DBs) so they all commit or all abort. The classic mechanism is Two-Phase Commit (2PC): a coordinator asks all participants to prepare, then commit only if everyone voted yes.

  • Pick it when: strong consistency across services is genuinely required (financial ledgers).
  • Trade-off: performance overhead and blocking — if the coordinator dies after prepare, participants hold locks (the "blocking" problem). Often avoided in favor of Sagas.

Real-world example — Google Spanner. When a single logical transaction must atomically update data living on different shards, Spanner runs two-phase commit on top of Paxos-replicated groups: a coordinator asks every participating shard to prepare (durably reserve the change and vote yes/no), and only if all vote yes does it broadcast commit. Spanner layers its TrueTime clock on top to give these distributed transactions strict serializability — externally-consistent global ordering — which is what lets it back systems like AdWords that genuinely need ACID across continents. The blocking weakness of 2PC is mitigated but not erased: participants hold locks between prepare and commit, so the protocol adds latency and a stalled coordinator can hold those locks. That cost is exactly why most internet-scale systems avoid cross-shard transactions where they can and reach for sagas instead; Spanner is notable precisely because it engineered 2PC to be viable at that scale. Traditional enterprise XA transactions apply the same prepare/commit handshake across multiple databases and message brokers.

Phase 1 (PREPARE): coordinator → all participants: "can you commit?"  (vote yes/no)
Phase 2 (COMMIT):  if all yes → "commit"   else → "abort"   (atomic across all)
class Participant:
    def __init__(self, name): self.name, self.prepared, self.value = name, False, None
    def prepare(self, value):                 # phase 1: reserve, can still abort
        self.value = value; self.prepared = True; return True   # vote yes
    def commit(self): print(f"{self.name} committed {self.value}")
    def abort(self):  self.prepared = False; print(f"{self.name} aborted")

class TwoPhaseCommit:
    def __init__(self, participants): self.participants = participants
    def execute(self, writes):
        # Phase 1 — prepare; collect votes
        votes = [p.prepare(v) for p, v in zip(self.participants, writes)]
        if all(votes):                        # Phase 2 — commit
            for p in self.participants: p.commit()
            return "COMMITTED"
        for p in self.participants: p.abort()  # Phase 2 — abort
        return "ABORTED"

coord = TwoPhaseCommit([Participant("inventory"), Participant("payment")])
print(coord.execute([("reserve", 1), ("charge", 50)]))   # COMMITTED

Interview Q&A - Q: Why do people avoid 2PC at scale? It's blocking and a coordinator failure can leave participants holding locks indefinitely; latency and availability suffer across a partition. Sagas trade atomicity for availability. - Q: 2PC vs 3PC? 3PC adds a pre-commit phase to reduce blocking on coordinator failure, but it assumes synchronous networks and still fails under partitions — rarely used in practice. - Q: What's the modern alternative? Saga pattern with compensating transactions and eventual consistency, plus idempotency keys.

15. Saga Pattern

Definitionsequence of local transactionscompensating actionorchestrationchoreographyPick it when

Definition. Model a long-running, cross-service transaction as a sequence of local transactions, each with a compensating action that undoes it. If a step fails, previously completed steps are compensated in reverse order. Two flavors: orchestration (central coordinator) and choreography (services react to events).

  • Pick it when: distributed business workflows need to span services without holding global locks.
  • Trade-off: only eventual consistency; you must design and test compensations carefully.

Real-world example — DoorDash order workflow. Placing a DoorDash order touches several services — create order, charge payment, notify the restaurant, assign a courier — and they live in separate services with their own databases, so a single ACID transaction spanning all of them is impossible. A saga runs them as a sequence of local transactions, each with a compensating action that semantically undoes it. If the payment succeeds but no courier can be assigned, the saga compensates backwards — refund the payment, cancel the order — to return the system to a consistent state, rather than leaving money taken for an order that won't happen. An orchestrator service commonly drives the sequence and decides when to trigger compensation (vs. choreography, where each service reacts to the previous one's event). The accepted trade-off is eventual consistency: for brief moments the order may be "charged but not yet assigned," and every step must be idempotent so that a retried "charge" doesn't bill the customer twice. The same shape appears in travel booking (flight + hotel + car, undo the ones that succeeded if a later one fails).

Create Order→Reserve Inventory→Charge Payment
if Charge FAILS→compensate: Release Inventory→Cancel Orderreverse order 
class Saga:
    """Orchestrated saga: run steps; on failure, compensate in reverse."""
    def __init__(self): self.steps = []      # (action, compensation)
    def add(self, action, compensation):
        self.steps.append((action, compensation)); return self

    def run(self):
        done = []
        try:
            for action, comp in self.steps:
                action()
                done.append(comp)            # remember how to undo
        except Exception as e:
            print(f"  ✗ failed: {e} → compensating")
            for comp in reversed(done):      # undo in reverse order
                comp()
            return "ROLLED_BACK"
        return "COMPLETED"

saga = (Saga()
    .add(lambda: print("create order"),     lambda: print("cancel order"))
    .add(lambda: print("reserve stock"),    lambda: print("release stock"))
    .add(lambda: (_ for _ in ()).throw(Exception("payment declined")),
                                            lambda: print("refund")))
print(saga.run())
# create order / reserve stock / ✗ failed → compensating / release stock / cancel order
# ROLLED_BACK

Interview Q&A - Q: Orchestration vs choreography? Orchestration uses a central coordinator (easy to reason about, single point to manage). Choreography uses events with no coordinator (loosely coupled but harder to trace/debug). - Q: Why must every step be idempotent? Retries and re-deliveries can run a step twice; idempotency (via keys) prevents double charges/double shipments. - Q: Saga vs 2PC? Saga gives availability and no global locks but only eventual consistency and requires compensations. 2PC gives atomic consistency but blocks and scales poorly.

16. Message Queue

DefinitionproducerconsumeracknowledgingPick it whenTrade-off

Definition. A buffer that holds messages between a producer and a consumer so they run independently. The producer enqueues and moves on; consumers dequeue and process at their own pace, acknowledging when done so failed work can be retried.

  • Pick it when: you need asynchronous processing, load leveling, or decoupling between services.
  • Trade-off: added end-to-end latency and operational complexity; ordering/duplicate handling needs care.

Real-world example — Amazon order processing. When you click "Buy now," Amazon doesn't make you wait while it reserves inventory, charges your card, schedules the warehouse pick, and emails a receipt. The order is dropped onto a queue (SQS-style) and the web request returns to you in milliseconds; pools of workers then pull from the queue and do the slow work asynchronously at their own pace. This decouples the spiky front end from the steady back end — a Prime Day traffic burst simply makes the queue longer rather than overwhelming the fulfillment systems, which is the "load leveling" benefit. The trade-offs are the pattern's: added end-to-end latency (your receipt email shows up seconds later, not instantly) and the need for idempotent consumers plus a dead-letter queue, because at-least-once delivery means a message can be processed more than once, and a "poison" message that always fails must be shunted aside so it doesn't block the queue forever.

producer ─► [ msg | msg | msg ] ─► consumer  (process → ack)
            (queue absorbs bursts; unacked msgs are redelivered)
from collections import deque

class MessageQueue:
    def __init__(self): self.q, self.inflight = deque(), {}
    def publish(self, msg): self.q.append(msg)

    def consume(self):
        if not self.q: return None
        msg = self.q.popleft()
        self.inflight[id(msg)] = msg        # held until ack
        return msg

    def ack(self, msg):  self.inflight.pop(id(msg), None)      # done
    def nack(self, msg):                                        # failed → requeue
        self.inflight.pop(id(msg), None); self.q.append(msg)

mq = MessageQueue()
mq.publish("send-email:1"); mq.publish("send-email:2")
m = mq.consume()
try:
    raise RuntimeError("smtp down")        # processing fails
except RuntimeError:
    mq.nack(m)                             # requeue for retry
print(mq.consume())                        # 'send-email:2'
print(mq.consume())                        # 'send-email:1' (redelivered)

Interview Q&A - Q: At-least-once vs exactly-once delivery? At-least-once (ack after processing) can duplicate on retry — make consumers idempotent. True exactly-once is hard; usually it's at-least-once + dedup/idempotency. - Q: How do you handle a "poison" message that always fails? A dead-letter queue (DLQ) after N retries, so it stops blocking the queue and can be inspected. - Q: How do you preserve ordering? Partition by key and process each partition with one consumer (per-key ordering), as Kafka does — global ordering kills parallelism.

17. Publish-Subscribe

Definitiontopicfan-outsallPick it whenTrade-off

Definition. Producers publish messages to a topic; the broker fan-outs a copy to every subscriber of that topic. Unlike a point-to-point queue (one consumer per message), pub/sub delivers each message to all interested subscribers.

  • Pick it when: multiple independent consumers need the same events (e.g., order placed → notify, ship, bill).
  • Trade-off: harder to debug (many consumers, async flows) and you must handle slow/failed subscribers.

Real-world example — LinkedIn / Kafka. LinkedIn created Kafka precisely because one event — "user updated their profile" — needs to reach many independent consumers: the search index, the news feed, analytics, the notifications service, and the data warehouse. With point-to-point queues you'd have to wire each producer to each consumer (an N×M mess); with pub-sub the producer just publishes to a topic and every subscriber gets its own copy, so a new consumer can be added later without touching — or even informing — the producer. Each consumer group tracks its own offset into the log, so a slow consumer, or a brand-new one, can read at its own pace and even replay history from the beginning. The trade-offs are debuggability (a single publish silently triggers many asynchronous side effects that are hard to trace end-to-end) and having to handle subscribers that lag, crash, or fall permanently behind. Google Cloud Pub/Sub and Redis Pub/Sub package the same broadcast semantics as a service.

                 ┌─► subscriber A (email)
publish("order")─┼─► subscriber B (shipping)
   topic         └─► subscriber C (analytics)     (every sub gets a copy)
class PubSub:
    def __init__(self): self.topics = {}          # topic -> [callbacks]

    def subscribe(self, topic, callback):
        self.topics.setdefault(topic, []).append(callback)

    def publish(self, topic, message):
        for cb in self.topics.get(topic, []):     # fan-out to all subscribers
            cb(message)

bus = PubSub()
bus.subscribe("order.placed", lambda m: print(f"[email]   confirm {m}"))
bus.subscribe("order.placed", lambda m: print(f"[ship]    pack {m}"))
bus.subscribe("order.placed", lambda m: print(f"[analytics] count {m}"))
bus.publish("order.placed", "order#42")
# [email] confirm order#42 / [ship] pack order#42 / [analytics] count order#42

Interview Q&A - Q: Pub/sub vs message queue? Queue = one message consumed by one worker (work distribution). Pub/sub = one message delivered to all subscribers (event broadcast). Kafka consumer groups combine both. - Q: How do you add a new consumer without touching producers? That's the point — subscribers register independently; the producer is unaware of who listens, enabling loose coupling. - Q: What if a subscriber is slow or down? Use durable per-subscriber queues/offsets so each consumes at its own pace and can catch up after downtime.

18. Event-Driven Architecture

Definitionemitting and reacting to eventsPick it whenTrade-offAWS LambdaInterview Q&A

Definition. Services communicate by emitting and reacting to events rather than calling each other directly. A component publishes "something happened"; interested components react autonomously. This maximizes decoupling and enables async, scalable workflows.

  • Pick it when: services should react to state changes without tight coupling or synchronous chains.
  • Trade-off: eventual consistency, harder end-to-end tracing, and event-ordering/duplication concerns.

Real-world example — Uber trip lifecycle. An Uber trip is a lifecycle of events — requested, driver-matched, started, completed, paid — and many services react to each event independently instead of one service calling all the others in a rigid chain. When trip.completed is emitted, pricing finalizes the fare, the receipt service emails the rider, the driver-earnings service credits the driver, and analytics records the trip — all without the trip service knowing those consumers even exist. This loose coupling is the whole point: a team can add a new reaction (say, loyalty points) by subscribing to the existing event, with zero changes to the emitter, and each consumer scales on its own. The trade-offs are the pattern's: eventual consistency (the receipt email lags the trip actually ending) and genuinely hard debugging, which is why event-driven shops invest heavily in correlation/trace IDs and distributed tracing to reconstruct "what happened" across the asynchronous fan-out. AWS Lambda triggering on S3/DynamoDB/EventBridge events is the same model in serverless form.

19. Stream Processing

Definitionunbounded streamtime windowsPick it whenTrade-offFlink

Definition. Continuously process an unbounded stream of events in near real-time, typically computing aggregations over time windows (counts, sums, averages) instead of waiting to batch-process at rest.

  • Pick it when: you need real-time analytics, monitoring, or alerting (fraud, metrics, dashboards).
  • Trade-off: operational complexity — windowing, late/out-of-order events, state management, and exactly-once semantics.

Real-world example — Uber surge pricing & fraud detection. Some answers are worthless if they arrive in tomorrow's batch job. Uber computes surge multipliers by continuously aggregating, per geographic cell over a rolling time window, the live ratio of ride requests to available drivers — a streaming computation that must update within seconds, not a nightly report. Banks similarly score each card transaction for fraud within milliseconds by maintaining streaming features (spend velocity, sudden location jumps, merchant risk) as events flow in. These pipelines are built on Kafka feeding stream processors like Flink or Spark Streaming, using windowed aggregations over the event stream. The operational trade-offs are precisely what makes streaming hard: handling events that arrive late or out of order (watermarks and allowed-lateness), managing large in-flight state across a cluster, and achieving exactly-once semantics so a single transaction isn't counted twice in the fraud features.

from collections import defaultdict

class TumblingWindowAggregator:
    """Count events per fixed-size time window (e.g. clicks per 10s)."""
    def __init__(self, window_size):
        self.window_size = window_size
        self.windows = defaultdict(int)

    def process(self, event_time, _value):
        window = event_time // self.window_size      # bucket by window index
        self.windows[window] += 1

    def results(self):
        return {f"[{w*self.window_size}-{(w+1)*self.window_size}s)": c
                for w, c in sorted(self.windows.items())}

20. Webhook Pattern

Definitioncalls the client backPick it whenTrade-offsignsretries

Definition. Instead of a client polling for changes, the server calls the client back at a pre-registered URL when an event occurs ("reverse API"). Common for third-party integrations (payments, CI, chat).

  • Pick it when: external systems must be notified of events promptly without polling.
  • Trade-off: delivery reliability — the receiver may be down; you need retries, signatures, and idempotency.

Real-world example — Stripe payments & GitHub. After a card payment, your server needs to know the result, but polling Stripe ("is it done yet?") thousands of times is wasteful and slow. Instead Stripe calls you: when the charge settles it sends an HTTP POST — a webhook — to your registered endpoint carrying a payment_intent.succeeded event, and your server fulfills the order on receipt. GitHub does the same to drive CI/CD: a push event fires a webhook that kicks off your build pipeline. Because the public internet is unreliable, this pattern's trade-offs are front and center and Stripe addresses each one explicitly: it signs every payload with an HMAC secret (so you can verify the request is genuinely from Stripe and not a forgery), it retries with backoff for hours if your endpoint is down, and it expects you to dedupe on the event ID because a webhook may legitimately be delivered more than once. Skipping any of those is how teams end up double-fulfilling orders or trusting spoofed callbacks.

import hmac, hashlib, time

class WebhookDispatcher:
    def __init__(self, secret): self.subs, self.secret = [], secret.encode()
    def register(self, url, handler): self.subs.append((url, handler))

    def _sign(self, body):                      # let receiver verify authenticity
        return hmac.new(self.secret, body.encode(), hashlib.sha256).hexdigest()

    def deliver(self, body, max_retries=3):
        sig = self._sign(body)
        for url, handler in self.subs:
            for attempt in range(max_retries):
                ok = handler(body, sig)         # simulate HTTP POST → expect 2xx
                if ok: break
                time.sleep(0.01 * (2 ** attempt))   # exponential backoff
            else:
                print(f"  → dead-letter for {url}")

def receiver(body, sig, secret=b"shh"):
    expected = hmac.new(secret, body.encode(), hashlib.sha256).hexdigest()
    if not hmac.compare_digest(sig, expected): return False   # reject forgery
    print(f"  received & verified: {body}"); return True

wh = WebhookDispatcher(secret="shh")
wh.register("https://acme/hook", receiver)
wh.deliver('{"event":"payment.succeeded","id":"pi_1"}')

Polling is pull (simple, robust) but wastes calls and adds latency. - Q: How do you make webhook handling safe against retries? 21. Circuit Breaker

DefinitionClosedOpenHalf-OpenPick it whenTrade-off

Definition. Wrap calls to a flaky dependency in a state machine that "trips" after repeated failures. Closed = calls pass through. Open = calls fail fast without hitting the dependency. Half-Open = after a cooldown, allow a probe call; success closes it, failure re-opens it. Prevents cascading failures.

  • Pick it when: a dependency's failures could cascade and exhaust your resources (threads, connections).
  • Trade-off: recovery tuning — thresholds/timeouts must be set right, and an open breaker rejects some requests that might have succeeded.

Real-world example — Netflix Hystrix. A Netflix homepage is assembled from dozens of microservices — personalization, bookmarks ("continue watching"), ratings, artwork, and more. Without protection, one slow dependency is catastrophic: callers' threads pile up blocked on it, that thread exhaustion spreads to the callers' callers, and the whole page eventually fails — a single weak service drags down everything. Hystrix wrapped every cross-service call in a circuit breaker: once errors/timeouts to a dependency cross a threshold, the breaker opens and further calls fail instantly — typically returning a graceful fallback, like a generic "popular titles" row instead of personalized recommendations — rather than hanging and consuming threads. After a cooldown it half-opens, lets a single probe call through, and closes again only if the dependency has recovered. The trade-off is tuning: set the thresholds and timeouts too tight and you trip on harmless blips (rejecting good traffic), too loose and you're still cascading before it opens.

CLOSED ──failures ≥ threshold──► OPEN ──after timeout──► HALF-OPEN
   ▲                                                        │
   └──────────── probe success ─────────────────┘   probe fail → OPEN
import time

class CircuitBreaker:
    def __init__(self, threshold=3, timeout=1.0):
        self.threshold, self.timeout = threshold, timeout
        self.failures, self.state, self.opened_at = 0, "CLOSED", None

    def call(self, fn, *args):
        if self.state == "OPEN":
            if time.time() - self.opened_at >= self.timeout:
                self.state = "HALF_OPEN"          # time to probe
            else:
                raise RuntimeError("circuit OPEN — failing fast")
        try:
            result = fn(*args)
        except Exception:
            self.failures += 1
            if self.failures >= self.threshold:
                self.state, self.opened_at = "OPEN", time.time()
            raise
        self.failures, self.state = 0, "CLOSED"   # success resets
        return result

cb = CircuitBreaker(threshold=2, timeout=0.5)
def flaky(): raise ConnectionError("down")
for _ in range(3):
    try: cb.call(flaky)
    except Exception as e: print(cb.state, "-", e)
# CLOSED - down / OPEN - down / OPEN - circuit OPEN — failing fast

Interview Q&A - Q: Why fail fast instead of waiting for timeouts? Each blocked call holds a thread/connection; under failure those pile up and take down the caller too. Failing fast frees resources and sheds load. - Q: What does half-open accomplish? It tests recovery with a single probe rather than flooding a recovering service — automatic, gradual recovery. - Q: Circuit breaker vs retry? Retry handles transient blips by trying again; circuit breaker handles sustained outages by stopping calls. They compose — but retry behind an open breaker, and add backoff to avoid retry storms.

22. Retry Pattern

Definitiontransientexponential backoffjitterPick it whenTrade-off

Definition. Automatically re-attempt a failed operation that is likely transient (timeout, brief 503). To avoid hammering a struggling service, use exponential backoff with jitter (randomization) so retries spread out.

  • Pick it when: temporary failures are common and operations are safe to repeat.
  • Trade-off: retry storms — naive synchronized retries can overload a recovering service; retries amplify load and must target only idempotent operations.

Real-world example — AWS SDK retries. Transient failures — a throttled request, a brief 503, a dropped packet — are simply normal at cloud scale, so every AWS SDK automatically retries failed calls. The important part is how: AWS published the now-standard analysis showing that naive retries make outages worse, because every client retries on the same fixed schedule and synchronously hammers a service that's trying to recover — a self-inflicted "retry storm" / thundering herd. The fix is exponential backoff with jitter: each attempt waits roughly double the previous delay, plus a random component so clients desynchronize and spread their load over time instead of spiking in lockstep. Retries are capped at a few attempts and applied only to ret-safe operations. The trade-off is that retrying a non-idempotent write without an idempotency key can duplicate the effect (e.g. a double charge), which is why production retry logic is almost always paired with idempotency keys and a circuit breaker that stops retries entirely once a dependency is clearly down.

attempt 1 fail→wait base·2⁰ ± jitter
attempt 2 fail→wait base·2¹ ± jitter
attempt 3 fail→wait base·2² ± jitter→give up / DLQ 
import random, time

def retry(fn, max_attempts=5, base=0.1, cap=2.0):
    for attempt in range(max_attempts):
        try:
            return fn()
        except Exception as e:
            if attempt == max_attempts - 1:
                raise
            backoff = min(cap, base * (2 ** attempt))
            sleep = backoff * (0.5 + random.random())     # full jitter
            print(f"  attempt {attempt+1} failed ({e}); retrying in {sleep:.2f}s")
            time.sleep(sleep)

calls = {"n": 0}
def sometimes():
    calls["n"] += 1
    if calls["n"] < 3: raise TimeoutError("transient")
    return "success"

print(retry(sometimes))   # retries twice, then 'success'

Interview Q&A - Q: Why add jitter? Without it, many clients retry at the exact same backoff intervals, creating synchronized spikes (thundering herd). Jitter desynchronizes them. - Q: Which operations are safe to retry? Idempotent ones (GET, or writes guarded by an idempotency key). Blindly retrying a non-idempotent POST can double-charge. - Q: How do retries interact with circuit breakers? Cap total attempts, retry only transient errors, and let an open circuit breaker short-circuit retries so you don't pummel a down service.

23. Bulkhead

Definitioncan't sink the whole systemPick it whenTrade-offInterview Q&AQ: Bulkhead vs circuit breaker?

Definition. Isolate resources into separate pools (like watertight compartments in a ship) so a failure or overload in one part can't sink the whole system. E.g., give each downstream dependency its own bounded thread/connection pool.

  • Pick it when: you want to contain failures so one misbehaving dependency doesn't exhaust shared resources for everyone.
  • Trade-off: resource fragmentation — partitioned pools can't share spare capacity, so you provision more in total.

Real-world example — Netflix thread pools. The name comes from a ship's watertight compartments: a hull breach floods one compartment, but the bulkheads keep the rest dry and the ship afloat. Netflix applies this by giving each downstream dependency its own bounded thread pool (again via Hystrix) instead of letting all calls share one global pool. So if the "recommendations" service goes slow and saturates its dedicated 10-thread pool, new calls to recommendations are rejected immediately once that pool is full — but the "playback" and "bookmarks" pools are completely untouched, and the rest of the page still renders. The failure is contained to one compartment instead of draining the shared resource that every feature depends on. The trade-off is resource fragmentation: partitioned pools can't lend each other spare capacity, so you must provision more threads/connections in total than a single shared pool would need — you're trading raw utilization for isolation. AWS applies the same principle at the architecture level with cell-based designs that cap each cell's blast radius.

Without bulkhead: one slow dependency drains the shared pool → everything stalls
With bulkhead:    [pool A: svc1] [pool B: svc2] [pool C: svc3]  → failure contained
import threading

class Bulkhead:
    """Cap concurrent calls per dependency with a bounded semaphore."""
    def __init__(self, max_concurrent):
        self.sem = threading.BoundedSemaphore(max_concurrent)

    def call(self, fn, *args):
        if not self.sem.acquire(blocking=False):
            raise RuntimeError("bulkhead full — rejected (protecting others)")
        try:
            return fn(*args)
        finally:
            self.sem.release()

payments = Bulkhead(max_concurrent=2)   # payments can use at most 2 slots
held = [payments.sem.acquire() for _ in range(2)]    # simulate 2 in-flight calls
try:
    payments.call(lambda: "charge")     # 3rd call rejected, not queued forever
except RuntimeError as e:
    print(e)                            # bulkhead full — rejected (protecting others)

They're complementary layers of isolation. - Q: Real-world example? Separate thread pools per downstream service so a slow recommendations API can't consume all threads and block checkout. - Q: Downside? Statically partitioned capacity can leave one pool starved while another sits idle — you trade utilization for isolation.

24. Rate Limiting

Definitiontoken bucketPick it whenTrade-offInterview Q&A

Definition. Cap how many requests a client may make in a time window to protect services from overload and abuse and ensure fair sharing. The token bucket is the most common algorithm: tokens refill at a fixed rate; each request spends one; empty bucket → reject (HTTP 429).

  • Pick it when: you need to protect a service from spikes/abuse or enforce quotas.
  • Trade-off: legitimate users may get throttled; distributed rate limiting needs shared state (Redis).

Real-world example — GitHub / Stripe APIs. A public API must defend itself against a single client — a buggy script, an aggressive scraper, or an attacker — consuming all of its capacity, so it caps each caller. GitHub's REST API, for instance, allows authenticated clients on the order of 5,000 requests per hour and returns HTTP 429 along with Retry-After and X-RateLimit-Remaining / X-RateLimit-Reset headers, so a well-behaved client can see exactly how much budget is left and self-throttle. The usual implementation is a token bucket keyed by API key or user, with the counters held in a shared store like Redis so the limit is enforced globally across all of the provider's servers rather than separately per instance (otherwise N servers would each allow the full limit). The trade-off is that a legitimate burst can get throttled, which is why good APIs surface the headers and sell higher tiers instead of silently dropping requests.

bucket capacity = 5, refill = 2/sec
[●●●●●] req→[●●●●] … refills over time … empty → 429 Too Many Requests
import time

class TokenBucket:
    def __init__(self, capacity, refill_rate):
        self.capacity, self.refill_rate = capacity, refill_rate
        self.tokens, self.last = capacity, time.time()

    def allow(self, cost=1):
        now = time.time()
        # refill based on elapsed time, capped at capacity
        self.tokens = min(self.capacity,
                          self.tokens + (now - self.last) * self.refill_rate)
        self.last = now
        if self.tokens >= cost:
            self.tokens -= cost
            return True
        return False                # → caller returns HTTP 429

bucket = TokenBucket(capacity=3, refill_rate=2)   # 3 burst, 2/sec sustained
print([bucket.allow() for _ in range(5)])   # [True, True, True, False, False]
time.sleep(1)                               # ~2 tokens refill
print(bucket.allow())                       # True

Centralize counters in Redis (atomic Lua script) so the limit is global, not per-instance. - Q: What response should you return? HTTP 429 with Retry-After and X-RateLimit-* headers so clients can back off gracefully.

25. Failover

DefinitionstandbyprimaryPick it whenTrade-offInterview Q&A

Definition. Maintain a standby that automatically takes over when the primary fails, detected via health checks/heartbeats. Active-passive keeps a warm standby; active-active runs both and reroutes on failure. Goal: high availability with minimal downtime.

  • Pick it when: high availability is required and downtime is costly.
  • Trade-off: duplicate infrastructure cost (idle standby) and risks like split-brain and failback complexity.

Real-world example — Amazon RDS Multi-AZ. For a managed database that has to stay up, RDS Multi-AZ keeps a synchronous standby replica in a different availability zone. Health checks continuously monitor the primary, and if it fails — hardware fault, AZ outage, crash — RDS automatically promotes the standby and flips the database's DNS endpoint to point at it, so applications reconnect to the same hostname and typically see only a minute or two of disruption. The choice of synchronous replication is what makes the failover safe: the standby is always up to date, so promoting it doesn't lose committed data (favoring a low RPO). The trade-offs are cost and correctness: you pay for a full standby that serves no read traffic in normal operation, and the system must use quorum/fencing so that a network partition can't leave two nodes both believing they're primary and accepting conflicting writes (split-brain).

heartbeat OK→traffic→PRIMARYSTANDBY idle/warm
heartbeat LOST→promote STANDBY→traffic→STANDBYnow primary 
class FailoverCluster:
    def __init__(self, primary, standby):
        self.nodes = {"primary": primary, "standby": standby}
        self.active = "primary"
        self.healthy = {"primary": True, "standby": True}

    def heartbeat(self, node, alive):
        self.healthy[node] = alive
        if node == self.active and not alive:
            self._failover()

    def _failover(self):
        backup = "standby" if self.active == "primary" else "primary"
        if self.healthy[backup]:
            print(f"  PRIMARY down → promoting {backup}")
            self.active = backup

    def handle(self, req):
        return self.nodes[self.active].serve(req)

class Node:
    def __init__(self, name): self.name = name
    def serve(self, req): return f"{self.name} served {req}"

cluster = FailoverCluster(Node("db-1"), Node("db-2"))
print(cluster.handle("read"))          # db-1 served read
cluster.heartbeat("primary", alive=False)   # primary dies → auto-failover
print(cluster.handle("read"))          # db-2 served read

Passive keeps a standby idle (cheaper, simpler, wasted capacity). Active-active serves from both (better utilization + instant failover) but needs conflict handling and is harder to keep consistent. - Q: RTO vs RPO? RTO = how fast you recover (downtime tolerance). 26. Leader Election

Definitionone leaderPick it whenTrade-offInterview Q&AQ: Why not just hardcode a leader?

Definition. Among a group of equal nodes, pick one leader to coordinate (e.g., be the single writer, scheduler, or sequencer). If the leader fails, the remaining nodes elect a new one. Often implemented with a lease/lock in a coordination service (ZooKeeper, etcd) or consensus (Raft).

  • Pick it when: exactly one node must perform an action (single coordinator/writer) to avoid conflicts.
  • Trade-off: election overhead and a brief unavailability window during re-election; needs a quorum to avoid split-brain.

Real-world example — Kafka controller. A Kafka cluster has many brokers, but exactly one must act as the controller — the single brain that assigns partition leaders and reacts to broker failures — because two controllers making conflicting decisions would corrupt cluster metadata. The brokers elect one controller through a coordination service (historically ZooKeeper, now Kafka's built-in KRaft Raft quorum); whoever wins holds the role, and if it dies the others detect the lost heartbeat and elect a new controller within seconds. MongoDB replica sets do the analogous thing to choose the single primary that accepts writes, and Kubernetes uses leader election (via etcd leases) so only one instance of a controller-manager is active at a time. The trade-offs are a brief unavailability window during re-election and the requirement for a quorum (majority) to vote — which is exactly what prevents two nodes from both believing they're leader after a network partition.

nodes acquire a lease (TTL) in etcd/ZK → holder = leader
leader renews lease (heartbeat). If it stops → lease expires → others elect new leader
import time

class LeaseManager:
    """One lease holder = the leader; expires if not renewed (heartbeat)."""
    def __init__(self, ttl=1.0):
        self.ttl, self.holder, self.expires_at = ttl, None, 0

    def acquire(self, node):
        now = time.time()
        if self.holder is None or now > self.expires_at:   # vacant/expired
            self.holder, self.expires_at = node, now + self.ttl
        return self.holder == node            # True if this node is leader

    def renew(self, node):
        if self.holder == node:
            self.expires_at = time.time() + self.ttl

mgr = LeaseManager(ttl=0.5)
print("n1 leader?", mgr.acquire("n1"))   # True  → n1 is leader
print("n2 leader?", mgr.acquire("n2"))   # False → n1 still holds lease
time.sleep(0.6)                           # n1 stopped renewing → lease expired
print("n2 leader?", mgr.acquire("n2"))   # True  → n2 takes over

Interview Q&A - Q: How do leases avoid two leaders? A single atomic lease/lock in a quorum-backed store; only one holder at a time, and it expires if not renewed. Fencing tokens stop a paused old leader from acting after losing the lease. - Q: Why not just hardcode a leader? A static leader is a single point of failure with no automatic recovery; election gives fault tolerance. - Q: How does Raft elect a leader? Nodes use randomized election timeouts; a candidate that gets votes from a majority for a term becomes leader and sends heartbeats to stay leader.

27. Service Discovery

DefinitionregistryPick it whenTrade-offInterview Q&AQ: How are dead instances removed?

Definition. In a dynamic environment where service instances come and go (autoscaling, restarts, new IPs), a registry tracks healthy instances. Clients look up "where is service X?" instead of hardcoding addresses. Client-side discovery queries the registry directly; server-side hides it behind a load balancer.

  • Pick it when: service locations change dynamically (containers, autoscaling).
  • Trade-off: the registry is additional infrastructure to run and keep highly available and consistent.

Real-world example — Netflix Eureka / Kubernetes. In an autoscaling cloud, instances are cattle, not pets — created and destroyed constantly, with ever-changing IPs — so hardcoding addresses is impossible. Netflix built Eureka as a registry where each instance registers itself on startup and then sends periodic heartbeats; a caller asks Eureka for the current healthy instances of, say, payment-service and load-balances across them, and any instance that stops heartbeating is dropped so traffic stops flowing to it. Kubernetes bakes the same idea in natively: a Service object gives a stable virtual name and IP, and kube-proxy plus cluster DNS resolve it to the live set of pod endpoints, which the control plane continuously updates as pods are created and killed. The trade-off is that the registry itself becomes critical infrastructure — it has to be run highly-available and kept reasonably consistent, because if discovery is wrong, callers route to dead instances.

import time, random

class ServiceRegistry:
    def __init__(self, ttl=2.0):
        self.ttl = ttl
        self.services = {}        # name -> {addr: last_heartbeat}

    def register(self, name, addr):
        self.services.setdefault(name, {})[addr] = time.time()

    def heartbeat(self, name, addr):
        self.services[name][addr] = time.time()

    def discover(self, name):
        now = time.time()
        alive = [a for a, ts in self.services.get(name, {}).items()
                 if now - ts < self.ttl]            # drop stale instances
        return random.choice(alive) if alive else None

reg = ServiceRegistry()
reg.register("payment", "10.0.0.1:8080")
reg.register("payment", "10.0.0.2:8080")
print(reg.discover("payment"))     # one healthy instance
time.sleep(2.1)                    # no heartbeats → both expire
print(reg.discover("payment"))     # None (all stale)

28. API Gateway

DefinitionroutesPick it whenTrade-offReal-world example — Netflix ZuulAWS API Gateway

Definition. A single entry point in front of many backend services. It routes requests to the right service and centralizes cross-cutting concerns: authentication, rate limiting, TLS termination, request/response transformation, and aggregation.

  • Pick it when: you have many backend services and want one front door for clients + shared policies.
  • Trade-off: a central component that can become a bottleneck or single point of failure (scale it out, keep it thin).

Real-world example — Netflix Zuul. A Netflix mobile app shouldn't have to open dozens of connections to dozens of microservices, each enforcing its own auth and rate limits. Zuul is the single front door: every client request hits the gateway, which authenticates it, enforces rate limits, terminates TLS, routes it to the correct backend, and can even aggregate several backend calls into one tailored response (a Backend-for-Frontend that shapes data differently for mobile vs. web). This centralizes cross-cutting concerns so individual services don't each reimplement authentication, throttling, and TLS. The trade-off is that the gateway is a potential bottleneck and single point of failure, so it's run as many stateless replicas behind a load balancer and kept deliberately thin — routing and policy only, with business logic pushed down into the services. AWS API Gateway is the managed equivalent, and Kong a popular self-hosted one.

client ─► API GATEWAY ─► [auth → rate-limit → route] ─► user-svc | order-svc | …

class APIGateway:
    def __init__(self):
        self.routes = {}                 # path prefix -> backend handler
        self.tokens = {"valid-token"}
        self.limiter = TokenBucket(capacity=5, refill_rate=5)  # from §24

    def add_route(self, prefix, backend): self.routes[prefix] = backend

    def handle(self, path, token):
        if token not in self.tokens:                 # 1) authenticate
            return "401 Unauthorized"
        if not self.limiter.allow():                 # 2) rate limit
            return "429 Too Many Requests"
        for prefix, backend in self.routes.items():  # 3) route
            if path.startswith(prefix):
                return backend(path)
        return "404 Not Found"

Run multiple stateless gateway instances behind a load balancer, keep logic thin, and push heavy work to backends. - Q: BFF (Backend-for-Frontend) pattern? 29. Sidecar Pattern

DefinitionPick it whenTrade-offFluent BitInterview Q&AQ: Examples of sidecars?

Definition. Deploy shared, cross-cutting functionality (logging, retries, TLS, metrics, config) as a separate process/container that runs alongside the main service in the same unit (pod), sharing its lifecycle and network. The app stays focused on business logic; the sidecar handles the platform concerns.

  • Pick it when: you want consistent cross-cutting behavior across services written in different languages, without embedding it in each app.
  • Trade-off: extra resource use (one sidecar per instance) and added operational/latency overhead per hop.

Real-world example — Envoy in Kubernetes/Istio. Cross-cutting networking concerns — mutual-TLS encryption, retries, timeouts, metrics, traffic shifting — are needed by every service regardless of the language it's written in. Rather than build and maintain a library for Java, Go, Python, and Node and then redeploy all of them every time a policy changes, the sidecar pattern runs an Envoy proxy as a second container in the same pod as each application, and routes all of the app's network traffic through that local Envoy. The application stays completely oblivious — it just makes a plain HTTP call to localhost — while Envoy transparently adds encryption, retries, and telemetry. This language-agnostic, independently-upgradable approach is the trade-off in action: you pay extra CPU/memory for one proxy per instance and an added local network hop of latency, in exchange for uniform behavior everywhere and the ability to change policy without touching app code. Log shippers like Fluent Bit run as sidecars for the same reason.

┌──────── pod ────────┐
│  app  ⇄  sidecar ⇄──┼──► network   (sidecar adds retries, mTLS, metrics, logs)
└─────────────────────┘
class Sidecar:
    """Proxy that adds cross-cutting concerns around the app's calls."""
    def __init__(self, app_name): self.app_name = app_name
    def outbound(self, send_fn, request):
        print(f"  [sidecar] log: {self.app_name} → {request}")   # observability
        for attempt in range(3):                                  # retries
            try:
                resp = send_fn(request)        # mTLS/encryption would go here
                print(f"  [sidecar] metric: success in {attempt+1} try")
                return resp
            except Exception:
                continue
        raise RuntimeError("[sidecar] all retries failed")

class App:
    def call_other_service(self, sidecar, payload):
        # app code is oblivious to retries/logging/mTLS — sidecar owns them
        return sidecar.outbound(self._raw_send, payload)
    def _raw_send(self, payload): return f"response to {payload}"

sidecar = Sidecar("order-service")
print(App().call_other_service(sidecar, "GET /inventory"))

Interview Q&A - Q: Why a sidecar instead of a shared library? A sidecar is language-agnostic and upgraded independently of the app; a library must be reimplemented per language and redeployed with each service. - Q: Examples of sidecars? Envoy proxy (in a service mesh), log shippers (Fluent Bit), and secret/cert agents (Vault agent). - Q: Downsides? One sidecar per instance multiplies resource usage, and every call adds a local proxy hop (latency).

30. Service Mesh

Definitionservice-to-service communicationdata planecontrol planePick it whenTrade-off

Definition. A dedicated infrastructure layer that manages service-to-service communication across a fleet of microservices. A data plane of sidecar proxies (one per service) handles routing, mTLS, retries, load balancing, and telemetry; a control plane configures all the proxies centrally. App code stays free of networking logic.

  • Pick it when: you operate many microservices and need uniform security, traffic management, and observability without changing app code.
  • Trade-off: significant operational complexity and per-hop latency/resource overhead — overkill for small systems.

Real-world example — Istio/Linkerd (Envoy from Lyft). A service mesh is what you get when you give every service a sidecar proxy (the data plane) and manage them all from a central control plane. Lyft built Envoy for exactly this situation — hundreds of microservices that all needed consistent mTLS, retries, load balancing, and observability for service-to-service ("east-west") traffic, without each team coding it themselves. With Istio or Linkerd, a platform team configures policy once in the control plane — "encrypt all internal traffic," or "shift 5% of orders-service traffic to the canary version" — and it's pushed automatically to every proxy in the fleet, enabling zero-code mTLS, canary/blue-green rollouts, and uniform distributed tracing across a polyglot system. The trade-off is heavy operational complexity (you now run and upgrade a mesh) and per-hop latency/resource overhead from the proxies, which is why a mesh is overkill for a handful of services and only pays for itself at large microservice scale — it's the natural endgame of the sidecar pattern (#29).

        ▼                 ▼                 ▼
[svc A | proxy] ⇄ [svc B | proxy] ⇄ [svc C | proxy]   ← data plane (sidecars)

class ControlPlane:
    """Pushes uniform policy to every data-plane proxy."""
    def __init__(self): self.policy = {"retries": 2, "mtls": True, "timeout": 1.0}
    def register(self, proxy): proxy.policy = self.policy   # central config

class MeshProxy:
    """Data-plane sidecar: applies mesh policy to each call."""
    def __init__(self, service): self.service, self.policy = service, {}
    def call(self, target_proxy, request):
        if self.policy.get("mtls"):
            print(f"  [{self.service}→{target_proxy.service}] mTLS handshake")
        for attempt in range(self.policy.get("retries", 1) + 1):
            try:
                return target_proxy.serve(request)
            except Exception:
                continue
        raise RuntimeError("mesh: retries exhausted")
    def serve(self, request): return f"{self.service} handled {request}"

cp = ControlPlane()
a, b = MeshProxy("orders"), MeshProxy("inventory")
cp.register(a); cp.register(b)            # both get uniform policy centrally
print(a.call(b, "reserve item"))          # mTLS + retries applied automatically

They're complementary. - Q: What problems does a mesh solve over per-app libraries? Uniform mTLS, retries, traffic shifting (canary/blue-green), and tracing across polyglot services — configured centrally, with zero app code changes. - Q: When is a mesh not worth it? Small systems with few services — the operational overhead (running Istio/Linkerd, extra proxies, latency) outweighs the benefits; start simpler.

A1. Virtual Private Cloud (VPC)

DefinitionIP address rangePick it whenTrade-offReal-world example — AWS VPCpublic

Definition. A VPC is a logically isolated virtual network you carve out inside a public cloud, with its own private IP address range (a CIDR block like 10.0.0.0/16). You launch resources — VMs, databases, load balancers — inside it, and you control its routing, address layout, and what may enter or leave. Although it runs on shared physical hardware alongside other tenants, traffic is isolated as if it were your own private data-center network.

  • Pick it when: essentially every cloud deployment — any time you need network isolation, private addressing, and control over which resources can reach the internet or each other.
  • Trade-off: configuration complexity. You now own CIDR planning, route tables, gateways, and peering; a poorly chosen address range (one that overlaps on-prem or another VPC) blocks future peering/VPN without painful re-addressing.

Real-world example — AWS VPC. Every AWS account ships with a default VPC so you can launch an instance immediately, but real deployments define a custom VPC to get control. A typical company gives its production VPC the range 10.0.0.0/16 (65,536 private addresses) and splits it into public subnets that hold internet-facing load balancers and NAT gateways, and private subnets that hold the application servers and the database. The database is given no route to the internet at all — it is reachable only from the app servers inside the VPC, which is the isolation guarantee the whole structure exists to provide. Companies like Netflix and Airbnb go further and put production, staging, and test into separate VPCs, then connect the ones that must talk via VPC peering or a Transit Gateway. This is exactly where the trade-off bites: peering only works if the two VPCs' CIDR ranges don't overlap, so address planning that looks like busywork on day one is what keeps the network connectable on day 500. Google Cloud VPC and Azure VNet are the same concept under different names.

 internet ──┤ Internet Gateway                                        │
            │   ┌── public subnet 10.0.1.0/24 ──┐  ┌──── private subnet 10.0.2.0/24 ──┐
            │   │  load balancer · NAT gateway  │  │  app servers · database          │
            │   └────────────────────────────────┘  └─────────────────────────────────┘
            │   route: 0.0.0.0/0 → IGW              route: 0.0.0.0/0 → NAT (outbound only)
            └──────────── isolated from every other tenant's VPC ─────┘
import ipaddress

class VPC:
    """A logically isolated network: one CIDR block, carved into subnets."""
    def __init__(self, name, cidr):
        self.name = name
        self.cidr = ipaddress.ip_network(cidr)    # e.g. 10.0.0.0/16
        self.subnets = []

    def add_subnet(self, subnet):
        # isolation rule: a subnet must fit inside the VPC and not overlap a sibling
        if not subnet.cidr.subnet_of(self.cidr):
            raise ValueError(f"{subnet.cidr} is outside {self.name} ({self.cidr})")
        for existing in self.subnets:
            if subnet.cidr.overlaps(existing.cidr):
                raise ValueError(f"{subnet.cidr} overlaps {existing.cidr}")
        self.subnets.append(subnet)
        return subnet

    def contains(self, ip):                        # is this address inside the VPC?
        return ipaddress.ip_address(ip) in self.cidr

    def can_peer_with(self, other):                # peering requires non-overlapping CIDRs
        return not self.cidr.overlaps(other.cidr)

vpc = VPC("prod", "10.0.0.0/16")           # 65,536 private addresses, isolated
print(vpc.contains("10.0.5.20"))           # True  — inside the VPC
print(vpc.contains("192.168.1.1"))         # False — a different network entirely
staging = VPC("staging", "10.1.0.0/16")
print(vpc.can_peer_with(staging))          # True  — CIDRs don't overlap → peering OK

Interview Q&A - Q: What does a VPC actually isolate, given it shares physical hardware? The network: private IP space, routing, and reachability. Other tenants on the same hosts cannot route packets into your VPC. Isolation is enforced in the virtualized network layer, not by dedicated wires. - Q: Why does CIDR planning matter so much up front? Two networks with overlapping ranges can never be peered or VPN-connected (a packet for 10.0.1.5 would be ambiguous). Overlap forces a re-addressing project later, so you allocate non-overlapping ranges for prod/staging/on-prem on day one. - Q: How do resources in a VPC reach the internet? Public resources route 0.0.0.0/0 to an internet gateway. Private resources route it to a NAT gateway, which allows outbound connections (e.g. pulling updates) while blocking unsolicited inbound traffic.

A2. Subnets

Definitionsingle availability zonepublicprivatesecurityavailability

Definition. A subnet is a sub-range of a VPC's address space (e.g. 10.0.1.0/24 inside a 10.0.0.0/16 VPC), bound to a single availability zone, into which you place resources. A public subnet has a route to an internet gateway; a private subnet does not (it reaches the internet only outbound, via NAT). Subnets are how you segment a VPC for security (separating tiers) and availability (spreading across zones).

  • Pick it when: you need to separate tiers (web / app / database), pin resources to specific availability zones for high availability, or apply different routing and firewall rules to different groups of resources.
  • Trade-off: sizing is semi-permanent — you fix each subnet's CIDR mask up front, so too small and you exhaust IPs (cloud providers also reserve a handful per subnet), too large and you waste address space and leave no room for other subnets. And because a subnet lives in one AZ, high availability requires duplicating each tier's subnet across multiple AZs.

Real-world example — the classic 3-tier layout. The canonical web architecture maps each tier to its own subnet, replicated across two or three availability zones. A public subnet holds the application load balancer and the NAT gateway; a private app subnet holds the EC2 instances or containers; a private data subnet holds the RDS database. Routing differs by subnet — the public subnet's route table points the default route at the internet gateway, the private subnets point it at the NAT gateway — and security groups lock down traffic between subnets, e.g. the database subnet accepts port 5432 only from the app subnet, never from the internet. Spreading each tier across us-east-1a and us-east-1b means losing an entire availability zone takes out one copy of each tier, not the system. The trade-off shows up operationally: AWS reserves 5 addresses in every subnet, so a /28 yields only 11 usable IPs, and a busy Kubernetes/EKS cluster that assigns an IP per pod can exhaust a subnet, which is exactly why teams size data-plane subnets generously (a /24 or larger) from the start.

class Subnet:
    """A slice of a VPC, bound to one AZ. 'public' = it has a route to the internet."""
    def __init__(self, name, cidr, az, public=False):
        self.name = name
        self.cidr = ipaddress.ip_network(cidr)
        self.az = az
        self.public = public

    def usable_hosts(self):
        # cloud providers reserve a few addresses per subnet (network, gateway, broadcast…)
        return self.cidr.num_addresses - 5         # AWS reserves 5 per subnet

    def route_for(self, dest_ip):
        dest = ipaddress.ip_address(dest_ip)
        if dest in self.cidr:   return "local"               # same subnet → direct
        if self.public:         return "internet-gateway"    # public tier → IGW
        return "nat-gateway"                                 # private tier → outbound only

# slice the VPC from A1 into a public web tier and a private db tier
vpc = VPC("prod", "10.0.0.0/16")
web = vpc.add_subnet(Subnet("web", "10.0.1.0/24", "us-east-1a", public=True))
db  = vpc.add_subnet(Subnet("db",  "10.0.2.0/24", "us-east-1a", public=False))

print(web.usable_hosts())             # 251   (256 addresses − 5 reserved)
print(web.route_for("8.8.8.8"))       # internet-gateway   (public subnet)
print(db.route_for("8.8.8.8"))        # nat-gateway        (private: no inbound from net)
print(db.route_for("10.0.2.40"))      # local              (destination in same subnet)

# the VPC's isolation rule rejects an overlapping subnet:
try:
    vpc.add_subnet(Subnet("dup", "10.0.1.128/25", "us-east-1b"))   # overlaps "web"
except ValueError as e:
    print("rejected:", e)             # rejected: 10.0.1.128/25 overlaps 10.0.1.0/24

Interview Q&A - Q: What actually makes a subnet "public" vs "private"? Its route table, not a checkbox. A public subnet has a route sending 0.0.0.0/0 to an internet gateway (and its instances have public IPs); a private subnet routes that to a NAT gateway or has no internet route at all. - Q: Why is a subnet tied to a single availability zone, and what follows from it? A subnet cannot span AZs, so an AZ failure takes down everything in that subnet. To be highly available you create one subnet per tier per AZ and spread instances across them — which is also why load balancers and databases are configured with subnets in multiple AZs. - Q: How do you control traffic between subnets? Security groups (stateful, instance-level allow rules — e.g. "DB accepts 5432 only from the app security group") and network ACLs (stateless, subnet-level allow/deny). The data tier permits traffic only from the app tier, never from the public internet.

  └───────────────────────────────────────────────────────────┘

  CONWAY'S LAW:
  "Organizations design systems that mirror their own
   communication structure."

  INVERSE CONWAY MANEUVER:
  Structure your teams to match the architecture you WANT.
  Example: If you want microservices, create small autonomous
  teams each owning a bounded context.

  ARCHITECTURE DECISION FACTORS:
  ┌──────────────────┬────────────────────────────────────────┐
  │ < 5 engineers    │ Monolith (maybe modular)               │
  │ 5-20 engineers   │ Modular monolith or 3-5 services       │
  │ 20-100 engineers │ Microservices (domain-aligned teams)   │
  │ 100+ engineers   │ Platform + domain services + cells     │
  └──────────────────┴────────────────────────────────────────┘

2. Domain-Driven Design (DDD)

DDD is a software design approach that focuses on modeling
the core business domain and building architecture around it.
Created by Eric Evans (2003).

═══════════════════════════════════════════════════════════════
STRATEGIC DDD (big-picture)
═══════════════════════════════════════════════════════════════

  BOUNDED CONTEXT:
  ┌────────────────────────────────────────────────────────────┐
  │ A boundary within which a particular domain model applies  │
  │ and terms have specific, consistent meanings.              │
  │                                                            │
  │ Example: "Product" means different things in:              │
  │   Catalog context: name, description, images, categories   │
  │   Inventory context: SKU, quantity, warehouse location     │
  │   Billing context: price, tax rules, discount eligibility  │
  │   Shipping context: weight, dimensions, shipping class     │
  │                                                            │
  │ Each bounded context has its OWN model of "Product"        │
  │ with only the attributes it needs.                         │
  └────────────────────────────────────────────────────────────┘

  UBIQUITOUS LANGUAGE:
  - Shared vocabulary between developers and domain experts
  - Used consistently in code, documentation, and conversation
  - Different bounded contexts may use different languages
  - "Account" in Banking ≠ "Account" in User Management

  CONTEXT MAP (relationships between bounded contexts):
  ┌───────────────────────┬────────────────────────────────────┐
  │ Partnership           │ Two teams cooperate, aligned goals │
  ├───────────────────────┼────────────────────────────────────┤
  │ Shared Kernel         │ Shared model subset (risky, tight) │
  ├───────────────────────┼────────────────────────────────────┤
  │ Customer-Supplier     │ Upstream provides, downstream      │
  │                       │ consumes. Upstream prioritizes     │
  │                       │ downstream needs.                  │
  ├───────────────────────┼────────────────────────────────────┤
  │ Conformist            │ Downstream conforms to upstream    │
  │                       │ model (no negotiation power)       │
  ├───────────────────────┼────────────────────────────────────┤
  │ Anti-Corruption Layer │ Downstream translates upstream     │
  │ (ACL)                 │ model to protect own model.        │
  │                       │ CRITICAL for integrating legacy.   │
  ├───────────────────────┼────────────────────────────────────┤
  │ Open Host Service     │ Upstream provides well-defined API │
  │                       │ for multiple consumers             │
  ├───────────────────────┼────────────────────────────────────┤
  │ Published Language    │ Shared schema (JSON Schema,        │
  │                       │ Protobuf, Avro) for integration    │
  └───────────────────────┴────────────────────────────────────┘

  SUBDOMAINS:
  Core Domain:       What makes your business unique (invest heavily)
  Supporting Domain: Needed but not differentiating (build or buy)
  Generic Domain:    Commodity (buy off the shelf: auth, email)

═══════════════════════════════════════════════════════════════
TACTICAL DDD (code-level patterns)
═══════════════════════════════════════════════════════════════

  ENTITY:
  - Has a unique identity (ID)
  - Identity persists through state changes
  - Example: User, Order, Product
  
  VALUE OBJECT:
  - No identity, defined by its attributes
  - Immutable
  - Example: Money(100, "USD"), Address, DateRange
  
  AGGREGATE:
  - Cluster of entities and value objects treated as a unit
  - Has an AGGREGATE ROOT (entry point)
  - Consistency boundary: transactions within one aggregate
  - Other aggregates referenced by ID only (not object reference)
  - Example: Order (root) → OrderItems, ShippingAddress

  ┌────────────────────────────────────────────────────────────┐
  │ AGGREGATE RULES:                                           │
  │ 1. Reference other aggregates by ID only                   │
  │ 2. One aggregate per transaction                           │
  │ 3. Keep aggregates small (performance + concurrency)       │
  │ 4. Use eventual consistency between aggregates             │
  │ 5. Aggregate root enforces all invariants                  │
  └────────────────────────────────────────────────────────────┘
  
  DOMAIN EVENT:
  - Something that happened in the domain
  - Immutable, past tense: OrderPlaced, PaymentProcessed
  - Used for communication between aggregates and contexts
  
  DOMAIN SERVICE:
  - Business logic that doesn't belong to any entity
  - Stateless
  - Example: PricingService, FraudCheckService
  
  REPOSITORY:
  - Abstraction for persisting and retrieving aggregates
  - One repository per aggregate root
  - Hides storage implementation details
  
  FACTORY:
  - Creates complex aggregates
  - Enforces creation invariants

  EXAMPLE — E-COMMERCE:
  ┌────────────────────────────────────────────────────────────┐
  │ Order Context:                                             │
  │   Aggregate: Order (root)                                  │
  │     ├── OrderItem (entity, local identity)                 │
  │     ├── ShippingAddress (value object)                     │
  │     └── OrderStatus (value object)                         │
  │   Domain Events: OrderPlaced, OrderShipped, OrderCancelled │
  │   Repository: OrderRepository                              │
  │                                                            │
  │ Inventory Context:                                         │
  │   Aggregate: InventoryItem (root)                          │
  │     ├── StockLevel (value object)                          │
  │     └── ReservationList (entity)                           │
  │   Listens to: OrderPlaced → reserve stock                  │
  │   Domain Events: StockReserved, StockDepleted              │
  └────────────────────────────────────────────────────────────┘

3. Hexagonal Architecture

HEXAGONAL ARCHITECTURE (Ports & Adapters)
Created by Alistair Cockburn (2005)

  CORE IDEA: The application core is isolated from external
  concerns (DB, UI, APIs) through PORTS (interfaces) and
  ADAPTERS (implementations).

  ┌──────────────────────────────────────────────────────────────┐
  │                                                              │
  │    ┌──────────┐     ┌──────────────────┐    ┌──────────┐     │
  │    │  REST     │     │                  │    │ PostgreSQL│   │
  │    │  Adapter  ├────→│   PORT           │    │  Adapter  │   │
  │    └──────────┘     │  (Interface)     │    └──────────┘     │
  │                     │       ↓          │                     │
  │    ┌──────────┐     │  ┌──────────┐    │    ┌──────────┐     │
  │    │  GraphQL  │     │  │ DOMAIN   │   │    │  Redis    │    │
  │    │  Adapter  ├────→│  │ LOGIC    │───├───→│  Adapter  │    │
  │    └──────────┘     │  │ (Core)   │   │    └──────────┘      │
  │                     │  └──────────┘    │                     │
  │    ┌──────────┐     │       ↓          │    ┌──────────┐     │
  │    │  CLI      │     │   PORT           │    │  Kafka    │   │
  │    │  Adapter  ├────→│  (Interface)     │    │  Adapter  │   │
  │    └──────────┘     │                  │    └──────────┘     │
  │                      └──────────────────┘                    │
  │  DRIVING (input)          CORE          DRIVEN (output)      │
  │  Adapters                                Adapters            │
  └──────────────────────────────────────────────────────────────┘

  PORTS (Interfaces):
  ┌──────────────────┬───────────────────────────────────────────┐
  │ Driving Ports    │ How the outside world USES the app        │
  │ (Primary/Input)  │ e.g., CreateOrderUseCase,                 │
  │                  │      SearchProductsQuery                  │
  ├──────────────────┼───────────────────────────────────────────┤
  │ Driven Ports     │ What the app NEEDS from the outside       │
  │ (Secondary/Output)│ e.g., OrderRepository,                   │
  │                  │      PaymentGateway, EmailSender          │
  └──────────────────┴───────────────────────────────────────────┘

  ADAPTERS (Implementations):
  ┌──────────────────┬───────────────────────────────────────────┐
  │ Driving Adapters │ REST controller, GraphQL resolver,        │
  │                  │ CLI handler, gRPC service, test           │
  ├──────────────────┼───────────────────────────────────────────┤
  │ Driven Adapters  │ PostgresOrderRepo, StripePayment,         │
  │                  │ SendGridEmail, InMemoryRepo (test)        │
  └──────────────────┴───────────────────────────────────────────┘

  BENEFITS:
  - Domain logic has ZERO dependency on infrastructure
  - Easy to test: swap real adapters with in-memory/mock
  - Easy to change infrastructure (swap DB, message broker)
  - Multiple entry points (REST + CLI + gRPC) share domain

  PROJECT STRUCTURE:
  ┌──────────────────────────────────────────────────────────────┐
  │ src/                                                         │
  │ ├── domain/           ← Entities, Value Objects, Events      │
  │                  │   ├── order.py                            │
  │                  │   └── events.py                           │
  │ ├── ports/            ← Interfaces (ABC)                     │
  │                  │   ├── order_repository.py                 │
  │                  │   └── payment_gateway.py                  │
  │ ├─────── application/      ← Use cases / Application services│
  │                  │   ├── create_order.py                     │
  │                  │   └── cancel_order.py                     │
  │ └── adapters/         ← Infrastructure implementations       │
  │     ├── api/                                                 │
  │                  │   └── rest_controller.py                  │
  │     ├── persistence/                                         │
  │                  │   └── postgres_order_repo.py              │
  │     └── messaging/                                           │
  │         └── kafka_publisher.py                               │
  └──────────────────────────────────────────────────────────────┘

4. Clean Architecture

CLEAN ARCHITECTURE (Robert C. Martin, 2012)
The Dependency Rule: Source code dependencies can only
point INWARD. Nothing in an inner circle can know about
anything in an outer circle.

  ┌─────────────────────────────────────────────────────────────┐
  │                                                             │
  │  ┌─────────────────────────────────────────────────────┐    │
  │  │                                                    │     │
  │  │  ┌─────────────────────────────────────────────┐   │     │
  │  │  │                                            │   │      │
  │  │  │  ┌───────────────────────────────────┐     │   │      │
  │  │  │  │         ENTITIES                  │     │   │      │
  │  │  │  │   (Enterprise Business Rules)     │     │   │      │
  │  │  │  └───────────────────────────────────┘     │   │      │
  │  │  │         USE CASES                          │   │      │
  │  │  │   (Application Business Rules)             │   │      │
  │  │  └─────────────────────────────────────────────┘   │     │
  │  │         INTERFACE ADAPTERS                         │     │
  │  │   (Controllers, Gateways, Presenters)              │     │
  │  └─────────────────────────────────────────────────────┘    │
  │         FRAMEWORKS & DRIVERS                                │
  │   (DB, Web, UI, External Interfaces)                        │
  └─────────────────────────────────────────────────────────────┘

  LAYERS:
  ┌─────────────────┬───────────────────────────────────────────┐
  │ Entities         │ Core business objects, domain logic      │
  │                  │ Least likely to change                   │
  │                  │ No framework dependencies                │
  ├─────────────────┼───────────────────────────────────────────┤
  │ Use Cases        │ Application-specific business rules      │
  │                  │ Orchestrates entity interactions         │
  │                  │ One class per use case                   │
  ├─────────────────┼───────────────────────────────────────────┤
  │ Interface        │ Converts data between use cases and      │
  │ Adapters         │ external format. Controllers, presenters,│
  │                  │ gateways.                                │
  ├─────────────────┼───────────────────────────────────────────┤
  │ Frameworks &     │ Databases, web frameworks, UI            │
  │ Drivers          │ "Glue code" — most volatile              │
  └─────────────────┴───────────────────────────────────────────┘

  CLEAN vs HEXAGONAL vs ONION:
  ┌─────────────────────────────────────────────────────────────┐
  │ All three express the same fundamental idea:                │
  │ "Domain logic at center, infrastructure at edges"           │
  │                                                             │
  │ Clean:     4 concentric circles with explicit layers        │
  │ Hexagonal: Ports & Adapters, emphasis on symmetry           │
  │ Onion:     Similar to Clean, originated independently       │
  │                                                             │
  │ In practice: Pick one and be consistent. The principle      │
  │ matters more than which variant.                            │
  └─────────────────────────────────────────────────────────────┘

5. Event-Driven Architecture

EVENT-DRIVEN ARCHITECTURE (EDA):
Systems communicate through events — immutable records
of something that happened.

  EVENT TYPES:
  ┌──────────────────┬────────────────────────────────────────┐
  │ Domain Event     │ Something happened in the business     │
  │                  │ OrderPlaced, PaymentReceived           │
  │                  │ Fine-grained, domain-specific          │
  ├──────────────────┼────────────────────────────────────────┤
  │ Integration Event│ Communication between bounded contexts │
  │                  │ Coarser-grained, versioned schema      │
  │                  │ May be a projection of domain events   │
  ├──────────────────┼────────────────────────────────────────┤
  │ Notification     │ Minimal data ("something happened")    │
  │                  │ Consumer fetches details if needed     │
  │                  │ Reduces coupling                       │
  ├──────────────────┼────────────────────────────────────────┤
  │ Event-Carried    │ Contains full state needed by consumer │
  │ State Transfer   │ Consumer doesn't need to call back     │
  │                  │ Higher coupling but lower latency      │
  └──────────────────┴────────────────────────────────────────┘

  EDA TOPOLOGIES:
  
  1. BROKER-BASED (Kafka, RabbitMQ):
     Producer → Broker → Consumers
     Decoupled, scalable, replay possible (Kafka)
  
  2. MEDIATOR (Event Bus with routing):
     Events routed based on type/content
     Richer routing logic, more coupling
  
  3. PEER-TO-PEER:
     Direct event exchange between services
     Simplest but doesn't scale

  EVENT CHOREOGRAPHY vs ORCHESTRATION:
  ┌───────────────────────────────────────────────────────────┐
  │ CHOREOGRAPHY:                                             │
  │ OrderService → emits OrderPlaced                          │
  │ InventoryService → listens, reserves stock,               │
  │                    emits StockReserved                    │
  │ PaymentService → listens, charges card,                   │
  │                  emits PaymentProcessed                   │
  │ ShippingService → listens, creates shipment               │
  │                                                           │
  │ Pros: Loose coupling, no SPOF, each service autonomous    │
  │ Cons: Hard to understand flow, debugging is painful,      │
  │       implicit dependencies, no central view              │
  ├───────────────────────────────────────────────────────────┤
  │ ORCHESTRATION:                                            │
  │ OrderSaga:                                                │
  │   1. Call InventoryService.reserve()                      │
  │   2. Call PaymentService.charge()                         │
  │   3. Call ShippingService.createShipment()                │
  │   On failure at step N → compensate steps N-1...1         │
  │                                                           │
  │ Pros: Clear flow, easy to monitor, centralized errors     │
  │ Cons: Orchestrator is SPOF, coupling to orchestrator      │
  └───────────────────────────────────────────────────────────┘

  EVENT SCHEMA EVOLUTION:
  ┌───────────────────────────────────────────────────────────┐
  │ 1. Use a schema registry (Confluent, AWS Glue)            │
  │ 2. Backward compatible: new consumers read old events     │
  │ 3. Forward compatible: old consumers read new events      │
  │ 4. Full compatible: both directions                       │
  │ 5. Version events: OrderPlaced_v1, OrderPlaced_v2         │
  │ 6. Use Avro or Protobuf (schema evolution built-in)       │
  │ 7. NEVER remove required fields, only add optional ones   │
  └───────────────────────────────────────────────────────────┘

6. CQRS + Event Sourcing Deep Dive

═══════════════════════════════════════════════════════════════
CQRS (Command Query Responsibility Segregation)
═══════════════════════════════════════════════════════════════

  Separate WRITE model (commands) from READ model (queries).

  ┌─────────────────────────────────────────────────────────┐
  │                                                         │
  │  Client ──Command──→ ┌──────────────┐                   │
  │                       │ Write Model  │──→ Event Store   │
  │                       │ (normalized) │                  │
  │                      └──────────────┘                  │
  │                              │                          │
  │                         Events ↓                        │
  │                              │                          │
  │                       ┌──────────────┐                  │
  │  Client ←──Query────  │ Read Model   │                  │
  │                       │(denormalized)│                  │
  │                       └──────────────┘                  │
  └─────────────────────────────────────────────────────────┘

  WHEN TO USE CQRS:
  √ Read and write patterns are very different
  √ Read-heavy systems (optimize read model independently)
  √ Complex domain with many aggregate interactions
  √ Different teams own read vs write paths
  √ Need different storage for reads vs writes

  WHEN NOT TO USE:
  × Simple CRUD with same read/write patterns
  × Small team, low complexity
  × Strong consistency required everywhere (read model is eventually consistent)

═══════════════════════════════════════════════════════════════
EVENT SOURCING
═══════════════════════════════════════════════════════════════

  Instead of storing CURRENT STATE, store all STATE CHANGES
  as an immutable sequence of events.

  TRADITIONAL (state-based):
    Account { balance: 500 }

  EVENT-SOURCED:
    1. AccountCreated { amount: 0 }
    2. MoneyDeposited { amount: 1000 }
    3. MoneyWithdrawn { amount: 300 }
    4. MoneyWithdrawn { amount: 200 }
    → Current state: balance = 500

  BENEFITS:
  ┌─────────────────────────────────────────────────────────┐
  │ 1. Complete audit trail (every change is recorded)      │
  │ 2. Time travel: reconstruct state at any point in time  │
  │ 3. Event replay: rebuild read models or fix bugs        │
  │ 4. Debugging: see exactly what happened and when        │
  │ 5. New projections: add new read models retroactively   │
  │ 6. Natural fit with event-driven architecture           │
  └─────────────────────────────────────────────────────────┘

  CHALLENGES:
  ┌─────────────────────────────────────────────────────────┐
  │ 1. Event schema evolution (old events + new format)     │
  │ 2. Snapshots needed for long event streams              │
  │    (can't replay 10M events on every request)           │
  │ 3. Eventual consistency (read model lags behind writes) │
  │ 4. Complexity: harder to understand than CRUD           │
  │ 5. Deleting data (GDPR): "crypto-shredding" pattern     │
  │    (encrypt PII with per-user key, delete key to forget)│
  └─────────────────────────────────────────────────────────┘

  SNAPSHOTS:
    Store periodic snapshots of aggregate state
    Rebuild = load snapshot + replay events after snapshot
    Snapshot every N events (e.g., every 100)

  PROJECTIONS:
    Events → Projection Handler → Read Model (table/view)
    
    Same events can produce multiple projections:
    OrderEvents → OrderListProjection (for UI)
    OrderEvents → OrderAnalyticsProjection (for dashboards)
    OrderEvents → SearchIndexProjection (for Elasticsearch)

  EVENT STORE IMPLEMENTATIONS:
  - EventStoreDB (purpose-built)
  - PostgreSQL (with append-only table + optimistic concurrency)
  - Kafka (event log, but not a true event store)
  - DynamoDB (with version-based concurrency)

  CQRS + EVENT SOURCING TOGETHER:
  ┌─────────────────────────────────────────────────────────┐
  │ Command → Aggregate → Validate → Emit Events →          │
  │ Event Store → Projection → Read Model                   │
  │                                                         │
  │ This is the MOST POWERFUL but MOST COMPLEX combination. │
  │ Only use when the domain truly warrants it:             │
  │ - Financial systems (audit trail + complex rules)       │
  │ - Collaborative editing (conflict resolution)           │
  │ - Complex domains with many state transitions           │
  └─────────────────────────────────────────────────────────┘

7. Microservices Patterns

═══════════════════════════════════════════════════════════════
DECOMPOSITION PATTERNS
═══════════════════════════════════════════════════════════════

  BY BUSINESS CAPABILITY:
  - Align services with what the business does
  - Order Management, Payment Processing, Shipping
  - Each service owns its business function end-to-end

  BY SUBDOMAIN (DDD):
  - Align services with DDD bounded contexts
  - Each service = one bounded context
  - Communication via domain events or APIs

  BY USE CASE / USER JOURNEY:
  - Optimize for user-facing flows
  - "Checkout Service" handles the entire checkout flow
  - Risk: services become mini-monoliths

═══════════════════════════════════════════════════════════════
COMMUNICATION PATTERNS
═══════════════════════════════════════════════════════════════

  ┌──────────────────┬───────────────────────────────────────┐
  │ Synchronous      │ REST, gRPC                            │
  │                  │ Simple, immediate response            │
  │                  │ Risk: temporal coupling, cascading    │
  │                  │ failure if downstream is slow/down    │
  ├──────────────────┼───────────────────────────────────────┤
  │ Asynchronous     │ Message queues, event streams         │
  │                  │ Decoupled, resilient, scalable        │
  │                  │ Complexity: eventual consistency,     │
  │                  │ message ordering, debugging           │
  ├──────────────────┼───────────────────────────────────────┤
  │ Request-Reply    │ Async request via queue, response     │
  │ (async)          │ via correlation ID on reply queue     │
  │                  │ Best of both: decoupled + gets answer │
  └──────────────────┴───────────────────────────────────────┘

═══════════════════════════════════════════════════════════════
DATA PATTERNS
═══════════════════════════════════════════════════════════════

  DATABASE PER SERVICE:
  - Each service owns its data store
  - No direct DB access across services
  - Communication only via APIs or events
  - Enables independent scaling and tech choices

  SAGA PATTERN (distributed transactions):
  See Section 5 for choreography vs orchestration details.

  API COMPOSITION:
  - API Gateway or BFF composes responses from multiple services
  - Handles the "join" that can't happen at DB level
  - Risk: latency (sequential calls), partial failures

  TRANSACTIONAL OUTBOX:
  ┌──────────────────────────────────────────────────────────┐
  │ Problem: Write to DB AND publish event atomically        │
  │ Solution:                                                │
  │   1. Write business data + event to outbox table         │
  │      in SAME transaction                                 │
  │   2. Separate process (CDC or poller) reads outbox       │
  │   3. Publishes event to message broker                   │
  │   4. Marks outbox entry as published                     │
  │                                                          │
  │ CDC approach: Debezium reads DB WAL → Kafka              │
  │ Polling approach: Periodic query on outbox table         │
  └──────────────────────────────────────────────────────────┘

═══════════════════════════════════════════════════════════════
RESILIENCE PATTERNS
═══════════════════════════════════════════════════════════════

  CIRCUIT BREAKER:
  Closed → Open (after N failures) → Half-Open (test)
  Prevents cascading failures. (Resilience4j, Polly)

  BULKHEAD:
  Isolate failure domains with separate thread pools/resources
  Service A's pool exhaustion doesn't affect Service B
  Like watertight compartments in a ship

  RETRY WITH BACKOFF:
  Exponential backoff + jitter
  Retry budget: max 10% of requests should be retries
  Distinguish retryable (503, timeout) from non-retryable (400, 404)

  TIMEOUT:
  Every inter-service call MUST have a timeout
  Cascade: set timeout < caller's timeout
  Aggressive timeouts + circuit breaker = fast failure

  LOAD SHEDDING:
  When overloaded, reject low-priority requests
  Return 503 with Retry-After header
  Prioritize: health checks > critical paths > best-effort

  RATE LIMITING:
  Per-client, per-service, per-endpoint limits
  Token bucket for burst tolerance
  Distributed: Redis or local + gossip sync

8. Monolith Decomposition

STRANGLER FIG PATTERN:
  Gradually replace monolith functionality with microservices.

  ┌─────────────────────────────────────────────────────────┐
  │ Phase 1: Route all traffic through API Gateway/Proxy    │
  │                                                         │
  │ Phase 2: Extract ONE bounded context to new service     │
  │          Route its traffic to new service               │
  │          Keep everything else in monolith               │
  │                                                         │
  │ Phase 3: Repeat for next bounded context                │
  │                                                         │
  │ Phase 4: Eventually monolith is empty → decommission    │
  │                                                         │
  │ CRITICAL RULES:                                         │
  │ 1. Never rewrite from scratch (Joel Spolsky's warning)  │
  │ 2. Extract one service at a time                        │
  │ 3. Maintain backward compatibility at every step        │
  │ 4. Run old + new in parallel, validate correctness      │
  │ 5. Data migration is the hardest part — plan carefully  │
  └─────────────────────────────────────────────────────────┘

  BRANCH BY ABSTRACTION:
  1. Create abstraction (interface) for the component to extract
  2. Refactor monolith to use the abstraction
  3. Create new implementation (microservice)
  4. Switch abstraction to use new implementation
  5. Remove old implementation

  PARALLEL RUN:
  - Route traffic to BOTH old and new
  - Compare results (shadow/dark traffic)
  - Alert on divergences
  - Switch over when confident

  DATA DECOMPOSITION STRATEGIES:
  ┌──────────────────┬──────────────────────────────────────┐
  │ Shared DB        │ Start here. Multiple services share  │
  │ (temporary)      │ one DB. Allows gradual decomposition.│
  ├──────────────────┼──────────────────────────────────────┤
  │ DB View          │ New service gets a read-only view    │
  │                  │ of the monolith's DB tables.         │
  ├──────────────────┼──────────────────────────────────────┤
  │ CDC Sync         │ Capture changes from monolith DB,    │
  │                  │ replicate to service's own DB.       │
  ├──────────────────┼──────────────────────────────────────┤
  │ Own DB           │ Final state. Service owns its data.  │
  │                  │ Sync via events, not DB access.      │
  └──────────────────┴──────────────────────────────────────┘

9. Cell-Based Architecture

CELL-BASED ARCHITECTURE:
Divide the system into independent, self-contained cells
that each serve a subset of users or traffic.

  ┌──────────────────────────────────────────────────────────┐
  │                                                          │
  │  Cell Router (routes by user_id / region / tenant)       │
  │       │                │                │                │
  │       ↓                ↓                ↓                │
  │  ┌─────────┐    ┌─────────┐    ┌─────────┐               │
  │  │ Cell A  │    │ Cell B  │    │ Cell C  │               │
  │  │ Users   │    │ Users   │    │ Users   │               │
  │  │ 1-1M    │    │ 1M-2M   │    │ 2M-3M   │               │
  │  │         │    │         │    │         │               │
  │  │ [API]   │    │ [API]   │    │ [API]   │               │
  │  │ [DB]    │    │ [DB]    │    │ [DB]    │               │
  │  │ [Cache] │    │ [Cache] │    │ [Cache] │               │
  │  │ [Queue] │    │ [Queue] │    │ [Queue] │               │
  │  └─────────┘    └─────────┘    └─────────┘               │
  │                                                          │
  │  Each cell is a complete, independent deployment         │
  │  Failure in Cell A does NOT affect Cell B or C           │
  └──────────────────────────────────────────────────────────┘

  WHY CELLS:
  - Blast radius containment (failure isolated to one cell)
  - Independent deployment and scaling per cell
  - Gradual rollout (deploy to one cell first)
  - Multi-tenancy isolation
  - Compliance (data residency per region)

  USED BY:
  - AWS (availability zones are essentially cells)
  - Slack (per-workspace cells)
  - Salesforce (per-tenant cells)
  - Microsoft Teams (per-ring deployment)

  ROUTING STRATEGIES:
  - Hash-based: hash(user_id) % num_cells
  - Range-based: user_id ranges per cell
  - Attribute-based: by region, tier, or tenant
  - Weighted: shift traffic for canary deployment

  CROSS-CELL COMMUNICATION:
  - Avoid when possible (cell independence is the goal)
  - When needed: async events via global message bus
  - Shared services: global user directory, billing
  - Minimize: keep the cross-cell surface area small

10. Modular Monolith

MODULAR MONOLITH:
A single deployable unit organized into well-defined modules
with clear boundaries — the best of monolith simplicity
and microservices modularity.

  ┌───────────────────────────────────────────────────────────┐
  │                    Single Deployment                      │
  │                                                           │
  │  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐   │
  │  │ Orders   │  │ Payments │  │ Shipping │  │ Catalog  │   │
  │  │ Module   │  │ Module   │  │ Module   │  │ Module   │   │
  │  │          │  │          │  │          │  │          │   │
  │  │ API      │  │ API      │  │ API      │  │ API      │   │
  │  │ Domain   │  │ Domain   │  │ Domain   │  │ Domain   │   │
  │  │ DB Schema│  │ DB Schema│  │ DB Schema│  │ DB Schema│   │
  │  └────┬─────┘  └────┬─────┘  └────┬─────┘  └────┬─────┘   │
  │       └──────events──┴────────────┴────────────┘          │

  └───────────────────────────────────────────────────────────┘

  RULES:
  1. Each module has its own DB schema (no cross-module tables)

  │ Operational cost    │ Low          │ High (K8s, mesh...)  │
  │ Team independence   │ Medium       │ High                 │
  │ Scale independently │ No           │ Yes                  │
  │ Technology choice   │ Same stack   │ Polyglot possible    │
  │ Best for team size  │ 5-30         │ 20-200+              │
  └─────────────────────┴──────────────┴──────────────────────┘

  ARCHITECT RECOMMENDATION:
  ┌───────────────────────────────────────────────────────────┐
  │ Start with a modular monolith.                            │
  │ Extract to microservices ONLY when you have evidence:     │
  │   - Independent scaling needed                            │
  │   - Different deployment frequencies                      │
  │   - Team ownership boundaries are clear                   │
  │   - Operational maturity to manage distributed systems    │

16. Architecture Anti-Patterns

ANTI-PATTERNS TO AVOID:

  1. DISTRIBUTED MONOLITH:
     Microservices that are tightly coupled.
     Deploying one requires deploying others.
     → "All the complexity of microservices with none of the benefits"
     Fix: Enforce service autonomy, async communication,
          database per service.

  2. NANO-SERVICES:
     Too many tiny services (each is a few endpoints).
     Operational overhead exceeds benefits.
     Fix: Merge related nano-services, use modular monolith.

  3. SHARED DATABASE:
     Multiple services directly accessing the same tables.
     Any schema change breaks multiple services.
     Fix: Database per service, APIs for data access.

  4. CHATTY SERVICES:
     Service A makes 50 calls to Service B per request.
     Network overhead, latency, fragility.
     Fix: Batch APIs, data denormalization, BFF pattern.

  5. GOLDEN HAMMER:
     Using the same technology/pattern for everything.
     "When all you have is a hammer..."
     Fix: Choose technology based on specific requirements.

  6. RESUME-DRIVEN DEVELOPMENT:
     Choosing technologies to pad resumes, not solve problems.
     Fix: Make decisions based on team capabilities and
          actual requirements.

  7. ACCIDENTAL COMPLEXITY:
     System is complex because of poor design, not because
     the problem is inherently complex.
     Fix: Simplify. YAGNI. Remove unnecessary abstractions.

  8. BIG BALL OF MUD:
     No discernible architecture. Everything is coupled.
     Fix: Incremental refactoring, strangler fig pattern,
          establish module boundaries.

  9. PREMATURE OPTIMIZATION:
     Building for 10M users when you have 100.
     Fix: Design for current needs + 10×. Redesign at 100×.

  10. CARGO CULT ARCHITECTURE:
      Copying Netflix/Google architecture without their
      scale, team size, or problems.
      Fix: Understand WHY they made those choices.
      Most companies are NOT Netflix.

18. Interview Deep Dive

CatalogOrderingPaymentShippingCustomerStep 1

Q1: Explain DDD and how you'd apply it to an e-commerce platform.

A: DDD is about modeling software around the business domain. For e-commerce, I'd identify bounded contexts: Catalog (product information, categories, search), Ordering (cart, checkout, order lifecycle), Payment (transactions, refunds), Shipping (fulfillment, tracking), Customer (profiles, preferences). Each context has its own model — "Product" in Catalog has description/images, while in Ordering it's just product_id/price/quantity. Communication between contexts via domain events (OrderPlaced → Payment processes → PaymentConfirmed → Shipping creates fulfillment). Each context maps to a team (inverse Conway). Aggregates: Order is an aggregate root with OrderItems; invariant — order total must equal sum of items. Reference Payment by order_id, not object reference.

Q2: When would you choose a modular monolith over microservices?

A: Modular monolith when: (1) Team is < 20 engineers — the operational overhead of microservices (K8s, service mesh, distributed tracing, saga patterns) isn't justified. (2) Domain boundaries aren't clear yet — extract to services only when you have evidence of differing scale/deployment needs. (3) Strong consistency is important — in-process calls + ACID transactions are simpler than sagas. (4) You value debugging simplicity — stack traces vs distributed traces. I'd structure modules with strict boundaries: each module has its own DB schema, communicates via in-process events or public interfaces, no direct access to another module's internals. This gives 80% of microservice benefits with 20% of the complexity. When a module genuinely needs independent scaling or deployment, extract it.

Q3: Explain the Strangler Fig pattern. How do you handle data migration?

A: Strangler Fig incrementally replaces monolith functionality. Step 1: Place an API gateway/proxy in front of the monolith. Step 2: Identify the bounded context to extract (start with the least coupled). Step 3: Build the new service, route traffic for those endpoints to it. Step 4: Repeat for next context. Data migration is the hardest part. My approach: (1) Start with shared DB — new service reads from monolith's DB via views. (2) Implement CDC (Debezium) to replicate relevant tables to the service's own DB. (3) Switch the service to its own DB + CDC sync. (4) Once validated, have the monolith send writes to the new service's API. (5) Remove CDC, monolith no longer owns that data. Throughout: run parallel reads comparing both sources, alert on divergence. Never do a big-bang migration.

Q4: What is event sourcing? When is it appropriate and inappropriate?

A: Event sourcing stores all state changes as immutable events rather than current state. Appropriate: (1) Financial systems — need complete audit trail (every balance change). (2) Collaborative editing — need to merge concurrent changes. (3) Complex domains with many state transitions — replay to rebuild projections. (4) Systems requiring temporal queries — "what was the state on March 15?". Inappropriate: (1) Simple CRUD — massive over-engineering for a basic web app. (2) When you need immediate consistency on reads — projections are eventually consistent. (3) When GDPR "right to delete" is critical — need crypto-shredding (encrypt PII with per-user key, delete key to "forget"). (4) When team lacks experience — event sourcing has a steep learning curve. Always combine with CQRS: write to event store, project to optimized read models.

Q5: Compare event-driven choreography and orchestration. Which do you prefer?

A: Choreography: Services react to events independently. OrderService emits OrderPlaced → InventoryService reacts → PaymentService reacts. Pros: loose coupling, no SPOF, autonomous teams. Cons: implicit flow (no central visibility), hard to debug, difficult error handling, potential circular dependencies. Orchestration: Central coordinator (saga orchestrator) directs steps explicitly. Pros: clear flow, centralized monitoring, simpler compensation logic. Cons: orchestrator is a coupling point and potential SPOF. My preference: Orchestration for complex business processes (>3 steps, compensation needed) using Temporal or Step Functions — gives durability, visibility, and retry semantics. Choreography for simple event propagation (notifications, analytics, cache invalidation) where order doesn't matter and failure is tolerable.

Q6: How do you evaluate and document architecture decisions?

A: I use ADRs (Architecture Decision Records) stored in version control alongside code. Format: Context → Decision → Alternatives → Consequences. Key practices: (1) Include a "review date" — revisit decisions when conditions change. (2) Number sequentially and never edit old ADRs — write new ones that supersede. (3) Link related ADRs. For evaluation, I use a weighted decision matrix: list criteria (scalability, team expertise, cost, time-to-market, operational complexity), assign weights based on priorities, score each option 1-5, multiply by weight, compare totals. But the matrix is a conversation tool, not the final answer — architectural intuition matters. I also use fitness functions (automated tests) to verify architecture characteristics are maintained over time.

Q7: What is a cell-based architecture? When would you use it?

A: Cell-based architecture divides the entire stack into independent, self-contained cells, each serving a subset of users. Each cell has its own compute, storage, cache, and queue — a complete mini-deployment. A cell router directs traffic based on user ID, region, or tenant. Benefits: (1) Blast radius — failure in one cell doesn't affect others. (2) Independent deployment — canary one cell at a time. (3) Compliance — data residency per region. (4) Scale — add cells to grow. When to use: Multi-tenant SaaS at scale, multi-region deployments, when blast radius containment is a top priority, when you need deployment confidence (progressive rollout). Trade-offs: Higher infrastructure cost (duplicated per cell), complexity in cross-cell operations, cell routing adds a layer. Used by: AWS (AZs), Slack (workspaces), Salesforce (orgs). I'd consider it when serving 10M+ users or 100+ enterprise tenants.
