Security & Cloud Architecture — Production-Grade Patterns

Scope: Authentication/authorization (OAuth2, OIDC, JWT), Zero Trust architecture, API security, encryption, secrets management, cloud-native patterns, serverless, multi-cloud, Infrastructure as Code. What architects must know for secure, cloud-ready systems.

•

Key Definitions (read first)

AuthN vs AuthZOAuth 2.0OIDCJWTSSO / SAMLMFA
TermPlain-language definition
AuthN vs AuthZAuthentication = "who are you?"; Authorization = "what may you do?"
OAuth 2.0Delegated authorization — grant an app limited access without sharing your password.
OIDCOpenID Connect — an authentication layer on top of OAuth 2.0 (adds the ID token).
JWTSigned, self-contained token carrying claims; verified without a DB lookup.
SSO / SAMLOne login across many apps / the XML federation standard often behind enterprise SSO.
MFAMulti-factor auth — something you know + have + are.
Zero Trust"Never trust, always verify" — authenticate/authorize every request, no implicit network trust.
RBAC vs ABACPermissions by role vs by attributes/policy (user, resource, context).
Encryption in transit vs at restTLS on the wire vs encrypted storage (KMS-managed keys).
mTLSMutual TLS — both client and server present certificates (service-to-service trust).
Secrets managementCentral, audited store for keys/passwords (Vault, KMS) — never in code.
WAF / API gatewayFilters malicious traffic / central policy + auth + rate-limit entry point.
Serverless (FaaS)Run functions on demand; no servers to manage, pay per invocation.
IaCInfrastructure as Code — provision infra declaratively (Terraform), versioned & repeatable.

1. Authentication & Authorization

AUTHENTICATION (AuthN): "Who are you?"
AUTHORIZATION (AuthZ):  "What can you do?"

  ┌──────────────────────────────────────────────────────────┐
  │                    IDENTITY STACK                        │
  │                                                          │
  │  Layer 4: SSO / Federation  (SAML, OIDC, social login)  │
  │  Layer 3: Token Management  (JWT, sessions, refresh)    │
  │  Layer 2: Authentication    (password, MFA, biometric)  │
  │  Layer 1: Identity Store    (LDAP, DB, IdP)             │
  └──────────────────────────────────────────────────────────┘

  AUTHENTICATION METHODS:
  ┌──────────────────────────────────────────────────────────┐
  │ Password-based: Hash (bcrypt/argon2) + salt              │
  │ MFA/2FA:        TOTP, SMS, push notification, hardware  │
  │                  keys (WebAuthn/FIDO2)                   │
  │ Passwordless:   Magic links, biometric, passkeys        │
  │ Certificate:    mTLS (mutual TLS) for service-to-service│
  │ API Keys:       For machine-to-machine (not users!)     │
  │ SSO:            SAML 2.0 (enterprise), OIDC (modern)    │
  └──────────────────────────────────────────────────────────┘

  AUTHORIZATION MODELS:
  ┌──────────────────────────────────────────────────────────┐
  │ RBAC: Role-Based Access Control                          │
  │   User → Role → Permissions                              │
  │   Simple, well-understood, most common                   │
  │   Limitation: role explosion in complex systems          │
  │                                                          │
  │ ABAC: Attribute-Based Access Control                     │
  │   Policy evaluates attributes: user, resource, env       │
  │   "Managers in finance dept can view Q3 reports          │
  │    during business hours from corporate network"         │
  │   Fine-grained but complex to manage                    │
  │                                                          │
  │ ReBAC: Relationship-Based Access Control                 │
  │   Based on relationships between entities                │
  │   "Can view if owner OR member of owning org"            │
  │   Used by: Google Zanzibar (Google Docs sharing model)  │
  │   Tools: SpiceDB, Ory Keto, AuthZed                     │
  │                                                          │
  │ Policy-as-Code: OPA (Open Policy Agent)                  │
  │   Rego language for policy definition                    │
  │   Decoupled from application logic                      │
  │   Unified policy across services, K8s, APIs             │
  └──────────────────────────────────────────────────────────┘

  GOOGLE ZANZIBAR (ReBAC at scale):
  ┌──────────────────────────────────────────────────────────┐
  │ Problem: Authorization for Google Docs, Drive, YouTube   │
  │ Scale: Millions of authorization checks per second       │
  │                                                          │
  │ Model:                                                   │
  │   Relationships stored as tuples:                        │
  │   (object, relation, user)                               │
  │   "doc:readme#viewer@user:alice"                         │
  │                                                          │
  │ Features:                                                │
  │   - Relationship expansion (viewer ← member ← admin)    │
  │   - Consistent check (new zookie = consistency token)    │
  │   - Global scale with Spanner backend                   │
  │   - < 10ms P99 for Check API                            │
  └──────────────────────────────────────────────────────────┘

2. OAuth 2.0 & OpenID Connect Deep Dive

OAUTH 2.0: Authorization framework (delegates access)
OIDC: Authentication layer ON TOP of OAuth 2.0

  OAUTH 2.0 GRANT TYPES:
  ┌──────────────────────────────────────────────────────────┐
  │ 1. AUTHORIZATION CODE (most common, most secure)        │
  │    For: Server-side web apps                             │
  │    Flow:                                                 │
  │    User → App → Redirect to AuthZ Server →               │
  │    User authenticates → Redirect back with code →        │
  │    App exchanges code for tokens (server-side) →         │
  │    App uses access token for API calls                   │
  │                                                          │
  │ 2. AUTHORIZATION CODE + PKCE                             │
  │    For: SPAs, mobile apps (public clients)               │
  │    Like auth code but with proof key:                    │
  │    code_verifier (random) → code_challenge (SHA256)      │
  │    Prevents code interception attacks                    │
  │                                                          │
  │ 3. CLIENT CREDENTIALS                                    │
  │    For: Machine-to-machine (no user involved)            │
  │    App sends client_id + client_secret → gets token      │
  │                                                          │
  │ 4. DEVICE CODE                                           │
  │    For: Smart TVs, CLI tools (no browser)                │
  │    Device shows code → User enters on another device     │
  │    Device polls for token                                │
  │                                                          │
  │ ❌ DEPRECATED:                                            │
  │    Implicit grant (token in URL — security risk)          │
  │    Resource owner password (shares password with app)    │
  └──────────────────────────────────────────────────────────┘

  AUTHORIZATION CODE FLOW (step by step):
  ┌──────────────────────────────────────────────────────────┐
  │ Browser        App Server       Auth Server    Resource  │
  │    │               │                │             │      │
  │    │──── GET /login ──►│            │             │      │
  │    │◄── 302 redirect ──│            │             │      │
  │    │────────────── /authorize ──────►│            │      │
  │    │               │   (+ scope, state, redirect_uri)    │
  │    │◄──── Login page ──────────────│             │      │
  │    │──── credentials ──────────────►│            │      │
  │    │◄── 302 + auth_code ───────────│             │      │
  │    │── GET /callback?code=xxx ─►│               │      │
  │    │               │── POST /token ─►│           │      │
  │    │               │  (code + client_secret)     │      │
  │    │               │◄─ access_token ─│           │      │
  │    │               │── GET /api ──────────────────►│    │
  │    │               │  (Bearer token)              │      │
  │    │               │◄─ data ─────────────────────│      │
  │    │◄── response ──│               │             │      │
  └──────────────────────────────────────────────────────────┘

  TOKENS:
  ┌──────────────────────────────────────────────────────────┐
  │ Access Token:  Short-lived (5-60 min). Used for API calls│
  │ Refresh Token: Long-lived. Used to get new access tokens │
  │ ID Token:      OIDC only. Contains user identity claims  │
  │                (sub, email, name, etc.)                   │
  │                                                          │
  │ Token storage:                                           │
  │   Server-side: HTTP-only secure cookies (best for web)   │
  │   Mobile: Secure enclave / keychain                      │
  │   NEVER: localStorage (XSS vulnerable)                   │
  │                                                          │
  │ Token rotation:                                          │
  │   Refresh token rotation: new refresh token on each use  │
  │   Detect reuse → revoke all tokens for that session     │
  └──────────────────────────────────────────────────────────┘

3. JWT Deep Dive

JWT (JSON Web Token): Compact, URL-safe token format

  STRUCTURE:
  ┌──────────────────────────────────────────────────────────┐
  │ header.payload.signature                                 │
  │                                                          │
  │ Header: {"alg": "RS256", "typ": "JWT", "kid": "key-1"} │
  │ Payload: {"sub": "user123", "role": "admin",            │
  │           "iat": 1700000000, "exp": 1700003600}         │
  │ Signature: RS256(base64(header) + "." + base64(payload),│
  │            privateKey)                                    │
  │                                                          │
  │ All three parts are Base64url encoded                    │
  └──────────────────────────────────────────────────────────┘

  ALGORITHMS:
  ┌──────────────────────────────────────────────────────────┐
  │ HS256: HMAC-SHA256 (symmetric — same key sign & verify) │
  │   Pro: Simple. Con: Shared secret must be distributed.  │
  │                                                          │
  │ RS256: RSA-SHA256 (asymmetric — private sign, public     │
  │   verify). Best for distributed systems. Auth server     │
  │   signs, any service verifies with public key.          │
  │                                                          │
  │ ES256: ECDSA-SHA256 (asymmetric, smaller keys).         │
  │   Preferred for mobile/constrained environments.        │
  │                                                          │
  │ ❌ NEVER set alg: "none" — disables verification!        │
  └──────────────────────────────────────────────────────────┘

  JWT BEST PRACTICES:
  ┌──────────────────────────────────────────────────────────┐
  │ ✅ Always validate: signature, exp, iss, aud             │
  │ ✅ Use asymmetric keys (RS256/ES256) for distributed sys │
  │ ✅ Keep tokens short-lived (5-15 min)                    │
  │ ✅ Use kid (Key ID) header for key rotation              │
  │ ✅ Publish public keys via JWKS endpoint                 │
  │                                                          │
  │ ❌ Don't store sensitive data in payload (it's base64,   │
  │    not encrypted — anyone can decode it)                  │
  │ ❌ Don't use JWT for sessions (can't revoke easily)      │
  │ ❌ Don't put JWT in URL (logged, cached, leaked)         │
  │ ❌ Don't skip audience (aud) validation                  │
  └──────────────────────────────────────────────────────────┘

  JWT vs OPAQUE TOKENS:
  ┌──────────────────────────────────────────────────────────┐
  │              JWT               │    Opaque Token         │
  │ ─────────────────────────────  │  ──────────────────── │
  │ Self-contained (no DB lookup)  │  Requires DB lookup    │
  │ Can't revoke before expiry     │  Instantly revocable   │
  │ Larger size (~800 bytes)       │  Small (~32 bytes)     │
  │ Good for microservices         │  Good for monoliths    │
  │ Stateless verification         │  Stateful verification │
  └──────────────────────────────────────────────────────────┘

  JWT REVOCATION STRATEGIES (when you must revoke):
  ┌──────────────────────────────────────────────────────────┐
  │ 1. Short TTL: 5-minute tokens, frequent refresh          │
  │ 2. Token blacklist: Store revoked JTIs in Redis          │
  │    (check on every request — defeats stateless benefit)  │
  │ 3. Token versioning: User has token_version in DB.       │
  │    JWT contains version. On revoke, increment version.  │
  │    Check version match on critical operations only.     │
  │ 4. Event-driven: Publish revocation event, services      │
  │    maintain local blacklist with TTL auto-cleanup.      │
  └──────────────────────────────────────────────────────────┘

4. Zero Trust Architecture

PRINCIPLE: "Never trust, always verify"
  Traditional: Castle-and-moat (trust inside network)
  Zero Trust: Verify every request regardless of source

  ┌──────────────────────────────────────────────────────────┐
  │                 ZERO TRUST PILLARS                       │
  │                                                          │
  │  1. VERIFY EXPLICITLY                                    │
  │     Authenticate and authorize every request             │
  │     Based on: identity, device, location, behavior      │
  │                                                          │
  │  2. LEAST PRIVILEGE ACCESS                               │
  │     Just-in-time (JIT) and just-enough-access (JEA)     │
  │     Time-bound access grants                            │
  │     Default deny — explicit allow                       │
  │                                                          │
  │  3. ASSUME BREACH                                        │
  │     Minimize blast radius with segmentation             │
  │     Encrypt all traffic (even internal)                  │
  │     Continuous monitoring and anomaly detection          │
  └──────────────────────────────────────────────────────────┘

  ZERO TRUST IN MICROSERVICES:
  ┌──────────────────────────────────────────────────────────┐
  │                                                          │
  │  Service A ──── mTLS ────► Service B                     │
  │     │                         │                          │
  │     ├── SPIFFE identity       ├── SPIFFE identity        │
  │     ├── JWT with claims       ├── Policy enforcement     │
  │     ├── Request-level authz   ├── OPA sidecar            │
  │     └── Audit logging         └── Audit logging          │
  │                                                          │
  │  SPIFFE (Secure Production Identity Framework):          │
  │    Standard for service identity                         │
  │    SPIFFE ID: spiffe://trust-domain/path                 │
  │    SVID: X.509 certificate or JWT proving identity       │
  │    SPIRE: Reference implementation                       │
  │                                                          │
  │  Service Mesh (Istio/Linkerd):                           │
  │    Automatic mTLS between all services                   │
  │    Authorization policies (who can call whom)            │
  │    Traffic encryption transparent to application         │
  └──────────────────────────────────────────────────────────┘

  BeyondCorp (Google's Zero Trust):
  ┌──────────────────────────────────────────────────────────┐
  │ No VPN required for internal applications                │
  │ Every request evaluated by Access Proxy:                 │
  │   - User identity (who)                                  │
  │   - Device trust level (what device, patched, managed?)  │
  │   - Request context (where from, when)                   │
  │   - Resource sensitivity                                 │
  │ Result: same security model internal and external        │
  └──────────────────────────────────────────────────────────┘

5. API Security

API SECURITY LAYERS:
  ┌──────────────────────────────────────────────────────────┐
  │ Layer 1: Transport (TLS 1.3)                             │
  │ Layer 2: Authentication (OAuth, API keys, mTLS)          │
  │ Layer 3: Authorization (RBAC, ABAC, OPA)                 │
  │ Layer 4: Input Validation (schema, sanitization)         │
  │ Layer 5: Rate Limiting (per user, per endpoint)          │
  │ Layer 6: Logging & Monitoring                            │
  └──────────────────────────────────────────────────────────┘

  OWASP API SECURITY TOP 10 (2023):
  ┌──────────────────────────────────────────────────────────┐
  │ 1. Broken Object Level Authorization (BOLA)              │
  │    GET /api/users/123/orders → change to 124 → BREACH   │
  │    Fix: Always check ownership. Never trust URL params.  │
  │                                                          │
  │ 2. Broken Authentication                                 │
  │    Weak password, no MFA, token leakage                  │
  │    Fix: Strong auth, short tokens, rotate secrets        │
  │                                                          │
  │ 3. Broken Object Property Level Authorization            │
  │    API returns more fields than user should see           │
  │    Fix: Response filtering based on user role            │
  │                                                          │
  │ 4. Unrestricted Resource Consumption                     │
  │    No rate limiting → DoS, cost explosion                │
  │    Fix: Rate limit, pagination, max payload size         │
  │                                                          │
  │ 5. Broken Function Level Authorization                   │
  │    Regular user accesses admin endpoints                  │
  │    Fix: Role-based endpoint access control               │
  │                                                          │
  │ 6. Unrestricted Access to Sensitive Flows                │
  │    Automated abuse of business logic                     │
  │    Fix: CAPTCHA, bot detection, business logic limits    │
  │                                                          │
  │ 7. Server Side Request Forgery (SSRF)                    │
  │    API fetches user-supplied URLs → access internal nets  │
  │    Fix: Allowlist URLs, block internal IPs               │
  │                                                          │
  │ 8. Security Misconfiguration                             │
  │    Debug enabled, default creds, verbose errors          │
  │    Fix: Hardening checklist, automated scanning          │
  │                                                          │
  │ 9. Improper Inventory Management                         │
  │    Old API versions still running, shadow APIs           │
  │    Fix: API gateway, version management, API catalog     │
  │                                                          │
  │ 10. Unsafe Consumption of APIs                           │
  │    Trusting third-party API responses without validation │
  │    Fix: Validate ALL external data                       │
  └──────────────────────────────────────────────────────────┘

  RATE LIMITING PATTERNS:
  ┌──────────────────────────────────────────────────────────┐
  │ Fixed Window:     100 req/min per user                   │
  │   Simple but allows burst at window boundary            │
  │                                                          │
  │ Sliding Window:   Weighted average of current + previous │
  │   Smoother distribution                                  │
  │                                                          │
  │ Token Bucket:     Tokens added at fixed rate, consumed   │
  │   per request. Allows controlled bursts.                │
  │   Used by: AWS API Gateway, Stripe                      │
  │                                                          │
  │ Leaky Bucket:     Requests queued, processed at fixed    │
  │   rate. Smooths traffic. Drops when queue full.         │
  │                                                          │
  │ Distributed rate limiting:                               │
  │   Redis + Lua script (atomic increment + expire)        │
  │   Or: centralized rate limiter service                   │
  │   Headers: X-RateLimit-Limit, X-RateLimit-Remaining     │
  └──────────────────────────────────────────────────────────┘

6. Encryption & Data Protection

ENCRYPTION AT REST:
  ┌──────────────────────────────────────────────────────────┐
  │ Level 1: Full-disk encryption (BitLocker, LUKS)          │
  │   OS-level, transparent to applications                  │
  │   Protects against: physical theft                      │
  │                                                          │
  │ Level 2: Database-level encryption (TDE)                 │
  │   DB encrypts data files automatically                   │
  │   Protects against: file-level access                   │
  │                                                          │
  │ Level 3: Application-level encryption (field-level)      │
  │   Encrypt specific fields (SSN, credit card)             │
  │   Protects against: DB admin access, SQL injection      │
  │   Most secure but adds complexity                       │
  │                                                          │
  │ Envelope Encryption:                                     │
  │   Data encrypted with DEK (data encryption key)         │
  │   DEK encrypted with KEK (key encryption key) from KMS  │
  │   Only encrypted DEK stored alongside data              │
  │   Used by: AWS KMS, Google Cloud KMS, Azure Key Vault   │
  └──────────────────────────────────────────────────────────┘

  ENCRYPTION IN TRANSIT:
  ┌──────────────────────────────────────────────────────────┐
  │ TLS 1.3 (minimum standard):                              │
  │   Faster handshake (1-RTT, 0-RTT for resumption)        │
  │   Removed weak ciphers (RC4, 3DES, SHA-1)               │
  │   Perfect forward secrecy mandatory                      │
  │                                                          │
  │ mTLS (mutual TLS):                                       │
  │   Both client AND server present certificates            │
  │   Standard for service-to-service communication         │
  │   Service mesh automates certificate management          │
  │                                                          │
  │ Certificate Management:                                  │
  │   Let's Encrypt: Free, automated certificates            │
  │   cert-manager (K8s): Automated cert lifecycle          │
  │   Rotation: Automate. Short-lived certs (hours/days).   │
  └──────────────────────────────────────────────────────────┘

  HASHING:
  ┌──────────────────────────────────────────────────────────┐
  │ Passwords: Argon2id (winner of PHC) or bcrypt            │
  │   NEVER: MD5, SHA-1, SHA-256 alone (too fast!)          │
  │   Always salt (unique per user)                          │
  │   Cost factor: tune to ~250ms per hash                  │
  │                                                          │
  │ Data integrity: SHA-256 (checksums, content addressing)  │
  │ HMAC: SHA-256 with key (message authentication)          │
  └──────────────────────────────────────────────────────────┘

7. Secrets Management

SECRETS: API keys, DB passwords, certificates, tokens, encryption keys

  ❌ ANTI-PATTERNS:
  ┌──────────────────────────────────────────────────────────┐
  │ Secrets in code (git history is FOREVER)                  │
  │ Secrets in environment variables (ps -e exposes them)    │
  │ Shared credentials across environments                   │
  │ Long-lived secrets never rotated                         │
  │ Secrets in container images or CI/CD logs                │
  └──────────────────────────────────────────────────────────┘

  SECRETS MANAGEMENT SOLUTIONS:
  ┌──────────────────────────────────────────────────────────┐
  │ HashiCorp Vault:                                         │
  │   - Dynamic secrets (generate on demand, auto-expire)   │
  │   - Secret rotation (automatic)                          │
  │   - Encryption as a service (transit engine)             │
  │   - Auth: K8s, AWS IAM, OIDC, certificates             │
  │   - Audit logging of all access                         │
  │                                                          │
  │ AWS Secrets Manager:                                     │
  │   - Automatic rotation with Lambda                       │
  │   - Cross-account sharing                               │
  │   - RDS, Redshift integration                            │
  │                                                          │
  │ K8s Secrets:                                             │
  │   - Base64 encoded (NOT encrypted by default!)           │
  │   - Must enable encryption at rest (etcd encryption)    │
  │   - External Secrets Operator: sync from Vault/AWS      │
  │   - Sealed Secrets: encrypted secrets in git            │
  └──────────────────────────────────────────────────────────┘

  SECRET ROTATION PATTERN:
  ┌──────────────────────────────────────────────────────────┐
  │ 1. Generate new secret (version N+1)                     │
  │ 2. Update consumers to accept BOTH versions              │
  │ 3. Update producers to use new version                   │
  │ 4. Verify old version unused                             │
  │ 5. Revoke old version                                    │
  │                                                          │
  │ Dual-read pattern: always try new, fallback to old      │
  │ Automate rotation: never rely on manual processes        │
  │ Target: rotate every 30-90 days (shorter = better)      │
  └──────────────────────────────────────────────────────────┘

8. Cloud-Native Architecture Patterns

CLOUD-NATIVE PRINCIPLES:
  ┌──────────────────────────────────────────────────────────┐
  │ 1. Designed for cloud (not lifted-and-shifted)           │
  │ 2. Microservices-oriented                                │
  │ 3. Container-packaged                                    │
  │ 4. Dynamically orchestrated (K8s)                        │
  │ 5. Automation-heavy (CI/CD, IaC)                         │
  └──────────────────────────────────────────────────────────┘

  12-FACTOR APP (Heroku):
  ┌──────────────────────────────────────────────────────────┐
  │  1. Codebase:      One codebase, many deploys            │
  │  2. Dependencies:  Explicitly declare & isolate          │
  │  3. Config:        Store in environment                   │
  │  4. Backing services: Treat as attached resources        │
  │  5. Build/Release/Run: Strictly separate stages          │
  │  6. Processes:     Execute as stateless processes        │
  │  7. Port binding:  Export services via port binding      │
  │  8. Concurrency:   Scale out via process model           │
  │  9. Disposability: Fast startup, graceful shutdown       │
  │ 10. Dev/Prod parity: Keep environments similar           │
  │ 11. Logs:          Treat as event streams                │
  │ 12. Admin:         Run admin tasks as one-off processes  │
  └──────────────────────────────────────────────────────────┘

  ┌──────────────────────────────────────────────────────────┐

  ┌──────────────────────────────────────────────────────────┐

13. Interview Deep Dive

Defense in depth with Zero TrustTransportIdentityAuthorizationAPI GatewaySecrets

Q1: How would you secure a microservices architecture?

A: Defense in depth with Zero Trust: (1) Transport: mTLS between all services via service mesh (Istio/Linkerd). Automatic cert rotation via SPIRE/cert-manager. (2) Identity: Each service has SPIFFE identity. JWT tokens with service-level claims propagated through call chain. (3) Authorization: OPA sidecar for policy enforcement. Policies defined as code, versioned in git, applied uniformly. (4) API Gateway: External entry point handles authentication, rate limiting, WAF rules. Internal services behind gateway never directly exposed. (5) Secrets: HashiCorp Vault with dynamic secrets. K8s pods auth via service account → Vault → short-lived DB credentials. No hardcoded secrets. (6) Network: K8s NetworkPolicies (default deny). Only explicitly allowed pod-to-pod communication. (7) Container security: Distroless base images, non-root, read-only FS, image scanning in CI. (8) Observability: Audit logs for all AuthZ decisions. Anomaly detection on access patterns. SIEM integration for security events.

Q2: Compare JWT vs opaque tokens for a distributed system.

A: JWT advantages: Self-contained — any service can validate without network call (just verify signature with public key via JWKS). Excellent for microservices where you want to avoid a round-trip to auth server on every request. Contains claims (role, permissions) so authorization decisions are local. JWT disadvantages: Can't revoke before expiry (must wait for token to expire or maintain a blacklist, which defeats the stateless benefit). Size is larger (~800 bytes vs ~32 bytes). Payload is readable (base64, not encrypted). Opaque token advantages: Instantly revocable (delete from server-side store). Smaller size. No sensitive data exposure. Opaque token disadvantages: Every API call requires lookup to token store — adds latency and creates single point of failure. My recommendation: Use JWT with short TTL (5-15 min) + refresh tokens for most microservice architectures. For high-security operations (financial), add a token introspection step or use opaque tokens. Use asymmetric signing (RS256) so any service can verify with public key.

Q3: How would you design a secrets management strategy?

A: Tiered approach: (1) Vault as central secret store: HashiCorp Vault (or cloud KMS) as the source of truth. All secrets centralized, audited, access-controlled. (2) Dynamic secrets: For database credentials, use Vault's database engine — generates unique credentials per application instance with automatic TTL expiry. No shared passwords. (3) K8s integration: External Secrets Operator syncs secrets from Vault → K8s Secrets. Pods never directly access Vault. CSI Secret Store driver for file-based injection. (4) Rotation: Automate rotation every 30 days minimum. Dual-read pattern during rotation window. (5) CI/CD: Secrets injected at deploy time, never in code or container images. GitHub Actions Secrets / GitLab CI variables for pipeline secrets. (6) Emergency: Break-glass procedure for emergency access. All break-glass access logged and reviewed. (7) Detection: git-secrets / trufflehog in pre-commit hooks to prevent secret commits. Regular scanning of repos for leaked secrets.

Q4: When would you choose serverless vs containers?

A: Choose serverless (Lambda/Functions) when: Traffic is spiky/unpredictable (scale to zero saves cost). Functions are short-lived (< 15 min). Event-driven processing (S3 triggers, webhook handlers). Team is small and doesn't want to manage infrastructure. Request volume is low-moderate (< 1M/day cheapest option). Choose containers (K8s/ECS) when: Consistent high traffic (always-on is cheaper than per-invocation). Need long-running processes. Latency-sensitive (cold start unacceptable). Complex networking or stateful requirements. Team has K8s expertise. Multi-cloud portability needed. Hybrid approach: API Gateway → Lambda for lightweight endpoints. ECS/K8s for core services. Step Functions for orchestration. Cost crossover: At ~1M requests/day with consistent load, containers become cheaper. Below that, serverless wins on cost. Cold start mitigation (provisioned concurrency) narrows the gap but adds cost.
