A — The Journey Begins: Locating the Server

Every concept below answers one question: how does a request get from a user's device to your code and back — reliably, quickly, and at scale? We start at the very beginning.

•

1. Client–Server Architecture

Definitionclientsends requestsserverprocessesreturns responses

Definition. The foundational model of the web. A client (browser, mobile app, IoT device) sends requests; a server processes them and returns responses.

   ┌──────────┐    1. REQUEST  ("GET me the homepage")   ┌──────────┐
   │  CLIENT  │  ─────────────────────────────────────►  │  SERVER  │
   │ (browser)│                                          │ (your    │
   │          │  ◄─────────────────────────────────────  │  code)   │
   └──────────┘    2. RESPONSE (HTML / JSON / image)     └──────────┘

Why it matters. It cleanly separates concerns: - The client handles presentation and user interaction. - The server owns business logic, data, and security.

Key properties: - Request/response is initiated by the client. A plain HTTP server cannot "push" to a client on its own — that limitation later forces us to invent WebSockets and Webhooks. - Stateless by default. Each request is independent; the server doesn't remember the last one unless you add sessions/cookies/tokens. Statelessness is what later lets us run many identical servers behind a load balancer.

Step-by-step of a single web request (the 30-second version): 1. User types algomaster.io → browser needs an IP (DNS). 2. Browser opens a TCP connection to that IP (over HTTP/HTTPS). 3. Browser sends an HTTP request; server runs code, maybe hits a database. 4. Server returns a response; browser renders it.

2. IP Addresses

Definitionpublic IPDetailIPv4IPv6Public vs Private IPs

Definition. "The internet's phone numbers." A unique numerical identifier for every device reachable on a network. Every deployed server has a public IP so clients can find it.

   algomaster.io  ─────resolves to────►  192.168.1.1
                                          └── the server's address on the network

Detail: - IPv4 — 192.168.1.1 style (32-bit, ~4.3 billion addresses — now exhausted). - IPv6 — 2001:0db8:85a3::8a2e:0370:7334 (128-bit, effectively unlimited). - Public vs Private IPs — 192.168.x.x, 10.x.x.x, 172.16–31.x.x are private (used inside home/office/VPC networks); the rest are public (routable on the open internet). - Ports complete the address: an IP gets you to the machine, a port (:443 for HTTPS, :80 for HTTP, :5432 for PostgreSQL) gets you to the specific service on it.

Why we don't use IPs directly: they're hard to memorize and they change (servers move, scale, fail over). We need a human-friendly layer of indirection → DNS.

3. DNS (Domain Name System)

Definitioninto machine-readable IP addressesBrowser/OS cacheRecursive resolverRoot nameserverTLD nameserver

Definition. The internet's phone book. DNS translates human-friendly domain names (algomaster.io) into machine-readable IP addresses (192.168.1.1).

                          DNS RESOLUTION (simplified)
   ┌────────┐   "where is algomaster.io?"   ┌───────────────────────┐
   │ CLIENT │ ────────────────────────────► │  DNS RESOLVER         │
   │        │                               │  (asks the hierarchy) │
   │        │ ◄──────────────────────────── │   Root → .io TLD →    │
   └────────┘     "it's at 192.168.1.1"      │   authoritative NS   │
                                             └──────────────────────┘

The resolution chain (what actually happens): 1. Browser/OS cache — checked first (fastest). 2. Recursive resolver (your ISP or 8.8.8.8) — does the legwork. 3. Root nameserver — "ask the .io TLD servers." 4. TLD nameserver — "ask algomaster.io's authoritative nameserver." 5. Authoritative nameserver — returns the actual IP.

Important for system design: - TTL (Time To Live) controls how long each layer caches the answer. Low TTL = faster failover, more DNS traffic; high TTL = less traffic, slower propagation of changes. - DNS is also a scaling/availability tool: a single domain can map to many IPs. GeoDNS / latency-based routing returns the closest server's IP — this is one mechanism behind CDNs and multi-region deployments. - Record types you should know: A (IPv4), AAAA (IPv6), CNAME (alias), MX (mail), TXT (verification/SPF), NS (nameserver).

4. Latency: The Cost of Distance

Definitionroundtrip delay (latency)TakeawaysYou cannot beat the speed of lightbatchparallelize

Definition. Data is bound by physics. Physical distance creates roundtrip delay (latency) — light/electricity simply takes time to travel. A request from India to a server in New York must physically cross the planet and come back.

   Client(India) ───────────────── Server(New York) ───────────────── back to India
   0ms        50ms       100ms       150ms        200ms+
   |───────────|───────────|───────────|───────────|──────────► ROUNDTRIP LATENCY

Why every architect memorizes these numbers:

Operation Approx. time
L1 cache reference 0.5 ns
Main memory (RAM) reference 100 ns
SSD random read ~150 μs
Round trip within same data center ~0.5 ms
Round trip cross-continent 50–150 ms

Takeaways: - RAM is ~100,000× faster than a cross-continent network hop. This single fact justifies caching. - You cannot beat the speed of light — so you move the data closer to the user instead (CDNs, edge nodes, multi-region replicas). - Latency is also why we batch, parallelize, and prefer fewer round trips (a core argument for GraphQL over chatty REST).

5. Forward Proxy vs Reverse Proxy

opposite sidesUse casesNGINX, HAProxy, Envoy, CloudflareMental modelforward proxy guards the clientguard the server

Both are intermediaries that sit between client and server — but they protect opposite sides.

Forward Proxy (protects the client)

Sits in front of the client. Hides the client's IP and identity from the destination server.

   CLIENT ──► [ FORWARD PROXY ] ──► INTERNET / SERVER
              (acts on behalf of the client)

Use cases: corporate egress filtering, anonymity (VPNs), bypassing geo-restrictions, client-side caching, content filtering.

Reverse Proxy (protects the server)

Sits in front of the server. Intercepts and routes incoming traffic, hiding the backend.

   INTERNET ──► [ REVERSE PROXY ] ──► SERVER(s)
                (acts on behalf of the server)

Use cases: load balancing, SSL/TLS termination, caching, compression, hiding internal topology, WAF / DDoS protection. Tools: NGINX, HAProxy, Envoy, Cloudflare.

Mental model: a forward proxy is "the client's bodyguard"; a reverse proxy is "the server's receptionist + bodyguard." The reverse proxy is the seed from which the load balancer and API gateway grow.

At a glance — proxy vs reverse proxy vs load balancer vs API gateway

All four are intermediaries on the request path. The forward proxy guards the client; the other three all guard the server and form a progression — each adds smarts on top of the last.

Dimension Forward Proxy Reverse Proxy Load Balancer API Gateway
Sits in front of The client The server(s) A pool of servers All backend services
Acts on behalf of Client Server Server Server / platform
Hides Client IP & identity from the server Backend topology from clients Individual servers from clients Microservice sprawl, behind one facade
Primary job Egress control, anonymity, client-side caching/filtering Routing, SSL/TLS termination, caching, compression, WAF Spread traffic across healthy servers (round-robin, least-conn, IP-hash) Single entry point: routing + auth + rate-limit + aggregation
Typical OSI layer L7 (HTTP) L4 / L7 L4 (fast) or L7 (content-aware) L7 (application)
Examples Squid, corporate egress proxy, VPN NGINX, HAProxy, Envoy, Cloudflare NGINX, HAProxy, AWS ELB/ALB, Envoy Kong, AWS API Gateway, Apigee, Spring Cloud Gateway

One-liner: forward proxy = the client's bodyguard; reverse proxy = the base server-side intermediary; a load balancer is a reverse proxy that distributes; an API gateway is a reverse proxy that also enforces app-layer policy (auth, rate limits, aggregation). 6. HTTP vs HTTPS

HTTP (HyperText Transfer Protocol)vulnerable to interceptionHTTPSTLS certificatesymmetricWhy it matters

HTTP (HyperText Transfer Protocol) — plain-text rules for client/server communication. Anyone on the network path can read the packet → vulnerable to interception.

HTTPS — HTTP wrapped in an encrypted transport layer (SSL/TLS). The same messages, but unreadable to eavesdroppers.

   HTTP  packet:  [ GET /login  user=alice  pass=1234 ]   ← readable by anyone
   HTTPS packet:  [ ░░░░ encrypted via TLS ░░░░ ] *        ← gibberish without the key

How HTTPS works (the TLS handshake, simplified): 1. Client says hello, lists supported ciphers. 2. Server presents its TLS certificate (proves identity, signed by a Certificate Authority). 3. They agree on keys (asymmetric crypto to exchange a shared symmetric session key). 4. All further traffic is encrypted with that fast symmetric key.

Why it matters: confidentiality (no eavesdropping), integrity (no tampering), and authentication (you're really talking to algomaster.io). HTTPS is mandatory today — browsers flag plain HTTP as "Not Secure," and HTTP/2 & HTTP/3 require it.

7. APIs — The Middleman

DefinitionJSONGood API design qualities

Definition. An API (Application Programming Interface) is the contract through which clients talk to your system. It processes the request, interacts with databases, and returns data in a structured format (usually JSON, sometimes XML).

   ┌────────┐  RAW REQUEST   ┌──────────────────┐   query    ┌──────────┐
   │ CLIENT │ ─────────────► │       API        │ ─────────► │ DATABASE │
   │        │ ◄───────────── │ (business logic) │ ◄───────── │          │
   └────────┘  STRUCTURED    └──────────────────┘   rows     └──────────┘
                DATA (JSON)

The API is where the "work" happens: validation, authentication, business rules, talking to the database/other services, and shaping the response. The client never touches the database directly — the API is the controlled, secured doorway.

Good API design qualities: consistent naming, versioning (/v1/...), clear error codes, pagination, authentication, and predictable structured responses.

8. REST vs GraphQL

HTTP verbscacheablemultiple round tripsA single endpoint + query languageexactly the fields it needsin one trip

Two dominant styles for designing that API.

REST (REpresentational State Transfer)

  • Stateless, resource-based endpoints. Uses standard HTTP verbs: GET, POST, PUT, PATCH, DELETE. Highly cacheable (leverages HTTP caching natively).
  • Drawback — over-fetching / under-fetching: each resource is its own endpoint, so building one screen often requires multiple round trips to gather related data.
   CLIENT ──GET /users──►  /users
   CLIENT ──GET /orders─►  /orders     ← 3 separate trips to assemble one view
   CLIENT ──GET /posts──►  /posts

GraphQL

  • A single endpoint + query language. The client asks for exactly the fields it needs and gets them in one trip. Eliminates over-fetching.
  • Drawback — complexity: harder to cache (everything is a POST to one URL), requires heavier server-side processing (resolvers), and risks expensive/abusive queries (need depth limiting).
   CLIENT ── one query ──►  ┌──────────────────┐
            { user {        │  GRAPHQL ENDPOINT │  ← assembles user+orders+posts
               orders       │  (resolvers)      │     in a single response
               posts } }    └──────────────────┘
Dimension REST GraphQL
Endpoints Many (per resource) One
Fetching Over/under-fetch common Exact fields
Round trips Often multiple Usually one
Caching Easy (HTTP) Harder
Server complexity Lower Higher
Best for Simple, cacheable, public APIs Complex, nested, client-driven UIs

Also worth knowing: gRPC (binary, HTTP/2, great for fast internal service-to-service calls) is a third option you'll meet in a microservices world.

9. SQL vs NoSQL

SQL (Relational)NoSQLStructurerelational schemasGuaranteesACID

Where does the data actually live? Two paradigms. Modern architectures frequently deploy both side by side.

Dimension SQL (Relational) NoSQL
Structure Tables with strict, predefined relational schemas Flexible schemas (Key-Value, Document, Graph, Wide-Column)
Guarantees ACID properties, strong consistency High performance, often eventual consistency
Scaling Vertically first; horizontal is harder Horizontal-friendly by design
Ideal use cases Banking, financial ledgers, transactional integrity Big data, rapid prototyping, highly distributed global apps

SQL (PostgreSQL, MySQL): when relationships and correctness are paramount — you want guarantees that money never disappears.

NoSQL families: - Key-Value (Redis, DynamoDB) — fastest possible lookups by key; caching, sessions. - Document (MongoDB) — JSON-like documents; flexible, evolving schemas. - Wide-Column (Cassandra, Bigtable) — massive write throughput, time-series, feeds. - Graph (Neo4j) — relationship-heavy data (social networks, fraud, recommendations).

The honest answer in interviews: "It depends on the access pattern." Pick the store whose data model matches how you read and write, not the trendiest one. This connects directly to the CAP theorem.

D — The Scaling Crisis

One server worked. Then traffic grew. Now the single box is melting. There are exactly two ways out.

•

10. Vertical Scaling (Scale Up)

DefinitionCPU/RAMone machineHard limits on capacityExpensiveSingle point of failure

Definition. Add more CPU/RAM to one machine — make the single box bigger.

        ┌──────┐                 ┌──────────┐
        │ 4 CPU│   scale up  ►   │  64 CPU  │
        │ 8 GB │                 │  512 GB  │
        └──────┘                 └──────────┘
  • ✅ Simple — no code changes, no distribution logic.
  • ❌ Hard limits on capacity — you can only buy so big a machine.
  • ❌ Expensive — high-end hardware costs scale non-linearly.
  • ❌ Single point of failure — that one machine dies → everything is down.
•

11. Horizontal Scaling (Scale Out)

Definitionacross multiple machinesEffectively infinite capacityHighly fault-tolerantstateless serversdistribute traffic

Definition. Distribute the workload across multiple machines — add more boxes.

        ┌──────┐   scale out  ►   ┌──┐ ┌──┐ ┌──┐ ┌──┐
        │ 1 box│                  │  │ │  │ │  │ │  │   ... add as many as needed
        └──────┘                  └──┘ └──┘ └──┘ └──┘
  • ✅ Effectively infinite capacity — keep adding nodes.
  • ✅ Highly fault-tolerant — one node dies, the rest keep serving.
  • ❌ More complex — requires stateless servers, a way to distribute traffic (load balancer), and distributed data strategies (replication, sharding).

Rule of thumb: scale up for quick wins early; design to scale out for true growth. The whole rest of this blueprint exists because we chose to scale out.

•

12. The Load Balancer

Definitiontraffic managerRouting algorithmsRound RobinLeast ConnectionsLeast Response Time

Definition. The traffic manager that sits in front of your fleet of horizontally-scaled servers and routes incoming traffic to healthy nodes.

                          ┌──► [Server 1] √
   INCOMING   ┌────────┐  ├──► [Server 2] √
   TRAFFIC ──►│  LOAD  │──┼──► [Server 3] × (failed → removed from rotation)
              │BALANCER│  └──► [Server 4] √
              └────────┘

Routing algorithms: - Round Robin — each server in turn (simple, even). - Least Connections — send to the server with the fewest active connections (good for uneven request durations). - Least Response Time — fastest responder wins. - IP Hash / Sticky Sessions — same client → same server (needed when state isn't shared). - Weighted — bigger servers get more traffic.

Critical extra job — health checks: the LB constantly pings each node; an unhealthy node is automatically removed from rotation, which is what makes horizontal scaling fault-tolerant.

Layers: L4 load balancers route by IP/port (fast, protocol-agnostic); L7 load balancers understand HTTP and can route by URL path, headers, or cookies (smarter, slightly slower).

The load balancer is a specialized reverse proxy. To avoid the LB itself becoming a single point of failure, you run it redundantly (active-passive with a floating IP, or a managed LB like AWS ELB across availability zones).

✅ Milestone achieved: a resilient core. But notice the database is still a single primary — that's the next bottleneck, and Part E is all about smashing it.

E — Optimizing the Data Bottleneck

The app tier scales out easily because it's stateless. The database holds state, so it becomes the hardest thing to scale. Here are the tools, in the order you'd typically reach for them.

•

14. Indexing

Definitionsuper-efficient lookup tableSpeeds up readsSlows down writesB-treehash

Definition. A super-efficient lookup table that lets the database locate data directly without scanning every row.

   WITHOUT INDEX:  scan all 10,000,000 rows  → O(n)   *
   WITH INDEX:     jump straight to the row   → O(log n) *

   USER_ID INDEX ──► ┌──────────────────────────────┐
                     │ ...........  TARGET ROW  ....│
                     └──────────────────────────────┘
  • Speeds up reads dramatically (the #1 first-line fix for slow queries).
  • Slows down writesevery INSERT/UPDATE/DELETE must also update the index.
  • Usually a B-tree (great for equality and range queries); hash indexes exist for equality-only.
  • Index the columns you filter, join, sort, and group bybut don't index everything (each index costs disk + write speed).

Full deep dive (composite, partial, covering indexes, selectivity, EXPLAIN ANALYZE) lives in 01_Python/30_Database_and_ORM/Database_and_ORM.md.

15. Replication

Definitioncopies of the databaseprimary handles all writesWhy it worksread-heavyKey concepts

Definition. Keep copies of the database. The primary handles all writes; replicas handle reads. This spreads read load and ensures high availability.

                  ┌──────────────────┐
                  │ PRIMARY (writes) │
                  └────────┬─────────┘
  data sync   ┌────────────┼────────────┐  data sync
              ▼            ▼            ▼
         ┌─────────┐  ┌─────────┐  ┌─────────┐
         │ REPLICA │  │ REPLICA │  │ REPLICA │  ◄ all serve READS
         └─────────┘  └─────────┘  └─────────┘

Why it works: most applications are read-heavy (think 90% reads, 10% writes). Offloading reads to replicas frees the primary to focus on writes.

Key concepts: - Replication lag — replicas are a few milliseconds (or more) behind the primary. A user who writes then immediately reads from a replica might not see their own change → read-your-writes considerations. - Sync vs async replication — synchronous = no data loss but slower writes; asynchronous = fast writes but possible data loss on primary failure. - Failover — if the primary dies, a replica is promoted to become the new primary. - Topologies — single-primary (most common), multi-primary (write anywhere, conflict resolution needed).

Replication helps reads and availability, but a single primary still caps your write throughput and total dataset size. To break that, you shard.

16. Sharding (Horizontal Partitioning)

Definitionsharding keyDistributes the heavy loadSharding strategiesRange-basedHash-based

Definition. Split database rows across multiple servers based on a sharding key (e.g., User IDs 1–1M on Shard A, 1M–2M on Shard B...). Distributes the heavy load — each shard holds only a slice of the data and handles only a slice of the traffic.

   ┌──────────────────────────── ALL USERS ───────────────────────────┐
   │ User IDs 1–1M │ User IDs 1M–2M │ User IDs 2M–3M │ ...            │
   └───────┬───────────────┬───────────────┬──────────────────────────┘
           ▼               ▼               ▼
      ┌─────────┐     ┌─────────┐     ┌─────────┐
      │ SHARD A │     │ SHARD B │     │ SHARD C │   ← each on its own SERVER
      │(Server 1)     │(Server 2)     │(Server 3)
      └─────────┘     └─────────┘     └─────────┘

This is the answer to the write/size bottleneck: replication copies the whole DB; sharding splits it, so each shard handles independent writes and stores less data.

Sharding strategies: - Range-based — IDs 1–1M, 1M–2M (simple, but risks hotspots if data is unevenly distributed). - Hash-based — hash(user_id) % N (even distribution, but resharding is painful). - Consistent hashing — minimizes data movement when adding/removing shards (used by Cassandra, DynamoDB). - Directory/lookup-based — a lookup service maps keys → shards (flexible, adds a hop).

The hard parts (why sharding is a "last resort"): - Cross-shard queries & joins become expensive or impossible (must query multiple shards and merge in the app). - Rebalancing when adding shards is operationally painful (consistent hashing helps). - Hotspots — a bad shard key (e.g., sharding by country when one country dominates) overloads one shard. - Choosing the shard key is the most important decision — it should spread load evenly and match your most common query pattern.

17. Vertical Partitioning

Definitionmassive table by columnsDifference from shardingrowscolumnsWhy do it

Definition. Split a massive table by columns based on access patterns. Reduces unnecessary disk I/O by scanning only the relevant fields.

   ┌──────────── PROFILE (hot) ────────────┐    ┌────────── BILLING (cold) ───────────┐
   │  User_ID │ Name │ Email │ Settings    │    │  User_ID │ Payment │ TX history     │
   │  (frequently accessed data)           │    │  (less-frequently accessed)         │
   └───────────────────┬───────────────────┘    └──────────────────┬──────────────────┘
                       └──────── shares the same User_ID ──────────┘

Difference from sharding: sharding splits rows (same columns, different rows on each server); vertical partitioning splits columns (different columns grouped by access frequency).

Why do it: - Keep hot, frequently-read columns in a small, fast table (better cache hit rates, less I/O per read). - Move large/rarely-used columns (BLOBs, audit history, big text) out so they don't bloat the common queries.

Both are forms of partitioning — the umbrella term for splitting data to beat size/throughput limits. Many real systems combine them (shard by user, vertically partition each shard's tables).

18. Caching — Memory Over Disk

Definitionfrequently accessed data in RAMTTL (Time To Live)Client / browser cacheCDN cacheApplication cache

Definition. Store frequently accessed data in RAM instead of fetching it from disk every time. Uses a TTL (Time To Live) to expire stale data. This is the single biggest speed hack — remember RAM is ~100,000× faster than a cross-continent disk/network fetch (§4).

                ┌────────────────────────────────┐
                │       App requests data.       │
                │   Checks CACHE (RAM) first.    │
                └────────────────┬───────────────┘
                    CACHE HIT ◄──┴──► CACHE MISS
                      │                      │
                      ▼                      ▼
            ┌────────────────────┐  ┌───────────────────────────────┐
            │    Return data     │  │  Fetch from DATABASE (disk)   │
            │     INSTANTLY      │  │     Save a copy to cache      │
            └────────────────────┘  │          Return data          │
                                    └───────────────────────────────┘

Where caches live (multiple layers): - Client / browser cache (closest, free). - CDN cache (edge, for static assets — see §22). - Application cache (in-process, e.g., local memory). - Distributed cache (Redis, Memcached) — shared across all app servers. - Database cache (query/buffer cache).

Caching strategies: - Cache-aside (lazy loading) — app checks cache, on miss reads DB and populates cache (shown above; most common). - Read-through / Write-through — the cache layer itself loads/writes the DB. - Write-behind — write to cache now, flush to DB asynchronously (fast, risk of loss).

The two hard problems: 1. Cache invalidation — keeping cache and DB in sync ("there are only two hard things in CS..."). TTLs, explicit invalidation on write, and versioned keys are the tools. 2. Stampede / thundering herd — when a hot key expires, thousands of requests hit the DB at once. Mitigate with locks, request coalescing, or staggered TTLs.

19. Denormalization — Trading Space for Speed

Definitiondata redundancywithout redundancyJOIN operationspre-assembled into one tablelightning-fast reads

Definition. Deliberately introduce data redundancy to avoid expensive JOINs.

Before (Normalized)

Data stored efficiently without redundancy. Requires expensive JOIN operations to assemble a complete record.

   USERS                       ORDERS
   ┌────────┬──────┬───────┐   ┌─────────┬────────┬─────────┬────────┐
   │User_ID │ Name │ Email │   │Order_ID │User_ID │ Product │ Amount │
   └────────┴──────┴───────┘   └─────────┴────────┴─────────┴────────┘
            └──────────  JOIN on User_ID  ──────────┘   ← work on every read

After (Denormalized)

Related data is pre-assembled into one table. Eliminates JOINs for lightning-fast reads, but introduces data duplication and complex/heavier writes.

   USER_ORDERS  (everything pre-joined)
   ┌─────────┬────────┬──────┬───────┬─────────┬────────┐
   │Order_ID │User_ID │ Name │ Email │ Product │ Amount │   ← read in one shot *
   └─────────┴────────┴──────┴───────┴─────────┴────────┘
                      ▲ Name/Email duplicated for every order

Trade-off summary:

Normalized Denormalized
Storage Minimal (no duplication) More (redundant copies)
Reads Slower (JOINs) Fast (single table)
Writes Simple (update once) Complex (update many copies)
Risk — Data can drift out of sync
Best for Write-heavy, integrity-critical Read-heavy, latency-critical

Normalization keeps data correct; denormalization makes reads fast. Real systems normalize the source of truth and denormalize into read models / materialized views (this is the heart of CQRS). Full normalization theory (1NF→BCNF) is in the Database & ORM notes.

  • Consistency (C)every read receives the most recent write (or an error).
  • Availability (A)every request gets a (non-error) response, even if not the latest.
  • Partition Tolerance (P)the system keeps working despite network failures between nodes.

The catch: because real networks always fail, P is mandatory for any distributed system. So the real choice architects make is between CP and AP:

Choice Sacrifices Behavior during a partition Examples
CP (Consistency + Partition tolerance) Availability Refuses/errors to avoid returning stale data Banking, MongoDB (default), HBase, etcd, ZooKeeper
AP (Availability + Partition tolerance) Consistency Always responds, may return stale data; reconciles later Shopping carts, Cassandra, DynamoDB, Couchbase

Practical lens: - Choose CP when correctness is non-negotiable (money, inventory, bookings). - Choose AP when uptime matters more than perfect freshness (feeds, likes, product catalogs) — these embrace eventual consistency. - This is the deep reason the SQL vs NoSQL split exists.

Related: PACELC extends CAP — if Partitioned, choose A or C; Else (normal operation), choose Latency or Consistency. Even with no failures, you trade latency for consistency.

21. Blob Storage

Definition. Highly scalable, unstructured storage for large media files (images, video, PDFs, backups). Each file — a BLOB (Binary Large OBject) — gets a unique URL.

   ┌───────────── OBJECT STORAGE (unlimited capacity) ─────────────┐

   │   * doc.pdf     →  blob_id: 1-2024-734, 12GB → unique URL     │

Why not store media in the database? Databases are terrible at large binaries — they bloat, slow down backups, and waste expensive DB I/O. Instead: - Store the file in blob storage (S3, Google Cloud Storage, Azure Blob). - Store only the URL/metadata in the database.

Properties: effectively unlimited scalability, pay-per-use, durable (data replicated across facilities — e.g., S3's "11 nines" durability), and directly serveable via URL (often fronted by a CDN).

Plain HTTP is request/response and client-initiated — the server can't push. These two patterns fix that, in opposite directions. (The naive alternative, polling — the client asking "any news?" every few seconds — wastes resources and adds latency; we go beyond polling.)

WebSockets (Client ↔ Server)

A persistent, two-way (full-duplex) connection. The server can push updates to the client instantly without waiting for a request.

   CLIENT  ◄═══════ persistent two-way connection ═══════►  SERVER

All features in one codebase, deployed as a single unit.

   ┌────────────── ONE DEPLOYABLE APP ─────────────┐

26. Message Queues — Decoupling Systems

The problemcascading failuresThe solutionAsynchronous decouplingproducer drops tasks into a queueWhat it buys you

The problem. Synchronous, direct API calls cause cascading failures — if the downstream service is slow or down, the caller blocks or fails, and the failure ripples upstream.

The solution. Asynchronous decoupling. A producer drops tasks into a queue; a consumer processes them at its own pace. 

   ┌────────────┐ enqueue    ┌──────────── MESSAGE QUEUE ─────────────┐ dequeue    ┌────────────┐
   │  PRODUCER  │───────────►│   ▪ ▪ ▪ ▪ ▪  (durable buffer)  ▪ ▪ ▪   │───────────►│  CONSUMER  │
   └────────────┘            └────────────────────────────────────────┘            └────────────┘

What it buys you: - Absorbs massive traffic spikes — the queue buffers a surge; consumers drain it steadily (load leveling). Prevents internal system overloads. - Decoupling — producer and consumer don't need to be up at the same time, or know about each other. You can add/remove/scale consumers freely. - Resilience — if a consumer crashes mid-message, the message isn't lost; it's redelivered. - Async work — offload slow jobs (emails, image processing, report generation) so the user's request returns instantly.

Concepts: - Queue vs Pub/Sub — a queue delivers each message to one consumer (work distribution); pub/sub broadcasts to many subscribers (fan-out). - Delivery guarantees — at-most-once, at-least-once (most common), exactly-once (hard — needs idempotency). - Dead-letter queue (DLQ) — messages that repeatedly fail are parked for inspection. - Ordering & backpressure — some queues preserve order (Kafka per-partition); consumers signal when they're overwhelmed.

Tools: Kafka (high-throughput log/stream), RabbitMQ (flexible broker), AWS SQS/SNS, Google Pub/Sub.

27. API Gateway & Rate Limiting

Responsibilitiesrate limitingoneenforcing a request quotafair usage and system stabilityAlgorithms

API Gateway

The single entry point for all client requests. It centralizes routing, authentication, and logging — hiding internal microservice complexity behind one clean facade.

   NORMAL USERS ──┐
                  │                ┌────────────────┐
   BOTS ──────────┼─── traffic ───►│  API GATEWAY   │── routes ──►  [ internal services ]
                  │                │  auth · route  │   [ auth | billing | catalog ]
   BOTS ──────────┘                │  log · limit   │
                                   └────────────────┘

Responsibilities: request routing, authentication/authorization, rate limiting, request/ response transformation, SSL termination, logging/metrics, API versioning, and aggregation. It means clients deal with one endpoint instead of dozens of services.

Rate Limiting

Protects against bots and resource exhaustion by enforcing a request quota (e.g., 100 requests/min per IP or per API key) to ensure fair usage and system stability.

Algorithms: - Token Bucket — tokens refill at a fixed rate; each request spends one; allows short bursts. (Most popular.) - Leaky Bucket — requests drain at a constant rate; smooths bursts. - Fixed Window — N requests per clock window (simple, but allows 2× burst at window edges). - Sliding Window — smooths the fixed-window edge problem.

On limit exceeded: return HTTP 429 Too Many Requests (often with a Retry-After header). Rate limiting also defends against DDoS, credential-stuffing, and runaway clients.

28. Idempotency — Handling Network Uncertainty

The guaranteeWhy it's neededsuccess response is lostretriescharged twiceHow to implement it

The guarantee. Making the same request multiple times produces the exact same result as making it once. Critical for financial transactions and robust edge-case handling in distributed networks.

Why it's needed. Networks are unreliable. A client sends "Charge $50," the server processes it successfully, but the success response is lost to a network failure. The client doesn't know it worked, so it retries. Without idempotency, the customer is charged twice.

   1) CLIENT ──Charge $50 (ID:123A)──► SERVER   √ processes
      CLIENT ◄──× response lost (network failure)── SERVER

   2) CLIENT ──RETRY: Charge $50 (ID:123A)──► SERVER
                                              ┌──────────────────────────┐
                                              │ DUPLICATE CHECK:         │
                                              │ "123A already processed" │
                                              │ → ignore duplicate logic │
                                              └──────────────────────────┘
      CLIENT ◄────────── √ Success (no double charge) ──────────────────

How to implement it: - The client generates a unique idempotency key (e.g., a UUID like 123A) per logical operation and sends it with the request (commonly an Idempotency-Key header — this is exactly how Stripe does payments). - The server records processed keys (and their result). On a repeat key, it returns the stored result instead of re-executing the side effect.

Naturally idempotent vs not: - GET, PUT, DELETE are idempotent by definition (same call → same end state). - POST (create/charge) is not — which is exactly why payment/checkout endpoints need explicit idempotency keys.

Idempotency is what makes at-least-once delivery (from message queues) safe — retries become harmless.

  │ 4. COMPUTE ESTIMATION                                     │
  │    Servers = Peak QPS / QPS_per_server                    │
  │    Add 30-40% headroom for spikes and failures            │
  │    Rule: never run above 70% CPU utilization              │
  └───────────────────────────────────────────────────────────┘

  SCALING THRESHOLDS:
  ┌──────────────────┬────────────────────────────────────────┐

  │ Memory > 80%     │ Scale up or optimize memory usage      │

  │ > 80% pool       │                                        │
  │ Queue depth      │ Add consumers, scale workers           │
  │ growing          │                                        │
  └──────────────────┴────────────────────────────────────────┘

3. Queuing Theory and Little's Law

LITTLE'S LAW:
  L = λ × W

  L = Average number of items in the system
  λ = Average arrival rate (requests per second)
  W = Average time each item spends in the system

  APPLICATIONS:
  ┌───────────────────────────────────────────────────────────┐
  │ How many concurrent connections?                          │
  │   λ = 1000 QPS, W = 200ms (0.2s)                          │
  │   L = 1000 × 0.2 = 200 concurrent connections             │
  │                                                           │
  │ What thread pool size do I need?                          │
  │   λ = 500 QPS, W = 100ms per request                      │
  │   L = 500 × 0.1 = 50 threads minimum                      │
  │                                                           │
  │ How many servers for target latency?                      │
  │   Target: 5000 QPS, 100ms latency, 50 QPS/server          │
  │   Servers = 5000 / 50 = 100 servers                       │
  │   But: include queuing delay!                             │
  └───────────────────────────────────────────────────────────┘

  QUEUING THEORY KEY INSIGHTS:
  ┌───────────────────────────────────────────────────────────┐
  │ 1. Latency grows NON-LINEARLY with utilization            │
  │                                                           │
  │    Utilization:   Latency multiplier:                     │
  │    50%            2× service time                         │
  │    80%            5× service time                         │
  │    90%            10× service time                        │
  │    95%            20× service time                        │
  │    99%            100× service time                       │
  │                                                           │
  │    → NEVER run services above 70-80% utilization!         │
  │                                                           │
  │ 2. VARIANCE KILLS PERFORMANCE                             │
  │    Even at low average utilization, high variance in      │
  │    processing time causes queuing spikes.                 │
  │    → Reduce processing time variance (consistent perf)    │
  │                                                           │
  │ 3. QUEUES ABSORB BURSTS but amplify SUSTAINED overload    │
  │    Short burst → queue absorbs, processes later           │
  │    Sustained overload → queue grows → OOM → crash         │
  │    → Always have backpressure (bounded queues)            │
  └───────────────────────────────────────────────────────────┘

  M/M/c QUEUE MODEL (most practical):
  - Poisson arrivals (M)
  - Exponential service times (M)
  - c servers
  - Wait time: W_q = (P0 × (λ/μ)^c) / (c! × (1-ρ)² × c × μ)
  - Where ρ = λ / (c × μ) = utilization per server
  - Key takeaway: more servers with lower individual load
    gives dramatically lower queuing delay

4. Amdahl's Law and Scalability

AMDAHL'S LAW:
  Speedup(N) = 1 / (S + (1-S)/N)

  S = fraction that is serial (cannot be parallelized)
  N = number of processors/servers
  1-S = fraction that is parallelizable

  IMPLICATIONS:
  ┌──────────────────────────────────────────────────────────┐
  │ Serial %  │ Max speedup with ∞ processors                │
  │ 1%        │ 100×                                         │
  │ 5%        │ 20×                                          │
  │ 10%       │ 10×                                          │
  │ 25%       │ 4×                                           │
  │ 50%       │ 2×                                           │
  │                                                          │
  │ Even 5% serial code limits you to 20× speedup!           │
  │ → Optimize the serial parts first                        │
  └──────────────────────────────────────────────────────────┘

  SERIAL BOTTLENECKS IN DISTRIBUTED SYSTEMS:
  ┌──────────────────┬───────────────────────────────────────┐
  │ Database locks    │ Contention on hot rows/tables        │
  │ Leader node       │ All writes go through one node       │
  │ Sequence gen      │ Auto-increment ID generation         │
  │ Global cache      │ Single cache server for popular keys │
  │ Queue consumer    │ Single-threaded consumer             │
  │ Aggregation       │ Fan-out results collected at one node│
  └──────────────────┴───────────────────────────────────────┘

  UNIVERSAL SCALABILITY LAW (USL):
  Extension of Amdahl's adding COHERENCY penalty:
  
  C(N) = N / (1 + α(N-1) + β·N·(N-1))
  
  α = contention (serial fraction)
  β = coherency (communication overhead between nodes)
  
  When β > 0, throughput actually DECREASES after a point!
  → This is why adding more microservices can slow things down
  → Network overhead, distributed locks, cross-service calls

  ARCHITECT INSIGHT:
  ┌──────────────────────────────────────────────────────────┐
  │ Before adding servers:                                   │
  │ 1. Profile: where is the actual bottleneck?              │
  │ 2. Optimize: can the serial part be made parallel?       │
  │ 3. Cache: can we avoid the bottleneck entirely?          │
  │ 4. Partition: can we shard the hot resource?             │
  │ 5. Then scale: add servers for the parallel parts        │
  └──────────────────────────────────────────────────────────┘

5. Latency Analysis

LATENCY PERCENTILES:
  P50 (median): 50% of requests are faster than this
  P90: 90% are faster (1 in 10 is slower)
  P95: 95% are faster (1 in 20 is slower)
  P99: 99% are faster (1 in 100 is slower)
  P99.9: 1 in 1000 is slower

  WHY TAIL LATENCY MATTERS:
  ┌──────────────────────────────────────────────────────────┐
  │ A single user request may fan out to 100 backend calls.  │
  │ The SLOWEST call determines user-perceived latency.      │
  │                                                          │
  │ If P99 = 1 second, and user request touches 100 services:│
  │ P(at least one > 1s) = 1 - (0.99)^100 = 63%!             │
  │                                                          │
  │ → At scale, tail latency BECOMES the user experience     │
  │ → Always measure and optimize P99, not just P50          │
  └──────────────────────────────────────────────────────────┘

  TAIL LATENCY CAUSES:
  ┌──────────────────┬───────────────────────────────────────┐
  │ GC pauses        │ Java/Go: 10-100ms+ pauses             │
  │ Resource contention│ CPU scheduling, disk I/O, network   │
  │ Head-of-line     │ Slow request blocks fast ones in queue│
  │ Cold cache       │ First request after cache eviction    │
  │ Background tasks │ Compaction, snapshots, log rotation   │
  │ Kernel interrupts│ Network interrupts, context switches  │
  │ Noisy neighbors  │ Shared infrastructure (cloud VMs)     │
  └──────────────────┴───────────────────────────────────────┘

  TAIL LATENCY MITIGATION:
  1. HEDGED REQUESTS: Send same request to 2 replicas,
     use first response, cancel the other
  2. TIED REQUESTS: Send to 2 servers, first to start
     processing notifies the other to cancel
  3. DEADLINE PROPAGATION: Propagate request deadline
     through call chain; services abort if deadline passed
  4. LATENCY BUDGET: Allocate budget per stage:
     Total: 200ms → Network: 20ms → Cache: 30ms →
     Compute: 50ms → DB: 50ms → Buffer: 50ms
  5. LOAD SHEDDING: Drop requests when overloaded
     rather than making everyone slow

  LATENCY BUDGETING:
  ┌──────────────────────────────────────────────────────────┐
  │ Total budget: 200ms                                      │
  │ ├── API Gateway:    10ms                                 │
  │ ├── Auth check:     15ms (cached JWT validation)         │
  │ ├── Feature fetch:  30ms (Redis, parallel)               │
  │ ├── Model inference: 50ms                                │
  │ ├── Business logic: 20ms                                 │
  │ ├── DB write:       40ms                                 │
  │ └── Buffer:         35ms (for variance)                  │
  │                                                          │
  │ Rule: Each component's P99 should be within its budget   │
  │ Alert when P95 approaches budget (early warning)         │
  └──────────────────────────────────────────────────────────┘

6. Caching Architectures

MULTI-TIER CACHING:

  Browser → CDN Edge → API Gateway → App Cache → DB Cache → DB
  
  ┌──────────────┬──────────┬───────────┬─────────────────────┐
  │ Layer        │ Latency  │ Hit Rate  │ What to cache       │
  ├──────────────┼──────────┼───────────┼─────────────────────┤
  │ Browser      │ 0ms      │ Varies    │ Static assets, API  │
  │ CDN          │ 1-30ms   │ 95-99%    │ Static, semi-static │
  │ API Gateway  │ 1-5ms    │ 30-60%    │ Auth tokens, routes │
  │ Application  │ 1-5ms    │ 80-95%    │ Session, hot data   │
  │ (Redis)      │          │           │                     │
  │ DB Query     │ varies   │ 20-40%    │ Prepared statements │
  │ Cache        │          │           │                     │
  └──────────────┴──────────┴───────────┴─────────────────────┘

  CACHE TOPOLOGY PATTERNS:
  ┌───────────────────────────────────────────────────────────┐
  │ LOCAL CACHE (in-process):                                 │
  │   - Fastest (no network hop)                              │
  │   - Per-instance (not shared)                             │
  │   - Inconsistent across instances                         │
  │   - Use for: immutable data, config, feature flags        │
  │   - Tools: Caffeine (Java), lru-cache (Python)            │
  │                                                           │
  │ DISTRIBUTED CACHE (Redis/Memcached):                      │
  │   - Shared across all instances                           │
  │   - Network hop (1-5ms)                                   │
  │   - Single source of truth for cached data                │
  │   - Use for: session, hot data, rate limiting             │
  │                                                           │
  │ TWO-TIER CACHE (Local + Distributed):                     │
  │   - Local cache with short TTL (10-60 seconds)            │
  │   - Distributed cache as fallback                         │
  │   - Best of both worlds                                   │
  │   - Complexity: invalidation across tiers                 │
  │                                                           │
  │ NEAR CACHE (e.g., Hazelcast):                             │
  │   - Local copy of distributed cache entries               │
  │   - Automatically synced with distributed cache           │
  │   - Managed by the caching framework                      │
  └───────────────────────────────────────────────────────────┘

  CACHE INVALIDATION PATTERNS:
  ┌───────────────────────────────────────────────────────────┐
  │ TTL-based: Set expiry on cache entries                    │
  │   Simple, eventual consistency (stale for TTL duration)   │
  │                                                           │
  │ Event-driven: DB change → event → invalidate cache        │
  │   More complex, near-real-time consistency                │
  │   Implementation: CDC (Debezium) → Kafka → cache updater  │
  │                                                           │
  │ Version-based: Include version in cache key               │
  │   cache_key = f"user:{user_id}:v{version}"                │
  │   Increment version on write → old cache ignored          │
  │                                                           │
  │ Write-through: Write to cache AND DB simultaneously       │
  │   Strong consistency, higher write latency                │
  └───────────────────────────────────────────────────────────┘

  CACHE WARMING STRATEGIES:
  - Pre-populate on deploy (for predictable hot data)
  - Async background job refreshes before TTL expires
  - On-demand with single-flight (avoid thundering herd)
  - Predictive: ML model predicts next hot keys

7. Connection Pooling Deep Dive

CONNECTION POOLING: Reuse expensive connections (DB, HTTP)
instead of creating new ones per request.

  WHY IT MATTERS:
  ┌─────────────────────────────────────────────────────────────┐
  │ Creating a PostgreSQL connection:                           │
  │   TCP handshake:       1ms                                  │
  │   TLS handshake:       5ms                                  │
  │   Auth + session init: 10ms                                 │
  │   Total: ~16ms per connection                               │
  │                                                             │
  │ With pool: Borrow from pool → 0.01ms                        │
  │ 1600× faster!                                               │
  └─────────────────────────────────────────────────────────────┘

  CONNECTION POOL SIZING:
  ┌─────────────────────────────────────────────────────────────┐
  │ FORMULA (for databases):                                    │
  │ pool_size = num_physical_cores × 2 + effective_spindle_count│
  │                                                             │
  │ For SSD (spindle_count ≈ 0):                                │
  │   pool_size ≈ cores × 2                                     │
  │                                                             │
  │ Example: 8-core DB server                                   │
  │   pool_size = 8 × 2 = 16 connections                        │
  │                                                             │
  │ COMMON MISTAKE: Setting pool too large!                     │
  │   100 connections per app × 10 app instances                │
  │   = 1000 connections to DB!                                 │
  │   → Context switching overhead kills DB performance         │
  │   → Use PgBouncer/ProxySQL between app and DB               │
  │                                                             │
  │ CONFIGURATION PARAMETERS:                                   │
  │   min_pool_size:    Minimum connections kept open           │
  │   max_pool_size:    Maximum connections allowed             │
  │   idle_timeout:     Close idle connections after duration   │
  │   max_lifetime:     Recycle connection after duration       │
  │   connection_timeout: Wait time for available connection    │
  │   validation_query: Test connection health ("SELECT 1")     │
  └─────────────────────────────────────────────────────────────┘

  CONNECTION POOL FOR MICROSERVICES:
  ┌─────────────────────────────────────────────────────────────┐
  │                                                             │
  │ App Instance 1 ──(pool: 20)──┐                              │
  │ App Instance 2 ──(pool: 20)──┤                              │
  │ App Instance 3 ──(pool: 20)──├────→ PgBouncer ──→ PostgreSQL│
  │ App Instance 4 ──(pool: 20)──┤    (pool: 30)   (max: 30)    │
  │ App Instance 5 ──(pool: 20)──┘                              │
  │                                                             │
  │ Without PgBouncer: 100 connections to DB!                   │
  │ With PgBouncer: 30 connections to DB, 100 to PgBouncer      │
  │ PgBouncer multiplexes using transaction-level pooling       │
  └─────────────────────────────────────────────────────────────┘

  HTTP CONNECTION POOLING:
  - HTTP/1.1 Keep-Alive: reuse TCP connections
  - HTTP/2 multiplexing: multiple requests on one connection
  - gRPC: built-in connection pooling via HTTP/2
  - Pool per (host, port) combination
  - Configure: max connections per host, keep-alive timeout

8. Database Performance Tuning

DATABASE PERFORMANCE OPTIMIZATION:

  QUERY OPTIMIZATION:
  ┌───────────────────────────────────────────────────────────┐
  │ 1. EXPLAIN ANALYZE every slow query                       │
  │    Look for: Sequential Scans, Nested Loops, Sort on disk │
  │                                                           │
  │ 2. INDEX STRATEGY:                                        │
  │    - Index WHERE, JOIN, ORDER BY columns                  │
  │    - Composite index: (a, b, c) serves queries on         │
  │      (a), (a,b), (a,b,c) — NOT (b), (c), (b,c)            │
  │    - Covering index: includes all SELECT columns          │
  │      (index-only scan, no table lookup)                   │
  │    - Partial index: WHERE is_active = true                │
  │    - Expression index: ON (lower(email))                  │
  │                                                           │
  │ 3. QUERY PATTERNS TO AVOID:                               │
  │    × SELECT * (fetch only needed columns)                 │
  │    × N+1 queries (use JOINs or batch fetches)             │
  │    × OFFSET-based pagination (use cursor/keyset)          │
  │    × Functions in WHERE (prevents index use)              │
  │    × LIKE '%prefix' (can't use B-tree index)              │
  │    × OR on different columns (use UNION instead)          │
  └───────────────────────────────────────────────────────────┘

  PAGINATION STRATEGIES:
  ┌───────────────────────────────────────────────────────────┐
  │ OFFSET (bad for large offsets):                           │
  │   SELECT * FROM items OFFSET 10000 LIMIT 20               │
  │   DB scans 10020 rows, returns 20. Gets slower with page. │
  │                                                           │
  │ KEYSET / CURSOR (good):                                   │
  │   SELECT * FROM items WHERE id > :last_seen_id LIMIT 20   │
  │   Uses index, constant performance regardless of page.    │
  │   Limitation: can't jump to page N directly.              │
  │                                                           │
  │ CURSOR-BASED (opaque token):                              │
  │   Encode (last_id, last_sort_value) into opaque token     │
  │   Client passes cursor, server decodes and queries.       │
  │   Used by: GraphQL Relay, Facebook Graph API              │
  └───────────────────────────────────────────────────────────┘

  DATABASE SCALING PATTERNS:
  ┌───────────────────────────────────────────────────────────┐
  │ 1. Optimize queries and indexes (first!)                  │
  │ 2. Add read replicas (read scaling)                       │
  │ 3. Connection pooling (PgBouncer, ProxySQL)               │
  │ 4. Caching layer (Redis for hot data)                     │
  │ 5. Vertical partitioning (split tables by column)         │
  │ 6. Horizontal sharding (split by shard key)               │
  │ 7. Move to distributed DB (CockroachDB, Spanner)          │
  │                                                           │
  │ Each step adds complexity. Only proceed when needed.      │
  └───────────────────────────────────────────────────────────┘

  HOT SPOT MITIGATION:
  - Shard key selection: avoid sequential keys (timestamps)
  - Salting: prepend random prefix to shard key
  - Write buffering: batch writes to hot rows
  - In-memory counters: aggregate, flush to DB periodically
  - Separate hot data: move frequently accessed to Redis

  SCALING DIMENSIONS:
  ┌──────────────────┬────────────────────────────────────────┐

  ┌───────────────────────────────────────────────────────────┐
  │ TARGET TRACKING:                                          │
  │   Maintain metric at target value                         │
  │   Example: Keep avg CPU at 60%                            │
  │   Simplest, self-adjusting                                │
  │                                                           │
  │ STEP SCALING:                                             │
  │   CPU 60-70% → add 1 instance                             │
  │   CPU 70-80% → add 2 instances                            │
  │   CPU > 80%  → add 3 instances                            │
  │   More control, requires tuning                           │
  │                                                           │
  │ SCHEDULED SCALING:                                        │
  │   Scale up at 9am, scale down at 6pm (known patterns)     │
  │   Pre-warm for expected traffic spikes                    │
  │                                                           │
  │ PREDICTIVE SCALING:                                       │
  │   ML model predicts traffic based on historical patterns  │
  │   Scales proactively (before spike arrives)               │
  │   AWS Predictive Scaling, GCP Predictive Autoscaling      │
  └───────────────────────────────────────────────────────────┘

  SCALING METRICS:
  ┌───────────────────────────────────────────────────────────┐
  │ CPU Utilization:     Most common, simple, but lagging     │
  │ Request Count (RPS): Direct traffic metric                │
  │ Queue Depth:         For async workers                    │
  │ Latency (P95/P99):   Scale based on user experience       │
  │ Custom Metrics:      Active users, ML inference queue     │
  │ Concurrent Requests: For connection-heavy workloads       │
  └───────────────────────────────────────────────────────────┘

  SCALING BEST PRACTICES:
  ┌───────────────────────────────────────────────────────────┐
  │ 1. Scale out faster than scaling in (asymmetric timing)   │
  │    Scale out: 1 minute cooldown                           │
  │    Scale in: 5-10 minute cooldown (avoid flapping)        │
  │                                                           │
  │ 2. Use multiple metrics (CPU AND request count)           │
  │                                                           │
  │ 3. Set minimum instances ≥ 2 (always available)           │
  │                                                           │
  │ 4. Pre-warm on deploy (health check before receiving      │
  │    traffic: load caches, warm JIT, establish connections) │
  │                                                           │
  │ 5. Design for sudden scale: stateless services,           │
  │    externalized state, fast startup time                  │
  │                                                           │
  │ 6. Test scaling: simulate traffic spikes, measure time    │
  │    to scale and impact on latency                         │

12. Performance Anti-Patterns

PERFORMANCE ANTI-PATTERNS:

  1. N+1 QUERY:
     Fetch 100 users → 100 queries for their orders
     Fix: JOIN or batch fetch (WHERE user_id IN (...))

  2. CHATTY SERVICE CALLS:
     Service A → 50 sequential calls to Service B
     Fix: Batch API, parallel calls, denormalize data

  3. SYNCHRONOUS EVERYTHING:
     Every operation waits for completion
     Fix: Async for non-critical paths (email, analytics)

  4. UNBOUNDED QUERIES:
     SELECT * FROM orders (returns 10M rows)
     Fix: Always paginate, always set LIMIT

  5. PREMATURE MICROSERVICES:
     Network call for what could be a function call
     Fix: Modular monolith until scale warrants decomposition

  6. CACHE STAMPEDE:
     Popular key expires → 10K requests hit DB
     Fix: Single-flight pattern, staggered TTLs

  7. HOT PARTITION:
     All traffic goes to one shard (celebrity, trending)
     Fix: Shard splitting, write buffering, read replicas

  8. LOCK CONTENTION:
     Multiple threads competing for same lock
     Fix: Reduce lock scope, lock-free data structures,
          optimistic concurrency

  9. MEMORY LEAKS:
     Gradual memory growth under sustained load
     Fix: Soak testing, profiling, proper cleanup

  10. MISCONFIGURED POOLS:
      Default connection pool settings (too small or too large)
      Fix: Tune based on Little's Law and load testing

  11. UNCOMPRESSED PAYLOADS:
      Sending 1MB JSON when 100KB compressed would do
      Fix: gzip/br compression, binary protocols (protobuf)

  12. MISSING TIMEOUTS:
      No timeout on HTTP/DB calls → thread pool exhaustion
      Fix: Set timeout on EVERY external call

  OPTIMIZATION ORDER OF OPERATIONS:
  ┌──────────────────────────────────────────────────────────┐
  │ 1. Measure (can't optimize what you can't measure)       │
  │ 2. Find the bottleneck (profiling, tracing)              │
  │ 3. Fix algorithmic issues (O(n²) → O(n log n))           │
  │ 4. Reduce I/O (caching, batching, connection pooling)    │
  │ 5. Parallelize (async, concurrent, distributed)          │
  │ 6. Scale out (more instances, replicas)                  │
  │ 7. Optimize hot paths (JIT, compiled, native)            │
  │ NEVER start at step 6!                                   │
  └──────────────────────────────────────────────────────────┘

14. SRE Fundamentals

SRE (Site Reliability Engineering) — Google's approach to
operating reliable, scalable production systems.

  SLI / SLO / SLA:
  ┌─────────────────────────────────────────────────────────────┐
  │ SLI (Service Level Indicator):                              │
  │   The metric you measure                                    │
  │   Examples:                                                 │
  │   - Request latency (P99 < 200ms)                           │
  │   - Error rate (% of 5xx responses)                         │
  │   - Availability (% of successful requests)                 │
  │   - Throughput (requests successfully served per second)    │
  │   - Freshness (data staleness in read replicas)             │
  │                                                             │
  │ SLO (Service Level Objective):                              │
  │   The target value for the SLI                              │
  │   "99.9% of requests will complete within 200ms"            │
  │   "99.95% availability over 30 days"                        │
  │   Internal promise (to your team/organization)              │
  │                                                             │
  │ SLA (Service Level Agreement):                              │
  │   The contract with customers, with consequences            │
  │   "99.9% uptime or we credit 10% of monthly fee"            │
  │   SLA should be LESS strict than SLO (buffer)               │
  └─────────────────────────────────────────────────────────────┘

  ERROR BUDGET:
  ┌─────────────────────────────────────────────────────────────┐
  │ Error budget = 1 - SLO                                      │
  │                                                             │
  │ SLO = 99.9% → Error budget = 0.1%                           │
  │   Per month (30 days): 43.2 minutes of downtime             │
  │   Per quarter: 2.16 hours of downtime                       │
  │                                                             │
  │ SLO = 99.95% → Error budget = 0.05%                         │
  │   Per month: 21.6 minutes                                   │
  │                                                             │
  │ SLO = 99.99% → Error budget = 0.01%                         │
  │   Per month: 4.3 minutes                                    │
  │                                                             │
  │ HOW TO USE ERROR BUDGET:                                    │
  │ Budget remaining? → Ship features, experiment, deploy.      │
  │ Budget spent? → STOP feature work. Focus on reliability.    │
  │                                                             │
  │ This creates alignment between dev (speed) and ops          │
  │ (reliability). Both teams share the same metric.            │
  └─────────────────────────────────────────────────────────────┘

16. Interview Deep Dive

RequirementsTraffic estimationStorageBandwidthComputeDatabase

Q1: How do you approach capacity planning for a new system?

A: (1) Requirements: Define expected DAU, peak concurrent users, read/write ratio, data retention. (2) Traffic estimation: DAU × actions/user / 86400 = avg QPS. Peak = 2-3× average. Plan for 2-3× peak (headroom). (3) Storage: Daily records × avg size × retention period × replication factor. Include indexes (2-3×). (4) Bandwidth: QPS × payload size for ingress/egress. (5) Compute: Peak QPS / QPS-per-server, with 30-40% headroom. (6) Database: Connection count, query patterns, indexing strategy. (7) Validate: Load test to confirm estimates, adjust. (8) Monitor: Set up dashboards for utilization, alert at 70% thresholds. Key: always work backward from SLOs — "we need P99 < 200ms at 10K QPS."

Q2: Explain Little's Law and how you'd use it to size a connection pool.

A: Little's Law: L = λ × W. L = concurrent items in system, λ = arrival rate, W = time per item. Connection pool example: If our API handles 1000 QPS and each DB query takes 50ms (0.05s), we need L = 1000 × 0.05 = 50 concurrent connections minimum. With 10 app instances, that's 5 connections per instance's pool. Add 20% buffer → pool_size = 6 per instance. But the DB can't handle 60 connections efficiently (context switching). Solution: PgBouncer between apps and DB, with DB-side pool of 30. App-side pool can be larger (20 per instance) since PgBouncer multiplexes. Always validate with load testing — the formula gives a starting point.

Q3: How do you handle tail latency at scale?

A: Tail latency is amplified at scale — if P99 = 1s and a user request touches 100 services, 63% of user requests will be > 1s. Strategies: (1) Hedged requests: Send same request to 2 replicas, use first response. Google reports this reduces P99.9 latency significantly with only 2% extra load. (2) Latency budgets: Allocate budget per stage, propagate deadlines — if deadline passed, abort early rather than waste resources. (3) Load shedding: When overloaded, return 503 to some requests rather than making ALL requests slow. (4) Cache warming: Eliminate cold-cache tail latency by proactive warming. (5) Reduce variance: Dedicated CPU cores, avoid noisy neighbors (dedicated instances), tune GC. (6) Monitor and alert on P99, not just P50 — P50 can be fine while P99 is terrible.

Q4: Walk me through how you'd set up SLOs for a critical service.

A: (1) Identify SLIs: For an API: latency (P99), error rate (5xx/total), availability (successful/total). For a data pipeline: freshness (time since last update), correctness (% valid records). (2) Set SLO targets based on user expectations and business impact: P99 latency < 200ms (99.9% of requests), availability > 99.95% per month. (3) Calculate error budget: 99.95% → 21.6 minutes downtime/month. (4) Instrument: OpenTelemetry → Prometheus → Grafana dashboard. (5) Alert on burn rate: If burning error budget 10× faster than expected, page on-call. This catches both sudden and slow degradation. (6) Error budget policy: If budget is spent → freeze feature releases, prioritize reliability work. This aligns product and engineering teams. (7) Review quarterly: Tighten SLOs as system matures, but SLA should always be less strict than SLO.

Q5: Describe your approach to chaos engineering.

A: (1) Start in staging with small blast radius. Define steady state (what "normal" looks like in metrics). (2) Hypothesize: "If we kill 1 of 3 API servers, latency should stay below SLO." (3) Experiment: Kill the instance. Observe. Was our hypothesis correct? (4) Findings: If latency spiked → fix auto-scaling warmup time, connection draining. (5) Graduate to production after staging confidence. Start with off-peak hours, small % of traffic. (6) Common experiments: Instance termination, network latency injection (100ms), DB failover, cache flush, dependency failure. (7) Tools: Litmus Chaos for K8s, AWS FIS, Toxiproxy for network. (8) Cadence: Run GameDays quarterly. Automated experiments weekly (Netflix's Chaos Monkey runs continuously). (9) Key: Always have a STOP mechanism and pre-agreed rollback plan.

Q6: How do you optimize cloud costs without sacrificing reliability?

A: (1) Right-size first: Analyze actual CPU/memory utilization. Most instances are over-provisioned by 30-50%. (2) Reserved instances for baseline load (predictable workloads: DBs, core API servers). Savings Compute Plans for flexible coverage. (3) Spot instances for fault-tolerant workloads: batch processing, CI/CD, data pipelines. Design for interruption (checkpointing, graceful shutdown). (4) Auto-scaling: Don't pay for idle capacity. Scale to zero for dev/staging outside work hours. (5) Storage tiering: Lifecycle policies to move old data to cheaper tiers. Delete what you don't need. (6) Network: Stay within AZ, use VPC endpoints, compress payloads. Cross-region data transfer is expensive. (7) Serverless for bursty workloads (Lambda, Cloud Run). (8) FinOps practice: Tag everything, weekly cost reviews, set budgets with alerts. Make cost a first-class architectural concern — include in ADRs.
