Q6: OpenAI starts returning 429 Rate Limit errors. What do you do?

A: 429 = you exceeded request/token quota or hit a burst limit. Layered response:

  1. Respect Retry-After. Honor the header; otherwise exponential backoff + jitter (Q3).
  2. Client-side rate limiting / token bucket so you never exceed your TPM/RPM ceiling in the first place.
  3. Request queue with concurrency capbound in-flight calls; smooth bursts.
  4. Batch / coalesce where possible; cache identical or semantically-identical prompts (see [[semantic-cache]]).
  5. Reduce token pressuretrim prompts, lower max_tokens, drop unnecessary context.
  6. Fallback model / provider when sustained (Q8).
  7. Ask for a quota increase if this is steady-state growth, not a spike.
def call_with_429_handling(client, **kw):
    for attempt in range(6):
        try:
            return client.chat.completions.create(**kw)
        except RateLimitError as e:
            wait = float(getattr(e, "retry_after", 0)) or min(60, 2 ** attempt)
            time.sleep(wait + random.uniform(0, 0.5))
    raise

Key takeaway: Honor Retry-After, back off with jitter, throttle client-side with a token bucket, cache/batch to cut volume, and fall back when 429s persist. Don't retry tightly — you make it worse.

Q7: The LLM response takes 60s but your API timeout is 30s. How do you handle it?

A: Two separate problems: the call is slow, and your timeout is fighting it.

  • Stream the response. With token streaming you get first tokens in ~1s and the connection stays alive; you're no longer waiting 60s for a single blob. This is usually the right answer for user-facing latency.
  • Make the work asynchronous. For long generations, return 202 Accepted + a job id; the client polls or you push via webhook/SSE when done. Don't hold a synchronous HTTP request open for a minute.
  • Tune timeouts to reality. A 30s ceiling on a task that legitimately needs 60s is a misconfiguration. Set client/gateway/load-balancer timeouts above the realistic P99, and set the LLM SDK timeout consistently with them.
  • Reduce the worklower max_tokens, shorter prompt, smaller/faster model, or split into chunks.
  • Cap output so worst-case generation time is bounded.

Key takeaway: Stream for interactive UX, go async (job id + polling/webhook) for genuinely long jobs, and align every timeout in the chain to the real P99. A blanket 30s timeout under a 60s workload is the bug.

Q8: OpenAI is completely unavailable. How do you implement fallback models?

A: Build a provider-abstracted, prioritized fallback chain guarded by a circuit breaker:

  1. Abstraction layer. One internal generate() interface; providers (OpenAI, Anthropic, Azure OpenAI, a self-hosted Llama) sit behind adapters. (LiteLLM / a thin router does this.)
  2. Ordered fallbacks. Try primary → on failure (5xx/timeout/circuit-open) → secondary → tertiary.
  3. Circuit breaker per provider so you stop sending to a dead provider and fail fast to the next.
  4. Health checks + automatic recovery (half-open probe).
  5. Mind compatibilityprompts, token limits, and JSON behavior differ across providers; test the fallback path, don't assume parity.
  6. Graceful degradationlast resort: cached answer, a smaller local model, or a polite "try again." 
def generate(prompt, providers):           # providers in priority order
    last = None
    for p in providers:
        if p.circuit_open():
            continue
        try:
            return p.complete(prompt)
        except (ProviderError, TimeoutError) as e:
            p.record_failure(); last = e
    raise AllProvidersDown(last)

Key takeaway: Put providers behind one interface, try them in priority order with per-provider circuit breakers, and test the fallback path for prompt/output-format parity. A fallback you've never exercised will break when you need it.

Q9: The LLM sometimes returns malformed JSON. How do you make the workflow robust?

A: Never json.loads() raw model output and hope. Defense in depth:

  1. Constrain generation. Use structured-output / JSON mode / function-calling / a strict schema where the provider supports it — this eliminates most malformations.
  2. Validate against a schema (Pydantic / JSON Schema) right after parsing. Treat validation failure as a retryable error.
  3. Repair then re-parse. Strip markdown fences, extract the outermost {...}, fix trailing commas before giving up.
  4. Re-ask with the error. Feed the validation error back: "Your JSON was invalid: . Return only valid JSON." Bounded retries.
  5. Fallback default after N attempts so the workflow doesn't wedge.
import json, re
from pydantic import BaseModel, ValidationError

class Answer(BaseModel):
    label: str
    score: float

def parse_llm_json(raw, retry):
    cleaned = re.sub(r"^```(json)?|```$", "", raw.strip(), flags=re.M).strip()
    m = re.search(r"\{.*\}", cleaned, re.S)        # grab outermost object
    try:
        return Answer(**json.loads(m.group()))     # parse + validate
    except (json.JSONDecodeError, ValidationError, AttributeError) as e:
        return retry(error=str(e))                 # re-ask with the error

Key takeaway: Constrain output (JSON mode/schema), validate with Pydantic, attempt a deterministic repair, then re-ask with the error message — all under bounded retries with a safe fallback. Don't trust free-form text to be valid JSON.

Q10: How do you handle partial streaming responses if the connection drops?

A: Mid-stream disconnects leave you with a truncated answer. Strategies:

  • Buffer and detect truncation. Accumulate tokens; if the stream ends without a finish_reason: stop (or your JSON/closing sentinel never arrives), treat it as incomplete.
  • Resume vs. retry. Most APIs can't truly resume a stream. Either (a) retry the whole request (idempotent, simplest), or (b) continuation prompt — feed the partial text back and ask the model to continue from where it stopped.
  • Idempotency for side-effects. If you act on streamed chunks (e.g. tool calls), key them so a retry doesn't double-execute.
  • Client UX. Show partial output, mark it "reconnecting…", and reconcile when the retry completes.
  • Timeouts / heartbeats to detect a silently dead connection rather than hanging forever.
  • Checkpoint the partial so a long generation isn't lost on a transient blip.

Key takeaway: Detect truncation via finish_reason/missing sentinel, then retry or send a continuation prompt; key any chunk side-effects idempotently so reconnection doesn't double-apply. Assume streams can't be resumed at the byte level.

1. Advanced Prompting, System Prompts & Context Engineering

One-sentence idea: Prompt engineering shapes what you say in one message; context engineering shapes the entire information payload the model sees at inference time — system instructions, retrieved documents, tool schemas, memory, conversation history — assembled and pruned turn by turn. As agents got longer-lived, the bottleneck moved from "write a clever prompt" to "manage a shrinking, contested context window well."

•

System prompt design in practice

specRole & objectiveHard constraintsTool contractsOutput formatGrounding instruction

A production system prompt is a spec, not a pep talk. Order matters (recency + primacy both count — put the most load-bearing constraints first and restate critical ones last): 1. Role & objective — who the assistant is, what "done" looks like. 2. Hard constraints — things it must never do (scope, safety, tone) — stated as rules, not suggestions. 3. Tool contracts — what tools exist, when to use each, what NOT to do without a tool (e.g., "never state an account balance without calling get_balance"). 4. Output format — schema, style, length. 5. Grounding instruction — "answer only from the provided context; say 'I don't know' if it's not there" (this single line is the cheapest hallucination-reduction lever in RAG). 6. Few-shot examples — for tasks needing exact format matching (last, closest to the actual query — recency helps).

•

Context engineering — what actually goes in the window, and why it's an engineering problem

scarce, contested resource budgetWriteSelectCompressIsolateOrder for recency bias

Think of the context window as a scarce, contested resource budget, not free real estate:

┌────────────────────────────── context window ──────────────────────────────────┐
│ system prompt (role, rules, tool schemas)      ← static, cached prefix         │
│ long-term memory recall (user prefs, facts)    ← retrieved, small              │
│ RAG-retrieved chunks                            ← dynamic, reranked, capped    │
│ tool outputs from this episode                  ← pruned/summarized as it grows│
│ conversation history                            ← windowed / summarized        │
│ current user turn                               ← always present, near the end │
└────────────────────────────────────────────────────────────────────────────────┘

Core moves an interviewer expects you to name: - Write — persist information outside the window (scratchpad file, memory store) instead of keeping it all in-context. - Select — retrieve only the relevant slice back in (RAG, memory search, tool-result filtering) rather than dumping everything. - Compress — summarize old turns/tool outputs once they cross a token threshold; keep the last K raw turns verbatim, summarize the rest. - Isolate — give sub-agents/sub-tasks their own smaller context instead of one shared, ever-growing window (see §5 multi-agent). - Order for recency bias — put the most decision-critical instruction closest to the generation point, because attention is strongest near the edges of the window (primacy + recency), weakest in the middle.

# 1) ReAct loop — the mechanism under every tool-using LLM agent
def react_loop(query, llm, tools, max_steps=6):
    scratchpad = []                                            # (thought, action, action_input, observation)
    for _ in range(max_steps):
        prompt = build_prompt(query, scratchpad)                # system prompt + tool schemas + scratchpad so far
        thought, action, action_input = llm.think(prompt)        # model emits Thought → Action → Action Input
        if action == "Final Answer":
            return action_input
        observation = tools[action](action_input)                # execute the chosen tool, observe the real result
        scratchpad.append((thought, action, action_input, observation))
    return "max_steps exceeded — abstain"                        # bounded loop, never infinite (recovery ladder, file 23)

# 2) Context compression — "write/compress" from the context-engineering moves above
def compress_history(messages, llm, keep_last=6, token_limit=3000):
    if count_tokens(messages) <= token_limit:
        return messages
    old, recent = messages[:-keep_last], messages[-keep_last:]
    summary = llm.summarize(old)                                  # one LLM call replaces N old messages
    return [{"role": "system", "content": f"Earlier context summary: {summary}"}] + recent

Q&A Drill

Q4. Explain ReAct vs plain CoTThought → Action → ObservationThe rest of this set

Q1. What's the difference between prompt engineering and context engineering? Prompt engineering optimizes the wording of a single instruction. Context engineering is the system-level discipline of deciding what dynamic content — retrieved docs, memory, tool results, history — gets assembled into the window on every call, and how it's pruned/ordered as the episode grows. Prompt engineering is a subset of context engineering focused on the static instruction layer.

Q2. Why put a grounding instruction ("only answer from context, else say you don't know") in the system prompt for RAG? It's the cheapest lever against hallucination: it doesn't fix bad retrieval, but it stops the model from filling gaps with parametric knowledge when retrieval comes up short, converting a silent wrong answer into a visible "I don't know."

Q3. What is "lost-in-the-middle" and how do you mitigate it? Long-context models recall information at the start/end of the context far more reliably than the middle. Mitigate by: reranking so the most relevant chunk is last (closest to the query) or first, keeping context short via aggressive retrieval filtering, and not relying on "just paste everything in" for large contexts.

Q4. Explain ReAct vs plain CoT. CoT is "think, then answer" — no interaction with the outside world. ReAct interleaves Thought → Action → Observation, so the model can call tools, see real results, and revise its plan based on them — this is the loop underneath essentially every tool-using LLM agent.

Q5. When would you use self-consistency over a single CoT call? When a task has a discoverable "right answer" (math, classification, code correctness) and you can afford N× the inference cost — sampling multiple reasoning paths at temperature > 0 and majority-voting reduces variance from any single flawed reasoning chain.

Q6. How do you defend a system prompt against prompt injection from retrieved/tool content? Structurally separate trusted instructions (system prompt) from untrusted content (retrieved docs, tool outputs, web pages) — e.g., wrap untrusted text in clearly delimited/tagged blocks and instruct the model that content inside those tags is data, never instructions; add an output-side guardrail/classifier; least-privilege the tools so even a hijacked plan can't do damage. See LLM Guardrails and Safety.

Q7. What's the difference between a system prompt, a developer message, and a user message in modern chat APIs? System/developer messages are the highest-priority, platform-controlled instructions (role, policy, tools) that the model is trained to weight above conversational turns; the user message is the lowest-trust, most changeable input. Some APIs now split "system" (platform-level, highest trust) from "developer" (app-level) from "user" for finer-grained instruction hierarchy and injection resistance.

Q8. Give a concrete example of "compress" in context engineering. Once a conversation exceeds N tokens, replace turns older than the last K with a single LLM-generated running summary, appended as a synthetic system/context message — keeps salient facts while bounding token growth (used by LangGraph's summarization node, ChatGPT-style memory).

Q9. Why does where you place instructions in the prompt matter as much as what they say? Attention isn't uniform across a long context — critical constraints stated once at the top can get diluted by the time generation starts. Repeating the single most important constraint immediately before the user's actual request measurably improves adherence in long-context prompts.

Production Issue #9: LLM Hallucination & Faithfulness

Scope: LLM Hallucination & Faithfulness — what hallucination really is, why RAG still hallucinates, detection (groundedness / NLI / self-consistency), mitigation (grounding, citations, abstention), and faithfulness evaluation in production.

•

Overview

One-sentence ideafluent next-token predictorconfidentlydetect and measure

One-sentence idea: An LLM is a fluent next-token predictor, not a database. It will always produce plausible-sounding text — and "plausible" and "true" are different things. A hallucination is when those two diverge and the model states something confidently false.

The dangerous word here is confidently. A hallucination doesn't look like an error — it looks exactly like a correct answer, same tone, same fluency. There's no stack trace, no null, no exception. That's why hallucination is a production problem you must actively detect and measure, not a bug you can simply fix in code.

•

Key Definitions (read first)

Hallucinationfluent but falseFaithfulness / groundednessIntrinsicExtrinsicFactuality
Term Plain-language definition
Hallucination The model generates content that is fluent but false or unsupported — invented facts, fake citations, wrong numbers.
Faithfulness / groundedness Whether the answer is actually supported by the provided source context. In RAG, the #1 thing to measure. A faithful answer makes no claim the documents don't back.
Intrinsic vs extrinsic hallucination Intrinsic = contradicts the given source ("the doc says 5%, the model says 50%"). Extrinsic = adds claims the source doesn't mention (can't be verified from context).
Factuality Whether the answer matches the real world (independent of any provided context). A closed-book question relies on factuality; RAG relies on faithfulness.
Abstention The model saying "I don't know / not in the documents" instead of guessing. A missing abstention path is a top cause of hallucination.
Grounding Forcing the model to answer only from supplied context and to cite it.
NLI (entailment) Natural Language Inference: does the context entail the claim (support), contradict it, or is it neutral? The core check behind automated faithfulness scoring.
Self-consistency Sampling several answers; if they disagree, the model is uncertain → likely hallucinating.
Calibration / confidence Whether the model's stated/derived confidence matches how often it's actually right. LLMs are famously overconfident.
•

Why It Happens (the intuition)

next tokenCommon triggersKnowledge gapsRare / long-tail factsLeading promptsOver-long outputs

A language model is trained to maximize the probability of the next token given the previous ones. Nothing in that objective rewards truth — it rewards plausibility. So:

Question: "What was Acme Corp's Q3 2023 revenue?"
The model has never seen Acme's filings, but "revenue" questions
in training were usually answered with "$<number> million", so it
emits a fluent, well-formatted, completely invented number.

The model is doing exactly what it was trained to do — fill in the most likely-looking continuation. It has no built-in concept of "I don't actually know this." Hallucination is the default behavior of an ungrounded model, not a malfunction.

Common triggers: - Knowledge gaps — asked about something outside training data (recent events, private/internal data). - Rare / long-tail facts — seen too few times to memorize correctly. - Leading prompts — "List 5 studies proving X" pressures it to invent 5, even if only 2 exist. - Over-long outputs — once it runs out of real content, it confabulates to keep going. - Conflicting context — contradictory documents force a guess.

•

"But I'm using RAG — why does it still hallucinate?"

Retrieval missUngrounded promptonlyNo abstention pathLost in the middleStale / wrong index

This is the most common production surprise. RAG only helps if the right context reaches the model and the model is forced to use it. RAG hallucinations almost always trace to one of these:

Cause What's happening Fix
Retrieval miss The relevant chunk was never retrieved, so the model fills the gap from parametric memory. Most common cause. Fix retrieval first (hybrid search, reranker) — see Production Scenarios Workflows Q11.
Ungrounded prompt Context is present but the prompt never says "answer only from this." Add grounding + abstention instructions.
No abstention path The model is never allowed to say "not in the docs," so it guesses. Give it an explicit "I don't know" out.
Lost in the middle The right chunk is buried in a huge context and ignored. Rerank; put key context at the start/end; trim bloat.
Stale / wrong index The retrieved doc is itself outdated or incorrect. Fix the source data; track index freshness.
Context vs. parametric conflict The model "knows" something different and overrides the context. Instruct it to prefer context; lower temperature.

Key insight: "Hallucination despite RAG" is usually a retrieval problem or a prompting problem — not a model problem. Verify the right chunk was retrieved before blaming the LLM.

Customer-support bot, grounded on a help-center KB.

Research-assistant LLM.

Reality: No such paper exists. The author, year, and statistics were all fabricated.

Root cause: Closed-book factual question with a leading "cite sources" instruction → the model produces citation-shaped text. Fix: Only allow citations that map to retrieved documents; post-validate every citation id against the retrieved set; reject answers with unverifiable citations.

Detection (from-scratch)

entailWorked exampleRAGASTruLensDeepEvalPhoenix

You cannot fix what you don't measure. Three complementary signals.

1. Groundedness via NLI / entailment

The idea: split the answer into atomic claims, and for each claim ask "does the retrieved context entail this?" If a claim is neither entailed nor implied → it's unsupported → likely hallucinated.

# Faithfulness = fraction of answer claims supported by the context.
# `entails(premise, hypothesis)` can be an NLI model OR an LLM judge call.

def split_claims(answer: str) -> list[str]:
    # Simple sentence split; production: use an LLM to extract atomic claims.
    import re
    return [s.strip() for s in re.split(r"(?<=[.!?])\s+", answer) if s.strip()]

def faithfulness_score(answer: str, context: str, entails) -> dict:
    claims = split_claims(answer)
    if not claims:
        return {"score": 1.0, "unsupported": []}
    unsupported = [c for c in claims if not entails(premise=context, hypothesis=c)]
    score = 1 - len(unsupported) / len(claims)
    return {
        "score": round(score, 3),          # 1.0 = fully grounded, 0.0 = all invented
        "n_claims": len(claims),
        "unsupported": unsupported,        # the exact sentences to flag/verify
    }

Worked example. Answer has 4 sentences; the context supports 3 of them; one ("termination penalty of $50,000") is not entailed:

claims      = 4
unsupported = 1   → ["...termination penalty of $50,000..."]
score       = 1 - 1/4 = 0.75

A 0.75 faithfulness means a quarter of the answer is ungrounded — below a 0.9 gate you'd block, regenerate, or flag for review.

2. LLM-as-judge (groundedness grader)

JUDGE_PROMPT = """You are a strict grader. Given CONTEXT and an ANSWER,
decide if EVERY claim in the ANSWER is supported by the CONTEXT.
Reply with JSON: {{"supported": true|false, "unsupported_claims": [...]}}.
Do not use outside knowledge.

CONTEXT:
{context}

ANSWER:
{answer}"""

def llm_groundedness(answer, context, call_llm):
    raw = call_llm(JUDGE_PROMPT.format(context=context, answer=answer))
    return json.loads(raw)   # validate with Pydantic in real code (see Q9)

Frameworks that package this: RAGAS (faithfulness, answer-relevance, context-precision), TruLens, DeepEval, Phoenix. They're LLM-judge pipelines under the hood.

3. Self-consistency (no context needed)

Sample the same question N times at temperature > 0. Agreement = confidence; disagreement = likely hallucination. 

def self_consistency(question, call_llm, n=5):
    answers = [call_llm(question, temperature=0.7) for _ in range(n)]
    from collections import Counter
    norm = [a.strip().lower() for a in answers]
    top, count = Counter(norm).most_common(1)[0]
    return {
        "agreement": count / n,            # 1.0 = all agree, 0.2 = all differ
        "consensus": top,
        "likely_hallucination": count / n < 0.6,
    }

If 5 samples give 5 different "facts," the model is guessing.

•

Mitigation (defense in depth)

Lower temperatureCap max_tokensstructured output / JSON mode

No single fix works — layer them, cheapest first.

1. Ground the prompt + give an abstention path

GROUNDED_SYSTEM = """Answer the question using ONLY the provided context.
Rules:
1. If the answer is not in the context, reply exactly:
   "I don't have that information in the provided documents."
2. Do not use outside knowledge or assumptions.
3. Cite the chunk id [n] after each claim.
4. Prefer a short, exact answer over a long, padded one."""

This single change removes a large fraction of RAG hallucinations, because the model now has permission to say "I don't know."

2. Require + verify citations

def validate_citations(answer: str, retrieved_ids: set[str]) -> bool:
    import re
    cited = set(re.findall(r"\[(\w+)\]", answer))
    # every citation must map to an actually-retrieved chunk
    return cited.issubset(retrieved_ids) and len(cited) > 0

Reject/regenerate any answer that cites a chunk that wasn't retrieved — that's a fabricated source.

3. Decode for faithfulness, not creativity

  • Lower temperature (0–0.3) for factual tasks — less random invention.
  • Cap max_tokens so the model can't run past supported content and confabulate.
  • Use structured output / JSON mode so it can't free-text its way into claims.

4. Verify-then-serve (the faithfulness gate)

def answer_with_gate(question, retrieve, generate, entails, threshold=0.9):
    chunks = retrieve(question)
    context = "\n".join(c.text for c in chunks)
    answer = generate(question, context)

    f = faithfulness_score(answer, context, entails)
    if f["score"] < threshold:
        # Don't serve a hallucination. Options, in order of preference:
        #  (a) regenerate with stricter prompt, (b) drop unsupported claims,
        #  (c) abstain and escalate to a human.
        return {"answer": "I'm not fully certain — let me connect you to a specialist.",
                "blocked": True, "faithfulness": f["score"]}
    return {"answer": answer, "blocked": False, "faithfulness": f["score"]}

5. Human-in-the-loop for high-stakes

Medical, legal, financial → sample outputs for expert review; require approval before acting on generated facts (ties to Production Scenarios Workflows Q50).

Regression-test prompts like code. Keep a golden set of (question, context, acceptable-answer/abstention) pairs and run faithfulness scoring on every prompt or model change — a new model can silently regress grounding.

def eval_suite(golden, pipeline, entails):
    results = []
    for case in golden:
        out = pipeline(case["question"])
        f = faithfulness_score(out["answer"], case["context"], entails)
        results.append({"q": case["question"], "faithfulness": f["score"],
                        "abstained": "don't have that information" in out["answer"].lower()})
    halluc = sum(1 for r in results if r["faithfulness"] < 0.9 and not r["abstained"])
    return {"hallucination_rate": halluc / len(results), "detail": results}

Production Issue #12: LLM Cost & Token Optimization

Scope: LLM Cost & Token Optimization — token economics, where the bill actually comes from, context bloat, semantic caching, model routing/cascades, prompt compression, batching/streaming, and budgeting.

•

Overview

One-sentence ideaper tokenWhy this needs its own filetokens

One-sentence idea: With an LLM API you don't pay for servers — you pay per token, every single call. So cost is driven by how much text goes in and out, and the fastest way to a shocking bill is a prompt that quietly grew to 8,000 tokens and runs a million times a day.

The mental model that fixes most LLM cost problems:

cost  ≈  (input_tokens × input_price  +  output_tokens × output_price)  ×  number_of_calls

Four levers, and that's it: fewer input tokens, fewer output tokens, cheaper per-token price (model choice), or fewer calls (caching). Every technique below pulls one of those four levers.

Why this needs its own file: classic ML cost optimization targets GPU/instance cost (you own the hardware). With hosted LLMs you don't own hardware — the cost surface is tokens, which behaves completely differently.

Lever 1: Cut Input Tokens (usually the biggest win)

Trim few-shot examplesRerank, don't dump, RAG contextrerankDrop redundant boilerplatePrompt caching

Input is normally the larger and most wasteful half. Attack it first.

  • Trim few-shot examples. Often 2–3 good examples match the quality of 10. Test it.
  • Rerank, don't dump, RAG context. Retrieve 50, rerank, pass the top 3–5 — not all 50. (Also fixes "lost in the middle" — see LLM Hallucination and Faithfulness.)
  • Summarize / window conversation history. Replace old turns with a short running summary instead of resending the entire transcript every turn.
  • Drop redundant boilerplate from the system prompt; reference, don't repeat.
  • Prompt caching for the fixed prefix (system prompt + stable few-shot): providers cache it so repeated calls skip re-processing it — cheaper and faster.
def trim_context(history, retrieved, summarize, max_history_tokens=400, top_k=4):
    # 1) compress history to a budget
    if count_tokens(history) > max_history_tokens:
        history = summarize(history)            # running summary, not full transcript
    # 2) only the most relevant retrieved chunks (assume already reranked)
    retrieved = retrieved[:top_k]
    return history, retrieved

Lever 2: Cut Output Tokens

Output is often priced higher per token, and long outputs also raise latency.

Lever 3: Cheaper Per-Token Price — Model Routing & Cascades

Not every query needs your most expensive model. Route by difficulty.

            ┌─ classify difficulty (cheap/heuristic) ─┐
query ──────┤                                         ├───────────────▶ answer
            ├─ easy/common  → small cheap model ──────┘
            └─ hard/uncertain → large model (only when needed)

Cascade pattern: try the cheap model first; only escalate when its confidence/quality is low.

def cascade(query, cheap, strong, confident):
    ans = cheap(query)                  # ~10–20× cheaper
    if confident(ans):                  # self-reported or judged confidence
        return ans                      # most traffic stops here
    return strong(query)                # escalate only the hard minority

If 80% of traffic is handled by a model that's 15× cheaper, your blended cost drops dramatically even though the hard 20% still uses the premium model. (Same idea as the classic ML "model cascade".)

Lever 4: Fewer Calls — Caching

close enoughCautionhigh

The cheapest token is the one you never send.

Exact cache

Identical prompt → return the stored answer. Trivial, instant, free.

Semantic cache

Many prompts mean the same thing without being byte-identical ("how do I reset my password?" vs "I forgot my password, what do I do?"). Embed the query, and if a past query is close enough, reuse its answer.

def semantic_cache_lookup(query, store, embed, threshold=0.95):
    """Reuse a past answer if a previous query is semantically near."""
    qv = embed(query)
    hit, sim = store.nearest(qv)            # vector similarity search
    if sim >= threshold:                    # tune carefully: too low = wrong answers
        return hit.answer                   # cache hit → 0 LLM tokens
    return None                             # miss → call the model, then store(qv, answer)

Caution: set the similarity threshold high (e.g. ≥0.95). A loose threshold serves almost-right cached answers to subtly different questions — a correctness bug masquerading as a cost win. Don't semantic-cache personalized or time-sensitive answers.

Cache hit rate is a first-class cost metric — a 40% hit rate is a direct 40% cut on those calls.

Production Issue #14: LLM Evaluation, Prompt Management & Fine-Tuning

Scope: LLM Evaluation, Prompt Management & Fine-Tuning — how to test a non-deterministic system, LLM-as-judge eval harnesses, treating prompts as versioned code (regression + A/B), and the RAG-vs-fine-tune decision (catastrophic forgetting, LoRA serving).

•

Overview

One-sentence ideaopen-ended textbuild"Vibe-based" prompt engineering

One-sentence idea: A classic model has a number you can gate on (accuracy ≥ 0.88). An LLM produces open-ended text that's different every run — so "did my change make it better or worse?" has no built-in answer. You have to build the answer: an eval set, a scoring method, and a pipeline that runs it on every prompt/model change.

Two failure modes this prevents: 1. "Vibe-based" prompt engineering — someone tweaks the prompt, it "looks better" on 3 examples, ships, and silently regresses on 30 others. 2. Fine-tuning that breaks more than it fixes — the model gets better at your task and worse at everything else (catastrophic forgetting), with no eval to catch it.

Part 1 — Evaluating LLMs

Why it's hard

  • Non-deterministictemperature > 0 gives different outputs each run; even at 0, providers aren't bit-stable.
  • Open-endedmany valid answers; no single "correct" string, so exact-match mostly fails.
  • Multi-dimensionalan answer can be correct but unsafe, or helpful but ungrounded. One number isn't enough.

The eval ladder (cheapest → most trustworthy)

Deterministic checks (start here)

def deterministic_evals(output: str, case: dict) -> dict:
    import json, re
    checks = {}
    if case.get("must_be_json"):
        try: json.loads(output); checks["valid_json"] = True
        except Exception: checks["valid_json"] = False
    if "must_contain" in case:
        checks["contains"] = all(s in output for s in case["must_contain"])
    if "must_not_contain" in case:                       # e.g. no PII, no system-prompt leak
        checks["safe"] = not any(s in output for s in case["must_not_contain"])
    if "max_words" in case:
        checks["length_ok"] = len(output.split()) <= case["max_words"]
    return checks

LLM-as-judge (for the subjective part)

JUDGE = """Score the ANSWER against the CRITERIA on a 1-5 scale.
Return JSON: {{"score": int, "reason": str}}. Be strict and consistent.

CRITERIA: {criteria}
QUESTION: {question}
ANSWER: {answer}"""

def llm_judge(question, answer, criteria, call_llm):
    raw = call_llm(JUDGE.format(criteria=criteria, question=question, answer=answer))
    return json.loads(raw)   # validate with Pydantic (see file 08, Q9)

Judge caveats (real failure modes): - Position bias — judges favor the first answer shown → randomize order, or average both orders in pairwise. - Verbosity/self bias — judges prefer longer answers and outputs from their own model family → control for length; use a different family as judge. - Prefer pairwise (A vs B) over absolute scores — "which is better?" is far more stable than "rate 1–10." - Validate the judge against human labels on a sample; track judge–human agreement.

For RAG specifically, the faithfulness/groundedness judge in LLM Hallucination and Faithfulness is the key eval. Frameworks: RAGAS, DeepEval, promptfoo, OpenAI Evals, LangSmith, Braintrust.

The eval harness

def run_eval(eval_set, pipeline, judge_fn) -> dict:
    rows = []
    for case in eval_set:
        out = pipeline(case["input"])
        det = deterministic_evals(out, case)
        score = judge_fn(case["input"], out, case["criteria"]) if case.get("criteria") else None
        rows.append({"id": case["id"], "deterministic": det,
                     "judge": score, "pass": all(det.values())})
    pass_rate = sum(r["pass"] for r in rows) / len(rows)
    return {"pass_rate": round(pass_rate, 3), "n": len(rows), "rows": rows}

Prompt regression testing (the core discipline)

Every prompt change must run the eval set before shipping — because LLM prompts are brittle: fixing one case routinely breaks three others.

def gate_prompt_change(old_prompt, new_prompt, eval_set, judge_fn, min_delta=-0.02):
    old = run_eval(eval_set, make_pipeline(old_prompt), judge_fn)["pass_rate"]
    new = run_eval(eval_set, make_pipeline(new_prompt), judge_fn)["pass_rate"]
    return {
        "old": old, "new": new, "delta": round(new - old, 3),
        "ship": new - old >= min_delta,   # block if the change regresses the suite
    }

This is exactly the classic ML CI/CD eval gate idea, applied to prompts.

A/B testing prompts in production

For changes the offline eval can't fully judge (tone, helpfulness), split live traffic between prompt versions and compare outcome metrics (thumbs-up rate, resolution rate, escalation rate). Same machinery as model A/B (Scaling and Infrastructure).

Prompt drift: a prompt tuned for one model version can silently degrade when the provider updates the underlying model. Re-run the eval set on model upgrades — your prompt is coupled to the model it was tuned on.

Part 3 — Fine-Tuning in Production

prompting + RAGPrompting / few-shotRAGknowledgeFine-tuningbehavior/format/style

First question: do you even need it?

Most teams reach for fine-tuning when prompting + RAG would do. They solve different problems:

Use… When you need to change… Example
Prompting / few-shot nothing in the model; just instructions quick behavior tweaks
RAG the model's knowledge (facts it should use) "answer from our latest docs"
Fine-tuning the model's behavior/format/style "always output our exact JSON schema / house tone / a narrow classification"

Key distinction: RAG injects knowledge at query time; fine-tuning bakes in behavior. Fine-tuning is a poor way to add facts (they go stale, can't be cited, and it hallucinates around them) and a good way to teach a consistent format/style or compress a long prompt into the weights. Try prompt + RAG first; fine-tune when behavior/format/cost demands it.

Catastrophic forgetting (the main production risk)

Fine-tuning on a narrow dataset can make the model worse at everything else — it over-specializes and loses general ability.

Before FT:  task accuracy 70% | general benchmark 85%
After FT:   task accuracy 92% | general benchmark 61%   ← forgot a lot

Defenses: - Always keep a general-capability eval (a held-out broad benchmark) in your eval set, not just task metrics — so you see the regression. - LoRA / PEFT — train small adapters instead of all weights: cheaper, and the base model stays intact (swap the adapter out to recover general behavior). - Mix in general data during fine-tuning; use a low learning rate and few epochs. - Validate on out-of-task prompts before shipping.

LoRA / adapter serving

LoRA produces tiny adapter weights you attach to a shared base model — so you can serve many fine-tunes from one base (load/swap adapters per request) instead of hosting many full models. Big cost win at serving time (relates to LLM Cost and Token Optimization).

Fine-tuning data & eval discipline

  • Data quality dominatesa few thousand clean, consistent, representative examples beat a huge noisy set. Garbage examples teach garbage behavior.
  • Hold out a real test set; never evaluate on training data.
  • Version the dataset + base model + adapter together (lineage, file 05) so a fine-tune is reproducible and rollback-able.
  • Re-run the full eval harness (task + general + safety) before promoting — same gates as any model change.

Input Guardrails

beforefirst layerclassifierdata, not instructionsretrieved documents

Run before the model — cheaper to stop bad input than to clean bad output.

1. Injection / jailbreak detection

import re

JAILBREAK_PATTERNS = [
    r"ignore\s+(all\s+)?(previous|above|prior)\s+(instructions|prompts)",
    r"disregard\s+(the\s+)?(system|above)",
    r"you\s+are\s+now\s+(?:a|an|in)\b",           # "you are now DAN / in developer mode"
    r"pretend\s+(you\s+are|to\s+be)",
    r"reveal\s+(your|the)\s+(system\s+)?(prompt|instructions)",
    r"\bDAN\b|developer\s+mode|jailbreak",
]

def scan_input(text: str) -> dict:
    hits = [p for p in JAILBREAK_PATTERNS if re.search(p, text, re.I)]
    return {"flagged": bool(hits), "patterns": hits}

Regex catches the obvious; it's a first layer, not a solution (attackers paraphrase/encode). Pair it with a small classifier and the provider's own safety. Defense in depth — never rely on one filter.

2. PII redaction (before the prompt)

Strip personal data so it never reaches a third-party model (also a privacy/compliance control).

PII = {
    "email": r"\b[\w.%+-]+@[\w.-]+\.\w{2,}\b",
    "phone": r"\b\d{3}[-.]?\d{3}[-.]?\d{4}\b",
    "ssn":   r"\b\d{3}-\d{2}-\d{4}\b",
    "card":  r"\b\d{4}[-\s]?\d{4}[-\s]?\d{4}[-\s]?\d{4}\b",
}
def redact(text: str) -> str:
    for tag, pat in PII.items():
        text = re.sub(pat, f"[{tag.upper()}]", text)
    return text   # production: add an NER model (e.g. Presidio) for names/addresses

3. Scope / topic filter

Keep a support bot on-topic; refuse medical/legal/financial advice if out of scope. A cheap classifier or keyword+embedding check on the input.

4. Separate instructions from data

Wrap untrusted input in explicit delimiters and tell the model everything inside is data, not instructions — and treat retrieved documents as untrusted too (indirect injection).

Output Guardrails

afterbeforecanary token

Run after the model, before the output reaches a user or triggers an action. This is the last line of defense — never serve raw model output in a sensitive app.

1. Content moderation

SAFETY_CATEGORIES = ["hate", "harassment", "violence", "self_harm", "sexual", "illegal"]

def moderate(text: str, classify) -> dict:
    """`classify` = a moderation model/API returning per-category scores 0–1."""
    scores = classify(text)
    violations = [c for c in SAFETY_CATEGORIES if scores.get(c, 0) > 0.5]
    return {"safe": not violations, "violations": violations, "scores": scores}

Use a dedicated moderation model/API (OpenAI Moderation, Llama Guard, Perspective API) rather than hand-rolled regex for toxicity.

2. PII / secret leak scan + canary

SECRETS = [r"(?:api[_-]?key|secret|password|token)\s*[:=]\s*\S+",
           r"sk-[A-Za-z0-9]{20,}", r"AKIA[0-9A-Z]{16}"]  # AWS key pattern

def output_safe(text: str, canary: str) -> dict:
    if canary and canary in text:
        return {"safe": False, "reason": "system_prompt_leak"}   # canary escaped → prompt leaked
    for pat in SECRETS + list(PII.values()):
        if re.search(pat, text, re.I):
            return {"safe": False, "reason": "pii_or_secret_leak"}
    return {"safe": True}

A canary token (a unique secret placed in the system prompt) that appears in output is proof the prompt leaked — a high-signal injection detector.

3. Schema / format validation

For structured output, validate against a schema (Pydantic) and never blindly execute generated commands/SQL/code. (See Production Scenarios Workflows Q9.)

4. Grounding / faithfulness guard

For RAG, gate on a faithfulness score so ungrounded claims are blocked or regenerated — see LLM Hallucination and Faithfulness.

The Guardrail Pipeline (putting it together)

Design principlesDefense in depthFail-closedblockLog every guardrail eventLeast privilege downstream 
def guarded_chat(user_input, context, llm, classify, canary):
    # ---- INPUT ----
    scan = scan_input(user_input)
    if scan["flagged"]:
        return refuse("That request can't be processed.")     # block, log, maybe step-up auth
    safe_input = redact(user_input)

    # ---- MODEL ----
    raw = llm(system=SYSTEM + f"\n[canary:{canary}]", context=context, user=safe_input)

    # ---- OUTPUT ----  (fail-closed: any check failing => don't serve raw)
    mod = moderate(raw, classify)
    leak = output_safe(raw, canary)
    if not mod["safe"] or not leak["safe"]:
        log_guardrail_event(mod, leak)
        return refuse("I can't help with that.")              # safe fallback, not the raw text

    return raw

Design principles: - Defense in depth — multiple imperfect layers; assume each can be bypassed alone. - Fail-closed — if a guardrail errors or is unsure, block (the safe default) rather than letting unchecked output through. (Trade off against over-refusal — see metrics.) - Guardrails are independent of the model — they still work if the model is swapped or jailbroken. - Log every guardrail event (what triggered, input/output references) for tuning and incident response. - Least privilege downstream — even a "safe" output shouldn't be able to execute arbitrary actions (file 10).

Over-Refusal: the other failure mode

Guardrails that are too aggressive refuse legitimate requests ("I can't discuss medication" to a pharmacy app), which destroys usefulness. Safety is a two-sided problem:

Too loose→harmful content slips throughfalse negatives
Too strict→blocks legitimate use, users leavefalse positives / over-refusal

Tune thresholds against both a harmful-content test set and a benign-but-tricky test set. Track false-positive (over-refusal) rate as a first-class metric, not just block rate.

You can't trust guardrails you haven't attacked. Build an adversarial suite and run it like a regression test (ties to LLM Eval Prompts and Finetuning).

def red_team(attacks, guarded_fn):

1. LLM Inference Optimization

Mental model — two phases of generation: 

PROMPT: "The capital of France is"   ──► [ PREFILL ]  one parallel forward pass over all prompt tokens
                                                         • compute-bound (big matmuls, GPU saturated)
                                                         • fills the KV cache for every prompt token
                                                         • determines TTFT (time-to-first-token)
                                              │
                                              ▼
OUTPUT:  " Paris" ► "." ► <eos>      ──► [ DECODE ]   one token at a time, autoregressively
                                                         • memory-bandwidth-bound (read whole cache each step)
                                                         • each step appends 1 token's K,V to the cache
                                                         • determines TPOT (time-per-output-token)

Key metrics: TTFT (prefill latency), TPOT / ITL (per-token decode latency), throughput (total tokens/s across all concurrent requests), and goodput (requests meeting an SLA). The headline insight interviewers want: decode is memory-bandwidth-bound, so the game is fitting more concurrent work in GPU memory and moving less data per step.

KV Cache

KeyValueMemory formula (this gets asked)Worked exampleGQA/MQAPagedAttention

During attention each past token's Key and Value are reused at every future step. Recomputing them is O(n²); caching them makes each new token O(n).

Memory formula (this gets asked): 

KV_bytes = 2 × n_layers × n_kv_heads × head_dim × seq_len × batch × dtype_bytes
           ^                                                              
           K and V

Worked example — Llama-2-13B-ish: layers=40, kv_heads=40, head_dim=128, seq_len=4096, batch=1, fp16(2B):

2 × 40 × 40 × 128 × 4096 × 1 × 2  ≈ 3.36 GB  for ONE sequence.

That's why the KV cache, not the weights, usually caps concurrency. Shrink it with: fewer KV heads (GQA/MQA, §4), quantized KV cache (FP8/INT8), shorter context, or PagedAttention (below) to stop wasting it.

# KV cache mechanics (single head, illustrative)
class KVCache:
    def __init__(self):
        self.K, self.V = None, None
    def append(self, k_new, v_new):           # k_new,v_new: (1, head_dim) for the new token
        self.K = k_new if self.K is None else np.vstack([self.K, k_new])
        self.V = v_new if self.V is None else np.vstack([self.V, v_new])
        return self.K, self.V                 # attention reads the full K,V each step

Speculative Decoding

drafttargetoneAcceptance ruleVariants

A small draft model proposes k tokens; the large target model verifies all k in one parallel pass. Accepted tokens are kept (the accept/reject rule makes the output distribution identical to sampling from the target); the first rejection is resampled from a corrected distribution.

draft (cheap):   proposes  "Paris is the capital"   (4 tokens, 4 cheap steps)
target (1 pass): verifies   ✓Paris ✓is ✓the ✗capital → keep 3, resample token 4
net: up to k tokens of the big model for ~1 big-model forward pass → 2–3× faster, same quality

Acceptance rule for token x with draft prob q(x), target prob p(x): accept with prob min(1, p(x)/q(x)); on reject, sample from normalized max(0, p−q). Works because verifying-in-parallel uses idle compute during the memory-bound decode phase. Variants: Medusa (extra heads, no separate model), EAGLE, n-gram/prompt-lookup (draft from the prompt).

Continuous Batching (in-flight / iteration-level)

staticContinuousevery decode step

Naive static batching runs a fixed batch to completion → short requests wait for the longest (head-of-line blocking, GPU idles). Continuous batching makes scheduling decisions every decode step: finished sequences are evicted, queued ones slotted in immediately.

static:      [R1████████][R2██][R3█████]   ← R2 done early but its slot idles until R1 finishes
continuous:  [R1████████]
             [R2██][R5███...]              ← R2 finishes, R5 takes its slot mid-flight
             [R3█████][R6██...]

Biggest real-world throughput win (often 5–20× over static). Used by vLLM, TGI.

•

Dynamic Batching

Server-side: wait a tiny window (a few ms) to group incoming requests into one batch, trading a little latency for throughput (classic Triton feature). Continuous batching is the LLM-specific, per-iteration evolution.

•

Prefix Caching

Many requests share a prefix (long system prompt, few-shot block, RAG context, chat history). Cache that prefix's KV once and reuse across requests/turns → skip re-prefill → lower TTFT and cost. vLLM hashes KV blocks to auto-detect reuse; providers expose it as "prompt caching."

•

Paged Attention (vLLM)

virtual-memory pagingblocksblock tablefragmentationcopy-on-write block sharing

Applies OS virtual-memory paging to the KV cache. The cache lives in fixed-size blocks (e.g. 16 tokens) that need not be contiguous; a per-sequence block table maps logical→physical blocks. - Kills fragmentation (naive contiguous allocation wastes 60–80% reserving max-length buffers). - Enables copy-on-write block sharing (shared prefixes, parallel samples of one prompt). Result: many more concurrent sequences per GPU → the core reason vLLM gets high throughput.

•

Flash Attention

ExactIO-awareSRAMnever materialize the N×N matrixonline-softmax

Exact (not approximate) attention that is IO-aware: tile Q/K/V, compute attention in fast on-chip SRAM, and never materialize the N×N matrix in slow HBM, using the online-softmax trick to stream tiles. - Memory O(N) instead of O(N²); fewer HBM round-trips → faster, especially long sequences. - FA-2 better work partitioning; FA-3 adds Hopper FP8. Same math, far less data movement.

# Online softmax — the trick that lets attention be computed in streaming tiles
# (combine partial softmaxes without ever seeing all scores at once)
def online_softmax_merge(m1, l1, o1, m2, l2, o2):
    m = max(m1, m2)                                  # running max (for numerical stability)
    l = np.exp(m1 - m) * l1 + np.exp(m2 - m) * l2    # running normalizer (sum of exp)
    o = (np.exp(m1 - m) * l1 * o1 + np.exp(m2 - m) * l2 * o2) / l   # running weighted output
    return m, l, o

Chunked Prefill

Split a long prompt's prefill into chunks and interleave them with ongoing decode steps in the same batch, so one giant prefill doesn't block (head-of-line) everyone's decode. Balances compute-bound prefill against memory-bound decode → smoother TPOT.

BM25 (sparse / lexical)

Bag-of-words ranking. Score of doc D for query Q:

BM25(Q,D) = Σ_term  IDF(term) · ( f · (k1+1) ) / ( f + k1·(1 - b + b·|D|/avgdl) )
   f      = term frequency in D
   |D|    = doc length, avgdl = average doc length
   k1≈1.5 (TF saturation), b≈0.75 (length normalization)
   IDF(t) = ln( (N - df + 0.5)/(df + 0.5) + 1 )      # df = # docs containing t, N = total docs

Great at exact keywords/IDs/codes/names that embeddings blur; no semantics/synonyms.

import math
from collections import Counter
def bm25_score(query, doc, corpus, k1=1.5, b=0.75):
    N = len(corpus)
    avgdl = sum(len(d) for d in corpus) / N
    tf = Counter(doc)
    score = 0.0
    for t in set(query):
        df = sum(1 for d in corpus if t in d)            # docs containing t
        if df == 0: continue
        idf = math.log((N - df + 0.5)/(df + 0.5) + 1)
        f = tf[t]
        score += idf * (f*(k1+1)) / (f + k1*(1 - b + b*len(doc)/avgdl))
    return score

Dense Retrieval

Embed query+docs into the same space; retrieve by vector similarity. Captures meaning/synonyms (query ≈ paraphrased passage even with no shared words). Weakness: can miss exact tokens/rare jargon; needs a retrieval-trained embedder.

Hybrid Search

Run dense + BM25 and fuse. Dense = meaning, BM25 = exact terms → beats either alone on enterprise data with codes/acronyms.

RRF (Reciprocal Rank Fusion)

Fuse ranked lists without comparable scores (BM25 and cosine live on different scales). Each list contributes 1/(k+rank) per doc (k≈60); sum; re-sort.

def rrf(rankings, k=60):                  # rankings: list of lists of doc_ids, each ranked best→worst
    scores = {}
    for ranked in rankings:
        for rank, doc in enumerate(ranked):     # rank starts at 0
            scores[doc] = scores.get(doc, 0) + 1/(k + rank + 1)
    return sorted(scores, key=scores.get, reverse=True)
# rrf([["A","B","C"], ["B","A","D"]]) → B and A bubble up (appear high in both lists)

MMR (Maximal Marginal Relevance)

relevancediversity

Re-rank to balance relevance vs diversity so context isn't five paraphrases of one fact:

MMR = argmax_{d ∉ S} [ λ·sim(d, query) − (1−λ)·max_{s∈S} sim(d, s) ]
def mmr(query_vec, doc_vecs, lam=0.7, k=5):
    selected, candidates = [], list(range(len(doc_vecs)))
    while len(selected) < k and candidates:
        best, best_score = None, -1e9
        for c in candidates:
            rel = cos(query_vec, doc_vecs[c])
            div = max([cos(doc_vecs[c], doc_vecs[s]) for s in selected], default=0)
            score = lam*rel - (1-lam)*div
            if score > best_score: best, best_score = c, score
        selected.append(best); candidates.remove(best)
    return selected

Similarity metrics (know all three)

import numpy as np
def cos(a, b): return np.dot(a, b) / (np.linalg.norm(a)*np.linalg.norm(b))  # angle, [-1,1]
def dot(a, b): return np.dot(a, b)                                          # angle × magnitude
def l2(a, b):  return np.linalg.norm(a - b)                                 # straight-line dist
  • Cosinemagnitude-invariant → direction = meaning; default for text.
  • Dot productcares about angle and magnitude; == cosine if vectors are L2-normalized (and faster → use inner-product indexes). Unnormalized, long vectors dominate.
  • Euclidean (L2)magnitude-sensitive; for normalized vectors L2 ranks identically to cosine (‖a−b‖² = 2 − 2cos).

Worked: a=[1,0], b=[0,1] → cos=0 (orthogonal, unrelated). a=[1,1], b=[2,2] → cos=1 (same direction) but dot=4, L2=√2 → cosine says "identical meaning," dot/L2 disagree because of magnitude. That's why text uses cosine.

ANN indexes

IVF (Inverted File)PQ (Product Quantization)IVFPQbillion-scaleScalar Quantization (SQ)

HNSW (Hierarchical Navigable Small World) — multi-layer proximity graph; greedy search descends sparse top layer → dense bottom. Fast, high recall, real-time. Cost: high memory (stores graph), awkward deletes. Knobs: M (edges/node), efConstruction, efSearch (recall↔speed).

Layer 2:   A ───────────── E          (few long-range links: coarse jumps)
Layer 1:   A ── C ──── E ── G
Layer 0:   A-B-C-D-E-F-G-H...          (all nodes, dense local links)
query: enter top, greedily hop to nearest, drop a layer, repeat → O(log N)-ish

IVF (Inverted File) — k-means partitions vectors into nlist cells (centroids); query searches only the nprobe nearest cells → sub-linear. Lower memory/faster build than HNSW; recall depends on nlist/nprobe; can miss vectors near cell borders. Needs a training step.

PQ (Product Quantization) — compress: split a vector into m sub-vectors, k-means each sub-space (256 centroids = 1 byte), store m centroid IDs. A 1536-d float32 vector (6 KB) → ~m bytes. Distances via precomputed lookup tables.

[───────── 128-dim vector ─────────]
 split → [s1][s2][s3][s4]                 (4 sub-vectors of 32-d)
 each sub-vec → nearest of 256 centroids → 1 byte
 stored as: [37][8][201][95]   ← 4 bytes instead of 512 bytes (128×fp32). 128× smaller.

IVFPQ — IVF (prune to few cells) + PQ (compress residuals in-cell) → the billion-scale workhorse (FAISS). Tune recall vs speed/memory via nprobe + PQ granularity.

Scalar Quantization (SQ) — per-dimension float32→int8 via min/max → ~4× smaller, fast, minimal recall loss; the simplest first compression step.

4. Transformer Architecture

Block: x → [MHA + residual + norm] → [FFN + residual + norm]. Tokens embedded + position-encoded, flow through N identical blocks, final linear+softmax predicts next token.

Self-Attention (from scratch)

Query, Key, ValueWorked (1-D, d_k=1)O(n²)

Each token makes Query, Key, Value (learned projections). It attends via softmax(QKᵀ/√d_k)·V: Q·K = relevance, ÷√d_k keeps softmax from saturating, softmax normalizes, weighted sum of V.

import numpy as np
def softmax(x, axis=-1):
    x = x - x.max(axis=axis, keepdims=True)          # numerical stability
    e = np.exp(x); return e / e.sum(axis=axis, keepdims=True)

def self_attention(X, Wq, Wk, Wv, causal=True):
    Q, K, V = X @ Wq, X @ Wk, X @ Wv                  # (seq, d_k)
    d_k = Q.shape[-1]
    scores = Q @ K.T / np.sqrt(d_k)                   # (seq, seq) relevance
    if causal:                                        # forbid attending to future tokens
        mask = np.triu(np.ones_like(scores), k=1).astype(bool)
        scores[mask] = -np.inf
    A = softmax(scores)                               # attention weights, rows sum to 1
    return A @ V                                      # (seq, d_k) context-mixed output

Worked (1-D, d_k=1): tokens with Q=K=[1,2,3]. scores/√1 → token3 vs others = [3,6,9]; softmax([3,6,9]) ≈ [0.002, 0.047, 0.95] → token 3 attends almost entirely to itself. Cost: O(n²) in seq len (every token scores every other).

Multi-Head Attention

MQAGQA

Run attention h times with different projections (each in a d/h subspace), concat, project. Heads specialize (syntax, coreference, position).

def multi_head(X, heads):                             # heads: list of (Wq,Wk,Wv)
    outs = [self_attention(X, *h) for h in heads]
    return np.concatenate(outs, axis=-1) @ Wo         # Wo: (d, d) output projection

Inference variants (KV-cache savers): MQA = all heads share ONE K/V; GQA = K/V shared per head-group (e.g. 8 query heads → 2 KV heads). Both shrink the KV cache (§1) with little quality loss → standard in modern LLMs (Llama-2-70B, Mistral).

Positional Encoding

RoPE (Rotary)relative

Attention is permutation-invariant → must inject order.

def sinusoidal(seq_len, d):                           # original Transformer
    pos = np.arange(seq_len)[:, None]
    i = np.arange(d)[None, :]
    angle = pos / np.power(10000, (2*(i//2))/d)
    pe = np.where(i % 2 == 0, np.sin(angle), np.cos(angle))
    return pe                                          # added to token embeddings

RoPE (Rotary) — rotate Q,K by an angle ∝ position. Because it acts on Q/K, the dot product depends on relative position; extends to longer contexts (interpolation/NTK/YaRN). Default in Llama/Qwen/Mistral.

def rope(x, pos, base=10000):                          # x: (d,) one token's Q or K vector
    d = len(x); out = x.copy()
    for k in range(0, d, 2):
        theta = pos / base**(k/d)
        c, s = np.cos(theta), np.sin(theta)
        out[k], out[k+1] = x[k]*c - x[k+1]*s, x[k]*s + x[k+1]*c   # rotate each 2-D pair
    return out

ALiBi — no position embeddings; add a distance-proportional negative bias to attention scores (closer favored), fixed per-head slope → cheap, extrapolates far beyond trained length.

•

Feed-Forward Network (FFN)

Per-token MLP, identical at each position; hidden ≈ 4× model dim. Where most params/"knowledge" live (attention mixes tokens, FFN processes each one). MoE replaces it with experts.

def ffn(x, W1, b1, W2, b2):
    h = np.maximum(0, x @ W1 + b1)    # GELU/SwiGLU in real models; ReLU shown
    return h @ W2 + b2
•

Layer Normalization

Pre-LNPost-LNRMSNorm

Normalize each token's vector (mean 0, var 1) then scale/shift → stabilizes/speeds training.

def layernorm(x, gamma, beta, eps=1e-5):
    mu = x.mean(-1, keepdims=True); var = x.var(-1, keepdims=True)
    return gamma * (x - mu)/np.sqrt(var + eps) + beta

Pre-LN (norm before sub-layer; modern default) > Post-LN for stability. RMSNorm (scale by RMS only, no mean-centering) is the cheaper Llama-era variant.

•

Residual (Skip) Connections

x + Sublayer(x) → gradients get a direct path (no vanishing), each layer learns a refinement. With LayerNorm, the backbone of trainable deep stacks.

7. Fine-Tuning

When: RAG injects knowledge; fine-tuning bakes in behavior/style/format/skill or domain adaptation. Often combine (FT for format, RAG for facts).

•

LoRA (Low-Rank Adaptation)

low-rank<1%hot-swappable

Freeze base W₀; add a trainable low-rank delta ΔW = B·A (rank r ≈ 8–64) → output W₀x + BAx. Train <1% of params → less memory, tiny checkpoints (MBs), hot-swappable adapters; merge BA into W₀ at inference for zero added latency.

W₀ : (d × d)  frozen                A : (r × d) trainable   ┐
                                    B : (d × r) trainable   ┘  r ≪ d  →  B·A ≈ low-rank ΔW
forward:  h = W₀x + (B·A)x · (α/r)        # α = scaling
class LoRALinear:
    def __init__(self, W0, r=8, alpha=16):
        d_out, d_in = W0.shape
        self.W0 = W0                                   # frozen
        self.A = np.random.randn(r, d_in) * 0.01       # trainable
        self.B = np.zeros((d_out, r))                  # trainable (init 0 → ΔW=0 at start)
        self.scale = alpha / r
    def __call__(self, x):
        return x @ self.W0.T + (x @ self.A.T @ self.B.T) * self.scale

2. Reward Model: humans rank responses → RM learns to score "better"

Skip the reward model + RL loop. Directly optimize on (chosen, rejected) pairs with a classification-style loss that raises chosen's relative likelihood (implicit KL):

L_DPO = −log σ( β·[ logπ(y_chosen|x) − logπ_ref(y_chosen|x) ]
                 − β·[ logπ(y_rejected|x) − logπ_ref(y_rejected|x) ] )

Simpler, stabler, cheaper than PPO → a default. Cousins: IPO, KTO, ORPO.

•

8. LLM Evaluation

Why: pick the cheapest model meeting quality; catch regressions on model/prompt swaps. Keep a labeled gold set.

•

Reference-based metrics

BLEUprecisionROUGErecallBERTScorecontextual-embedding cosine

BLEU — n-gram precision + brevity penalty (from MT). Surface overlap, penalizes valid paraphrases.

BLEU = BP · exp( Σ_n w_n · log p_n )      p_n = clipped n-gram precision, BP = brevity penalty

ROUGE — recall-oriented n-gram overlap (from summarization). ROUGE-N (n-gram recall), ROUGE-L (longest common subsequence). Like BLEU, lexical/surface — blind to paraphrase.

def rouge_n(pred, ref, n=1):
    def ngrams(s): return Counter(tuple(s[i:i+n]) for i in range(len(s)-n+1))
    p, r = ngrams(pred), ngrams(ref)
    overlap = sum((p & r).values())
    return overlap / max(sum(r.values()), 1)         # recall

BERTScore — match pred/ref tokens by contextual-embedding cosine (greedy) → P/R/F1. Captures semantics/paraphrase BLEU/ROUGE miss; needs a reference + an encoder.

Exact Match (EM) — output == reference after normalization; strict; closed-form QA/classification/extraction. Pair with token-level F1 for partial credit.

•

Generation-quality metrics

Hallucination DetectionLLM-as-judgeself-consistencyFaithfulnessprovided contextRelevance

Hallucination Detection — content not supported by source/facts. Methods: NLI/entailment vs source, LLM-as-judge support checks, self-consistency (sample N; disagreement → likely fabricated, e.g. SelfCheckGPT), retrieval-verification vs trusted KB.

Faithfulness — does every claim follow from the provided context? Core RAG-generation metric (decompose → check each claim supported). ≠ correctness (faithful to wrong context = still wrong). RAGAS measures it.

Relevance — answer relevance (addresses the question, not off-topic/padded) and context relevance/precision (were retrieved chunks pertinent?). Separating them localizes retrieval-vs-generation failures.

Groundedness — near-synonym of faithfulness: output anchored in / attributable to evidence. Often enforced with citations + verified by judge/NLI.

•

Judge & human

LLM-as-a-JudgerubricBiases to controlHuman EvaluationEval-loop talking pointssame

LLM-as-a-Judge — strong LLM scores against a rubric or picks the better of two. Scales to open-ended tasks; decent human correlation. Biases to control: position (randomize order), verbosity (longer ≠ better), self-preference (own family), inconsistency (temp 0, clear rubric). Spot-check vs human labels.

Human Evaluation — gold standard: pairwise preference (→ Elo, Chatbot Arena), Likert, expert review. Expensive/slow; needs guidelines + inter-annotator agreement. Reserve for final validation + calibrating judges.

Eval-loop talking points: representative labeled set of your prompts; metrics by task type (EM/F1 closed, judge/RAGAS open); compare candidates on the same set tracking quality × latency (p50/p95) × cost; version everything; standard benchmarks (MMLU, GSM8K, HumanEval, MT-Bench) are signals but contaminable — your task eval matters more.

Quantization math (gets asked)

PTQQATGPTQsecond-order (Hessian)AWQ (Activation-aware)salient weight channels

Map float → int with a scale (and zero-point for asymmetric):

scale = (max - min) / (2^bits - 1)
q     = round(x / scale) + zero_point        # to int
x̂     = (q - zero_point) * scale             # dequant (lossy)

Worked (INT8 symmetric, weights in [-0.4, 0.4]): scale = 0.8/255 ≈ 0.00314. Weight 0.27 → round(0.27/0.00314)=86 → dequant 86×0.00314 ≈ 0.270. Error ≈ 0.0003. INT8 ≈ 4× smaller than FP32, 2× vs FP16; INT4 ≈ 8× vs FP32.

def quantize_int8(w):
    scale = np.abs(w).max() / 127
    q = np.round(w / scale).astype(np.int8)
    return q, scale
def dequantize(q, scale): return q.astype(np.float32) * scale
  • PTQ (post-training, no retrain — GPTQ/AWQ): cheap, common. QAT (quantization-aware training): simulate quant in training → best accuracy at very low bits.

GPTQ — layer-wise PTQ using approximate second-order (Hessian) info to quantize weights column-by-column while minimizing output error. Accurate to 3–4 bits; slower to produce; weight-only. AWQ (Activation-aware) — protect the ~1% salient weight channels (high-magnitude activations) by scaling, quantize the rest aggressively to 4-bit. Strong accuracy, fast kernels, no backprop. Weight-only. SmoothQuant — enables W8A8 (8-bit weights and activations) by migrating activation-outlier difficulty into weights via a per-channel scale (math-equivalent) → accurate full-INT8, unlocks integer tensor cores. INT8 / INT4 — INT8 near-lossless with outlier handling (LLM.int8() keeps outlier channels FP16); INT4 needs GPTQ/AWQ/NF4, activations usually higher precision (weight-only) → the sweet spot for local/consumer-GPU LLMs.

Mixture of Experts (MoE)

expertsrouter/gatetop-ksparse activationload balancingexpert-parallel

Replace the dense FFN with many experts + a router/gate sending each token to its top-k (e.g. 2 of 8). Only those fire → sparse activation: huge total params, low per-token compute (Mixtral, DeepSeek).

def moe_layer(x, router, experts, k=2):
    logits = router(x)                            # (n_experts,)
    idx = np.argsort(logits)[-k:]                 # top-k experts
    w = softmax(logits[idx])
    return sum(w[i] * experts[e](x) for i, e in enumerate(idx))

Challenges: load balancing (auxiliary loss so experts get even traffic), routing instability, memory to hold all experts, expert-parallel serving (§1). More capacity per FLOP.

Sliding Window Attention

Each token attends only to the last W tokens → cost O(n·W) not O(n²) + bounded KV cache. Stacking layers grows the effective receptive field (CNN-like). Mistral/Longformer; pair with a few global tokens for long-range info.

Decoding / sampling (full code)

def softmax(z, T=1.0):
    z = np.array(z)/T; z -= z.max(); e = np.exp(z); return e/e.sum()

def greedy(logits):                 # argmax — deterministic, myopic, can loop
    return int(np.argmax(logits))

def sample_temperature(logits, T):  # T<1 sharper/factual, T>1 flatter/creative
    return np.random.choice(len(logits), p=softmax(logits, T))

def top_k(logits, k, T=1.0):        # keep k highest, renormalize, sample (fixed count)
    idx = np.argsort(logits)[-k:]
    p = softmax(np.array(logits)[idx], T)
    return int(np.random.choice(idx, p=p))

def top_p(logits, p_thresh, T=1.0): # nucleus: smallest set with cumprob ≥ p (adaptive)
    p = softmax(logits, T)
    order = np.argsort(p)[::-1]
    cum = np.cumsum(p[order])
    keep = order[:np.searchsorted(cum, p_thresh)+1]
    pk = p[keep]/p[keep].sum()
    return int(np.random.choice(keep, p=pk))
  • Temperature scales logits before softmax → reshapes the whole distribution. ~0 for extraction/code/RAG; 0.7–1.0 creative. (T=0 ≈ greedy; not perfectly deterministic in practice due to HW/batching.)
  • Top-k = fixed count; Top-p (nucleus) = adaptive (few tokens when confident, many when uncertain) → generally preferred. Tune temperature OR top-p, not both hard.
  • Greedy = argmax (fast, repetition-prone). Beam search = keep b best sequences each step → higher-likelihood overall → good for deterministic tasks (translation/summarization) but bland/repetitive for open-ended chat; b× compute.
  • Stop Sequencesstrings that halt generation ("\n\n", </answer>, turn delimiter) → control boundaries, stop rambling/hallucinating next turn. With max_tokens.
  • Logitsraw un-normalized vocab scores (pre-softmax). Sampling controls (temp, top-k/p, repetition penalty, logit bias, grammars) operate here. logprobs (log of softmaxed logits) expose confidence for analysis/eval.

Tokenization

SubwordBPE (Byte-Pair Encoding)Byte-level BPESentencePiecelibrary/algorithmUnigram LM

Text ↔ integer token IDs. Subword units balance vocab size vs rare-word handling (no OOV). ~4 chars/token English; non-English/code cost more tokens. Token count drives context limits + cost; tokenizer mismatch breaks models.

BPE (Byte-Pair Encoding) — start from chars/bytes; greedily merge the most frequent adjacent pair repeatedly → subword vocab. Byte-level BPE (GPT) works on bytes → never true OOV. Most common LLM tokenizer.

def bpe_train(words, n_merges):                 # words: list of (char_tuple, count)
    merges = []
    for _ in range(n_merges):
        pairs = Counter()
        for w, c in words:
            for i in range(len(w)-1): pairs[(w[i], w[i+1])] += c
        if not pairs: break
        best = max(pairs, key=pairs.get)        # most frequent adjacent pair
        merges.append(best)
        words = [(merge_pair(w, best), c) for w, c in words]   # replace pair with merged token
    return merges

SentencePiece — tokenizer library/algorithm (BPE + Unigram LM), language-agnostic: treats input as raw Unicode (spaces → ▁), no pre-tokenization/whitespace assumptions → any language/script. Used by T5, Llama, multilingual models.

14. Production & MLOps

LLM apps fail silently on quality → invest early in eval sets + monitoring + tracing + versioning.

Model Monitoring — operational (latency p50/p95/p99, throughput, error rate, GPU/cost, tokens) and quality (sampled LLM-judge/human, hallucination/refusal rates, 👍/👎 feedback, drift in inputs/outputs/embeddings). LLM-specific: prompt/response logging, toxicity/PII flags, tool-call success.

Prompt Versioning — prompts are versioned artifacts (git/registry), tied to eval results, enabling rollback + A/B + per-response provenance. A one-word change swings behavior. Tools: LangSmith, PromptLayer.

Embedding Versioning — track which embedding model+version made each vector. Changing it means re-embed the whole corpus (old/new not comparable) + reindex → plan migrations (dual-write/backfill); store model version as metadata. A silent swap corrupts retrieval.

Vector DB Updates — keep the index fresh: incremental upsert/delete by doc ID, handle re-chunking, avoid stale/duplicate vectors, manage rebuilds (HNSW deletes are soft → periodic compaction), version the corpus. CDC on sources → re-embed changed → upsert. Freshness vs reindex cost.

A/B Testing — split live traffic, measure business/quality metrics (resolution rate, CSAT, latency, cost) with significance. Canary/shadow first; watch novelty effects + guardrail metrics. The only proof a change helps real users.

Guardrails — programmable input + output controls: input (prompt-injection/jailbreak detection, topic limits, PII scrubbing), output (toxicity, PII leakage, groundedness/format/schema validation, blocklists), + action restrictions for agents. NeMo Guardrails, Guardrails AI, Llama Guard, provider moderation. Fail safe (block/escalate).

PII Masking — detect (regex for email/phone/SSN/cards + NER/ML like Presidio for names/addresses) → redact/pseudonymize before the LLM, logs, telemetry. Placeholders (<EMAIL>), reversible tokenization (re-insert in final answer), or drop. Required for GDPR/HIPAA.

Content Moderation — filter harmful content (hate, violence, self-harm, sexual, illegal) on input + output via moderation endpoints/classifiers (Llama Guard, OpenAI Moderation); define policy, thresholds, action (block/redact/escalate/safe-complete).

Observability — end-to-end tracing of every step (prompt → retrieval → tool calls → generation) with inputs/outputs/tokens/latency/cost + structured logs + replay of a specific bad response. LLM apps are non-deterministic multi-step → tracing is essential. Tools: LangSmith, Langfuse, Arize Phoenix, OpenTelemetry.

LangSmith — LangChain's observability + eval: traces chains/agents, captures prod datasets, runs evals (LLM-judge/custom), manages + versions prompts, A/B + regression testing. (Works standalone too.)

MLflow — ML lifecycle: experiment tracking (params/metrics/artifacts), model registry (versioning, stage transitions, lineage), packaging/reproducibility, deployment, + LLM features (prompt tracking, eval, tracing). The classic MLOps backbone.

§14 gold: invest in eval sets + monitoring + tracing + versioning (prompt/model/embedding) from day one; ship behind A/B/canary; layer guardrails/PII/moderation on input and output; keep a rollback path for prompts/models/indexes; track cost/request as a first-class metric.

15. One-page rapid-fire
  • Prefill vs decode? Prefill = parallel, compute-bound, fills KV cache (TTFT); decode = sequential, memory-bandwidth-bound (TPOT).
  • Biggest serving wins? Continuous batching + PagedAttention; then prefix caching, quantization, speculative decoding.
  • KV cache size driver? 2·layers·kv_heads·head_dim·seq·batch·dtype; it caps concurrency, not weights. Shrink via GQA/MQA + KV quant + paging.
  • Speculative decoding correctness? Accept/reject rule makes output distribution identical to the target model.
  • RAG vs fine-tuning? RAG = knowledge (fresh, citable, cheap); FT = behavior/style/format. Combine.
  • Hybrid search? Dense (meaning) + BM25 (exact terms) fused by RRF; rerank top-k with a cross-encoder.
  • Cosine vs dot vs L2? Cosine = direction (text default); == dot if normalized; L2 ranks same as cosine when normalized.
  • HNSW vs IVFPQ? HNSW = fast/high-recall/memory-heavy; IVFPQ = compressed, billion-scale, tunable recall.
  • Why positional encodings? Attention is order-agnostic; RoPE (rotate Q/K, relative, extends) + ALiBi (distance bias, extrapolates) dominate.
  • GQA/MQA? Share K/V across heads/groups → smaller KV cache, little quality loss.
  • Decoder-only? Causal-masked next-token — the modern generative LLM.
  • LoRA vs QLoRA? LoRA = low-rank deltas on frozen weights (<1% params, swappable); QLoRA = LoRA on 4-bit base → big models on one GPU.
  • DPO vs RLHF? DPO = direct preference classification loss, no reward model/PPO; simpler/stabler.
  • Top-k vs top-p? k = fixed count; p (nucleus) = adaptive cumulative-prob set (preferred). Tune temperature OR top-p.
  • MoE? Sparse top-k experts → huge params, low per-token compute; needs load balancing + expert parallelism.
  • GIL? One thread runs Python bytecode at a time → threads for I/O, multiprocessing/asyncio otherwise.
  • BF16 vs FP16? BF16 = FP32 exponent range (stable, no loss scaling); FP16 = more precision, needs loss scaling.
  • PTQ vs QAT? PTQ = quantize after training (GPTQ/AWQ, cheap); QAT = simulate quant during training (best at low bits).
  • Multi-tenant RAG leak? Always pre-filter by tenant metadata (or separate indexes); enforce access control per query.
  • Reduce hallucination? RAG grounding + citations, "say I don't know", low temp, self-consistency, faithfulness evals.
  • Cut cost/latency? Smaller model + routing/cascade, prompt/semantic caching, shorter context, streaming, quantization, speculative decoding.
  • Eval a RAG system? Split: retrieval (recall@k, MRR, hit-rate) + generation (faithfulness, answer relevance, context precision/recall — RAGAS).
  • RabbitMQ vs Kafka? RabbitMQ = task queue + rich routing; Kafka = durable replayable event log for streaming at scale.

Production Issue #29: Model Deprecation, Version Drift & Provider Migration

Scope: what happens when the model underneath your product changes or disappears — deprecation notices, silent alias upgrades, prompt portability, structured-output and tokenizer differences, embedding-model retirement (the expensive one), multi-provider fallback routing, quota/rate-limit changes, and the eval-gated migration playbook.

Overview

One-sentence idea: In classic ML you own the model — it sits in your registry and runs until you replace it. With a hosted LLM you are renting a dependency that expires, and the vendor sets the date.

Everything else in this folder assumes the model is a constant and something around it broke. This file is the case where the constant moves. It's the most common "surprise" incident in LLM products and almost nobody prepares for it, which is exactly why it's a good interview question.

The Failure Modes

DetectionNobody reads theseThe fix is one line and one habitlog the model ID the API returnedchatembedding

1. Pinned model retired — the forced march

You did the right thing and pinned a snapshot. Eighteen months later you get a 90-day notice. Now you must migrate a system whose prompts were tuned against behaviour that is about to cease to exist, with a hard deadline and no rollback.

Detection: vendor deprecation feed, Deprecation/Sunset HTTP headers, console warnings, release notes. Nobody reads these, which is why this needs to be an automated monitor, not a habit.

2. Floating alias silently upgraded — the invisible incident

Monday:    "…-latest" → snapshot-2026-03-11    JSON parse failures: 0.4%
Tuesday:   "…-latest" → snapshot-2026-06-02    JSON parse failures: 7.1%   ← no deploy of yours

Your on-call sees an error-rate spike with an empty change log and burns two hours before someone thinks to check the model. This is the single most common version incident.

The fix is one line and one habit: pin snapshots in production, and log the model ID the API returned, not the one you sent. They are not always the same, and the returned value is the only ground truth.

3. Prompt regression — prompts don't transfer

Prompts are fitted to a model the way hyperparameters are fitted to a dataset. Moving models breaks:

What breaks Typical symptom
Few-shot count/order sensitivity Accuracy drops on the same examples
"Think step by step" scaffolding A reasoning model does it natively; your CoT instruction now makes it over-think and inflates cost
Output-format instructions New model wraps JSON in ```json fences, or adds a preamble your parser doesn't expect
Refusal boundaries Newer, safer model refuses legitimate domain requests (medical, financial, security)
Verbosity/tone Answers get 40% longer → cost and latency rise with no quality gain
System-prompt adherence Different weighting of system vs user messages changes persona stability

4. Structured output & tool-calling differences

The highest-risk surface, because it fails hard and often in code paths you don't cover:

  • Strict JSON-schema mode support varies by model and version.
  • Parallel tool calls: some models emit several per turn, some one — an agent loop written for one shape breaks on the other.
  • Tool-argument fidelity differs (optional fields omitted vs null, numbers as strings).
  • Max tool count and schema-depth limits differ.
  • Reasoning models interleave thinking blocks that a naive response.content[0].text parser will read as the answer.

5. Tokenizer & pricing changes

A different tokenizer means the same text is a different token count. Your context budget math, truncation thresholds, and cost forecast are all silently wrong.

Illustrative: 3,000-word document, two tokenizers
  Model A: 4,010 tokens   → fits your 4,096 truncation guard
  Model B: 4,380 tokens   → truncated at 4,096; the last 284 tokens (the conclusion) vanish
                            → answers quietly degrade, zero errors raised

Silent truncation is the worst class of migration bug: no exception, no alert, just worse answers.

6. Embedding-model deprecation — the expensive one

Deprecating a chat model costs you prompt work. Deprecating an embedding model costs you a full re-index of the corpus — and you cannot mix vector spaces.

The rule to say out loud: vectors from two different embedding models are not comparable. There is no partial migration, no "re-embed the new documents only." It's all or nothing, per index.

Illustrative cost, 5M chunks @ 400 tokens:
  re-embed:  5M × 400 = 2.0B tokens × $0.02/1M   ≈ $40   (cheap!)
  the real cost:  index rebuild + dual-storage during cutover
                  + re-tuning score thresholds   ← the part teams forget

That last item bites: your score_threshold = 0.78 abstain guard was calibrated on the old model's similarity distribution. On the new model 0.78 may mean something completely different, so your no-context guard either fires constantly or never fires.

7. Fine-tuned models die with their base

Your fine-tune is a set of weights on top of a base model. Base retired → your fine-tune is retired. You need the training data, the recipe, and the eval harness preserved and re-runnable, or the asset is simply gone.

Store, forever, in version control: training data snapshot + hyperparameters + base model ID + eval results. If you can't re-create the fine-tune in a day, you don't own it.

8. Quota, rate limits & regional availability

New model, new rate-limit tier — often lower at launch while capacity is constrained. A migration that passes every quality gate can still fail on day one because the new model's TPM ceiling is a third of the old one's. Also: launch-region restrictions can break data-residency commitments you've made to customers.

9. Provider outage → the fallback you never tested

Everyone plans a fallback provider. Almost nobody keeps the fallback's prompts current. Six months later the primary goes down, the fallback engages, and it's running a prompt tuned for a model that was replaced twice — a worse outage than a clean 503.

Step 2 — One abstraction layer

The goal: swapping providers is a config change, not a refactor. Keep provider objects from leaking into business logic.

The 80% win is normalising tool_calls. Text is easy to abstract; tool-call and structured-output shapes are where provider differences actually live, and where a migration silently breaks an agent loop.

Step 3 — Golden set + eval harness

You cannot migrate safely without a frozen, representative test set. Build it before you need it.

Golden set composition (aim 200–1,000 cases):
  60%  representative production traffic (sampled across intents, sanitised)
  20%  known-hard cases — the ones that caused past incidents
  10%  edge/adversarial — injection attempts, empty context, non-English, huge inputs
  10%  format/contract cases — must produce valid JSON / correct tool call

Score every case on the same metrics, old model vs new:

Metric Gate
Task accuracy / LLM-judge win-rate vs old model ≥ parity (report with position randomised)
Valid-JSON / schema-compliance rate ≥ old, and ≥ 99.5% absolute
Tool-selection accuracy ≥ old
Refusal rate on legitimate requests ≤ old
p95 latency within budget
Cost per request within budget
Mean output tokens flag Δ > 20% (verbosity creep)

No traffic moves until every gate is green. That's what "eval-gated" means, and it's the phrase to use in an interview.

Step 4 — Shadow, then canary

  1. SHADOW Replay production traffic to the new model. Compare offline. Zero user risk. Catches format/parse breakage immediately.
  2. RE-TUNE Fix prompts against the new model. Expect real work here — prompts are model-specific artifacts, not portable config.
  3. CANARY 1% → 5% → 25% → 50% → 100%, with a bake at each step. Watch: parse failures, refusals, latency, cost, output length, and the actual product metric (deflection, CSAT, conversion).
  4. KILL SWITCH A runtime flag that reverts routing without a deploy. Test it during the canary — an untested rollback is not a rollback.
  5. DECOMMISSION Remove the old path only AFTER the retirement date passes cleanly.

Keep both prompt versions live during canary. summarise@v7 (old model) and summarise@v8 (new model) run side by side, selected by which model the request routed to. Rolling back the model without rolling back the prompt is how canaries turn into incidents.

Step 6 — Fallback routing (and its trap)

import time

class ModelRouter:
    """Primary → fallback with a circuit breaker. Note what's attached to each entry."""
    def __init__(self, chain):
        self.chain = chain                 # [{"provider":…, "model":…, "prompt":…}, …]
        self.failures, self.opened_at = {}, {}

    def _open(self, key, threshold=5, cooldown=60):
        if self.failures.get(key, 0) < threshold:
            return False
        if time.time() - self.opened_at.get(key, 0) > cooldown:
            self.failures[key] = 0          # half-open: let one through to probe
            return False
        return True

    def complete(self, **kw):
        last = None
        for entry in self.chain:
            key = f'{entry["provider"]}:{entry["model"]}'
            if self._open(key):
                continue                                       # skip a known-dead provider fast
            try:
                # the prompt travels WITH the model — this is the whole point
                out = call(entry["provider"], entry["model"], PROMPTS[entry["prompt"]], **kw)
                self.failures[key] = 0
                return out
            except (RateLimitError, APIError, TimeoutError) as e:
                self.failures[key] = self.failures.get(key, 0) + 1
                self.opened_at[key] = time.time()
                log.warning("provider_failover", extra={"from": key, "error": str(e)})
                last = e
        raise AllProvidersFailed(last)

The trap: a fallback path that never carries traffic is a path that rots. Force 1% of traffic through the fallback continuously, and include the fallback in the golden-set eval every release. An untested fallback is a second outage waiting inside your first one.

Step 7 — Quota and rate limits

  • Check the new model's TPM/RPM tier before the canary, not during it. New models frequently launch at lower limits.
  • Request a quota increase at Step 0 — approval takes days.
  • Implement token-bucket client-side limiting + backoff-with-jitter so you degrade rather than storm. See LangChain Failure Handling.
  • Verify regional availability against your data-residency commitments.

Q1. Your provider announces the model you built on retires in 90 days. Walk me through it.

First, inventory — I'd grep for every hardcoded model ID, because it's never in one place, and I'd list every prompt, fine-tune, and index tied to that model. In parallel I'd request a quota increase for the successor, since approval takes days and it's free to ask early. Then the actual gate: assemble a golden set of a few hundred cases — mostly sampled production traffic, plus the known-hard cases from past incidents, plus adversarial and contract cases — and baseline the old model on it first, because I need the incumbent's numbers to compare against and after retirement I can never get them again. Shadow-replay traffic to the new model, compare offline, and expect to re-tune prompts, because prompts are fitted to a model, not portable config. Once every gate is green — accuracy, schema-compliance, refusal rate, latency, cost, and output length — canary at 1/5/25/100% with a kill switch I've actually tested. Old path comes out only after the retirement date passes uneventfully. And the meta-answer: I'd rather not be in this position, so going forward production pins snapshots and staging runs a nightly eval against the floating alias — that way I meet the next model on my schedule, not the vendor's.

Q2. Error rate spiked overnight. No deploy went out. Where do you look?

If nothing on my side changed, something on the vendor's side did. First check: was I using a floating alias? If so it's almost certainly been re-pointed to a new snapshot. That's why I log the model field the API returns, not the one I sent — it's the only ground truth, and an alert on model_served != model_requested turns this from a two-hour hunt into a page with the answer in it. I'd confirm by diffing today's outputs against yesterday's on a handful of replayed requests, then look at the shape of the failure: a jump in JSON-parse failures or tool-call errors points at structured-output changes; a jump in output length points at a verbosity change that's also inflating my bill; a jump in refusals points at shifted safety boundaries. Immediate mitigation is to pin to the previous snapshot if it's still available, which buys time to migrate properly. If it isn't, the kill switch routes to the fallback provider while I re-tune.

Q3. Why is deprecating an embedding model worse than deprecating a chat model?

Because vectors from two different embedding models aren't comparable — they live in different spaces. A chat-model migration is prompt work; an embedding migration is a full corpus re-index, and there's no partial path. You can't embed just the new documents with the new model, because then half your index is unsearchable relative to the other half. The compute cost is usually trivial — a few million chunks is tens of dollars — but the operational cost isn't: you need dual-write to old and new indexes, an off-peak backfill, storage for both simultaneously, and a gradual read cutover. And the step everyone forgets is re-calibrating thresholds: score cutoffs, top_k, and any abstain guard were tuned on the old model's similarity distribution, so after cutover the same numeric threshold means something different and your no-context guard either fires constantly or never fires. I'd also store the embedding model ID as metadata on the index itself, so it's impossible to accidentally query a v1 index with a v2 vector.

Q4. Pinned versions or floating "latest" in production?

Pinned, always. A floating alias trades a scheduled, controlled migration for an unscheduled, unattributable incident — and the incident always arrives at the worst time, with no change log to correlate against. The objection is that pinning means you carry migration debt and eventually get a deadline. That's true, and the answer isn't to float; it's to run the floating alias in staging on a nightly golden-set eval. You get early warning of what the next model does to your system, on your own schedule, without exposing users. By the time the deprecation notice arrives you already know your gaps. Floating is fine for prototypes and internal tools where a bad day costs nothing.

Q5. How do you build for provider portability without over-engineering?

One thin abstraction, and I'd be honest that most of its value is in one place. Business logic refers to logical names — "summariser", "router", "extractor" — and a config table maps each to a provider, a physical model ID, and a prompt version. The interface returns a normalised response object. The part that actually earns the abstraction is normalising tool calls and structured output, because plain text is easy to paper over and tool-call shapes are where provider differences really live — parallel vs single calls, optional fields as null vs omitted, reasoning blocks interleaved with content. What I would not do is build a full framework abstracting every provider feature; you end up with a lowest-common-denominator API that blocks you from using the thing you switched providers for. And I'd make sure the fallback path carries about 1% of live traffic permanently — an untested failover with a stale prompt is a second outage hiding inside the first one.

Q6. What migrates worse than you'd expect?

Three things. Prompts — teams treat them as portable config, but they're fitted artifacts. Scaffolding you added to work around one model's weakness ("think step by step", "respond only in JSON") can actively hurt on a model that doesn't have that weakness; migration often means deleting instructions. Tokenizers — the same text is a different token count, so context budgets and truncation thresholds silently shift, and silent truncation is the worst bug class because it raises no error and just quietly drops your document's conclusion. Fine-tunes — they're weights on a base model, so when the base retires, your fine-tune retires with it. That means the training data, hyperparameters, base model ID, and eval harness have to be reproducible from source control, or the asset is simply gone. If I can't re-create a fine-tune in a day, I don't own it — I'm renting it too.
