1. RAG Fundamentals

Retrieval-Augmented Generation (RAG) is an architecture that enhances LLM responses by retrieving relevant documents from an external knowledge base and injecting them as context before generation. RAG reduces hallucination, enables access to up-to-date and domain-specific information, and provides verifiable answers with source citations — all without retraining the model.

RETRIEVAL-AUGMENTED GENERATION:
  Instead of relying on the LLM's training data alone,
  RETRIEVE relevant documents from external knowledge
  and AUGMENT the prompt with that context before GENERATING.

  ┌──────┐    ┌───────────┐    ┌──────────┐    ┌──────────┐
  │ Query│───→│ Retriever │───→│ Context  │───→│ LLM      │
  └──────┘    │(VectorDB) │    │ + Query  │    │ Answer   │
              └───────────┘    └──────────┘    └──────────┘

  WHY RAG?
  - Access to up-to-date information (training data has a cutoff)
  - Grounded in source documents (reduces hallucination)
  - No model retraining needed (just update the knowledge base)
  - Domain-specific knowledge without fine-tuning cost
  - Verifiable answers with source citations
2. RAG vs Fine-Tuning vs Prompting

Choosing between prompting, RAG, and fine-tuning depends on whether you need to change what the model knows or how it behaves. Prompting is the simplest approach for general tasks, RAG injects external knowledge at query time, and fine-tuning adapts the model's behavior or reasoning style — these methods are complementary and can be combined.

DECISION MATRIX:
  Approach       │ When to Use                     │ Cost    │ Latency
  ───────────────┼─────────────────────────────────┼─────────┼────────
  Prompting      │ Simple tasks, general knowledge │ Low     │ Low
  RAG            │ Domain docs, current data,      │ Medium  │ Medium
                 │ need citations, data changes    │         │
  Fine-Tuning    │ Style/format adaptation,        │ High    │ Low
                 │ specialized reasoning           │         │
  RAG + FT       │ Both domain knowledge AND       │ Highest │ Medium
                 │ specialized behavior needed     │         │

  RULES OF THUMB:
  - Start with prompting → try RAG → fine-tune as last resort
  - RAG for "what the model KNOWS" → inject knowledge
  - Fine-tuning for "how the model BEHAVES" → change behavior
  - They're complementary, not competing approaches
3. Embeddings

Embeddings are dense vector representations of text that capture semantic meaning, enabling similarity-based retrieval by mapping queries and documents into a shared vector space. The choice of embedding model (OpenAI, open-source like BGE or MiniLM) directly affects retrieval quality, latency, and cost.

from langchain_openai import OpenAIEmbeddings
from sentence_transformers import SentenceTransformer

# ── OpenAI embeddings ────────────────────────────────────
embeddings = OpenAIEmbeddings(model="text-embedding-3-small")  # 1536 dims
# text-embedding-3-large: 3072 dims, better quality, higher cost

# ── Open-source embeddings ───────────────────────────────
model = SentenceTransformer("all-MiniLM-L6-v2")  # 384 dims, very fast
# BAAI/bge-large-en-v1.5: 1024 dims, competitive quality
# nomic-ai/nomic-embed-text-v1.5: 768 dims, good quality/speed
# Alibaba-NLP/gte-large-en-v1.5: 1024 dims, MTEB leaderboard top

vectors = model.encode(["Hello world", "AI is amazing"])  # (2, 384)

4. Chunking Strategies

Definition: Chunking is the process of splitting large documents into smaller, semantically meaningful segments that fit within embedding model token limits and enable precise retrieval. The chunking strategy and parameters (size, overlap) directly impact retrieval quality — too small loses context, too large dilutes relevance.

4.1.1 Fixed-Size Chunking

Splits text into chunks of exactly N characters or tokens regardless of content.

# Simplest approach — just split every N characters
def fixed_size_chunk(text, chunk_size=500, overlap=50):
    chunks = []
    for i in range(0, len(text), chunk_size - overlap):
        chunks.append(text[i:i + chunk_size])
    return chunks

# Pros: Fast, predictable chunk sizes
# Cons: Splits mid-sentence, mid-paragraph — breaks meaning

4.1.2 Recursive Character Chunking (Most Common)

Tries to split by paragraphs first, then sentences, then words — preserving meaning.

from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,       # Max characters per chunk
    chunk_overlap=200,     # Overlap for context continuity
    separators=["\n\n", "\n", ". ", " ", ""],  # Try splits in order
    # First tries double-newlines (paragraphs), then newlines, 
    # then sentences, then words, then characters
)
chunks = splitter.split_documents(docs)
# Best general-purpose chunker — USE THIS AS YOUR DEFAULT

4.1.3 Sentence-Based Chunking

Groups complete sentences together.

from langchain.text_splitter import NLTKTextSplitter, SpacyTextSplitter

# Using NLTK sentence tokenizer
nltk_splitter = NLTKTextSplitter(chunk_size=1000)

# Using spaCy sentence tokenizer (more accurate)
spacy_splitter = SpacyTextSplitter(chunk_size=1000, pipeline="en_core_web_sm")
# Respects sentence boundaries — never splits mid-sentence

4.1.4 Token-Based Chunking

Splits by token count (matches LLM/embedding model token limits exactly).

from langchain.text_splitter import TokenTextSplitter

token_splitter = TokenTextSplitter(
    chunk_size=256,      # 256 tokens per chunk
    chunk_overlap=50,    # 50 token overlap
    encoding_name="cl100k_base"  # OpenAI tokenizer
)
# Why use this? Embedding models have token limits (512 for many models)
# Token-based ensures you never exceed the limit

4.1.5 Semantic Chunking

Uses embedding similarity to detect topic changes and split at meaning boundaries.

from langchain_experimental.text_splitter import SemanticChunker
from langchain_openai import OpenAIEmbeddings

semantic_splitter = SemanticChunker(
    OpenAIEmbeddings(), 
    breakpoint_threshold_type="percentile",  # or "standard_deviation", "interquartile"
    breakpoint_threshold_amount=95  # Split at 95th percentile of dissimilarity
)
chunks = semantic_splitter.split_text(long_text)

# HOW IT WORKS:
# 1. Split text into sentences
# 2. Embed each sentence
# 3. Compare consecutive sentence embeddings (cosine similarity)
# 4. Where similarity drops significantly → insert chunk boundary
# 5. Result: Chunks that are topically coherent

# Example: A document about "Python basics" then "ML algorithms"
# Semantic chunker detects the topic shift and splits there
# vs. fixed-size might split in the MIDDLE of the ML section

4.1.6 Document-Structure / Markdown-Aware Chunking

Respects document structure (headings, sections).

from langchain.text_splitter import MarkdownHeaderTextSplitter, HTMLHeaderTextSplitter

# Markdown-aware — splits at heading boundaries
md_splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=[
        ("#", "Header 1"),
        ("##", "Header 2"),
        ("###", "Header 3"),
    ]
)
# Each chunk gets header metadata: {"Header 1": "ML Basics", "Header 2": "SVM"}

# HTML-aware — splits at HTML heading tags
html_splitter = HTMLHeaderTextSplitter(
    headers_to_split_on=[("h1", "Header 1"), ("h2", "Header 2")]
)

4.1.7 Code-Aware Chunking

Splits source code by functions, classes, and logical boundaries.

from langchain.text_splitter import RecursiveCharacterTextSplitter, Language

# Python code splitter
python_splitter = RecursiveCharacterTextSplitter.from_language(
    language=Language.PYTHON,
    chunk_size=2000,
    chunk_overlap=200,
)
# Splits at: class → function → method → decorator boundaries
# Supports: Python, JavaScript, TypeScript, Java, Go, Ruby, Rust, etc.

4.1.8 Proposition / Agentic Chunking

Uses an LLM to extract atomic factual propositions from text.

# Concept: Instead of splitting by structure, ask LLM to decompose
# the document into standalone factual statements

# Example input: "Albert Einstein was born in 1879 in Germany. 
#                 He developed the theory of relativity."
# Proposition chunks:
#   1. "Albert Einstein was born in 1879"
#   2. "Albert Einstein was born in Germany"  
#   3. "Albert Einstein developed the theory of relativity"

# Each proposition is self-contained and independently retrievable
# Very high quality but expensive (requires LLM call per document)

4.1.9 Parent-Child (Small-to-Big) Chunking

Index small chunks for precise retrieval, but return parent (larger) chunk for context.

from langchain.retrievers import ParentDocumentRetriever
from langchain.storage import InMemoryStore

# Small chunks (128 chars) for precise matching
child_splitter = RecursiveCharacterTextSplitter(chunk_size=128)

# Large parent chunks (2000 chars) for context
parent_splitter = RecursiveCharacterTextSplitter(chunk_size=2000)

store = InMemoryStore()
retriever = ParentDocumentRetriever(
    vectorstore=vectorstore,
    docstore=store,
    child_splitter=child_splitter,
    parent_splitter=parent_splitter,
)
# Search matches small precise chunks → returns the full parent document

4.1.10 Late Chunking / Contextual Retrieval

Embed the FULL document first, then create chunks that inherit full-document context.

# Approach 1: Late Chunking (Jina AI)
# 1. Pass full document through embedding model (long-context model)
# 2. Get token-level embeddings for entire document
# 3. THEN chunk and pool token embeddings per chunk
# Each chunk embedding is aware of the full document context

# Approach 2: Contextual Retrieval (Anthropic)
# Prepend context to each chunk before embedding:
# "This chunk is from the Q4 2024 earnings report, section on revenue..."
# The context helps the embedding model understand chunk meaning

# Both approaches solve the "lost context" problem of naive chunking

4.2 Chunking Decision Guide

CHUNKING RULES:
  Chunk size 500-1000 chars:  Good for Q&A (precise retrieval)
  Chunk size 1000-2000 chars: Good for summarization (more context)
  Overlap 10-20%:             Prevents losing cross-boundary info

  TOO LARGE: Dilutes relevant info, wastes context window tokens
  
  DECISION TREE:
  ├── Simple text docs? → Recursive Character (default)
  ├── Structured docs (MD/HTML)? → Markdown/HTML-aware
  ├── Source code? → Code-aware (Language-specific)
  ├── Mixed topics in one doc? → Semantic chunking
  ├── Need precision + context? → Parent-Child
  ├── Quality critical? → Proposition/Agentic chunking
  └── Not sure? → Start with RecursiveCharacter(1000, 200)
  
  BEST PRACTICE: Start with RecursiveCharacter(1000, 200), tune based on eval

4.3 What is Semantic Search?

Definitionmeaningintent

Definition: Semantic search is a search technique that understands the meaning and intent behind a query rather than just matching keywords. It uses vector embeddings to represent text as high-dimensional numerical vectors, then finds documents whose vectors are closest to the query vector in the embedding space.

KEYWORD SEARCH vs SEMANTIC SEARCH:

Keyword Search (BM25/TF-IDF):
  Query: "How to fix a broken heart"
  Matches: Documents containing "fix", "broken", "heart"
  Problem: Returns plumbing articles about fixing broken pipes!

Semantic Search (Embeddings):
  Query: "How to fix a broken heart"  
  Embedding: [0.23, -0.87, 0.45, ...]  (captures MEANING)
  Matches: Documents about emotional healing, breakups, coping
  Why: Embeddings capture that "broken heart" = emotional pain

HOW SEMANTIC SEARCH WORKS:
  1. OFFLINE (Indexing):
     Document → Embedding Model → Vector [768 dims] → Store in Vector DB
     
  2. ONLINE (Querying):
     Query → Same Embedding Model → Query Vector [768 dims]
     → Find nearest vectors in Vector DB (cosine similarity)
     → Return top-K matching documents

  3. SIMILARITY METRICS:
     Cosine Similarity: cos(θ) = (A·B) / (||A|| × ||B||)
       → Measures angle between vectors (0=opposite, 1=identical)
     Dot Product: A·B = Σ(aᵢ × bᵢ)
       → Measures magnitude-weighted similarity
     L2 / Euclidean: √Σ(aᵢ - bᵢ)²
       → Measures straight-line distance (smaller = more similar)

WHY SEMANTIC SEARCH MATTERS FOR RAG:
  - Users ask questions in natural language, not keywords
  - Same concept expressed differently still matches
  - "automobile" matches "car", "vehicle", "sedan"
  - Understands context: "Python" (programming) vs "Python" (snake)

4.4 Why Can't We Store Embeddings in a Normal (Relational) Database?

Definition: Embeddings are high-dimensional floating-point vectors (768-3072 dimensions). Regular relational databases (MySQL, PostgreSQL without extensions) are designed for structured scalar data, not for high-dimensional vector similarity search. Vector databases are purpose-built for this task.

WHY NORMAL DATABASES FAIL FOR EMBEDDINGS:

1. NO NATIVE SIMILARITY SEARCH:
   SQL: SELECT * FROM docs WHERE embedding = [0.23, -0.87, ...]  ← Exact match only!
   Need: "Find the 5 closest vectors" ← SQL has no operator for this
   
2. BRUTE FORCE IS TOO SLOW:
   To find similar vectors without an index:
   Compare query vector against EVERY stored vector
   1M documents × 768 dims = 768M floating-point operations PER QUERY
   → Several seconds per query — unusable in production

3. NO VECTOR INDEXING:
   Normal DB indexes: B-tree, Hash → designed for exact match, range queries
   Vector search needs: ANN (Approximate Nearest Neighbor) indexes
   → HNSW (Hierarchical Navigable Small Worlds): Graph-based, O(log n)
   → IVF (Inverted File Index): Cluster-based, O(√n)
   → Normal B-tree cannot index 768-dimensional space efficiently

4. STORAGE INEFFICIENCY:
   768 floats × 4 bytes = 3 KB per vector
   1M documents = 3 GB just for vectors
   Normal DBs store as BLOB/ARRAY → no compression, no quantization
   Vector DBs: Product Quantization can compress 768 floats to ~96 bytes

5. NO METADATA FILTERING + VECTOR SEARCH:
   Need: "Find similar documents WHERE category='finance' AND date > 2024"
   This requires COMBINED filtering + ANN search
   Normal DBs can filter but not search vectors; Vector DBs do both

COMPARISON:
  ┌─────────────────────┬──────────────────────┬──────────────────────┐
  │ Feature             │ Normal DB (MySQL)    │ Vector DB (Qdrant)   │
  ├─────────────────────┼──────────────────────┼──────────────────────┤
  │ Store vectors       │ As BLOB/JSON (slow)  │ Native format        │
  │ Similarity search   │ Full scan O(n)       │ ANN O(log n)         │
  │ 1M vector search    │ ~5-10 seconds        │ ~5-50 milliseconds   │
  │ Vector indexing     │ None                 │ HNSW, IVF, PQ        │
  │ Quantization        │ No                   │ Yes (4x compression) │
  │ Hybrid search       │ No                   │ Yes (vector + filter)│
  │ Batch upsert        │ Slow                 │ Optimized            │
  │ Dimensionality      │ Not optimized        │ Purpose-built        │
  └─────────────────────┴──────────────────────┴──────────────────────┘

EXCEPTION: pgvector
  PostgreSQL + pgvector extension DOES support vector search!
  → Adds vector data type and similarity operators
  → Supports HNSW and IVF indexing
  → Good for small-medium scale when you already use PostgreSQL
  → But purpose-built vector DBs are faster at large scale
5. Vector Stores & Indexing

Vector stores are specialized databases that index and search high-dimensional embedding vectors using approximate nearest neighbor (ANN) algorithms like HNSW and IVF. The choice of vector store (FAISS for prototyping, Qdrant/Pinecone for production) depends on scale, filtering needs, hybrid search support, and infrastructure constraints.

from langchain_community.vectorstores import FAISS, Chroma
from langchain_pinecone import PineconeVectorStore
from langchain_qdrant import QdrantVectorStore

# ── FAISS (Facebook AI Similarity Search) ────────────────
# Best for: Prototyping, single-machine, no persistence needed
vectorstore = FAISS.from_documents(chunks, embeddings)
vectorstore.save_local("faiss_index")
vectorstore = FAISS.load_local("faiss_index", embeddings)

# ── Chroma (open-source, easy to use) ───────────────────
# Best for: Development, small-medium datasets
vectorstore = Chroma.from_documents(chunks, embeddings, persist_directory="./chroma")

# ── Pinecone (managed, scalable) ─────────────────────────
# Best for: Production, large-scale, fully managed
vectorstore = PineconeVectorStore.from_documents(chunks, embeddings, index_name="my-index")

# ── Qdrant (open-source, production-grade) ───────────────
# Best for: Production, filtering, hybrid search
vectorstore = QdrantVectorStore.from_documents(chunks, embeddings, url="http://localhost:6333")

# ── pgvector (PostgreSQL extension) ──────────────────────
# Best for: When you already use PostgreSQL

5.1 What "The Index" Actually Is (intuition first)

notindex type

When you call FAISS.from_documents(...) something gets built and saved. What is that thing? An index is not the text — the text lives elsewhere. An index is three things stored together:

A VECTOR INDEX = 3 PIECES

  1. THE VECTORS          The N×d float32 numbers themselves
                          (sometimes COMPRESSED — see PQ below)

  2. A SEARCH STRUCTURE   A precomputed map that lets you AVOID comparing
                          the query against all N vectors:
                            • centroids + cluster lists  (IVF)
                            • a navigable graph           (HNSW)
                            • nothing                     (Flat = brute force)

  3. AN ID MAPPING        internal row 0..N-1  →  your real id ("doc_42")
                          so a hit can be traced back to a chunk

  The CHUNK TEXT + METADATA do NOT live in the index. They live in a
  separate "docstore" keyed by id. The index returns ids + distances;
  you then look up the text in the docstore.

      ┌─────────── vector store on disk ───────────┐
      │  index file   →  vectors + structure + ids │   "which ids are nearest?"
      │  docstore     →  id → {text, metadata}      │   "what text is id 42?"
      └─────────────────────────────────────────────┘

So the answer to "what will the index be?" depends on which index type you pick. Each stores a different structure:

5.2 The Four Index Types — What Each One Stores

FLAT  (IndexFlatL2 / IndexFlatIP)  ── exact, the baseline
  STORES:  just the raw matrix  →  N × d float32   (nothing else)
  SEARCH:  compute distance to EVERY vector, sort. O(N·d). Exact.
  DISK:    N × d × 4 bytes  (1M × 768 → ~3 GB)
  USE:     ground-truth / <100k vectors

IVF  (IndexIVFFlat)  ── cluster-and-prune
  STORES:  • centroids        k × d        (the "coarse quantizer")
           • inverted lists   cluster_id → [vector ids + their vectors]
  SEARCH:  find the nprobe nearest centroids, scan ONLY those lists.
           Touches ~ (nprobe/k) of the data.  O(√N) typical.
  DISK:    vectors + centroids + the list assignments
  USE:     1M–100M vectors, tunable recall via nprobe

HNSW  (IndexHNSWFlat)  ── navigable small-world graph
  STORES:  • the vectors
           • a multi-LAYER graph: per vector, a neighbour list per layer
             (top layers sparse "highways", bottom layer dense)
  SEARCH:  greedy walk — start at an entry node on the top layer, hop to
           the closest neighbour, descend layers. O(log N).
  DISK:    vectors + adjacency lists (the graph is the big extra cost)
  USE:     default for low-latency production; best recall/speed, more RAM

PQ / IVF-PQ  (IndexIVFPQ)  ── compression
  STORES:  • codebooks   m × 256 × (d/m)   (m little sub-quantizers)
           • each vector as m BYTES (codes), NOT the original floats
  SEARCH:  approximate distance from the codes (asymmetric distance table)
  DISK:    768 floats (3072 B)  →  m bytes (e.g. 96 B): ~32× smaller
  USE:     billions of vectors / RAM-constrained; trades some recall
PICKING ONE (rule of thumb):
  < 100k          → Flat (exact, simplest)
  100k – 10M      → HNSW (best latency/recall) or IVF
  > 100M / RAM↓   → IVF-PQ (compressed)
  need exact recall guarantee → Flat

    \  \  |  /  /                              every single one measured
     (exact nearest neighbour = GUARANTEED)
   recall 100% · cost O(N·d) · no training · the ground-truth baseline
IVF (Inverted File) — k-means cuts space into cells; scan only the nearest few
        ┌──────────┬──────────┬──────────┐
        │  ●   ●   │    ● ●   │   ●     │   each cell = one "inverted list"
        │   ✦c1    │   ✦c2 ●  │  ✦c3  ● │   ✦ = centroid (the coarse quantizer)
        ├──────────┼──────────┼──────────┤
        │  ● q     │  ●    ●  │   ●  ●  │   q falls near c1 & c4 →
        │   ✦c4 ●  │   ✦c5    │  ✦c6  ● │   scan ONLY those nprobe lists,
        └──────────┴──────────┴──────────┘   skip every other cell
   nprobe=2 → touch ~2/6 of the data · O(√N) · recall tuned by nprobe (↑nprobe = ↑recall, ↓speed)
HNSW (Hierarchical Navigable Small World) — a layered "skip-list of graphs"
  Layer 2  (sparse highways)   ●───────────────────●        ← few, long-range links
                                \                  /
  Layer 1  (medium density)  ●───●────●────●────●───●        ← descend toward q
                              \   |   /  \   |   /
  Layer 0  (ALL nodes)    ●─●─●─●─●─●─●─●─●─●─●─●─●─●         ← dense, full graph
                          entry node → greedily hop to the closest neighbour →
                          drop a layer → repeat → converge on q's neighbourhood
   O(log N) · best recall/latency in production · the graph (adjacency lists) costs extra RAM
PQ (Product Quantization) — chop each vector into m sub-vectors, store a code byte each
   original 768 floats:  [ 0.12 … │ … │ ……… │ … 0.47 ]   3072 bytes
                           sub-1     sub-2  …    sub-m
                             │         │           │
                      nearest    nearest      nearest        ← per-chunk codebook
                      centroid   centroid     centroid          (256 options = 1 byte)
                        =17         =4          =200
   stored as codes:   [ 17 , 4 , … , 200 ]  →  m bytes (e.g. 96)   ~32× smaller on disk
   distance ≈ summed from a precomputed code→distance table (approximate, no raw floats)
IVF-PQ — combine both: IVF PICKS the lists, PQ COMPRESSES the vectors inside them
   query ─► nearest centroids (IVF prune) ─► scan those lists, but each vector
            is just a few PQ code-bytes (not full floats) ─► billions fit in RAM
   the production answer for >100M vectors on a memory budget.
LSH (Locality-Sensitive Hashing) — random hyperplanes hash near points to the SAME bucket
   hash(x) = ( sign(x·r1), sign(x·r2), sign(x·r3) )  →  e.g. "101"
        bucket 101 : ● ● ●        query hashes to 101 → only compare bucket 101's points
        bucket 100 : ●            collisions ≈ similarity; use several hash tables to ↑ recall
        bucket 011 : ● ●          simple & streaming-friendly, but lower recall than IVF/HNSW
AT A GLANCE
  TECHNIQUE  IDEA               SPEED    RECALL    MEMORY   TRAIN?   BEST WHEN
  ─────────  ─────────────────  ───────  ────────  ───────  ──────   ──────────────────────
  Flat       scan everything    slow     100%      high     no       <100k / need exact
  IVF        cluster + prune    medium   tunable   medium   yes      1M–100M, tune nprobe
  HNSW       greedy graph hops  fast     high      high     no       low-latency production
  PQ         compress to codes  fast     lower     tiny     yes      RAM-bound, flat list
  IVF-PQ     prune + compress   fast     medium    tiny     yes      billions of vectors
  LSH        hash into buckets  fast     lower     low      no       simple / streaming

DiskANN / ScaNN are the "next tier": DiskANN keeps an HNSW-like graph on SSD (RAM holds only compressed vectors → billions per node); ScaNN (Google) pairs anisotropic quantization with fast scoring. Both are IVF/HNSW/PQ ideas pushed further — reach for them only at extreme scale.

5.4 From Scratch — Build, Search, and SAVE an IVF Index

centroidsinverted list

This makes "what the index is" concrete: k-means gives centroids, each vector is filed into an inverted list, and search scans only a few lists. The save/load methods show exactly what bytes hit the disk.

import numpy as np, pickle, os

# ============================================================
#  FROM-SCRATCH IVF (Inverted File) INDEX  +  on-disk storage
# ============================================================
class IVFIndex:
    def __init__(self, dim, nlist=16, nprobe=3):
        self.dim, self.nlist, self.nprobe = dim, nlist, nprobe
        self.centroids = None   # (nlist, dim)  ← the coarse quantizer
        self.lists = {}         # cluster_id -> [row indices]  ← the structure
        self.vectors = None     # (N, dim)      ← the raw vectors
        self.ids = None         # (N,)          ← row -> your real id

    def _kmeans(self, X, iters=25):
        rng = np.random.default_rng(0)
        C = X[rng.choice(len(X), self.nlist, replace=False)].copy()   # init
        for _ in range(iters):
            d = ((X[:, None, :] - C[None, :, :]) ** 2).sum(-1)        # (N, nlist)
            assign = d.argmin(1)
            for c in range(self.nlist):
                pts = X[assign == c]
                if len(pts):
                    C[c] = pts.mean(0)
        return C

    def build(self, vectors, ids):
        self.vectors = np.asarray(vectors, dtype=np.float32)
        self.ids = np.asarray(ids)
        self.centroids = self._kmeans(self.vectors)
        d = ((self.vectors[:, None, :] - self.centroids[None]) ** 2).sum(-1)
        assign = d.argmin(1)                                          # nearest centroid
        self.lists = {c: np.where(assign == c)[0].tolist() for c in range(self.nlist)}

    def search(self, q, k=4):
        q = np.asarray(q, dtype=np.float32)
        cd = ((self.centroids - q) ** 2).sum(1)        # 1) distance to each centroid
        probe = cd.argsort()[:self.nprobe]             #    keep nprobe nearest lists
        cand = np.array([i for c in probe for i in self.lists[c]])    # 2) candidates only
        if cand.size == 0:
            return []
        dist = ((self.vectors[cand] - q) ** 2).sum(1)  # 3) brute force inside lists
        order = dist.argsort()[:k]
        return list(zip(self.ids[cand[order]].tolist(), dist[order].tolist()))

    # ---- PERSISTENCE: this is literally "how the index is stored" ----
    def save(self, path):
        os.makedirs(path, exist_ok=True)
        np.save(f"{path}/vectors.npy",   self.vectors)    # the vectors
        np.save(f"{path}/centroids.npy", self.centroids)  # the coarse quantizer
        np.save(f"{path}/ids.npy",       self.ids)        # row -> real id
        with open(f"{path}/structure.pkl", "wb") as f:    # the inverted lists + params
            pickle.dump({"lists": self.lists, "dim": self.dim,
                         "nlist": self.nlist, "nprobe": self.nprobe}, f)

    @classmethod
    def load(cls, path):
        with open(f"{path}/structure.pkl", "rb") as f:
            meta = pickle.load(f)
        idx = cls(meta["dim"], meta["nlist"], meta["nprobe"])
        idx.vectors   = np.load(f"{path}/vectors.npy")
        idx.centroids = np.load(f"{path}/centroids.npy")
        idx.ids       = np.load(f"{path}/ids.npy", allow_pickle=True)
        idx.lists     = meta["lists"]
        return idx

5.5 From Scratch — Product Quantization (how vectors get COMPRESSED on disk)

codebookcodebooks + the byte codes

PQ is why a billion vectors fit in RAM. It splits each vector into m sub-vectors, learns 256 centroids per sub-space (a codebook), and stores each vector as m bytes (one centroid id per sub-space) instead of the original floats. What lands on disk is the codebooks + the byte codes.

class PQ:
    """768 float32 (3072 B)  ->  m uint8 codes (e.g. 96 B): ~32x smaller."""
    def __init__(self, dim, m=8, nbits=8):
        self.m, self.k = m, 2 ** nbits        # m sub-spaces, k=256 centroids each
        self.dsub = dim // m
        self.codebooks = None                 # (m, k, dsub)  ← persisted on disk

    def fit(self, X):
        rng = np.random.default_rng(0)
        self.codebooks = np.zeros((self.m, self.k, self.dsub), np.float32)
        for j in range(self.m):                            # learn one codebook per sub-space
            sub = X[:, j*self.dsub:(j+1)*self.dsub]
            C = sub[rng.choice(len(sub), self.k, replace=False)].copy()
            for _ in range(10):
                a = ((sub[:, None] - C[None]) ** 2).sum(-1).argmin(1)
                for c in range(self.k):
                    p = sub[a == c]
                    if len(p):
                        C[c] = p.mean(0)
            self.codebooks[j] = C

    def encode(self, X):                       # vector -> m bytes  (what gets STORED)
        codes = np.empty((len(X), self.m), np.uint8)
        for j in range(self.m):
            sub = X[:, j*self.dsub:(j+1)*self.dsub]
            codes[:, j] = ((sub[:, None] - self.codebooks[j][None]) ** 2).sum(-1).argmin(1)
        return codes

    def decode(self, codes):                   # codes -> approximate vector (reconstruction)
        return np.concatenate([self.codebooks[j][codes[:, j]] for j in range(self.m)], axis=1)

# codes = PQ(dim=768, m=8).encode(vecs)   # store `codes` (uint8) + `codebooks`, NOT vecs

Search is a greedy walk over those links from a fixed entry node. Production code: use faiss.IndexHNSWFlat or hnswlib; the from-scratch IVF above is the clearest illustration of the "store centroids + lists, then prune" idea.

6. Similarity Search & Metrics

Similarity search retrieves the most relevant document chunks by comparing their embedding vectors to the query vector using distance metrics like cosine similarity, dot product, or L2 distance. Advanced retrieval strategies such as Maximum Marginal Relevance (MMR), score thresholds, and metadata filtering further refine result quality and diversity.

)

SIMILARITY METRICS:
  Cosine Similarity:  cos(θ) = A·B / (||A|| × ||B||)
    Range: [-1, 1] (normalized), most common for text
    
  Dot Product:  A·B = Σ aᵢbᵢ
    Range: (-∞, ∞), faster, equivalent to cosine for normalized vectors
    
  L2 (Euclidean):  ||A - B|| = √(Σ(aᵢ-bᵢ)²)
    Range: [0, ∞), smaller = more similar
    
  RULE: Use cosine for text. Dot product for speed. L2 for images.
7. Naive RAG Pipeline

A naive RAG pipeline is the simplest end-to-end implementation: embed the query, retrieve top-K chunks from the vector store, inject them as context into the prompt, and generate an answer. from langchain_core.runnables import RunnablePassthrough
from langchain_core.output_parsers import StrOutputParser

def format_docs(docs):
    return "\n\n".join(
        f"[Source: {doc.metadata.get('source', 'unknown')}]\n{doc.page_content}" 
        for doc in docs
    )

rag_prompt = ChatPromptTemplate.from_messages([
    ("system", """Answer the question based ONLY on the provided context. 
If the context doesn't contain the answer, say "I don't have enough information."
Always cite your sources.

{context}"""),
    ("human", "{question}"),
])

naive_rag = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}

8. Advanced RAG — Query Transformation

Query transformation techniques improve retrieval quality by reformulating the user's original query before searching the vector store. Methods include multi-query retrieval (generating multiple query perspectives), HyDE (embedding a hypothetical answer instead of the question), step-back prompting (asking a more general question first), and query decomposition (breaking complex questions into sub-queries).

# ── Multi-Query Retrieval ────────────────────────────────
# Generate multiple queries from different angles for better recall
from langchain.retrievers.multi_query import MultiQueryRetriever

multi_retriever = MultiQueryRetriever.from_llm(retriever, model)
# "What is climate change?"  →  Multiple generated queries:
#   1. "How is global warming affecting Earth?"
#   2. "What are the causes of climate change?"
#   3. "Environmental impact of greenhouse gases"
# Union of results from all queries

# ── HyDE (Hypothetical Document Embeddings) ──────────────
# Generate a hypothetical answer, embed THAT, then retrieve
def hyde_retrieval(query):
    hypothetical = model.invoke(
        f"Write a short paragraph answering: {query}"
    ).content
    return retriever.invoke(hypothetical)  # Embed hypothetical answer

# ── Step-Back Prompting ──────────────────────────────────
# Ask a more general question first, then use that context
def step_back(query):
    general = model.invoke(
        f"What is a more general question that would help answer: {query}"
    ).content
    general_docs = retriever.invoke(general)
    specific_docs = retriever.invoke(query)
    return general_docs + specific_docs

# ── Query Decomposition ─────────────────────────────────
# Break complex query into sub-queries
def decompose(query):
    sub_queries = model.with_structured_output(SubQueries).invoke(
        f"Break this into 2-3 simpler questions: {query}"
    )
    all_docs = []
    for sq in sub_queries.questions:
        all_docs.extend(retriever.invoke(sq))
    return all_docs

9.1 BM25 — What It Is and How It Scores

BM25lexicalterm-frequency saturationdocument-length normalization

BM25 ("Best Matching 25") is the standard lexical (keyword) ranking function — an improved TF-IDF. It scores a document by how often the query terms appear in it, with two crucial corrections that plain TF-IDF lacks: term-frequency saturation (the 10th occurrence of a word adds far less than the 2nd) and document-length normalization (long documents don't win just by being long).

BM25 SCORE of document D for query Q = sum over each query term qᵢ of:

                          f(qᵢ, D) · (k₁ + 1)
   IDF(qᵢ) · ─────────────────────────────────────────────
              f(qᵢ, D) + k₁ · (1 − b + b · |D| / avgdl)

  f(qᵢ, D)  term frequency of qᵢ in D        |D|     length of D (in words)
  N         total number of documents        avgdl   average document length
  n(qᵢ)     number of docs containing qᵢ

  IDF(qᵢ) = ln( (N − n(qᵢ) + 0.5) / (n(qᵢ) + 0.5) + 1 )    ← rare terms score higher

  TUNING KNOBS
    k₁ (≈1.2–2.0)  term-frequency saturation. Higher = TF matters more.
    b  (≈0.75)     length normalization. b=0 ignores length; b=1 fully normalizes.

  WHY IT BEATS TF-IDF
    • Saturation: with k₁, going from 1→2 hits helps a lot, 50→51 barely moves.

      mentions a term twice doesn't outrank a focused paragraph.

9.2 BM25 From Scratch (so you understand what the library does)

import math
from collections import Counter

class BM25:
    """Minimal, correct BM25 (Okapi). Educational — use rank_bm25 in production."""

    def __init__(self, corpus: list[list[str]], k1: float = 1.5, b: float = 0.75):
        self.corpus = corpus                 # corpus = list of tokenized docs
        self.k1, self.b = k1, b
        self.N = len(corpus)
        self.doc_len = [len(doc) for doc in corpus]
        self.avgdl = sum(self.doc_len) / self.N
        self.tf = [Counter(doc) for doc in corpus]          # term freq per doc
        # document frequency: in how many docs does each term appear?
        df = Counter()
        for doc in corpus:
            df.update(set(doc))
        # BM25 idf (the +0.5 smoothing handles common terms gracefully)
        self.idf = {
            term: math.log(1 + (self.N - n + 0.5) / (n + 0.5))
            for term, n in df.items()
        }

    def score(self, query: list[str], index: int) -> float:
        score = 0.0
        for term in query:
            if term not in self.tf[index]:
                continue
            freq = self.tf[index][term]
            idf = self.idf.get(term, 0.0)
            denom = freq + self.k1 * (1 - self.b + self.b * self.doc_len[index] / self.avgdl)
            score += idf * (freq * (self.k1 + 1)) / denom
        return score

    def search(self, query: list[str], top_k: int = 5) -> list[tuple[int, float]]:
        scores = [(i, self.score(query, i)) for i in range(self.N)]
        scores.sort(key=lambda x: x[1], reverse=True)
        return scores[:top_k]

9.4 Hybrid Search — Fusing BM25 + Vector Scores

You can't add a BM25 score (unbounded, e.g. 0–15) to a cosine score (0–1) directly — their scales differ. Two standard fusion methods:

# ── Method A: weighted fusion after min-max normalization ──
def normalize(scores: dict[str, float]) -> dict[str, float]:
    if not scores:
        return {}
    lo, hi = min(scores.values()), max(scores.values())
    if hi == lo:
        return {k: 1.0 for k in scores}      # avoid divide-by-zero
    return {k: (v - lo) / (hi - lo) for k, v in scores.items()}

def weighted_hybrid(bm25_scores: dict, vector_scores: dict, alpha: float = 0.5) -> list:
    """alpha = weight on semantic (vector); 1-alpha on lexical (BM25)."""
    bm, vec = normalize(bm25_scores), normalize(vector_scores)
    all_ids = set(bm) | set(vec)             # union — a doc may be in only one list
    fused = {doc_id: alpha * vec.get(doc_id, 0) + (1 - alpha) * bm.get(doc_id, 0)
             for doc_id in all_ids}
    return sorted(fused.items(), key=lambda x: x[1], reverse=True)
# ── Method B: Reciprocal Rank Fusion (RRF) — rank-based, no normalization ──
# The de-facto default (used by Elastic, Weaviate, Qdrant). Uses each doc's
# RANK in each list, not its raw score, so scale mismatches simply don't matter.
def reciprocal_rank_fusion(ranked_lists: list[list[str]], k: int = 60) -> list[tuple[str, float]]:
    """ranked_lists = [bm25_doc_ids_in_order, vector_doc_ids_in_order, ...]"""
    scores: dict[str, float] = {}
    for ranking in ranked_lists:
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)

9.5 Re-ranking — Cross-Encoder (the actual scoring)

Retrieval uses a bi-encoder (query and docs embedded separately, compared by cosine) — fast but approximate. A cross-encoder feeds the (query, document) pair together through a transformer so every query token attends to every doc token, producing a far more accurate relevance score. It's too slow to run over the whole corpus, so it runs as a second stage on the ~20–100 candidates that retrieval already narrowed down.

9.7.2 BM25 — the algorithm, and why it is fast

BM25 scores a document against a query as a sum over query terms:

                     f(t,d) · (k1 + 1)
  score(d,q) = SUM  ------------------------------------  · IDF(t)
                t∈q  f(t,d) + k1 · (1 - b + b · |d|/avgdl)

  f(t,d)  term frequency, with SATURATION: the 10th occurrence adds almost nothing (k1)
  |d|/avgdl  length normalisation: a long document is not more relevant for being long (b)
  IDF(t)  log((N - df + 0.5)/(df + 0.5) + 1): a term in every document is worth nothing

The speed does not come from that formula — it comes from the inverted index. The index maps each term to a posting list of the documents containing it:

  term 4711 -> [(doc 12, tf 3), (doc 88, tf 1), (doc 415, tf 2)]      <- 3 postings
  term 9    -> [(doc 0, tf 1), (doc 1, tf 4), ... 199,867 more ...]   <- a stopword

  query = 3 terms  ->  score ONLY the documents in those 3 posting lists.
                       Everything else in the corpus is never touched.

So the cost of a BM25 query is the total length of the posting lists for its terms — which depends on how common the query's words are, and barely on how big the corpus is. Measured:

N=10000   build  0.10s  |  rare terms (df<=60):  0.184 ms,    177 postings  |  3 commonest terms:    21.64 ms,    29983 postings
N=50000   build  0.49s  |  rare terms (df<=60):  0.143 ms,    180 postings  |  3 commonest terms:   112.42 ms,   149903 postings
N=200000  build  2.10s  |  rare terms (df<=60):  0.154 ms,    180 postings  |  3 commonest terms:   472.42 ms,   599601 postings

Read those two columns against each other:

  • Discriminative terms: 0.15 ms, and flat as the corpus grows 20x. 180 postings at N=10,000 and 180 postings at N=200,000 — the corpus grew, the posting lists for a rare term did not. This is why BM25 over millions of documents is still a single-digit-millisecond operation.
  • The three commonest terms: 21 ms → 472 ms, growing linearly with N. Those posting lists contain most of the corpus, so the "index" degenerates into a full scan.

That contrast is the whole performance story of keyword search, and it is why production engines do three things: drop stopwords at index time, keep posting lists sorted so they can be intersected rather than unioned, and use WAND / block-max WAND to skip blocks of a posting list whose best possible score cannot reach the current top-k threshold. Block-max WAND typically evaluates 5–20% of the postings a naive scorer would.

Interview line. "BM25 is O(postings touched), not O(N). A query of rare terms is sub-millisecond on millions of documents; a query of stopwords degenerates to a full scan, which is why stopword handling and WAND-style pruning exist."

9.7.3 Dense search — brute force is faster than people expect

A dense search is one matrix multiply: scores = M @ q, then a partial sort for the top k. It is O(N · d) with a perfect memory-access pattern, which BLAS turns into near-peak FLOPs. Measured at 384 dimensions:

N=10000   d=384     0.39 ms/query     15.4 MB resident   2550 queries/sec/core
N=50000   d=384     2.14 ms/query     76.8 MB resident    468 queries/sec/core
N=100000  d=384     3.61 ms/query    153.6 MB resident    277 queries/sec/core

Below roughly 100k chunks, do not build an ANN index. A flat NumPy matrix answers in single milliseconds, gives exact results, needs no tuning, no training and no rebuild, and the memory is N · d · 4 bytes — 154 MB at 100k × 384. Reach for HNSW when N passes about 10⁵–10⁶, or when you need many queries per second per core.

9.7.4 HNSW — the algorithm, and the one knob that matters

HNSW is a proximity graph you walk greedily. Every vector is a node linked to M of its near neighbours; searching means hopping to whichever neighbour is closer to the query, over and over, until no neighbour improves.

  BUILD (insert one node)
    1. pick a level from a decaying distribution: P(level >= l) = e^(-l/mL)
       -> most nodes live only on layer 0, a few reach the sparse upper layers
    2. greedy-search from the top entry point down to the node's own level
    3. link it to M neighbours chosen by the DIVERSITY HEURISTIC:
       keep candidate c only if c is closer to the new node than to any neighbour
       already kept. Plain "keep the M nearest" packs the links inside one cluster
       and strands the walk there.
    4. prune over-full neighbour lists with the same rule

  SEARCH (one query)
    1. start at the entry point on the top layer, ef=1, hop greedily until no
       neighbour is closer, then drop a layer                    <- the "teleport"
    2. on layer 0, run a best-first search with a candidate heap of size ef_search
    3. stop when the closest unexplored candidate is further than the worst of the
       current top-ef                                            <- the cutoff
    4. return the best k

Three parameters, and only one of them is a runtime decision:

Parameter When it applies Effect Typical
M build links per node. Higher = better recall, more memory, slower build 16–48
ef_construction build how hard the builder searches for neighbours. Higher = better graph, slower build 100–400
ef_search query time size of the candidate list. The recall/latency dial 50–400

ef_search is the one to know, because it is tunable per query without rebuilding anything. Measured on the from-scratch graph, at three corpus sizes:

Three things to take from that table:

  1. Distance computations barely grow with N. At ef_search=16 the walk touched 466 vectors at N=5,000 and 526 at N=20,000 — the corpus quadrupled and the work rose 13%. As a share of the corpus that is 9.3% falling to 2.6%, and it keeps falling. That sublinearity is the entire reason HNSW exists, and it is why the same index answers in similar time at 1M vectors where brute force would need 50x longer.
  2. ef_search buys recall linearly in work. 16 → 128 costs about 5x the distance computations and takes recall from 0.45 to 0.90 at N=5,000. Tune it against your own recall target; do not accept a library default.
  3. Recall falls as the corpus grows at fixed ef. 0.90 → 0.83 → 0.61 at ef=128. A bigger corpus needs a bigger ef for the same recall — the dial is not "set once and forget".

Honest caveat about these numbers. This is a teaching implementation: pure Python, one layer for the sweep above, M=16, ef_construction=32, and adversarial synthetic data (200 Gaussian clusters in 128 dimensions, where the true 10 nearest neighbours are nearly equidistant). Production HNSW in C++ with M=32, ef_construction=200 reaches recall above 0.95 while touching well under 1% of the corpus. The scaling shape is what transfers, not the absolute recall.

Two further results from the same harness, both worth knowing:

  • The diversity heuristic beats "keep the M nearest", but not dramatically at this scale: recall@10 of 0.56 versus 0.51 at N=10,000, ef_search=48, at the same ~1,100 distance computations. The heuristic's value grows with corpus size, because that is when a walk stranded in the wrong cluster has furthest to go.
  • The layer hierarchy is worth almost nothing at 10,000 vectors: a full multi-layer build scored 0.59 against a single flat layer's 0.58 at ef_search=48. This is not a bug — recent ANN literature reports the same, that flat navigable graphs match hierarchical ones in high dimensions, and the hierarchy mainly pays off at very large N where finding a good entry point is itself expensive.

Memory, which is the other reason to choose an index:

  vectors      N · d · 4 bytes            1M × 768 float32 = 3.07 GB
  HNSW links   N · 2M · 4 bytes           1M × 32 × 4      = 128 MB   (layer 0 gets 2M links)
  PQ codes     N · m bytes                1M × 96          = 96 MB    (~32x smaller than raw)

  -> HNSW keeps the raw vectors, so it is RAM-hungry. IVF-PQ compresses them, which is
     why billion-scale indexes are IVF-PQ or DiskANN rather than plain HNSW.

9.7.5 The program that produced those numbers

import heapq, math, random, time
from collections import defaultdict
import numpy as np

random.seed(7); np.random.seed(7)
VOCAB, DOC_LEN = 20000, 80


def make_corpus(n):
    """Zipf token ids: a few terms in nearly every document, most in very few."""
    return [row.tolist() for row in np.random.zipf(1.6, size=(n, DOC_LEN)) % VOCAB]


def timeit(fn, reps):
    t0 = time.perf_counter()
    for _ in range(reps):
        fn()
    return (time.perf_counter() - t0) / reps * 1000.0


class BM25:
    def __init__(self, docs, k1=1.5, b=0.75):
        self.k1, self.b, self.N = k1, b, len(docs)
        self.len = np.array([len(d) for d in docs], dtype=np.float32)
        self.avgdl = float(self.len.mean())
        self.postings = defaultdict(list)                 # term -> [(doc, tf), ...]
        for i, d in enumerate(docs):
            tf = defaultdict(int)
            for t in d:
                tf[t] += 1
            for t, f in tf.items():
                self.postings[t].append((i, f))
        self.idf = {t: math.log(1 + (self.N - len(p) + 0.5) / (len(p) + 0.5))
                    for t, p in self.postings.items()}

    def search(self, query, k=10):
        """Only documents containing a query term are ever scored."""
        scores = defaultdict(float)
        for t in query:
            plist = self.postings.get(t)
            if not plist:
                continue
            idf = self.idf[t]
            for doc, f in plist:
                dl = self.len[doc]
                scores[doc] += idf * f * (self.k1 + 1) / (
                    f + self.k1 * (1 - self.b + self.b * dl / self.avgdl))
        return heapq.nlargest(k, scores.items(), key=lambda kv: kv[1]), len(scores)


class HNSWish:
    """One layer of HNSW: the graph, the best-first search, the diversity heuristic."""

    def __init__(self, vecs, M=16, ef_build=32):
        self.v, self.M = vecs, M
        self.nbrs = [[] for _ in range(len(vecs))]
        self.calls = 0
        for i in range(1, len(vecs)):
            found = self._search(vecs[i], ef_build, entry=random.randrange(i), limit=i)
            for _d, j in self._select(found, M):
                self.nbrs[i].append(j)
                self.nbrs[j].append(i)
                if len(self.nbrs[j]) > 2 * M:
                    ds = 1.0 - self.v[self.nbrs[j]] @ self.v[j]
                    self.calls += len(self.nbrs[j])
                    self.nbrs[j] = [b for _a, b in
                                    self._select(sorted(zip(ds.tolist(), self.nbrs[j])), M)]

    def _d(self, q, i):
        self.calls += 1
        return 1.0 - float(self.v[i] @ q)

    def _select(self, cands, M):
        """Keep a candidate only if it is closer to the new node than to anything already
        kept - that is what preserves the long-range links a greedy walk needs."""
        kept = []
        for d, c in cands:
            if all(1.0 - float(self.v[c] @ self.v[k]) >= d for _dk, k in kept):
                kept.append((d, c))
            if len(kept) >= M:
                break
        return kept

    def _search(self, q, ef, entry=0, limit=None):
        d0 = self._d(q, entry)
        cand, top, seen = [(d0, entry)], [(-d0, entry)], {entry}
        while cand:
            d, c = heapq.heappop(cand)
            if len(top) >= ef and d > -top[0][0]:
                break                                     # nothing closer is reachable
            for nb in self.nbrs[c]:
                if nb in seen or (limit is not None and nb >= limit):
                    continue
                seen.add(nb)
                dn = self._d(q, nb)
                if len(top) < ef or dn < -top[0][0]:
                    heapq.heappush(cand, (dn, nb))
                    heapq.heappush(top, (-dn, nb))
                    if len(top) > ef:
                        heapq.heappop(top)
        return sorted((-d, i) for d, i in top)

    def search(self, q, k=10, ef=48):
        return [i for _d, i in self._search(q, max(ef, k), entry=0)[:k]]


def clustered(n, d=128, centres=200):
    """Real embeddings are clustered by topic. Uniform random vectors are the worst
    case for every ANN index and nothing like production data."""

9.7.6 HyDE and multi-query — the expensive ones

HyDE, multi-query and decomposition all do the same thing structurally: they put an LLM generation in front of retrieval. That single decision dominates the latency budget.

  HyDE:  query -> LLM writes a fake answer (~120 tokens) -> embed THAT -> search
                  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                  300-2000 ms, depending on model and tokens/sec

  Put against the measured search costs above, one HyDE call costs roughly:
      ~3,900 BM25 queries        (600 ms / 0.154 ms)
      ~280 brute-force searches  (600 ms / 2.14 ms at N=50,000)
      ~300 HNSW searches

So the question is never "does HyDE improve recall" — it usually does — but "does it improve recall more than spending the same 600 ms on a reranker over a wider candidate set?" Usually it does not.

Technique Extra cost per query Buys you Use it when
HyDE 1 generation, 300–2000 ms Bridges vocabulary mismatch: the query is short and keyword-like, the documents are prose Queries and documents are written in different registers, and latency is not tight
Multi-query 1 generation + k× the searches Recall on ambiguous questions Recall matters more than latency; the searches parallelise
Step-back 1 generation + 2 searches Context for questions needing background Explanatory questions over a technical corpus
Decomposition 1 generation + n searches + n prompts The only way to answer multi-hop questions The question genuinely spans documents ("compare X and Y")
Cross-encoder rerank k forward passes, ~5–15 ms each on GPU The largest precision gain per millisecond in this table Almost always — do this before reaching for query transformation

Run them in parallel where you can. Multi-query's k searches are independent, and BM25 and the vector search in a hybrid pipeline are independent — issuing them concurrently makes hybrid search cost max(BM25, vector) rather than their sum.

9.7.7 The end-to-end budget

Putting the pyramid's five levels on the clock, for a corpus of ~100k chunks:

Level Pipeline Retrieval budget Share of a 2.5 s answer
1 embed + vector search ~10 ms + 4 ms = 14 ms 0.6%
3 + BM25 in parallel + RRF fusion ~16 ms 0.6%
4 + cross-encoder rerank of 20 candidates +150–250 ms = ~250 ms 10%
2 + HyDE in front +600 ms = ~850 ms 34%
5 + decomposition into 3 sub-queries +600 ms + 3 pipelines = ~1.5 s 60%

The conclusion that matters. Search itself is never the bottleneck — retrieval was 19.9% of the worked trace in 27_LLM_Observability_and_Tracing.md and the LLM was 75.7%. Optimise the vector index only when a trace says the vector index is slow. Everywhere else, the latency you can actually recover is in how many model calls you put in the path.

10. Advanced RAG Patterns

Advanced RAG patterns introduce self-reflective and adaptive retrieval strategies that go beyond static retrieve-then-generate pipelines. These include Self-RAG (the LLM evaluates its own retrieval quality), CRAG (corrective retrieval with web search fallback), Adaptive RAG (routing by query complexity), and Graph RAG (knowledge graph traversal for multi-hop reasoning).

# ── Self-RAG (self-reflective retrieval) ─────────────────
# LLM decides: Do I need retrieval? Is the retrieved doc relevant?
# Is my answer faithful to the context? Is it useful?
# Loops until quality criteria met.

# ── CRAG (Corrective RAG) ───────────────────────────────
# After retrieval, evaluate document relevance:
#   Correct → use documents
#   Ambiguous → web search for supplementary info
#   Wrong → discard, fall back to web search

# ── Adaptive RAG ────────────────────────────────────────
# Route based on query complexity:
#   Simple factual → direct LLM (no retrieval needed)
#   Medium → standard RAG
#   Complex multi-hop → iterative retrieval with reasoning

# ── Graph RAG ───────────────────────────────────────────
# Build a knowledge graph from documents
# Traverse relationships for multi-hop reasoning
# Combine with vector search for hybrid graph+vector retrieval

11. Agentic RAG

Agentic RAG wraps retrieval tools inside an autonomous agent that dynamically decides when, where, and how to retrieve information based on the query. Unlike static RAG pipelines, the agent can route queries to different knowledge sources (vector store, web search, SQL database), evaluate result quality, and re-retrieve with refined queries if needed.

from langgraph.prebuilt import create_react_agent
from langchain_core.tools import tool

@tool
def search_knowledge_base(query: str) -> str:
    """Search the internal knowledge base for relevant information."""
    docs = retriever.invoke(query)
    return "\n".join(doc.page_content for doc in docs)

@tool
def search_web(query: str) -> str:
    """Search the web for current information not in the knowledge base."""

Caching in RAG systems stores LLM responses and embedding computations to avoid redundant processing, reducing both cost and latency. Semantic caching — cache at two levels (retrieval and response)

meaningSaferexact-matchembedding cachePitfallsinvalidation

"Semantic" caching matches by meaning (embedding similarity), not exact string — so paraphrases hit the cache. There are two distinct places to do it:

(a) Response cache → skip retrieval and the LLM. Embed the incoming query; if cosine similarity to a previously-answered query ≥ a (high) threshold, return that cached answer directly. Biggest saving (skips the whole pipeline) but riskiest — a near-miss serves a wrong answer — so keep the bar high (~0.95–0.98) + a TTL.

Cached:  "How do I reset my password?"  → "Go to Settings → Security → Reset…"
New:     "I forgot my password, how do I change it?"
         embed → cosine 0.93 vs cached query
         ≥ threshold?  → return cached answer  (~10 ms, $0)   instead of ~2 s + retrieval + LLM cost

(b) Retrieval cache → skip the vector search, still run the LLM. Cache query → retrieved chunk-IDs. If a new query is semantically close to a cached one, reuse its chunks and go straight to generation. Safer than the response cache (the LLM still grounds on context and can re-phrase / personalize), and it removes the vector-search + rerank cost. Use it when answers must stay fresh/personalized but the relevant documents are stable.

Plus the two already shown above: exact-match (hash the normalized query) and embedding cache (don't re-embed unchanged chunks).

# query vector store of past queries -> (chunks, answer)
def answer(query):
    qv  = embed(query)
    hit = cache.search(qv, k=1)              # nearest past query
    if hit and hit.score >= 0.97:            # RESPONSE cache — very high bar
        return hit.answer                    #   → skip everything
    chunks = hit.chunks if (hit and hit.score >= 0.90) \
             else retriever.search(query)    # RETRIEVAL cache, else cold path
    ans = llm(prompt(query, chunks))         #   LLM still runs (fresh grounding)
    cache.add(qv, query, chunks, ans, ttl=3600)
    return ans

Pitfalls: threshold tuning (too low → confidently wrong answers; too high → low hit rate); invalidation when the KB changes (TTL or a version key in the cache namespace); never share personalized/permissioned answers across users; treat cache-hit-rate as a first-class metric. 14.1 Retrieval Metrics (the IR layer) — formulas + from scratch

LLM-judgedinformation-retrievalno LLMWhich to optimize, in orderRecall@K firstMRR / nDCG next

RAGAS above grades LLM-judged quality. But retrieval is an information-retrieval problem, so also grade it with classic IR metrics on a golden set of query → relevant_doc_ids. These need no LLM — cheap, deterministic, and runnable in CI on every ingest.

Notation (one query):  K = top-K cutoff · rel(i)=1 if doc at rank i is relevant · R = total relevant docs

  Precision@K = (# relevant in top-K) / K          "of what I showed, how much was good?"
  Recall@K    = (# relevant in top-K) / R          "of what exists, how much did I find?"
  Hit@K       = 1 if ANY relevant doc in top-K     "did a good doc make the cut at all?"
  MRR         = mean over queries of 1/(rank of FIRST relevant)   "how high is the first hit?"
  AP          = mean of Precision@i at each relevant rank i   →  MAP = mean of AP over queries
  DCG@K       = Σ rel(i)/log2(i+1)  ;  nDCG@K = DCG@K / ideal-DCG@K   (graded, rank-weighted)
import math

def precision_at_k(ranked, relevant, k):
    return sum(d in relevant for d in ranked[:k]) / k

def recall_at_k(ranked, relevant, k):
    return sum(d in relevant for d in ranked[:k]) / len(relevant) if relevant else 0.0

def hit_at_k(ranked, relevant, k):
    return 1.0 if any(d in relevant for d in ranked[:k]) else 0.0

def reciprocal_rank(ranked, relevant):
    for i, d in enumerate(ranked, start=1):          # 1-indexed rank
        if d in relevant:
            return 1.0 / i
    return 0.0

def average_precision(ranked, relevant):
    hits, score = 0, 0.0
    for i, d in enumerate(ranked, start=1):
        if d in relevant:
            hits += 1
            score += hits / i                        # precision@i at each relevant hit
    return score / len(relevant) if relevant else 0.0

def ndcg_at_k(ranked, gains, k):                     # gains: doc_id -> graded relevance (0..3)
    dcg  = sum(gains.get(d, 0) / math.log2(i + 1) for i, d in enumerate(ranked[:k], start=1))
    idcg = sum(g / math.log2(i + 1) for i, g in enumerate(sorted(gains.values(), reverse=True)[:k], start=1))
    return dcg / idcg if idcg else 0.0

# ── one query ──────────────────────────────────────────────
ranked   = ["d3", "d7", "d1", "d9", "d2"]            # retriever output, in rank order
relevant = {"d1", "d2"}                              # golden labels
print(precision_at_k(ranked, relevant, 5))           # 2/5 = 0.4
print(recall_at_k(ranked, relevant, 5))              # 2/2 = 1.0
print(reciprocal_rank(ranked, relevant))             # first relevant at rank 3 → 0.333
print(average_precision(ranked, relevant))           # (1/3 + 2/5)/2 = 0.366
# Report MRR / MAP / nDCG as the MEAN of these over the whole eval set.

Which to optimize, in order: - Recall@K first — if the right chunk isn't retrieved, no reranker or LLM can recover it. Set K to your rerank fetch_k. - MRR / nDCG next — once it's in the set, are you ranking it to the top? This is exactly what reranking (§9.5) moves. - Hit@K is the blunt "did we even have a chance" gate; MAP / nDCG are the graded, rank-aware versions for dashboards. - Binary labels (relevant/not) → Precision/Recall/MRR/MAP. Graded labels (0–3) → nDCG. Pair these IR metrics (retrieval health) with RAGAS faithfulness/relevancy (generation health) — they fail for different reasons.

16.4 Deduplication & Maintaining Unique Records

notprimary key5. Retrieval-time diversity (MMR)Summary pattern

Duplicate vectors waste storage, bias retrieval (one fact crowds out diversity), and burn context tokens. A vector DB does not enforce uniqueness on the embedding itself (two different texts can collide to near-identical vectors), so uniqueness is enforced through the primary key plus active dedup at ingestion and retrieval.

1. Exact dedup — deterministic content-hash IDs (idempotent upsert) 

import hashlib, re

def normalize(text: str) -> str:
    # Strip noise so trivial differences don't defeat dedup
    return re.sub(r"\s+", " ", text.lower().strip())

def content_id(text: str) -> str:
    return hashlib.sha256(normalize(text).encode()).hexdigest()

# Use the hash AS the vector-DB id → re-ingesting identical content
# overwrites the same record instead of creating a copy.
records = [{"id": content_id(chunk), "text": chunk, "vector": embed(chunk)}
           for chunk in chunks]
# Pinecone: index.upsert(records) | Qdrant: client.upsert(...) | pgvector: ON CONFLICT DO UPDATE

2. Near-duplicate dedup — embedding cosine threshold (from scratch) Exact hashing misses "almost identical" chunks (boilerplate, minor edits). Drop any candidate too close to one already kept:

import numpy as np

def cosine(a, b):
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

def dedup_by_embedding(items, threshold=0.95):
    """items: list of (text, vector). Keep first seen, drop near-duplicates."""
    kept = []
    for text, vec in items:
        if all(cosine(vec, k_vec) < threshold for _, k_vec in kept):
            kept.append((text, vec))
    return kept
# O(n²) — fine per batch. At scale: query the index for the nearest neighbour
# of each candidate and skip the insert if best match ≥ threshold.

3. Near-duplicate at scale — MinHash + Jaccard (from scratch) For millions of docs, pairwise cosine is too slow. MinHash estimates the Jaccard similarity of token shingles cheaply; pair it with LSH to bucket only likely duplicates.

import hashlib

def shingles(text, k=5):
    tokens = text.lower().split()
    return {" ".join(tokens[i:i+k]) for i in range(len(tokens) - k + 1)}

def minhash(shingle_set, num_perm=128):
    sig = []
    for p in range(num_perm):
        sig.append(min((int(hashlib.md5(f"{p}:{s}".encode()).hexdigest(), 16)
                        for s in shingle_set), default=0))
    return sig

def est_jaccard(sig_a, sig_b):
    return sum(x == y for x, y in zip(sig_a, sig_b)) / len(sig_a)
# est_jaccard ≈ |A∩B| / |A∪B|; threshold ~0.8 flags near-duplicate documents.

4. Maintaining uniqueness on document UPDATE A changed source doc must not leave orphaned old chunks. Tag every chunk with its doc_id, then delete-by-filter before re-inserting:

def reindex_document(doc_id, new_chunks):
    index.delete(filter={"doc_id": doc_id})            # remove all old chunks
    records = [{"id": content_id(c), "text": c, "vector": embed(c),
                "metadata": {"doc_id": doc_id}} for c in new_chunks]
    index.upsert(records)                              # insert the fresh set

5. Retrieval-time diversity (MMR) — even a clean index can return redundant top-K. Maximal Marginal Relevance penalizes results similar to ones already selected:

MMR = argmaxd∈ R\ S[λ sim(d,q) − (1−λ)maxs∈ Ssim(d,s)]

LangChain: vs.as_retriever(search_type="mmr", search_kwargs={"k": 4, "fetch_k": 20}).

Summary pattern: normalize → content-hash id → upsert → near-dup filter (cosine / MinHash) → delete-orphans-on-update → MMR at query time.

Q1: Explain RAG architecture. What are the key components?

A: RAG has three stages: (1) Indexing (offline): Load documents → split into chunks (RecursiveCharacterTextSplitter, 1000 chars, 200 overlap) → embed (text-embedding-3-small) → store in vector database (FAISS/Pinecone/Qdrant). Key components: Document loader, text splitter, embedding model, vector store, retriever, LLM, prompt template.

Q2: How do you improve RAG quality when naive RAG isn't performing well?

A: Layered improvements: (1) Chunking: Adjust size/overlap, try semantic chunking, add metadata. (2) Query transformation: Multi-query (retrieve from multiple perspectives), HyDE (embed hypothetical answer). (3) Hybrid search: Combine BM25 (keyword) + vector (semantic) with ensemble retriever. (4) Re-ranking: Cross-encoder scores query-doc pairs more accurately than bi-encoder. (5) Contextual embeddings: Prepend document context to each chunk before embedding. (6) Self-RAG: LLM evaluates retrieval quality and re-retrieves if needed. Always measure with RAGAS before and after changes.

Q3: What's the difference between bi-encoder and cross-encoder?

Bi-encoderCross-encoder

A: Bi-encoder: Encodes query and document independently into vectors, uses cosine similarity. Fast (can pre-compute doc embeddings), but less accurate because query and doc don't interact. Used for retrieval (first stage). Cross-encoder: Takes (query, document) pair together, outputs a relevance score. More accurate because query and doc tokens attend to each other, but slow (can't pre-compute). Used for re-ranking (second stage). Pipeline: Bi-encoder retrieves 50-100 candidates → cross-encoder re-ranks → top 5 go to LLM.

Q4: How do you choose chunk size?

Q&ASummarizationOverlap

A: Depends on use case: (1) Q&A: Smaller chunks (500-800 chars) — more precise retrieval. (2) Summarization: Larger chunks (1500-2000) — more context per chunk. (3) Overlap: 10-20% of chunk size to avoid losing cross-boundary information. Evaluation-driven: try multiple sizes, measure RAGAS context precision and recall. Too small → fragments without enough context. Too large → dilutes relevant info with irrelevant text. Also consider the embedding model's max token limit (most support 512 tokens) and the LLM's context window.

Q7: What is agentic RAG? When would you use it?

A: Agentic RAG wraps retrieval tools inside an agent that decides when and how to retrieve. Instead of always retrieving, the agent: (1) Decides if retrieval is needed. (2) Chooses which knowledge source (KB, web, SQL). (3) Formulates the right query. (4) Evaluates retrieved results. (5) May re-retrieve with a refined query. Q8: How do you evaluate a RAG system?

FaithfulnessAnswer RelevancyContext PrecisionContext Recall

A: RAGAS framework with four key metrics: (1) Faithfulness: Is the answer grounded in retrieved context? (LLM-as-judge checks if each claim is supported.)   • Use a vision-language model (PaliGemma) to produce multi-vector embeddings for each page.
  • At query time, compute late interaction (MaxSim, like ColBERT) between query token embeddings and page patch embeddings.

Advantages: Handles complex layouts, figures, and tables natively. Much simpler pipeline. Trade-offs: Higher compute at indexing, less granular retrieval (page-level, not chunk-level).

def chunk_python_file(file_content: str) -> list[dict]:
    """Chunk a Python file by top-level definitions."""

def code_rag_retrieval(query: str, vector_store, code_graph) -> list[str]:

# Build a lightweight code graph using AST analysis
class CodeGraph:
    def __init__(self):
        self.nodes = {}  # {"file::func_name": CodeNode}
        self.edges = []  # [(source, target, relation_type)]

    def add_file(self, file_path: str, content: str):
        import ast
        tree = ast.parse(content)
        for node in ast.walk(tree):
            if isinstance(node, ast.FunctionDef):
                key = f"{file_path}::{node.name}"
                self.nodes[key] = {"type": "function", "content": ast.unparse(node)}
                # Track function calls within this function
                for child in ast.walk(node):
                    if isinstance(child, ast.Call) and isinstance(child.func, ast.Name):
                        self.edges.append((key, child.func.id, "calls"))
            elif isinstance(node, ast.ClassDef):
                key = f"{file_path}::{node.name}"
                self.nodes[key] = {"type": "class", "content": ast.unparse(node)}
                for base in node.bases:
                    if isinstance(base, ast.Name):
                        self.edges.append((key, base.id, "inherits"))

20.1 Your RAG system is getting heavy traffic — how do you scale it?

pipelineCache hardest, cache firstsemantic cacheVector DBquantizationingestion/indexing path

Intuition first: a RAG query is a pipeline, and each stage scales differently — so you scale the bottleneck, not "the system":

query → embed query → ANN search (vector DB) → [rerank] → assemble context → LLM generate
         (embed model)   (vector DB QPS)        (cross-encoder)              (tokens, $$$)

Bottlenecks and their fixes:

  • Cache hardest, cache first. Exact-match query cache, then a semantic cache: embed the incoming query, and if it's within a cosine threshold of a previously answered query, return the cached answer — no retrieval, no LLM call. Also cache document embeddings so you only re-embed changed docs.
  • Vector DB: add read replicas / shard the index; tune the ANN index (HNSW ef, IVF nprobe) for the recall-vs-latency point you need; apply quantization (PQ/scalar) to shrink memory and speed search. Separate the ingestion/indexing path (async, queued) from the query path so re-indexing never blocks reads.
  • Embedding model: use a smaller/faster model, batch embedding requests, and cache.
  • Reranker (the silent latency killer): cross-encoders are expensive — only rerank the top-k candidates, batch them, use a smaller reranker, or skip reranking under load.
  • LLM: route simple queries to a smaller model, stream the answer, and compress retrieved context (fewer/denser chunks) to cut output latency and tokens.
  • Boundary: per-tenant rate limiting + backpressure (429) so a traffic spike degrades cleanly.
import numpy as np

class SemanticCache:
    """Skip retrieval+LLM when a near-duplicate query was already answered."""
    def __init__(self, embed, threshold: float = 0.95):
        self.embed, self.threshold = embed, threshold
        self.keys: list[np.ndarray] = []
        self.answers: list[str] = []

    def get(self, query: str):
        q = self.embed(query); q /= np.linalg.norm(q)
        for k, ans in zip(self.keys, self.answers):
            if float(q @ k) >= self.threshold:   # cosine sim (both unit-norm)
                return ans                       # cache hit → return immediately
        return None

    def put(self, query: str, answer: str):
        q = self.embed(query); q /= np.linalg.norm(q)
        self.keys.append(q); self.answers.append(answer)

20.2 What happens when the budget (cost/tokens) is over?

Cap the contextCap iterationsTiered modelsTwo scopesandGraceful output

In RAG, the dominant cost is LLM generation, and it scales with how much retrieved context you stuff into the prompt — plus embedding calls, vector search, and reranking. Budget overruns almost always come from too many / too-large chunks or too many retrieval iterations (multi-query, multi-hop, agentic-RAG loops).

When the budget is hit, degrade gracefully — never silently loop:

  • Cap the context. Enforce a token budget on assembled context: pack chunks by relevance until the budget is reached, then stop. Smaller top_k, or compress chunks (contextual compression — §16) before generation.
  • Cap iterations. For Self-RAG / CRAG / agentic loops (§10–§11), set a max number of retrieval rounds; if still under-grounded, stop and answer with what you have, flagged low_confidence.
  • Tiered models. Cheap model first; escalate to the expensive model only when a confidence/groundedness check is low.
  • Two scopes: per-query token budget and per-tenant monthly quota (enforced at the API boundary → 429).
  • Graceful output: return the best-effort grounded answer + an insufficient_context flag, or "I don't have enough information," rather than a runaway bill.
def assemble_context(chunks, count_tokens, max_context_tokens=3000):
    """Pack highest-ranked chunks until the token budget is spent — a hard cost cap."""
    context, used = [], 0
    for ch in chunks:                      # chunks already sorted by relevance
        t = count_tokens(ch.text)
        if used + t > max_context_tokens:
            break                          # budget reached → stop adding
        context.append(ch.text); used += t
    return "\n\n".join(context), used

20.3 Challenges when coordinating multiple retrievers / agentic RAG

agent decide when/what to retrieveResult fusion & conflictsRedundant retrieval & costContext-window contentionRoutingGrounding / trust boundary

Modern RAG rarely has a single retriever — you fuse BM25 + vector (§9.4), query multiple sources, or let an agent decide when/what to retrieve (agentic RAG, §11). Coordinating these is the RAG version of the multi-agent problem:

  • Result fusion & conflicts. BM25 and vector return different docs with incomparable scores → you can't just concatenate. Sources may also disagree on facts → which do you trust (authority/recency)?
  • Redundant retrieval & cost. Multiple retrievers / multi-query re-fetch overlapping chunks; iterative agentic loops can re-retrieve forever → cost & latency blowup.
  • Context-window contention. Merging results from N sources overflows the window → you must dedupe + rerank + compress, not just append.
  • Routing. Which retriever for which query? A misroute (sending a code question to the policy index) poisons the context.
  • Grounding / trust boundary. The generator must cite which source each claim came from; an unverified retrieval becomes a confident hallucination.

The standard fix for fusing incomparable rankings is Reciprocal Rank Fusion (RRF) — it ignores raw scores and uses only rank position, so BM25 and vector results combine cleanly:

def reciprocal_rank_fusion(ranked_lists, k: int = 60, top_n: int = 5):
    """ranked_lists: list of result-lists (each already ordered best→worst).
    RRF score for a doc = Σ over lists of 1 / (k + rank_in_that_list)."""
    scores: dict[str, float] = {}
    for results in ranked_lists:           # e.g. [bm25_hits, vector_hits]
        for rank, doc_id in enumerate(results):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    fused = sorted(scores, key=scores.get, reverse=True)
    return fused[:top_n]                    # dedup is automatic — keyed by doc_id

Then rerank the fused set with a cross-encoder (§9), apply source-priority rules for conflicts, and cap retrieval iterations for agentic loops. See [[multi-agent-coordination]] in the agentic notes for the general pattern.

20.4 Guardrails in RAG — what they are and how you used them

Inputprompt injection via documentsRetrievalrelevance thresholdGenerationonly

RAG guardrails enforce the one promise RAG makes: the answer is grounded in retrieved context, safe, and only drawn from sources the user is allowed to see. The model is probabilistic; guardrails are the deterministic checks around it.

  • Input: PII/injection detection on the query. (RAG-specific risk: prompt injection via documents — a retrieved chunk can contain "ignore previous instructions." Treat retrieved content as untrusted data, delimit it clearly, never as instructions.)
  • Retrieval: access control / row-level security so a user only retrieves docs they're authorized to see (critical in multi-tenant RAG); a relevance threshold — if the top similarity score is below a floor, return "I don't have that information" instead of forcing an answer over irrelevant chunks; source allowlists.
  • Generation: an "answer only from the provided context; if it's not there, say you don't know" instruction.
  • Output (the RAG-specific one): a groundedness / faithfulness check — every claim in the answer must be supported by a retrieved chunk (LLM-as-judge or an NLI model), enforced citations (each statement points to its source), plus PII redaction and a policy/toxicity filter.

How I used them: I chained them as a gate — query injection filter → ACL-filtered retrieval → relevance gate (below threshold ⇒ "insufficient information") → grounded generation → faithfulness check (RAGAS faithfulness / NLI) → citation enforcement + PII redaction. Any ungrounded or below-threshold answer was blocked and escalated rather than returned, and every block was logged to improve the thresholds.

def guarded_rag(query, retriever, llm, rel_threshold=0.35):
    if injection_detector(query):
        return block("input rejected")

    hits = retriever.search(query, top_k=5, user=current_user)   # ACL-filtered
    if not hits or hits[0].score < rel_threshold:                # relevance gate
        return "I don't have enough information to answer that."

    context = "\n\n".join(f"[doc {h.id}] {h.text}" for h in hits)  # delimited = untrusted
    answer = llm.generate(grounded_prompt(query, context))

    if not is_faithful(answer, context):     # output groundedness guardrail
        log_for_review(query, answer); return "I couldn't find a grounded answer."
    return redact_pii(answer)                # + citations already embedded as [doc N]

This mirrors the agent guardrail stack in Q204; the faithfulness gate and document-injection defense are the parts unique to RAG. See also §14 (RAGAS) for measuring faithfulness offline.

  • What is RAG? Retrieval-Augmented Generation: fetch relevant passages from an external store and inject them into the prompt so the answer is grounded in your data, not just the model's parametric memory. (§1, §17 Q1)

  • When should you NOT use RAG? Pure reasoning/creative tasks needing no external facts; a corpus small enough to fit in context; when you need behavior/format change (fine-tune instead); ultra-low-latency paths where retrieval overhead hurts and the data is small/static.

Embeddings

What are embeddings?How do embeddings work?Why convert text into vectors?CosineEuclideanEmbedding models used?
  • What are embeddings? Dense numeric vectors that encode meaning; semantically similar text maps to nearby vectors.
  • How do embeddings work? A trained transformer maps text → a fixed-length vector in a space where distance ≈ semantic dissimilarity; trained with contrastive objectives so similar pairs sit close together.
  • Why convert text into vectors? It turns "meaning" into math, enabling fast nearest-neighbor similarity search. Keyword matching misses synonyms/paraphrase; vectors capture semantics.
  • Cosine similarity vs Euclidean distance? Cosine measures angle (direction), ignores magnitude — the standard for text (vectors often normalized → cosine ∝ dot product). Euclidean is straight-line distance, magnitude-sensitive. For normalized vectors they rank identically; default to cosine. (§6)
  • Embedding models used? text-embedding-3-small/large (OpenAI), all-mpnet-base-v2/all-MiniLM (sentence-transformers), BGE-M3 (multilingual), Voyage (incl. code). Choose by quality/cost/dimension/domain/max-tokens. (§3)

Chunking

What is chunking?Why chunk?preciselyIdeal chunk size?What is chunk overlap?Chunks too large?
  • What is chunking? Splitting documents into smaller passages before embedding/indexing.
  • Why chunk? Embedding models have token limits, smaller units retrieve more precisely, and LLM context is finite. Whole-doc embeddings blur meaning. (§4)
  • Ideal chunk size? Use-case dependent: ~500–800 tokens for Q&A (precise), ~1500–2000 for summarization (context). Evaluation-driven — measure RAGAS context precision/recall. (§17 Q4)
  • What is chunk overlap? Repeating ~10–20% of text between adjacent chunks so information spanning a boundary isn't lost.
  • Chunks too large? Dilute relevant info with noise, inflate context/cost, lower precision, may exceed the embedding token limit.
  • Chunks too small? Fragments lack context, the answer gets split across many chunks, and retrieval may miss the full picture.

Retrieval

What is Top-K retrieval?What is semantic search?What is hybrid search?Keyword vs vector search?Hybrid = bothWhat is re-ranking?
  • What is Top-K retrieval? Return the K most similar chunks to the query. K trades recall (more) vs noise/cost (fewer) — typically 3–10, then rerank.
  • What is semantic search? Search by meaning via embedding similarity, not exact words — finds paraphrases and synonyms.
  • What is hybrid search? Combine keyword (BM25) + vector (semantic) and fuse the rankings (e.g., RRF) — captures exact terms and meaning. (§9.4, §20.3)
  • Keyword vs vector search? Keyword (BM25) = exact term match, great for names/codes/rare tokens, misses synonyms. Vector = semantic, handles paraphrase, can miss exact rare tokens. Hybrid = both.
  • What is re-ranking? A second-stage cross-encoder scores (query, chunk) pairs jointly for accurate relevance; rerank the top ~50 candidates → keep top ~5 for the LLM. (§9, §17 Q3)
  • Why do irrelevant chunks get retrieved? Poor chunking, a domain-weak embedding model, ambiguous/short queries, no reranker, semantic-only missing exact terms, near-duplicate noise, or wrong k. Fix with hybrid + rerank + better chunking + query rewriting.

Vector Databases

  • Why use a vector database? Fast approximate nearest-neighbor (ANN) search over millions/billions of vectors, with metadata filtering, persistence, and scaling — brute-force cosine doesn't scale.
  • Vector DBs used? FAISS (library, prototyping), Pinecone (managed), Qdrant/Weaviate/Milvus (self-host or cloud), pgvector (Postgres), Chroma (local). (§17 Q6)
  • Vector DB vs relational DB? Relational = exact match/filtering on structured rows (B-tree, SQL). Vector = similarity search in high-dim space (ANN). Different query model; many vector DBs add metadata filters to do both.
  • How are embeddings stored? As float arrays (the vector) + an ANN index structure + metadata/payload + a reference to the source text; often quantized to save memory.
  • Indexing techniques? HNSW (graph; fast/accurate, RAM-heavy), IVF (clustering/inverted file), PQ/scalar quantization (compression), Flat (brute force, exact). Tune recall vs latency. (§5, §20.3)

  • How do you improve retrieval accuracy? Hybrid search, reranking, better chunking, query rewriting/multi-query/HyDE, contextual retrieval, metadata filtering, and domain/code-specific embeddings. (§8, §9)
  • How do you measure RAG quality? RAGAS: faithfulness, answer relevancy, context precision, context recall, plus end-to-end answer correctness and latency/cost. Build a golden test set and re-run on every change. (§14, §17 Q8)
  • What metrics do you track? Retrieval: precision@k, recall@k, MRR/nDCG, hit-rate. Generation: faithfulness, answer relevancy, correctness. Ops: P99 latency, cost/query, cache hit-rate, "I don't know" rate.
  • How do you cache retrieval results? Exact-match query cache + semantic cache (embed query, reuse if cosine > threshold) + document-embedding cache; TTL/invalidate on re-index. (§20.1)
  • What happens if the vector DB is unavailable? Degrade gracefully: serve from cache, fail over to a replica/secondary or keyword search, or answer "knowledge base temporarily unavailable" — never hallucinate. Prevent with replicas/HA, circuit breaker, and retries. (Mirrors agentic Q207/Q208)

  • User uploads a PDF and asks questions — full flow. Parse the PDF (text + tables) → chunk respecting structure → embed → store in a per-user namespace → on each question: embed query → ANN top-k (+ rerank) → assemble context within a token budget → LLM generates a grounded, cited answer → faithfulness/relevance gate. (§7, §18, §20)
  • Company data changes daily — keep the vector DB updated? Event-driven/scheduled incremental ingestion: detect changed docs by hash, re-embed + upsert by ID, delete removed chunks, keep updated_at metadata; full re-index only on model/chunking change. (§21.1)
  • Retrieved chunk doesn't contain the answer — what do you do? First check recall (is the gold chunk in top-k at all?). Missing → fix retrieval (hybrid, rerank, query rewrite, larger k, better chunking). Present but ignored → reorder/compress context + groundedness gate. Truly absent → return "I don't know." (§21.4)
  • Question outside the knowledge base — how to handle? A relevance-threshold gate: if top similarity < floor, don't force an answer — reply "I don't have that information," optionally fall back to web/general LLM with a disclaimer, or route to a human. (§20.4)
  • Retrieval returns 100 chunks — pick the best? Rerank with a cross-encoder, dedupe near-duplicates, apply MMR for diversity, filter by metadata/recency, then pack the top ~5 within the context token budget. (§9, §20.2)
  • RAG for millions of documents — how to build? Scalable vector DB (sharding + replicas, HNSW/IVF + quantization), distributed/batched ingestion, metadata filtering + routing to sub-indexes, hybrid search + rerank, caching, monitoring; keep the ingest path separate from the query path; incremental indexing. (§20.1, §5)
