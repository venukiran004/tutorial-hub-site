Fine-Tuning LLMs with LoRA & QLoRA — Simple Guide

The simplest path to understanding fine-tuning: what it is, why you'd use it (instead of RAG or prompting), the one formula that matters (and why the α/r part exists), and one complete example you can actually run.

•

1. What is fine-tuning?

smart new employeesending them to traininglots of examplesKey ideahow the model behavesnot the facts it knows

Imagine the model is a smart new employee. Fine-tuning is sending them to training so a new behavior becomes second nature.

You show the model lots of examples of the input → the answer you want, and it adjusts its internal numbers (weights) to copy that behavior.

   Base model            show it ~1000 examples            Fine-tuned model
   (generic)      ───────  of the behavior you want  ──►   (your style / skill)

🔑 Key idea: fine-tuning changes how the model behaves (style, tone, format, a skill) — not the facts it knows. (For facts, use RAG — see next section.)

•

2. Why fine-tune? (vs RAG & prompt engineering)

threePrompt engineeringRAGfactsFine-tuningbehavior

There are three ways to change what an LLM gives you. Using the employee analogy:

ApproachLike…What it changesBest for
Prompt engineeringgiving better instructionsnothing permanentquick, one-off tweaks
RAGhanding them a reference binderadds facts at answer timefresh / private knowledge
Fine-tuningsending them to trainingbehavior, baked into the weightsconsistent style / format / skill
WHICH ONE DO I PICK?
  Need fresh / private FACTS? ───────────────► RAG
  Just a quick one-off change? ──────────────► PROMPT ENGINEERING  (try this first!)
  Need the SAME behavior every time,
   a skill too complex to describe in words,
   or shorter prompts (lower cost)? ─────────► FINE-TUNE  (LoRA / QLoRA)

So why fine-tune at all?

  • Prompts are temporary and limited — long instructions cost tokens on every call, and the model can still drift off-style.
  • RAG adds knowledge, not behaviorit can fetch facts, but it can't make the model reliably write in your style/format or do a tricky task.
  • Fine-tuning bakes the behavior into the weights → consistent every time, no giant prompt to repeat, and it can learn patterns too complex to put into words.

👍 They also team up: fine-tune the style, use RAG for the facts.

•

3. How LoRA works — the one idea

weight gridsLoRA's trickFreeze itadd-ononly A and Bway fewer numbers

A model's knowledge sits in huge weight grids W (millions of numbers each). Retraining all of them is expensive.

LoRA's trick: don't touch W. Freeze it, and learn a small add-on made of two thin matrices, A and B. Their product B·A is the "change" you wanted (ΔW). You train only A and B — under 1% of the numbers.

   new weights  =  frozen W₀   +   B × A
                   (millions,       (tiny, the
                    untouched)       only part we train)

Because A and B are tiny, you train way fewer numbers — that's the whole reason LoRA is cheap:

4. The formula (and why α/r)

base + add-onfrozentrainablerank8–16strong

For one layer, the output is just base + add-on:

$$ h \;=\; \underbrace{W_0\,x}{\text{base (frozen)}} \;+\; \underbrace{\tfrac{\alpha}{r}\,(B\,A)\,x}{\text{LoRA add-on (trained)}} $$

SymbolMeaning (simple)
W₀the original weights — frozen, never change
xthe input to the layer
B, Athe small trainable matrices (B·A is the change)
rthe rank = size of the add-on = its capacity. Typical: 8–16
αhow strong the add-on is

Why the α / r part? (it's a volume knob)

α/r controls how loud the add-on is — how strongly B·A shifts the output.

  • α = the strength you choose.
  • We divide by r so that changing the rank doesn't accidentally change the strength. (A bigger r makes B·A produce bigger numbers; dividing by r cancels that out.)
  • This lets you tune r (capacity) and α (strength) separately, without re-tuning everything each time.

✅ Simple rule: set α = 2 × r and forget it — then you only ever tweak r.

•

5. QLoRA — why it fits on one GPU

Default choiceQLoRA

QLoRA = LoRA + store the frozen base model in 4-bit (instead of 16-bit). The add-on (A, B) is the only thing trained, so squashing the frozen base to 4-bit cuts memory hugely with almost no quality loss.

👉 Default choice: use QLoRA — it lets a 7–8B model train on a single 16–24 GB GPU.

•

6. What happens during training

About A and Bnothingtrains themproper learned weights

Each training example flows through the model like this:

Text
  ↓
Tokenizer          split the text into pieces
  ↓
Token IDs          each piece → a number
  ↓
Embedding          each number → a vector
  ↓
Transformer        the model "thinks"      ← LoRA's A and B sit here
  ↓
Predicted Tokens   the model's guess
  ↓
Loss               how wrong the guess was
  ↓
Backpropagation    figure out which way to nudge
  ↓
Weight Updates     only A and B change   (base stays frozen ❄️)

About A and B: they start tiny (B is all zeros, A is small random) — so at first the add-on does nothing and the model behaves exactly like the base. Each pass trains them a little. After enough passes, A and B hold the proper learned weights. That's all fine-tuning is.

•

7. One complete example (step by step)

QLoRAanswer like a pirateStep 1 — Install the librariesStep 2 — A tiny datasetStep 3 — Load the model in 4-bitStep 6 — Test it (see the change)

A full QLoRA fine-tune on a single GPU. The task is tiny and obvious — teach a small chat model to answer like a pirate — so the change is easy to see. (Real tasks need ~500–1000+ examples; we use 6 just to demonstrate.)

Step 1 — Install the libraries.

Step 2 — A tiny dataset (each row = a prompt and the reply we want):

pairs = [
    ("Hello, how are you?",       "Ahoy! I be doin' grand, matey! Arrr!"),
    ("What's the weather today?", "Arrr, the skies be clear fer sailin', cap'n!"),
    ("Can you help me?",          "Aye! I be at yer service, ye fine scallywag!"),
    ("Thank you very much.",      "Yer most welcome, me hearty! Arrr!"),
    ("Tell me a joke.",           "Why be pirates great singers? They hit the high C's! Arrr!"),
    ("Goodbye!",                  "Fair winds to ye, matey! Until we meet again! Arrr!"),
]

Step 3 — Load the model in 4-bit (this is the "Q" in QLoRA):

import torch
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig

MODEL = "Qwen/Qwen2.5-1.5B-Instruct"   # small + open, downloads without sign-up

bnb = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4",
                         bnb_4bit_compute_dtype=torch.bfloat16)

tok = AutoTokenizer.from_pretrained(MODEL)
tok.pad_token = tok.eos_token
model = AutoModelForCausalLM.from_pretrained(MODEL, quantization_config=bnb, device_map="auto")

The base is now stored in 4-bit (small), but the math still runs in bfloat16.

Step 4 — Turn each pair into a chat the model understands:

from datasets import Dataset

def to_text(prompt, reply):
    msgs = [{"role": "user", "content": prompt},
            {"role": "assistant", "content": reply}]
    return tok.apply_chat_template(msgs, tokenize=False)   # adds the model's chat tokens

dataset = Dataset.from_list([{"text": to_text(p, r)} for p, r in pairs])

Step 5 — Add the LoRA add-on and train it:

from peft import LoraConfig
from trl import SFTTrainer, SFTConfig

lora = LoraConfig(
    r=16, lora_alpha=32,            # rank=16, strength α=2×r  (the α/r knob = 2)
    lora_dropout=0.05, bias="none", task_type="CAUSAL_LM",
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                    "gate_proj", "up_proj", "down_proj"],   # where to add the adapter
)

cfg = SFTConfig(
    output_dir="./pirate-lora",
    num_train_epochs=10,            # many passes — only because the dataset is tiny
    per_device_train_batch_size=2,
    learning_rate=2e-4,             # step size
    bf16=True,
    optim="paged_adamw_8bit",       # memory-friendly
)

trainer = SFTTrainer(model=model, args=cfg, train_dataset=dataset,
                     peft_config=lora, processing_class=tok)
trainer.train()                     # runs the loop from §6
trainer.save_model("./pirate-lora") # saves ONLY the tiny adapter (~tens of MB)

Step 6 — Test it (see the change):

def ask(q):
    ids = tok.apply_chat_template([{"role": "user", "content": q}],
                                  add_generation_prompt=True, return_tensors="pt").to(model.device)
    out = model.generate(ids, max_new_tokens=60, do_sample=False)
    return tok.decode(out[0][ids.shape[1]:], skip_special_tokens=True)

print(ask("Hi, can you recommend a book?"))
BEFORE training:  "Sure! A great book is 'Sapiens' by Yuval Noah Harari."
AFTER  training:  "Arrr! Ye be wantin' a good yarn? Set sail with 'Treasure Island', matey!"

Step 7 (optional) — Merge the add-on into the model so it's a normal standalone model:

from peft import PeftModel
base   = AutoModelForCausalLM.from_pretrained(MODEL, torch_dtype=torch.bfloat16, device_map="auto")
merged = PeftModel.from_pretrained(base, "./pirate-lora").merge_and_unload()  # folds B·A into W₀
merged.save_pretrained("./pirate-merged")
tok.save_pretrained("./pirate-merged")

In one breath: load model in 4-bit → bolt on a tiny LoRA add-on → train only that on a few examples → the model picks up the pirate voice → (optionally) merge it back into a plain model.

9. Quick FAQ

Q: Fine-tuning or RAG?fine-tunefactsRAGQ: LoRA or QLoRA?QLoRA

Q: Fine-tuning or RAG? Behavior/style/format/skill → fine-tune. Fresh or private facts → RAG. Often: both.

Q: LoRA or QLoRA? Same tiny add-on; QLoRA just stores the frozen base in 4-bit. On one consumer GPU → QLoRA. Lots of VRAM to spare → LoRA.

Q: How much data do I need? Quality > quantity. 1K–10K clean, consistent examples usually beat 100K messy ones. Always keep ~10–20% aside to check for overfitting.

Q: Does fine-tuning add new facts? Not reliably — it changes behavior, not knowledge. Use RAG for facts.

LLM Training & Alignment — Pretraining → SFT → RLHF → DPO → GRPO

Scope: how a raw next-token predictor becomes a helpful assistant. The full post-training stack — supervised fine-tuning, reward modelling, RLHF/PPO, DPO and its cousins, GRPO and RLVR, reasoning models and test-time compute — with the formulas, worked numbers, and from-scratch code for each.

Why this file exists: 03_Fine_Tuning_LLM.md answers "how do I adapt a model cheaply?" (LoRA/QLoRA — a parameter question). This file answers "how does a model learn what a good answer even is?" (an objective question). They're different axes: you can do DPO with LoRA, or full-parameter SFT with no alignment at all.

Key Definitions (read first)

Post-trainingEverything after pretraining: SFT + alignment. Turns a base model into an assistant. Also called alignment.

Preference dataTriples (prompt, chosen, rejected) — a human (or AI) said "this answer is better than that one".

0. The one idea

A pretrained LLM is not trying to be helpful. It is trying to predict the most likely next token given the internet. Ask it "What is the capital of France?" and a plausible continuation is "What is the capital of Germany? What is the capital of Spain?" — because on the internet, questions come in lists.

Post-training fixes this in two moves:

SFT       "Here is what a good answer looks like."      ← imitation      (cheap, gets you 80%)
ALIGNMENT "Here is which of two answers is better."     ← preference     (expensive, gets the last 20%)

Why the second stage at all? Because it is far easier for a human to rank two answers than to write the perfect one. You cannot hire people to hand-write a million ideal responses, but you can have them click "A is better" a million times. Alignment is the machinery for converting cheap comparisons into model weights.

The whole pipeline:

  Raw text (trillions of tokens)
        │  next-token prediction
        ▼
  BASE MODEL ─────────────────────────────────► completes text, ignores instructions
        │  SFT on (instruction, answer) pairs
        ▼
  SFT MODEL  ─────────────────────────────────► follows instructions, mediocre judgement
        │
        ├── path A: RM + PPO      (classic RLHF — OpenAI/Anthropic 2022)
        ├── path B: DPO           (2023 — no RM, no RL loop, the default for most teams)
        └── path C: GRPO + RLVR   (2025 — reasoning models: DeepSeek-R1 style)
        ▼
  ALIGNED MODEL ──────────────────────────────► helpful, harmless, formatted, calibrated
1. Stage 1 — Pretraining

You almost certainly will not do this (it costs millions), but interviewers ask about it because it sets up everything else.

Objective — next-token prediction, i.e. cross-entropy over the vocabulary:

L_pretrain  =  − (1/T) Σ_t  log P_θ( x_t | x_<t )

That's it. One loss, no labels, no humans. Everything the model knows arrives through this.

Compute scaling (Chinchilla, 2022). The rule of thumb interviewers want:

Training FLOPs ≈ 6 · N · D          N = parameters, D = training tokens
Compute-optimal:  D ≈ 20 · N        (~20 tokens per parameter)

Worked: a 7B model, compute-optimally trained → D ≈ 140B tokens → FLOPs ≈ 6 × 7e9 × 1.4e11 ≈ 5.9 × 10²¹.

The nuance that scores points: Chinchilla optimises training cost. In production you serve the model billions of times, so inference cost dominates — which is why modern open models are deliberately "over-trained" (Llama-3 8B saw ~15T tokens, ~1,875 tokens/param, ~90× Chinchilla). You knowingly waste training FLOPs to get a smaller model of the same quality, because the small model is cheaper forever afterwards.

What you actually control at this stage: data mix and dedup. Quality of the corpus beats almost every architectural tweak.

2. Stage 2 — Supervised Fine-Tuning (SFT)

Intuition

Show the model thousands of examples of the shape of a good conversation and it learns the shape. This is plain supervised learning — same loss as pretraining, different data.

The one detail that matters: loss masking

You train on (prompt, response) pairs but you only compute loss on the response tokens. Training on the prompt tokens teaches the model to generate user questions, which is not the job.

# From scratch: build labels with the prompt masked out.
IGNORE = -100                      # PyTorch cross-entropy ignores this index

prompt_ids   = tok("<|user|>\nSummarise this email.\n<|assistant|>\n").input_ids
response_ids = tok("Here is the summary: ...<|end|>").input_ids

input_ids = prompt_ids + response_ids
labels    = [IGNORE] * len(prompt_ids) + response_ids   # ← only the answer is supervised

loss = F.cross_entropy(
    logits[:, :-1].reshape(-1, V),                      # shift: predict token t+1
    torch.tensor(labels[1:]).reshape(-1),
    ignore_index=IGNORE,
)

Interview trap: "Your SFT model started asking itself questions." → You forgot to mask the prompt. Classic.

Chat templates

Every model family has its own special-token layout. Using the wrong one silently degrades quality — the model never sees the turn boundaries it was trained on.

messages = [{"role": "user", "content": "Summarise this email."},
            {"role": "assistant", "content": "Here is the summary: ..."}]
text = tokenizer.apply_chat_template(messages, tokenize=False)   # always use this, never hand-format

How much data?

GoalExamples needed
Output format / JSON shape100 – 1,000
Domain tone + task behaviour1,000 – 10,000
General instruction-following from scratch10,000 – 100,000+

Quality ≫ quantity. The LIMA result (1,000 carefully curated examples ≈ far larger noisy sets) is the standard citation. A few hundred bad examples can undo thousands of good ones.

3. Stage 3a — The Reward Model

Intuition

You want a function that says "this answer is worth 7.2 and that one is worth 3.1". But humans can't give calibrated absolute scores — ask ten people to rate an answer 1-10 and you get ten different scales. They can reliably say "A is better than B."

So: collect comparisons, and fit a scalar-scoring model whose differences explain those comparisons.

The formula — Bradley-Terry

Model the probability that a human prefers answer A over B as a sigmoid of the reward gap:

P(A ≻ B)  =  σ( r(A) − r(B) )          σ(z) = 1 / (1 + e^−z)

Maximise the likelihood of the observed human choices → minimise:

L_RM  =  − E_(x, y_w, y_l) [ log σ( r_θ(x, y_w) − r_θ(x, y_l) ) ]

     y_w = chosen ("winner"),  y_l = rejected ("loser")

Read it in words: push the winner's score above the loser's score; stop pushing once the gap is comfortably positive (the sigmoid saturates).

Worked numbers

Suppose for one pair the RM currently outputs r(y_w) = 1.5, r(y_l) = 0.9.

gap  = 1.5 − 0.9 = 0.6
σ(0.6) = 1 / (1 + e^−0.6) = 1 / (1 + 0.5488) = 0.6457
loss = −log(0.6457) = 0.4372

Now suppose the model had it backwards: r(y_w) = 0.4, r(y_l) = 1.7.

gap  = −1.3 → σ(−1.3) = 0.2142 → loss = −log(0.2142) = 1.5412     ← 3.5× the penalty

And when it's already confident: gap = 4.0 → σ = 0.982 → loss = 0.018. Near zero — no more gradient. That's the saturation: the RM stops burning capacity on pairs it already ranks correctly.

From scratch

import torch, torch.nn as nn, torch.nn.functional as F

class RewardModel(nn.Module):
    """Base LLM + a scalar head on the LAST token. One number per (prompt, answer)."""
    def __init__(self, backbone, hidden):
        super().__init__()
        self.backbone = backbone                  # e.g. the SFT model, LM head removed
        self.v_head   = nn.Linear(hidden, 1, bias=False)

    def forward(self, input_ids, attention_mask):
        h = self.backbone(input_ids, attention_mask=attention_mask).last_hidden_state
        last = attention_mask.sum(1) - 1                          # index of final real token
        pooled = h[torch.arange(h.size(0)), last]                 # (B, hidden)
        return self.v_head(pooled).squeeze(-1)                    # (B,)

def rm_loss(model, chosen, chosen_mask, rejected, rejected_mask):
    r_w = model(chosen,   chosen_mask)
    r_l = model(rejected, rejected_mask)
    return -F.logsigmoid(r_w - r_l).mean()        # == BCE-with-logits on the gap

-F.logsigmoid(gap) rather than -torch.log(torch.sigmoid(gap)) — numerically stable for large negative gaps.

Practical notes

  • Initialise the RM from the SFT model, not the base model — it needs to understand the task distribution.
  • Train ~1 epoch. RMs overfit fast and an overfit RM is worse than a small one.
  • The absolute scale is meaningless (only differences matter), so normalise scores before use.
  • The single most useful RM metric is preference accuracy on held-out pairs — how often does r(y_w) > r(y_l)? Below ~65% and downstream RL will chase noise.
4. Stage 3b — RLHF with PPO

Intuition

Now you have a scorer. Let the model generate answers, score them, and push its weights toward whatever scored well — with a leash so it doesn't wander off into gibberish that happens to fool the scorer.

The objective

max_θ   E_{x~D, y~π_θ} [ r_φ(x, y) ]   −   β · KL( π_θ(·|x) ‖ π_ref(·|x) )
        └──── get a high reward ────┘       └──── but stay near the SFT model ────┘

π_ref is the frozen SFT model. β (typically 0.01–0.1) sets the leash length.

Why the KL term is non-negotiable: without it the policy collapses onto whatever degenerate text maximises the RM — repeated flattery, huge lists, a specific formatting tic. You get a model with a phenomenal reward score that is useless to humans. In practice the KL is applied as a per-token penalty folded into the reward:

R_t  =  r_φ(x, y) · 1[t is last token]  −  β · ( log π_θ(y_t|·) − log π_ref(y_t|·) )

PPO's clipped surrogate

PPO's contribution is how you take the gradient step without blowing up the policy:

ρ_t(θ) = π_θ(y_t | s_t) / π_old(y_t | s_t)                    # importance ratio

L_PPO = E[ min( ρ_t · Â_t ,  clip(ρ_t, 1−ε, 1+ε) · Â_t ) ]     # ε ≈ 0.2

Â_t is the advantage (usually GAE) — "how much better than expected was this token?". The clip says: if this update would move the probability of a token more than ±20%, stop giving credit for going further. It caps how far one batch can drag the policy.

The cost: four models in memory

ModelRoleTrained?
Policy π_θThe LLM you're improving✅
Reference π_refFrozen SFT model, for the KL leash❌
Reward model r_φScores completions❌
Value/critic V_ψPredicts expected reward → baseline for Â✅

For a 7B policy that's roughly 4 × 7B parameters resident, two of them with optimiser states. This memory bill — plus the need to generate samples every step, plus PPO's hyperparameter sensitivity — is exactly why DPO and GRPO exist.

The loop

for batch of prompts:
    1. GENERATE   completions from π_θ                (slow — this is autoregressive sampling)
    2. SCORE      each with r_φ                       → scalar reward
    3. PENALISE   per-token KL vs π_ref               → shaped reward R_t
    4. ESTIMATE   advantages Â_t via GAE using V_ψ
    5. UPDATE     π_θ (clipped surrogate) and V_ψ (MSE), a few inner epochs
5. DPO — deleting the reward model

Intuition

Here's the insight: the KL-constrained objective above has a closed-form optimum. If you know what the optimal policy looks like as a function of the reward, you can run that backwards — write the reward as a function of the policy — and then you never need to build a reward model at all. Train directly on the preference pairs.

The derivation (three lines, worth memorising)

•

1. The optimum of the RLHF objective is a reweighted reference policy:

π*(y|x)  =  (1 / Z(x)) · π_ref(y|x) · exp( r(x,y) / β )
•

2. Invert it — solve for the reward:

3. Substitute into Bradley-TerrycancelsThe whole trick in one sentence+1.0+0.5What β does here
r(x,y)  =  β · log( π*(y|x) / π_ref(y|x) )  +  β · log Z(x)

3. Substitute into Bradley-Terry. The intractable partition function Z(x) depends only on x, so it appears in both terms of the difference and cancels:

L_DPO = − E [ log σ(  β·log( π_θ(y_w|x) / π_ref(y_w|x) )  −  β·log( π_θ(y_l|x) / π_ref(y_l|x) )  ) ]
                      └────────── "implicit reward" of the winner ─────┘   └──── of the loser ────┘

The whole trick in one sentence: the language model is secretly its own reward model — the log-ratio against the frozen reference is the reward, so you can optimise preferences with a supervised loss.

Worked numbers

Say for one pair the summed response log-probs are:

log π_θlog π_reflog-ratio log π_θ − log π_ref
chosen y_w−12.0−13.0+1.0 (policy likes it more than the reference did)
rejected y_l−15.0−15.5+0.5 (policy also likes it more — but less so)

With β = 0.1:

implicit reward (chosen)   = 0.1 × (−12.0 − (−13.0)) = 0.1 × 1.0  = 0.10
implicit reward (rejected) = 0.1 × (−15.0 − (−15.5)) = 0.1 × 0.5  = 0.05
margin = 0.10 − 0.05 = 0.05
loss   = −log σ(0.05) = −log(0.5125) = 0.6685

Compare to a well-separated pair (margin 1.2): −log σ(1.2) = 0.2634. And an inverted pair (margin −0.8): −log σ(−0.8) = 1.1711. Same saturating shape as the RM loss — because it is the RM loss, with the LLM playing the role of the RM.

What β does here: it scales the margin before the sigmoid. Small β (0.01) → tiny margins → the sigmoid is near-linear → aggressive updates, more drift from π_ref. Large β (0.5) → the model is held tightly to the reference. β is the leash, exactly as in PPO. Typical: 0.1.

From scratch

import torch, torch.nn.functional as F

def sequence_logprob(model, input_ids, labels, attn):
    """Sum of log P(token) over the RESPONSE tokens only (labels == -100 elsewhere)."""
    logits = model(input_ids, attention_mask=attn).logits[:, :-1]      # predict t+1
    tgt    = labels[:, 1:]
    mask   = tgt != -100
    tgt    = tgt.masked_fill(~mask, 0)
    lp     = torch.log_softmax(logits, dim=-1).gather(-1, tgt.unsqueeze(-1)).squeeze(-1)
    return (lp * mask).sum(-1)                                          # (B,)

def dpo_loss(policy, ref, batch, beta=0.1):
    pi_w  = sequence_logprob(policy, batch["chosen_ids"],   batch["chosen_labels"],   batch["chosen_mask"])
    pi_l  = sequence_logprob(policy, batch["rejected_ids"], batch["rejected_labels"], batch["rejected_mask"])
    with torch.no_grad():                                               # reference is FROZEN
        ref_w = sequence_logprob(ref, batch["chosen_ids"],   batch["chosen_labels"],   batch["chosen_mask"])
        ref_l = sequence_logprob(ref, batch["rejected_ids"], batch["rejected_labels"], batch["rejected_mask"])

    margin = beta * ((pi_w - ref_w) - (pi_l - ref_l))                   # the whole algorithm
    loss   = -F.logsigmoid(margin).mean()

    metrics = {                                                         # log these — see below
        "reward_chosen":   (beta * (pi_w - ref_w)).mean().item(),
        "reward_rejected": (beta * (pi_l - ref_l)).mean().item(),
        "reward_accuracy": (margin > 0).float().mean().item(),          # target: 0.65–0.80
        "margin":          margin.mean().item(),
    }
    return loss, metrics

DPO can only re-rank behaviours already latent in the model. Hence the modern compromise: online/iterative DPO — generate fresh completions, label them with an RM or a judge, run DPO, repeat.

6. The DPO family — ORPO, KTO, SimPO, IPO

Each drops one requirement of DPO. Know what each removes — that's the interview answer.

MethodRemovesLoss ideaUse when
DPOthe reward model + RL looplog-sigmoid of reference-relative marginDefault; you have pairs and an SFT model
ORPOthe reference model and the separate SFT stageSFT loss + λ · odds-ratio penalty on the rejected answerOne-stage pipeline, tight memory — go base → aligned directly
KTOthe need for pairsProspect-theory value function on individual good/bad labelsYour data is thumbs-up/thumbs-down feedback, not A-vs-B
SimPOthe reference modelLength-normalised average log-prob as the implicit reward + a target margin γDPO output is drifting long; you want the length bias fixed at the loss

ORPO in one line (the useful one for small teams):

L_ORPO = L_SFT  +  λ · L_OR,        L_OR = − log σ( log odds(y_w) − log odds(y_l) )

It learns the good answer and pushes away from the bad one in the same step, with no reference model and no prior SFT run. Two stages collapse into one.

KTO in one line: you no longer need someone to compare two answers — a single "this response was bad" is enough. That is a massive practical difference, because production thumbs-down data is exactly that shape and pairwise data is not.

7. GRPO — deleting the critic

Intuition

PPO needs a value network to answer "how good was this expected to be?" — that's a whole second trainable LLM. GRPO's insight: sample G answers to the same prompt and let the group's mean be the baseline. If an answer beats its siblings, reinforce it; if it lags them, suppress it. No critic needed.

PPO :   advantage = actual reward − critic's prediction        (learned baseline, extra model)
GRPO:   advantage = actual reward − mean reward of G siblings  (empirical baseline, free)

The formula

For prompt x, sample a group {y_1 … y_G} and score each:

Â_i  =  ( r_i − mean(r_1..r_G) )  /  std(r_1..r_G)         ← group-normalised advantage

L_GRPO = −E[ (1/G) Σ_i  min( ρ_i·Â_i, clip(ρ_i, 1−ε, 1+ε)·Â_i ) ]  +  β·KL(π_θ ‖ π_ref)

Same clipped surrogate as PPO, different advantage, one fewer model.

Worked numbers

Prompt: a math problem. Sample G = 6 answers, reward = 1 if the final answer is correct else 0.

rewards r = [1, 0, 1, 0, 0, 1]
mean = 3/6 = 0.5
std  = sqrt( mean((r−0.5)²) ) = sqrt(0.25) = 0.5

Â    = (r − 0.5)/0.5  =  [ +1, −1, +1, −1, −1, +1 ]

Correct answers get advantage +1 (reinforce every token in them), wrong ones −1 (suppress). Clean and intuitive.

The degenerate case interviewers probe: if all 6 are correct, std = 0 → advantage is 0/0 → no gradient at all. Same if all 6 are wrong. So GRPO learns only from prompts where the model is partly right — which means prompt difficulty curation is part of the algorithm, not a nicety. Too easy or too hard, and the batch teaches nothing.

From scratch

import torch

def grpo_advantages(rewards, eps=1e-4):
    """rewards: (num_prompts, G). Returns per-sample advantages, normalised within each group."""
    mean = rewards.mean(dim=1, keepdim=True)
    std  = rewards.std(dim=1, keepdim=True)
    return (rewards - mean) / (std + eps)          # eps guards the all-same-reward case

r = torch.tensor([[1., 0., 1., 0., 0., 1.]])
print(grpo_advantages(r))     # tensor([[ 0.9129, -0.9129,  0.9129, -0.9129, -0.9129,  0.9129]])
                              # (0.913 not 1.0 because torch.std uses the n−1 denominator)

Then every token of sample i is weighted by Â_i in the clipped surrogate — a sequence-level reward broadcast to token-level gradients.

Why GRPO took over for reasoning

  1. No critic → ~40% less memory, and no critic-collapse failure mode (a bad value head silently ruins PPO).
  2. Rewards for math/code are binary and verifiable, which is exactly the regime where a learned value function is hardest to fit and least necessary.
  3. Sampling G answers per prompt is already what you do for reasoning models, so the group comes free.
8. RLVR & reasoning models

The shift

Classic RLHF: reward = learned model of human taste → can be hacked, hard to trust, expensive to maintain. RLVR: reward = a program.

def reward(problem, completion):
    if problem.type == "math":
        return 1.0 if extract_boxed(completion) == problem.gold else 0.0
    if problem.type == "code":
        return fraction_of_unit_tests_passing(completion, problem.tests)
    if problem.type == "format":
        return 1.0 if re.search(r"<think>.*?</think>.*", completion, re.S) else 0.0

Why it changes everything: a verifier cannot be flattered. The model cannot write a longer, more confident answer to make a unit test pass. This removes the ceiling that reward-model overoptimization imposes — you can run RL for far longer without the reward becoming a lie.

The limitation, and the honest interview answer: RLVR only works where correctness is checkable — math, code, formal logic, structured extraction, tool-call validity. For "write a warm apology email" there is no verifier, so preference-based methods (DPO/RLHF) remain necessary. Real pipelines use both: RLVR on verifiable domains, DPO on subjective ones.

How reasoning models are trained (DeepSeek-R1 shape)

  1. (optional) Cold-start SFT on a few thousand long chain-of-thought examples → readable reasoning format
  2. GRPO + verifiable rewards on math/code → the model learns to think longer
  3. Rejection sampling: keep the RL model's CORRECT traces → new SFT data → consolidate
  4. A final preference/safety pass (DPO or RLHF) → helpfulness + harmlessness

The famous result: nobody told the model to think longer. Given only "correct answer = 1", response length grew on its own over training — the model discovered that backtracking, re-checking, and enumerating cases raise its hit rate. Emergent behaviours like "Wait, let me reconsider…" appear without ever being demonstrated.

I route: cheap single-pass for easy queries, verified sampling for hard ones." That routing idea connects directly to 21_LLM_Cost_and_Token_Optimization.md.

10. Reward hacking & overoptimization

The core phenomenon (Goodhart's law, applied): the RM is a proxy for human preference. Optimise the proxy hard enough and the two come apart — true quality peaks and then falls while the RM score keeps climbing.

  quality
    ▲          ┌── RM score (proxy) — keeps rising
    │      ────┘
    │    ╱‾‾‾╲            ← TRUE human preference: peaks, then degrades
    │   ╱      ╲___
    └──────────────────────────► KL distance from π_ref
              ↑
        stop training here

The catalogue

HackWhat the model learnsFix
Length biasLonger = higher reward (annotators mistake length for effort)Length-normalise the RM; length-penalty term; SimPO; report win-rate controlled for length
SycophancyAgree with the user's premise even when wrongInclude preference pairs where the correct answer contradicts the user
Formatting ticsAlways bullet points, always bold headersDiversify RM training data across formats
HedgingNever commit → never wrong → never penalisedReward decisiveness explicitly; measure abstention rate
Confident hallucinationFluent + assertive scores well; truth isn't checkedVerifiable rewards; grounding/citation checks

Detection & control

  • Monitor KL divergence from π_ref as a first-class metric. Rising KL + rising reward + flat/falling human eval = you are overoptimizing. Early-stop on it.
  • Hold out a separate RM ("gold RM") that never trains the policy, and watch for divergence between the two scores.
  • Track mean output length every eval. If it creeps up 40% during alignment, you've bought length, not quality.
  • Keep a small human eval set that never touches training. The RM cannot grade its own homework.
11. RLAIF & Constitutional AI

Human preference labels cost $1–5 each and take weeks. RLAIF replaces the labeller with an LLM:

Prompt → sample 2 responses → ask a strong LLM "which is better, and why?" → preference pair → DPO/RM

At a modest quality cost you get labels for ~$0.001 each and a full dataset overnight. In practice most teams use hybrid: AI labels for volume, human labels for calibration and for the safety-critical slice.

Constitutional AI (Anthropic) adds structure — the AI critiques against an explicit written set of principles:

  1. SUPERVISED PHASE response → "Critique this against principle: 'do not assist with harm'" → revision → SFT on the (prompt, revised response) pairs
  2. RL PHASE sample pairs → an AI judge picks the more constitution-compliant one → preference model → RL

Why it matters beyond safety: the alignment target becomes a document you can read, version, and argue about rather than the implicit average taste of a labelling vendor. That auditability is the answer when an interviewer asks how you'd govern model behaviour.

This connects to 23_LLM_Guardrails_and_Safety.md — note the distinction: alignment shapes the model's tendencies; guardrails are a runtime filter. You need both, because alignment is probabilistic and guardrails are deterministic.

12. Distillation & model merging

Distillation — transfer capability to a smaller model

TypeSignal usedNotes
Response (black-box)Teacher's generated text → SFT the studentWhat you can do with an API-only teacher. Works surprisingly well.
Logit (white-box)KL between full output distributionsMuch richer signal per token; needs weight access + shared tokenizer
Reasoning distillationTeacher's full chain-of-thought → studentThe big 2025 result: a 7B model SFT'd on a reasoning model's traces beats the same 7B trained with RL directly. Distilling reasoning is cheaper than discovering it.
L_distill = α · CE(student, hard_labels)  +  (1−α) · τ² · KL( student/τ ‖ teacher/τ )

τ (temperature) softens both distributions so the student learns the teacher's relative preferences among wrong answers, not just the argmax. The τ² restores gradient magnitude.

Model merging — combine fine-tunes without retraining

You have three LoRAs (a code model, a chat model, a domain model) and want one model. Merging combines weights arithmetically — zero training compute.

MethodIdea
Linear / weighted averageθ = Σ wᵢ·θᵢ. Simplest; works when models share an ancestor.
Task arithmeticTask vector τᵢ = θᵢ − θ_base; add them: θ = θ_base + Σ λᵢ·τᵢ. You can also subtract a vector to remove a behaviour.
TIESTrim small deltas, elect a sign per parameter, average only the agreeing ones — resolves interference between tasks.
DARERandomly drop most deltas and rescale the rest; surprisingly lossless, and composes with TIES.
SLERPSpherical interpolation between exactly two models; preserves vector norms better than a straight average.

Where this shows up in practice: merging is the standard cheap fix for catastrophic forgetting — merge your domain fine-tune back with the base/instruct model at ~0.3–0.5 weight and you recover general ability while keeping most of the domain gain.

13. Choosing a method — decision guide
Do you need the model to know NEW FACTS?
  └─► No fine-tuning. Use RAG.  →  05_RAG_and_Vector_Stores.md
      (Fine-tuning teaches behaviour, not facts. This mistake is the #1 interview filter.)

Do you need a specific FORMAT / TONE / TASK behaviour?
  └─► SFT (+ LoRA). 1k–10k examples. Stop here — most projects should.

Is the model's behaviour "correct but not preferred" — too verbose, wrong register,
unsafe edge cases, doesn't pick the answer humans like?
  ├─ You have PAIRWISE data ..................... DPO   (β=0.1, lr≈5e-7, 1 epoch)
  ├─ You have THUMBS UP/DOWN only ............... KTO
  ├─ You want ONE stage from a base model ....... ORPO
  └─ Outputs keep getting longer ................ SimPO

Do you have a PROGRAMMATIC verifier (tests, exact answer, schema)?
  └─► GRPO + RLVR. This is how you build a reasoning/agentic model.

Do you have a labelling budget, an RM, GPUs for 4 models, and a team?
  └─► PPO/RLHF. Highest ceiling, highest cost. Rarely the right first move.

Realistic 2026 pipeline for a product team:

open instruct model  →  LoRA SFT (5k curated examples)  →  LoRA DPO (2k preference pairs
harvested from production thumbs-down + LLM-judge labels)  →  merge  →  eval-gated deploy

That's two GPU-days, not a research programme — and it is the answer that lands in an interview, because it's the one that ships.

15. Interview Deep Dive
•

Q1. Walk me through how a base model becomes ChatGPT.

Three stages. Pretraining is next-token prediction over trillions of tokens — that gives knowledge and fluency but no instruction-following; a base model will happily continue your question with more questions. SFT is supervised learning on (instruction, ideal answer) pairs with the loss masked to the response — that teaches the shape of assistant behaviour, and it gets you most of the way. Then alignment converts cheap human comparisons into weights: classically, fit a Bradley-Terry reward model on preference pairs and optimise the LLM against it with PPO plus a KL leash to the SFT model; modern practice usually replaces that with DPO, which proves the LLM's own log-ratio against the frozen reference is the reward, so you get the same objective as a supervised loss with two models instead of four. For reasoning models you add a fourth stage: GRPO against verifiable rewards.

•

Q2. Why not just do more SFT instead of RLHF/DPO?

Two reasons. First, data economics: SFT needs someone to write the ideal answer; preference learning only needs someone to pick between two. Comparisons are an order of magnitude cheaper and far more consistent between annotators. Second, and more fundamental — SFT can only ever imitate the best answer in your dataset, and it gives no signal about what to avoid. Preference learning has an explicit negative: it actively pushes probability mass away from the rejected response. That's how you fix subtle failures like sycophancy or verbosity, where you can't easily write down the right answer but you can always recognise the wrong one.

•

Q3. Explain DPO's derivation.

Start from the KL-regularised RLHF objective. It has a closed-form optimum: the optimal policy is the reference policy reweighted by the exponentiated reward over β, divided by a partition function Z(x). Invert that to express the reward in terms of the policy — reward equals β times the log-ratio of policy to reference, plus β log Z(x). Now substitute into the Bradley-Terry likelihood, which only ever uses the difference of two rewards for the same prompt. Z(x) depends only on x, so it cancels. What's left is a log-sigmoid of β times the difference of two log-ratios — a supervised loss over preference pairs, no reward model, no sampling, no RL machinery.

•

Q4. What does β control in DPO, and what happens at the extremes?

β is the leash to the reference model — the same role it plays in the PPO KL penalty. It scales the implicit-reward margin before the sigmoid. Small β, say 0.01, means small margins land in the near-linear region of the sigmoid, so gradients stay large and the policy drifts far from the reference — you get strong preference-fitting but risk degeneration and capability loss. Large β, say 0.5, holds the policy tight and the model barely changes. 0.1 is the standard start. In practice I tune it by watching KL drift and output length rather than by looking at the loss.

•

Q5. Why does GRPO drop the value network, and what breaks if the group is homogeneous?

PPO's critic exists to supply a baseline — "how good was this expected to be?" — so advantages aren't just raw rewards. GRPO gets that baseline empirically: sample G answers to the same prompt and use the group's mean and standard deviation, so advantage is the z-score of a sample within its own group. That deletes an entire trainable LLM from memory and removes the critic-collapse failure mode. The cost is that when all G samples get the same reward — all correct or all wrong — the standard deviation is zero and the advantages vanish, so the prompt contributes no gradient. That makes curriculum a real part of the algorithm: you need prompts sitting at the model's frontier, and you monitor the fraction of "degenerate groups" per batch as a health metric.

•

Q6. Your RLHF model scores great on the reward model but users say it got worse. Diagnose.

Textbook reward-model overoptimization — Goodhart. The RM is a proxy fit on finite data; past some KL distance the policy finds regions where the proxy and true preference diverge, and the proxy keeps rising while real quality falls. First I'd check the two cheap tells: mean output length and KL from the reference model. If length jumped, it's length bias — annotators equate long with thorough, the RM learned it, the policy exploited it. Then I'd score checkpoints with a held-out gold RM that never trained the policy, plus a small frozen human eval set, and find where the curves separate. Fixes, in order: early-stop at that checkpoint, raise β to shorten the leash, length-normalise or debias the RM, and add preference pairs that specifically punish the hacked behaviour. Longer term, move whatever is verifiable onto RLVR, because a program can't be flattered.

•

Q7. When would you use RLVR over DPO?

Whenever correctness is programmatically checkable — math with a gold answer, code with unit tests, SQL that must run, tool calls that must validate against a schema, extraction that must match a ground-truth record. The reward is a function, not a learned model, so it can't be gamed by fluency and it doesn't decay as the policy moves — which means you can run RL far longer than an RM allows. The catch is coverage: most user-facing tasks aren't verifiable. So in a real pipeline I'd run RLVR on the verifiable slice and DPO on the subjective slice, and evaluate them separately.

•

Q8. You fine-tuned on domain data and the model got worse at everything else. What now?

Catastrophic forgetting. Cheapest fixes first: use LoRA rather than full fine-tuning so the base weights are untouched and the delta is small and removable; drop the learning rate and the epoch count, since most forgetting comes from over-training on a narrow set. Then mix ~10–30% general instruction data back into the fine-tuning set as replay. If it's already trained, model merging is the fastest repair — average the fine-tune with the original instruct model, or use TIES, at around 0.3–0.5 weight, and you usually recover general benchmarks while keeping most of the domain gain. And measure it: a fixed general-capability suite run before and after every fine-tune, so you're quantifying the alignment tax rather than discovering it in production.

•

Q9. What's the difference between alignment and guardrails?

Alignment changes the model's tendencies — it makes bad outputs less probable. Guardrails are a runtime filter — deterministic checks on input and output that block things regardless of what the model wanted to do. Alignment is probabilistic and can be jailbroken; guardrails are deterministic but blunt and add latency. You need both, and they fail differently: alignment failures look like a model that gradually drifts or gets talked into something, guardrail failures look like a hard block on a legitimate request. In production I'd treat alignment as the model's default behaviour and guardrails as the enforceable policy boundary — and I'd log every guardrail trip as training signal for the next alignment round.
