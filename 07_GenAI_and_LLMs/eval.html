LLM Evaluation — Models *and* Applications

Scope: how to measure whether an LLM (the model) and an LLM system (RAG, agents, your product) are actually good. Two halves: Part A — model evaluation (perplexity, benchmarks, LLM-as-judge) and Part B — application evaluation (RAG, agents, online eval, CI gates).

Pairs with 05_RAG_and_Vector_Stores.md (RAGAS section) and ../08_LangChain_and_LangGraph/43_Agent_Evaluation.md (agent eval in depth).

•

0. The one idea

repeatable harnessKey termsOffline evalOnline evalReference-basedReference-free

You cannot improve what you cannot measure — and for LLMs, "measure" is hard because output is open-ended. There is rarely one right answer, so evaluation blends:

   exact metrics  ──▶  reference-based metrics  ──▶  model-graded (LLM-as-judge)  ──▶  human judgment
   (cheap, narrow)     (BLEU/ROUGE/F1)              (scalable, noisy)                 (gold, expensive)

The skill is choosing the cheapest method that still correlates with what users care about, and building a repeatable harness so every prompt/model/retriever change is scored before it ships.

Key terms - Offline eval — run against a fixed dataset before deploy (regression testing). - Online eval — measure on live traffic (A/B, feedback, drift). - Reference-based — compare output to a gold answer. Reference-free — score output on its own (e.g. "is it grounded in the context?"). - Model-graded / LLM-as-judge — use a strong LLM to score another LLM's output.

PART A — Evaluating the MODEL

A1. Intrinsic metric: Perplexity

Use it forDon't use it forbits-per-byte (BPB)

Perplexity measures how "surprised" a language model is by held-out text — the exponential of the average per-token cross-entropy. Lower is better.

                ┌   1   N                  ┐
PPL(X) = exp ⎢ - ─── Σ  log p(xᵢ | x<ᵢ) ⎢
                └   N  i=1                 ┘
  • Cross-entropy H = -(1/N) Σ log p(xᵢ|x<ᵢ) (in nats or bits); PPL = e^H (or 2^H for bits).
  • Intuition: PPL = the effective number of equally-likely choices the model is deciding among at each token. PPL 1 = perfect; PPL 20 ≈ "choosing among ~20 options."
  • Use it for: pretraining/checkpoint comparison on the same tokenizer + dataset.
  • Don't use it for: comparing instruction-tuned chat models, or models with different tokenizers — PPL isn't comparable across tokenizers, and low PPL ≠ helpful/safe answers.
  • Related: bits-per-byte (BPB) normalizes by bytes to be tokenizer-independent.
import math
def perplexity(token_logprobs):           # logprobs of the actual next tokens (natural log)
    return math.exp(-sum(token_logprobs) / len(token_logprobs))

pass@k (code) — the standard for HumanEval/MBPP. Unbiased estimator from n samples with c correct:

pass@k = 1 - C(n-c, k) / C(n, k)
from math import comb
def pass_at_k(n, c, k):                    # n samples, c correct, report pass@k
    if n - c < k: return 1.0
    return 1.0 - comb(n - c, k) / comb(n, k)

Why BLEU/ROUGE are weak for modern LLMs: they reward surface overlap with a reference. A perfectly correct answer phrased differently scores low; a fluent wrong answer can score high. Use them for translation/summarization regression, not for open-ended chat quality.

Caveats that matter in interviews & practice: - Contamination — benchmark data leaks into training sets; high scores can be memorization. Mitigate with private/held-out sets and freshly-authored questions. - Prompt sensitivity — scores shift with formatting, few-shot count, and answer-parsing. Always report the harness (e.g. lm-eval-harness) and settings. - Benchmark ≠ your task — MMLU says nothing about your domain. Build your own eval set.

A4. Leaderboards & Elo (preference at scale)

LMSYS Chatbot ArenaElo rating

LMSYS Chatbot Arena collects blind pairwise human votes ("which answer is better?") and converts them to an Elo rating (the chess system). Each comparison updates ratings:

Expected(A) = 1 / (1 + 10^((R_B - R_A)/400))
R_A ← R_A + K · (S_A - Expected(A))        # S_A = 1 win, 0 loss, 0.5 tie

Strength: captures holistic human preference no static benchmark can. Weakness: preference ≠ correctness (favors confident, well-formatted answers), and it's slow/expensive.

•

A5. LLM-as-a-Judge (the workhorse of modern eval)

Pointwise / rubricPairwiseKnown biases (and fixes)Position biasVerbosity biasSelf-preference

Use a strong model to grade outputs. Two modes:

  1. Pointwise / rubricscore one answer 1–5 on a criterion (helpfulness, correctness).
  2. Pairwise"Is A or B better?" — more reliable than absolute scores; powers MT-Bench/Arena.
JUDGE PROMPT (pairwise, reference-free)
You are an impartial judge. Compare two answers to the user question on
correctness, completeness, and clarity. Think step by step, then output JSON.
Question: {q}
Answer A: {a}
Answer B: {b}
Output: {"winner": "A"|"B"|"tie", "reason": "..."}

Known biases (and fixes):

BiasWhat happensMitigation
Position biasjudge favors the first (or second) answerrun both orders, average / require agreement
Verbosity biaslonger answers score highernormalize for length; instruct to ignore length
Self-preferencea model prefers its own styleuse a different judge family; use pairwise + humans
Formatting biasmarkdown/structure inflates scoresstrip formatting or score content only

Calibrate the judge: measure judge-vs-human agreement (e.g. Cohen's κ) on a sample before trusting it. A judge is itself a model you must evaluate. Use a top model (e.g. the latest Claude / GPT-class) as judge; cheaper models are noisier graders.

A6. Safety, truthfulness, robustness, calibration

Hallucination rateToxicity / biasCalibrationExpected Calibration Error (ECE)Robustnesssystem
  • Hallucination rate% of factual claims unsupported by ground truth (or, for RAG, by the retrieved context → "groundedness", Part B).
  • Toxicity / biasPerspective API, ToxiGen, BBQ, BOLD; report disaggregated by group.
  • Jailbreak / prompt-injection resistanceattack suites; % of refusals held under attack.
  • Calibrationdoes confidence match accuracy? Expected Calibration Error (ECE) bins predictions by confidence and averages |confidence − accuracy| per bin.
  • Robustnessaccuracy under paraphrase, typos, distractors, long context ("lost in the middle").

PART B — Evaluating the APPLICATION (RAG, agents, your product)

The model is one component. Users experience the system: retrieval + prompt + tools + guardrails + orchestration. Most production "LLM is wrong" bugs are actually retrieval or orchestration bugs. Evaluate the pipeline, component by component, then end-to-end.

        ┌──────────── component evals ────────────┐   ┌── end-to-end ──┐   ┌── online ──┐
query ─▶│ retrieval quality │ generation quality   │ ▶ │ task success    │ ▶ │ A/B, feedback│
        │ (recall, nDCG)    │ (faithfulness, ...)  │   │ on golden set   │   │ drift, cost │
        └──────────────────────────────────────────┘   └────────────────┘   └────────────┘

B1. RAG evaluation — two stages

Recall@kPrecision@kHit rate@kMRRnDCG@kRAGAS

(a) Retrieval metrics (is the right context fetched?)

Given a query with known relevant chunks (a labeled set):

MetricFormula / meaning
Recall@k(relevant retrieved in top-k) / (all relevant) — did we get them?
Precision@k(relevant in top-k) / k — how much noise?
Hit rate@kfraction of queries with ≥1 relevant in top-k
MRRmean of 1/rank of the first relevant result — how high?
nDCG@krank-weighted gain, normalized by ideal ordering — graded relevance
def recall_at_k(retrieved_ids, relevant_ids, k):
    top = set(retrieved_ids[:k])
    return len(top & set(relevant_ids)) / max(len(relevant_ids), 1)

def mrr(retrieved_ids, relevant_ids):
    for i, rid in enumerate(retrieved_ids, 1):
        if rid in relevant_ids:
            return 1.0 / i
    return 0.0

nDCG (graded relevance, rel_i = relevance of result at rank i):

DCG@k = Σ (2^rel_i - 1) / log2(i + 1)         nDCG@k = DCG@k / IDCG@k

(b) Generation metrics (is the answer good, given the context?) — RAGAS

The RAGAS quartet is the de-facto standard; most are reference-free and LLM-graded:

MetricQuestion it answersReference needed?
Faithfulness / GroundednessAre the answer's claims supported by the retrieved context? (anti-hallucination)no
Answer RelevancyDoes the answer actually address the question?no
Context PrecisionAre the retrieved chunks relevant (and ranked well)?no
Context RecallDid retrieval get everything needed to answer?yes (ground-truth answer)
Answer CorrectnessIs the final answer factually right vs gold?yes

Faithfulness ≈ (# claims in answer supported by context) / (# claims in answer). Compute by having a judge decompose the answer into atomic claims and check each against the context.

FAITHFULNESS JUDGE
Context: {retrieved_chunks}
Answer:  {answer}
1) List each factual claim in the Answer.
2) For each claim, is it supported by the Context? yes/no.
Return: supported_claims / total_claims  (0..1)

The most important RAG metric is faithfulness/groundedness — it directly measures hallucination, the #1 enterprise risk. A faithful-but-incomplete answer is usually safer than a fluent-but-fabricated one.

B2. Agent & tool-use evaluation

trajectoryTask successTool selectionTool-argument correctnessTrajectory qualityEfficiency

Agents add new failure modes — wrong tool, wrong arguments, infinite loops, giving up. Evaluate the trajectory, not just the final answer.

DimensionMetric
Task successdid it accomplish the goal? (final-state check or LLM-judge)
Tool selectionaccuracy of choosing the right tool for the step
Tool-argument correctnessare the args valid & sensible (schema + semantics)?
Trajectory qualitydid it take a reasonable path? (step-by-step judge vs a gold trace)
Efficiency# steps / # tool calls / tokens vs optimal; loop/retry count
Recovery / resiliencedoes it recover from a tool error or empty retrieval?
Cost & latency$ and ms per resolved task (the production KPIs)
# example checks (cf. the runnable harness in evals.py)
assert "calculator" in tools_used                 # tool selection
assert any(c["type"] == "kb" for c in citations)  # grounded / cited
assert result["error"] is None                    # resilient: no failure path
assert steps <= 6                                  # efficiency / no runaway loop

Trajectory eval options: (1) exact/soft match against a gold action sequence; (2) LLM-judge rates the trajectory; (3) outcome-only (final state) when the path doesn't matter.

•

B3. End-to-end & regression evaluation

Golden datasetEval-driven developmentfails CISlice analysisReference-free where possible
  • Golden datasetcurated (input → expected behavior/answer) cases covering happy paths, edge cases, known past bugs, and adversarial inputs. Grow it from real production failures.
  • Eval-driven developmentevery prompt/model/retriever/tool change runs the suite; a metric regression (e.g. Recall@6 < 0.8, faithfulness < 0.9) fails CI and blocks the merge.
  • Slice analysisreport metrics per segment (query type, language, doc source). Aggregate numbers hide failures on a critical slice.
  • Reference-free where possiblegolden answers age fast; faithfulness/relevancy don't need them.
•

B4. Guardrail / safety evaluation (application-level)

Prompt-injection / jailbreakPII / data-leakRefusal correctnessTool-abuse
  • Prompt-injection / jailbreak suites against your system prompt + tools (can a doc make the agent exfiltrate data or call a tool it shouldn't?).
  • PII / data-leak checks on outputs and on tool arguments.
  • Refusal correctnessrefuses the unsafe, doesn't over-refuse the benign (track both).
  • Tool-abusedoes the agent respect tool permissions and rate limits under adversarial prompts?

Offline can't catch everything; measure live:

C. Worked example — evaluating a RAG answer end-to-end

Question:    "How many vacation days do employees get per year?"
Gold answer: "18 days per year (1.5/month)."
Retrieved:   [KB-1] "Employees accrue 1.5 vacation days per month..." (relevant)
             [KB-2] "Expense reimbursement up to $60/day..."         (irrelevant)
Answer:      "Employees get 18 vacation days per year, accrued at 1.5/month [KB-1]."
MetricValueHow
Recall@21.0the 1 relevant chunk (KB-1) was retrieved
Precision@20.51 of 2 retrieved chunks was relevant
Context Precisionlow-ishKB-2 is noise, ranked #2
Faithfulness1.0both claims (18/yr, 1.5/mo) supported by KB-1
Answer Relevancyhighdirectly answers the question
Answer Correctness1.0matches gold

Diagnosis: generation is great; retrieval precision is the weak link (pulled an irrelevant chunk). Fix = better reranking / metadata filter, not prompt tweaking. This is why component-level eval matters — it tells you where to fix.

F. Pitfalls & interview soundbites

ContaminationLLM-as-judge is biasedFaithfulness > fluencyEval-driven development
  • "Benchmarks are necessary but not sufficient." Always build a task-specific golden set.
  • Contamination inflates benchmark scores — prefer private/fresh evals.
  • BLEU/ROUGE don't measure correctnessthey measure overlap; weak for open-ended output.
  • LLM-as-judge is biased (position, verbosity, self-preference) — use pairwise + order-swap, and validate the judge against humans before trusting it.
  • Most RAG failures are retrieval failuresmeasure retrieval separately or you'll "fix" the prompt forever.
  • Faithfulness > fluency for enterprise — a confident hallucination is the dangerous failure.
  • Eval-driven developmentgate merges on metrics, grow the golden set from production failures, and measure online — offline eval alone never catches everything.
