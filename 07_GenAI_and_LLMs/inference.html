LLM Inference Optimization — Serving LLMs at Scale

Scope: LLM inference fundamentals, KV cache, quantization for inference, attention optimizations, batching strategies, speculative decoding, serving frameworks, distributed inference, model compression, deployment architectures, benchmarking & monitoring, cost optimization, interview Q&A.

Key Definitions (read first)
TermPlain-language definition
Autoregressive generationProduce one token at a time, each conditioned on all previous ones.
Prefill vs decodePhase 1: process the whole prompt in parallel (compute-bound). Phase 2: emit tokens one by one (memory-bound).
KV cacheStored keys/values for past tokens so each new token doesn't recompute attention over the whole sequence.
TTFTTime To First Token — latency until the first output token (dominated by prefill).

Compute-bound vs memory-boundLimited by FLOPs (prefill) vs by weight-loading bandwidth (decode).
1. LLM Inference Fundamentals
•

Two Phases of Autoregressive Generation

Phase 1: PREFILL (Prompt Processing)
├── Process all input tokens in parallel
├── Compute-bound (matrix multiplications)
├── Generates KV cache for all input tokens
└── Time ∝ prompt_length

Phase 2: DECODE (Token Generation)
├── Generate one token at a time (autoregressive)
├── Memory-bound (loading model weights for 1 token)
├── KV cache grows with each new token
└── Time ∝ output_length × per_token_latency
•

Memory Requirements

# Model weights memory (float16)
memory_weights = num_params × 2 bytes  # float16

# KV Cache memory per request
memory_kv = 2 × n_layers × n_heads × head_dim × seq_len × 2 bytes
# 2 for K and V, 2 bytes for float16

# Example: LLaMA-2 7B, seq_len=4096
# Weights: 7B × 2 = 14 GB
# KV Cache (per request): 2 × 32 × 32 × 128 × 4096 × 2 = ~1 GB
# Batch of 16: ~16 GB just for KV cache!
•

Bottleneck Analysis

PhaseBottleneckWhy
PrefillComputeLarge batch matrix multiplication
DecodeMemory bandwidthLoad entire model weights for 1 token
Arithmetic Intensity = FLOPs / Bytes loaded
- Prefill: High AI → compute-bound
- Decode: Low AI → memory-bound

Memory bandwidth utilization:
  Decode throughput ≈ Model size / Memory bandwidth
  E.g., 14 GB model / 2 TB/s A100 bandwidth ≈ 7ms/token
2. KV Cache
•

How It Works

Without KV Cache: recompute attention for ALL previous tokens at each step
With KV Cache: store and reuse K, V from previous steps

Step 1: Q₁, K₁, V₁ → store K₁, V₁ in cache
Step 2: Q₂, K=[K₁,K₂], V=[V₁,V₂] → append K₂, V₂ to cache
Step 3: Q₃, K=[K₁,K₂,K₃], V=[V₁,V₂,V₃] → append K₃, V₃

Saves: O(n²) → O(n) compute per step (but O(n) memory)
•

KV Cache Memory Management

PagedAttention (vLLM)

Problem: Naive KV cache pre-allocates max_seq_len → wastes memory
Solution: Allocate KV cache in pages (blocks), like OS virtual memory

Benefits:
- No pre-allocation waste
- Memory sharing (prompt prefix caching)
- Non-contiguous memory → reduced fragmentation
- ~2-4x more concurrent requests

Block table:
Request 1: [Block 3, Block 7, Block 1]  (non-contiguous)
Request 2: [Block 3, Block 5]            (shares Block 3 = prefix cache)

Multi-Query Attention (MQA) & Grouped-Query Attention (GQA)

Multi-Head Attention (MHA): n_heads × (K, V)  → full KV cache
Multi-Query Attention (MQA): 1 × (K, V)       → n_heads share one KV
Grouped-Query Attention (GQA): n_groups × (K, V)  → groups share KV

KV Cache reduction:
MHA:  2 × n_layers × n_heads × head_dim × seq_len
GQA:  2 × n_layers × n_groups × head_dim × seq_len  (n_groups << n_heads)
MQA:  2 × n_layers × 1 × head_dim × seq_len

Example: LLaMA-2 70B uses GQA with 8 groups (vs 64 heads)
→ 8x KV cache reduction
•

Prefix Caching

System prompt + common prefixes → cache and share across requests

Request 1: [System prompt | User query A]
Request 2: [System prompt | User query B]
           └── shared ──┘ └── unique ──┘

- Avoid recomputing shared prefix KV cache
- vLLM, SGLang support automatic prefix caching

AWQ (Activation-Aware Weight Quantization)

Key insight: Not all weights are equally important
- Protect salient weights (corresponding to large activations)
- Scale important weight channels before quantization
- Better quality than GPTQ at same bit width

4. Attention Optimizations
•

Flash Attention

Problem: Standard attention: Q×Kᵀ creates O(n²) intermediate matrix
→ Requires O(n²) memory, slow for long sequences

Flash Attention solution:
- Tile-based computation (process blocks that fit in SRAM)
- Fused kernel: softmax + matmul in one GPU kernel
- IO-aware: minimize HBM ↔ SRAM data movement
- Online softmax trick (compute softmax without materializing full matrix)

Results:
- 2-4x faster than standard attention
- O(n) memory instead of O(n²)
- Exact computation (not approximate)
•

Flash Attention 2/3

Flash Attention 2:
- Better parallelism across sequence length
- Reduced non-matmul FLOPs
- 2x faster than Flash Attention 1

Flash Attention 3 (Hopper GPUs):
- WGMMA (Warp Group Matrix Multiply-Accumulate)
- Asynchronous operations (overlap compute + memory)
- FP8 support
- Up to 1.5-2x faster than FA2 on H100
•

Sliding Window Attention

Full attention: O(n²) — every token attends to all others
Sliding window: Each token attends to only W nearby tokens → O(n × W)

Used in: Mistral, Mixtral
Benefits: Handles long contexts with bounded memory
Limitation: Cannot directly attend to distant tokens (but info propagates through layers)
5. Batching Strategies
•

Static Batching

Problem: All requests wait for longest request to finish

Request 1: [=====]------   (done early, waits)
Request 2: [============]  (longest)
Request 3: [========]---   (done early, waits)

→ Low GPU utilization, high latency for short requests
•

Continuous/Dynamic Batching

Requests enter and leave independently

Time →
Request 1: [=====]
Request 2: [============]
Request 3:    [========]
Request 4:       [====]

→ No waiting, higher throughput, lower latency
•

Iteration-Level Scheduling

Each decode step, scheduler decides:
1. Which requests to include in this iteration
2. Preempt lower-priority requests if memory full
3. Insert new arrivals immediately

vLLM/TGI implement this automatically
•

Chunked Prefill

Problem: Long prefill blocks decode for other requests
Solution: Break prefill into chunks, interleave with decode steps

Without chunking:
[PREFILL (2000 tokens)............][DECODE][DECODE]...

With chunking:
[PREFILL chunk 1][DECODE][PREFILL chunk 2][DECODE]...

→ Better TPOT for ongoing requests during new prefills
6. Speculative Decoding
•

Core Idea

Problem: Decode is memory-bound → GPU underutilized
Solution: Use a small "draft" model to generate K tokens speculatively,
          then verify all K tokens in parallel with the large model

Step 1: Draft model generates K tokens (fast, low quality)
Step 2: Target model validates all K tokens in one forward pass
Step 3: Accept matching tokens, reject and resample from divergence point

Speedup: Up to 2-3x (depends on acceptance rate)
Quality: Mathematically identical to target model (rejection sampling)
•

Implementation

def speculative_decode(target_model, draft_model, prompt, K=5):
    tokens = prompt
    while not done:
        # Draft K tokens
        draft_tokens = []
        draft_probs = []
        for _ in range(K):
            prob = draft_model(tokens + draft_tokens)
            token = sample(prob)
            draft_tokens.append(token)
            draft_probs.append(prob[token])
        
        # Verify all K tokens in one forward pass
        target_probs = target_model(tokens, draft_tokens)  # parallel
        
        # Accept/reject
        for i in range(K):
            r = random.random()
            if r < target_probs[i][draft_tokens[i]] / draft_probs[i]:
                tokens.append(draft_tokens[i])  # accept
            else:
                # Reject: resample from adjusted distribution
                token = sample(adjusted_distribution(target_probs[i], draft_probs[i]))
                tokens.append(token)
                break  # discard remaining draft tokens
    
    return tokens

8. Distributed Inference
•

Tensor Parallelism (TP)

Split model layers across GPUs (horizontal split)

GPU 0: First half of attention heads + first half of FFN
GPU 1: Second half of attention heads + second half of FFN

AllReduce after each layer to sync outputs

Pros: Low latency (GPUs work in parallel on same layer)
Cons: Requires high-bandwidth interconnect (NVLink)
Best for: Within a single node
•

Pipeline Parallelism (PP)

Split model layers across GPUs (vertical split)

GPU 0: Layers 0-15   →
GPU 1: Layers 16-31  →  Sequential flow

+ Micro-batching to fill pipeline bubbles

Pros: Works across nodes (less communication)
Cons: Pipeline bubbles, higher latency
Best for: Across nodes
•

Expert Parallelism (EP)

For Mixture-of-Experts (MoE) models like Mixtral

GPU 0: Experts 0-3
GPU 1: Experts 4-7

Tokens routed to appropriate GPU based on gating
Reduces per-GPU compute but requires routing communication
•

Multi-GPU Configuration

# vLLM: simple tensor parallelism

# For very large models: combine TP + PP

9. Model Compression
•

Knowledge Distillation

Teacher (large model) → Student (small model)

Loss = α × L_CE(student, labels) + (1-α) × L_KD(student_logits, teacher_logits)
L_KD = KL(softmax(teacher_logits/T), softmax(student_logits/T))

T = temperature (higher → softer distributions → more knowledge transfer)
•

13. Grammar-Constrained Decoding

Grammar-constrained decoding forces LLM outputs to conform to a formal grammar, eliminating malformed JSON, invalid code syntax, or off-schema responses at the token-sampling level.

•

How It Works

At each decoding step, the grammar defines which tokens are valid continuations. Invalid tokens are masked (logits set to $-\infty$) before sampling, guaranteeing structurally correct output.

Standard Decoding:          Grammar-Constrained Decoding:

Logits → Softmax → Sample   Logits → Grammar Mask → Softmax → Sample
                                       ↑
                              Only tokens valid per
                              grammar state are kept
•

15. Interview Questions
•

Conceptual

Explain PagedAttentionMHA vs GQA vs MQA?How does Flash Attention work?What is speculative decoding?GPTQ vs AWQ vs GGUF?How to reduce TTFT?

  1. What are the two phases of LLM inference? Prefill (process prompt in parallel, compute-bound) and Decode (generate tokens one-by-one, memory-bound).

  2. Explain PagedAttention. Manages KV cache like OS virtual memory — allocates in pages/blocks, avoids pre-allocation waste, enables memory sharing across requests with common prefixes. Used in vLLM.

  3. MHA vs GQA vs MQA? MHA: each head has own K,V. GQA: groups of heads share K,V (LLaMA-2 70B). MQA: all heads share one K,V. GQA/MQA reduce KV cache memory.

  4. How does Flash Attention work? Tiles attention computation into blocks that fit in GPU SRAM, avoids materializing O(n²) attention matrix in HBM. IO-aware algorithm that minimizes memory transfers.

  5. What is speculative decoding? Draft model generates K tokens cheaply, target model verifies all K in one forward pass. Accepted tokens are mathematically identical to target model output. ~2-3x speedup.

  6. Continuous batching vs static batching? Static: all requests wait for longest one. Continuous: requests enter/leave batch independently per decode step. Much higher throughput.

  7. GPTQ vs AWQ vs GGUF? GPTQ: calibration-based weight quantization (GPU). AWQ: activation-aware, preserves salient weights (GPU, better quality). GGUF: CPU-optimized, mixed precision (llama.cpp).

  8. How to estimate GPU memory for serving? Weights memory + KV cache per request × max batch size + overhead. KV cache = 2 × layers × heads × head_dim × seq_len × dtype_bytes.

  9. When to use tensor parallel vs pipeline parallel? TP: within node, splits layers horizontally, needs NVLink. PP: across nodes, splits layers vertically, tolerates lower bandwidth. Often combined for large models.

  10. How to reduce TTFT? Prefix caching, chunked prefill, Flash Attention, FP8 compute, tensor parallelism, smaller context windows, prompt compression.

•

Practical

  1. Design a serving architecture for a 70B model serving 1000 QPS. Multiple vLLM instances with TP=2 behind load balancer, INT4 quantization, prefix caching for system prompts, auto-scaling based on queue depth, semantic caching layer.

  2. How to handle long contexts (100K+ tokens)? Ring Attention for distributed context, sliding window attention, context compression, RAG to reduce context, streaming prefill with chunking.

  3. Your LLM API has high P99 latency. Debug steps? Check queue depth, GPU utilization, KV cache pressure, long prefills blocking decode, garbage collection pauses, network latency, individual request token counts.

  4. Compare self-hosting vs API for a startup. Depends on volume, privacy needs, and ops capability. Start with API (fast, no ops), migrate to self-hosted when volume justifies cost and you have GPU/ML infra expertise.

  5. How to serve multiple LoRA adapters efficiently? S-LoRA or vLLM multi-LoRA: load base model once, swap LoRA weights per request. Batch requests with same adapter together. KV cache shared across adapters.
