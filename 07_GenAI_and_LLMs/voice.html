Voice Agents and Real-Time Speech

The thesis of this file: a voice agent is not a chatbot with a microphone bolted on. Text chat is turn-based and forgiving; speech is full-duplex, interruptible, and judged on a 200-millisecond budget that human conversation set long before you shipped anything. Almost every hard problem here is a latency or turn-taking problem, not a language problem.

Every number below comes from the model in section 3, and its output is pasted verbatim.

Companion: the speech stack underneath — mel spectrograms, CTC, Whisper, TTS models — is in ../05_Deep_Learning/08_Audio_Speech_Processing.md.

1. Why voice is a different problem
Text chat Voice
Turn boundary the user presses Enter nobody tells you they finished — you have to guess
Latency tolerance seconds under ~800 ms, and 200 ms is what humans do to each other
Interruption impossible expected, and the agent must stop mid-word
Input fidelity exactly what they typed a transcript that is 5–15% wrong, more with names
Output format markdown, lists, links one spoken paragraph; a bulleted list is unspeakable
Recovery scroll up and re-read nothing to look at; a wrong answer must be caught in the moment
Duplex half full — both sides can talk at once, and sometimes do

The consequence: the model is usually the easy part. What breaks voice products is deciding when the user has stopped talking, stopping fast enough when they interrupt, and hiding the 1.5 seconds it takes to produce an answer.

2. Two architectures 
  CASCADED
    mic -> VAD -> ASR -> text -> LLM -> text -> TTS -> speaker
                   |                |            |
             every stage is swappable, debuggable, and adds its own latency

  SPEECH-TO-SPEECH
    mic -> [ one multimodal model, audio in and audio out ] -> speaker
                   |
             fewer stages, lower latency, far less to inspect
Cascaded Speech-to-speech
Latency ~1.6 s to first audio ~0.9 s
Debuggability you can read the transcript at every stage the audio went in and audio came out
Control swap ASR, bias the vocabulary, edit the text before TTS prompt only
Prosody flat — the TTS never heard the user keeps tone, emotion, emphasis, laughter
Tools/RAG ordinary function calling on text supported, but the ecosystem is younger
Compliance transcripts fall out for free you have to transcribe separately for the record
Cost three bills one, usually higher per minute

How to choose, in one line. Cascaded when you need control, auditability, domain vocabulary and tool use — which is most enterprise work. Speech-to-speech when naturalness and latency are the product, and when the conversation is not carrying a compliance obligation.

Rule of thumb. Build cascaded first even if you intend to end up speech-to-speech. The transcripts are how you learn what your users actually say, and you cannot build an eval set without them.

3. The latency budget, worked

This is the single most useful artefact in a voice project. Time to first audio, stage by stage:

CASCADED  (ASR -> LLM -> TTS)
   STAGE                            ms   why
   endpoint silence                700   wait to be sure the user stopped talking             ############################
   ASR finalisation                120   flush the decoder, apply the LM, punctuate           #####
   network to LLM                   40   one round trip                                       ##
   LLM time to first token         350   prefill the prompt                                   ##############
   LLM first clause                200   12 tokens at 60 tok/s, enough to start speaking      ########
   TTS first chunk                 180   synthesise the opening clause                        #######
   playout buffer                   60   jitter buffer before audio leaves the speaker        ##
   TIME TO FIRST AUDIO            1650   <- what the user experiences

SPEECH-TO-SPEECH  (one model)
   STAGE                            ms   why
   endpoint silence                500   the model hears prosody, so it can commit sooner     ####################
   network                          40   one round trip                                       ##
   model time to first audio       320   no ASR text, no TTS stage                            #############
   playout buffer                   60   jitter buffer                                        ##
   TIME TO FIRST AUDIO             920   <- what the user experiences

Now the part that decides where you spend your week — halve each stage in turn and see what it buys:

   halve endpoint silence             saves   350 ms  ->    1300 ms total  (21.2% better)
   halve ASR finalisation             saves    60 ms  ->    1590 ms total  ( 3.6% better)
   halve network to LLM               saves    20 ms  ->    1630 ms total  ( 1.2% better)
   halve LLM time to first token      saves   175 ms  ->    1475 ms total  (10.6% better)
   halve LLM first clause             saves   100 ms  ->    1550 ms total  ( 6.1% better)
   halve TTS first chunk              saves    90 ms  ->    1560 ms total  ( 5.5% better)
   halve playout buffer               saves    30 ms  ->    1620 ms total  ( 1.8% better)

   the LLM is 33.3% of the budget; endpointing is 42.4%

Endpointing is 42.4% of the budget — a bigger share than the language model. Teams reliably spend their optimisation effort on a faster model and win 10%, while the 700 ms of silence they are waiting out sits untouched. The wins, in order: a smarter endpointer, then streaming the first clause into TTS, then a faster prefill.

For scale: humans leave roughly 200 ms between turns. Under 800 ms an agent feels responsive; past 1,200 ms it feels like it is thinking, and users start repeating themselves.

def budget(name, rows):
    total = sum(ms for _n, ms, _w in rows)

print("=" * 96)
MEDIAN_PAUSE, SIGMA = 220.0, 0.75          # intra-utterance pauses, lognormal


def p_pause_exceeds(t):
    """P(a mid-sentence pause lasts longer than t) -> the model cuts the user off."""
    z = (math.log(t) - math.log(MEDIAN_PAUSE)) / SIGMA
    return 0.5 * math.erfc(z / math.sqrt(2.0))

print("   700 ms is the usual pick: %.1f%% of turns get cut off, and it costs 700 ms."
      % (100 * p_pause_exceeds(700)))
print("   A semantic endpointer - one that asks 'is this sentence FINISHED?' rather than")
print("   'has it been quiet?' - is how you get 300 ms latency at 900 ms reliability.")

5. Endpointing: the hardest problem

Endpointing is deciding that the user has finished their turn. It is not VAD. VAD answers "is there speech in this 20 ms frame"; endpointing answers "was that a pause for breath, or the end of a thought?"

The naive rule is "N milliseconds of silence". Every millisecond of N is a millisecond of latency added to every single turn, and every pause longer than N is the agent talking over someone mid-sentence. With intra-utterance pauses modelled as lognormal with a 220 ms median:

   threshold    added latency          P(cut the user off)      per 100 turns
   300 ms       +300 ms                0.340                    34.0 interruptions
   500 ms       +500 ms                0.137                    13.7 interruptions
   700 ms       +700 ms                0.061                    6.1 interruptions
   900 ms       +900 ms                0.030                    3.0 interruptions
   1200 ms      +1200 ms               0.012                    1.2 interruptions
   1500 ms      +1500 ms               0.005                    0.5 interruptions

There is no good row in that table. At 300 ms you interrupt a third of turns. At 1,200 ms you are unusably slow and still interrupt one turn in eighty. This is the trade-off that makes voice hard, and a fixed threshold cannot escape it.

What actually escapes it — semantic endpointing. Ask a different question: is this utterance complete?

Signal What it adds
Partial-transcript syntax "set the temperature to" is obviously unfinished; "set the temperature to twenty" might be done. A small classifier over the partial transcript beats silence alone.
Prosody pitch falls at the end of a statement and rises mid-list. Speech-to-speech models get this for free; cascaded ones throw it away at the ASR boundary.
Dialogue state if you asked a yes/no question, commit after one word. If you asked for an address, be patient.
Adaptive thresholds some people pause a lot. Track it per speaker within the session.

A semantic endpointer runs an aggressive 300 ms timer but only commits when the utterance looks complete, holding on when it does not — which is how you get 300 ms latency with the interruption rate of a 900 ms threshold.

6. Barge-in and echo cancellation

Barge-in is the user talking over the agent. Supporting it is the difference between a product people use and a phone tree people hate.

   VAD detects speech             30 ms
   stop the TTS stream            20 ms
   fade out the audio             50 ms
   flush the playout buffer       60 ms
   TOTAL                         160 ms   <- above ~200 ms the user repeats themselves

Four things must happen and all four are easy to get wrong:

  1. Stop generating. Cancel the LLM stream, or you pay for tokens nobody hears.
  2. Stop synthesising and flush the buffer. Audio already in the jitter buffer will keep playing for as long as the buffer is deep — a 500 ms buffer means half a second of the agent still talking after it "stopped".
  3. Truncate the conversation history at what was actually spoken. If the model said three sentences and the user heard one, the transcript must record one. Otherwise the model believes it told them things they never heard, and the conversation drifts.
  4. Decide whether it was a real interruption. "Mm-hm" and "right" are backchannels — the user encouraging you to continue, not taking the floor. Stopping for those is as annoying as not stopping at all.

None of it works without acoustic echo cancellation. The microphone hears the speaker. Without AEC the agent's own voice trips its VAD and it barges in on itself, which is the single most common bug in a first voice prototype. AEC, plus beamforming on a mic array, plus a reference signal of what is being played, are pipeline components — not optional polish.

7. Streaming every stage

The budget in section 3 only holds if nothing waits for a complete result.

  BAD  (each stage waits for the previous one to finish)
    [------ ASR ------][-------- LLM --------][------ TTS ------]  ~3.2 s

  GOOD (each stage starts on the first fragment of the last)
    [------ ASR ------]
                 [-------- LLM --------]
                        [------ TTS ------]                        ~1.6 s
Stage Streaming means
ASR emit partial hypotheses as they arrive; start prefilling the LLM prompt with the partial so the final token flush is all that remains
LLM token streaming, and speculative prefill: begin prefill on the partial transcript before endpointing fires, discard if the user keeps talking
TTS synthesise clause by clause. Chunk on punctuation and clause boundaries, never on a fixed token count, or prosody breaks mid-phrase
Playout the smallest jitter buffer the network tolerates — every buffered millisecond is added latency and added barge-in lag

Speculative prefill is the cheapest large win. Prefill on the partial transcript while the user is still speaking; if they continue, throw it away and prefill again. You pay for a few wasted prefills and you delete most of the 350 ms.

8. Prompting a model that will be spoken aloud

Written-text habits are actively harmful when the output is read out.

Written answer Spoken answer
"Here are three options:\n1. …\n2. …" "There are three. The cheapest is… want the others?"
"The total is $1,234.56" "One thousand two hundred thirty four dollars and fifty six cents"
"See the documentation at example.com/x" "I can text you the link"
A 200-word paragraph Two sentences, then a question
"Important: …" Markdown is read aloud as asterisks. Never emit it.

A system prompt for voice should state, explicitly:

  - One or two sentences, then stop. Never a list unless asked.
  - Plain speech: no markdown, no URLs, no emoji, no abbreviations.
  - Write numbers, dates and currency the way they are said aloud.
  - If you need something, ask ONE question, not three.
  - If a tool is going to be slow, say a short filler first, then answer.

Response length is a latency control, not a style preference. Every extra clause is time the user waits before they can reply, and time during which they may interrupt — leaving the agent with a half-delivered answer in its history.

9. Living with ASR errors

The transcript is wrong 5–15% of the time, and disproportionately wrong on exactly the words that matter — names, numbers, addresses, part codes.

Technique What it does
Contextual biasing Inject the session's vocabulary — contacts, playlist names, order numbers — into the decoder so the beam prefers them. The single highest-value fix.
N-best rescoring Send the top 3 ASR hypotheses to the LLM and let it pick using dialogue context. "Call Erin" versus "Call Aaron" is decidable from who you called last week.
Confidence-gated confirmation Confirm only the low-confidence slots, never the whole utterance. "Twenty two degrees, yes?" beats "Did you say 'set the temperature to twenty two degrees'?"
Constrained slots If the answer must be one of nine known values, match against that list rather than trusting free text.
Spelling mode For a name or a code, fall back to letter-by-letter with a phonetic alphabet. Ugly, and it works.
Phonetic matching Compare a transcript to your catalogue with a phonetic algorithm, so "mum" and "mom" collapse.

Design rule. Never make the user repeat the whole sentence. Repair the slot you are unsure about and keep everything else you already have.

10. Tools and latency hiding

A tool call in a voice loop is a silence, and silence in conversation reads as failure.

  user: "is my order out for delivery yet"
        |
        +--> agent begins speaking IMMEDIATELY: "Let me check that for you."   <- 300 ms
        |
        +--> in parallel: order_status(id) ... 900 ms
                 |
                 +--> "It left the depot at nine this morning."

Three rules that make this work:

  1. Speak first, then call. Emit a short filler before the tool call, not after it. It buys the whole tool latency and it is what a human does.
  2. Fillers must be honest and varied. "Let me check", "one moment" — rotated, because the same phrase every time is worse than silence.
  3. Have a timeout story. Past ~3 s say something else: "still looking, this one's slow." A silent agent is assumed broken and the user hangs up or repeats themselves.

For anything past a few seconds — a database query, a RAG retrieval over a large corpus — return partial information first ("I can see the order, checking the delivery status now") rather than holding the floor with nothing.

11. The conversation state machine

Voice needs explicit state, because "who has the floor" is a real variable that both parties mutate.

        +--------------------------------------------------+
        |                                                  |
        v                                                  |
   [ LISTENING ] --speech detected--> [ USER SPEAKING ]     |
        ^                                    |              |
        |                            endpoint fires         |
        |                                    v              |
        |                              [ THINKING ] --------+ (barge-in: discard, back to LISTENING)
        |                                    |
        |                          first audio chunk ready
        |                                    v
        +---- playback done ---------- [ SPEAKING ] <--+
                                             |         |
                                     user starts talking|
                                             v         |
                                      [ INTERRUPTED ] --+
                                             |
                                   truncate history to what was
                                   actually heard, then LISTENING

The transition everyone forgets is INTERRUPTED → truncate history. The model's own turn must be rewritten to the words that actually reached the speaker. Skip it and the agent will refer back to things the user never heard, which reads as the agent being confused about its own conversation.

12. Evaluating a voice agent

Text metrics do not cover this. Measure four layers.

Layer Metric Target
Recognition WER, and entity error rate on names, numbers, addresses entity ERR is the one that matters
Interaction median and p95 time to first audio; interruption rate; barge-in latency under 800 ms median; under 5% false interruptions
Task task success rate, turns to completion, containment (no human handoff) the product metric
Experience MOS or CMOS for the synthesised voice; abandonment rate; talk-over rate measured on real calls, not in a lab

Build the eval set from recorded audio, not text. A text-only eval hides the failure mode that dominates production: the agent answering a misheard question perfectly. Replaying audio through the whole pipeline is the only way to see it.

Two evaluation methods worth running:

  • Audio replay suite. A frozen set of recordings — clean, noisy, accented, with barge-ins — replayed nightly through the full stack, scored on transcript, entities and task outcome.
  • Simulated caller. A second LLM given a persona and goal, talking to your agent over synthesised speech. Cheap, scales, and catches turn-taking bugs a script never would.
13. Observability for voice

Every stage becomes a span, and the trace is what makes a 2-second turn explicable:

  span  turn                          1,650 ms
    +-- span vad.endpoint                700 ms   threshold=700, semantic=false
    +-- span asr.finalise                120 ms   model, partial_count=7, confidence=0.82
    +-- span llm.generate                550 ms   ttft=350, tokens_out=64, model pinned
    +-- span tts.first_chunk             180 ms   voice, chars=48, streamed=true
    +-- span playout                      60 ms   buffer_ms=60

The attributes that resolve voice incidents:

Span Log
vad / endpoint threshold used, silence observed, whether a semantic endpointer overrode it
asr model and version, confidence, number of partials, n-best, biasing list size
llm pinned model version, TTFT, tokens in/out, whether the turn was cancelled by barge-in
tts voice ID, characters, chunk count, time to first chunk
turn end-to-end latency, interrupted yes/no, words actually played versus words generated

That last one is the voice-specific gold: generated versus actually heard. When they diverge the conversation history is wrong, and no text-level metric will show you why the agent started making no sense three turns later. The general method — metric to cohort to trace to span — is in 27_LLM_Observability_and_Tracing.md.

14. What a call costs 
   ASR    3.0 min x $0.006/min          = $0.0180
   TTS   1800 chars x $0.015/1k chars    = $0.0270
   LLM   4200 in + 700 out tokens        = $0.0231
   TOTAL                                  = $0.0681 per call
   at 10,000 calls a day: $681/day, $20430/month

Two things to notice, because they are counter-intuitive:

  • TTS is the biggest line, not the LLM. Synthesis is billed per character and an agent talks a lot. Shorter answers cut cost and latency at the same time — the rare optimisation with no trade-off.
  • The LLM cost is dominated by input tokens, because the whole conversation is resent every turn. Prompt caching on the stable system prompt, and summarising older turns, cut that materially. See 21_LLM_Cost_and_Token_Optimization.md.
15. Telephony, in-car, and on-device
Telephony In-car App / smart speaker
Audio 8 kHz, codec-compressed 16 kHz, mic array, loud noise floor 16 kHz, near-field
Dominant problem band-limited audio, hold music, DTMF, transfers road and HVAC noise, echo, multiple occupants wake word false accepts
Connectivity assumed tunnels, garages, dead zones usually fine
Latency floor PSTN adds 100–200 ms none if on-device network round trip
Non-negotiable barge-in, because callers expect an IVR they can talk over works offline for safety-critical commands; hands stay on the wheel privacy — audio not leaving the device

The in-car pattern is a hierarchy: wake word and VAD always on device; a compact streaming recogniser on device for the fixed command grammar — climate, navigation, media — so those never depend on a network; and a cloud model for open-ended questions, degrading to "I need a connection for that" when there is none. Speaker identification chooses whose profile applies when several people are in the cabin, and beamforming decides which seat is talking.

16. Pitfalls
Pitfall Why it hurts
Fixed silence endpointing 700 ms of latency on every turn, and it still cuts off 6% of them.
No barge-in The product feels like a phone tree. Users talk over it anyway and are not heard.
No echo cancellation The agent hears itself and interrupts itself. Every first prototype does this.
Not truncating history on interruption The model believes it said things the user never heard, and the dialogue drifts.
Markdown in a spoken answer The TTS reads the asterisks out loud.
Waiting for the full LLM response before TTS Doubles time to first audio for nothing — stream the first clause.
Silent tool calls Silence reads as a dropped call. Speak first, then call.
Evaluating on typed text Hides the dominant production failure: a perfect answer to a misheard question.
Ignoring entity error rate 5% WER can still mean 30% of names wrong, and names are the whole task.
A deep jitter buffer Every buffered millisecond is added latency and added barge-in lag.
17. Interview drill
•

Q1. Cascaded or speech-to-speech, and why?

Cascaded when I need control and auditability — domain vocabulary biasing, tool calls, transcripts for compliance, the ability to swap any stage. Speech-to-speech when latency and naturalness are the product: it is roughly 900 ms to first audio against 1,650, and it keeps prosody the cascade throws away. I would build cascaded first regardless, because the transcripts are how you build an eval set.

•

Q2. Where does the latency actually go?

In my budget, endpointing is 42% and the language model is 33%. Halving the endpoint threshold saves 350 ms; halving time to first token saves 175. So the first thing I optimise is the endpointer, then streaming the first clause into TTS, then prefill — not the model.

•

Q3. What is endpointing and why is it hard?

Deciding the user's turn is over. VAD tells you whether there is speech; endpointing tells you whether they are finished. A fixed silence threshold trades directly against interruptions: at 300 ms you cut off 34% of turns, at 700 ms 6%, and every millisecond is added to every turn. The escape is semantic endpointing — a classifier over the partial transcript plus prosody plus dialogue state — which gets 300 ms latency at the interruption rate of 900 ms.

•

Q4. How do you implement barge-in?

VAD on the input while the agent is speaking, then cancel the LLM stream, stop the TTS, fade the audio and flush the playout buffer — about 160 ms end to end. Then truncate the conversation history to what was actually played, or the model thinks it said things nobody heard. And it requires acoustic echo cancellation, or the agent hears its own voice and interrupts itself.

•

Q5. The ASR mishears a customer's name. What do you do?

Contextual biasing first — inject the session's contact or account list into the decoder. Then n-best rescoring: give the LLM the top three hypotheses and let dialogue context choose. Then confirm only the low-confidence slot rather than the whole sentence, and keep a spelling mode as the fallback. I would also track entity error rate separately from WER, because that is the one the product lives on.

•

Q6. How is prompting different when the output is spoken?

One or two sentences, no markdown, no URLs, numbers and currency spelled as they are said, one question at a time. Length is a latency control: every extra clause is time the user waits and an opportunity for a half-delivered answer.

•

Q7. A tool call takes 900 ms. How do you keep the conversation alive?

Speak a short filler before the call rather than after — "let me check that" — which covers the whole tool latency, and rotate the phrasing. Past about three seconds, say something else rather than going quiet, and return partial information as soon as any of it is available.

•

Q8. How do you evaluate a voice agent?

Four layers: recognition (WER and entity error rate), interaction (median and p95 time to first audio, interruption rate, barge-in latency), task (success rate, turns to completion, containment), and experience (MOS, abandonment). Critically, evaluate by replaying audio through the whole stack — a text eval hides the agent answering a misheard question perfectly.

•

Q9. What would you log on every turn?

Spans for endpoint, ASR, LLM and TTS, with the endpoint threshold and whether it was overridden, ASR confidence and partial count, the pinned model version and TTFT, TTS characters and chunks, and at the turn level: total latency, whether it was interrupted, and words generated versus words actually played. That last pair is the voice-specific one, and it is what explains a conversation that stopped making sense.

•

Q10. Design the voice assistant for a car.

Wake word and VAD always on device, tiny and tuned to false accepts per hour. A compact streaming recogniser on device covering the fixed command grammar — climate, navigation, media — so those work in a tunnel.
