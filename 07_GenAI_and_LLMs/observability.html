LLM Observability: Metrics, Traces and Spans

The question this file answers: the chatbot was at 95% and this morning it is at 60%. Nothing in the code changed. Where do you look, in what order, and how do you prove it?

Evaluation tells you how good a system is on a fixed dataset. Observability tells you what is happening right now, on real traffic, and — when it breaks — which layer broke. The metrics are the same; the difference is that observability attaches them to a trace so a number on a dashboard can be traced back to the exact request that produced it.

Companions: the metric arithmetic is in 26_LLM_Metrics_and_LLM_as_Judge.md; an interactive version of this page with a live trace waterfall, a retrieval calculator and the incident walkthrough is at LLM_Observability_Visual_Guide.html.

1. Why LLM systems need their own observability

A normal service is observable through status codes and latency. An LLM service returns HTTP 200 with a confidently wrong answer, in 1.8 seconds, at normal cost. Every classical signal is green while the product is broken.

  classical service          LLM service
  ------------------         ---------------------------------------------
  200 vs 500                 200 always. Correctness is a separate signal.
  latency                    still matters, plus time-to-first-token
  throughput                 plus tokens/sec, plus queue depth at the provider
  error rate                 plus refusal rate, hallucination rate, empty-retrieval rate
  deterministic              same input, different output, run to run
  you own the code           the model is a vendor's, and it changes underneath you

Three properties make this worse than it sounds:

  • Non-determinism. You cannot reproduce a failure by replaying the input. You need the actual request captured — inputs, retrieved chunks, the assembled prompt, the raw output.
  • Compound systems. A RAG answer passes through embed → search → rerank → prompt → generate → guardrail. A single accuracy number tells you the pipeline failed, not which stage.
  • Silent drift. Nothing crashes when your corpus grows 3x, when the provider swaps the weights behind a model alias, or when users start asking about a product you never indexed.

The one-line framing. In an LLM system, quality is a production signal, not a pre-deploy signal. If it is only measured at eval time, you will find out about a regression from a customer.

2. The four signals: metrics, logs, traces, evals

The three classical pillars, plus the one LLM systems add.

Signal Shape Answers Cardinality
Metrics numbers over time, aggregated Is something wrong, and since when? low — cheap to keep forever
Logs timestamped text lines What did this component say? high — sampled or expired
Traces a tree of timed spans per request Where in the pipeline did it go wrong? high — sampled
Evals scores attached to traces or datasets Was the answer any good? medium — the LLM-specific one

How they work together, in the order you actually use them during an incident:

  METRIC   answer_accuracy fell 95% -> 60%          "something is wrong"
     |
     v
  METRIC   sliced by cohort: new-product queries at 21%   "it is wrong HERE"
     |
     v
  TRACE    open 20 failing requests, look at the retriever span
     |                                              "it is wrong AT THIS STAGE"
     v
  SPAN     retrieve.docs_above_threshold = 0, top_score = 0.31
     |                                              "and this is the mechanism"
     v
  LOG      indexer: "skipped 1,284 files: unsupported content-type application/pdf"
                                                    "and this is the cause"

A metric without a trace tells you that you are bleeding, not where the wound is. That path — metric to cohort to trace to span to log — is the whole discipline, and it is the answer to "how would you debug this" in an interview.

3. What to measure: the four layers

Instrument four layers. Most teams instrument the third and fourth and then cannot explain a quality drop, because the numbers that explain it live in the first two.

Layer 1 — Quality (the product)

Metric Definition Where it comes from Alert when
Answer accuracy matches ground truth on a fixed regression set offline eval, nightly falls 2 sigma below the 7-day mean
Faithfulness share of answer claims supported by the retrieved context LLM judge on sampled live traces below 0.90
Answer relevancy does the answer address the question LLM judge below 0.85
Refusal rate share of "I cannot answer that" regex or classifier on output doubles week on week
Thumbs-down rate explicit user feedback product UI, joined to the trace doubles, or beats 5%

Layer 2 — Retrieval (the layer that fails most often)

Metric Definition Where it comes from Alert when
Context recall did retrieval find everything the answer needed LLM judge against ground truth below 0.85
Context precision were the retrieved chunks relevant, and ranked well LLM judge, or labelled qrels below 0.60
Recall@k, MRR, NDCG@k the classical ranking metrics, on a labelled set nightly retrieval eval recall@10 below 0.90
Empty-retrieval rate share of requests where nothing cleared the score threshold the retriever span itself above 2%
Mean top-1 score the raw similarity of the best chunk the retriever span drops more than 0.10
Index size and freshness chunk count, age of newest document the indexer job count moves more than 5% unexpectedly

The arithmetic for recall@k, precision@k, MAP, MRR and NDCG — with a five-query worked example you can check on paper — is in 26_LLM_Metrics_and_LLM_as_Judge.md, section 8.

Two of these are free and almost nobody logs them: empty-retrieval rate and mean top-1 score come straight off the retriever span, need no judge, no labels and no LLM call — and they move before answer quality does. They are the cheapest early-warning signal in a RAG system.

Layer 3 — System

Metric Why it matters
p50 / p95 / p99 latency, end to end and per span p95 is where users live; the average hides the tail
Time to first token the only latency number a streaming UI actually feels
Tokens per second the generation-speed signal, independent of answer length
Error rate by type timeout, rate limit, context-length, content filter, tool failure
Retry and fallback rate a fallback to a smaller model is a silent quality change
Queue depth and concurrency saturation shows up here before it shows up in latency

Layer 4 — Cost

Metric Why it matters
Tokens in / out per request the unit of cost; log it on every LLM span
Cost per request, per session, per user the only number finance will ask about
Cache hit rate prompt-cache and semantic-cache hits are the biggest lever
Cost per resolved conversation the honest metric: cheap answers that fail cost more

Rule of thumb. If a metric cannot trigger a decision, do not put it on the dashboard. Four numbers people act on beat forty nobody reads.

4. Traces and spans: the vocabulary

This is the part interviewers probe, because it is where people bluff.

Term What it is
Trace everything that happened for one request, end to end. Identified by a trace_id.
Span one unit of work inside that trace: a function, a call, a stage. Has a span_id.
Parent span the span that caused this one. The parent link is what makes a trace a tree.
Root span the span with no parent — the request itself. Its duration is the user-visible latency.
Span kind SERVER (received a request), CLIENT (called out to something), INTERNAL (in-process work), PRODUCER / CONSUMER (queues).
Attributes key-value pairs on a span: model name, token counts, top_k, chunk IDs, temperature.
Events timestamped points inside a span: first token received, retry attempted, guardrail fired.
Status OK, ERROR, or unset. An exception sets ERROR and records the type.
Context propagation passing trace_id and span_id across threads, processes and HTTP calls so the tree survives a service boundary.
Session / thread the multi-turn grouping above a trace: one conversation is many traces. 
  session  s-8841                      one conversation, many turns
    +-- trace  4f1c9a                  one user message -> one answer
    |     +-- span  chat_request       root, SERVER, 3134 ms
    |     |     +-- span guardrail.input      INTERNAL
    |     |     +-- span retrieve             INTERNAL
    |     |     |     +-- span embed_query    CLIENT
    |     |     |     +-- span vector_search  CLIENT
    |     |     |     +-- span rerank         CLIENT
    |     |     +-- span build_prompt         INTERNAL
    |     |     +-- span llm.generate         CLIENT
    |     |     +-- span guardrail.output     INTERNAL
    +-- trace  4f1d02                  the next turn

Why the tree matters. A flat log of the same request gives you nine lines with no relationship between them. The tree gives you three things a log cannot: self time (a span's own work with its children subtracted), the critical path (which chain of spans actually determines the total), and blame by stage — the ability to say "76% of this request was the model, 20% was retrieval" without instrumenting anything else.

5. A worked trace of one RAG request

One request through a RAG chatbot, drawn from the span timings. This is the output of the tracer in section 7, and every number in it is that program's real output:

TRACE 4f1c9a  duration 3134 ms
SPAN                                   ms     %  WHEN
chat_request                         3134 100.0%  ##############################################
  guardrail.input                      41  1.3%  #
  retrieve                            624 19.9%   #########
    embed_query                        84  2.7%   #
    vector_search                     274  8.7%    ####
    rerank                            259  8.3%        ####
  build_prompt                          7  0.2%            #
  llm.generate                       2371 75.7%            ###################################
  guardrail.output                     77  2.5%                                               #

Read it top to bottom:

  • llm.generate owns 75.7% of the request. Any latency work that does not start with streaming, a shorter prompt or a faster model is decoration. This is the number that kills the "let's optimise the vector search" instinct — the vector search is 8.7%.
  • retrieve is 624 ms but its children are 617 ms, so its own overhead is 7 ms. That is what self time means, and it is how you tell orchestration overhead from real work.
  • rerank at 259 ms is nearly as expensive as the search it reranks. That is the price of a cross-encoder, and it is a deliberate trade — 259 ms for the ranking quality in 26_LLM_Metrics_and_LLM_as_Judge.md, section 8.7.
  • The gaps between bars are yours. Consistent 2 ms gaps here; if they were 200 ms you would be looking at connection-pool waits or JSON serialisation, invisible to every metric.

And the attributes on those spans are where the quality answer lives:

  span retrieve
    top_k                    = 5
    index                    = support-docs-v4
    docs_above_threshold     = 0        <-- nothing cleared the score cut-off
  span rerank
    model                    = rerank-v2
    kept                     = 5
    top_score                = 0.31     <-- best chunk was weak; usually 0.78
  span llm.generate
    model                    = chat-large
    prompt_tokens            = 1842
    completion_tokens        = 214

The trace is green. Status OK, 3.1 seconds, normal cost — and the answer is garbage, because the model was handed five chunks whose best similarity was 0.31. Nothing but a span attribute could have told you that.

6. What every span must carry

The schema below is what turns traces from a curiosity into a debugging tool. Anything missing here is a question you will not be able to answer at 2 a.m.

Span Must carry Nice to have
root / request trace_id, session_id, user_id (hashed), route, app version, prompt-template version tenant, region, client type
retrieve query text, top_k, index name and version, number returned, number above threshold, chunk IDs, scores filters applied, embedding model, rewritten query
embed_query model name and version, dimensions, input length cache hit or miss
rerank model, candidates in, kept out, top score, score of the dropped best latency budget consumed
llm.generate model with the exact version pin, temperature, max tokens, prompt tokens, completion tokens, finish reason, prompt template ID seed, top_p, cache hit, cost
tool / function call tool name, arguments, result size, status, retry count schema version
guardrail which checks ran, which fired, action taken (allow, redact, block) rule version
eval / judge judge model, rubric version, score, the reasoning string human override

Three attributes earn their place above all others:

  1. The exact model version. chat-large is not a version. chat-large-2026-03-11 is. When a provider rolls an alias forward, the only way to prove it is a version string in your traces from before and after.
  2. The prompt template ID or hash. Prompts change more often than code, frequently outside version control. Hash the template and log the hash.
  3. The index version. Every re-index is a deploy. Naming the index support-docs-v4 rather than support-docs turns "did the index change?" from a conversation into a query.

The rule that saves incidents. Log the inputs and outputs of every stage, not just the final answer. If you keep only the question and the answer, a retrieval failure and a generation failure look identical.

7. A tracer from scratch, in 25 lines

Tracing looks like magic until you write one. It is a stack, two timestamps and a parent pointer — the vendors add storage, a UI and sampling, not concepts.

import contextlib


class Tracer:
    """Spans, nesting and timing in 25 lines. A real exporter ships these as JSON."""

    def __init__(self, clock):
        self.clock = clock          # () -> milliseconds; time.perf_counter()*1000 in prod
        self.spans = []             # flat list, parents identified by id
        self.stack = []

    @contextlib.contextmanager
    def span(self, name, kind, **attrs):
        rec = {"id": len(self.spans), "name": name, "kind": kind,
               "parent": self.stack[-1] if self.stack else None,
               "depth": len(self.stack), "attrs": attrs,
               "start": self.clock(), "status": "OK"}
        self.spans.append(rec)
        self.stack.append(rec["id"])
        try:
            yield rec                                   # rec["attrs"] is writable inside
        except Exception as exc:                        # an error is an attribute of a span
            rec["status"] = "ERROR: %s" % type(exc).__name__
            raise
        finally:
            rec["end"] = self.clock()
            self.stack.pop()


class ScriptedClock(object):
    """Returns preset timestamps so the printed trace is byte-identical every run."""

    def __init__(self, ticks):
        self.ticks, self.i = ticks, 0

    def __call__(self):
        self.i += 1
        return self.ticks[self.i - 1]


# one chat request: guardrail -> retrieve(embed, search, rerank) -> prompt -> llm -> guardrail
clock = ScriptedClock([0, 3, 44, 46, 47, 131, 133, 407, 409, 668, 670,
                       672, 679, 681, 3052, 3054, 3131, 3134])
t = Tracer(clock)

with t.span("chat_request", "SERVER", session="s-8841", user_tier="pro"):
    with t.span("guardrail.input", "INTERNAL", checks="pii,injection", blocked=False):
        pass
    with t.span("retrieve", "INTERNAL", top_k=5, index="support-docs-v4") as r:
        with t.span("embed_query", "CLIENT", model="embed-v3", dims=1536):
            pass
        with t.span("vector_search", "CLIENT", index="support-docs-v4", returned=20):
            pass
        with t.span("rerank", "CLIENT", model="rerank-v2", kept=5) as rr:
            rr["attrs"]["top_score"] = 0.31           # <- the number that mattered
        r["attrs"]["docs_above_threshold"] = 0        # <- and the one that named the bug
    with t.span("build_prompt", "INTERNAL", context_chunks=5, prompt_tokens=1842):
        pass
    with t.span("llm.generate", "CLIENT", model="chat-large",
                prompt_tokens=1842, completion_tokens=214, temperature=0.0):
        pass
    with t.span("guardrail.output", "INTERNAL", checks="pii,groundedness", blocked=False):
        pass

# ---------------------------------------------------------------- the waterfall
total = t.spans[0]["end"] - t.spans[0]["start"]
scale = 46.0 / total
print("TRACE 4f1c9a  duration %d ms" % total)
print("%-34s %6s %5s  %s" % ("SPAN", "ms", "%", "WHEN"))
for s in t.spans:
    dur = s["end"] - s["start"]
    off = int(round((s["start"] - t.spans[0]["start"]) * scale))
    bar = max(1, int(round(dur * scale)))
    print("%-34s %6d %4.1f%%  %s%s"
          % ("  " * s["depth"] + s["name"], dur, 100.0 * dur / total,
             " " * off, "#" * bar))

# self time = a span's own work, with its children's time taken out
print()
kids = {}
for s in t.spans:
    kids.setdefault(s["parent"], []).append(s)
for s in t.spans:
    child = sum(c["end"] - c["start"] for c in kids.get(s["id"], []))
    self_ms = (s["end"] - s["start"]) - child
    if self_ms > 20:
        print("self time  %-24s %5d ms" % (s["name"], self_ms))

# rollups: the two numbers every LLM span must carry
print()
tok_in = sum(s["attrs"].get("prompt_tokens", 0) for s in t.spans if s["kind"] == "CLIENT")
tok_out = sum(s["attrs"].get("completion_tokens", 0) for s in t.spans if s["kind"] == "CLIENT")
print("tokens in=%d out=%d   cost = %.5f USD at 3.00/15.00 per 1M"
      % (tok_in, tok_out, tok_in / 1e6 * 3.0 + tok_out / 1e6 * 15.0))

# the assertion that turns a trace into an alert
bad = [s for s in t.spans if s["attrs"].get("docs_above_threshold") == 0]
print("ALERT: %s returned 0 chunks above the score threshold" % bad[0]["name"] if bad else "clean")

SPAN                                   ms     %  WHEN
chat_request                         3134 100.0%  ##############################################
  guardrail.input                      41  1.3%  #

    embed_query                        84  2.7%   #

    rerank                            259  8.3%        ####

Four things in 25 lines that a vendor SDK also does and nothing more:

  • the stack gives you parent links, which give you the tree;
  • two clock reads give you duration, which gives you the waterfall and self time;
  • **attrs gives you the searchable dimensions — model, index, token counts;
  • the except clause attaches errors to the span that raised them, not to the request.

In production, swap ScriptedClock for time.perf_counter, add an exporter that batches spans to a collector, and use contextvars so the stack survives async and threads. The model is identical.

8. OpenTelemetry and the GenAI conventions

OpenTelemetry (OTel) is the vendor-neutral standard for traces, metrics and logs. It matters here for one reason: the LLM tools all speak it, so instrumenting once means you can change backend without re-instrumenting.

The GenAI semantic conventions standardise the attribute names, so a trace from one library is readable by another tool:

  gen_ai.system                  the provider
  gen_ai.request.model           the model asked for
  gen_ai.response.model          the model that actually answered   <- these two differ!
  gen_ai.request.temperature
  gen_ai.request.max_tokens
  gen_ai.usage.input_tokens
  gen_ai.usage.output_tokens
  gen_ai.response.finish_reasons stop | length | content_filter | tool_calls
  gen_ai.operation.name          chat | embeddings | ...

Warning — the two model fields. gen_ai.request.model is what you asked for; gen_ai.response.model is what answered. When a provider moves an alias, only the second one changes, and the difference between them is the cheapest possible detector for "the model changed underneath us". Log both, and alert when the response model is not the one you pinned.

A minimal instrumentation, which is the same shape as the from-scratch tracer:

from opentelemetry import trace

tracer = trace.get_tracer("rag-chatbot")

with tracer.start_as_current_span("retrieve") as span:
    span.set_attribute("index.name", "support-docs-v4")
    span.set_attribute("retrieval.top_k", 5)
    chunks = retriever.search(query, k=5)
    span.set_attribute("retrieval.returned", len(chunks))
    span.set_attribute("retrieval.above_threshold",
                       sum(1 for c in chunks if c.score >= 0.55))
    span.set_attribute("retrieval.top_score", chunks[0].score if chunks else 0.0)
    span.set_attribute("retrieval.chunk_ids", [c.id for c in chunks])

Framework auto-instrumentation (LangChain callbacks, LlamaIndex handlers, the OpenInference instrumentors) gives you the tree for free. It does not give you your own domain attributes — above_threshold, the chunk IDs, the prompt-template hash, the tenant. Auto-instrument for the skeleton, then add the five attributes that are specific to your system; those five are what actually resolve incidents.

10. Sampling, PII and the cost of observability

Tracing every request with full payloads is how observability bills reach the size of the inference bill.

Decision Sensible default Why
Trace sampling 100% of metadata, 100% of errors and thumbs-down, 5–10% of full payloads metadata is small; prompts and chunk text are not
Retention payloads 14–30 days, aggregated metrics forever incidents are found in weeks, trends in months
Payload truncation first 2 KB of each chunk, always the full prompt template ID you rarely need chunk 5 in full, you always need to know which chunk it was
PII redact before export, not in the UI once it is in the vendor's store, it is in their backups
Tail sampling keep 100% of slow, errored or low-scored traces the interesting traces are exactly the unrepresentative ones

Head sampling versus tail sampling. Head sampling decides at the start of a request ("keep 5%") — cheap, and it throws away failures. Tail sampling decides after the request finishes, once you know it was slow, errored, or scored badly — a little more infrastructure, and it keeps every trace you will actually want. Use tail sampling for anything with a quality signal.

Redaction that works: run the same PII detector you use in the input guardrail over the span payloads at export time, hash user IDs with a per-tenant salt so traces are still joinable, and keep an allowlist of attributes that may leave the boundary rather than a blocklist of ones that may not.

11. Online evals: scoring live traffic

Offline evaluation runs a fixed dataset before deploy. Online evaluation scores real traffic after deploy — and it is the signal that catches everything the dataset did not anticipate.

  every request  -> trace stored
        |
        +-- cheap, deterministic checks on 100%      free, instant
        |     empty retrieval, top_score, schema valid, refusal regex,
        |     citation present, answer length, latency, cost
        |
        +-- LLM judge on a 1-5% sample               costs money, runs async
        |     faithfulness, answer relevancy, context precision
        |
        +-- human review on the worst 20/day         the ground truth
              anything the judge scored low, all thumbs-down, all escalations

Three rules that make this affordable and honest:

  1. Never block the response on a judge. Score asynchronously from the stored trace. A judge in the request path adds a second of latency and a second failure mode.
  2. Deterministic checks are free — run them on everything. Empty retrieval, missing citation, malformed JSON and refusal patterns need no model. In practice these catch most real incidents; the judge explains the rest.
  3. Sample for the judge, and stratify. Random 2% plus 100% of thumbs-down plus 100% of low-similarity retrievals. Judge cost then scales with your traffic's problems, not your traffic.

Wire user feedback back onto the trace ID. A thumbs-down that cannot be resolved to the exact retrieved chunks and prompt is an anecdote; one that can is a test case.

12. Alerts that actually fire

A quality alert is a statistical statement, and the sample size decides what you can even see. With a daily eval set of N at a baseline accuracy p, the standard error is sqrt(p * (1 - p) / N):

  N=50   /day  smallest drop a 2-sigma alert can see: 6.2 pts
  N=200  /day  smallest drop a 2-sigma alert can see: 3.1 pts
  N=1000 /day  smallest drop a 2-sigma alert can see: 1.4 pts

So a 200-sample daily eval cannot distinguish 95% from 93%, and an alert set at "any drop" will page you constantly on noise. Set the threshold from the arithmetic, not from a round number.

Alert Condition Why this one
Quality regression daily accuracy below the 7-day mean by 2 sigma, two days running catches drift without paging on noise
Empty retrieval rate above 2% over 30 min the earliest RAG signal there is, and it needs no judge
Top-1 score collapse mean top-1 similarity falls more than 0.10 day over day catches an index or embedding change within an hour
Response model mismatch gen_ai.response.model is not the pinned version catches a provider alias roll immediately
Refusal spike refusal rate doubles day over day catches guardrail and prompt regressions
p95 latency above the SLO for 10 min classical, still necessary
Cost per request 1.5x the 7-day mean catches prompt bloat and retry storms

The one that pays for itself. Empty-retrieval rate and mean top-1 score come off the retriever span, cost nothing to compute, and move hours before answer quality does. If you add exactly two alerts to a RAG system, add those.

13. Scenario: accuracy fell from 95% to 60%

"Our RAG chatbot was at 95% accuracy. It is now at 60%. Nobody deployed anything. How do you find out what happened, and what do you do about it?"

A 35-point drop is almost always a breakdown in one of two layers: retrieval (the model was handed the wrong context) or generation (the model had the right context and mishandled it). Everything below is a way of deciding which — before touching a single prompt.

Step 1 — Isolate: retrieval failure or generation failure?

Do not theorise. Decouple the two layers and let the numbers pick a branch:

                        +--- RETRIEVAL failure: the right chunk never reached the prompt
      95% -> 60%  ------+
                        +--- GENERATION failure: the right chunk was there and was ignored

Four metrics split the blame, and they are the reason to compute four numbers rather than one satisfaction score:

Metric Question Needs Points at
Context recall did the top-k chunks contain what the answer needed? context + ground truth retrieval
Context precision were the retrieved chunks relevant, and ranked well? question + context retrieval / ranking
Faithfulness is every claim in the answer supported by the context? answer + context generation
Answer relevancy does the answer address the question asked? question + answer generation

Run those four on 200 failing requests and read the pair:

Context recall Faithfulness Verdict Where to go
low high Retrieval failure. The model was faithful to context that did not contain the answer. Step 3, Stages 1-2, then the Step 4 catalogue
high low Generation failure. The answer was there and the model invented something else. Step 3, Stage 3, then the Step 4 catalogue
high Neither — the ground truth or the judge moved. Re-check the eval set and the judge prompt. Step 2, then the eval set
low low Both, or a systemic change (index empty, wrong tenant, truncated prompt). Step 2, look at one trace

In this incident the numbers came back like this:

Metric Four weeks ago Today Read
Answer accuracy 0.95 0.60 the symptom
Context recall 0.93 0.48 collapsed
Context precision 0.71 0.44 fell with it
Faithfulness 0.96 0.95 unchanged
Answer relevancy 0.94 0.91 broadly fine
Mean top-1 similarity 0.78 0.41 the mechanism
Empty-retrieval rate 0.4% 11.2% the alarm nobody had set

Faithfulness is unchanged at 0.95 while context recall halved. The generator is doing its job perfectly — faithfully summarising context that no longer contains the answer. This is a retrieval failure, and every hour spent on the prompt would have been wasted.

Step 2 — Trace and monitor: get from "wrong" to "wrong here"

Two moves, in this order.

2a. Slice the metric before you open a trace. An average is a mix of populations, and a mix can move for reasons that have nothing to do with quality. Split by document type, tenant, query intent, language, channel, model version, and query date versus document date:

Cohort Share of traffic Accuracy Change
Questions about existing product docs (A) 60% 0.86 was 0.96
Questions about the new product line (B) 40% 0.21 was 0.86

That single table converts "the bot got worse" into "the bot cannot answer anything about the product we launched three weeks ago, and it got slightly worse at everything else". Those are two different bugs with two different fixes.

Decompose the headline number so you can say exactly how much each effect contributed — changing one thing at a time:

import math

# cohort A = questions about the existing product docs, cohort B = the new product line
BASE = {"mix": (0.90, 0.10), "acc": (0.96, 0.86)}      # four weeks ago
NOW = {"mix": (0.60, 0.40), "acc": (0.86, 0.21)}       # today


def overall(mix, acc):
    return mix[0] * acc[0] + mix[1] * acc[1]


b, n = overall(**BASE), overall(**NOW)
print("baseline %.1f%%   today %.1f%%   drop %.1f points" % (b * 100, n * 100, (b - n) * 100))

# change one thing at a time, in order: mix, then each cohort's own accuracy
steps = [("traffic mix 90/10 -> 60/40, accuracy unchanged", NOW["mix"], BASE["acc"]),
         ("cohort A accuracy 96% -> 86%", NOW["mix"], (NOW["acc"][0], BASE["acc"][1])),
         ("cohort B accuracy 86% -> 21%", NOW["mix"], NOW["acc"])]
prev = b
for label, mix, acc in steps:
    cur = overall(mix, acc)
    print("  %-45s %.1f%%  (%+.1f pts)" % (label, cur * 100, (cur - prev) * 100))
    prev = cur
print("  %-45s %+.1f pts" % ("total", (prev - b) * 100))

# is any of this noise? binomial standard error on the daily eval set
print()
for label, N, p in (("baseline, 200/day", 200, 0.95), ("today, 200/day", 200, 0.60),
                    ("cohort B only, 80 samples", 80, 0.21)):
    se = math.sqrt(p * (1 - p) / N)
    print("%-28s p=%.2f  95%% CI = +/-%.1f pts" % (label, p, 1.96 * se * 100))
se = math.sqrt(0.95 * 0.05 / 200)
print("the 35-point drop is %.1f standard errors: not noise" % (0.35 / se))

# how big a drop can you even detect at a given daily sample size?
print()
for N in (50, 200, 1000):
    print("N=%-5d/day  smallest drop a 2-sigma alert can see: %.1f pts"
          % (N, 2 * math.sqrt(0.95 * 0.05 / N) * 100))
baseline 95.0%   today 60.0%   drop 35.0 points
  traffic mix 90/10 -> 60/40, accuracy unchanged 92.0%  (-3.0 pts)
  cohort A accuracy 96% -> 86%                  86.0%  (-6.0 pts)
  cohort B accuracy 86% -> 21%                  60.0%  (-26.0 pts)
  total                                         -35.0 pts

The 35 points are now three separate numbers with three separate owners:

  • 3 points are not a regression at alltraffic shifted towards a harder cohort. Same system, worse average. Reporting this as a quality failure would be wrong.
  • 6 points are cohort A getting worse, which needs its own explanation.
  • 26 points are cohort B collapsing, and that is the incident.

And the confidence intervals settle the "is it noise?" question before anyone asks it: the drop is 22.7 standard errors from baseline. Cohort B's 21% carries ±8.9 points on 80 samples, so it is somewhere between 12% and 30% — precise enough to act on, not precise enough to quote.

2b. Now open the traces. Twenty failing requests from cohort B, and read the retriever span, not the answer:

Span attribute Healthy trace Failing trace
retrieve.index support-docs-v4 support-docs-v4 — same index
retrieve.returned 20 20 — the search itself worked
retrieve.above_threshold 6 0 — nothing cleared the cut-off
rerank.top_score 0.78 0.31 — the best chunk was weakly related
retrieve.chunk_ids mixed doc IDs all from the old product manual
llm.generate.model pinned version same pinned version
build_prompt.prompt_tokens 1842 1799 — no truncation

The retrieved chunk IDs are all from the old manual. Not one chunk from the new product documentation appears in any failing trace, at any rank. The retriever is not misranking the new documents — it has never seen them.

One query against the index closes it: SELECT count(*) WHERE source LIKE 'new-product%' returns 0. And the indexer log from the day the new docs landed says:

  indexer 2026-07-28T02:14Z  processed 4,102 files, indexed 2,818,
                             skipped 1,284: unsupported content-type application/pdf

The new product documentation shipped as PDFs. The ingestion pipeline silently skipped every one of them — logged at INFO, alerted on by nothing.

Step 3 — Walk the stack bottom-up, in three stages

Step 1 told you which half of the system to look at. This is the order to search it in — from the data layer upward, because every layer's input is the layer below's output. Debugging retrieval while the ingestion is broken is how teams lose a week: the retriever is behaving perfectly, over a corpus that is missing a third of its documents.

  Stage 1  DATA         did the right content get in, intact and current?
     |                  (verify this BEFORE you look at the AI at all)
     v
  Stage 2  RETRIEVAL    given that it is in, does the right chunk come back, and rank high?
     |
     v
  Stage 3  GENERATION   given that the chunk arrived, does the model use it properly?

Stage 1 — Data ingestion and pipeline health

Nothing here involves a model. It is also where most "the AI got worse" incidents actually live — including this one.

Check The question How to verify it in ten minutes Fix
New-data poisoning Did a recent ingest introduce noise, boilerplate, or contradictory content? Count chunks by source and by ingest date; sample 20 of the newest; measure the near-duplicate ratio Deduplicate at ingest; supersede old versions instead of adding beside them; stamp an effective date and filter on it
Stale index Was the source updated but re-indexing never triggered? Compare the newest document timestamp in the index against the source system Publish index freshness as a metric and alert on it; a job that exits 0 is not proof that documents landed
Chunking strategy Does the current chunking handle newly added document types — tables, PDFs, code, slides? Mean and minimum chunk length per source; eyeball chunks from the new type for cut sentences and orphaned table rows Structure-aware splitting, 10–15% overlap, keep tables and headers with their content, and version the chunk config next to the index

The contradiction case deserves its own sentence, because it is the subtle one: when the old policy document and its replacement are both in the index, retrieval works flawlessly and returns both, and the model picks one — sometimes the wrong one. Precision and recall both look fine. Only recency metadata or a supersede step fixes it.

Stage 2 — Embedding and retrieval performance

The data is verified. Now check how it is being fetched.

Check The question Signature Fix
Embedding model drift Did the embedding model version change, so queries no longer live in the same space as the stored vectors? Every similarity score drops at once, across all cohorts, on a specific date Pin the embedding model and dimensions; re-embed the whole corpus — a half-migrated index is worse than either version
Distance metric mismatch Cosine, dot product or L2 — did the index config change? Scores land in a different range than before Pin it in the index config; assert the score distribution at deploy
Threshold and filters Is the similarity cut-off or a metadata filter silently excluding everything? Empty-retrieval rate up with the search itself returning results Log the filter and the threshold on the span; assert non-empty results after filtering

Then measure against the labelled ground truth — this is where the three retrieval metrics earn their keep, and the arithmetic for all of them is in 26_LLM_Metrics_and_LLM_as_Judge.md, section 8:

  • Recall@kis the chunk containing the answer retrieved at all? If this is low, nothing downstream can save you: the answer never reached the prompt. Fix chunking, embeddings, k, or add hybrid search.
  • Precision@kare the retrieved chunks actually relevant, or is the model reading noise? Low precision with healthy recall means the answer is in there with distractors around it — tighten the threshold, deduplicate, filter on metadata.
  • MRRhow far down the list does the correct chunk appear? Good recall with poor MRR is the classic reranker case: retrieval found it and ranked it eighth, and the generator never looks that far down. 
  recall LOW                  -> it was never retrieved.      fix ingestion, chunking, embeddings, k
  recall HIGH, MRR LOW        -> retrieved but buried.        add a reranker
  recall HIGH, precision LOW  -> retrieved with noise around. threshold, dedupe, metadata filters

Stage 3 — Generation and LLM behaviour

Only reached if the correct context demonstrably arrived in the prompt. The failure is now in how the model was asked, or in what it was asked to do.

Check The question Signature Fix
Context overflow / lost in the middle Are we fetching so many chunks that the prompt truncates, or that the answer sits in the middle where attention is weakest? prompt_tokens near the limit, finish_reason = length, accuracy fell after top_k was raised, gold chunk at rank 6+ Rerank down to 3–5 dense chunks; budget tokens explicitly; place the best chunk first and last; truncate deliberately, never by accident
Instruction drift Was the system prompt or a baseline instruction altered, so the model formats badly or drops a constraint? Prompt-template hash changed; format-error or refusal rate jumped with no model change Version prompt templates and treat an edit as a deploy with an eval gate; log the template ID on the span
Shift in user behaviour Have users started asking fundamentally different questions — multi-hop, comparative, analytical — that the retrieval strategy was never designed for? Query length and intent mix moved; failures cluster on "compare", "why", "across all" Query decomposition and multi-hop retrieval, an intent router, and — first — new eval cases, because the system is not broken, it is being asked something new

That last row is the one candidates miss. Nothing regressed; the job changed. A pipeline built for "what is the refund window" does not answer "how did the refund policy change between the 2024 and 2026 contracts" — that needs two retrievals and a comparison, and no amount of prompt tuning gets there. It is also the honest answer when the change log is genuinely empty.

Where this incident sat. Stage 1. The retriever, the embeddings, the reranker, the prompt and the model were all behaving exactly as designed — over a corpus that was missing 1,284 documents. Stages 2 and 3 would have been a week of tuning something that was never broken.

Step 4 — The cause catalogue, by layer

The stage walk narrows it to a layer; this is the catalogue inside each one — the signature of every common cause, so you can name the check rather than guess.

Scenario A — Retrieval layer (Stages 1 and 2)

Cause Signature in metrics and traces Fix
Ingestion gap (this incident) context recall collapses for one cohort; chunk IDs never include the new source; index count flat after an ingest fail the ingest job on skipped files; assert expected document count per source; re-index; alert on index count deltas
Embedding drift / model change every similarity score drops at once, across all cohorts, on a known date pin the embedding model version; queries and documents must use the same model — re-embed the whole corpus, never half
Chunking change recall falls where answers span boundaries; mean chunk length changed re-chunk with overlap (roughly 10–15%); keep chunk config in version control and stamp the version on the index
Index degradation or rebuild failure vector count changed; search returns fewer results; raw search is bad with no LLM involved rebuild; test the retriever without the LLM — that isolates it in one query
Distance-metric mismatch scores in a different range than before (cosine versus dot product versus L2) pin the metric in the index config; assert the score distribution at deploy
Corpus dilution precision falls slowly as the index grows; near-duplicate chunks crowd the top k add a reranker; metadata filters; deduplicate at ingest
Query drift user phrasing changed — shorter, more keyword-like, a new language query rewriting, HyDE, hybrid BM25 + dense search with RRF fusion
Metadata filter bug a filter silently matches nothing, so recall is zero for one tenant or date range assert non-empty results after filtering; log the filter on the span

Scenario B — Generation layer (Stage 3)

Cause Signature in metrics and traces Fix
Provider rolled the model gen_ai.response.model differs from gen_ai.request.model; behaviour changes with no deploy pin exact dated versions; alert on the mismatch; keep a regression set to re-run on every version bump
Prompt regression prompt-template hash changed; refusal or format-error rate jumped version prompt templates; treat a prompt edit as a deploy with an eval gate
Sampling settings temperature or top_p changed; output variance up, exact-match accuracy down pin temperature (0 for extraction); log sampling params on the span
Context overflow / truncation prompt tokens at the limit; finish_reason = length; the answer stops mid-sentence budget the context; count tokens before the call; truncate deliberately, not accidentally
Lost in the middle accuracy falls after top_k was raised; the right chunk is present but at rank 8 rerank down to 3–5 dense chunks; put the best chunk first and last; do not confuse more context with better context
Fallback model firing error or timeout rate up, and a cheaper model in the response-model attribute alert on fallback rate — a silent fallback is a silent quality change
Guardrail over-blocking refusal rate up; guardrail span shows a rule firing version the rules; log which rule fired; review the false-positive rate

The 30-second version of Step 4. Faithfulness high and context recall low means fix retrieval. Faithfulness low and context recall high means fix the prompt or the model. Both low means look at one trace before touching anything, because something systemic changed.

Step 5 — Mitigate, in three horizons

When Action Why
Hour 0–1 Re-index the new product PDFs through the OCR path. Add a "we do not have docs on X yet" fallback so the bot stops guessing. Restores cohort B, and an honest refusal beats a confident wrong answer.
Hour 1–4 Fail the ingest job on any skipped file. Alert on empty-retrieval rate above 2% and on index count deltas. The bug was invisible for three weeks because nothing watched the ingest.
Day 1–2 Add cohort B queries to the regression set. Add a reranker for cohort A's dilution. Re-run the four RAG metrics per cohort. Fixes the 6-point half of the drop and proves the 26-point half.
Week 1 Eval gate in CI: no deploy, prompt change or re-index ships without the retrieval suite passing. Per-cohort dashboards. Tail-sampled traces on every low-score answer. Turns a three-week incident into a same-day alert.

Communicating it — the sentence to say to a stakeholder: "Two things happened. Traffic shifted towards a new product, which accounts for 3 points. And the documentation for that product never made it into the index because it arrived as scanned PDFs, which accounts for 26. The docs are re-indexing now and the bot will say it does not know rather than guess in the meantime. We are adding an alert that would have caught this on day one."

Step 6 — The answer as you would say it out loud

"First I would check whether it is real — with a 200-sample daily eval, ±3 points is noise, and 35 points is 23 standard errors, so it is real. Then I would slice before theorising: by document type, tenant, query intent and date. Here that showed the drop was concentrated in one cohort, and that a traffic-mix shift accounted for 3 of the 35 points on its own.

Then I would decouple retrieval from generation, because a RAG answer can fail in two completely different places. Faithfulness was flat at 0.95 while context recall halved from 0.93 to 0.48 — the model was faithfully summarising context that did not contain the answer. That is a retrieval failure, so the prompt is not the problem.

Then traces. Twenty failing requests all showed zero chunks above the similarity threshold and a top score of 0.31 against a normal 0.78, and every retrieved chunk came from the old manual. A count against the index confirmed nothing from the new product was in it, and the indexer log showed 1,284 PDFs skipped as an unsupported content type.

Short term: re-index through the OCR path and make the bot say it does not know instead of guessing. Medium term: fail the ingest on skipped files and alert on empty-retrieval rate and index-count deltas — both come free off the retriever span. Long term: an eval gate in CI so a re-index cannot ship without the retrieval suite passing, and per-cohort dashboards so an average never hides a cohort again."

14. The runbook, condensed

Pin this next to the dashboard.

   1. Is it real?          sample size, confidence interval, 2 days of data
   2. When did it start?   the exact hour. Line it up against the change log.
   3. What changed?        deploys, prompt edits, index rebuilds, provider notices,
                           config, traffic mix. Assume something did.
   4. Slice it.            cohort, tenant, doc type, intent, language, model version.
                           An average is a mix of populations.
   5. Split the blame.     context recall vs faithfulness -> retrieval or generation.
   6. Open 20 traces.      failing ones, and healthy ones from before, side by side.
   7. Read the spans.      above_threshold, top_score, chunk_ids, response.model,
                           prompt_tokens, finish_reason.
   8. Test the layer.      run the retriever with no LLM. Run the LLM with hand-picked
                           perfect context. Whichever fails is the culprit.
   9. Mitigate first.      roll back, refuse honestly, or fall back. Then fix.
  10. Add the alert.       the incident is not closed until the detector exists.

Step 8 is the one people skip and the one that ends arguments: run the retriever on its own, then run the generator with hand-picked perfect context. Two experiments, ten minutes, and they name the broken layer with no metrics at all.

15. Pitfalls
Pitfall Why it hurts
Only logging the final answer Retrieval and generation failures look identical. You cannot debug what you did not capture.
One accuracy number, no slices An average hides a cohort collapsing. Here it hid a 21% cohort inside a 60% headline.
No version pins Model alias, embedding model, prompt template, index, chunking config. Without all five, "nothing changed" is unprovable.
Blocking on an LLM judge in the request path A second of latency and a second failure mode, for a score you can compute afterwards.
Alerting on any drop 200 samples carry ±3 points. Alert on 2 sigma over two days, or people stop reading alerts.
Tracing without attributes A tree of span names with no top_score, no chunk IDs and no token counts is a pretty picture.
Head sampling at 5% You keep a random 5% and throw away the failures. Tail-sample on error, latency and score.
Shipping payloads with PII to a vendor Redact at export. Once it is in their store it is in their backups.
No eval gate on re-index A re-index is a deploy of your knowledge base and deserves the same gate as code.
Fixing the prompt first It is the most visible knob and, in RAG, usually the wrong one. Check context recall before touching it.
16. Interview drill
•

Q1. What is the difference between a trace and a span?

A trace is one request end to end; a span is one unit of work inside it. Spans carry a parent pointer, which makes a trace a tree — that is what lets you attribute latency and failure to a stage rather than to the request as a whole. A session groups the traces of one conversation.

•

Q2. Your RAG bot's accuracy dropped 35 points overnight. First three things you check?

Is it statistically real given the eval sample size; when exactly it started, lined up against the change log; and context recall versus faithfulness, to decide whether it is a retrieval or a generation failure. Only then do I open traces.

•

Q3. Faithfulness is 0.95 and accuracy is 60%. What does that tell you?

That generation is healthy and retrieval is not. The model is faithfully summarising the context it was given, so the context is missing the answer. Look at context recall, the empty-retrieval rate and the top-1 similarity score.

•

Q4. Which two RAG metrics would you alert on if you could only have two?

Empty-retrieval rate and mean top-1 similarity. Both come straight off the retriever span, need no judge and no labels, cost nothing, and move hours before answer quality does.

•

Q5. How do you tell whether the provider changed the model under you?

Log gen_ai.request.model and gen_ai.response.model separately and alert when they differ from the pinned version. Then re-run the frozen regression set against both versions to quantify the change rather than argue about it.

•

Q6. What do you put on a retriever span?

Query, index name and version, top_k, number returned, number above threshold, chunk IDs, scores, and any metadata filter applied. The two that resolve incidents are above_threshold and the chunk IDs.

•

Q7. How do you keep observability from costing more than inference?

Metadata on 100% of requests, payloads tail-sampled — every error, every slow request, every low score, plus a few per cent of the rest. Truncate chunk text, keep aggregated metrics forever and payloads for two to four weeks, and run the LLM judge on a stratified sample rather than on everything.

•

Q8. Why does raising top_k sometimes lower accuracy?

More context is more distractors. Recall improves, precision falls, and the model has to find the answer in the middle of a long prompt, where attention is weakest. The fix is a reranker that cuts a wide candidate set down to three to five dense chunks, not a bigger prompt.

•

Q9. Your eval set says 95% and users are complaining. What is wrong?

The eval set is not the traffic. Mine real queries from logs, check the cohort mix, and look for populations the dataset never contained — a new product, a new language, a new document type. This is exactly the mix shift that accounted for 3 of the 35 points in section 13.

•

Q10. What is the smallest useful observability setup for a RAG service?

Trace every request with spans for retrieve and generate; on the retrieve span log above_threshold, top_score and chunk IDs; on the generate span log the pinned model version and token counts; run deterministic checks on 100% and a judge on 2%; and set two alerts — empty retrieval and top-1 score collapse. That is an afternoon of work and it catches most of what actually breaks.
