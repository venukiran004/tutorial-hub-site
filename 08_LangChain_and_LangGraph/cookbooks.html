Implementing RAG with LangChain — Retrieval Strategies Cookbook

Scope: One place to implement every RAG retrieval strategy: plain similarity search (dense/bi-encoder), BM25 (sparse/keyword), hybrid search, RRF fusion, MMR (diversity), cross-encoder reranking, and accuracy/evaluation. For each: intuition → formula → from-scratch Python (verified, with real output) → the LangChain one-liner. Ends with the full combined pipeline and how to measure it.

Why from-scratch AND LangChain? The LangChain call is one line, but if you don't know what it does you can't tune or debug it. Every section shows the mechanism, then the shortcut.

1. The Mental Model — Recall then Precision

two stagesStage 1 must not missStage 2 must rank correctly

Every serious RAG retriever is two stages, and almost every strategy below is just "which stage am I improving?"

        ┌──────────── STAGE 1: RECALL ────────────┐   ┌─── STAGE 2: PRECISION ───┐
query ─▶│ cast a WIDE net, cheaply → top ~20-50   │──▶│ re-score them EXPENSIVELY │──▶ top 3-5 ─▶ LLM
        │  • dense similarity (bi-encoder)         │   │  • cross-encoder reranker │
        │  • BM25 (keyword)                        │   │  (slow, very accurate)    │
        │  • hybrid = both, fused by RRF           │   └──────────────────────────┘
        │  • MMR = drop near-duplicates            │
        └─────────────────────────────────────────┘
        "don't MISS the right doc"                     "put the right doc FIRST"
  • Stage 1 must not miss the answer (high recall) — it's fast and approximate, so cast wide (fetch_k=20-50).
  • Stage 2 must rank correctly (high precision) — it's slow and accurate, so only run it on stage 1's shortlist.

The one-line summary of this whole file: hybrid + RRF fixes recall; MMR fixes redundancy; the cross-encoder fixes ranking.

2. The "Encoder Thing" — Bi-Encoder vs Cross-Encoder

Used forInputseparatelytogether as one pairOutputCost

This is the concept that makes the two-stage design make sense, and it's the thing most people get fuzzy on.

BI-ENCODER (retrieval — fast)          CROSS-ENCODER (reranking — accurate)

Why not use the cross-encoder for everything? It can't be indexed. Scoring 1M docs per query = 1M forward passes. So: bi-encoder to get 50 candidates, cross-encoder to rank those 50. That's the whole game.

4. Strategy 1 — Similarity Search (dense)

IntuitionparaphraseFormula — cosine similarityFrom scratchLangChainWeakness

Intuition. Embed the query, find the chunks whose vectors point in the most similar direction. Direction ≈ meaning, so this matches paraphrase ("how do I get my money back?" finds a "Refund Policy" chunk with no shared words).

Formula — cosine similarity (angle between vectors, ignores length):

                  A · B            Σ aᵢbᵢ
cos(A, B) = ───────────────  = ──────────────────
              ‖A‖ · ‖B‖        √Σaᵢ² · √Σbᵢ²

  = 1.0  → identical direction (same meaning)
  = 0.0  → orthogonal (unrelated)
  = -1.0 → opposite

From scratch (verified output):

import math

def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    na  = math.sqrt(sum(x * x for x in a))
    nb  = math.sqrt(sum(y * y for y in b))
    return dot / (na * nb) if na and nb else 0.0

q = [1.0, 0.0]
print(cosine(q, [1.0, 0.0]))   # 1.0     identical direction
print(cosine(q, [0.0, 1.0]))   # 0.0     orthogonal → unrelated
print(cosine(q, [1.0, 1.0]))   # 0.7071  45° apart → partially related

LangChain:

# Plain top-k similarity
retriever = vectorstore.as_retriever(search_type="similarity",
                                     search_kwargs={"k": 4})

# With scores (needed for the no-context guard — see 16_RAG_Failure_Handling.md)
hits = vectorstore.similarity_search_with_relevance_scores("how do I get a refund?", k=4)
for doc, score in hits:
    print(f"{score:.3f}  {doc.page_content[:60]}")

    search_type="similarity_score_threshold",
    search_kwargs={"score_threshold": 0.75, "k": 4},
)

Weakness: embeddings capture semantics, not exact tokens — so rare IDs, product codes, and acronyms ("X-4471", "ERR_5012") get no strong signal. That's what BM25 fixes.

5. Strategy 2 — BM25 (sparse / keyword)

IntuitionrareoftenTF (term frequency)IDF (inverse document frequency)Length normalization

Intuition. The classic keyword ranking function (what search engines used for decades). A doc scores high when it contains the query's rare words often, adjusted for document length. No embeddings involved — pure term statistics.

Three ideas baked into the formula: 1. TF (term frequency) — more occurrences = more relevant, but with saturation (the 10th "refund" adds less than the 2nd). 2. IDF (inverse document frequency) — rare words matter more ("refund" > "the"). 3. Length normalization — a term in a short doc counts more than in a long one.

Formula:

                       f(q,D) · (k₁ + 1)
BM25(D,Q) = Σ IDF(q) · ─────────────────────────────────
            q∈Q         f(q,D) + k₁ · (1 - b + b · |D|/avgdl)

  f(q,D) = times term q appears in doc D       k₁ ≈ 1.5 (TF saturation)
  |D|    = length of D,  avgdl = mean length   b  ≈ 0.75 (length normalization)

              N - n(q) + 0.5
IDF(q) = ln( ──────────────── + 1 )      N = total docs, n(q) = docs containing q
                n(q) + 0.5

From scratch (verified output):

import math

class BM25:
    def __init__(self, corpus_tokens, k1=1.5, b=0.75):
        self.corpus, self.k1, self.b = corpus_tokens, k1, b
        self.N = len(corpus_tokens)
        self.avgdl = sum(len(d) for d in corpus_tokens) / self.N
        self.df = {}                                  # how many docs contain each term
        for doc in corpus_tokens:
            for term in set(doc):
                self.df[term] = self.df.get(term, 0) + 1

    def idf(self, term):
        n = self.df.get(term, 0)
        return math.log((self.N - n + 0.5) / (n + 0.5) + 1)

    def score(self, query_tokens, idx):
        doc, dl, s = self.corpus[idx], len(self.corpus[idx]), 0.0
        for term in query_tokens:
            f = doc.count(term)
            if f == 0:
                continue                              # term absent → contributes nothing
            num = f * (self.k1 + 1)
            den = f + self.k1 * (1 - self.b + self.b * dl / self.avgdl)
            s += self.idf(term) * num / den
        return s

    def search(self, query_tokens, k=3):
        scored = [(i, self.score(query_tokens, i)) for i in range(self.N)]
        scored.sort(key=lambda x: -x[1])
        return scored[:k]

docs_text = [
    "the cat sat on the mat",
    "the dog sat on the log",
    "cats and dogs are pets",
    "python is a programming language",
]
bm25 = BM25([d.split() for d in docs_text])

print(bm25.avgdl)          # 5.5
print(bm25.idf("cat"))     # 1.204   ← rare term, high IDF
print(bm25.idf("the"))     # 0.6931  ← common term, low IDF

for i, s in bm25.search(["cat"], k=4):
    print(f"doc{i} {s:.4f} | {docs_text[i]}")
# doc0 1.1567 | the cat sat on the mat
# doc1 0.0000 | the dog sat on the log
# doc2 0.0000 | cats and dogs are pets      ← ⚠️ "cats" ≠ "cat"!
# doc3 0.0000 | python is a programming language

⚠️ Read that last result — it's the whole argument for hybrid search. BM25 scores "cats and dogs are pets" at 0.0 for the query "cat", because BM25 matches exact tokens and "cat" != "cats". Stemming helps, but the general lesson stands: BM25 is literal. A dense retriever would score that doc highly (it knows cats≈cat). Conversely, dense retrieval would miss "ERR_5012". Each fails where the other succeeds → run both.

6. Strategy 3 — Hybrid Search (dense + sparse)

IntuitionbothThe merge problemcannot just add themLangChainTuning weights

Intuition. Run both retrievers and merge their results. Dense catches meaning, sparse catches exact terms. The union has far better recall than either alone.

              ┌─▶ dense (bi-encoder) ─▶ [d1, d5, d2, ...] ─┐
query ────────┤                                            ├─▶ FUSE (RRF) ─▶ merged ranking
              └─▶ sparse (BM25)      ─▶ [d5, d9, d1, ...] ─┘

The merge problem: dense scores are cosines (~0.0–1.0), BM25 scores are unbounded (0 → 15+). You cannot just add them — different scales. Two options: normalize both (fragile, corpus-dependent), or ignore the scores and use only the ranks → that's RRF, next section.

LangChain — EnsembleRetriever does hybrid + RRF fusion for you:

from langchain.retrievers import EnsembleRetriever

dense_retriever = vectorstore.as_retriever(search_kwargs={"k": 10})
bm25_retriever  = BM25Retriever.from_documents(chunks); bm25_retriever.k = 10

hybrid = EnsembleRetriever(
    retrievers=[bm25_retriever, dense_retriever],
    weights=[0.4, 0.6],          # relative trust; must sum to 1.0
)                                 # ← fuses internally with weighted RRF
hybrid.invoke("what is the refund window for ERR_5012?")

Tuning weights: start [0.5, 0.5]. Lean sparse ([0.6, 0.4]) for keyword/code/ID-heavy corpora (logs, error codes, legal citations); lean dense for natural-language Q&A. Measure with Recall@k (§11) — don't guess.

7. Strategy 4 — RRF (Reciprocal Rank Fusion)

Intuitionbothno score calibrationFormulaFrom scratchThe insight in one line

Intuition. "Forget the scores — trust the ranks." Each list votes for a doc with strength 1/(k + rank). Being #1 in a list is worth a lot; being #40 is worth almost nothing. A doc ranked decently by both retrievers beats one ranked #1 by only one. It needs no score calibration, which is exactly why it's the default hybrid fusion.

Formula:

                      1
RRF(d) =  Σ    ─────────────────           k ≈ 60 (dampens the top ranks)
        lists   k + rank(d, list)          rank is 1-based

Why k=60? It flattens the curve so the #1 slot isn't overwhelming:
  rank 1 → 1/61 = 0.0164        rank 5  → 1/65 = 0.0154
  rank 2 → 1/62 = 0.0161        rank 20 → 1/80 = 0.0125
A doc at rank 2 in BOTH lists (0.0323) beats a doc at rank 1 in ONE (0.0164).

From scratch (verified output):

def reciprocal_rank_fusion(ranked_lists, k=60):
    scores = {}
    for lst in ranked_lists:
        for rank, doc_id in enumerate(lst):          # enumerate is 0-based
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank + 1)
    return sorted(scores, key=scores.get, reverse=True)

dense  = ["A", "B", "C", "D"]     # A is dense's favourite
sparse = ["C", "A", "E", "B"]     # C is sparse's favourite

print(reciprocal_rank_fusion([dense, sparse]))
# ['A', 'C', 'B', 'E', 'D']
#   A: 1/61 + 1/62 = 0.032522   ← rank 1 in dense, rank 2 in sparse → WINS
#   C: 1/63 + 1/61 = 0.032266   ← rank 3 in dense, rank 1 in sparse → close 2nd
#   B: 1/62 + 1/64 = 0.031754   ← decent in both → still beats...
#   E: 1/63        = 0.015873   ← ...a doc that only ONE list found
#   D: 1/64        = 0.015625

The insight in one line: agreement across retrievers beats a single strong opinion. A/C/B all appear in both lists and cluster at the top; E and D appear in only one and fall to the bottom — exactly the behavior you want from a fusion rule.

8. Strategy 5 — MMR (Maximal Marginal Relevance)

Intuitionfive near-identical chunksFormulaFrom scratchLangChainfetchk is the one people miss

Intuition. Plain top-k often returns five near-identical chunks (the same paragraph repeated across doc versions) — you burn the context window on redundancy and still miss the other half of the answer. MMR picks each next doc by trading off "is it relevant?" against "is it different from what I already picked?"

Formula (greedy — pick one at a time):

MMR = argmax [ λ · sim(dᵢ, q)  -  (1-λ) · max sim(dᵢ, dⱼ) ]
      dᵢ∈R\S                            dⱼ∈S
              └── relevance ──┘         └── redundancy ──┘

  λ = 1.0 → pure relevance (identical to plain similarity search)
  λ = 0.5 → balanced
  λ = 0.0 → pure diversity (relevance ignored)
  S = already-selected docs,  R = candidate pool

From scratch (verified output):

def mmr(query_vec, doc_vecs, k=3, lambda_mult=0.5):
    selected, candidates = [], list(range(len(doc_vecs)))
    while len(selected) < k and candidates:
        best_i, best_score = None, -1e9
        for i in candidates:
            relevance  = cosine(query_vec, doc_vecs[i])
            # redundancy = similarity to the MOST similar already-picked doc
            redundancy = max((cosine(doc_vecs[i], doc_vecs[j]) for j in selected), default=0.0)
            score = lambda_mult * relevance - (1 - lambda_mult) * redundancy
            if score > best_score:
                best_i, best_score = i, score
        selected.append(best_i)
        candidates.remove(best_i)
    return selected

qv = [1.0, 0.0]
dv = [[0.90, 0.10],   # d0 most relevant           cos(q,d0)=0.9939
      [0.90, 0.12],   # d1 NEAR-DUPLICATE of d0    cos(q,d1)=0.9912, cos(d1,d0)=0.9998
      [0.50, 0.50],   # d2 relevant, different     cos(q,d2)=0.7071, cos(d2,d0)=0.7809
      [0.20, 0.90]]   # d3 least relevant, most different  cos(q,d3)=0.2169, cos(d3,d0)=0.3234

print(mmr(qv, dv, k=3, lambda_mult=1.0))   # [0, 1, 2]  ← grabs the near-duplicate d1!
print(mmr(qv, dv, k=3, lambda_mult=0.3))   # [0, 3, 2]  ← skips d1, takes the diverse d3

The 2nd pick at λ=0.3, after d0 is selected — the redundancy penalty flips the winner:

d1: 0.3·0.9912 − 0.7·0.9998 = −0.4025   ← most relevant, but a near-dup → heavily penalized
d2: 0.3·0.7071 − 0.7·0.7809 = −0.3345
d3: 0.3·0.2169 − 0.7·0.3234 = −0.1613   ← WINS: least redundant

LangChain:

retriever = vectorstore.as_retriever(
    search_type="mmr",
    search_kwargs={
        "k": 4,             # how many to RETURN
        "fetch_k": 20,      # how many to FETCH first, then MMR-select k from these
        "lambda_mult": 0.5, # 1.0 = relevance only, 0.0 = diversity only
    },
)

fetch_k is the one people miss: MMR can only diversify within what it fetched. fetch_k=20, k=4 means "grab 20 by similarity, then pick the 4 best-but-different." If fetch_k == k, MMR does nothing. Rule of thumb: fetch_k ≈ 4-5× k.

9. Strategy 6 — Cross-Encoder Reranking

Intuitioncross-encoderFrom scratchLangChainAlways over-fetch before reranking

Intuition. Stage 1 gave you ~20 plausible candidates but its ordering is mediocre (the bi-encoder never let the query and doc interact). A cross-encoder reads [query SEP doc] together and scores true relevance. Slow — so only on the shortlist. This is usually the single biggest quality win in RAG for the least effort.

        [bi-encoder retrieval]              [cross-encoder rerank]
query ──▶ 10,000 docs → top 20   ──────▶   score each (q, dᵢ) pair → top 4 ──▶ LLM
          ~5ms, approximate                 20 × ~20ms = ~400ms, accurate

From scratch (the mechanism — a real cross-encoder is a fine-tuned transformer):

def rerank(query, docs, cross_encoder, top_n=4):
    # The defining move: query and doc go in TOGETHER as a PAIR.
    pairs  = [(query, d.page_content) for d in docs]
    scores = cross_encoder.predict(pairs)              # one forward pass per pair
    ranked = sorted(zip(docs, scores), key=lambda x: -x[1])
    return [d for d, _ in ranked[:top_n]]

LangChain:

from langchain.retrievers import ContextualCompressionRetriever
from langchain.retrievers.document_compressors import CrossEncoderReranker
from langchain_community.cross_encoders import HuggingFaceCrossEncoder

model = HuggingFaceCrossEncoder(model_name="BAAI/bge-reranker-base")
reranker = CrossEncoderReranker(model=model, top_n=4)      # keep best 4 after rescoring

# base retriever casts a WIDE net (k=20) → reranker narrows to the best 4
compression_retriever = ContextualCompressionRetriever(
    base_compressor=reranker,
    base_retriever=vectorstore.as_retriever(search_kwargs={"k": 20}),
)
compression_retriever.invoke("what is the refund window?")

# Hosted alternative (no local model):
# from langchain_cohere import CohereRerank
# reranker = CohereRerank(model="rerank-english-v3.0", top_n=4)

Always over-fetch before reranking. k=20 → top_n=4 is the point. Reranking k=4 → top_n=4 just reorders four docs and adds latency for nothing — the win comes from the reranker rescuing a great doc that the bi-encoder ranked #17.

11. Accuracy — How to Measure Any of This

Which metric to optimizeRecall@kThe main RAG metricHit@kPrecision@kMRR

You cannot tune weights, lambda_mult, k, or "is the reranker worth it?" by vibes. Measure two halves separately — they fail for different reasons:

RETRIEVAL accuracy→did we FETCH the right chunks?fix: hybrid/rerank/chunking
GENERATION accuracy→did the LLM USE them faithfully?fix: prompt/grounding/model

11a. Retrieval metrics — from scratch (verified output)

Build a small golden set: (query → ids of the chunks that truly answer it), then:

import math

def hit_at_k(retrieved, relevant, k):          # did we find ANY relevant doc in top-k?
    return 1.0 if set(retrieved[:k]) & set(relevant) else 0.0

def precision_at_k(retrieved, relevant, k):    # what fraction of top-k is relevant?
    return len(set(retrieved[:k]) & set(relevant)) / k

def recall_at_k(retrieved, relevant, k):       # what fraction of relevant docs did we get?
    return len(set(retrieved[:k]) & set(relevant)) / len(relevant) if relevant else 0.0

def mrr(retrieved, relevant):                  # 1/rank of the FIRST relevant doc
    for i, d in enumerate(retrieved):
        if d in relevant:
            return 1.0 / (i + 1)
    return 0.0

def ndcg_at_k(retrieved, relevant, k):         # rank-aware: rewards relevant docs placed HIGH
    dcg   = sum(1.0 / math.log2(i + 2) for i, d in enumerate(retrieved[:k]) if d in relevant)
    ideal = sum(1.0 / math.log2(i + 2) for i in range(min(len(relevant), k)))
    return dcg / ideal if ideal else 0.0

retrieved = ["d3", "d1", "d7", "d2", "d9"]     # what the retriever returned, in order
relevant  = ["d1", "d2"]                        # ground truth

# k=1: hit=0.00 prec=0.0000 rec=0.00 ndcg=0.0000   ← top-1 is wrong
# k=3: hit=1.00 prec=0.3333 rec=0.50 ndcg=0.3869   ← found d1
# k=5: hit=1.00 prec=0.4000 rec=1.00 ndcg=0.6509   ← found both
# MRR = 0.5   (first relevant doc d1 sits at rank 2 → 1/2)

Hit@k"Did we get at least one good chunk?"Simple pass/fail sanity check
Precision@k"How much of what I sent is junk?"Context-window efficiency / cost
MRR"How high is the first good chunk?"When one good chunk suffices
NDCG@k"Is the whole ordering good?"Judging rerankers (order is the point)

The practical loop: Recall@20 measures stage 1 (hybrid/BM25 weights, chunking). NDCG@4 / Precision@4 measures stage 2 (the reranker). If Recall@20 is low, no reranker can save you — the answer was never fetched. Fix recall first.

11b. Generation metrics — RAGAS

2. Router / Dispatcher

Core ideaUse whenDon't use when

Core idea: one LLM call classifies the request → a conditional edge sends it down one of N known paths. No loop, no tools. The cheapest "agentic" thing that works.

query ─▶ [classify] ─┬─▶ billing_handler ──▶ END
                     ├─▶ tech_handler    ──▶ END
                     └─▶ general_handler ──▶ END
from pydantic import BaseModel, Field

class Route(BaseModel):
    destination: Literal["billing", "tech", "general"] = Field(description="where to route")

def classify(state: State):
    # structured output = a guaranteed valid enum, not free text you must parse
    route = llm.with_structured_output(Route).invoke(state["messages"])
    return {"route": route.destination}

def billing(state: State): return {"messages": [llm.invoke("Billing expert: " + last(state))]}
def tech(state: State):    return {"messages": [llm.invoke("Tech expert: " + last(state))]}
def general(state: State): return {"messages": [llm.invoke(last(state))]}

g = StateGraph(State)
g.add_node("classify", classify)
for name, fn in [("billing", billing), ("tech", tech), ("general", general)]:
    g.add_node(name, fn)
    g.add_edge(name, END)
g.add_edge(START, "classify")
g.add_conditional_edges("classify", lambda s: s["route"],
                        {"billing": "billing", "tech": "tech", "general": "general"})
app = g.compile()

Use when: support triage, query classification, model tiering (cheap vs expensive). Don't use when: the request needs multiple steps or tools.

3. ReAct (tool-calling agent)

Core ideaReasonsActsThe critical guardUse whenDon't use when

Core idea: the workhorse. LLM Reasons about what to do, Acts by calling a tool, sees the result, repeats until it can answer. This is what most people mean by "an agent."

        ┌──────────────────────────────┐
        ▼                              │
 [agent] ──has tool_calls?──▶ [tools] ─┘
        │
        └──no──▶ END

The one-liner (use this in real life):

from langgraph.prebuilt import create_react_agent

agent = create_react_agent(llm, tools)
agent.invoke({"messages": [("user", "What is 25 * 4?")]})

From scratch (what the one-liner does — know this for interviews):

from langgraph.prebuilt import ToolNode, tools_condition

llm_with_tools = llm.bind_tools(tools)          # tell the model which tools exist

def agent(state: State):
    return {"messages": [llm_with_tools.invoke(state["messages"])]}

g = StateGraph(State)
g.add_node("agent", agent)
g.add_node("tools", ToolNode(tools))
g.add_edge(START, "agent")
# tools_condition: if the last message has tool_calls → "tools", else → END
g.add_conditional_edges("agent", tools_condition)
g.add_edge("tools", "agent")                     # ← the loop: tool result goes back to agent
app = g.compile()

The critical guard — a ReAct agent with no cap can loop forever:

app.invoke({"messages": [...]}, config={"recursion_limit": 15})   # ALWAYS set this

Use when: the steps depend on what tools return (most agent use-cases). Don't use when: you know the sequence (use a chain) or the task needs long-horizon planning (use Plan-and-Execute).

4. Reflection (self-critique)

Core ideacritique your own outputUse whenDon't use when

Core idea: generate → critique your own output → revise. Loop a fixed number of times. Quality goes up, cost goes up linearly.

[generate] ──▶ [critique] ──▶ good enough? ──no──▶ [generate] (with critique)
                                   │yes
                                   ▼
                                  END
class ReflectState(TypedDict):
    messages: Annotated[list, add_messages]
    draft: str
    critique: str
    iterations: int

def generate(state: ReflectState):
    prompt = f"Write an essay on: {state['messages'][0].content}"
    if state.get("critique"):                       # revise using the critique
        prompt += f"\n\nPrevious draft:\n{state['draft']}\n\nFix this critique:\n{state['critique']}"
    return {"draft": llm.invoke(prompt).content, "iterations": state.get("iterations", 0) + 1}

def critique(state: ReflectState):
    c = llm.invoke(f"Critique this essay harshly. If it's excellent, reply exactly 'APPROVED'.\n\n{state['draft']}")
    return {"critique": c.content}

def should_continue(state: ReflectState) -> Literal["generate", "end"]:
    if "APPROVED" in state["critique"]:  return "end"
    if state["iterations"] >= 3:         return "end"    # ← hard cap: cost control
    return "generate"

g = StateGraph(ReflectState)
g.add_node("generate", generate); g.add_node("critique", critique)
g.add_edge(START, "generate"); g.add_edge("generate", "critique")
g.add_conditional_edges("critique", should_continue, {"generate": "generate", "end": END})
app = g.compile()

Use when: writing, code generation, anything where a second look genuinely helps. Don't use when: latency-sensitive, or the task is simple (you're paying 3× for nothing).

5. Reflexion (reflection + episodic memory)

Core ideaforgetsepisodic memory

Core idea: Reflection forgets its lessons after each run. Reflexion writes the lesson into episodic memory that survives across trials/sessions — so it stops repeating the same mistake. "Reinforcement learning where the gradient is natural language."

[act] ──▶ [evaluate] ──fail──▶ [reflect: write a LESSON] ──▶ memory ──┐
   ▲                                                                  │
   └────────────── next trial reads the lessons ─────────────────────┘
class ReflexionState(TypedDict):
    task: str
    attempt: str
    memory: Annotated[list[str], add]     # ← episodic memory: lessons ACCUMULATE
    trial: int

def act(state: ReflexionState):
    lessons = "\n".join(f"- {m}" for m in state.get("memory", []))
    prompt = f"Task: {state['task']}"
    if lessons:
        prompt += f"\n\nLessons from your PAST failures — do not repeat them:\n{lessons}"
    return {"attempt": llm.invoke(prompt).content, "trial": state.get("trial", 0) + 1}

def evaluate(state: ReflexionState):
    v = llm.invoke(f"Task: {state['task']}\nAttempt: {state['attempt']}\nReply PASS or FAIL + why.")
    return {"verdict": v.content}

def reflect(state: ReflexionState):
    lesson = llm.invoke(
        f"Your attempt failed: {state['verdict']}\nWrite ONE concise lesson to remember next time."
    ).content
    return {"memory": [lesson]}            # add reducer APPENDS → memory grows across trials

def route(state) -> Literal["reflect", "end"]:
    if "PASS" in state["verdict"] or state["trial"] >= 3: return "end"
    return "reflect"

g = StateGraph(ReflexionState)
g.add_node("act", act); g.add_node("evaluate", evaluate); g.add_node("reflect", reflect)
g.add_edge(START, "act"); g.add_edge("act", "evaluate")
g.add_conditional_edges("evaluate", route, {"reflect": "reflect", "end": END})
g.add_edge("reflect", "act")               # retry the WHOLE task, now wiser
app = g.compile(checkpointer=checkpointer) # + a Store → lessons persist across SESSIONS

Reflection vs Reflexion in one line: Reflection critiques this draft; Reflexion remembers the lesson for the next task. See the memory-types section in 02_LangGraph_Notes.md §7.

6. Plan-and-Execute

Core ideawhole plan up frontre-planUse whenDon't use when

Core idea: make the whole plan up front, execute steps one by one, then re-plan with what you learned. ReAct decides one step at a time (myopic); this keeps a long-horizon goal.

[planner] ──▶ [execute step 1] ──▶ [replan] ──▶ [execute step 2] ──▶ ... ──▶ END
             (plan = [s1, s2, s3])   (revise remaining steps)
class PlanState(TypedDict):
    task: str
    plan: list[str]
    done: Annotated[list[str], add]        # completed step → result
    answer: str

class Plan(BaseModel):
    steps: list[str] = Field(description="ordered steps to complete the task")

def planner(state: PlanState):
    p = llm.with_structured_output(Plan).invoke(f"Make a step-by-step plan for: {state['task']}")
    return {"plan": p.steps}

def execute(state: PlanState):
    step = state["plan"][0]                             # take the next step
    worker = create_react_agent(llm, tools)             # a ReAct agent executes it
    result = worker.invoke({"messages": [("user", step)]})
    return {"done": [f"{step} → {result['messages'][-1].content}"],
            "plan": state["plan"][1:]}                  # pop the completed step

def replan(state: PlanState):
    # Re-plan with what we learned — steps may be added, removed, or reordered.
    p = llm.with_structured_output(Plan).invoke(
        f"Task: {state['task']}\nCompleted:\n{state['done']}\nRemaining: {state['plan']}\n"
        f"Return the REVISED remaining steps (empty list if done)."
    )
    return {"plan": p.steps}

def route(state) -> Literal["execute", "end"]:
    return "end" if not state["plan"] else "execute"

g = StateGraph(PlanState)
g.add_node("planner", planner); g.add_node("execute", execute); g.add_node("replan", replan)
g.add_edge(START, "planner"); g.add_edge("planner", "execute"); g.add_edge("execute", "replan")
g.add_conditional_edges("replan", route, {"execute": "execute", "end": END})
app = g.compile()

Use when: research reports, multi-stage jobs, anything where step 7 depends on a coherent goal. Don't use when: 1-3 steps (planning overhead isn't worth it).

7. Supervisor (multi-agent)

Core ideasupervisorUse whenDon't use when

Core idea: one supervisor LLM routes work to specialist agents; each returns to the supervisor, which decides the next move or finishes. The most common and most controllable multi-agent shape.

              ┌──────▶ [researcher] ──┐
[supervisor] ─┼──────▶ [coder]      ──┼──▶ back to supervisor ──▶ ... ──▶ END
              └──────▶ [writer]     ──┘
from langgraph.prebuilt import create_react_agent

# 1) specialists — each is just a ReAct agent with its own tools
researcher = create_react_agent(llm, [search])
coder      = create_react_agent(llm, [calculator])

class SupState(TypedDict):
    messages: Annotated[list, add_messages]
    next: str

class Router(BaseModel):
    next: Literal["researcher", "coder", "FINISH"]

# 2) the supervisor picks the next worker (or finishes)
def supervisor(state: SupState):
    decision = llm.with_structured_output(Router).invoke(
        [("system", "Route to the right worker. Reply FINISH when the task is complete.")]
        + state["messages"])
    return {"next": decision.next}

# 3) workers report back with a labelled message
def make_worker(agent, name):
    def node(state: SupState):
        out = agent.invoke({"messages": state["messages"]})
        return {"messages": [("assistant", f"[{name}] {out['messages'][-1].content}")]}
    return node

g = StateGraph(SupState)
g.add_node("supervisor", supervisor)
g.add_node("researcher", make_worker(researcher, "researcher"))
g.add_node("coder", make_worker(coder, "coder"))
g.add_edge(START, "supervisor")
g.add_edge("researcher", "supervisor")      # ← workers ALWAYS return to the supervisor
g.add_edge("coder", "supervisor")
g.add_conditional_edges("supervisor", lambda s: s["next"],
                        {"researcher": "researcher", "coder": "coder", "FINISH": END})
app = g.compile()

Use when: distinct specialties (research vs code vs write), and you want one place in control. Don't use when: one agent with 3 tools would do (don't build a committee for a simple job).

8. Swarm (peer handoff)

Core ideahand off directly to each otherUse whenDon't use whenCap handoffs

Core idea: no boss — agents hand off directly to each other when they hit something outside their specialty. Handoff = a tool that returns Command(goto=...).

[flight_agent] ◀──── handoff ────▶ [hotel_agent]
       └──────── handoff ────────▶ [car_agent]
from langgraph.types import Command

def make_handoff(target: str):
    @tool
    def handoff() -> Command:
        f"""Transfer control to the {target} agent."""
        # Command is the secret: a tool that CHANGES THE GRAPH'S NEXT NODE.
        return Command(goto=target, graph=Command.PARENT)
    handoff.name = f"transfer_to_{target}"
    return handoff

flight_agent = create_react_agent(llm, [search, make_handoff("hotel_agent")], name="flight_agent")
hotel_agent  = create_react_agent(llm, [search, make_handoff("flight_agent")], name="hotel_agent")

g = StateGraph(State)
g.add_node("flight_agent", flight_agent)
g.add_node("hotel_agent", hotel_agent)
g.add_edge(START, "flight_agent")
app = g.compile()

Use when: peer specialists with natural handoffs (travel booking, tiered support). Don't use when: you need auditability/control — swarms can ping-pong forever. Cap handoffs or use a Supervisor as the single arbiter.

10. Agentic RAG (self-correcting retrieval)

Core ideagradesrewrites the query and retriesCRAG/Self-RAG

Core idea: plain RAG retrieves once and hopes. Agentic RAG grades what it retrieved, and if it's bad, rewrites the query and retries — or gives up honestly.

[retrieve] ──▶ [grade docs] ──relevant──▶ [generate] ──▶ END
                     │
                  irrelevant
                     ▼
              [rewrite query] ──▶ back to retrieve  (max N times)
class RagState(TypedDict):
    question: str
    documents: list
    generation: str
    attempts: int

class Grade(BaseModel):
    relevant: bool = Field(description="do the docs answer the question?")

def retrieve(state: RagState):
    return {"documents": retriever.invoke(state["question"]),
            "attempts": state.get("attempts", 0) + 1}

def grade(state: RagState):
    ctx = "\n".join(d.page_content for d in state["documents"])
    g = llm.with_structured_output(Grade).invoke(
        f"Question: {state['question']}\nDocs: {ctx}\nDo these docs answer it?")
    return {"relevant": g.relevant}

def rewrite(state: RagState):
    q = llm.invoke(f"Rewrite this question to retrieve better results: {state['question']}")
    return {"question": q.content}

def generate(state: RagState):
    ctx = "\n".join(d.page_content for d in state["documents"])
    return {"generation": llm.invoke(f"Answer using ONLY:\n{ctx}\n\nQ: {state['question']}").content}

def route(state) -> Literal["generate", "rewrite", "give_up"]:
    if state["relevant"]:        return "generate"
    if state["attempts"] >= 3:   return "give_up"     # ← don't loop forever
    return "rewrite"

def give_up(state: RagState):
    return {"generation": "I don't have enough information to answer that."}

g = StateGraph(RagState)
for n, f in [("retrieve", retrieve), ("grade", grade), ("rewrite", rewrite),
             ("generate", generate), ("give_up", give_up)]:
    g.add_node(n, f)
g.add_edge(START, "retrieve"); g.add_edge("retrieve", "grade")
g.add_conditional_edges("grade", route,
    {"generate": "generate", "rewrite": "rewrite", "give_up": "give_up"})
g.add_edge("rewrite", "retrieve")
g.add_edge("generate", END); g.add_edge("give_up", END)
app = g.compile()

One-sentence ideasilently dropsoriginal

One-sentence idea: Text-only RAG silently drops the most information-dense parts of real documents — the revenue table, the architecture diagram, the chart — so multimodal RAG's whole job is to make those retrievable (via a text or image representation) while making sure the LLM ultimately sees the original, not a lossy summary of it.

Why text-only RAG fails on real documents:

A 10-K financial report:            What naive text extraction gets:
  ┌────────────────────────┐
  │ prose  prose  prose    │  ✓ extracted fine
  │ ┌────────────────────┐ │
  │ │ REVENUE TABLE      │ │  ✗ rows mangled into "2023 4.2 5.1 2024 6.3..."
  │ │ (the actual answer)│ │     — numbers divorced from their headers
  │ └────────────────────┘ │
  │ [Chart: margin trend]  │  ✗ dropped entirely (it's pixels)
  │ prose  prose           │  ✓ fine
  └────────────────────────┘

The user asks "what was the 2024 revenue?" — the answer lives in the table your pipeline mangled or the chart it dropped. Every multimodal RAG design is an answer to one question: what do you embed, and what do you hand the LLM?

Option A — Shared-Space Embeddings (CLIP)

IntuitiontogetherLangChain implementationWhere A breaks

Intuition. CLIP trained an image encoder and a text encoder together on 400M (image, caption) pairs with a contrastive objective: matching pairs pulled close, mismatched pairs pushed apart. Result: one vector space where embed_text("a dashboard screenshot") lands near actual dashboard screenshots — so text→image search is just cosine, no captions needed.

      "revenue chart" ──[text encoder]──▶ ●───┐
                                              │ close in the SAME space
      chart.png ───────[image encoder]──▶ ●───┘
      cat.jpg ─────────[image encoder]──▶           ● (far away)

LangChain implementation:

from langchain_experimental.open_clip import OpenCLIPEmbeddings
from langchain_community.vectorstores import Chroma

clip = OpenCLIPEmbeddings(model_name="ViT-g-14", checkpoint="laion2b_s34b_b88k")

vectorstore = Chroma(collection_name="mm", embedding_function=clip,
                     persist_directory="./mm_chroma")

# Index IMAGES directly (no captions needed) + text chunks into the SAME store
vectorstore.add_images(uris=["report_p3_chart.png", "arch_diagram.png"])
vectorstore.add_texts(texts=[c.page_content for c in text_chunks])

# One text query searches BOTH modalities — cosine in the shared space
docs = vectorstore.similarity_search("margin trend chart", k=4)
# → returns the chart image (base64 in page_content) ranked against text chunks

Where A breaks: CLIP sees an image globally — it knows "this is a chart" but reads dense in-image text and table cells poorly. For a corpus of tables-as-images, retrieval quality collapses. That's exactly the gap B and C fill.

Option B — Summarize-then-Embed with MultiVectorRetriever (the production workhorse)

Intuitiondescription of itoriginalFull implementationWhy this wins for documentsSame trick, other uses

Intuition. Don't embed the image — embed a description of it. At index time a VLM writes "Bar chart of quarterly revenue 2022-2024; Q4-2024 peaks at $6.3M…" and that text goes in the vectorstore. The original image/table goes in a plain docstore under the same doc_id. Query time: search hits the summary (plain text retrieval), but what comes back — and what the LLM sees — is the original.

The rule that makes B work: retrieve by the proxy, generate from the original. The summary only has to be good enough to be found; the VLM re-reads the real pixels/HTML at answer time, so summary lossiness doesn't cap answer quality.

INDEX (once)                                          QUERY (per request)

                       ├ tables (HTML) ─▶ LLM summary ─▶ ┌─────────────┐      "2024 revenue?"
                       └ images (b64) ──▶ VLM summary ─▶ │ vectorstore │◀────── embed & search
                                                          │ (summaries) │
                              originals ────────────────▶ │  docstore   │─▶ doc_id hit → ORIGINAL
                              keyed by doc_id             │ (originals) │       │
                                                          └─────────────┘       ▼
                                                              text + b64 images → VLM → answer

Full implementation:

import uuid, base64
from unstructured.partition.pdf import partition_pdf
from langchain.retrievers.multi_vector import MultiVectorRetriever
from langchain.storage import InMemoryStore          # prod: Redis/SQL doc store
from langchain_community.vectorstores import Chroma
from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langchain_core.documents import Document
from langchain_core.messages import HumanMessage

# ── 1) EXTRACT: split the PDF into typed elements ─────────────────────────
elements = partition_pdf(
    "10k_report.pdf",
    infer_table_structure=True,            # tables come back as HTML (structure kept!)
    strategy="hi_res",
    extract_image_block_types=["Image"],   # figures extracted as base64
    extract_image_block_to_payload=True,
)
texts  = [e for e in elements if e.category not in ("Table", "Image")]
tables = [e.metadata.text_as_html for e in elements if e.category == "Table"]
images = [e.metadata.image_base64  for e in elements if e.category == "Image"]

# ── 2) SUMMARIZE the non-text modalities (one-time indexing cost) ─────────
vlm = ChatOpenAI(model="gpt-4o")

def summarize_table(html):
    return vlm.invoke(f"Summarize this table for retrieval. Include what it measures, "
                      f"units, date ranges, and the key figures:\n{html}").content

def summarize_image(b64):
    return vlm.invoke([HumanMessage(content=[
        {"type": "text", "text": "Describe this figure for retrieval: what it shows, "
                                 "axis labels, trends, and any numbers visible."},
        {"type": "image_url", "image_url": {"url": f"data:image/jpeg;base64,{b64}"}},
    ])]).content

table_summaries = [summarize_table(t) for t in tables]
image_summaries = [summarize_image(i) for i in images]

# ── 3) THE MULTI-VECTOR SPLIT: summaries → vectorstore, originals → docstore ──
vectorstore = Chroma(collection_name="mm_rag", embedding_function=OpenAIEmbeddings())
docstore = InMemoryStore()
retriever = MultiVectorRetriever(vectorstore=vectorstore, docstore=docstore,
                                 id_key="doc_id")

def index(originals, proxies, kind):
    ids = [str(uuid.uuid4()) for _ in originals]
    retriever.vectorstore.add_documents([
        Document(page_content=proxy, metadata={"doc_id": i, "type": kind})
        for proxy, i in zip(proxies, ids)])                 # searched
    retriever.docstore.mset(list(zip(ids, originals)))      # returned

index([t.text for t in texts], [t.text for t in texts], "text")   # text: proxy = itself
index(tables, table_summaries, "table")                            # search summary → get HTML
index(images, image_summaries, "image")                            # search summary → get b64

# ── 4) QUERY: search summaries, receive ORIGINALS ─────────────────────────
originals = retriever.invoke("What was 2024 revenue?")
# → the raw table HTML and/or the raw chart base64 — NOT the summaries

# ── 5) GENERATE: hand text AND images to the VLM in one multimodal prompt ──
def build_prompt(question, originals):
    content = [{"type": "text",
                "text": f"Answer from this context only.\nQuestion: {question}\n\nContext:\n"}]
    for o in originals:
        if isinstance(o, str) and not o.startswith("/9j/"):      # text or table HTML
            content.append({"type": "text", "text": o})
        else:                                                     # base64 image → real pixels
            content.append({"type": "image_url",
                            "image_url": {"url": f"data:image/jpeg;base64,{o}"}})
    return [HumanMessage(content=content)]

answer = vlm.invoke(build_prompt("What was 2024 revenue?", originals)).content

Why this wins for documents: retrieval is plain text-over-summaries, so your entire existing stack — hybrid + RRF, cross-encoder rerank, score-threshold guards (17/16) — applies with zero changes. The multimodality is confined to indexing (summaries) and generation (originals in the prompt).

Same trick, other uses: MultiVectorRetriever also powers hypothetical questions (embed LLM-generated questions each chunk answers, return the chunk) and parent-document retrieval (embed small precise chunks, return the bigger parent) — one mechanism: search a proxy, return the payload.

Option C — ColPali (page-as-image, late interaction)

Intuitionpatch vectorstoken vectorsMaxSimMaxSim from scratchUsing it

Intuition. Skip extraction entirely. Screenshot each page; a vision-language model turns the page into ~1,000 patch vectors (one per visual region — a table cell block, a chart axis, a paragraph). The query becomes a handful of token vectors. Score = MaxSim: each query token finds its best patch, and those maxima are summed — so a page must cover every aspect of the query to win.

MaxSim from scratch (verified — run in this repo):

def dot(a, b): return sum(x*y for x, y in zip(a, b))

def maxsim(query_vecs, page_vecs):
    """For EACH query token: best-matching patch. Sum the maxima."""
    return sum(max(dot(q, p) for p in page_vecs) for q in query_vecs)

# query "revenue chart" → two token vectors
q_revenue, q_chart = [1.0, 0.0], [0.0, 1.0]

page_A = [[0.9, 0.1], [0.1, 0.95], [0.2, 0.2]]    # revenue-ish patch AND chart-ish patch
page_B = [[0.95, 0.05], [0.85, 0.1], [0.1, 0.1]]  # all revenue, NO chart patch

print(maxsim([q_revenue, q_chart], page_A))   # 1.850  (0.90 revenue + 0.95 chart)
print(maxsim([q_revenue, q_chart], page_B))   # 1.050  (0.95 revenue + only 0.10 chart)
# page_A wins: it covers BOTH aspects of the query. A single pooled vector
# would likely rank B first (more "revenue" overall) — THAT's what late interaction fixes.

Using it: the colpali-engine / byaldi libraries index PDFs page-by-page; retrieval returns page images you feed straight to a VLM:

# pip install byaldi
from byaldi import RAGMultiModalModel

rag = RAGMultiModalModel.from_pretrained("vidore/colpali-v1.2")
rag.index(input_path="10k_report.pdf", index_name="10k", store_collection_with_index=True)
results = rag.search("What was 2024 revenue?", k=3)   # → page images, MaxSim-ranked
# hand results[0].base64 to GPT-4o/Claude exactly like Option B step 5

Trade-offs: no OCR/parsing/chunking (huge win on scanned & layout-heavy docs); but retrieval is page-level (coarser), the index is heavy (~1k vectors/page), and you need a vector DB with multi-vector/late-interaction support (or brute-force scoring) rather than plain cosine top-k.

Evaluation — per modality, or you're blind

A single aggregate score hides exactly the failure you built all this to fix. Tag every golden-set query with the modality its answer lives in, then compute retrieval metrics (17 §11 — Recall@k, MRR, NDCG) per tag:

golden = [
    {"q": "what was 2024 revenue?",        "relevant": ["tbl_12"], "modality": "table"},
    {"q": "describe the margin trend",     "relevant": ["img_3"],  "modality": "image"},
    {"q": "who audited the statements?",   "relevant": ["txt_88"], "modality": "text"},
]

from collections import defaultdict
recalls = defaultdict(list)
for g in golden:
    got = [d.metadata["doc_id"] for d in retriever.vectorstore.similarity_search(g["q"], k=5)]
    recalls[g["modality"]].append(len(set(got) & set(g["relevant"])) / len(g["relevant"]))

for m, r in recalls.items():
    print(f"Recall@5 [{m}]: {sum(r)/len(r):.2f}")
# Typical failure signature: text 0.90, table 0.55, image 0.40
#   → your TABLE/IMAGE SUMMARIES are the weak link (improve the summary prompt:
#     force units, date ranges, key figures INTO the summary), not the retriever.

Also eval generation per modality (RAGAS faithfulness on table-answer questions specifically) — VLMs misread dense tables from pixels more often than from HTML, which is an argument for keeping infer_table_structure=True (HTML originals) rather than treating tables as images.

Q: How would you build RAG over 10-K reports full of tables and charts? Summarize-then-embed with MultiVectorRetriever: partition_pdf splits elements by type (tables kept as HTML); a VLM writes a retrieval-oriented summary of each table/chart; summaries are embedded in the vectorstore while originals sit in a docstore under the same doc_id. Search hits the summary; the LLM receives the original HTML/image in a multimodal prompt. Retrieval stays plain text, so hybrid search + reranking + thresholds all still apply. Rule: retrieve by the proxy, generate from the original.

Q: Why not just embed the chart images with CLIP? CLIP's shared space is great for "find images like this" but reads dense in-image text and table cells poorly — a corpus of tables-as-images collapses retrieval quality. CLIP is the right tool for visual-similarity search, not document QA.

Q: What is ColPali and when is it worth it? Treat each page as an image; a VLM emits ~1k patch vectors per page; queries score pages by MaxSim (each query token takes its best patch; sum the maxima), so a page must cover every query aspect. No OCR, no chunking — layout, tables, and figures handled natively. Worth it for scanned/layout-heavy corpora; costs page-level granularity and a heavy multi-vector index.

Q: Your multimodal RAG answers text questions well but fumbles table questions. Diagnose. Per-modality eval first: if table Recall@k lags, the table summaries are under-specified — force what-it-measures/units/dates/key-figures into the summary prompt. If retrieval is fine but answers are wrong, check what the LLM receives: if tables arrive as pixels, switch to HTML originals (VLMs misread dense tables from images); and confirm you're passing originals, not summaries.
