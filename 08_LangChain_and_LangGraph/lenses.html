Production Lenses — RAG, Agentic RAG and Agent Systems

Every topic below is examined through the same five lenses: Scaling, Productionization, Optimization, Latency and Metrics. That structure is the point — an interview answer that covers all five reads as someone who has run the thing, not read about it.

Pattern deep-dives and the question banks live in RAG Production Technical QA, Agentic RAG Technical Interview QA and Agentic AI Technical Interview QA.

Classic RAG

Retrieval-Augmented Generation: give the model the facts at query time instead of baking them into weights. Everything else on this site is a modification of this pipeline — so this is the one you must be able to draw from memory.

One-liner: two pipelines sharing a vector store — an offline one that indexes documents, and an online one that retrieves, reranks, assembles and generates. RAG fixes missing knowledge; fine-tuning fixes wrong behaviour. Confusing those two is the most common interview filter.

Number What it is
~867ms typical uncached end-to-end
~87% of that is generation
5–15ms on a semantic-cache hit
Recall@k the metric to fix first
•

Scaling — capacity vs throughput are different levers

Ingestionidempotent by content hashIndexshard for capacityreplicate for QPS/availabilityThe RAM cliff

  • Ingestion — batch + parallel workers, idempotent by content hash so a re-run is free, dead-letter queue for corrupt files. Never re-embed what hasn't changed.

  • Index — shard for capacity (corpus outgrows RAM), replicate for QPS/availability. These are not the same lever and interviewers listen for that distinction.

  • The RAM cliff — an HNSW index that spills out of RAM goes from ~50ms to ~5s. Do the memory math up front: vectors × dim × 4 bytes × ~1.1 graph overhead; use PQ/quantized vectors when it won't fit.

  • Retrieval — metadata pre-filtering shrinks the candidate set before ANN search; dense and sparse run in parallel (cost is the max, not the sum).

  • Serving — stateless API pods behind autoscaling; the vector DB and the LLM are the stateful dependencies, so they get their own scaling story and their own circuit breakers.

•

Productionization — what separates a demo from a system

Index versioning + alias cutoverNo-context guardabstainCitations on every claimObservability per hopGolden set + canary

  • Pin the embedding model as metadata on the index. Vectors from two models are not comparable — this single field prevents the worst silent failure in RAG.

  • Index versioning + alias cutover so a rebuild is atomic and reversible.

  • Access control via metadata filters, applied at query time, never post-hoc filtering of results.

  • No-context guard — if the best score is under threshold, abstain rather than generate. Ungrounded confidence is worse than "I don't know".

  • Citations on every claim, with a post-generation check that cited chunks were actually retrieved.

  • Observability per hop — log query, retrieved IDs + scores, reranked set, final prompt tokens, answer, latency per stage. You cannot debug retrieval you didn't log.

  • Golden set + canary on every prompt, model, chunking or embedding change.

•

Optimization — cheapest and broadest first

Hybrid search (BM25 + vector)Rerank to fewer, better chunksSemantic cachePrefix / KV cacheRight-size the chunkQuantize the reranker

  • Hybrid search (BM25 + vector) — the highest-value single addition in most enterprise corpora, because exact terms (error codes, part numbers, names) are exactly what dense retrieval misses.

  • Rerank to fewer, better chunks — going 20→4 usually improves faithfulness and cuts cost and cuts latency. The rare change with no trade-off.

  • Semantic cache on the query — a hit skips the entire pipeline.

  • Prefix / KV cache — keep the stable prompt prefix first so it caches; never put a timestamp above it.

  • Right-size the chunk — or decouple it entirely with small-to-big: search small chunks, return their parent.

  • Quantize the reranker or distil it — cross-encoders are the second-biggest cost after generation.

•

The diagnostic that matters: high context precision/recall + low faithfulness points at generation. Low context recall points at retrieval. Reporting one blended score hides which half is broken.

Agentic RAG

Classic RAG retrieves once and hopes. Agentic RAG wraps that pipeline in a loop that can decide whether to retrieve, where from, and whether what came back is good enough — and retry if not.

One-liner: the pipeline stops being a straight line and becomes a control loop. Every extra hop costs money and latency, so the whole discipline is proving the loop earned its cost.

Number What it is
~2,025ms 3-hop loop, end to end
~2.3× vs vanilla RAG
3 hops the hard cap you must set
Routing acc. the metric vanilla RAG doesn't have
•

Scaling — the loop is the thing that scales badly

Distil the graderCache tool resultsQueue long runs

  • Parallelize decomposition, never iteration. Independent sub-questions (known up front) fan out and collapse N hops toward one hop's wall-clock. Iterative retrieval — where query n+1 depends on result n — cannot be parallelized, ever. Knowing which you have is the design decision.

  • Distil the grader. A ~300ms frontier-model grading call per hop is the agentic tax. A small distilled model or even a similarity threshold does the same job for a fraction of the cost.

  • Cache tool results keyed on (tool, args) — distinct from a query-keyed semantic cache, and reusable across entirely different runs.

  • Stateless workers + externalized checkpointer so any pod can resume any run.

  • Queue long runs (async, webhook/poll) rather than holding an HTTP connection open for 10 seconds.

•

Productionization — a loop in production needs brakes

A hard hop capPer-request budgetLoop detectionGraceful degradationTrace every decisionHuman-in-the-loop

  • A hard hop cap. Not a suggestion in the prompt — a counter in code with a guaranteed exit branch. Runaway loops are the #1 agentic failure mode and they are a cost incident as much as a latency one.

  • Per-request budget in tokens and wall-clock; abort and degrade to vanilla RAG when exceeded.

  • Loop detection — if the rewritten query is semantically the same as the last one, you are not making progress; break.

  • Graceful degradation — when the loop fails or the budget blows, fall back to a single-pass answer with lower confidence, not an error.

  • Trace every decision, not just every call: which source was routed to, what the grade was, why it retried. A trace without decisions is unusable for debugging an agent.

  • Human-in-the-loop for high-stakes actions, wired as an interrupt rather than a prompt instruction.

•

Optimization — the cheapest hop is the one you don't take

Route first, and route cheaplySkip retrieval entirelySmall models for router and graderCap and cache

  • Route first, and route cheaply — a small fast model deciding "does this even need retrieval?" pays for itself immediately. If routing itself becomes multi-step you've made deciding as expensive as doing.

  • Skip retrieval entirely when the query doesn't need it. Correctly skipping is a win worth reporting.

  • Small models for router and grader, frontier model only for final synthesis.

  • Cap and cache before you optimise anything else — most agentic cost blowups are loops, not slow calls.

•

The question every review asks: "you added a loop — prove it was worth it." Bring both deltas in one table.

Self-RAG

The generator grades itself, inline. Reflection isn't a separate node in your graph — it's part of the model's own output, emitted as reflection tokens while it works.

One-liner: same problem as Corrective RAG, solved inside the model. The generator emits its own judgments — should I retrieve? is this passage relevant? is my draft supported? is this answer useful? — instead of a wrapper asking on its behalf.

Number What it is
4 reflection tokens
1 model — trained, not wrapped
0 extra model calls
Overconfidence the failure mode to watch
•

Scaling — cheapest reflective pattern to scale

No second model to scaleCap the regenerate loop

  • No second model to scale — reflection rides along with generation, so throughput is bounded by your existing LLM capacity, not by a separate grader fleet.

  • The Retrieve? token is a scaling lever in disguise — every query it correctly answers "no" to skips the retrieval pipeline entirely, taking load off the vector DB.

  • Cap the regenerate loop. IsSup? failing repeatedly must terminate — two attempts then abstain, never unbounded.

  • Output tokens grow because reflection is emitted — budget for it, and strip reflection tokens before showing the user.

•

Productionization — you are trusting the model to mark its own homework

Log every reflection judgmentParse defensivelyStrip reflection tokensany

  • Never ship self-assessment as your only quality gate in a high-stakes flow. Pair it with an independent check — a citation verifier, an NLI entailment check, or a sampled external judge.

  • Log every reflection judgment alongside the answer. These are the ground truth for measuring whether self-grading is calibrated at all.

  • Parse defensively — reflection tokens are model output, so they can be malformed or absent. Treat a missing judgment as "unsupported", not as a pass.

  • Strip reflection tokens from user-facing output, but keep them in the trace.

  • Re-validate after any model change — self-grading behaviour is a property of the specific model version and does not survive migration.

•

Optimization — spend the savings on verification

skip retrievalswitch to CRAG

  • Use the Retrieve? judgment to skip retrieval, then spend part of the saved budget on an independent groundedness check — net cost is roughly flat, and reliability goes up.

  • Keep reflection terse — a one-token judgment, not a paragraph of reasoning, unless you need the rationale for audit.

  • Prefix-cache the reflection instructions with the rest of the system prompt.

  • If self-grading measures poorly calibrated on your traffic, switch to CRAG rather than tuning the prompt indefinitely. That is the honest optimisation.

•

Self-RAG is the lowest-latency way to add reflection, because the judgment travels inside a call you were already making.

Corrective RAG (CRAG)

Grade what you retrieved, then act on the grade. A separate grading step sits between retrieval and generation and routes to one of three outcomes — generate, correct, or escape.

One-liner: a wrapper you can bolt onto any existing RAG pipeline. The generator is unchanged; the grader is the new moving part — and its calibration quietly becomes a dependency of the whole system.

Number What it is
3 knowledge actions
1 small evaluator — LLM untouched
Any pipeline it can wrap
Calibration the metric that decides everything
•

Scaling — the grader is the thing that multiplies

Distil the graderTry a threshold firstBatch gradingCap the correction loop hardfallback source

  • Distil the grader. This is the single biggest lever. Relevance grading is a narrow classification task — a small distilled model or a fine-tuned classifier matches a frontier model at a fraction of the cost and latency, and you can retrain it independently.

  • Try a threshold first. Sometimes a plain reranker score cutoff grades well enough, at zero LLM cost. Measure before assuming you need a model.

  • Batch grading across retrieved documents in one call rather than one call per document.

  • Cap the correction loop hard — one or two rewrites, then escape to fallback or abstain. Uncapped rewrite loops are the classic CRAG cost incident.

  • Rate-limit and circuit-break the fallback source (web search) separately — it's an external dependency with its own failure modes and its own bill.

•

Productionization — a grader is a model in production, with all that implies

Alert on grade distribution shiftindexGuard the web-search fallbackLog the grade with every trace

  • Version and monitor the grader like a model, because it is one: pinned version, eval set, drift monitoring, rollback path.

  • Alert on grade distribution shift. A sudden jump in "irrelevant" almost always means the index broke — a failed reindex, a bad embedding migration — not that the world changed. This is one of the best early-warning signals you can have.

  • Make abstention a first-class outcome with its own UX. "I couldn't find this in our documentation" is a good answer; a confident guess is not.

  • Guard the web-search fallback — it pulls untrusted content into your context, so treat results as data, never instructions, and apply prompt-injection defences.

  • Log the grade with every trace so you can reconstruct why a given answer took the path it did.

•

Optimization — grade cheaply, correct rarely

only on the reranked top-kCache gradesTune the thresholds asymmetrically

  • Fix retrieval before adding correction. Hybrid search + reranking removes many of the cases CRAG exists to catch, and costs less per query than a grading call.

  • Run grading only on the reranked top-k, not the raw candidate set.

  • Cache grades keyed on (query, doc-id) — repeated queries re-grade the same documents constantly.

  • Tune the thresholds asymmetrically: the cost of a false "relevant" (hallucinated answer) usually far exceeds a false "irrelevant" (one extra retrieval). Set the boundary where the business cost is symmetric, not where accuracy peaks.

•

Latency — you pay the grader on every query, corrections only on some

+~300ms~300ms → ~40–80msThe honest framing
Path Added latency Share of traffic
Grade → relevant → generate +~300ms (grading only) The majority, if retrieval is healthy
Grade → partial → rewrite + re-retrieve + re-grade +~650ms per correction cycle Should be a minority — watch this rate
Grade → irrelevant → web fallback +500–2,000ms (external call) Small — and cap it

The honest framing: CRAG trades a fixed latency tax on every query for a large reduction in confidently-wrong answers on some. Whether that's worth it is an eval question, not a taste question.

Agent Systems

Nine patterns, one decision. Everything here follows from a single question: does the next step depend on the result of the last one?

One-liner: an agent is an LLM in a loop with tools and a termination condition. The patterns differ only in who decides the next step — and every one of them fails by looping.

Number What it is
9 patterns worth knowing
#1 failure is runaway loops
Supervisor sequential, sum of hops
Orchestrator parallel, slowest branch
•

Scaling — call count is the thing that explodes

Do the call-count math out loudcapabilityParallel tool callsAsync queuesTool-result cachingCode-enforced execution paths

  • Do the call-count math out loud. Three agents × five steps = 15 LLM calls versus a single agent's ~6. Multi-agent is a capability decision, not a performance one — it usually costs more, not less.

  • Parallel tool calls within one step: a worked example goes 1,800ms → 1,050ms (~42%) from orchestration alone, with zero model changes.

  • Stateless workers + externalized checkpointer — any pod resumes any run; this is what makes horizontal scaling possible at all.

  • Async queues (Kafka/SQS/Redis Streams) for long-running jobs; return a run ID, not a held connection.

  • Tool-result caching keyed on (tool, args) — reusable across entirely different runs.

  • Code-enforced execution paths — a deterministic state machine where the LLM only fills decision nodes. Cheaper, faster, and far more testable than letting the model drive the whole graph.

•

Productionization — brakes, budgets, and blast radius

Least privilege per toolSaga/compensationDistributed tracingDead-letter + human escalation

  • Recursion limit + explicit step cap + a guaranteed exit branch the router can always reach. Every pattern needs all three.

  • Least privilege per tool. The agent gets the narrowest credential that works — and destructive tools sit behind human approval, wired as an interrupt, not a prompt instruction.

  • Idempotency keys on every side-effecting tool so a retry doesn't double-charge a customer.

  • Saga/compensation for multi-step side effects that can half-apply.

  • Treat tool output as untrusted data, never as instructions — this is the prompt-injection boundary.

  • Distributed tracing: a span per model call, tool call and routing decision, with a propagated run ID. Debugging an agent without this is guesswork.

  • Dead-letter + human escalation for runs that exhaust their budget.

•

Optimization — the best optimization is a smaller graph

Fewer, better-scoped toolsModel routingPrompt/prefix cachingSub-agents for context isolationReplace LLM decisions with code

  • Fewer, better-scoped tools. Tool-selection accuracy degrades measurably as tool count grows and as descriptions overlap. Non-overlapping trigger conditions, or merge into one parametric tool.

  • Model routing — small model for routing/grading/extraction, frontier model only where reasoning genuinely matters.

  • Prompt/prefix caching on the stable system + tool-definition prefix (audit it — 20 rich tool schemas can be 5k tokens on every call).

  • Sub-agents for context isolation — keep a context-heavy subtask's 40 documents out of the parent's window; the parent sees only the 300-token finding.

  • Replace LLM decisions with code wherever the decision is actually deterministic.

Self-RAG vs Corrective RAG — definitions and the difference

A single language model, trained to retrieve on demand and to critique its own work by emitting special reflection tokens inline with its output. Those tokens decide whether retrieval happens at all, judge each retrieved passage, judge whether the draft is actually supported by it, and score how useful the answer is — and at inference they are used to rank candidate answers and pick the best one.

In one line: the critic is the generator. Self-correction is a property of the model, learned during training.

A lightweight retrieval evaluator bolted in front of an unchanged generator. It scores the confidence of what retrieval returned and triggers one of three knowledge actions before generation: refine the retrieved text, discard it and go to web search, or combine both. The correction happens in the retrieval layer.

In one line: the critic is a separate, small model sitting outside the generator. Self-correction is a property of your pipeline.

Both fix the same failure — generating confidently from evidence that was never any good. They differ in who does the checking, and everything else follows from that one choice.

Self-RAG Corrective RAG
Who critiques The generator itself A separate retrieval evaluator
What is trained The LM itself — fine-tuned to emit reflection tokens Only the evaluator — a small classifier; the LM is untouched
Where correction happens Generation layer — re-draft or re-retrieve Retrieval layer — refine, replace, or supplement the evidence
When it acts During generation, continuously Once, between retrieval and generation
Granularity Per segment — each passage drafts a candidate, scored and ranked Per retrieval set — one confidence verdict drives one action
Retrieval is… Adaptive — the Retrieve token can skip it entirely Always performed, then judged after the fact
Bolt onto an existing system? No — needs a model trained (or reliably prompted) for reflection Yes — genuinely plug-and-play around any RAG pipeline
Extra model call None — the judgments ride inside the generation call Yes, but cheap — and it can be a threshold instead
Independently tunable / auditable No — changing grading means changing the model or its prompt Yes — retrain or re-threshold the evaluator alone
External fallback Not part of the method Built in — web search on low confidence
Main failure mode Overconfidence — models grade their own output generously Miscalibration — a wrong evaluator misdirects every query, confidently
Latency cost Extra output tokens only; can be net negative when it skips retrieval A fixed evaluator tax on every query, plus web latency on the bad ones

Say it like this: "Both are self-correcting RAG, but the correction sits in different places. Self-RAG pushes it into the model — one LM trained to emit reflection tokens, so it can skip retrieval when it isn't needed and rank its own candidate answers; it's cheaper at inference but you're trusting the model to mark its own homework. CRAG keeps the generator untouched and puts a small evaluator in front of it that grades the retrieved evidence and either refines it, replaces it with web results, or combines both. CRAG is the one you can actually bolt onto an existing pipeline and audit independently, so it's usually what I'd reach for in production; Self-RAG is the more elegant idea and the cheaper one per query if you control the model."

They compose. Nothing stops you running a CRAG-style evaluator on retrieval and asking the generator for a groundedness judgment on its draft. In practice that pairing — an external check on the evidence, an internal check on the answer — catches more than either alone.
