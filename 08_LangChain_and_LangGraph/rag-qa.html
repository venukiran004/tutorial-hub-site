1. Explain your end-to-end RAG architecture

Say it like this

"I think about it as two pipelines that share a vector store. Offline, an indexing pipeline ingests documents, chunks them, embeds each chunk, and writes them into a vector index along with metadata. Online, a query pipeline takes a user question, embeds it (or runs hybrid search), retrieves the top candidates, reranks them, assembles a token-budgeted context, and sends it to the LLM with the question. The LLM generates a grounded answer, I gate it with a citation check, and it goes back to the user. Underneath both pipelines sits observability — every hop is logged — and a caching layer that can short-circuit the query pipeline entirely on a repeat question."

OFFLINEingest→parse→chunk→embed→indexbuild the library
ONLINEquery→[embed / hybrid]→retrieve→rerank→assemble→generate→deliver

Draw this diagram first, then let the interviewer pick which box to go deeper on — that's what the rest of this file is for. Full layer-by-layer failure + scaling treatment: Scaling Optimization RAG.

2. Why RAG instead of fine-tuning?

Saybehavior or stylefactsandknowledgebehavior/style/format
Say it like this

"They solve different problems. Fine-tuning changes the model's weights to teach it a behavior or style — a tone, a task format, a domain vocabulary. RAG changes what facts the model has access to, at query time, without touching the weights at all. If my problem is 'the model doesn't know our internal docs, and those docs change weekly,' fine-tuning is the wrong tool — I'd have to retrain every time something changes, I can't cite a source, and I can't restrict what one user sees. RAG solves all three: it's updatable by just re-indexing, it's inherently citable because I know which chunk produced the answer, and it's access-controllable via metadata filtering. I'd reach for fine-tuning when the problem is how the model behaves — a consistent output format, a narrower domain style, lower latency by shrinking the model — and I'd combine both when I need a model that behaves a certain way and knows current facts."

RAG Fine-tuning
Fixes Missing/changing knowledge Wrong behavior/style/format
Update cost Re-index (cheap, fast) Re-train (expensive, slow)
Citability Yes — traces to a chunk No — baked into weights
Access control Yes — metadata filter per query No — one model, one knowledge set
Hallucination risk Lower (grounded in retrieved text) Can still hallucinate confidently
When it's the right call Facts change often; need sources Need consistent format/tone/domain jargon

The trap answer to avoid: "RAG is cheaper so always use RAG." The honest answer is they're orthogonal — most production systems that need both facts and behavior control use RAG and a lightly fine-tuned or well-prompted model together.

3. Explain the stages in a production RAG pipeline

Saysilently
Say it like this

"Nine stages, split offline/online. Offline: ingest the raw document, chunk it into retrievable units, embed each chunk, and write it to the index. Online: understand the query — maybe rewrite it — retrieve candidates, rerank them for precision, assemble them into a token-budgeted prompt, generate the answer, and run it through delivery checks like citation gating before it ships. The thing I'd emphasize in an interview is that most of these stages fail silently — nothing throws an exception, the pipeline just produces a worse answer — so every stage needs its own detection signal, not just a try/except around the whole thing." 

A. Ingest & parse      → per-doc parse status, DLQ for failures
B. Chunk                → structure-aware split + overlap
C. Embed                → batched, model+version stamped in metadata
D. Index                → HNSW/IVF, sharded/replicated
E. Query understanding  → rewrite/decompose if needed
F. Retrieve             → hybrid (dense+sparse), relevance threshold
G. Rerank                → cross-encoder, bounded candidate count
H. Assemble context      → token budget, dedupe, recency
I. Generate + deliver    → groundedness check, citation gating

Full per-stage "what breaks / detect / fix / speed up / scale" treatment: Scaling Optimization RAG; step-by-step recovery code (retry/circuit-breaker/DLQ): RAG and Agent Stepwise Failure Handling.

4. How would you ingest 500K documents?

SayConcretelyQueue-based fan-outBatch the embedding callsCheckpoint progressRate-limit / backoff
Say it like this

"500K documents is squarely a batch-parallel problem, not a real-time one, so I'd design for throughput, not latency. I'd fan the work out across a queue-backed worker pool — each worker pulls a document, parses it, chunks it, and pushes the chunks to an embedding stage — so parsing scales horizontally since documents are independent of each other. I'd batch the embedding step heavily rather than embedding one chunk at a time; that alone is usually a 10x+ throughput difference on the same hardware. I'd make every write idempotent, keyed on doc-id plus a content hash, so if a worker crashes and the job retries, nothing double-writes. And I would not try to do this as one giant synchronous job — I'd checkpoint progress so a failure at document 400,000 doesn't mean restarting from zero."

Concretely: 1. Queue-based fan-out (e.g. SQS/Kafka + a worker pool) — parsing/chunking is embarrassingly parallel across documents. 2. Batch the embedding calls — group chunks into batches (e.g. 100–256 at a time) per forward pass instead of one-by-one. 3. Checkpoint progress per batch so a crash resumes instead of restarting. 4. Rate-limit / backoff against the embedding API so a burst doesn't trip provider rate limits. 5. Dead-letter queue for anything that fails parsing after retries — never silently dropped. 6. Validate a sample of resulting chunks before considering the run "done" — this class of bug is silent.

Worked number: embedding 10M chunks batched on one GPU is roughly 90 minutes; unbatched, one-at-a-time, it's closer to 14 hours on the same hardware — batching is the single biggest lever, bigger than adding machines.

5. How do you make ingestion idempotent?

Sayupsert
Say it like this

"Idempotent means running the same ingestion job twice produces the same end state, not duplicated data — which matters because retries after a crash are inevitable at scale. My approach is to key every write on a stable identifier — document id plus a content hash of the document — and use an upsert, not an insert, so re-processing an unchanged document overwrites the same record rather than creating a duplicate. If the content hash hasn't changed, I skip re-embedding entirely, which is also my incremental-reindexing mechanism for free. Deletes are handled the same way — I don't just remove a row, I write a tombstone, so a retried delete is still a no-op the second time, not an error." 

def upsert_chunk(chunk):
    key = f"{chunk.doc_id}:{chunk.chunk_index}"
    content_hash = sha256(chunk.text)
    existing = index.get(key)
    if existing and existing.content_hash == content_hash:
        return  # unchanged — skip re-embedding, idempotent no-op
    vector = embed(chunk.text)
    index.upsert(key, vector, metadata={"content_hash": content_hash, **chunk.metadata})

6. How do you handle corrupted files?

Say it like this

"I never let one bad file take down a batch job — the parser runs in a try/except per document, and anything that fails isn't just logged and forgotten, it goes to a dead-letter queue with the actual error attached, so it's inspectable and replayable once I fix the root cause. Before that, I try a fallback chain: a primary parser, then OCR if the primary fails on something like a scanned PDF, then plain-text extraction as a last resort — each rung is worse quality but never zero. And I run a sanity check on whatever text comes out — is it long enough, is the printable-character ratio reasonable — because a parser can 'succeed' and still hand you garbage, and that failure is completely silent unless I check for it explicitly." 

def ingest(doc):
    for parser in [parse_primary, parse_with_ocr, parse_plaintext]:
        try:
            text = parser(doc)
            if len(text) > MIN_LEN and printable_ratio(text) > 0.8:
                return upsert(doc.id, text)
        except Exception as e:
            last_err = e
    dead_letter_queue.put(doc, error=str(last_err))  # never silently dropped

7. How do you chunk PDFs with tables, images, and diagrams?

Sayown atomic chunkTablesImages/diagramsMixed layout (columns)Everything
Say it like this

"Plain text-splitting destroys tables and ignores images entirely, so I treat PDFs as multi-modal documents, not flat text. For tables, I use a layout-aware parser — something that detects table structure — and I keep each table as its own atomic chunk, often serialized to markdown or a row-per-line format so the LLM can actually read the structure, rather than letting a fixed-size splitter cut it mid-row. For images and diagrams, I have two options depending on the budget: either run them through a vision-capable model to generate a text description or caption at ingestion time and index that caption as a searchable chunk linked back to the image, or store the image separately and do multimodal retrieval directly with something like a vision-language embedding model. Either way, the key design decision is: never let a table or diagram get silently dropped or shredded by a naive text splitter — detect it, handle it as its own unit, and link it back to its page/section for citation."

Element Approach
Tables Layout-aware extraction (e.g. table-detection parser) → serialize to markdown/rows → keep atomic, never split mid-table
Images/diagrams Caption via a vision model at ingestion → index the caption text; or embed the image itself with a multimodal embedder for direct image retrieval
Mixed layout (columns) Structure-aware parser (reading order, not raw character stream) to avoid interleaving unrelated columns
Everything Attach page/section metadata to every chunk so a citation can point back to the exact source location

8. Why do we use chunk overlap?

SaytwoBetter fix than overlap alone
Say it like this

"Because a fixed chunk boundary doesn't know where an idea actually ends — it can cut a sentence, a table row, or the one sentence that connects a question to its answer, right in half, so that neither resulting chunk alone contains the full answer. A 10 to 20 percent overlap means the content near a boundary appears in two chunks, so if the split lands badly, the complete thought still exists intact in at least one of them. The tradeoff is index size and some redundancy — more overlap means more stored chunks and a bit more noise in retrieval — so I don't maximize it, I tune it against retrieval eval: if Recall@k for boundary-spanning questions is fine, I don't need more overlap than that."

Better fix than overlap alone: structure-aware chunking (split on headings/paragraphs instead of raw character counts) reduces how often a bad boundary happens in the first place — overlap is the safety net for the boundaries you can't avoid, not a replacement for splitting on natural units.

9. How do you choose an embedding model?

SayChecklistDimensionalityDomain fitLatency/cost per callSymmetric vs asymmetric
Say it like this

"I weigh four things: retrieval quality on my data, not a generic leaderboard; dimensionality, because that directly drives vector-store RAM and cost at scale; latency and cost per embedding call; and domain fit — a general-purpose model can miss vocabulary that's specific to my corpus, like legal or medical terms. My process is to shortlist two or three candidates, run them through the same chunking and the same labeled eval set, and compare Recall@k and MRR — not trust a public benchmark, because MTEB-style leaderboards don't reflect my specific documents or query patterns. I also weigh the practical cost: a smaller, faster embedder that's 2 points worse on my eval but embeds 5x faster and cheaper is often the right trade, especially since I can usually recover more quality per dollar by investing that savings into a reranker instead."

Checklist: 1. Benchmark on your own labeled eval set (query → relevant doc pairs), not a public leaderboard alone. 2. Dimensionality — higher isn't free; it's RAM at index time, multiplied by corpus size. 3. Domain fit — does it handle your jargon (legal, medical, internal codenames)? A domain-tuned or fine-tuned embedder can beat a bigger general one. 4. Latency/cost per call, especially for the query-time embedding, which is on the critical path. 5. Symmetric vs asymmetric — is it tuned for query-to-passage retrieval (asymmetric) or just similarity (symmetric)? Most production retrieval wants an asymmetric-trained model. 6. Right-size, don't max out — spend the budget you save on a reranker; it usually buys back more quality per dollar than the biggest embedder available.

10. How do you migrate embedding models without downtime?

Sayblue-green re-embed
Say it like this

"The one thing I will never do is swap the embedding model in place — mixing vectors from two different models in one index makes similarity scores meaningless, and it's a completely silent failure, nothing errors, search just quietly gets worse. So a migration is always a blue-green re-embed: I build a brand-new index with the new model, re-embedding the entire corpus into it, while the old index keeps serving live traffic unchanged. Once the new index is fully built, I validate it — run my retrieval eval set against it and confirm it's at least as good as the old one — and only then do I cut query traffic over, either instantly or via a gradual percentage rollout. The old index stays around for a rollback window in case the new model underperforms in ways my eval didn't catch. And critically, I stamp the embedding model name and version into each index's metadata and assert query-model equals index-model on every request, so even a config mistake can't silently point queries at the wrong index."

  1. Build new index (new model) alongside the live one — corpus re-embedded end to end
  2. Validate: run the eval set against the new index, compare Recall@k/MRR to the baseline
  3. Canary: route a small % of live traffic to the new index, compare live metrics
  4. Cut over fully once validated; keep the old index warm for a rollback window
  5. Never serve from an index whose stamped model doesn't match the query embedder (fail closed)

11. What is metadata filtering?

Saybefore or duringinto
Say it like this

"Metadata filtering is narrowing the search space by structured attributes — tenant id, date range, document type, access level — before or during the vector search, not after it. The critical detail is where the filter happens: if I filter after retrieval, a post-filter can leave me with fewer than my requested top-k results, because the filter throws away some of what the ANN search already returned, and worse, it can silently drop the single most relevant result. So the correct approach is pushing the filter into the ANN search itself, so the index only considers eligible candidates in the first place. The two biggest production use cases are multi-tenancy — user A must never retrieve user B's private documents — and recency — always search only documents from the last 90 days, say. It's a correctness and security control as much as a relevance one." 

results = vector_db.search(
    query_vector,
    top_k=10,
    filter={"tenant_id": current_user.tenant_id, "doc_type": {"$in": ["policy", "faq"]}},
)  # filter applied INSIDE the ANN search, not after

Full strategies (pre-filter vs post-filter vs hybrid metadata indexes): RAG and Vector Stores §16.3.

12. Semantic Search vs BM25

Saymeaninghybrid
Say it like this

"They fail in opposite ways, which is the whole reason to know both cold. Semantic search embeds text into vectors and finds nearest neighbors by meaning — it's great at paraphrase, synonyms, conceptual questions, but it can blur exact-match terms like an error code, a SKU, or an ID number, because those don't have rich 'meaning' to embed. BM25 is classic term-frequency keyword search — it nails exact terms and rare vocabulary, but it has zero understanding of synonyms or paraphrase; if the user's words don't literally appear in the document, BM25 won't find it. In production I don't pick one — I run both and fuse the results, because their failure modes barely overlap, so together they cover far more query types than either alone."

Semantic / Vector BM25 / Keyword
Matches on Meaning (embedding similarity) Exact term frequency
Strong at Paraphrase, synonyms, conceptual queries Exact IDs, codes, rare/specific terms
Weak at Exact-match terms it never learned as "meaningful" Synonyms, paraphrase, conceptual similarity
Needs An embedding model + vector index An inverted index (cheap, classic IR)
Production default Neither alone — hybrid (next question)

13. What is Hybrid Search?

Sayconcurrentlymax
Say it like this

"Hybrid search runs dense vector search and sparse BM25 search concurrently against the same query, then fuses the two ranked lists into one — usually with Reciprocal Rank Fusion. The reason it's my production default rather than a special case is that it directly patches each method's blind spot: BM25 catches the exact SKU or error code that the embedding blurred, and vector search catches the paraphrased question that BM25's literal matching misses. Running them concurrently, not sequentially, also means the added latency is the max of the two paths, not the sum — so I'm not paying a real latency tax for meaningfully better recall." 

dense_results  = vector_index.search(embed(query), k=50)
sparse_results = bm25_index.search(query, k=50)     # run concurrently, not after
fused = reciprocal_rank_fusion(dense_results, sparse_results)  # see Q14

14. What is Reciprocal Rank Fusion (RRF)?

Sayrank positionboth
Say it like this

"RRF is how I merge two differently-scored ranked lists — vector similarity scores and BM25 scores aren't on the same scale, so I can't just add them together. RRF sidesteps that by ignoring the raw scores entirely and using only rank position: each document gets a score of 1 over k plus its rank, in each list it appears in, and those scores are summed across lists. The constant k, usually around 60, dampens the effect of a very high rank so one list's number-one pick doesn't completely dominate. A document that ranks reasonably well in both lists ends up scoring higher than one that's rank-one in only one list — which is exactly the property I want, because it rewards results both retrieval methods agree are relevant." 

RRF_score(doc) = Σ  1 / (k + rank_i(doc))     over each ranked list i the doc appears in, k ≈ 60
def reciprocal_rank_fusion(*ranked_lists, k=60):
    scores = {}
    for ranked_list in ranked_lists:
        for rank, doc_id in enumerate(ranked_list, start=1):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return sorted(scores.items(), key=lambda x: -x[1])

Why not just average the raw scores? Cosine similarity (0–1, dense) and BM25 scores (unbounded, sparse) live on incomparable scales — averaging them directly is apples-to-oranges. RRF only needs rank order, which is always comparable.

15. Bi-Encoder vs Cross-Encoder

Sayseparatelyandtogether
Say it like this

"A bi-encoder embeds the query and each document separately, into the same vector space, and compares them with a cheap similarity like cosine — that separateness is exactly what lets me pre-compute every document's embedding once, offline, so query time is just one embed plus a fast nearest-neighbor lookup. A cross-encoder instead feeds the query and a candidate document together into one transformer pass and outputs a single relevance score directly — because it sees both texts jointly with full cross-attention, it's meaningfully more accurate at judging true relevance. The cost is that nothing about a cross-encoder can be pre-computed — every query-document pair needs its own forward pass at query time, so it doesn't scale to searching a whole corpus. That's exactly why they're used in sequence: bi-encoder for cheap, corpus-wide retrieval, cross-encoder for expensive, precise reranking of a short candidate list."

Bi-Encoder Cross-Encoder
Encodes Query and document separately Query and document together
Pre-computable Yes — every doc embedded once, offline No — needs the query at inference time
Speed at scale Fast — nearest-neighbor search over millions Slow — one forward pass per pair
Accuracy Good Better (full cross-attention between query and doc)
Used for Initial retrieval (top-k from millions) Reranking a short candidate list

16. Why not use Cross-Encoder for the entire corpus?

Sayevery single query-document pairthat
Say it like this

"Because it doesn't scale — a cross-encoder has to run a full forward pass for every single query-document pair, since nothing can be pre-computed ahead of time the way a bi-encoder's document embeddings can. Scoring one query against a million documents means a million forward passes at query time, which is both far too slow and far too expensive for an online request. So the two-stage design exists specifically to dodge this: a cheap bi-encoder narrows a million documents down to a short list — say fifty — using pre-computed embeddings and fast nearest-neighbor search, and only that short list ever touches the cross-encoder. I get the cross-encoder's better accuracy where it matters, at a cost that scales with the reranking candidate count, not the corpus size."

The number that makes this concrete: cross-encoder cost scales with candidates × query length, not corpus size — bounding candidates to ~50 (not 500) is the cheapest lever in the whole reranking layer, precisely because that's the term the cost actually scales with.

17. How do you debug poor retrieval?

Sayvocabulary gapA concrete triage orderRegress against a labeled eval set
Say it like this

"I branch by symptom, because 'retrieval is bad' has several distinct root causes that need different fixes. First I check whether it's an infrastructure problem — is the store actually erroring or timing out — versus a relevance problem, where it returns results but they're just not good. If it's relevance, I look at the similarity scores: uniformly low scores across the board usually means a vocabulary gap between how the user phrased the question and how the documents are written, which points me at query rewriting or hybrid search rather than assuming the index itself is broken. If scores look reasonable but the right document just isn't in the top-k, I check whether it's a chunking problem — is the answer split across a chunk boundary — by literally reading the chunks around where the right answer should be. And I always keep a small labeled eval set of (query → correct document) pairs on hand, because 'it feels wrong' is not a debugging signal — Recall@k on a fixed set is."

A concrete triage order: 1. Is the store even returning results? — infra/error, not relevance (check logs, latency, error rate). 2. Are similarity scores uniformly low? — vocabulary gap → try query rewriting, or hybrid search if not already on. 3. Are scores fine but the right chunk missing from top-k? — read the actual chunks; check if the answer got split across a boundary (chunking bug) or if top-k is too small for what the reranker needs. 4. Is retrieval fine but the final answer still wrong? — that's not a retrieval bug, that's Q18 (generation not grounding on the context). 5. Regress against a labeled eval set — Recall@k / MRR before and after any fix, so you know the change actually helped.

Full per-cause decision flow: Scaling Optimization RAG — Layer D.

18. How do you reduce hallucinations?

Sayonlyafter
Say it like this

"I attack it at three points, not one. First, retrieval: if nothing relevant was actually found, I don't even let the model try to answer — I abstain and say so, because handing a doomed context to the generator is asking it to fill the gap with parametric memory. Second, the prompt: I instruct the model explicitly to answer only from the provided context and to say it doesn't know if the answer isn't there — this alone measurably cuts ungrounded answers. Third, and most important for production, I verify after generation with a groundedness check — either an NLI model or an LLM-judge asking 'is every claim in this answer actually supported by the retrieved context' — and if it fails, I do one guided retry, and if that still fails, I degrade to quoting the raw retrieved snippets rather than let a fluent, confident, wrong answer ship."

  1. Retrieval gate: no relevant context found → abstain, don't even call the generator
  2. Prompt gate: "answer ONLY from the context; say 'I don't know' if it's not there"
  3. Post-gen check: groundedness/faithfulness check (NLI or LLM-judge) on the output
  4. Recovery: ungrounded → one guided retry → still ungrounded → quote snippets or abstain
  5. Delivery gate: citation-support check — does the cited chunk actually support the sentence?

Deep dive on hallucination types and why RAG still hallucinates: LLM Hallucination and Faithfulness.

19. How do you evaluate a RAG system (RAGAS)?

SayContext PrecisionContext RecallFaithfulnessAnswer RelevancyDiagnostic move
Say it like this

"RAGAS splits evaluation into retrieval-side and generation-side metrics, and I care about both because a system can fail at either half independently. On the retrieval side: Context Precision — of what I retrieved, how much was actually relevant — and Context Recall — of what's relevant in the corpus, how much did I actually retrieve. On the generation side: Faithfulness — is the answer actually grounded in the retrieved context, not the model's own memory — and Answer Relevancy — does the answer actually address the question asked. The reason I want all four rather than one end-to-end score is diagnosis: if faithfulness is low but context precision is high, that's a generation problem — the model had good context and still ignored it. If context recall is low, no amount of prompt tuning fixes it — that's a retrieval or chunking problem. I run these as an LLM-judge harness against a curated eval set, and I track them over time, not just once, so a regression after a prompt or model change shows up immediately."

Metric Question it answers Points to a bug in
Context Precision Of what was retrieved, how much is relevant? Retrieval/reranking (too much noise)
Context Recall Of what's relevant, how much was retrieved? Retrieval/chunking (missing the answer entirely)
Faithfulness Is the answer grounded in the retrieved context? Generation (ignoring context, hallucinating)
Answer Relevancy Does the answer address the actual question? Generation (answering a different question)

Diagnostic move: high context precision/recall + low faithfulness = generation bug, not retrieval. Low context recall = no prompt fix will save it, go fix chunking/retrieval. Full metric formulas + TruLens RAG Triad comparison: Client Round RAG and Agents §4.

20. How do you scale a production RAG system?

SayBy layerRetrieval/rerankVector indexShardReplicate
Say it like this

"I scale each layer independently, because they have different bottlenecks — treating RAG as one monolith to scale wastes effort on the wrong thing. Retrieval and reranking are stateless and read-heavy, so I just add replicas behind a load balancer. The vector index is memory-bound — the real scaling question there is whether it fits in RAM, and if not I shard for capacity, replicate for read throughput, or compress with product quantization before I'd throw more nodes at it blindly. Generation is compute-bound and usually dominates cost, so that's where continuous batching and more model replicas matter most. And underneath everything, I put a caching hierarchy in front — prefix cache, then exact, then semantic, then embedding, then retrieval — because for any traffic with repetition, a cache hit is the cheapest possible way to 'scale': you just don't do the work again."

By layer: 1. Retrieval/rerank — stateless, horizontal replicas behind a load balancer. 2. Vector index — the layer most often mis-scaled, and where sharding vs. replication get mixed up: - Shard to scale capacity (index size) across nodes — split by hash, range, or tenant/namespace once one node's index no longer fits in RAM. - Replicate to scale read QPS and availability, not capacity — read replicas behind a load balancer; a different axis from sharding, and the exact distinction interviewers probe. - PQ/quantization compresses vectors ~4–32x smaller in RAM at a small recall cost — the lever when RAM, not QPS, is the actual constraint (worked number: 50M × 768-dim float32 vectors ≈ 150GB uncompressed → ~19GB at 8x PQ, a typically 1–3 point recall cost). - Push metadata filters into the ANN search itself, not a post-filter step — post-filtering can silently return fewer than top-k after the filter drops results. - Blue-green reindex — build the new index alongside the live one, cut over only once it's warm and validated; never rebuild in place. 3. Generation — continuous batching, more replicas, model cascading for simple vs. hard queries. 4. Caching hierarchy — cheapest tier checked first (prefix → exact → semantic → embedding → retrieval) — the biggest win for repeated traffic. 5. Load balancing — route generation traffic by queue depth, not round-robin; backpressure (a controlled reject) over unbounded queueing when a layer saturates. 6. Autoscale on queue depth/p99, not CPU% — LLM-serving saturates memory/compute in ways CPU% doesn't reflect. 7. Scale each layer independently — the vector index is memory-bound, generation is compute-bound; they don't share one bottleneck or one autoscaling policy.

Full layer-by-layer scaling levers with worked numbers: Scaling Optimization RAG.

21. How do you reduce latency?

SayperceivedLatency leversTrace per-hop firstPrefix/prompt cachingContinuous batching
Say it like this

"I trace per-hop first, because guessing which layer is slow wastes time — in a typical uncached RAG request, generation is roughly 85-90 percent of total latency, so that's usually where I look first, but I confirm it with a trace rather than assume. The single biggest win at the generation layer is prefix caching, since every RAG prompt shares a large static system-prompt prefix across every query — caching its KV once is close to free money. After that: continuous batching for bursty traffic, quantization for raw throughput, and streaming, which doesn't reduce total latency but cuts perceived latency to first token, which is often what users actually judge. Upstream of generation, I run dense and sparse retrieval concurrently so their latency is the max of the two, not the sum, and I put a semantic cache in front of the whole pipeline so a repeated question skips everything and returns in single-digit milliseconds."

Latency levers: - Trace per-hop first — never guess which layer is slow; in a typical uncached request generation is ~85–90% of total latency, but confirm it, don't assume it. - Prefix/prompt caching — cache the KV of the static system-prompt prefix shared across every query; the single biggest win at the generation layer. - Continuous batching — smooths bursty traffic at the generation layer. - Quantization — raw throughput at the generation layer. - Streaming — doesn't cut total latency, but cuts perceived latency to first token, which is what users actually judge. - Parallel dense + sparse retrieval — latency becomes the max of the two, not the sum. - Bound reranker candidates (~50, not 500) — cross-encoder cost/latency scales with candidates × query length, not corpus size. - Semantic cache in front of the whole pipeline — a repeated question skips everything, single-digit-ms response.

Worked latency budget (cold cache): embed ~10ms → hybrid retrieve (parallel) ~25ms → rerank top-50 ~80ms → assemble ~1ms → LLM prefill ~150ms → LLM decode ~600ms ≈ ~867ms total, generation alone ~87%. Prefix caching drops prefill to ~40-60ms; a semantic-cache hit collapses the whole thing to ~5-15ms. Full breakdown: Scaling Optimization RAG.

Cost levers (mostly the same knobs, different metric): - Generation tokens dominate cost — trim/dedupe context and cap output length before anything else. - Model cascading — cheap model for simple queries, frontier model only for genuinely hard ones. - Caching hierarchy — every cache hit is a query that costs nothing; check cheapest-first. - Bound reranker candidates — the cheapest lever in the reranking layer, since cost scales with candidates × query length, not corpus size. - Batch embedding at ingest time — query-time embedding is the only one on the cost-critical path; batch document embedding offline. - Track cost per query as a distribution — catches drift before it shows up as a bill surprise.

24. Conversation State vs Persistent Memory

Saycurrent sessionacross
Say it like this

"Conversation state is short-lived — it's the back-and-forth of the current session: the message history, what the user just asked, what was just retrieved. It typically lives in something fast like Redis or in-process, keyed by session id, and it's fine for it to disappear when the session ends. Persistent memory is different in kind, not just duration — it's durable facts the system should recall across sessions: user preferences, prior decisions, long-term context about this specific user or account. That needs to live in a real database or its own vector store, indexed and retrievable independently of any one conversation. The failure I watch for is conflating the two: if you store long-term facts inside the same object as the trimmable, summarizable conversation trajectory, a routine context-window compaction can silently delete something you actually needed to remember permanently."

25. How do you update or delete documents in a Vector DB?

Sayworsetombstone
Say it like this

"Updates and deletes both need to be first-class parts of the ingestion pipeline, not an afterthought, because a stale or wrongly-still-present document is often a worse failure than a missing one — think a deleted contract still being retrievable. For an update, I don't try to patch a vector in place — I re-chunk and re-embed the changed document, and upsert with the same doc-id key, using a content hash so unchanged documents are skipped, not re-processed. For a delete, I propagate it from the source system as an explicit tombstone — a deletion event that removes the chunks from the index — and I run a periodic audit that diffs the source system against the index to catch anything that fell through, because if delete propagation ever breaks silently, that's a compliance problem, not just a staleness one."

Delete:  source doc removed → tombstone event → remove/mark-deleted its chunks in the index
Audit:   periodic diff of source system vs. index — catches any update/delete that silently failed to propagate

27. How do you perform regression testing after prompt/model changes?

Saybeforebetter or worse
Say it like this

"I keep a curated, version-controlled eval set — real and synthetic (query, expected-behavior) pairs, including known edge cases and past incidents — and I run it against every prompt or model change before it ships, the same way you'd run a unit-test suite before merging code. I compare RAGAS-style metrics — faithfulness, context precision/recall, answer relevancy — plus task-specific checks, against the previous baseline, not just an absolute pass/fail threshold, because what I actually care about is whether the change made things better or worse, not whether it's perfect. I also keep a small set of known-hard or previously-broken cases pinned in that set specifically so a regression that was already fixed once doesn't silently come back. And critically, this has to run automatically in CI on every change to the prompt or the model — not manually, and not only when someone remembers."

  1. Version-controlled eval set: labeled (query → expected answer/behavior) pairs + known past-incident cases
  2. Run RAGAS metrics (faithfulness, context precision/recall, answer relevancy) against the new version
  3. Compare to the last-known-good baseline, not an absolute threshold alone
  4. Gate the deploy on regression, not just "did it pass" — a drop from 0.92 to 0.85 faithfulness should block
  5. Automate in CI — triggered by any prompt, model, or retrieval-config change, not run manually

28. How would you debug production failures after deployment?

Say it like this

"First move is always the same: pull the full trace for a failing request — the query, any rewrites, what was retrieved and its scores, the assembled prompt, and the final answer — because most RAG failures are silent, nothing throws an exception, so I can't debug from an error log alone, I need to see every hop. From there I localize which stage actually broke: did retrieval return nothing relevant, did it return good context that generation ignored, or is this an infra fault like a timeout. I check whether it's isolated to one query pattern or systemic — a systemic issue right after a deploy points hard at whatever just changed, which is why I always check the deploy diff and the eval-set regression results (Q27) first if the timing lines up. And I check the boring, silent-failure suspects by habit: did the embedding model/index version actually match, did context get silently truncated, is the index stale. Only after localizing do I fix — and I always re-run the eval set after the fix to confirm it's actually resolved, not just no-longer-reproducing on my one test query."

  1. Pull the full per-hop trace for the failing request — query, rewrites, retrieved ids+scores, prompt, answer
  2. Localize the stage: infra fault (error/timeout) vs. retrieval miss vs. generation ignoring good context
  3. Check "did anything just change": recent deploy diff, config change, index rebuild, model version bump
  4. Check the silent-failure usual suspects: embed-model/index version mismatch, context truncation, stale index
  5. Isolated to one query pattern, or systemic? Systemic + recent deploy = strong correlation, check there first
  6. Fix, then re-run the eval set (Q27) — confirm the regression is actually gone, not just this one query

29. How do you handle failures for DB, Embedding Model, Chat Model?

Sayvector DBembedding modelchat/generation modelBM25 fallbackversion mismatch is NOT transient
Say it like this

"Each dependency gets its own retry-then-fallback pattern, because they fail differently and recover differently. If the vector DB is down or slow, I put a circuit breaker in front of it — after a few consecutive failures, stop hammering it and fall back to BM25 keyword search on separate infrastructure, labeled internally as a degraded response, rather than erroring the whole request. If the embedding model API is down, that's usually transient — retry with exponential backoff — but if the query-time embedder and the index's embedder ever disagree on model version, that's not a transient fault, that's a config bug, and I fail closed rather than serve a meaningless ranking. If the chat/generation model is down or rate-limited, I retry with backoff, then fall back to a secondary model or provider, and if even that's unavailable, I degrade to a cached or canned response rather than a bare error — always retry only transient faults, since retrying a persistent one, like a malformed request, just burns time before I reach the actual fix."

Dependency Transient fault Recovery
Vector DB Timeout, brief unavailability Retry once → circuit breaker → BM25 fallback (different infra), labeled degraded
Embedding model API timeout/429 Retry with backoff + batch splitting; version mismatch is NOT transient → fail closed, don't serve a meaningless ranking
Chat/generation model API timeout/429, rate limit Retry with backoff → fallback to a secondary model/provider → cached/canned degraded answer as last resort 
class CircuitBreaker:
    def __init__(self, threshold=3, cooldown=30):
        self.fails, self.threshold, self.cooldown, self.opened_at = 0, threshold, cooldown, None
    def is_open(self):
        return self.opened_at and time.time() - self.opened_at < self.cooldown
    def record_failure(self):
        self.fails += 1
        if self.fails >= self.threshold:
            self.opened_at = time.time()
    def record_success(self):
        self.fails, self.opened_at = 0, None

def search(query_vec, query_text, breaker):
    if not breaker.is_open():
        try:
            result = vector_db.search(query_vec, timeout=1.0)
            breaker.record_success()
            return result
        except Exception:
            breaker.record_failure()
    return bm25.search(query_text)  # degraded but honest fallback

1. What is context engineering, and how is it different from prompt engineering?

Saybudget I allocate
Say it like this

"Prompt engineering is about writing the instructions well — wording, examples, output format. Context engineering is the layer above it: deciding what information occupies the window at each step, from a much larger pool of candidates. In an agent, the prompt might be 500 tokens and fixed, while the context — retrieved documents, tool results, conversation history, memory, tool definitions — is 50,000 tokens and different on every turn. That's the part that determines whether the answer is good. So the mental model I use is that the context window is a budget I allocate, not a bucket I fill. Every token I spend on one thing is a token unavailable to another, and past a certain fill level extra tokens actively hurt. Prompt engineering was the discipline when models had 4k windows and one turn. Context engineering is the discipline when the model has 200k and thirty turns, because now the binding constraint isn't 'can I fit it' — it's 'what deserves to be there.'"

─────────────────           ───────────────────
how you ASK                 what the model SEES
static, authored            dynamic, assembled per step

optimise wording            optimise the ALLOCATION

2. What is context rot? Why doesn't a bigger window solve everything?

Say it like this

"Context rot is the observation that model performance degrades as the window fills, even well below the stated limit — and even when the needed information is definitely in there. Two things drive it. First, attention is a finite resource spread across all tokens, so every irrelevant token dilutes it; a model given one relevant chunk plus nineteen plausible-but-wrong ones will often answer worse than one given the single chunk alone. Second is position: models attend most reliably to the beginning and end of the context and are weakest in the middle — the 'lost in the middle' effect. So a 200k window doesn't mean I should send 200k. In practice I treat somewhere around 30 to 50 percent fill as the comfortable zone and I measure rather than assume, because the effect is task- and model-specific. The concrete consequence for RAG is that reranking down to fewer, better chunks usually beats retrieving more — going from twenty chunks to four typically improves faithfulness and cuts cost and latency at the same time. That's the rare change with no trade-off, which is why it's the first thing I try."

Practical corollary: put the most important content last, immediately before the question. Recency is the strongest position, and it's free to exploit.

3. What are the four context strategies?

SayWriteSelectCompressIsolate
Say it like this

"I organise everything under four verbs: write, select, compress, isolate. Write means getting information out of the window and into durable storage — a scratchpad, a memory store, a file — so it survives without occupying tokens. Select means pulling back only what this step needs: that's retrieval, but it also covers selecting which tools to expose and which memories to load. Compress means shrinking what must stay — summarising old turns, truncating tool outputs, dropping superseded intermediate results. Isolate means splitting work across separate contexts so no single window has to hold everything, which is the real argument for sub-agents. Almost every context problem is one of these four applied in the wrong proportion. If the agent forgets things, I'm under-writing or under-selecting. If it overflows, I'm under-compressing or under-isolating. Naming them like this is useful in an interview because it turns a vague 'manage the context' answer into a diagnosis."

Write Scratchpad, long-term memory store, files on disk Information is needed later, not now
Select RAG, memory retrieval, dynamic tool loading The candidate pool is much bigger than the budget
Compress Summarisation, compaction, tool-output truncation History must stay but not verbatim
Isolate Sub-agents, separate graph state, sandboxed execution Sub-tasks generate context the parent never needs

4. How do you budget a context window?

Sayevery single callgradual
Say it like this

"I write down an actual allocation before I write any code, because otherwise the retrieval step just expands to fill whatever's left. A typical split for a support agent on a 128k model, where I'm targeting maybe 30k of real fill: system prompt and rules get about 1,500 tokens; tool definitions maybe 2,000 — and that one surprises people, because twenty tools with rich schemas can be 5,000 tokens on every single call; retrieved context gets the largest share, say 8,000 after reranking; conversation history gets 4,000 with a compaction trigger; long-term memory gets 1,000; the user's message is small; and I reserve headroom for the output. Then I instrument it — I log the token count of each segment per request and alert when any one drifts. The reason to be explicit is that context bloat is always gradual: someone adds two tools, someone raises top-k from five to eight, someone stops truncating tool results, and three months later the average prompt has doubled with nobody noticing. A budget makes each of those a visible decision instead of a silent regression."

5. When and how do you compact an agent's history?

Say it like this

"I trigger on a token threshold, not a turn count — turns vary wildly in size because one tool result can be bigger than twenty exchanges. Something like: when history exceeds 70% of its budget, compact. The mechanic is to keep the most recent turns verbatim — usually the last two or three, because that's what the model needs for immediate coherence — and replace everything older with a structured summary. And 'structured' is the important word: a free-text summary loses exactly the things you need later. I ask for specific fields — the user's goal, decisions made and why, facts established, actions already taken with their results, and open questions — because those are what a resumed agent actually needs. Two things I always preserve outside the summary: the original user request, verbatim, because goal drift is the classic long-horizon failure and a summary-of-a-summary erodes it; and any hard identifiers like IDs, file paths, or amounts, because those must survive exactly and paraphrase destroys them. Then I log compaction events, since a spike in compactions usually means the real bug is elsewhere — an agent looping, or a tool returning far too much."

6. How do sub-agents help with context?

Saycontext isolationnarrow contract
Say it like this

"The strongest reason to use sub-agents isn't parallelism — it's context isolation. If a research task requires reading forty documents, doing that in the main agent's window means all forty pollute every subsequent turn. Instead I spawn a sub-agent whose entire job is 'read these forty and return a 300-token finding.' The forty documents live and die in the sub-agent's window; the parent only ever sees the conclusion. So the parent's context stays clean and the parent stays on-goal. The way I'd phrase the design rule is that a sub-agent should have a narrow contract: one clear objective, its own tools, and a small structured return value. If the sub-agent needs to hand back everything it saw, isolation has bought me nothing and I should have inlined it. The trade-off is real, though — every sub-agent is extra latency, extra tokens for its own system prompt, and a place for information to be lost in the handoff. So I use it when the sub-task is genuinely context-heavy and its output is genuinely small. That ratio is the test."

7. What is context offloading?

Sayreference
Say it like this

"Offloading is the 'write' strategy applied to tool results: instead of putting a large payload into the context, you put it somewhere addressable and put a reference into the context. A tool that queries a database returns 4,000 rows — I don't paste 4,000 rows into the window. I write them to a file or a store and return 'saved 4,000 rows to results.parquet; columns are X, Y, Z; here are the first three.' The agent can then run a follow-up tool against that file if it needs more. Same idea for a long document: return a resource link and a summary, not the whole thing. This is exactly what MCP's resource links are for. The payoff is large because tool results are usually the biggest and least controllable part of an agent's context — you wrote the prompt, but the tool output is whatever the world hands back. The related discipline is to truncate every tool result at the tool boundary, with a hard cap and a clear marker that it was truncated, so one badly-behaved API can't blow up the window."

8. How does prompt caching change how you order context?

Sayprefixstablevariable
Say it like this

"Prompt caching works on a prefix — the provider caches a fixed leading segment, so repeated calls sharing that prefix are much cheaper and faster on the input side. The design consequence is that context ordering stops being arbitrary and becomes an optimisation: put everything stable at the front and everything variable at the back. So system prompt first, then tool definitions, then any long fixed reference material — those are identical across calls and cache well. Then retrieved context, then history, then the user's message, which change every time. The failure mode is subtle: if you inject something variable early — a timestamp in the system prompt, a session ID, a user's name — you invalidate the cache for every single call and lose the entire benefit while everything still works, so nothing alerts. I've seen that quietly cost a lot of money. So the rule is: never let a variable token appear before a stable one, and monitor the cache-hit rate as a first-class metric rather than assuming it's working."

✅  [system][tools][stable refs] | [docs][history][question]

9. What is HyDE and when does it help?

Saywrite a fake answerthat
Say it like this

"HyDE is Hypothetical Document Embeddings. The problem it solves is that a question and its answer often don't look alike in embedding space — a short question like 'why did Q3 margins fall?' has very different vocabulary and shape from the paragraph that answers it. So instead of embedding the question, you ask the LLM to write a fake answer — a plausible passage that would answer the question — and embed that, then search with it. You're matching answer-shaped text against answer-shaped documents, so the geometry lines up. It doesn't matter that the hypothetical answer is factually wrong; you never show it to the user, you only use its embedding. Where it helps most is short, vague, or jargon-light queries over a technical corpus. Where it hurts: it adds a full LLM call of latency to every query, and on queries that are already keyword-rich it can reduce precision by hallucinating terms that pull retrieval off-target. So I'd treat it as a targeted fix for a measured recall problem on hard queries, not a default — and I'd usually reach for hybrid search plus reranking first, because those are cheaper and help more broadly." 

Standard:  "why did Q3 margins fall?"  ──embed──►  search
HyDE:      "why did Q3 margins fall?"  ──LLM──►  "Q3 margins declined due to
                                                   increased input costs and…"  ──embed──► search

10. What is contextual retrieval?

Sayand index the BM25 term foringestzero added query latencyQueryNone
Say it like this

"It fixes the fact that a chunk, once split out of its document, loses the context that made it meaningful. A chunk that says 'revenue grew 3% over the previous quarter' is nearly useless on its own — which company, which quarter? So before embedding, you prepend a short generated blurb that situates the chunk in its document: something like 'This chunk is from ACME Corp's Q2 2026 10-Q, in the section on segment performance; it discusses revenue growth versus Q1 2026.' You generate that with a cheap model, giving it the chunk plus the surrounding document, and you embed and index the BM25 term for the contextualised version. The reported result is a large reduction in retrieval failures, and the reason it works is that it fixes both retrieval paths at once — the embedding gets disambiguating semantics, and the keyword index gets the entity names that were previously missing from the chunk entirely. The cost is one cheap LLM call per chunk at ingest time, which prompt caching over the parent document makes quite affordable, and crucially it's a one-time offline cost with zero added query latency. That trade — pay at ingest, free at query — is why I like it more than HyDE."

11. What is late chunking?

Saywhole documentthen
Say it like this

"Normal pipelines chunk first and embed second, so each chunk is embedded in complete isolation — a pronoun in chunk seven has no idea who it refers to. Late chunking inverts that: you run the whole document through a long-context embedding model to get token-level embeddings, so every token has attended to the full document, and only then you slice the token embeddings into chunks and mean-pool each slice into a chunk vector. The chunk vectors come out contextualised, because the contextualisation happened before the split rather than after. It solves the same problem as contextual retrieval — chunks losing their context — but with a different trade-off: late chunking needs no LLM calls at all, just a long-context embedding model, so it's cheaper at ingest; contextual retrieval works with any embedding model and also improves your keyword index, which late chunking doesn't touch. If I had a long-context embedding model available and a mostly-semantic search, I'd try late chunking first because it's nearly free. If I'm running hybrid search, contextual retrieval buys more because it lifts both retrieval paths."

12. Explain small-to-big / parent-document retrieval

Saysearchreturn
Say it like this

"There's a tension in choosing a chunk size. Small chunks embed precisely — one idea per vector, so retrieval is accurate — but they're poor context for generation because the model gets a fragment. Big chunks are great context but their embeddings are muddy, since one vector has to represent several ideas and ends up representing none of them well. Small-to-big resolves it by decoupling the two: you search over small chunks and you return their larger parent. So you index child chunks of a couple hundred tokens, keep a mapping to the parent section or document, and after retrieval you swap each hit for its parent before assembling the context. You get precise retrieval and complete context. Two details matter in practice: deduplicate parents, because five child hits from the same section shouldn't return that section five times; and watch your token budget, since parents are by definition bigger — this pairs well with reranking on the children and only expanding the survivors. It's the same 'retrieve by proxy, generate from the original' pattern that multi-vector retrieval uses for tables and images."

13. Query rewriting vs decomposition vs step-back

SayRewritingDecompositionparallelStep-back
Say it like this

"They're three different fixes for three different bad queries, and mixing them up is a common tell. Rewriting is for a query that's badly formed — conversational, full of pronouns, or ambiguous. 'What about last year?' is unsearchable, so I rewrite it against the conversation into 'What was ACME's revenue in 2025?' That's mandatory in any multi-turn RAG system; without it, follow-up questions retrieve garbage. Decomposition is for a query that contains several independent questions: 'Compare our refund policy to our exchange policy' needs two separate retrievals, one per policy, then a synthesis — one blended embedding of both would land somewhere between them and retrieve neither well. The bonus is that independent sub-queries run in parallel, so it often costs little latency. Step-back is for a query that's too specific to match anything: 'Can I return a blue size-9 running shoe bought on the 14th?' has no document. Stepping back to 'What is the return policy on footwear?' retrieves the policy, and then the model applies it to the specifics. So: rewriting fixes form, decomposition fixes multiplicity, step-back fixes over-specificity. In a router-based agentic RAG system I'd have the planner classify which one the query needs rather than always applying all three."

14. What is GraphRAG and when is it worth the cost?

Sayknowledge graphglobalmulti-hop relationalspecific failing query classHigh — LLM pass over corpus
Say it like this

"GraphRAG replaces — or more usually augments — the flat vector index with a knowledge graph: you extract entities and relationships from the corpus at ingest, build a graph, cluster it into communities, and pre-summarise each community. At query time you traverse relationships instead of, or alongside, matching embeddings. The reason to do it is a class of question vector search structurally cannot answer: global questions like 'what are the main themes across these 10,000 documents?' — no single chunk contains the answer, so top-k retrieval will always fail — and multi-hop relational questions like 'which suppliers are indirectly exposed to the vendor we just flagged?', where the answer is a path through relationships that no chunk states. Vector search finds similar text; a graph finds connected facts. The honest part of the answer is the cost: ingestion means an LLM extraction pass over the entire corpus, which is expensive and slow, the graph has to be maintained as documents change, and quality depends heavily on the extraction schema. So I would not start here. I'd start with hybrid plus reranking, and I'd only move to GraphRAG when I could point at a specific failing query class that is relational or global — and even then I'd run it as a second retriever behind a router, not as a replacement for the vector path."

15. How do you do RAG over PDFs with tables and charts?

Saysummariesoriginalspage as an image
Say it like this

"The failure everyone hits first is running a text extractor over the PDF: tables come out as scrambled text, charts come out as nothing at all, and scanned pages come out empty — so the answer confidently omits exactly the numbers the user asked about. There are three architectures. The one I'd default to in production is summarise-then-embed with a multi-vector retriever: partition the document into text, tables, and images; use a vision model to write a text summary of each table and figure; embed the summaries into the vector store, but keep the originals in a docstore keyed by ID. At query time you retrieve by matching the summary, then hand the original table or image to the generating model. The principle is 'retrieve by proxy, generate from the original' — summaries are what search well, originals are what answer well. The second option is a shared embedding space like CLIP, where images and text live in one vector space; it's elegant but weaker on dense text-in-image, which is most business documents. The third is ColPali, which embeds the page as an image with late interaction and skips parsing entirely — very strong on complex layouts and scans, at the cost of much larger indexes. For evaluation I tag the golden set by modality and report recall per type, because an aggregate number will hide the fact that tables are at 40%."

16. You have all these techniques. How do you choose?

Sayretrievedfaithfulcheapest and broadest first
Say it like this

"I choose by diagnosing which stage is failing, not by picking favourites. So first I split the metric: is the right document being retrieved at all, and separately, given the right document, is the answer faithful? Those have completely different fixes and conflating them wastes weeks. If retrieval recall is the problem, I look at why. Wrong vocabulary between question and answer — HyDE, or query rewriting. Chunks that lost their meaning when split — contextual retrieval or late chunking. Exact terms like error codes or part numbers not matching — hybrid search with BM25, which is the highest-value fix in most enterprise corpora and it's the first thing I'd add. Multi-part or over-specific queries — decomposition or step-back. Relational or global questions — that's the GraphRAG case. If recall is fine but the answer is bad, the fix is downstream: rerank to fewer, better chunks; expand to parent documents so the model sees whole thoughts; tighten the grounding prompt; add a citation check. The ordering principle is cheapest and broadest first — hybrid search and reranking help almost every corpus and cost almost nothing, while GraphRAG helps a narrow query class and costs a lot. And every one of these ships behind an eval on a golden set, because they all sound good and about half of them make things worse on any given corpus."

17. How do tools, MCP, and A2A fit together?

SayFunction/tool callingMCPA2Atoolsagents
Say it like this

"They sit at three different layers and people conflate them. Function/tool calling is the model-level primitive: the LLM emits a structured request to run something, and your application executes it. That's provider-specific and lives inside one app. MCP standardises the layer below that — how an application discovers and connects to tool providers. Instead of writing a custom integration per app per tool, a tool exposes an MCP server once and any MCP-capable client can use it, which turns an N×M integration problem into N+M. MCP tools still ultimately become function calls when they reach the model; MCP is about the plumbing and discovery, not about how the model decides. A2A is a layer up again: agent-to-agent, how one autonomous agent delegates a task to another agent it doesn't own — capability advertisement, task lifecycle, negotiation. The clean summary is that MCP connects an agent to its tools, A2A connects an agent to other agents, and function calling is how the model expresses intent within either. In a real system I'd expect all three: my LangGraph agent calls tools via function calling, sources several of those tools from MCP servers, and if it needs a capability owned by another team's agent, that's the A2A boundary."

18. Semantic, episodic, procedural memory — what goes where?

SaySemanticEpisodicProceduralcheckpointerYes
Say it like this

"The three-way split comes from cognitive science and it maps cleanly onto what an agent needs to store. Semantic memory is facts about the user or the world — 'this user's account tier is enterprise', 'their timezone is IST'. It's retrieved by relevance, so it lives in a vector store or a key-value profile, and you select the relevant few per turn rather than loading all of it. Episodic memory is specific past experiences — 'last Tuesday we tried approach X on this ticket and it failed because of Y'. That's what makes an agent improve across sessions instead of repeating mistakes; Reflexion is essentially episodic memory used as a learning signal. Procedural memory is how to do things — the system prompt, learned workflows, refined instructions. It's usually the least dynamic, though self-improving agents rewrite it. The distinction that matters operationally is that all three are separate from the checkpointer. A checkpointer persists the state of one thread so a conversation survives a restart — that's short-term and thread-scoped. Long-term memory is cross-thread and user-scoped, it lives in a store, and it has to be written deliberately and selected deliberately. Conflating the two is the common design error: teams turn on a checkpointer, call it memory, and then wonder why the agent doesn't remember anything from last week."

19. How do you evaluate a context-engineering change?

SayAnswer qualityFaithfulnessToken count and cost per requestLatency
Say it like this

"The trap is measuring the wrong thing, because most context changes improve one number while quietly degrading another. So I fix a golden set and report a small panel rather than a single score. Answer quality — task accuracy or an LLM-judge win-rate against the current system, with position randomised. Retrieval recall@k measured separately, because if recall didn't move, any quality change came from generation and I've misattributed the win. Faithfulness — is the answer grounded in what I actually supplied. Token count and cost per request, since a lot of context 'improvements' are just spending more. Latency, especially for anything that adds an LLM call at query time like HyDE or query rewriting. And for long-horizon agents specifically, goal adherence at the end of the run, because compaction bugs show up as an agent that drifts off-task on turn thirty while looking perfectly fine on turn three. That last one needs multi-turn eval, not single-turn — a change that improves every individual turn can still make the trajectory worse. I'd also A/B rather than trusting the offline number alone, since context effects are strongly corpus- and traffic-dependent."
