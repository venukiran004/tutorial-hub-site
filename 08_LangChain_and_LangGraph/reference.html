Agentic AI & RAG — Reference: Definitions, Differences, Trade-offs

The one-page revision sheet. Nothing here is new material — it is the same content as the question banks, arranged for lookup rather than for reading.

  • Definitionsone clean sentence per term; where a term is commonly confused with another, the confusion is named.
  • Differencesthe "what's the difference between…" questions, each answered as a table you could redraw on a whiteboard.
  • Trade-offsevery technique costs something. The last column is what separates a candidate who has read about a technique from one who has shipped it.
1. Definitions
•

Core RAG

RAGChunkChunk overlapEmbeddingnot comparableVector store
Term Definition
RAG Retrieval-Augmented Generation. Fetch relevant text at query time and put it in the prompt, so the model answers from supplied facts instead of memorised ones.
Chunk A slice of a document small enough to embed meaningfully and to fit a context budget. The unit of retrieval.
Chunk overlap Repeating a few tokens between adjacent chunks so a sentence split across a boundary is still retrievable from one side.
Embedding A fixed-length vector encoding meaning, so semantic similarity becomes vector distance. Vectors from two different models are not comparable.
Vector store A database that indexes embeddings for approximate nearest-neighbour search, usually with metadata filtering alongside.
ANN / HNSW / IVF / PQ Approximate nearest neighbour search and its common index types. HNSW = navigable graph, fast, RAM-hungry. IVF = cluster-then-search. PQ = compress vectors to fit memory.
Top-k How many candidates retrieval returns. Bigger k raises recall and lowers precision, and costs context.
Metadata filtering Restricting the search space by structured fields (tenant, date, ACL) before or during the vector search. Also how access control is enforced.
Grounding Requiring the answer to be traceable to supplied context rather than model memory.
Abstention Declining to answer when retrieval confidence is too low. A feature, not a failure.
•

Retrieval techniques

Semantic (dense) searchBM25 (sparse / lexical)Hybrid searchRRFrank not scoreBi-encoder
Term Definition
Semantic (dense) search Match by embedding similarity. Strong on paraphrase, weak on exact tokens like error codes and part numbers.
BM25 (sparse / lexical) Classic keyword ranking on term frequency and rarity. Strong on exact terms, blind to synonyms.
Hybrid search Run dense and sparse together and fuse. Usually the highest-value single addition to an enterprise RAG system.
RRF Reciprocal Rank Fusion — combine ranked lists by 1/(k+rank). Uses rank not score, so it needs no score calibration between retrievers.
Bi-encoder Encodes query and document separately, so document vectors can be precomputed. Fast, less accurate. The retriever.
Cross-encoder Encodes query and document together, so it can't precompute. Slow, far more accurate. The reranker.
Reranking Re-scoring a shortlist with a stronger model, then keeping the best few. Usually improves faithfulness, cost and latency at once.
MMR Maximal Marginal Relevance — trades relevance against diversity so you don't return five copies of the same paragraph.
HyDE Ask the LLM to write a hypothetical answer, embed that, and search with it — matching answer-shaped text against answer-shaped documents. Costs an LLM call per query.
Contextual retrieval Prepend a generated blurb situating each chunk in its document before embedding and indexing it. Ingest-time cost, zero query latency, helps BM25 too.
Late chunking Embed the whole document's tokens first (full-document attention), then slice and pool per chunk. Needs a long-context embedding model, no LLM calls.
Small-to-big / parent-document Search over small precise chunks, return their larger parent for generation. Decouples retrieval precision from generation context.
Query rewriting Rewriting a conversational or ambiguous query into a standalone searchable one. Mandatory in multi-turn RAG.
Query decomposition Splitting a compound question into independent sub-questions, known up front — so they can run in parallel.
Step-back prompting Generalising an over-specific query so it can match a policy or principle document, then applying it to the specifics.
GraphRAG Extract entities and relations into a knowledge graph and traverse it. The answer to global ("themes across the corpus") and multi-hop relational questions vector search structurally cannot serve.
Multimodal RAG Retrieval over tables, charts and scans. Production default: summarise each element, embed the summary, keep the original, and generate from the original.

Agentic

AgentAgentic RAGdecisionRouterPlannerExecutor
Term Definition
Agent An LLM in a loop with tools and a termination condition. It decides the next step; it does not execute it.
Agentic RAG RAG where retrieval is a decision, not a fixed step — whether to retrieve, from where, and whether the result was good enough.
Router Picks which path or source handles a query. Evaluate it as a classifier, because it is one.
Planner Decomposes a goal into steps, up front or as it goes.
Executor Runs the chosen tool call and returns the observation.
Reflection The agent critiques its own draft and revises. Cheap to add, real cost multiplier.
Reflexion Reflection plus episodic memory — remembering what failed last time so the next attempt differs.
Self-RAG One LM trained to emit reflection tokens that gate retrieval and rank its own candidate answers. The critic is the generator.
Corrective RAG (CRAG) A lightweight retrieval evaluator in front of an unchanged generator, triggering refine / web-search / combine. The critic is a separate small model.
Iterative retrieval Each query is derived from the previous result, so it cannot be parallelised and needs a hard hop cap.
Hop cap A hard, code-enforced ceiling on loop iterations with a guaranteed exit branch. Not a prompt instruction.
Tool calling The model emits a structured request naming a tool and arguments; your application executes it and returns the result as data.
MCP Model Context Protocol — a standard for how applications discover and connect to tool providers, turning N×M integrations into N+M. Connects an agent to its tools.
A2A Agent-to-agent. How one autonomous agent delegates to another it doesn't own. Connects an agent to other agents.
HITL Human-in-the-loop — a real interrupt in the graph that pauses for approval, not a line in the prompt.

Multi-agent patterns

Supervisorsum of hopsOrchestrator-workerslowest branchSwarmHierarchical
Term Definition
Supervisor A central LLM routes to one worker per turn, sees the result, routes again. Sequential; latency is the sum of hops.
Orchestrator-worker A planner splits the goal into N subtasks, dispatches them in parallel, and a synthesizer merges. Latency is the slowest branch.
Swarm Peers hand off directly to each other with no central router. Flexible, prone to ping-pong loops.
Hierarchical Teams of teams — supervisors whose workers are themselves supervised graphs. Scales org-shaped problems, costs latency.
Plan-and-Execute Plan the whole sequence up front, execute the steps, optionally re-plan. A bad plan poisons every step.
Sub-agent A child agent with a narrow contract, used mainly for context isolation — its 40 documents never enter the parent's window.

Context engineering

Context engineeringContext rotLost in the middlelastCompactionstructured
Term Definition
Context engineering Deciding what occupies the window at each step, from a much larger candidate pool. The layer above prompt engineering.
Context rot Quality degrading as the window fills, well below the stated limit, because attention is finite and spread across all tokens.
Lost in the middle Models attend most reliably to the start and end of the context. Put the most important content last.
Write / Select / Compress / Isolate The four context strategies: move it to storage, retrieve only what's needed, shrink what must stay, split across separate windows.
Compaction Replacing older turns with a structured summary (goal, decisions, facts, actions, open questions) on a token threshold, keeping recent turns verbatim.
Context offloading Returning a reference to a large payload instead of the payload. MCP resource links exist for exactly this.
Prompt caching Providers cache a fixed prompt prefix. Stable content first, variable last — a timestamp up top silently kills the cache while everything still works.
Checkpointer vs Store Checkpointer = one thread's state, survives restart but not a new conversation. Store = cross-thread, user-scoped, and you write to it deliberately.
Semantic / Episodic / Procedural memory Facts about the user · specific past experiences · how to do things. Different retrieval patterns, different stores.

Serving & optimization

Prefill vs decodeKV cachePagedAttentionContinuous batchingSpeculative decodingQuantization
Term Definition
Prefill vs decode Prefill processes the whole prompt in parallel (compute-bound). Decode emits one token at a time (memory-bound). Different bottlenecks, different fixes.
KV cache Cached attention keys/values so each new token doesn't recompute the whole sequence. The reason decode is memory-bound.
PagedAttention Paging the KV cache like virtual memory, removing fragmentation and raising batch size. The core vLLM idea.
Continuous batching Admitting new requests into a running batch as slots free up, instead of waiting for the whole batch to finish.
Speculative decoding A small draft model proposes several tokens, the big model verifies them in one pass. Same output distribution, fewer big-model steps.
Quantization Storing weights at lower precision (INT8/INT4) for memory and speed, at some accuracy cost.
Distillation Training a small model on a big model's outputs. The standard fix for expensive routers, graders and rerankers.
Semantic cache Serving a stored answer when a new query is semantically close to an old one. A hit skips the entire pipeline.
Tool-result cache Caching on (tool, args) — reusable across entirely different runs, unlike a query-keyed cache.
Sharding vs replication Shard for capacity when the corpus outgrows RAM; replicate for QPS and availability. Different problems.
TTFT Time to first token. What users actually perceive — which is why streaming beats most backend tuning.

Evaluation

Recall@kPrecision@kMRRMean Reciprocal Rankposition, not presenceNDCG
Term Definition
Recall@k Is the right chunk anywhere in the top-k? Fix this first — nothing downstream recovers from a miss.
Precision@k How much of what you retrieved was actually useful.
MRR Mean Reciprocal Rank — for one query, 1/(rank of the first relevant result); report the mean over the eval set. First hit at rank 1 → 1.0, rank 3 → 0.33, never → 0. It measures position, not presence, which is why reranking moves it and recall@k does not.
NDCG Graded relevance across the whole ranking, discounted by position.
Faithfulness / groundedness Is the answer supported by the context you supplied? The anti-hallucination metric.
Answer relevancy Does it answer the question that was asked?
Context precision / recall Was useful context ranked high · did retrieval get everything the answer needed. Splitting these tells you which half is broken.
RAGAS A framework packaging faithfulness, answer relevancy and context precision/recall for RAG pipelines.
Outcome vs trajectory eval Did it get the right answer · did it take a sound path. Agents need both; outcome alone hides a lucky guess.
Tool-selection / argument accuracy Right tool for the step · right arguments for the tool. Distinct and separately common failures.
pass^k Succeeds k times in a row. Consistency, not best-case — an agent that passes once and fails twice isn't shippable.
LLM-as-judge Using a model to grade outputs. Needs position randomisation, length control, and its own calibration check.
Golden set A frozen, representative set of cases with accepted outputs. The thing you re-run to prove a change is safe.
Grader calibration Whether a grading step agrees with human judgment. In CRAG this single number decides whether the whole loop helps or hurts.

3. Optimization Techniques — by Layer

what it doeswhen it is the right leverSmall / distilled model (SLM)Model routingQuantization (INT8/INT4)Speculative decoding

Grouped by the layer you would actually change. Each row: what it does in one line, and when it is the right lever — because naming a technique without naming its trigger is what makes an answer sound rehearsed.

3a. LLM / serving layer

Technique What it does When it is the right lever
Small / distilled model (SLM) Runs a smaller model, often distilled from a larger one. The task is classification, extraction or routing — not open reasoning.
Model routing Sends each request to the cheapest model that can handle it. Your traffic is a mix of easy and hard, and you pay frontier prices for all of it.
Quantization (INT8/INT4) Cuts weight/activation precision to shrink memory and speed up inference. You are memory-bound or GPU-poor, and can afford a small accuracy cost.
Speculative decoding A draft model proposes several tokens; the big model verifies them in one pass. Decode-bound workloads with predictable text — acceptance rate decides the win.
Continuous / dynamic batching Adds and removes sequences from a running GPU batch as they arrive and finish. Throughput is the goal and requests arrive at uneven times. The default for any real server.
Prefix caching Reuses the computed KV cache for a shared prompt prefix across requests. A long, stable system prompt or tool block sits in front of every call.
KV cache Stores attention keys/values for past tokens so each new token attends without recompute. Always on — the question is how you manage it, not whether to use it.
Flash attention A fused attention kernel that never materialises the full attention matrix. Long sequences where attention memory I/O, not compute, is the ceiling.
Paged attention (vLLM) Manages the KV cache in fixed-size pages, like OS virtual memory. KV fragmentation is capping your batch size and therefore your throughput.
Chunked prefill Interleaves a long prompt's prefill with other requests' decode steps. One user's 100k-token prompt is stalling everyone else's token stream.
Tensor parallelism Splits individual matrix operations across GPUs within a layer. The model does not fit on one GPU.
Pipeline parallelism Splits layers across GPUs, each handling one stage of the forward pass. The model still does not fit, and you have more GPUs than one layer needs.
Mixture of experts (MoE) Activates only a subset of expert sub-networks per token. You want large-model quality at a fraction of the per-token compute.

3b. Retrieval layer

Technique What it does When it is the right lever
Hybrid search Fuses keyword (BM25) and dense vector results, usually with RRF. Queries contain names, codes or identifiers that dense search silently misses.
Reranking A cross-encoder rescores the top-N candidates and keeps the best few. The right passage is retrieved, but ranked below your cut-off.
Metadata filters Restricts the search to a subset before the vector scan. The corpus is large but each query only concerns one tenant, date range or document type.
Embedding cache Reuses embeddings for text already embedded. The same documents or queries are embedded repeatedly — pure cost saving.
Retrieval cache Caches the retrieved chunk set for a query. A head of popular queries repeats often.

3c. System / orchestration layer

Technique What it does When it is the right lever
Parallel tool calls Issues independent tool calls concurrently rather than in sequence. The agent makes 3+ independent calls and total latency is their sum.
Async processing Moves slow work to a queue and answers the user immediately. The work does not have to finish before the user gets a useful response.
Autoscaling Adds and removes instances based on load. Traffic is spiky and you are either over-provisioned or dropping requests.
Response streaming Sends tokens as they are produced. Perceived latency is the complaint — it does not reduce total time at all.

4. Caching — the seven places an LLM system can cache

layerkeyed onstaleExact / prompt cachePrefix cacheKV cache

Caching is the highest-leverage optimization in this whole sheet, and “we use a cache” is not an answer. Name the layer, what it is keyed on, and what makes it stale.

# Cache type What is stored Keyed on Typical saving What makes it wrong
1 Exact / prompt cache The full generated response Hash of the exact prompt 100% of the call — cost and latency both go to ~0 Any personalisation or timestamp in the prompt drops the hit rate to near zero
2 Prefix cache The KV tensors for a shared prompt prefix The literal token prefix Prefill only: ~150ms → ~40–60ms One changing byte early in the prompt (a timestamp, a user id) invalidates everything after it
3 KV cache Attention keys/values for tokens already generated Position within one sequence Turns O(n²) regeneration into O(n) Memory: it grows with every token and is what caps your batch size
4 Semantic cache Past answers, retrieved by embedding similarity Embedding of the query, with a similarity threshold A large share of a repetitive head of traffic A threshold set too loose returns a confidently wrong neighbour's answer
5 Embedding cache Vectors for text already embedded Hash of the text + model version The whole embedding call Forgetting the model version in the key — you silently mix two vector spaces
6 Retrieval / result cache The chunk set a query retrieved Normalised query + filters The vector search, typically 20–60ms Reindexing without invalidating: you serve retrieval results for documents that changed
7 Tool / API response cache What an external tool returned Tool name + arguments The whole external call Caching a non-idempotent or time-sensitive call (prices, availability, balances)

And the two below the application, which behave like any other web system:

Cache type What is stored Notes
CDN / edge cache Static assets and cacheable responses Closest to the user and the cheapest hit you will ever get.
Database / query cache Query results, buffer pool pages Usually the database's own concern — but know that it exists before you add another layer above it.

4a. Cache write & eviction policies

Policy How it behaves Pick it when
Cache-aside (lazy) App checks the cache, misses, reads the source, then fills the cache. The default. Simple, and the cache can fail without taking the app with it.
Read-through The cache itself loads from the source on a miss. You want the application code to never know about the source.
Write-through Writes go to cache and source together, synchronously. Staleness is unacceptable and you can pay the write latency.
Write-behind Writes hit the cache and reach the source asynchronously. Write bursts must be absorbed — accepting that a node loss loses acknowledged writes.
Refresh-ahead Hot keys are refreshed just before they expire. A small set of hot, expensive, predictable keys.
LRU Evicts the least recently used entry. General-purpose default — matches temporal locality.
LFU Evicts the least frequently used entry. A stable hot set that a burst of one-off queries would otherwise flush.
FIFO Evicts the oldest entry regardless of use. Rarely the right choice; simple to reason about.
TTL Every entry expires after a fixed time. Always set one — it is your ceiling on staleness. Add jitter.

4b. The four classic cache failures

Failure What happens The fix
Stampede / dogpile A hot key expires and N concurrent misses all hit the source at once. Single-flight lock, or serve stale while one request refreshes.
Avalanche A large number of keys expire in the same second and the source collapses. Jitter the TTLs so expiry is spread out.
Penetration Requests for keys that do not exist bypass the cache every time. Cache the negative result briefly, or use a Bloom filter.
Hot key One key takes so much traffic that a single cache node saturates. Replicate that key across nodes, or add a small local in-process cache in front.

The two sentences to say out loud: every cache needs a TTL and an explicit invalidation path; and a cache changes your failure mode from slow to wrong, which is a trade you should make deliberately rather than discover in production.

7. Glossary — Term Definitions

Each row above is a keyword hook. Full definitions below, grouped to match sections 1–4.

RAG terms

Term Definition
Hybrid Search (BM25 + Vector) Combines sparse keyword search (BM25) with dense vector similarity search, then merges results — catches exact-term matches and semantic matches.
Re-ranking (Cross-Encoder / Cohere Rerank) A second-pass model that jointly scores each (query, chunk) pair for relevance and reorders the initial retrieval set — more accurate but slower than bi-encoder retrieval.
Semantic / Recursive Chunking Splitting documents along meaning boundaries (sentences, sections) or recursively by separators instead of fixed character counts — keeps chunks coherent.
MMR (Maximal Marginal Relevance) Re-ranks retrieved chunks to balance relevance to the query against similarity to already-selected chunks — reduces redundant/duplicate context.
Query Rewriting / Multi-Query Retrieval The LLM reformulates the query into one or more alternate phrasings to retrieve a broader, more relevant candidate set.
Reciprocal Rank Fusion (RRF) Merges ranked lists from multiple retrievers by summing 1/(k+rank) per document across lists — no score normalization needed.
Metadata Filtering Pre-filters the search space using structured fields (date, tenant, doc type) before or during the vector/ANN search.
Sharding & Replication Sharding splits the index across nodes for capacity; replication duplicates it for availability/read throughput — different scaling levers, often confused.
Embedding Cache Stores previously computed embeddings keyed by input hash to skip redundant embedding-model calls.
Retrieval Cache Caches the full retrieval result (the chunk set) for a given query to skip the search step entirely on repeat queries.

Agent scaling terms

Term Definition
Multi-Agent Architecture Splits a task across specialized agents that can run concurrently instead of one agent handling everything sequentially.
Supervisor Agent An orchestrator agent that delegates subtasks to worker agents and assembles their outputs.
Async Queues (Kafka, RabbitMQ, Redis Streams, SQS) Decouples request submission from processing via a message broker, so long tasks don't block callers and consumers scale independently.
Stateless APIs API instances hold no session state in memory, so any instance can serve any request — enables simple horizontal scaling/load balancing.
Horizontal Scaling (Kubernetes) Adding more instances/pods behind a load balancer rather than growing one machine's resources (vertical scaling).
External Memory (Redis/DB) Agent/conversation state stored outside the process, so any instance can pick up and continue execution.
Parallel Tool Calls Independent tool/function calls issued concurrently instead of one after another.
Retry + Circuit Breaker Retry re-attempts a failed call, usually with backoff; a circuit breaker stops calling a consistently failing dependency to prevent cascading failure.
Max Iterations / Reasoning Limit A hard cap on agent loop steps or tool calls, preventing infinite or runaway reasoning loops.
Workflow Checkpointing Persists intermediate workflow state so a long-running job can resume from the last checkpoint instead of restarting after a failure.

Optimization (LLM/serving) terms

Term Definition
SLM (small/distilled model) A smaller model, often trained via distillation from a larger one, used for lower-cost/lower-latency inference on simpler tasks.
Model Routing Sends each request to the cheapest model capable of handling it, reserving the frontier/reasoning model for hard cases.
Quantization (INT8/INT4) Reduces the numerical precision of model weights/activations to cut memory footprint and speed up inference, at some accuracy cost.
Speculative Decoding A small "draft" model proposes several tokens ahead, which the large model verifies in a single pass — speeds up generation when drafts are accepted.
Continuous / Dynamic Batching Groups concurrent requests into a shared GPU batch, adding and removing sequences as they arrive or finish rather than waiting for a fixed batch to fill.
Prefix Caching Reuses the computed KV cache for a shared prompt prefix (e.g., system prompt) across requests instead of recomputing it each time.
KV Cache Stores the key/value attention tensors for already-generated tokens so each new token only computes attention for itself, not the whole sequence.
Flash Attention A fused, memory-efficient attention kernel that avoids materializing the full attention matrix — reduces memory I/O and speeds up training/inference.
Paged Attention (vLLM) Manages the KV cache in fixed-size, non-contiguous "pages" (like OS virtual memory) to eliminate fragmentation and support higher batch concurrency.
Chunked Prefill Splits a long prompt's prefill computation into chunks interleaved with decode steps, so one large prompt doesn't stall other requests' token generation.
Tensor Parallelism Splits individual matrix operations (e.g., a weight matrix) across multiple GPUs within a layer — used when a model doesn't fit on one GPU.
Pipeline Parallelism Splits the model's layers across GPUs, with different GPUs handling different stages of the forward pass in a pipeline.
Mixture of Experts (MoE) Only a subset of "expert" sub-networks activate per token, giving a large total parameter count at a lower per-token compute cost.
Autoscaling Automatically adds or removes compute instances based on load (CPU/GPU utilization, queue depth) to match capacity to demand.
Response Streaming Sends generated tokens to the client incrementally as they're produced instead of waiting for the full response — lowers perceived latency (time-to-first-token).

Latency terms

Term Definition
Prompt Cache Caches the model's response (or KV state) for an identical or near-identical prompt to skip regeneration.
Conversation Summarization Periodically compresses older turns of a long conversation into a summary to keep the context window small.
ANN Index (HNSW, IVF) Approximate Nearest Neighbor index structures (graph-based HNSW, cluster-based IVF) that trade a little recall for much faster vector search than exact search.
Regional Deployment Runs inference/serving infrastructure in multiple geographic regions so requests hit a nearby endpoint, cutting network round-trip time.
Batch Requests Groups multiple independent calls (e.g., embedding calls) into one API request to amortize per-call overhead.
Context Compression Reduces prompt token count (summarization, pruning, selective retrieval) before sending to the LLM to cut prefill time and cost.
Batch Embedding Generation Embeds many texts in a single forward pass instead of one at a time, improving throughput.
Timeouts + Fallbacks Bounds how long a slow tool/dependency call is allowed to run, falling back to a default or cached response if the bound is exceeded.

Read these first — every other section is an elaboration of one of them.

Term One line
Graph Your application, expressed as nodes (work) connected by edges (control flow).
State The single typed object every node reads from and writes to. The graph is a state machine.
Node A plain function: takes state, returns a partial update to state. That is the whole contract.
Edge What runs next. Fixed (always B after A) or conditional (a function picks).
Reducer How two writes to the same state key get merged. Without one, last write wins.
Superstep One tick of execution. Everything scheduled in a tick runs, then state is committed.
Checkpointer Saves state after every superstep, so a run can pause, resume, crash, or rewind.
Thread One conversation/session. A thread_id is what makes checkpoints addressable.
Tool A typed function the model may call. The model chooses it; your code runs it.
Agent An LLM in a loop with tools and a stopping condition — the LLM decides control flow.

1. Graph structure

StateGraphMessageGraphNodepartialEdgeparallel
Term What it is Why it exists / the gotcha
StateGraph The builder you add nodes and edges to. Parameterised by a state schema. The schema is not decoration — it defines the channels nodes may write to.
MessageGraph Legacy shorthand for a graph whose state is just a message list. Superseded by StateGraph with an add_messages field. Don't start new work here.
Node def node(state) -> dict. Returns a partial update, not the whole state. Returning the full state re-writes every channel and can clobber concurrent updates.
Edge add_edge(a, b) — after a, always run b. Unconditional. Two edges out of one node means parallel execution, not a choice.
Conditional edge add_conditional_edges(src, router_fn, path_map) — a function returns the name(s) of the next node(s). The router returns names, not state. Returning a list fans out. A name missing from path_map raises at runtime, not build time.
START Sentinel for the graph's entry point. add_edge(START, "first"). A graph with no edge from START compiles and then does nothing.
END Sentinel for termination. Routing to it ends that branch. Ending one branch doesn't end the graph — other branches keep running.
.compile() Turns the builder into a runnable graph; attaches checkpointer, store, interrupts. Compile-time is where structural errors surface (unreachable nodes, unknown targets).
CompiledStateGraph The runnable result. Implements the Runnable interface (invoke / stream / batch). Because it's a Runnable, a whole graph can be a node inside another graph.
Command A return value that carries both a state update and a routing decision: Command(update={...}, goto="b"). The alternative to a conditional edge. Use it when the node already knows where to go — it avoids a second function that re-derives the decision.
Command(graph=Command.PARENT) Routes to a node in the parent graph from inside a subgraph. The mechanism behind multi-agent handoffs.
Send Send("node", payload) — dynamically fan out N copies of a node, each with its own payload. Map-reduce. The count is decided at runtime, so you cannot express it with static edges. Each Send payload is that node's state, not the parent state.
Subgraph A compiled graph used as a node inside another graph. Shares state by key name. If parent and child use different key names you must map them explicitly with a wrapper function.
Branch / fan-out Multiple nodes scheduled in the same superstep. They run concurrently and their writes are merged by reducers — which is exactly why concurrent writes to a non-reduced key raise InvalidUpdateError.

2. State and schemas

State schemaChannelReduceradd_messagesupdates in place when IDs matchAnnotated
Term What it is Why it exists / the gotcha
State schema A TypedDict, Pydantic model, or dataclass declaring the state's keys and types. Pydantic gives you runtime validation at node boundaries; TypedDict is faster and does not validate.
Channel The internal name for one key of state. Each has a type and an update rule. "Channel" is the word LangGraph internals and error messages use for a state key.
Reducer The merge function for a channel, declared as Annotated[list, operator.add]. Default is overwrite. Under parallelism, overwrite means one branch's work silently disappears.
add_messages The built-in reducer for message lists: appends, and updates in place when IDs match. The ID-matching behaviour is how you edit or delete a prior message rather than appending a duplicate.
Annotated The typing construct that attaches a reducer to a key. Annotated[list[str], operator.add] — the metadata slot is where the reducer lives.
Input / output schema Separate schemas narrowing what callers may pass in and what they see coming out. Keeps internal scratch keys out of your public contract.
Private state A schema used only between two specific nodes. Lets a node pass working data downstream without widening the shared state.
Context / context_schema Runtime data that is not state: user ID, tenant, DB handle, model choice (v0.6+, via Runtime). State is checkpointed and mutable; context is per-run and read-only. Putting a DB connection in state tries to serialise it and fails.
RunnableConfig The per-invocation dict carrying configurable (incl. thread_id), tags, metadata, recursion_limit, callbacks. thread_id lives in config["configurable"], not in state. Forgetting it with a checkpointer attached raises.

Key idea: state vs context vs config is a standing interview question. State = what the graph computes and checkpoints. Context = what the run needs but never changes (identity, dependencies). Config = how this particular invocation is wired (thread, limits, tracing).

3. Execution model

SuperstepnotPregel / BSPinvoke / ainvokestream / astreambatch
Term What it is Why it exists / the gotcha
Superstep One tick of the Pregel/BSP execution loop: run everything scheduled, merge writes, commit a checkpoint. State updates are not visible to peers within the same superstep — only in the next one.
Pregel / BSP The bulk-synchronous parallel model LangGraph implements. Explains the batching: it's a graph-processing model, not an event loop.
invoke / ainvoke Run to completion, return final state.
stream / astream Run and yield progress as it happens. See §7 for the modes.
batch Run many inputs concurrently. Each needs its own thread_id if checkpointing, or they share a conversation.
recursion_limit Max supersteps before GraphRecursionError (default 25). It is a circuit breaker, not a plan. Hitting it means the agent is looping — raising the number usually hides the bug.
GraphRecursionError Raised when the limit is hit. Catch it and return a degraded answer rather than a 500.
InvalidUpdateError Two parallel branches wrote the same key with no reducer. The fix is a reducer, not serialising the branches.
RetryPolicy Per-node retry config: attempts, backoff, which exceptions qualify. Retry the transient (429, 5xx, timeout). Retrying a validation error just burns budget.
CachePolicy Per-node result caching keyed on the node's input. Turns a re-run after a human edit from "call the model again" into a cache hit.
Durability mode How often state is persisted ("exit" / "async" / "sync"). The throughput-vs-safety dial. "sync" for anything with side effects you can't repeat.
Deferred node A node that waits for all inbound branches before running. The fan-in half of map-reduce; without it an aggregator can fire on the first arrival.
Node caching See CachePolicy. Cache key includes the node input, so a changed prompt correctly misses.

4. Persistence, memory, time travel

CheckpointerCheckpointthread_idcheckpoint_idMemorySaver / InMemorySaverSqliteSaver / PostgresSaver
Term What it is Why it exists / the gotcha
Checkpointer The persistence layer. Writes a checkpoint after every superstep. Without one, there is no memory, no HITL, no resume, no time travel. It is the single most load-bearing option.
Checkpoint An immutable snapshot: channel values, next nodes, metadata, parent pointer. Being a linked list of snapshots is what makes rewind possible.
thread_id The key identifying one conversation's checkpoint history. One thread_id = one conversation. Reusing it across users leaks context between them.
checkpoint_id Identifies one specific point within a thread. Pass it to replay from, or fork off, that exact moment.
MemorySaver / InMemorySaver In-process checkpointer. Development only. It dies with the process — the usual cause of "my agent forgot everything after deploy".
SqliteSaver / PostgresSaver Durable checkpointers. Postgres for production. Remember .setup() on first use to create tables.
get_state / StateSnapshot Read the current state of a thread, plus what's scheduled next. The debugging entry point: snapshot.next tells you where it's paused.
get_state_history Every checkpoint of a thread, newest first. The raw material for time travel.
update_state Write to a thread's state from outside the graph. How a human edit is applied before resuming. as_node= controls which reducer path the write takes.
Time travel Resume from an older checkpoint_id, optionally with edited state. Resuming from a past checkpoint forks the history rather than rewriting it.
Store (BaseStore) Long-term memory across threads, namespaced, optionally vector-searchable. Checkpointer = memory within a conversation. Store = memory across conversations. Conflating the two is the classic design error.
Namespace The tuple key partitioning the store, e.g. (user_id, "preferences"). Your tenancy boundary. Get it wrong and users read each other's memories.
Semantic / episodic / procedural memory Facts / past events / learned behaviour. Useful taxonomy for deciding what to persist and for how long.
Short-term vs long-term memory Message history in state vs facts in the store. Short-term is bounded by the context window; long-term is bounded by your retrieval quality.
•

5. Human-in-the-loop

interrupt()re-runs from the topCommand(resume=value)interrupt_before / interrupt_afterApproval gateDouble-texting
Term What it is Why it exists / the gotcha
interrupt() Called inside a node to pause and surface a payload to the caller (dynamic interrupt). The node re-runs from the top on resume. Any side effect before the interrupt() call happens twice — do them after.
Command(resume=value) Resumes an interrupted graph, delivering the human's answer as interrupt()'s return value. Invoke with this instead of a new input; passing new input starts a fresh turn.
interrupt_before / interrupt_after Static interrupts declared at compile time on named nodes. Good for a fixed approval gate; can't express "only pause when the amount exceeds £10k" — that needs interrupt().
Approval gate The pattern: pause before an irreversible tool, get a human decision, resume or reject. The standard answer to "how do you make an agent safe in production".
Double-texting The user sends a new message while a run is in flight. Four strategies: reject, enqueue, interrupt (keep work, start new), rollback (discard). A real product needs an explicit choice here.
Breakpoint Informal name for a static interrupt used while debugging. Combine with Studio to step through supersteps.

6. Tools and tool calling

Tool@tool
Term What it is Why it exists / the gotcha
Tool A typed function exposed to the model with a name, description, and argument schema. The description is the prompt. Vague descriptions are the top cause of wrong tool choice.
@tool The decorator that turns a function into a tool, inferring schema from type hints and docstring. Untyped **kwargs gives the model nothing to fill in correctly.
Function / tool calling The model emits a structured request to invoke a tool; it never executes anything. The security boundary: you decide whether to honour the call.
tool_call The structured request: {name, args, id}. The id is what pairs a result back to its request.
ToolMessage The result message, carrying tool_call_id. A missing or mismatched tool_call_id is a hard API error on the next model call.
ToolNode Prebuilt node that executes every tool call in the last AI message, in parallel. handle_tool_errors decides whether a raised exception becomes a ToolMessage the model can recover from, or crashes the graph.
tools_condition Prebuilt router: "tool calls present → tools node, else → END". The two-line version of the ReAct loop's branch.
Parallel tool calls One assistant turn requesting several tools at once. Every call needs its own ToolMessage before the next model call, or the conversation is malformed.
InjectedState / InjectedToolCallId Annotations that pass graph state (or the call ID) into a tool without exposing it in the model-visible schema. How a tool reads context it must not be able to hallucinate.
Structured output Forcing the model's final answer into a schema. Prefer native/strict schema modes over "please reply in JSON" — it removes a whole class of parse-retry cost.
Tool error handling Returning the error to the model as an observation instead of raising. Lets the agent self-correct. Cap it — an un-capped correction loop is an expensive infinite loop.

7. Streaming

stream_mode="values"stream_mode="updates"stream_mode="messages"stream_mode="custom"stream_mode="debug"astream_events
Term What it is
stream_mode="values" The full state after each superstep. Simplest; heaviest payload.
stream_mode="updates" Only the delta each node returned. What you want for a progress UI.
stream_mode="messages" LLM tokens as they're generated, with metadata. What users perceive as "it's typing".

StreamWriter The injected callable a node uses to push custom stream items.

9. Multi-agent

HandoffSupervisorSwarmHierarchicalNetworkOrchestrator-worker
Term What it is Why it exists / the gotcha
Handoff One agent transferring control (and context) to another, usually via Command(goto=..., graph=Command.PARENT). What gets handed over is the design decision: full history is expensive, a summary loses detail.
Supervisor A central router agent that picks which specialist runs next. Easiest to reason about and to evaluate. The default choice.
Swarm Peer agents that hand off directly, no central router. Fewer hops, harder to trace and to bound.
Hierarchical Supervisors of supervisors. For genuinely large tool inventories; adds a full LLM call per level.
Network Any-to-any communication. Maximum flexibility, minimum predictability. Rarely the right production answer.
Orchestrator-worker An orchestrator decomposes a task and fans work out to workers. Distinct from supervisor: it plans and splits, rather than routes turn by turn.
Shared vs private state Whether sub-agents read the same state object or their own. Shared is simpler; private prevents one agent's scratch work from polluting another's context.
Agent-as-tool Wrapping a whole agent as a callable tool of another agent. The simplest multi-agent topology, and often sufficient.

Warning: the honest interview answer is that one well-instrumented agent beats a multi-agent system for most problems. Multi-agent multiplies cost, latency and failure surface; reach for it when tool count or context genuinely won't fit in one agent.

11. Failure vocabulary

Loop / oscillationThrashingContext rotLost in the middleTool-output injectionDeadlock / stuck state
Term What it is The tell
Loop / oscillation The agent repeats a step or alternates between two forever. recursion_limit hit; the same tool call twice with identical args.
Thrashing Repeatedly retrieving without making progress. Rising step count, flat answer quality.
Context rot Quality degrading as history grows, even inside the window limit. Late-conversation answers contradict early ones.
Lost in the middle Facts in the middle of a long context get ignored. Moving the same fact to the end fixes the answer.
Tool-output injection Retrieved or tool-returned text carrying instructions the model obeys. Treat every tool result as untrusted input. This is the top agentic security issue.
Deadlock / stuck state Nothing is schedulable but the graph hasn't ended. Usually a conditional edge that returns a name with no path onward.
Cascading retry Retries at several layers multiplying. One 3× retry under another 3× retry is 9 calls. Retry at exactly one layer.
Silent truncation History trimmed mid-conversation without anyone noticing. Answers stop referencing things the user said earlier.

13. The disambiguations interviewers actually probe

LangChain vs LangGraphWorkflow vs agentCheckpointer vs storeState vs context vs configConditional edge vs Commandinterrupt_before vs interrupt()
Pair The distinction in one line
LangChain vs LangGraph LangChain composes straight-line pipelines; LangGraph adds loops, branches, state and pauses. Need a cycle → LangGraph.
Workflow vs agent Workflow = developer fixed the path. Agent = LLM picks the path at runtime.
Checkpointer vs store Checkpointer remembers this thread. Store remembers this user, across threads.
State vs context vs config Computed and persisted / read-only run dependencies / how this invocation is wired.
Conditional edge vs Command Edge = a separate router function decides. Command = the node itself decides while returning its update.
interrupt_before vs interrupt() Static, always pauses at a node / dynamic, pauses only when your condition fires.
Subgraph vs Send Subgraph = one reusable composed unit. Send = N dynamic copies of one node.
Node retry vs agent retry RetryPolicy re-runs the function on a transient error. Agent retry feeds the error back to the model to decide.
MemorySaver vs PostgresSaver Dev, dies with the process / production, survives restarts and scales across workers.
stream_mode messages vs updates Tokens for the user / node deltas for your logs and progress UI.
Fan-out edges vs Send Static, count known at build time / dynamic, count decided from state.
Reducer vs overwrite Merge concurrent writes / last write wins and the other branch's work is lost.
