Q1: A 40-step workflow fails at step 30. How do you resume without rerunning the first 29?

durable executionPersist state after every stepOn restart, replay the journalTemporalAWS Step FunctionsAirflow

A: You need durable execution — the workflow's progress must survive a process crash. Two ingredients:

  1. Persist state after every step, not just at the end. Each step writes its output (and the fact that it completed) to a store keyed by a stable run_id.
  2. On restart, replay the journalskip any step whose output already exists, resume at the first incomplete step. 
def run_workflow(run_id, steps, store):
    state = store.load(run_id)            # {} on first run, partial on resume
    for i, step in enumerate(steps):
        if f"step_{i}" in state:          # already done -> skip, no recompute
            continue
        state[f"step_{i}"] = step(state)  # run it
        store.save(run_id, state)         # checkpoint BEFORE moving on
    return state

The store can be Postgres, Redis, or S3. Frameworks that give you this for free: Temporal, AWS Step Functions, Airflow (per-task state), and LangGraph checkpointers. The key property is that each step is replayable — given the saved inputs, re-running it produces the same effect (see [[idempotency]]).

Key takeaway: Checkpoint after every step keyed by a stable run_id; on resume, skip completed steps and continue from the first gap. Don't checkpoint only at the end.

Q2: A workflow crashes after generating the answer but before saving it to the DB. How do you prevent duplicate processing?

idempotencyIdempotency key + upsertDedup table / processed-setTransactional outboxsame DB transactionKey takeaway

A: This is the classic "did my write happen?" problem. The fix is idempotency so that re-running the step is safe:

  • Idempotency key + upsert. Derive a deterministic key for the unit of work (e.g. hash(input_id + step_name)) and write with INSERT ... ON CONFLICT DO NOTHING (Postgres) / conditional put. Re-processing simply overwrites or no-ops instead of creating a duplicate row.
  • Dedup table / processed-set. Before doing expensive work, check "have I already recorded a result for this key?" If yes, return the stored result.
  • Transactional outbox. Write the answer and a "completed" marker in the same DB transaction, so either both land or neither does. The side-effect (e.g. publishing) is driven from the committed outbox row.
def save_answer(conn, input_id, answer):
    conn.execute(
        """INSERT INTO answers (input_id, answer, created_at)
           VALUES (%s, %s, now())
           ON CONFLICT (input_id) DO NOTHING""",  # idempotent
        (input_id, answer),
    )

Key takeaway: Make the save idempotent with a deterministic key + upsert, or bind the write and the "done" marker into one transaction. Then a retry after a crash can't create duplicates.

Q3: A workflow is stuck in an infinite retry loop. How do you detect and stop it?

non-retryable errorDetectattempt counterStop / preventBounded retriesexponential backoff + jitter

A: Infinite retries usually mean retrying a non-retryable error (bad input, 4xx, logic bug) as if it were transient.

Detect: - Per-run attempt counter persisted with the state; alert when attempts > N. - Metrics: a retry-rate spike or a run whose age >> expected_duration. - Logs: same error signature repeating with no progress.

Stop / prevent: - Bounded retries (e.g. max 5) with exponential backoff + jitter. - Classify errors: retry only transient ones (429, 503, timeouts); fail fast on 4xx/validation errors. - Circuit breaker: after K consecutive failures, open the circuit and stop hammering the dependency. - Dead Letter Queue: after max retries, route the item to a DLQ for human inspection instead of looping (see [[dead-letter-queue]]).

import random, time

def with_retry(fn, max_attempts=5, base=0.5, cap=30):
    for attempt in range(max_attempts):
        try:
            return fn()
        except RetryableError as e:
            if attempt == max_attempts - 1:
                send_to_dlq(e); raise         # stop the loop
            sleep = min(cap, base * 2 ** attempt) + random.uniform(0, 0.5)
            time.sleep(sleep)                 # backoff + jitter
        except FatalError:
            raise                             # never retry these

Key takeaway: Cap retries, back off exponentially with jitter, distinguish retryable vs fatal errors, and dump exhausted items into a DLQ. An unbounded retry without error classification is the root cause.

Q4: How do you implement checkpointing for a multi-step agent?

Define explicit stateAfter each node completesResumeidempotent

A: A checkpoint is a serializable snapshot of everything needed to resume: current node/step, accumulated state (messages, scratchpad, tool results), and a pointer to "what runs next."

Design: 1. Define explicit state (a dataclass / TypedDict / Pydantic model) — never rely on in-memory locals. 2. After each node completes, serialize state → store under (thread_id, step_seq). 3. Resume by loading the latest checkpoint for thread_id and dispatching to the next node. 4. Keep step transitions idempotent so a replayed step is safe.

@dataclass
class AgentState:
    thread_id: str
    step: int
    messages: list
    tool_results: dict

def checkpoint(store, state: AgentState):
    store.put(f"{state.thread_id}:{state.step}", asdict(state))

def resume(store, thread_id) -> AgentState:
    latest = store.latest(thread_id)
    return AgentState(**latest) if latest else AgentState(thread_id, 0, [], {})

LangGraph implements exactly this with Checkpointer (Memory / SQLite / Postgres) keyed by thread_id (see [[langgraph-checkpoint]], Q48–Q49).

Key takeaway: Make state explicit and serializable, snapshot it after every node keyed by thread_id, and resume by loading the latest snapshot. Keep steps idempotent.

Q5: What happens if the checkpoint database itself goes down?

Fail safe, not silentnotMake the DB highly availableBuffer + retryDegrade gracefullySeparate from the app DB

A: Your durability layer becoming unavailable is a real failure mode — handle it deliberately:

  • Fail safe, not silent. If a checkpoint write fails, do not advance to the next step pretending it saved. Either block/retry the write, or stop the run so it can resume cleanly later. The dangerous bug is "step ran, checkpoint lost, side-effect repeats on resume."
  • Make the DB highly available. Replication + failover (e.g. Postgres primary/replica, managed multi-AZ). Treat the checkpoint store as Tier-1 infra.
  • Buffer + retry. Queue checkpoint writes locally and flush with backoff when the store recovers — acceptable only if steps are idempotent on replay.
  • Degrade gracefully. For non-critical flows, you may continue in-memory and lose resumability (accepting full re-run on crash); for critical flows, halt.
  • Separate from the app DB. Don't co-locate the checkpoint store with the main workload DB, or one outage takes out both.
  • Monitor it with health checks and alerting — checkpoint write latency/error rate is a first-class SLI.

Key takeaway: A down checkpoint store must cause a visible failure, never a silent skip. Make it HA, retry writes with backoff, and rely on step idempotency so a buffered/replayed checkpoint can't double-apply side-effects.

Q11: The retriever returns irrelevant documents. How do you debug it?

Inspect what's retrievedsame modelChunkingEmbedding quality / domain fitDistance metric & normalizationHybrid search

A: Walk the retrieval pipeline end-to-end and isolate the failing stage:

  1. Inspect what's retrieved. Log the query, the top-k chunks, and their scores. Eyeball relevance — is it totally off or almost right?
  2. Query vs. corpus embedding mismatch. Are query and documents embedded with the same model? A mismatch silently kills relevance (Q14).
  3. Chunking. Too-large chunks dilute the signal; too-small lose context. Check chunk size/overlap and whether chunks split mid-thought.
  4. Embedding quality / domain fit. Generic embeddings may miss domain jargon — consider a domain-tuned or stronger embedding model.
  5. Distance metric & normalization. Cosine vs. dot vs. L2 mismatch, unnormalized vectors.
  6. Hybrid search. Pure dense retrieval misses exact keywords (IDs, names) — add BM25/keyword and fuse (RRF).
  7. Reranker. Add a cross-encoder reranker over the top-50 to reorder by true relevance.
  8. Query transformation. Expand/rewrite vague queries; use HyDE or multi-query.
  9. Evaluate quantitatively. Build a labeled set and measure Recall@k / MRR / nDCG so changes are measurable, not vibes.

Key takeaway: Log retrieved chunks + scores first, then check embedding-model consistency, chunking, metric, and add hybrid search + a reranker. Measure with Recall@k/MRR rather than eyeballing.

Q12: Users say answers are hallucinated despite RAG. What could be wrong?

Retrieval failedContext present but ignoredonly"Lost in the middle."No abstention pathStale / wrong index

A: RAG only helps if the right context reaches the model and the model is forced to use it.

  • Retrieval failed (Q11): the relevant chunk isn't in context, so the model fills the gap from parametric memory. Most common cause — fix retrieval first.
  • Context present but ignored. The prompt doesn't instruct "answer only from the context; if not present, say you don't know." Add grounding instructions.
  • "Lost in the middle." Relevant chunk is buried; reorder so key context is at the start/end, and reduce context bloat.
  • No abstention path. The model is never allowed to say "not in the documents," so it guesses. Give it an explicit out.
  • Stale / wrong index. Outdated or low-quality source docs → confidently wrong answers.
  • No citation/verification. Require the model to cite chunk ids; post-check that the claim is supported (faithfulness/groundedness scoring, e.g. RAGAS).
  • Over-long answers beyond what context supports invite confabulation.

Key takeaway: Hallucination-despite-RAG is usually a retrieval miss or an ungrounded prompt. Verify the right chunk is retrieved, instruct "answer only from context, else abstain," require citations, and measure faithfulness.

Q13: Vector DB latency jumps from 50ms to 5s. What do you investigate?

Load & trafficIndex healthMemory pressureFilteringRecall/efficiency paramsNetwork / co-location

A: Systematic, from cheapest to deepest:

  1. Load & traffic. QPS spike? Larger k? Bigger query batches? Saturated CPU/RAM/IOPS on the DB nodes?
  2. Index health. Did the index fall back to a brute-force/flat scan? After heavy inserts, an ANN index (HNSW/IVF) may need rebuild/compaction; un-indexed new vectors get scanned linearly.
  3. Memory pressure. Index no longer fits in RAM → swapping to disk → latency cliff. Check resident set vs. index size.
  4. Filtering. Heavy metadata pre/post-filters can force scans; missing payload indexes.
  5. Recall/efficiency params. ef_search / nprobe raised? Replica removed so each node carries more?
  6. Network / co-location. App and DB in different AZs, DNS, connection-pool exhaustion, GC pauses.
  7. Background ops. Compaction, snapshotting, reindexing, or a concurrent bulk upsert competing for resources.
  8. Recent deploy. Correlate the latency change with the last index build, config change, or data load.

Key takeaway: Check traffic/load, then index health and whether it still fits in RAM (the classic 50ms→5s cliff is index spilling to disk or degrading to a flat scan), then filters/params/network. Correlate with the last data load or deploy.

Q14: How do you version embeddings when changing embedding models?

mustFull re-embedentire corpusPin the query pathDual-write / shadowoffline eval

A: Query and document embeddings must come from the same model — you cannot mix vector spaces. So a model change means a coordinated migration:

  1. Tag every vector with embedding_model + version in metadata (and ideally separate collections/namespaces per version).
  2. Full re-embed. A new model = a new vector space; re-embed the entire corpus into a new index. You cannot incrementally mix old and new vectors.
  3. Pin the query path. The query is embedded with the same model/version as the index it searches. Never query a v2 index with a v1 query embedding.
  4. Dual-write / shadow. Build the new index alongside the old, run offline eval (Recall@k, answer quality) on both, then cut over.
  5. Blue-green cutover with instant rollback to the old index if quality regresses (Q15).
  6. Track dimension/metric changesnew models often differ in dim and preferred distance.

Key takeaway: Treat an embedding-model change as a full re-index into a new versioned space; tag vectors with model+version, keep query and index on the same version, validate offline, and blue-green the cutover. Never mix vector spaces.

Q15: How do you reindex 100M documents without downtime?

New index, side by sideBackfill in batchesresumable/idempotentDual-write during backfillbothValidate

A: Build the new index alongside the live one, then atomically switch — never reindex in place.

  1. New index, side by side. Create index_v2; keep index_v1 serving all reads.
  2. Backfill in batches (parallel workers, rate-limited so you don't starve serving). Track progress; make it resumable/idempotent (Q1–Q2) so a crash mid-backfill continues, not restarts.
  3. Dual-write during backfill. New/updated docs are written to both v1 and v2 so v2 doesn't go stale while you backfill. (Or capture a CDC/change log and replay it after backfill.)
  4. Validate. Compare counts; run retrieval-quality eval on v2 vs v1.
  5. Atomic cutover. Flip an alias/pointer (e.g. an index alias or a config flag) from v1 → v2 in one step. Reads switch instantly.
  6. Keep v1 warm briefly for instant rollback, then decommission.

Key takeaway: Backfill a new index in resumable batches while dual-writing live updates, validate, then flip an alias atomically. The alias indirection is what gives you zero-downtime cutover and instant rollback.

Q46: An agent repeatedly calls the same tool forever. How do you stop it?

Max-iteration / recursion limitLoop / repetition detectionBetter tool feedbackForce progressHuman-in-the-loop / escalationKey takeaway

A: Agents loop when the result never satisfies the goal (or the model ignores it). Guardrails:

  1. Max-iteration / recursion limit. Hard cap on steps per run (LangGraph's recursion_limit); stop and return best-effort or escalate when hit. The essential safety net.
  2. Loop / repetition detection. Track recent (tool, args) calls; if the same call recurs with no state change, break out, return an error to the model, or force a different action.
  3. Step budget / cost budget / timeout per run.
  4. Better tool feedback. A clear, actionable result (incl. "this didn't work because…") helps the model stop repeating; a vague/empty result invites retries.
  5. Force progress. After N identical calls, inject a system message ("you already called X with Y and got Z — choose a different step or finish").
  6. Human-in-the-loop / escalation when budget is exhausted (Q50).
seen = collections.Counter()
def guard(tool, args, max_repeats=3, max_steps=25, step=0):
    if step >= max_steps:
        raise StepBudgetExceeded
    key = (tool, json.dumps(args, sort_keys=True))
    seen[key] += 1
    if seen[key] > max_repeats:                 # same call, no progress
        raise RepeatedToolCall(key)

Key takeaway: Always set a hard recursion/step limit, plus repeated-call detection that breaks the loop, plus budgets/timeouts. Improve tool feedback and inject a "you already tried this" nudge so the model changes course — and escalate to a human when budget runs out.

Q47: A tool returns invalid data. How should the agent react?

Validate at the tool boundaryBounded retryFallbackDon't hallucinate around itLog itKey takeaway

A: Don't feed garbage into the model or crash — handle it gracefully:

  1. Validate at the tool boundary. Schema-check the tool output (Pydantic). Catch exceptions inside the tool wrapper; never let a raw traceback bubble into the agent loop.
  2. Return a structured error to the model, not invalid data: {"error": "...", "hint": "..."}. The model can then retry differently, pick another tool, ask for clarification, or report it can't proceed.
  3. Bounded retry of the tool (transient failure) with backoff — but cap it (Q46) so it doesn't loop (Q3).
  4. Fallback. Alternate tool, default/cached value, or graceful degradation.
  5. Don't hallucinate around it. Instruct the agent: if the tool fails, say so / use the error — don't fabricate the result.
  6. Log it (Q42) for debugging the tool itself.

Key takeaway: Validate tool output at the boundary, convert failures into a structured error message the model can reason about (retry differently / pick another tool / abstain), cap retries, and never let invalid data or raw exceptions flow unchecked into the agent. The agent should react to a clear error, not garbage.

Q48: How do you checkpoint an agent with memory?

Define serializable statememoryCheckpointer keyed by thread_idSqliteSaver / PostgresSaverTwo memory tiersShort-term (thread/session)

A: Persist the agent's full state — including memory — so a thread can pause/crash/resume:

  1. Define serializable statemessage history, scratchpad, tool results, current node, plus memory (short-term conversation + any long-term store references).
  2. Checkpointer keyed by thread_id. After each node, persist a snapshot. LangGraph: pass a checkpointer (MemorySaver for dev; SqliteSaver / PostgresSaver for prod) and invoke with config={"configurable": {"thread_id": ...}}. State auto-persists per step.
  3. Two memory tiers:Short-term (thread/session): lives in the checkpoint — restored on resume so the conversation continues seamlessly. - Long-term (cross-session): an external store (vector DB / DB) the agent reads/writes; the checkpoint holds references/keys, not the whole store.
  4. Idempotent nodes so a resumed step doesn't double-apply effects (Q2).
  5. Time-travelversioned checkpoints let you inspect/replay/fork from any prior step (great for debugging).

Key takeaway: Use a durable checkpointer (Postgres/SQLite) keyed by thread_id that snapshots state after each node; keep short-term memory inside the checkpoint and long-term memory in an external store referenced by the checkpoint. Idempotent nodes make resume safe; versioned checkpoints enable time-travel debugging.

Q49: How do you resume an interrupted LangGraph execution?

checkpointerSame thread_idlatest checkpointInspect firstCrash recoveryHuman-in-the-loop interrupts

A: Resumption falls out of the checkpointer (Q48) — that's the whole point of it:

  1. Same thread_id. Re-invoke the graph with the same config={"configurable": {"thread_id": ...}}; LangGraph loads the latest checkpoint and continues from the next pending node — completed nodes aren't re-run.
  2. Inspect first with graph.get_state(config) to see where it stopped and the saved values; get_state_history to see all steps.
  3. Crash recovery: because state was persisted after each step, a fresh process/pod (Q29) resumes by just loading that thread_id.
  4. Human-in-the-loop interrupts: for an intentional pause (interrupt / interrupt_before), resume by calling the graph again (e.g. with Command(resume=...) / updated state) — it picks up at the interrupted node.
  5. Update-then-resume: you can update_state to correct/inject values before continuing (e.g. after human approval — Q50).
  6. Idempotency ensures the in-flight node re-running on resume is safe (Q2).

Key takeaway: Resume by re-invoking with the same thread_id — the checkpointer reloads the latest state and continues from the next pending node (skipping completed ones). Use get_state to inspect, update_state/Command(resume=...) for human-in-the-loop or corrections, and rely on idempotent nodes for safety.

Q50: How do you implement human approval before executing dangerous actions?

human-in-the-loop gateClassify dangerous actionsInterrupt + persistcheckpointSurface the proposed actionResume on decision

A: Insert a human-in-the-loop gate that pauses the workflow before the irreversible step and waits for a decision:

  1. Classify dangerous actions (delete, payment, send-email, prod change, large spend) and route them through an approval gate; safe actions proceed automatically.
  2. Interrupt + persist. Before executing, checkpoint and pause (LangGraph interrupt / interrupt_before on the tool node). State is durable (Q48) so the pause can last seconds or days across a process restart.
  3. Surface the proposed action to a human (UI/Slack/ticket) with full context: what, why, args, predicted effect.
  4. Resume on decision. Approve → continue and execute (Q49, Command(resume=...)). Reject → skip/abort and feed the rejection (with reason) back to the agent. Optionally allow edit of the args before approving.
  5. Constrain execution regardless: least-privilege, parameter validation, allow-lists (Q36) — approval complements, not replaces, guardrails.
  6. Audit every approval/rejection (who, when, what) and time-out stale approvals safely (default to not executing).
# pseudo-LangGraph: pause before the dangerous tool
graph.add_node("dangerous_action", execute_action)
app = graph.compile(checkpointer=saver, interrupt_before=["dangerous_action"])
# ... runs up to the gate, persists, and waits ...
state = app.get_state(cfg)                 # show proposed action to a human
if human_approves(state):
    app.invoke(Command(resume=True), cfg)  # approved -> execute
else:
    app.invoke(Command(resume=False), cfg) # rejected -> skip + inform agent

Key takeaway: Gate irreversible actions behind a durable interrupt: checkpoint and pause before execution, present the proposed action to a human, then resume (execute) on approve or skip on reject — with audit and a safe default (don't execute) on timeout. Pair approval with least-privilege execution; it complements guardrails rather than replacing them.

2. RAG & Agentic RAG

One-sentence idea: RAG grounds generation in retrieved evidence instead of relying on parametric memory; Agentic RAG goes further by letting the model decide whether/what/how many times to retrieve, evaluate what it got back, and act on that judgment — turning a fixed pipeline into a controllable loop.

Key Definitions (read first)

Term Plain-language definition
Chunking Splitting source docs into retrievable units; size/overlap trade recall against precision and context cost.
Hybrid search Combine sparse lexical search (BM25) with dense vector search, fused by rank (RRF) so exact-term matches and semantic matches both surface.
RRF (Reciprocal Rank Fusion) Merge multiple ranked lists by score = Σ 1/(k + rank_i), k≈60 — rank-based, so it doesn't need score calibration across retrievers.
MMR (Maximal Marginal Relevance) Re-rank/select to balance relevance to the query against redundancy with already-picked docs: argmax [λ·Sim(d,q) − (1−λ)·max Sim(d, d_selected)].
Reranking A second, more expensive cross-encoder pass over the top-N retrieved candidates to reorder by true relevance (bi-encoder retrieval is fast but coarser).
Agentic RAG The retrieval step is wrapped in agent reasoning: the model decides whether to retrieve, rewrites/decomposes the query, evaluates retrieved evidence, and can loop/re-retrieve or route to a different source.
Self-RAG The model is trained/prompted to emit reflection tokens judging its own retrieval and generation quality, deciding to retrieve more or revise.
Corrective RAG (CRAG) A lightweight retrieval evaluator grades retrieved docs; on low confidence, falls back to query rewriting + web search instead of generating from bad context.
GraphRAG Build a knowledge graph (entities + relations) from the corpus, retrieve by graph traversal/community summaries instead of (or alongside) vector similarity — better for multi-hop, "how are X and Y connected" questions.
HyDE (Hypothetical Document Embeddings) Have the LLM first generate a hypothetical answer, embed that, and search with it — the hypothetical answer is semantically closer to the target doc than the raw question is.

Vanilla RAG pipeline

ingest → chunk → embed → index → [query] → retrieve (hybrid) → rerank → assemble context → generate → post-process/cite

The failure mode this is judged on in interviews: naming where it breaks (chunk boundary cuts a fact in half, embedding model mismatch between query/doc domain, retrieval returns topically-similar-but-wrong-answer chunks, context window can't fit enough evidence, generation ignores retrieved context and hallucinates anyway). def reciprocal_rank_fusion(ranked_lists, k=60):
    scores = {}
    for ranked in ranked_lists:                 # e.g. [bm25_ranked_ids, dense_ranked_ids]
        for rank, doc_id in enumerate(ranked, start=1):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

def mmr(query_vec, doc_vecs, k=5, lam=0.5, sim=cosine_sim):
    selected, remaining = [], list(doc_vecs.keys())
    while remaining and len(selected) < k:
        def mmr_score(d):
            relevance = sim(query_vec, doc_vecs[d])
            redundancy = max((sim(doc_vecs[d], doc_vecs[s]) for s in selected), default=0)
            return lam * relevance - (1 - lam) * redundancy
        best = max(remaining, key=mmr_score)
        selected.append(best); remaining.remove(best)
    return selected

Why Agentic RAG, concretely

Vanilla RAG retrieves once, unconditionally, then generates — even when the query needs no retrieval, needs multiple retrievals against different sources, or the first retrieval is garbage. Agentic RAG wraps retrieval in a decision loop:

                         ┌────────────────────────────┐
 user query ──► Agent ──►│ decide: retrieve? which    │
                         │ source? rewrite query?     │
                         └─────────────┬──────────────┘
                                        ▼
                              retrieve (vector / SQL / web / graph)
                                        ▼
                              grade evidence (relevant? sufficient?)
                              ├── good enough ──► generate + cite
                              └── weak/irrelevant ──► rewrite query / try another source / retrieve again
                                                        (bounded retry count — never infinite)

Concrete Agentic-RAG behaviors worth naming in interview: - Query decomposition/routing — split a multi-part question into sub-queries, route each to the right index (product docs vs FAQs vs SQL database) instead of one flat vector search. - Retrieval grading (CRAG-style) — a cheap classifier/LLM call scores retrieved chunks as correct/ambiguous/incorrect before generation; ambiguous/incorrect triggers query rewrite + fallback retrieval (e.g., web search) rather than generating from weak context. - Iterative/multi-hop retrieval — for "how does A relate to B" questions, retrieve for A, extract what's needed, retrieve again for B using that context (can't be answered by one shot of top-k). - Self-critique (Self-RAG-style) — after drafting an answer, the model checks its own claims against the retrieved context and either fixes unsupported claims or re-retrieves. - Tool-augmented retrieval — the "index" isn't only a vector store; it can be a SQL query tool, an internal API, or live web search, chosen by the agent per sub-question.

Retrieval optimization — cutting latency without cutting recall

  • ANN index choice is the first lever. Exact k-NN is O(n) per query — fine at 10k vectors, dead at 100M. Approximate Nearest Neighbor indexes trade a small recall loss for large speedups:
  • HNSW (Hierarchical Navigable Small World) — graph-based, very fast/high-recall queries, but higher memory footprint and slower index build/updates — the default choice for most production vector DBs (Pinecone, Qdrant, Weaviate, pgvector).
  • IVF-PQ (Inverted File + Product Quantization) — clusters vectors, searches only nearby clusters, and compresses vectors (quantization) to shrink memory — better for very large, memory-constrained corpora, at some recall cost vs HNSW.
  • Flat/brute-forceexact, simplest, fine only for small corpora or as a reranking-stage exact pass over an already-small candidate set.
  • Quantized embeddings (int8/binary instead of float32) shrink index memory 4-32× and speed up distance computation, at a small, usually-acceptable recall cost — pair with a small exact-rerank pass on the top candidates to recover precision.
  • Result/embedding cachingcache embeddings for repeated/near-duplicate queries (semantic cache, §3) and cache full retrieval results for high-frequency queries (FAQ-style traffic) to skip the ANN search entirely on a hit.
  • Reduce round trips, not just per-call latencypre-filter with metadata (tenant/date/category) inside the ANN search (most vector DBs support filtered search) rather than retrieving broad-then-filtering in application code, which wastes both latency and top-k budget on results you'll discard.
  • Parallelize multi-source retrievalin agentic/hybrid RAG, fire the vector search, BM25 search, and any tool-based retrieval concurrently and fuse (RRF) once all return, instead of sequentially.
  • Rerank only a bounded candidate setcross-encoder rerank cost scales with N candidates; retrieve a modest top-N (e.g., 20-50), not top-500, before reranking — rerank latency is usually the second-biggest RAG latency line item after generation itself.

Validating a RAG system before and after it ships

  • Retrieval regression testsa fixed (query → expected relevant chunk IDs) set run on every index/embedding-model/chunking change; gate the change if Recall@k/MRR drops beyond a threshold, exactly like a unit-test suite (ties to §4's golden dataset).
  • Schema/citation validationif the generator is required to cite sources, validate at inference time that every citation ID actually exists in the retrieved set (a model can hallucinate a citation number that was never retrieved) — reject/regenerate on failure rather than surfacing a broken citation to the user.
  • Structured-output validationwhen the RAG answer must fit a schema (JSON fields, a specific answer format), validate against a Pydantic/JSON-schema contract post-generation, with a bounded auto-retry-with-error-feedback loop before falling back to a safe default — a form of the recovery ladder (file 23) applied to output shape, not just pipeline failures.
  • Shadow/canary rolloutrun a new retrieval config (new embedding model, new chunking) in shadow mode against production traffic (log its results, don't serve them) or canary it to a small traffic slice, comparing eval metrics (§4) and latency before full cutover — never swap a production RAG pipeline's retrieval config on eval-set performance alone.

Code — Agentic RAG / CRAG-style workflow in LangGraph

from typing import TypedDict
from langgraph.graph import StateGraph, END

class RAGState(TypedDict):
    question: str
    query: str
    docs: list[str]
    grade: str      # "good" | "weak"
    retries: int
    answer: str

def retrieve(state: RAGState) -> RAGState:
    state["docs"] = vector_store.similarity_search(state["query"], k=5)
    return state

def grade_documents(state: RAGState) -> RAGState:                 # CRAG-style evaluator, before generation
    verdicts = [llm_grade_relevance(state["question"], d) for d in state["docs"]]
    state["grade"] = "good" if sum(verdicts) / len(verdicts) >= 0.6 else "weak"
    return state

def rewrite_query(state: RAGState) -> RAGState:
    state["query"] = llm.rewrite(state["question"], reason="prior retrieval was weak")
    state["retries"] += 1
    return state

def generate(state: RAGState) -> RAGState:
    state["answer"] = llm.generate(state["question"], context=state["docs"])
    return state

def route_after_grade(state: RAGState) -> str:
    if state["grade"] == "good" or state["retries"] >= 2:          # bounded retry — never infinite (§2 Q8)
        return "generate"
    return "rewrite_query"

graph = StateGraph(RAGState)
graph.add_node("retrieve", retrieve)
graph.add_node("grade_documents", grade_documents)
graph.add_node("rewrite_query", rewrite_query)
graph.add_node("generate", generate)
graph.set_entry_point("retrieve")
graph.add_edge("retrieve", "grade_documents")
graph.add_conditional_edges("grade_documents", route_after_grade,
                             {"generate": "generate", "rewrite_query": "rewrite_query"})
graph.add_edge("rewrite_query", "retrieve")     # loop back and re-retrieve with the rewritten query
graph.add_edge("generate", END)
crag_app = graph.compile()

Q&A Drill

•

Q1. What's the actual difference between RAG and Agentic RAG?

RAG is a fixed pipeline: always retrieve top-k, always generate from it. Agentic RAG makes retrieval a decision the model reasons about — whether to retrieve, from which source, whether the evidence is good enough, and whether to loop — so it can skip retrieval for trivial queries, decompose multi-hop questions, and recover from bad first-pass retrieval instead of generating from it anyway.

•

Q2. Why hybrid search instead of pure dense retrieval?

Dense embeddings capture semantic similarity but are weak on exact matches — product SKUs, error codes, acronyms, rare proper nouns — where lexical (BM25) search wins. Hybrid fuses both ranked lists (typically via RRF) so you get semantic recall and exact-match precision.

•

Q3. Walk through RRF vs a naive score-average fusion.

Dense cosine similarity and BM25 scores live on incompatible scales, so averaging raw scores is meaningless without careful calibration. RRF sidesteps this entirely by fusing on rank position (1/(k+rank)), which is scale-free — a doc ranked #1 in either list gets a strong contribution regardless of what its raw score was.

•

Q4. When does MMR help and what's the failure mode it fixes?

When top-k retrieval returns several near-duplicate chunks (e.g., the same fact restated across five doc versions), MMR trades a bit of pure relevance to enforce diversity, so the LLM's limited context window gets more distinct evidence instead of five copies of the same sentence. λ near 1 = pure relevance (redundant), λ near 0 = pure diversity (may drift off-topic).

•

Q5. What's CRAG's evaluator step doing that vanilla RAG skips?

It scores retrieved documents for relevance before they reach the generator. If confidence is low, instead of blindly stuffing weak context into the prompt (and risking a hallucinated or wrong answer stated confidently), CRAG rewrites the query and/or falls back to an external source like web search.

•

Q6. How does HyDE improve retrieval, and what's its weakness?

It embeds a hypothetical LLM-generated answer instead of the raw question, because answer-shaped text is semantically closer to the target passages than question-shaped text — this helps on sparse/short queries. Weakness: if the LLM's hypothetical answer is confidently wrong, retrieval chases the wrong evidence entirely, and it adds an extra LLM call's latency/cost per query.

•

Q7. When would you reach for GraphRAG over vector RAG?

When questions are relational/multi-hop ("what products did customers who complained about X also buy?") rather than "find the passage most similar to this question" — vector similarity per-chunk can't answer questions that require traversing relationships across many documents; a knowledge graph with entity/relation extraction and community summaries can.

•

Q8. Why cap the retrieval-retry loop in agentic RAG?

Same reason you bound any agent loop — an evaluator that never says "good enough" (or a source that's genuinely missing the answer) causes infinite re-retrieval, burning cost/latency with no better outcome. Bound retries (e.g., max 2-3 rewrite/re-retrieve attempts), then degrade to "abstain" or hand off, per the recovery ladder in file 23.

•

Q9. Chunk size trade-off — how do you reason about it in an interview?

Small chunks → precise retrieval (less irrelevant text per chunk) but risk splitting a fact across chunk boundaries and losing context; large chunks → preserve context but dilute the embedding (a long chunk's vector represents an "average" of many ideas, hurting retrieval precision) and cost more tokens per retrieved item. Common mitigation: smaller chunks for indexing/retrieval, but expand to include neighboring chunks (parent-document / sentence-window retrieval) once a hit is found.

•

Q10. Reranking — why not just retrieve top-k with a cross-encoder directly and skip the bi-encoder step?

Cross-encoders score a (query, doc) pair jointly and are far more accurate, but they can't be pre-computed/indexed — you'd have to run one inference per document in the entire corpus per query, which doesn't scale. So: use a fast bi-encoder (pre-computed embeddings, ANN index) to get top-N candidates cheaply, then a cross-encoder reranks just those N — accuracy of cross-encoders at the cost of only N inferences.

•

Q11. HNSW vs IVF-PQ — how do you choose?

HNSW gives faster, higher-recall queries via a navigable graph but costs more memory and has slower index builds/updates — the default for most workloads that fit in memory. IVF-PQ clusters + compresses vectors, trading some recall for a much smaller memory footprint — reach for it when the corpus is too large to fit an HNSW graph affordably, and pair it with a small exact rerank pass to claw back precision.

•

Q12. How do you validate a new embedding model or chunking strategy before flipping production over to it?

Treat it like a code change: run it against a fixed retrieval regression set (Recall@k/MRR/nDCG against known-relevant chunk IDs) and the full Ragas/TruLens metric suite (§4) offline first; if it passes, roll it out via shadow mode (log results on live traffic without serving them) or a small canary slice, comparing both quality metrics and latency, before a full cutover — never swap it on offline eval-set performance alone.

3. LangChain & LangGraph — Orchestration, Memory, Performance, Scaling, Latency, Cost

One-sentence idea: LangChain gives you composable building blocks for LLM calls (LCEL chains, retrievers, output parsers); LangGraph gives you a stateful graph to orchestrate those blocks across cycles, branches, and multiple agents, with checkpointing that makes long-running, resumable, human-in-the-loop workflows possible. The interview-differentiating layer is everything around the framework calls: memory design, latency budget, horizontal scaling, and cost control.

Key Definitions (read first)

Term Plain-language definition
LCEL LangChain Expression Language — pipe (\|) composition of Runnables (prompt \| model \| parser) that's uniformly sync/async/streaming/batchable.
StateGraph LangGraph's core abstraction — a graph of nodes (functions) and edges (incl. conditional) that read/write a shared, typed state object.
Checkpointer Persists graph state after every step (e.g., to Postgres/Redis/SQLite) — enables pause/resume, time-travel debugging, and crash recovery ("durable execution").
Thread / short-term memory State scoped to one conversation/session, persisted via the checkpointer keyed by thread_id.
Store / long-term memory Cross-session memory (user facts, preferences) persisted independently of any one thread, retrieved by semantic search when relevant.
Human-in-the-loop (HITL) The graph can interrupt() before/after a node, wait for external approval/edits, then resume from the checkpoint.
Supervisor pattern One LLM node routes work to specialist worker nodes/agents and synthesizes their outputs; workers don't talk to each other directly.
Semantic cache Cache LLM responses keyed by embedding similarity of the prompt, not exact string match — catches paraphrased repeat queries.
Model routing/cascading Send easy queries to a cheap/small model, escalate to a larger model only when needed (confidence-based or complexity-based routing).

Orchestration

  • LCEL chainsbest for linear or lightly-branching pipelines: retrieve → format → prompt → generate. No cycles, no long-running state.
  • LangGraph StateGraphneeded once you have cycles (agent loops, retry-with-different-approach), conditional branching based on runtime state, multi-actor coordination, or durability (must survive a process restart mid-task). Nodes are plain functions; edges (including add_conditional_edges) route based on the state; the graph compiles to a runnable with automatic checkpointing.
  • Orchestrator vs Supervisor vs Swarm (see Orchestrator vs Supervisor for the deep dive): an orchestrator runs a mostly-fixed plan across workers; a supervisor is itself an LLM that dynamically decides which worker to call next and when to stop; a swarm/network lets agents hand off to each other directly without a central router — more flexible, harder to reason about/debug/bound cost.

Memory, concretely

short-term (thread-scoped)      → conversation buffer / running summary, keyed by thread_id,
                                   persisted by the checkpointer, restored automatically on resume
long-term (cross-session store) → semantic memory (facts about the user/domain), episodic memory
                                   (past interactions/outcomes), procedural memory (learned
                                   preferences/rules) — retrieved via similarity search and
                                   injected into context only when relevant, not dumped wholesale

Design rule interviewers probe: memory retrieval should look like RAG, not "load the whole history." Summarize/evict old turns from short-term memory past a token threshold; write salient facts out to long-term store instead of letting the window grow unbounded (this is context engineering, §1, applied to a running agent).

Performance / latency

  • Streamingstream tokens (and intermediate node outputs in LangGraph) to the client as they're produced; this doesn't reduce total latency but massively improves perceived latency (time-to-first-token vs time-to-full-response).
  • Async + parallel tool/branch executionindependent tool calls or independent graph branches (Send API in LangGraph) run concurrently instead of sequentially; the single biggest latency win in multi-tool agents.
  • Prefix/prompt cachinga static system prompt + tool schema prefix shared across calls gets cached server-side by the model provider, skipping re-processing of that prefix on every turn.
  • Semantic cachingcache full responses for semantically-repeated queries (FAQ-heavy workloads) to skip the LLM call entirely on a cache hit.
  • Reduce round tripsbatch tool calls in one LLM turn instead of one-tool-per-turn where the API supports parallel tool calling; avoid re-planning from scratch every loop iteration.

Latency optimization — the full request lifecycle

Treat latency as a budget spent across every hop, not one number to optimize at the model. Walking one agentic-RAG turn end to end, with the lever at each hop:

 hop                              latency lever
 ─────────────────────────────    ──────────────────────────────────────────────────
 client → API gateway              connection pooling / keep-alive, edge/CDN termination
 auth + guardrail input check      cheap, fast classifier — not a full LLM call
 context assembly (memory recall)  bounded-k memory search, not a full history scan
 retrieval (vector/hybrid)         ANN index (HNSW), filtered search, parallel multi-source fan-out (§2)
 rerank                            bound candidate set (top 20-50, not top-500) before cross-encoder
 LLM prefill (prompt processing)   prompt/prefix caching for the static system-prompt+tool-schema block

                                    accuracy bar, speculative decoding / continuous batching server-side

The single highest-leverage habit for an interview answer: name where in this chain the latency actually is (TTFT vs TPOT vs retrieval vs tool calls) before proposing a fix — "make it faster" without localizing the hop is the answer that loses points. Measure with per-hop tracing/spans (OpenTelemetry-style), not just end-to-end wall clock.

Scaling

  • Statelessness at the compute layerbecause LangGraph checkpointers externalize state (Postgres/Redis), the graph-executing workers themselves can be stateless and horizontally scaled behind a queue/load balancer; any worker can pick up any thread's next step.
  • Queueing & backpressurelong-running agent tasks go through a task queue (e.g., Celery/SQS-style) rather than holding an HTTP connection open; poll/webhook for completion.
  • Rate-limit handlingtoken-bucket client-side limiting + exponential backoff on 429s; multiple provider/model fallback chains so one provider's outage/limit doesn't stall the whole system.
  • Batchingfor offline/bulk workloads, batch APIs (async, higher latency, lower cost) instead of the synchronous endpoint.

Cost optimization

  • Model cascading/routingcheap model attempts first (or classifies difficulty), escalate to a frontier model only on low confidence or high-stakes steps.
  • Context pruningdon't re-send full tool-call history every turn; summarize or drop stale intermediate results once they're no longer decision-relevant.
  • Prompt compressionshorten static context (compress retrieved chunks, trim boilerplate) — every token in the system prompt is paid on every single call.
  • Cachingsemantic cache for repeat queries, provider-side prompt caching for the static prefix.
  • Right-size the loopcap agent steps/retries (a runaway loop is a cost incident, not just a latency one — see Agentic AI Failure Modes); use the smallest model that hits the accuracy bar for each sub-task rather than one frontier model for everything.
  • Token budgets per componentallocate a max-token budget to retrieved context, memory recall, and tool-output injection independently, so no one component can silently blow up the bill.

Validating a LangChain/LangGraph system

  • Structured-output/tool-call schema validationvalidate every tool call's arguments against its declared schema (Pydantic/JSON-schema) before execution — catches malformed args from the LLM before they hit a real API/side effect; on failure, feed the validation error back to the model for a bounded retry rather than executing blindly.
  • Graph-level contract testsfor a given input state, assert the graph reaches an expected terminal node / doesn't exceed N steps / doesn't call a forbidden tool — run as CI tests on every prompt or graph-topology change, the same discipline as unit tests for regular code.
  • Trajectory/behavioral regression seta fixed set of scenarios with expected tool-call sequences (or acceptable sequence classes, since exact-match is often too strict for LLM outputs) — catches "the agent still gets the right answer but now takes a wasteful/wrong path" regressions that output-only testing misses (ties to Agent Evaluation, Agent Evaluation).
  • Checkpoint replay / time-travel debuggingbecause LangGraph persists state at every step, a production failure can be replayed step-by-step from its checkpoint history to find exactly where behavior diverged — a validation/debugging capability plain stateless chains don't have.
  • Canary + shadow before promoting a prompt/model/graph changesame discipline as retrieval config changes (§2): shadow-run the new version on live traffic, compare quality + latency + cost metrics, canary a small slice, then promote — never a direct swap on an internal eval set alone.

Q&A Drill

•

Q1. When do you reach for LangGraph instead of a plain LCEL chain?

When the workflow needs cycles (agent retry loops), conditional branching on runtime state, multiple coordinating actors, or durability (must resume after a crash/interrupt) — LCEL chains are DAGs executed once through; they can't natively loop or pause mid-execution for human approval.

•

Q2. What does a checkpointer actually buy you in production?

Durable execution: state is persisted after every graph step, so a crashed process, a deploy, or a human-in-the-loop pause can resume exactly where it left off instead of restarting the whole task — plus "time travel" (replay from any past checkpoint) for debugging.

•

Q3. Explain short-term vs long-term memory in a LangGraph agent.

Short-term memory is thread-scoped conversational state (this session's messages/running summary), restored automatically via the checkpointer keyed by thread_id. Long-term memory is a separate store of durable facts/preferences that persists across sessions and is pulled in via semantic search only when relevant — treating memory recall as a retrieval problem, not "keep everything forever in context."

•

Q4. Your agent's latency is dominated by 4 sequential tool calls. What's the fix?

Check whether the tool calls are actually dependent; if independent, execute them concurrently (async/parallel tool execution, or LangGraph's Send API to fan out to parallel branches) instead of sequentially — this is usually the single biggest latency win before touching the model itself.

•

Q5. How do you horizontally scale a LangGraph-based agent service?

Externalize all state via the checkpointer (Postgres/Redis instead of in-memory), which makes the graph-executing workers stateless — any worker instance can pick up the next step for any thread, so you scale by adding workers behind a queue, with no sticky-session requirement.

•

Q6. Describe a model-cascading strategy for cost control.

Route each request first to a cheap/small model (or a lightweight classifier); if its confidence is high or the task is simple, return that answer, otherwise escalate to a larger/more capable model. Net effect: pay frontier-model prices only on the subset of traffic that actually needs it.

•

Q7. What's the difference between prompt caching and semantic caching?

Prompt/prefix caching is provider-side and exact-prefix-based — it skips re-computing the KV cache for a static prefix (system prompt, tool schemas) shared across calls, saving compute/cost but not correctness risk. Semantic caching is application-side and similarity-based — it returns a previously-computed response for a paraphrased-but-equivalent query, saving the entire LLM call but risking a stale/wrong-context answer if similarity matching is too loose.

•

Q8. Supervisor vs swarm — which would you pick for a client-facing agent and why?

Supervisor, in most production cases: a central router LLM decides which specialist to call and when to stop, which makes cost, latency, and behavior far easier to bound, log, and debug. Swarm (agents handing off directly) is more flexible/emergent but harder to guarantee termination, budget, or predictable behavior for — better suited to research/exploratory settings than a client-facing SLA.

•

Q9. How do you keep a multi-turn agent's context from growing unbounded across a long session?

Cap the raw message window (keep last K turns verbatim), summarize everything older into a running summary node, and move durable facts into long-term memory store instead of the live thread state — same "write/select/compress" moves as context engineering (§1), applied to LangGraph state.

•

Q10. What's interrupt() / human-in-the-loop for, concretely?

Pausing the graph before or after a sensitive node (e.g., "about to send this email" or "about to execute this trade") to get human approval/edits, then resuming from the exact checkpoint — critical for any agent with side effects in regulated or high-stakes domains (ties directly into the fraud-investigation agent pattern in §6).

•

Q11. A client asks "the agent feels slow" — how do you actually diagnose it instead of guessing?

Instrument per-hop tracing (retrieval, rerank, prefill, decode, each tool call) so you can see the latency budget broken down by hop instead of one wall-clock number. Common culprits, in likely-order: sequential tool calls that should be parallel, no prefix caching on a large static system prompt, an unbounded/unreranked top-k blowing up prefill size, or a frontier model used for a sub-task a smaller model could handle — fix the actual bottleneck the trace shows, not the first guess.

•

Q12. How do you validate a tool call before executing it, and why does that matter more in agents than in a normal API?

Validate the LLM-produced arguments against the tool's declared schema (types, required fields, value ranges) before execution, and on failure return the validation error to the model for a bounded retry instead of executing malformed/hallucinated arguments. It matters more here because, unlike a typed function call from application code, the caller (the LLM) can produce syntactically plausible but semantically wrong or malicious-shaped arguments — schema validation is the last deterministic gate before a side effect happens.

4. RAG Evaluation — Ragas, TruLens, Deep Eval, Data Eval

One-sentence idea: RAG has two failure surfaces — retrieval (did we find the right evidence?) and generation (did the model actually use it faithfully?) — and you need separate metrics for each, because a system can retrieve perfectly and still hallucinate, or retrieve badly and still "sound" right. Ragas and TruLens both operationalize this split with LLM-as-judge metrics; "deep evaluation" is layering human review, adversarial sets, and production online eval on top of the automated metrics; "data evaluation" is auditing the knowledge base itself, not just the pipeline's behavior on it.

Key Definitions (read first)

Term Plain-language definition
Context Precision Of the retrieved chunks, what fraction are actually relevant — and are the relevant ones ranked near the top?
Context Recall Of the ground-truth answer's claims, what fraction are actually supported by the retrieved context (did retrieval miss evidence)?
Faithfulness / Groundedness Of the claims in the generated answer, what fraction are actually supported by the retrieved context (is the model hallucinating on top of good retrieval)?
Answer Relevancy Does the generated answer actually address the question asked (not off-topic, not incomplete)?
Answer Correctness Does the generated answer match the ground-truth answer factually (needs a labeled reference answer)?
RAG Triad (TruLens) Context Relevance + Groundedness + Answer Relevance — three feedback functions that together localize where in the pipeline a bad answer came from.
LLM-as-judge Using a (usually stronger) LLM to score outputs against a rubric — scalable but needs its own validation against human labels to be trusted.
Golden/gold dataset A curated set of (question, ground-truth answer, ground-truth relevant chunks) used as the fixed yardstick for regression testing the pipeline over time.

Ragas — metrics and how they're actually computed

Ragas metrics are computed by decomposing text into atomic claims/statements via an LLM, then checking each claim against context or ground truth — not a single black-box "score":

  • Faithfulness = (# claims in the generated answer that are supported by the retrieved context) / (total # claims in the generated answer). The LLM first extracts claims from the answer, then for each claim asks "is this entailed by the context?" — a low score directly means hallucination, independent of whether retrieval was good.
  • Answer Relevancy = mean cosine similarity between the embedding of the original question and embeddings of several questions the LLM reverse-generates from the answer. If the answer is on-topic and complete, the reverse-engineered questions should closely match the original.
  • Context Precision = a precision-at-k style metric weighted by rank — for each retrieved chunk (LLM-judged relevant/irrelevant), it rewards relevant chunks appearing earlier in the ranked list, not just being present somewhere in top-k.
  • Context Recall = (# claims in the ground-truth answer attributable to the retrieved context) / (total # claims in the ground-truth answer) — this is the metric that tells you retrieval missed evidence, independent of what the generator did with what it got.
  • Context Entity Recall = overlap of named entities between retrieved context and the ground-truth answer — useful specifically for fact/entity-lookup-heavy domains.
  • Answer Semantic Similarity = embedding cosine similarity between the generated and reference answer (a soft, paraphrase-tolerant correctness proxy).
  • Answer Correctness = a weighted blend of factual overlap (TP/FP/FN of claims vs. ground truth) and semantic similarity — the most "did we get it right" metric, but needs labeled reference answers, unlike faithfulness/relevancy which are reference-free.

Ragas also ships a TestsetGenerator that synthesizes (question, ground-truth answer, source chunks) triples directly from your corpus using an LLM — solving the classic "we don't have a labeled eval set" bootstrap problem, including generating harder multi-hop/reasoning questions on purpose, not just simple lookups.

TruLens — the RAG Triad

                     ┌──────────────────┐
        query ──────►│ Context Relevance│──► is retrieved context relevant to the query?
                     └──────────────────┘
                              │
                              ▼
                     ┌──────────────────┐
     context ───────►│   Groundedness   │──► is the generated answer supported by that context?
     + answer         └─────────────────┘
                              │
                              ▼
                     ┌──────────────────┐
   answer + query ──►│ Answer Relevance │──► does the answer actually address the question?
                     └──────────────────┘

Why three separate scores instead of one: they localize the failure. - Context Relevance low → retrieval problem (wrong chunks fetched) — fix chunking/embeddings/hybrid search. - Context Relevance high, Groundedness low → generation problem — model ignored good context and hallucinated — fix the prompt's grounding instruction, or the model. - Groundedness high, Answer Relevance low → model faithfully summarized the context but didn't actually answer the question asked — fix instruction-following/prompt clarity.

TruLens is built more around continuous observability/tracing (feedback functions run automatically over logged production traces, with a dashboard) whereas Ragas leans more toward batch/offline test-set evaluation (you run it over a dataset and get aggregate scores) — in practice teams often use Ragas for pre-release regression testing and TruLens-style tracing for production monitoring.

Deep evaluation — going beyond the four headline metrics

  • Per-stage isolationevaluate retrieval-only (Recall@k, MRR, nDCG against a labeled relevant-chunk set) separately from generation-only (feed the generator the gold context and score faithfulness — isolates whether the generator itself is the weak link).
  • Adversarial/edge-case test setsdeliberately include out-of-scope questions (correct behavior: abstain), ambiguous questions, contradictory-context questions, and multi-hop questions — not just easy lookups; a system that scores 95% on easy questions can fail almost entirely on these.
  • Human-in-the-loop calibrationLLM-as-judge scores must be validated against a sample of human ratings periodically (judge drift, judge bias toward verbose answers, judge blind spots are real failure modes of the eval system itself).
  • Online vs offline evaluationoffline (Ragas-style, against a fixed golden set) catches regressions before release; online (production A/B testing, implicit signals like thumbs-down/regeneration rate, explicit user feedback) catches what the offline set didn't anticipate — both are needed, not either/or. See AB Testing and Experimentation.
  • Regression testing as a CI gaterun the golden set + metrics on every prompt/model/retrieval-config change; block deploys on metric drops, the same way you'd block on a failing unit test.

Data evaluation for RAG — auditing the knowledge base itself

This is the layer people skip: even a perfect pipeline can't answer well from a bad corpus. - Coverage — does the corpus actually contain the answer to the questions users ask? (Gap analysis: cluster unanswerable/low-score production queries, check if the source doc is missing entirely.) - Freshness — stale docs (old pricing, deprecated APIs) actively cause confidently wrong answers; need a re-ingestion/staleness-TTL policy, not just "eval once at launch." - Duplicate / near-duplicate chunks — redundant content wastes retrieval slots and can cause contradictory chunks (old vs new policy) to both surface, confusing the generator — dedup (exact + near-duplicate via embedding similarity threshold) during ingestion. - Chunk quality — chunks that cut a table, code block, or definition mid-way are a data problem, not a retrieval problem — audit a sample of actual chunks, not just the pipeline's downstream scores. - Label/gold-set quality — the golden dataset itself needs review; LLM-synthesized test questions can be too easy (near-verbatim from a chunk) or subtly wrong — spot-check a sample before trusting it as ground truth.

Q&A Drill

•

Q1. A RAG system's Ragas faithfulness score is low but context precision is high. What does that tell you, and where do you look?

Retrieval is doing its job (relevant chunks are being fetched), but the generator isn't using them faithfully — it's hallucinating on top of good evidence. Look at the generation prompt (is there a grounding instruction?), the model's tendency to over-elaborate beyond the given context, and whether the context was truncated before it reached the generator.

•

Q2. How is Ragas' Context Recall different from Context Precision, and why do you need both?

Precision asks "of what we retrieved, how much is relevant" (and ranked well); recall asks "of what's needed for the ground-truth answer, how much did we actually retrieve." A system can have perfect precision (every retrieved chunk relevant) but terrible recall (missed the one chunk with the actual answer) — you need both numbers to know if retrieval is too narrow or too noisy.

•

Q3. Why is Answer Relevancy computed by reverse-generating questions from the answer instead of just comparing answer to context?

Because relevancy is about the answer-question relationship, not the answer-context relationship (that's faithfulness's job) — if the LLM can regenerate questions from the answer that closely match the original question, the answer is on-topic and complete for what was actually asked.

•

Q4. Explain the RAG Triad and how you'd use it to debug a bad-answer report.

Score Context Relevance, Groundedness, and Answer Relevance independently for the failing example. Low context relevance → fix retrieval (chunking/embeddings/search). High context relevance but low groundedness → fix generation/prompting (model is ignoring good context). High groundedness but low answer relevance → the model answered faithfully from context but not the actual question — fix instruction clarity or query understanding.

•

Q5. What's the risk of relying purely on LLM-as-judge metrics like Ragas/TruLens without any human review?

Judge models have their own biases (favoring longer/more confident-sounding answers, blind spots on domains they're weak in, inconsistency across runs) and can drift from what humans actually consider correct — periodically sampling and human-validating a subset of judge scores is necessary to trust the automated numbers at all.

•

Q6. Retrieval-only vs end-to-end evaluation — why isolate them?

If you only measure end-to-end answer quality, a bad score could come from retrieval, generation, or both, and you can't tell which to fix. Feeding the generator the gold (known-correct) context and scoring faithfulness isolates the generator; scoring Recall@k/MRR against labeled relevant chunks isolates the retriever — you fix each independently before re-measuring end-to-end.

•

Q7. How would you build a golden evaluation set for a RAG system that has none yet?

Use an LLM-based synthetic generator (Ragas' TestsetGenerator or equivalent) to produce (question, ground-truth answer, source chunks) triples directly from the corpus — deliberately including simple, multi-hop, and out-of-scope/adversarial questions, not just easy ones — then human-spot-check a sample before trusting it as the regression baseline.

•

Q8. What is "data evaluation" for RAG, and how is it different from evaluating the pipeline?

Pipeline evaluation asks "given this corpus, did retrieval+generation do a good job?" Data evaluation asks "is the corpus itself good?" — coverage of real user questions, freshness/staleness, duplicate/near-duplicate chunks, and chunk-boundary quality. A perfectly-tuned pipeline over a stale or gapped corpus still fails; this audit catches that class of failure that behavioral metrics alone won't surface.

•

Q9. How do offline and online RAG evaluation complement each other?

Offline (Ragas-style golden-set scoring) is fast, repeatable, and catches regressions pre-deploy, but is bounded by what's in the golden set. Online (production monitoring/tracing à la TruLens, A/B testing, implicit signals like regeneration/thumbs-down rate) catches real-world query patterns the golden set never anticipated — ship gates should use offline, ongoing health should use online, and online failures should get folded back into the offline set.

•

Q10. Why can chunk deduplication meaningfully move your generation-quality metrics even though you didn't touch the generator or prompt?

Near-duplicate chunks (e.g., an old and new version of the same policy) can both surface in top-k, occupying retrieval slots that could've held genuinely different evidence, and can hand the generator contradictory context, directly hurting faithfulness/correctness — deduping at ingestion is a data-layer fix with a generation-layer payoff.

5. Multi-Agent Systems

One-sentence idea: Split a task across multiple specialized LLM "agents" instead of one monolithic prompt/agent when the task has naturally separable sub-skills, needs parallelism, or would otherwise overload a single agent's context/tool budget — but every agent you add is also a new coordination-failure surface, so it's a cost/complexity trade, not a free win.

Key Definitions (read first)

Term Plain-language definition
Supervisor / orchestrator-worker A router agent decides which specialist to call next and synthesizes results; workers don't talk to each other.
Hierarchical Supervisors-of-supervisors — a top-level agent delegates to mid-level supervisors, each managing their own worker agents (scales the supervisor pattern to large agent counts).
Network / swarm Agents can hand off directly to any other agent (peer-to-peer), no fixed central router — most flexible, least controllable.
Sequential pipeline Fixed order: Agent A's output is Agent B's input is Agent C's input — simplest topology, no dynamic routing needed.
Blackboard pattern Agents read/write to a shared state/workspace rather than passing messages directly to each other — decouples agents from knowing who else exists.
Handoff One agent explicitly transfers control (and optionally context) to another agent/tool, as a first-class action.
Trajectory evaluation Scoring how a multi-agent system reached its answer (which agents were invoked, in what order, with what tool calls) — not just the final output.

Why multi-agent instead of one bigger agent

  • Context isolationone agent doing research + coding + review accumulates a huge, noisy shared context; splitting into specialists means each agent's context stays small and relevant to its sub-task (directly the "isolate" move from context engineering, §1).
  • Tool/permission scopinga "read-only research agent" and a "code-execution agent" can have genuinely different tool access — least-privilege by construction, not by convention.
  • Specializationdifferent sub-tasks can use different models/prompts tuned to them (a cheap fast model for classification/routing, an expensive reasoning model only for the hard sub-task) — a cost lever too (§3).
  • Parallelismindependent sub-tasks (research 3 unrelated topics) can run concurrently across agents instead of one agent doing them serially.

The trade-off to always name back: more agents = more coordination overhead, more places for errors to compound, harder to debug/trace, and no free accuracy — a well-scoped single agent often beats a poorly-decomposed multi-agent system.

Topologies, compared

Sequential:     A ──► B ──► C ──► done          simple, predictable, no dynamic routing, brittle to
                                                  unexpected sub-task order

                Sup ──► ┼── worker 2 ──┼──► Sup synthesizes   bounded, debuggable, central bottleneck
                        └── worker 3 ──┘                      /cost-controllable, single point of failure

                        └► MidSup B ──► workers                adds latency (multiple routing hops)

                                                                 cost/termination/predictability

Coordination failure modes (what an interviewer probes)

  • Redundant worktwo agents independently do the same sub-task because there's no shared state/plan (fix: blackboard/shared state, explicit task assignment).
  • Conflicting actionstwo agents write conflicting updates (e.g., both modify the same record) — fix: ownership boundaries, locking, or a single agent with write access while others only read/propose.
  • Error/hallucination compoundingagent B trusts agent A's (wrong) output as ground truth and builds on it, amplifying the error downstream — fix: verification steps between handoffs, a supervisor that spot-checks before synthesizing, not blind pass-through.
  • Runaway delegation loopsA hands off to B, B hands off back to A, indefinitely — fix: max-hop budgets, cycle detection, same recovery-ladder discipline as single-agent loops (file 23).
  • Cost/latency multiplicationN agents each making LLM calls multiplies token spend and adds sequential-hop latency unless parallelized — must be budgeted explicitly, not discovered in the bill.

Frameworks, one line each

  • LangGraph multi-agentsupervisor/hierarchical/network patterns built from the same StateGraph primitive; state is explicit and typed, checkpointing/HITL work the same way as single-agent, Send API for fan-out/parallel workers.
  • AutoGenconversation-centric: agents are "conversable" and coordinate via a group-chat abstraction; strong for research/exploratory multi-agent dialogue.
  • CrewAIrole-based abstraction (agents have a role/goal/backstory, tasks are assigned to them) sitting on top of a mostly-sequential/hierarchical process — quick to set up for well-defined role pipelines.
  • OpenAI Agents SDK / Swarmlightweight handoff primitive: any agent can explicitly transfer control to another with context, minimal framework overhead, closer to the network/swarm topology.

Code — a LangGraph supervisor multi-agent workflow

from typing import TypedDict, Literal
from langgraph.graph import StateGraph, END
from langgraph.types import Command

MEMBERS = ["retrieval_agent", "risk_score_tool", "report_agent"]

class SupervisorState(TypedDict):
    messages: list


def supervisor(state: SupervisorState) -> Command[Literal[*MEMBERS, "__end__"]]:
    decision = llm_router.invoke(                                # supervisor LLM picks the next worker, or "done"
        f"Given the case so far, which agent should act next? Options: {MEMBERS + ['done']}"
    )
    if decision == "done":
        return Command(goto=END)
    return Command(goto=decision, update={"next": decision})     # explicit, logged handoff — bounded, auditable

def retrieval_agent(state: SupervisorState) -> Command[Literal["supervisor"]]:
    result = crag_app.invoke({"question": state["messages"][-1]})  # reuses the §2 agentic-RAG graph
    return Command(goto="supervisor", update={"messages": state["messages"] + [result["answer"]]})

def risk_score_tool(state: SupervisorState) -> Command[Literal["supervisor"]]:
    score = fraud_model.predict_proba(extract_features(state))    # deterministic ML call, NOT an LLM (§6 guardrail)
    return Command(goto="supervisor", update={"messages": state["messages"] + [f"risk_score={score}"]})

def report_agent(state: SupervisorState) -> Command[Literal["supervisor"]]:
    report = llm.draft_report(state["messages"])
    return Command(goto="supervisor", update={"messages": state["messages"] + [report]})

graph = StateGraph(SupervisorState)
for name, fn in [("supervisor", supervisor), ("retrieval_agent", retrieval_agent),
                  ("risk_score_tool", risk_score_tool), ("report_agent", report_agent)]:
    graph.add_node(name, fn)
graph.set_entry_point("supervisor")
supervisor_app = graph.compile()   # every worker hands control back to the supervisor — no redundant/conflicting work

Q&A Drill

•

Q1. When would you choose multi-agent over a single agent with more tools?

When sub-tasks need context isolation (each specialist's context stays small/focused instead of one bloated shared context), genuinely different tool/permission scopes, model specialization (cheap model for routing, expensive model only for the hard step), or parallelizable independent sub-tasks — not by default, since coordination overhead and debuggability get worse with every agent added.

•

Q2. Supervisor vs swarm/network topology — what's the real trade-off?

Supervisor centralizes routing through one agent, which makes cost, latency, and behavior bounded and auditable (you can log every routing decision), at the cost of a single bottleneck/point of failure and less flexibility for truly emergent collaboration. Swarm lets agents hand off freely, which is more flexible for open-ended collaboration but much harder to guarantee termination, cost bounds, or predictable behavior — riskier for a client-facing, SLA-bound system.

•

Q3. How do you prevent two agents from doing redundant or conflicting work?

Use a shared state/blackboard (so agents see what's already been claimed/done) with explicit task ownership, rather than isolated agents each independently deciding what to do; for writes specifically, restrict write access to one agent (or one at a time via locking) while others operate read-only or propose-only.

•

Q4. What's "error compounding" in a multi-agent pipeline, and how do you catch it?

A downstream agent treats an upstream agent's output as ground truth without verification, so an early mistake propagates and gets amplified rather than corrected. Catch it with verification/critique steps between handoffs (a supervisor or dedicated verifier agent spot-checks before passing forward) instead of blind sequential trust.

•

Q5. How is evaluating a multi-agent system different from evaluating a single LLM call?

You need trajectory evaluation, not just final-answer scoring — which agents were invoked, in what order, with what tool calls/arguments, and whether the path was efficient and correct, because a right final answer via a wasteful/wrong path (excess cost, wrong reasoning that happened to land right) is a latent risk that final-answer-only eval hides. See Agent Evaluation.

•

Q6. How do you bound cost in a multi-agent system with dynamic handoffs?

Cap total hops/agent-invocations per task, budget tokens per agent role, prefer a supervisor topology (centralized, loggable routing decisions) over free-form swarm handoffs for cost-sensitive production paths, and route cheap sub-tasks to cheap models within the multi-agent graph rather than one frontier model for every agent.

•

Q7. Give a concrete multi-agent design for a customer-support use case.

retrieval/RAG agentaccount-actions agentescalation agent

Supervisor agent classifies/routes the incoming request; a retrieval/RAG agent answers from the knowledge base for informational queries; an account-actions agent (scoped, tool-restricted) handles state-changing requests like refunds behind a human-approval interrupt; a escalation agent hands off to a human when confidence is low or the account-actions agent's tool calls fail repeatedly — bounded topology, clear ownership, HITL gate on anything with side effects.
