1. Architecture & Core Concepts

LangChain v0.3 is a modular Python framework for building applications powered by large language models. Its architecture is split into core packages (langchain-core for base abstractions, partner packages for provider-specific integrations, and langgraph for stateful agents), all unified by the Runnable interface and LCEL pipe syntax.

LANGCHAIN v0.3 ARCHITECTURE:
  ┌──────────────────────────────────────────────┐
  │  langchain           — high-level chains     │
  │  langchain-core      — LCEL, base interfaces │
  │  langchain-community — 3rd-party integrations│
  │  langchain-openai    — OpenAI-specific       │
  │  langchain-anthropic — Anthropic-specific    │
  │  langgraph           — stateful agents       │
  │  langsmith           — observability         │
  └──────────────────────────────────────────────┘
  
  KEY CONCEPTS:
  - Runnable: Base unit — anything with invoke/ainvoke/stream/astream
  - LCEL: Pipe syntax (|) to chain Runnables
  - Everything is a Runnable: Models, Prompts, Parsers, Retrievers, Tools
# pip install langchain langchain-openai langchain-community

from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

# Simplest chain: Prompt → Model → Parser
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful assistant."),
    ("human", "{question}"),
])

model = ChatOpenAI(model="gpt-4o", temperature=0)
parser = StrOutputParser()

chain = prompt | model | parser  # LCEL pipe syntax
result = chain.invoke({"question": "What is LangChain?"})

2. Chat Models & Providers

deprecatedRule of thumb

Chat models are the primary LLM interface in LangChain, wrapping provider-specific APIs (OpenAI, Anthropic, Google) behind a unified BaseChatModel abstraction. This allows swapping providers without changing application code, since all models share the same invoke/stream/batch interface.

from langchain_openai import ChatOpenAI
from langchain_anthropic import ChatAnthropic
from langchain_google_genai import ChatGoogleGenerativeAI

# OpenAI
gpt4o = ChatOpenAI(model="gpt-4o", temperature=0, max_tokens=4096)

# Anthropic
claude = ChatAnthropic(model="claude-sonnet-4-20250514", temperature=0)

# Google
gemini = ChatGoogleGenerativeAI(model="gemini-2.0-flash")

# All share the same interface:
response = gpt4o.invoke("Hello!")  # Returns AIMessage
response.content                    # String content
response.usage_metadata             # Token usage info

# Messages
from langchain_core.messages import SystemMessage, HumanMessage, AIMessage
messages = [
    SystemMessage(content="You are a Python expert."),
    HumanMessage(content="Explain decorators."),
]
response = gpt4o.invoke(messages)
# ── init_chat_model: provider-agnostic initializer (modern, preferred) ──
from langchain.chat_models import init_chat_model

llm = init_chat_model("gpt-4o", model_provider="openai", temperature=0)
llm = init_chat_model("claude-sonnet-4-20250514", model_provider="anthropic")
llm = init_chat_model("gemini-2.0-flash", model_provider="google_genai")
# provider is inferred from the name when unambiguous: init_chat_model("gpt-4o")

# Swap the model at RUNTIME without rebuilding the chain:
configurable = init_chat_model(configurable_fields=("model", "model_provider"))
configurable.invoke("hi", config={"configurable": {"model": "claude-sonnet-4-20250514",
                                                    "model_provider": "anthropic"}})
# → one entry point, any provider; ideal for A/B tests and multi-tenant model choice.

3. Prompt Templates

Prompt templates provide a structured, reusable way to construct prompts with variable substitution, message role management, and few-shot example injection. They ensure consistent formatting across calls and support dynamic example selection for better in-context learning.

from langchain_core.prompts import (
    ChatPromptTemplate, 
    FewShotChatMessagePromptTemplate,
    MessagesPlaceholder,
)

# ── Basic template ───────────────────────────────────────
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a {role} expert."),
    ("human", "{question}"),
])
prompt.invoke({"role": "Python", "question": "What are generators?"})

# ── With conversation history ────────────────────────────
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful assistant."),
    MessagesPlaceholder(variable_name="history"),
    ("human", "{input}"),
])

# ── Few-shot prompting ───────────────────────────────────
examples = [
    {"input": "2+2", "output": "4"},
    {"input": "3+3", "output": "6"},
]

example_prompt = ChatPromptTemplate.from_messages([
    ("human", "{input}"),
    ("ai", "{output}"),
])

few_shot = FewShotChatMessagePromptTemplate(
    example_prompt=example_prompt,
    examples=examples,
)

final_prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a calculator."),
    few_shot,
    ("human", "{input}"),
])

4. Output Parsers & Structured Output

Output parsers transform raw LLM text responses into structured Python objects such as Pydantic models, JSON, or enums. The preferred approach in LangChain v0.3 is model.with_structured_output(), which uses the model's native tool-calling or JSON mode for reliable schema-compliant responses.

from langchain_core.output_parsers import StrOutputParser, JsonOutputParser
from pydantic import BaseModel, Field

# ── Structured output (model.with_structured_output) ─────
class MovieReview(BaseModel):
    title: str = Field(description="Movie title")
    rating: float = Field(ge=1, le=10, description="Rating out of 10")
    summary: str = Field(description="Brief review summary")
    recommended: bool

structured_model = model.with_structured_output(MovieReview)
review = structured_model.invoke("Review the movie Inception")
print(review.title, review.rating)  # Typed Pydantic object

# ── JSON output parser ───────────────────────────────────
parser = JsonOutputParser(pydantic_object=MovieReview)
prompt = ChatPromptTemplate.from_messages([
    ("system", "Extract movie review info.\n{format_instructions}"),
    ("human", "{text}"),
])
chain = prompt.partial(format_instructions=parser.get_format_instructions()) | model | parser

# ── Enum / Literal constraints ────────────────────────────
from typing import Literal

class Sentiment(BaseModel):
    sentiment: Literal["positive", "negative", "neutral"]
    confidence: float = Field(ge=0, le=1)

classifier = model.with_structured_output(Sentiment)

Auto-correcting malformed output (fixing & retry parsers)

When a model returns text that doesn't match the schema, these parsers send the broken output (and error) back to an LLM to repair it — instead of raising.

from langchain.output_parsers import OutputFixingParser, RetryOutputParser
from langchain_core.output_parsers import PydanticOutputParser

base_parser = PydanticOutputParser(pydantic_object=MovieReview)

# OutputFixingParser: re-asks the LLM to fix output that failed to parse
fixing_parser = OutputFixingParser.from_llm(parser=base_parser, llm=model)

# RetryOutputParser: also re-sends the ORIGINAL prompt for better context
retry_parser = RetryOutputParser.from_llm(parser=base_parser, llm=model)

# Prefer with_structured_output() first (native tool-calling is most reliable);
# reach for fixing/retry parsers when forced to parse free-form text output.

5. LCEL

Intuitionsame methodseverykw)and addRunnableLambda

LCEL (LangChain Expression Language) is a declarative composition syntax that chains Runnables using the pipe (|) operator. It provides built-in streaming, async support, parallel execution, fallbacks, and automatic tracing — replacing the legacy LLMChain API with a more functional, composable pattern.

from langchain_core.runnables import (
    RunnablePassthrough, RunnableLambda, RunnableParallel, 
    RunnableBranch, chain as chain_decorator
)

# ── Pipe syntax (|) — compose Runnables ──────────────────
chain = prompt | model | parser

# ── RunnablePassthrough — pass input through ─────────────
chain = RunnableParallel(
    context=retriever,
    question=RunnablePassthrough(),
) | prompt | model | parser

# ── RunnableParallel — run multiple branches in parallel ──
chain = RunnableParallel(
    summary=summary_chain,
    translation=translation_chain,
    sentiment=sentiment_chain,
)
result = chain.invoke({"text": "..."})
# result = {"summary": ..., "translation": ..., "sentiment": ...}

# ── RunnableLambda — wrap any function ───────────────────
def format_docs(docs):
    return "\n\n".join(doc.page_content for doc in docs)

chain = retriever | RunnableLambda(format_docs) | prompt | model

# ── RunnableBranch — conditional routing ─────────────────
branch = RunnableBranch(
    (lambda x: "math" in x["topic"].lower(), math_chain),
    (lambda x: "code" in x["topic"].lower(), code_chain),
    general_chain,  # Default
)

# ── Fallbacks — retry with different model ───────────────
model_with_fallback = gpt4o.with_fallbacks([claude, gemini])
# If gpt4o fails, try claude, then gemini

# ── @chain decorator ─────────────────────────────────────
@chain_decorator
def my_chain(input: dict) -> str:
    if input["type"] == "question":
        return question_chain.invoke(input)
    return summary_chain.invoke(input)

5.1 The Runnable interface (the unifying contract)

Intuition: A Runnable is just "anything that takes one input and produces one output, and knows how to do it sync, async, streamed, and batched." Every LangChain building block — prompts, models, parsers, retrievers, tools, and whole chains — implements this one interface. Because they all speak the same protocol, the | pipe can glue any of them together. Think of it as the Iterable/Promise of LangChain: a small contract that everything agrees to.

Every Runnable gives you the same methods for free:

Method What it does Returns
invoke(input) Run once, sync single output
ainvoke(input) Run once, async awaitable output
batch([i1, i2, …]) Run many inputs in parallel (thread pool) list of outputs
abatch([...]) Async batch awaitable list
stream(input) Yield output incrementally sync generator of chunks
astream(input) Async incremental async generator
astream_events(input, version="v2") Stream every internal step (tokens, tool calls, retriever hits) async event stream

Plus composition helpers on every Runnable:

Helper Purpose
r1 \| r2 Pipe — feed output of r1 into r2 (builds a RunnableSequence)
.with_config(...) Attach tags / metadata / callbacks / run_name
.with_retry(...) Auto-retry on exceptions
.with_fallbacks([...]) Try backups if this one raises
.bind(**kwargs) Pre-fill call args (e.g. model.bind(stop=["\n"]))
.map() Apply the Runnable to each item of a list input
.configurable_fields(...) / .configurable_alternatives(...) Expose runtime-swappable params 
# Build your OWN Runnable from scratch — proves "everything is a Runnable"
from langchain_core.runnables import Runnable

class ShoutRunnable(Runnable):
    def invoke(self, input, config=None):
        return str(input).upper() + "!"

(ShoutRunnable() | RunnableLambda(lambda s: s[::-1])).invoke("hi")  # → "!IH"
# You only HAVE to implement invoke(); base class derives batch/stream/async from it.

5.2 Catalogue of built-in Runnable types

Runnable One-liner Typical use
RunnableSequence What a \| b \| c actually builds; runs steps in order every chain
RunnableParallel (a.k.a. RunnableMap) Run branches concurrently, return a dict of results fan-out: build a {context, question} dict
RunnablePassthrough Forward input unchanged keep the original input alongside computed values
RunnablePassthrough.assign(**kw) Pass input through and add new keys enrich a dict mid-chain without dropping existing keys
RunnableLambda Wrap any plain function as a Runnable custom glue / formatting (format_docs)
RunnableBranch if/elif/else routing to sub-chains route by topic/intent
RunnableWithMessageHistory Auto-load & save chat history around a chain conversational memory (see §10)
RunnableWithFallbacks Built by .with_fallbacks([...]) model/provider failover
RunnableRetry Built by .with_retry(...) transient error handling (see §17)
RunnableGenerator Wrap a generator fn for custom streaming transforms stream-process tokens yourself
RunnableConfigurableFields / …Alternatives Swap params/whole-Runnables at runtime via config A/B a temperature or swap models (see ConfigurableField, line ~980)
@chain decorator Turn a normal function into a Runnable imperative logic that still composes with \| 
from operator import itemgetter
from langchain_core.runnables import RunnablePassthrough, RunnableParallel

# ── .assign() — add keys while passing the rest through ───
enrich = RunnablePassthrough.assign(
    word_count=lambda x: len(x["text"].split())
)
enrich.invoke({"text": "a b c"})        # → {"text": "a b c", "word_count": 3}

# ── itemgetter — pull one key out of a dict input ────────
chain = (
    {"context": itemgetter("question") | retriever, "question": itemgetter("question")}
    | prompt | model | parser
)

# ── .map() — run a Runnable over a list ──────────────────
upper = RunnableLambda(str.upper)
upper.map().invoke(["a", "b", "c"])     # → ["A", "B", "C"]

# ── RunnableParallel == a plain dict literal in a pipe ───
# These two are equivalent — LangChain coerces dicts → RunnableParallel,
# and bare functions → RunnableLambda automatically inside a pipe:
chain_a = RunnableParallel(ctx=retriever, q=RunnablePassthrough())
chain_b = {"ctx": retriever, "q": RunnablePassthrough()}   # same thing

Mental model of auto-coercion inside |: a dict → RunnableParallel, a function → RunnableLambda. That's why {"context": retriever, "question": RunnablePassthrough()} | prompt | model "just works" without wrapping anything.

6. Chains

Chains are sequences of Runnables that connect prompts, models, parsers, and retrievers into end-to-end workflows. Common patterns include sequential chains (output of one step feeds the next), parallel chains (multiple branches run concurrently), and retrieval chains for RAG pipelines.

# ── Sequential chain (output of one → input of next) ────
analyze_chain = prompt1 | model | parser
improve_chain = prompt2 | model | parser

full_chain = (
    {"analysis": analyze_chain, "original": RunnablePassthrough()}
    | improve_chain
)

# ── Map-reduce pattern ───────────────────────────────────
from langchain.chains.combine_documents import create_stuff_documents_chain
from langchain.chains import create_retrieval_chain

# Stuff: Put all documents into one prompt (simple, limited by context)
# Map-reduce: Process each doc individually, then combine
# Refine: Iteratively refine answer with each doc

# ── Retrieval chain (RAG) ────────────────────────────────
retrieval_chain = create_retrieval_chain(retriever, combine_docs_chain)
result = retrieval_chain.invoke({"input": "What is LCEL?"})
print(result["answer"])

7. Tools & Tool Calling

Tools are functions that LLMs can invoke to interact with external systems — APIs, databases, search engines, or custom logic. LangChain's tool-calling mechanism lets models decide when and which tool to call via structured function schemas, enabling dynamic action-taking during inference.

from langchain_core.tools import tool
from langchain_community.tools import DuckDuckGoSearchRun

# ── Define custom tools ──────────────────────────────────
@tool
def calculate(expression: str) -> str:
    """Evaluate a mathematical expression safely."""
    return str(eval(expression))

@tool
def search_database(query: str, table: str = "products") -> list[dict]:
    """Search the database for matching records."""

    return results

# ── Bind tools to model ─────────────────────────────────
tools = [calculate, DuckDuckGoSearchRun()]
model_with_tools = model.bind_tools(tools)

# Model decides WHEN and WHICH tool to call
response = model_with_tools.invoke("What is 42 * 17?")
# response.tool_calls → [{"name": "calculate", "args": {"expression": "42 * 17"}}]

# ── Execute tool calls ──────────────────────────────────
from langchain_core.messages import ToolMessage

for tool_call in response.tool_calls:
    tool_fn = {"calculate": calculate, "duckduckgo_search": DuckDuckGoSearchRun()}[tool_call["name"]]
    result = tool_fn.invoke(tool_call["args"])
    tool_msg = ToolMessage(content=str(result), tool_call_id=tool_call["id"])

The full tool-calling loop (feed results back until done)

One round isn't enough — append the ToolMessages and re-invoke until the model stops asking for tools.

from langchain_core.messages import HumanMessage, ToolMessage

tool_map = {t.name: t for t in tools}
messages = [HumanMessage("What's 42*17, and search the latest LangChain news?")]

while True:
    ai = model_with_tools.invoke(messages)
    messages.append(ai)
    if not ai.tool_calls:               # no more tools → final answer
        break
    for tc in ai.tool_calls:            # may be MULTIPLE (parallel) calls in one turn
        out = tool_map[tc["name"]].invoke(tc["args"])
        messages.append(ToolMessage(content=str(out), tool_call_id=tc["id"]))
print(ai.content)

Agents are LLM-powered reasoning loops that dynamically decide which tools to call and when to stop, unlike chains which follow a fixed execution path. LangChain 1.0 — create_agent and middleware

LangChain 1.0 (Oct 2025) rebuilt the package around agents: create_agent is now the front door, and the old sprawl of chains/agent-executors is gone from the core namespace. What's genuinely new is middleware — a pipeline of hooks that runs around every model call and tool call, which is where production concerns (context trimming, HITL approval, PII scrubbing, fallbacks, call limits) now live instead of being hand-rolled into the loop.

from langchain.agents import create_agent

# ── Basic: same ReAct loop, new front door ────────────────
agent = create_agent(
    model="openai:gpt-4o",          # "provider:model" string or a model instance
    tools=[search, calculator],
    system_prompt="You are a research assistant. Always cite sources.",
)
agent.invoke({"messages": [("user", "What's 25 * 4?")]})
# It compiles to a LangGraph graph → checkpointer, streaming, HITL all work as in §8 above.

# ── Built-in middleware: production concerns as plug-ins ──
from langchain.agents.middleware import (
    SummarizationMiddleware,        # auto-summarize history when tokens exceed a budget
    HumanInTheLoopMiddleware,       # pause for approval before configured tools run
    PIIMiddleware,                  # detect/redact emails, phones, etc. in messages

    model="openai:gpt-4o",
    tools=[search, send_email],
    middleware=[
        PIIMiddleware("email", strategy="redact"),
        SummarizationMiddleware(model="openai:gpt-4o-mini", max_tokens_before_summary=4000),
        HumanInTheLoopMiddleware(interrupt_on={"send_email": True}),  # gate the dangerous tool

# ── Custom middleware: decorate a function with the hook you need ──
from langchain.agents.middleware import before_model, wrap_model_call

@before_model
def enforce_step_budget(state, runtime):
    if len(state["messages"]) > 40:                      # loop guard as middleware
        return {"jump_to": "end"}                        # short-circuit the agent
    return None                                          # None = continue unchanged

@wrap_model_call
def fallback_model(request, handler):
    try:
        return handler(request)                          # normal call
    except Exception:
        return handler(request.override(model=backup))   # swap model on failure

agent = create_agent(model="openai:gpt-4o", tools=tools,
                     middleware=[enforce_step_budget, fallback_model])
MIDDLEWARE HOOK POINTS (each middleware can implement any of these):
  before_agent  → once, before the run starts        (load memory, validate input)
  before_model  → every loop iteration, pre-LLM      (trim/summarize context, budgets)
  wrap_model_call  → around the LLM call             (retry, fallback, cache, rewrite)
  wrap_tool_call   → around each tool call           (approval, retry, sandboxing)
  after_model   → every iteration, post-LLM          (guardrails on the response)
  after_agent   → once, at the end                   (save memory, final validation)

How to think about it: middleware is to agents what LCEL decorators (with_retry, with_fallbacks) are to chains — cross-cutting behavior composed around the core loop instead of coded into it. Interview line: "create_agent = create_react_agent + a middleware pipeline where context engineering and safety live."

Also new in 1.0, one line each: content_blocks gives provider-agnostic access to message content (reasoning/citations/text typed uniformly across OpenAI/Anthropic/Google — no more provider-specific parsing), and langchain-classic is where anything legacy (old chains, AgentExecutor) moved if you still need it.

Agent patterns beyond ReAct — Reflection & Reflexion

create_react_agent gives you the ReAct loop (reason → act → observe). Two self-improvement patterns build on top of it when output quality matters:

Pattern Loop Learns across attempts? Use when
Reflection generate → critique → revise (critique stays in-context) ❌ one-shot polish improve a single answer (legal/creative/spec text)
Reflexion attempt → score → reflect → retry (lessons saved to episodic memory) ✅ "verbal RL" a hard, verifiable task (code/math/SQL) the agent keeps failing 
# ── Reflection (generate → critique → revise) ────────────
critic_prompt = ChatPromptTemplate.from_messages([
    ("system", "Critique the draft. Rate 1-5 and give SPECIFIC fixes. Say 'PERFECT' if done."),
    ("human", "Task: {task}\n\nDraft:\n{draft}"),
])
draft = (prompt | model | StrOutputParser()).invoke({"task": task})
for _ in range(3):                                   # hard cap — non-negotiable
    feedback = (critic_prompt | model | StrOutputParser()).invoke({"task": task, "draft": draft})
    if "PERFECT" in feedback.upper():
        break
    draft = (prompt | model | StrOutputParser()).invoke({"task": f"{task}\nFix per: {feedback}\nPrev:\n{draft}"})

# ── Reflexion = Reflection + a reward signal + memory across TRIALS ──
# The actor is usually a ReAct agent; an Evaluator scores each full attempt and a
# Self-Reflection step writes a verbal lesson into an episodic-memory buffer that is
# injected into the next trial. Learning happens in language, not weights.

Trimming history to fit the context window (trim_messages)

Long conversations eventually overflow the context window. trim_messages keeps the history within a token budget while preserving message-structure validity (e.g., keeping the system message, not splitting a tool call from its result).

from langchain_core.messages import trim_messages

trimmer = trim_messages(
    max_tokens=4000,
    strategy="last",            # keep the most RECENT messages
    token_counter=model,        # use the model's tokenizer to count
    include_system=True,        # always retain the system prompt
    start_on="human",           # ensure a valid message sequence
)

# Drop-in before the model in an LCEL chain
chain = trimmer | prompt | model
# For summary-style memory instead of dropping, summarize trimmed messages first.

Legacy Conversation Memory Classes (langchain.memory, deprecated)

Before RunnableWithMessageHistory, LangChain shipped a family of Memory classes that differ only in how much of the history gets replayed into the prompt each turn. They're deprecated but still asked about by name in interviews.

Class Strategy Trade-off
ConversationBufferMemory Stores the full raw history verbatim Simple, exact — but unbounded; eventually blows the context window
ConversationBufferWindowMemory Keeps only the last k turns (sliding window) Bounded size — but hard-forgets anything older than the window
ConversationSummaryMemory Makes an LLM call each turn to fold history into a running summary Flat token cost regardless of length — loses exact wording, costs an extra LLM call per turn
ConversationSummaryBufferMemory Verbatim buffer for recent messages + running summary once the buffer exceeds a token threshold Best of both — recent turns exact, older ones compressed. The most commonly used of the family
ConversationTokenBufferMemory Same idea as window memory, but the cutoff is measured in tokens, not turn-count Precise context-window control
ConversationKGMemory Extracts entities/facts ("user's name is Alice") into a structured knowledge graph instead of raw transcript Durable facts, not conversational flow
VectorStoreRetrieverMemory Embeds past exchanges into a vector store, retrieves only the semantically relevant ones each turn Scales to very long histories where relevance beats recency

Long-Term Memory Taxonomy: Semantic / Episodic / Procedural

A different axis entirely — this isn't about buffering mechanics, it's about what kind of long-term memory an agent keeps (from the CoALA paper, adopted by LangGraph's memory docs). LangGraph implements it with a cross-thread Store (long-term) that sits alongside the per-thread checkpointer (short-term, one conversation's state).

Type What it holds Analogue above
Semantic Facts about the user/world ("prefers Python", "manager is X") Entity memory (ConversationKGMemory) — a profile written to the Store
Episodic Specific past experiences/trajectories, replayed as few-shot examples so the agent learns from prior runs The Reflexion "lessons learned" buffer (§8)
Procedural How to do things — the agent's own rules/instructions The system prompt itself, sometimes rewritten by the agent over time

})

# Procedural: the agent updates its own instructions based on feedback

10. RAG Pipeline

Retrieval-Augmented Generation (RAG) enhances LLM responses by retrieving relevant documents from an external knowledge base and injecting them as context before generation. This pipeline involves loading documents, splitting them into chunks, embedding them into a vector store, retrieving the most relevant chunks at query time, and passing them to the LLM.

from langchain_community.document_loaders import PyPDFLoader, WebBaseLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings
from langchain_community.vectorstores import FAISS
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnablePassthrough

# ── Load documents ───────────────────────────────────────
loader = PyPDFLoader("report.pdf")
docs = loader.load()

# ── Split into chunks ───────────────────────────────────
splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,
    chunk_overlap=200,
    separators=["\n\n", "\n", ". ", " ", ""],
)
chunks = splitter.split_documents(docs)

# ── Create vector store ─────────────────────────────────
embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
vectorstore = FAISS.from_documents(chunks, embeddings)
retriever = vectorstore.as_retriever(search_kwargs={"k": 4})

# ── RAG chain ───────────────────────────────────────────
rag_prompt = ChatPromptTemplate.from_messages([
    ("system", "Answer based on context. If unsure, say so.\n\nContext:\n{context}"),
    ("human", "{question}"),
])

def format_docs(docs):
    return "\n\n".join(doc.page_content for doc in docs)

rag_chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | rag_prompt
    | model
    | StrOutputParser()
)

answer = rag_chain.invoke("What were the Q4 results?")

# ── Advanced retrieval ───────────────────────────────────
# Multi-query retriever (generates multiple queries for better recall)
from langchain.retrievers.multi_query import MultiQueryRetriever
multi_retriever = MultiQueryRetriever.from_llm(retriever, model)

# Ensemble retriever (combines BM25 + vector search)
from langchain.retrievers import EnsembleRetriever
from langchain_community.retrievers import BM25Retriever
bm25 = BM25Retriever.from_documents(chunks)
ensemble = EnsembleRetriever(retrievers=[bm25, retriever], weights=[0.4, 0.6])

# ── Cross-encoder reranking ───────────────────────────────
# After vector retrieval, rerank top-k docs using a cross-encoder for
# precision. Cross-encoders score (query, doc) jointly — much more
# accurate than cosine similarity but too slow to run on the full corpus.
# pip install sentence-transformers
from sentence_transformers import CrossEncoder
from langchain_core.documents import Document

reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")

def rerank_docs(query: str, docs: list[Document], top_n: int = 3) -> list[Document]:
    pairs = [(query, doc.page_content) for doc in docs]
    scores = reranker.predict(pairs)
    ranked = sorted(zip(scores, docs), key=lambda x: x[0], reverse=True)
    return [doc for _, doc in ranked[:top_n]]

# Drop into LCEL chain as a RunnableLambda
from langchain_core.runnables import RunnableLambda

rerank_step = RunnableLambda(lambda x: rerank_docs(x["question"], x["docs"]))

# Strips irrelevant passages from each retrieved doc before passing to LLM.
from langchain.retrievers.document_compressors import LLMChainExtractor

compressor = LLMChainExtractor.from_llm(model)
compression_retriever = ContextualCompressionRetriever(
    base_compressor=compressor,
    base_retriever=retriever,

# LLM translates natural language into both a semantic query AND metadata
# filters (e.g. "papers about RAG published after 2023").
from langchain.retrievers.self_query.base import SelfQueryRetriever

    AttributeInfo(name="source", description="Source document name", type="string"),
    AttributeInfo(name="year", description="Publication year", type="integer"),

    model, vectorstore,

Retriever search types (MMR & score threshold)

as_retriever() defaults to plain similarity. Two important alternatives:

# ── MMR: maximal marginal relevance — relevance AND diversity ──
# Stops you returning 4 near-duplicate chunks; balances similar vs. novel.
retriever = vectorstore.as_retriever(
    search_type="mmr",
    search_kwargs={"k": 4, "fetch_k": 20, "lambda_mult": 0.5},  # 0=diverse … 1=relevant
)

# ── Similarity score threshold — drop weak matches ─────────
retriever = vectorstore.as_retriever(
    search_type="similarity_score_threshold",
    search_kwargs={"score_threshold": 0.75, "k": 8},
)

# ── Metadata filtering at query time ──────────────────────
retriever = vectorstore.as_retriever(search_kwargs={"k": 4, "filter": {"year": 2024}})
VECTOR STORE PICKER:
  FAISS     — in-process, fast, no server; great for dev / prototyping
  Chroma    — local-first, easy persistence; good default for small apps
  pgvector  — reuse Postgres; SQL filters alongside vectors, transactional
  Pinecone  — managed, serverless scaling; production SaaS
  Qdrant / Weaviate / Milvus — self-host or cloud; rich filtering + hybrid search at scale

Beyond RecursiveCharacterTextSplitter 

# Token-based — align chunks to the model's tokenizer (not characters)
from langchain_text_splitters import TokenTextSplitter
TokenTextSplitter(chunk_size=512, chunk_overlap=50)

Incremental indexing & dedup (Indexing API + RecordManager)

Re-embedding the whole corpus on every sync is wasteful. The Indexing API tracks content hashes in a RecordManager, so unchanged docs are skipped and removed source docs are cleaned up — idempotent ingestion.

from langchain.indexes import SQLRecordManager, index

record_manager = SQLRecordManager("rag/main", db_url="sqlite:///rm.db")
record_manager.create_schema()

index(
    chunks, record_manager, vectorstore,
    cleanup="incremental",      # delete vectors whose source doc changed/was removed
    source_id_key="source",     # which metadata field identifies the source doc
)
# → {num_added, num_updated, num_skipped, num_deleted}. Re-running does near-zero work.

14. Security & Guardrails

Security guardrails protect LLM applications from prompt injection attacks, sensitive data leakage, and unsafe model outputs. Key techniques include input sanitization (regex-based filtering of injection patterns), output validation (PII detection, format checks), and constrained output schemas that limit what the model can return.

# ── Input sanitization ───────────────────────────────────
import re

def sanitize_input(text: str) -> str:
    """Remove potential prompt injection patterns."""
    # Remove attempts to override system prompt
    patterns = [
        r"ignore\s+(previous|above|all)\s+instructions",
        r"you\s+are\s+now",
        r"system\s*:\s*",
        r"<\|.*?\|>",
    ]
    for pattern in patterns:
        text = re.sub(pattern, "[FILTERED]", text, flags=re.IGNORECASE)
    return text

# ── Output validation ────────────────────────────────────
def validate_output(response: str) -> str:
    """Check model output for unsafe content."""
    # Check for PII leakage
    if re.search(r'\b\d{3}-\d{2}-\d{4}\b', response):  # SSN pattern
        return "[Response contained PII and was filtered]"
    return response

# ── Guardrails in chain ──────────────────────────────────
safe_chain = (
    RunnableLambda(sanitize_input)
    | prompt
    | model
    | StrOutputParser()
    | RunnableLambda(validate_output)
)

16. Custom Components

Custom components let you wrap proprietary or unsupported LLMs, embedding models, and data sources behind LangChain's standard interfaces. By subclassing BaseChatModel, Embeddings, or BaseRetriever, your custom implementations become fully compatible with LCEL, streaming, async, and all other LangChain features.

from langchain_core.language_models import BaseChatModel
from langchain_core.embeddings import Embeddings

# ── Custom LLM wrapper ──────────────────────────────────
import requests
from typing import Any, AsyncIterator, Iterator
from langchain_core.language_models import BaseChatModel
from langchain_core.messages import BaseMessage
from langchain_core.outputs import ChatGeneration, ChatGenerationChunk, ChatResult

class CustomLLM(BaseChatModel):
    """Wrap a proprietary API as a LangChain chat model."""
    api_url: str
    api_key: str

    @property
    def _llm_type(self) -> str:
        return "custom"

    def _generate(self, messages: list[BaseMessage], stop=None, **kwargs) -> ChatResult:
        payload = {"messages": [{"role": m.type, "content": m.content} for m in messages]}
        response = requests.post(self.api_url, json=payload,
                                  headers={"Authorization": f"Bearer {self.api_key}"})
        response.raise_for_status()
        text = response.json()["choices"][0]["message"]["content"]
        return ChatResult(generations=[ChatGeneration(message=AIMessage(content=text))])

    def _stream(self, messages: list[BaseMessage], stop=None, **kwargs) -> Iterator[ChatGenerationChunk]:
        """Sync streaming — yield token chunks one by one."""
        payload = {"messages": [{"role": m.type, "content": m.content} for m in messages],
                   "stream": True}
        with requests.post(self.api_url, json=payload, stream=True,
                           headers={"Authorization": f"Bearer {self.api_key}"}) as r:
            for line in r.iter_lines():
                if line:
                    token = line.decode().strip()
                    yield ChatGenerationChunk(message=AIMessageChunk(content=token))

    async def _astream(self, messages: list[BaseMessage], stop=None, **kwargs) -> AsyncIterator[ChatGenerationChunk]:
        """Async streaming — required for astream / astream_events support."""
        import aiohttp
        payload = {"messages": [{"role": m.type, "content": m.content} for m in messages],
                   "stream": True}
        async with aiohttp.ClientSession() as session:
            async with session.post(self.api_url, json=payload,
                                    headers={"Authorization": f"Bearer {self.api_key}"}) as resp:
                async for line in resp.content:
                    token = line.decode().strip()
                    if token:
                        yield ChatGenerationChunk(message=AIMessageChunk(content=token))

class CustomEmbeddings(Embeddings):

        return [self._embed(text) for text in texts]

    def embed_query(self, text: str) -> list[float]:

        # Replace with your model inference (e.g. sentence-transformers)

19. Error Handling, Fallbacks & Retries

Production LangChain apps must handle LLM failures gracefully. with_fallbacks() chains backup models, with_retry() retries on transient errors, and RunnableLambda catches exceptions within chains.

from langchain_openai import ChatOpenAI
from langchain_anthropic import ChatAnthropic

# Fallback: try GPT-4o, fall back to Claude on failure
primary = ChatOpenAI(model="gpt-4o")
fallback = ChatAnthropic(model="claude-sonnet-4-20250514")
llm = primary.with_fallbacks([fallback])

# Retry: retry up to 3 times on rate limit / timeout
llm_retry = ChatOpenAI(model="gpt-4o").with_retry(
    stop_after_attempt=3,
    wait_exponential_jitter=True
)

# Exception handling in chains
from langchain_core.runnables import RunnableLambda

def safe_parse(text):
    try:
        return json.loads(text)

        return {"error": "Failed to parse", "raw": text}

20. Interview Deep Dive

IngestionRetrievalGenerationEvaluationProductionChains

Q1: What is LCEL and why was it introduced?

A: LCEL (LangChain Expression Language) is a declarative way to compose LangChain components using the pipe (|) operator. Every component is a Runnable with a standard interface: invoke, ainvoke, stream, astream, batch. Benefits: (1) Streaming support by default — first token appears immediately. (2) Async support — same chain works sync and async. (3) Parallel execution — RunnableParallel runs branches concurrently. (4) Retry/fallback built-in. (5) LangSmith tracing automatic. It replaced the old LLMChain/SequentialChain API with a more composable, functional approach.

Q2: How would you build a production RAG system with LangChain?

A: (1) Ingestion: Load docs (PyPDFLoader/WebBaseLoader), split with RecursiveCharacterTextSplitter (1000 chunk, 200 overlap), embed with text-embedding-3-small, store in FAISS/Pinecone. (2) Retrieval: Use ensemble retriever (BM25 + vector) for hybrid search. Apply multi-query retriever for query expansion. Re-rank with cross-encoder. (3) Generation: RAG prompt with context + question → GPT-4o → structured output. (4) Evaluation: RAGAS metrics (faithfulness, answer relevancy, context precision). (5) Production: LangSmith tracing, caching, rate limiting, fallback models, input sanitization.

Q3: Explain the difference between chains and agents.

A: Chains have a fixed execution path — the developer predetermines what happens and in what order. Think of it as a pipeline. Agents have dynamic execution — the LLM decides which tools to call, when to call them, and when to stop. The LLM acts as a reasoning engine in a loop (observe → think → act). Use chains when the workflow is predictable. Use agents when the task requires flexible tool use, multi-step reasoning, or when you can't predict the steps in advance. In LangChain v0.3, agents are built with LangGraph for better control over the execution flow.

Q4: How do you handle memory in a chatbot?

A: In LangChain v0.3, memory is managed through RunnableWithMessageHistory which stores conversation history per session. For persistence, use RedisChatMessageHistory or PostgresChatMessageHistory. For LangGraph agents, use checkpointers (MemorySaver for dev, PostgresSaver for production). Key techniques: (1) Window memory: Keep only last N messages to stay within context window. (2) Summary memory: Summarize older messages. (3) Long-term memory: Store facts about the user in a separate store, retrieve when relevant. Always set thread_id per conversation/user for isolation.

Q5: How do you defend against prompt injection?

A: Layered defense: (1) Input sanitization: Regex to detect "ignore previous instructions" patterns. (2) Separate system/user prompts: Use ChatPromptTemplate with distinct message roles. (3) Output validation: Check for PII, unexpected format, harmful content. (4) Constrained output: Use with_structured_output to force Pydantic schema compliance. (5) Tool restrictions: Limit which tools agents can access. (6) LLM-as-judge: Have a second LLM evaluate whether the output follows the original instructions. (7) Rate limiting: Prevent abuse through request throttling.

Q6: How do you evaluate and test LangChain applications?

A: Three levels: (1) Unit tests: Mock the LLM, test that chains call components correctly, validate Pydantic schemas. (2) Integration tests: Use real LLM with test prompts, validate output format and quality against golden answers. (3) Evaluation pipelines: LangSmith datasets with input/expected output pairs. Run evaluate() with metrics like correctness, faithfulness, relevance. For RAG: RAGAS metrics. For agents: track tool call accuracy, step count. Key: regression testing — re-run evals after prompt changes to catch regressions.

Q7: When should you use LangChain vs. building from scratch?

A: Use LangChain when: prototyping quickly, need integrations with many providers/vector stores, want built-in tracing (LangSmith), building standard patterns (RAG, chatbot, agent). Build from scratch when: you need maximum control and performance, your use case is simple (single API call), you want to minimize dependencies, or your team has strong LLM engineering experience. Middle ground: use langchain-core for the Runnable interface and LCEL without the full framework. Many production teams start with LangChain, then gradually replace components with custom code as they understand their needs better.

Q8: How do you optimize LangChain applications for cost and latency?

A: Cost: (1) Start with cheap models (gpt-4o-mini), use expensive ones as fallbacks. (2) Cache responses (SQLiteCache). (3) Count tokens before sending — truncate context if needed. (4) Use structured output to reduce output tokens. Latency: (1) Stream responses for perceived speed. (2) Use RunnableParallel to run independent operations concurrently. (3) Use async (ainvoke) for I/O-bound operations. (4) Batch similar requests. (5) Pre-compute and cache embeddings. (6) Use smaller embedding models. (7) Limit retrieval results (k=3-5 instead of 10+).

Q9: How do you build multimodal pipelines in LangChain?

A: Pass content blocks (list of dicts) in HumanMessage.content instead of a plain string. For images: {"type": "image_url", "image_url": {"url": ...}} works across OpenAI, Anthropic, and Gemini (LangChain normalizes the format). For audio: GPT-4o-audio-preview uses {"type": "input_audio", "input_audio": {"data": b64, "format": "wav"}}; Gemini uses {"type": "media", "mime_type": "audio/wav", "data": b64}. Video is only natively supported by Gemini 1.5 Pro / 2.0 Flash via the same media block. For production: (1) Validate media type/size before sending — large payloads time out. (2) Use Gemini's Files API for videos >20 MB. (3) Cache base64 encoding results if the same file is processed repeatedly. (4) Use with_structured_output to extract structured data from vision responses rather than parsing free text. Claude is best for document/PDF analysis; GPT-4o for general image reasoning; Gemini for long video.

Q10: What is the boundary between LangChain and LangGraph — when do you reach for LangGraph?

A: LangChain handles linear and moderately branching pipelines (LCEL chains, retrieval chains, single-pass agents). LangGraph is the right tool when you need: (1) Cycles / loops — an agent that keeps calling tools until a condition is met; LCEL is DAG-only, no cycles. (2) Persistent state across turns — LangGraph checkpointers (MemorySaver, PostgresSaver) serialize the full graph state after every step, enabling pause/resume, human-in-the-loop approval, and long-running workflows. (3) Multi-agent coordination — supervisor agent routing subtasks to specialist agents is natural in LangGraph but awkward in plain chains. (4) Fine-grained control flow — conditional edges, parallel node execution, and rollback are first-class in LangGraph. In practice: use LangChain's create_react_agent (which wraps LangGraph under the hood) for standard tool-calling agents, and drop into raw LangGraph graph construction only when you need custom node logic, interrupts, or multi-agent topologies.

Q11: What types of memory does LangChain/LangGraph support, and how do episodic/semantic/procedural memory differ from buffer/summary memory?

A: These are two different axes. The legacy langchain.memory module (deprecated in v0.3) is a buffer/summary family distinguished by how much history gets replayed into the prompt: ConversationBufferMemory (full verbatim history), ConversationBufferWindowMemory (last k turns), ConversationSummaryMemory (LLM-summarized running history), ConversationSummaryBufferMemory (verbatim buffer + summary once a token threshold is hit — the most commonly used), ConversationTokenBufferMemory (token-based cutoff instead of turn-count), and ConversationKGMemory (extracted entities/facts). All are superseded by RunnableWithMessageHistory + trim_messages, backed by LangGraph checkpointers for persistence. Semantic / episodic / procedural memory is a separate taxonomy (from the CoALA paper, used in LangGraph's long-term Store) describing what kind of long-term memory an agent keeps, not how it's buffered: semantic = facts about the user/world (analogous to entity memory), episodic = specific past experiences/trajectories replayed as few-shot examples (the Reflexion "lessons learned" pattern, §8), procedural = the agent's own rules/system prompt, sometimes rewritten over time. In LangGraph, short-term memory (the per-thread checkpointer) and long-term memory (the cross-thread Store, holding semantic/episodic/procedural entries) are two distinct systems.
