1. What is Agentic RAG?

Saydecision
Say it like this

"Agentic RAG is RAG where an LLM controls the retrieval process itself — deciding whether to retrieve, what to retrieve, from which source, how many times, and whether what came back is good enough — instead of a fixed retrieve-then-generate pipeline that runs the same way for every query. The 'agentic' part is that retrieval becomes a decision, made by a model reasoning in a loop, not a step that always executes identically."

•

2. How is Agentic RAG different from Classic RAG?

Say it like this

"Classic RAG is a straight line: embed the query, retrieve top-k, generate — always exactly once, no judgment involved, regardless of whether the question needed retrieval at all or whether the first retrieval was any good. Agentic RAG wraps that same pipeline in a decision loop: it can skip retrieval for a trivial query, decompose a complex question into sub-questions, grade what it retrieved and re-retrieve if it's insufficient, or switch to a different source entirely. The practical difference is that classic RAG's failure mode is generating from a bad retrieval anyway; agentic RAG's whole point is to catch that and recover — at the cost of extra LLM calls and a new failure surface: the loop itself can now fail."

Dimension Classic RAG Agentic RAG
Control flow Fixed: retrieve → generate Dynamic: the model decides the next step
Retrieval count Always exactly one Zero, one, or many (looped/decomposed)
Bad first retrieval Generates from it anyway Detects it (grading) and recovers
Cost/latency Cheap, predictable Multiplies with hops — needs a cap

3. Why do we need Agentic RAG?

Say it like this

"Because vanilla RAG treats every query identically, and real query distributions aren't uniform — some questions need zero retrieval, some need one lookup, some need facts chained across two documents, and some corpora have uneven retrieval quality where the top-k is sometimes great and sometimes irrelevant. Agentic RAG exists to handle that variance: route trivial queries around retrieval entirely, decompose multi-hop questions, and grade-and-recover when retrieval quality is uneven — none of which a fixed pipeline can do by construction, no matter how well you tune it."

•

4. When would you choose Agentic RAG over Classic RAG?

Sayspecific, measured
Say it like this

"I don't default to it — I only reach for it when eval on classic RAG shows a specific, measured gap: questions that need facts chained across multiple documents, meaningfully uneven retrieval quality where wrong answers are costly, a meaningful share of traffic that needs no retrieval at all, or an information need that only becomes clear after seeing the first retrieval. If classic RAG's eval numbers are already solid and the questions are single-hop, single-source, I'd stay with the simpler, cheaper, more predictable pipeline — every extra decision point in agentic RAG is an extra LLM call and an extra place to fail."

5. Advantages and disadvantages of Agentic RAG

Say it like this

"The advantages are real: it self-corrects bad retrievals instead of generating from them, it handles multi-hop questions no single retrieval could answer, and it can skip unnecessary work for trivial queries. The disadvantages are just as real and often underweighted: cost and latency multiply with every hop — a 3-hop query can run 2 to 2.5x the latency and cost of a single vanilla pass — and it introduces an entirely new failure class vanilla RAG doesn't have: the loop itself can fail, spinning on evidence that was never in the corpus, or trusting a miscalibrated grader. My honest framing in an interview is: agentic RAG trades predictability for adaptability, and that trade needs to be proven with an A/B against the vanilla baseline, not assumed."

Advantages Disadvantages
Self-corrects bad retrieval (grading + retry) Cost/latency multiply with hops (~2–2.5x for 3 hops)
Handles multi-hop, chained-fact questions New failure class: the loop itself can fail (infinite retrieval, miscalibrated grader)
Skips retrieval for trivial queries (routing) Harder to evaluate — need trajectory eval, not just answer quality
Can switch sources / fall back mid-query Harder to debug — more moving, model-decided parts

6. End-to-end architecture of Agentic RAG

Say it like this

"Query comes in, a router decides whether it even needs retrieval or which source to use. If it's multi-hop, a planner decomposes it into sub-questions. Each sub-question goes through retrieval, then a grading step scores what came back — sufficient evidence moves to generation with citations, insufficient evidence triggers a bounded retry: rewrite the query, re-retrieve, or switch to a fallback source. Everything that loops back is capped by a hard hop limit. Once evidence is sufficient — or the cap is hit and the system abstains — a synthesis step generates the final, cited answer."

             │                          ┌─sufficient──▶ GENERATE + cite ──▶ answer

7. How would you design Agentic RAG using LangGraph?

Say it like this

"I'd model it as a StateGraph where each node is one of the decision points — route, decompose, retrieve, grade, generate — and edges are conditional, driven by the state after each node runs. The state object carries the query, sub-questions, retrieved evidence, and hop count. A conditional edge out of the grade node routes either to generate (evidence sufficient) or back to a rewrite-and-retrieve node (insufficient, hop count under the cap) or to an abstain node (cap hit). I'd persist state through a checkpointer so a long-running or paused trajectory survives a crash and supports human-in-the-loop approval before anything consequential. This is exactly the deterministic-state-machine pattern — the LLM fills the decision at each node, but the set of reachable next-states is fixed by the graph, not freely chosen by the model."

8. Main components of an Agentic RAG system

Sayrouterplanner/decomposerretrieval toolsgradergenerator
Say it like this

"Six pieces: a router that decides whether/where to retrieve, a planner/decomposer for multi-hop questions, one or more retrieval tools — vector search, SQL, an API, web search — a grader that scores retrieved evidence, a generator that synthesizes the final cited answer, and an orchestrator (the loop itself, or a LangGraph graph) that wires all of that together with a hard hop cap. Everything else — caching, tracing, budgets — sits underneath as infrastructure, not a core decision-making component."

•

9. Role of the Planner node, and why do we need one?

Say it like this

"The planner's job is to turn one incoming question into an executable plan — is this single-hop or does it need decomposing into ordered sub-questions, and if there's a dependency between sub-questions, what order do they need to run in. We need it because a single retrieval call can't answer a question like 'was the vendor who supplied our Q3 servers also involved in last year's security incident' — that needs two separate lookups and a join, and nothing in a fixed pipeline knows to do that. Without a planner, agentic RAG can grade and retry, but it can't handle genuinely compound questions."

•

10. Role of the Router/Decider

Say it like this

"The router is the up-front classification step that decides whether a query needs retrieval at all, and if so, which source — the docs index, a tickets index, a code index, or none. It's deliberately cheap: a small, fast classifier call, not the main generator, because it's a narrow classification task run on every single query. Its value shows up as a measurable number: what fraction of traffic did it correctly skip or redirect — if that's near zero, routing is pure overhead and I'd cut it."

•

11. Can one Planner manage multiple retrieval agents?

Say it like this

"Yes, and that's actually the more common production shape than N independent agents — a single planner or supervisor decomposes the task and dispatches each sub-question to the right specialist retrieval agent (vector, SQL, API), then synthesizes their results itself. The alternative — letting specialist agents coordinate peer-to-peer — adds real coordination overhead (mutual loops, conflicting evidence) for very little benefit in most cases, so I default to one planner/supervisor owning dispatch and termination unless a single agent's context or tool budget is genuinely overloaded."

•

12. Single-Agent vs Multi-Agent architecture

Say it like this

"I default to single-agent-with-tool-access or single-agent-with-routing, and only split into a multi-agent, supervisor-coordinated system when one agent's context or tool budget is genuinely overloaded by the number of sources it has to juggle. The reason is math, not opinion: three specialist agents at five steps each is already fifteen LLM calls before any retry, against a single well-guarded agent doing the same task in maybe six larger steps — multi-agent needs to win on quality by something like three to five times the calls to be worth it. When I do go multi-agent, I use a supervisor topology, not a peer-to-peer swarm, because a supervisor bounds coordination cost and termination predictably."

13. How do specialized retrieval agents work (Vector DB, SQL, API, Web Search)?

Saydisambiguation
Say it like this

"Each source is wrapped as its own tool with a strict schema and a non-overlapping trigger description — vector search for unstructured docs/policies, SQL for structured/numeric exact lookups, an API for live external data, web search for anything outside the internal corpus. The agent (or router) picks which tool to call based on the query shape, executes it, and treats the result as untrusted data that gets validated before being trusted forward. The design discipline that matters most here is disambiguation: if two tools could both plausibly answer a query — a vector search and a SQL query that both 'know about' inventory — selection accuracy drops, so each tool's description needs a genuinely distinct trigger condition, or they should be merged into one parametric tool."

15. How does the Planner decide which tool to call?

Say it like this

"It reasons over the query against each available tool's description and picks the one whose trigger condition matches — this is exactly a tool-selection decision, so the same discipline applies as any agent tool call: few tools, strictly scoped, with non-overlapping descriptions, because tool-selection accuracy measurably degrades as tool count grows and as descriptions overlap. For a genuinely compound question needing two sources, the planner doesn't pick one tool, it decomposes first (Q9) and then each sub-question independently picks its own tool."

•

16. How does the agent decide whether to retrieve again?

Say it like this

"That decision belongs to the grading step, not the planner — after a retrieval, a grader scores the evidence's relevance to the current sub-question, and if the score is below a calibrated threshold, the agent retries: rewrite the query and re-retrieve, capped by the hop limit. If the score clears the threshold, it moves straight to generation. The grader is the load-bearing piece here, so I calibrate it against human-labeled relevance samples the same way I'd calibrate any LLM-judge — an uncalibrated grader either never corrects anything (too lenient) or burns budget re-retrieving queries that were already fine (too strict)."

•

17. What happens if the retrieved context is not relevant?

Saynot
Say it like this

"The grading step catches it before it ever reaches generation — a low relevance score triggers a bounded retry loop: rewrite the query with what's known so far, re-retrieve, re-grade. If it's still insufficient after the hop cap, the system does not force a final generation from bad evidence — it either switches to a fallback source, like web search, or abstains and says it couldn't find sufficient evidence. The one thing it must never do is quietly generate from irrelevant context and let the model produce a confident, ungrounded answer."

•

18. How do you validate retrieval quality before generating an answer?

Say it like this

"Two checks, stacked. First, a similarity/relevance threshold on the retrieved results themselves — low scores across the board signal a vocabulary gap or genuinely missing content. Second, an explicit grading step — an LLM or a small classifier scoring 'do these documents actually answer this question,' not just 'are they topically similar.' Only evidence that clears both gates goes to generation; anything else triggers the retry-or-abstain path in Q17. The mistake I'd flag in an interview is treating 'retrieval returned k results' as success — a nonempty result set is not the same as a relevant one."

19. How do iterative retrieval loops work?

Sayfrom the previous result
Say it like this

"Unlike decomposition, where all sub-questions are known up front, iterative retrieval discovers each next query from the previous result — retrieve, reason about what's still missing, retrieve again with a refined query, repeated until there's enough evidence or the hop cap is hit. Because each step depends on the last, this pattern is inherently sequential — there's no parallelizing your way out of the cost, which is exactly why the hop cap matters more here than in any other agentic RAG pattern."

Step 2: retrieve("treatment for X in children")  → refined from step 1's gap
Step 3: retrieve("drug interactions with {step-2 treatment}") → refined again
   ... capped at N hops → synthesize across all retrieved evidence

20. What is self-reflection (self-evaluation) in Agentic RAG?

Say it like this

"Self-reflection, or Self-RAG, is when the generator model itself emits judgments about its own process inline — should I retrieve here at all, is this retrieved passage actually relevant, is my draft answer actually supported by it — instead of relying on a separate grading model wrapped around it, which is what CRAG does. The trade-off is real: Self-RAG is cheaper, no second model call, and works well with capable instruction-following models, but models are often overconfident graders of their own output, so its failure mode is the model's self-assessment being wrong. CRAG's external grader is more robust and independently tunable, at the cost of an extra call."

CRAG Self-RAG
Who grades A separate grading step/model The generator itself, inline

Failure mode Grader is miscalibrated Model is overconfident about its own output
Easier to retrofit onto an existing pipeline Yes — add a grading node Needs the generator to support reflection

21. How do you prevent infinite reasoning loops?

Say it like this

"A hard hop cap, non-negotiable — the single most important guardrail in the whole system, for cost and for correctness. The failure it prevents is specific: a grader keeps saying 'insufficient' for a query that genuinely has no good answer in the corpus, and unlike vanilla RAG, which would just generate a thin answer once and stop, an agentic loop can keep chasing evidence that was never there. When the cap is hit, the system must abstain, never force one more retrieval or a final low-confidence generation — that's the worst possible outcome, full cost paid and still a bad answer. I also add repeat detection — hashing recent (tool, query) pairs — so a near-identical retry gets caught even before the numeric cap."

22. How many iterations should an agent perform?

Say it like this

"I don't pick a round number up front — I set the cap from measured evidence-gain-per-hop on an eval set: track how much new relevant evidence each successive hop actually surfaces, and if hop 3 rarely adds anything hop 2 didn't already find, that's my signal to cap at 2. In practice, most production systems land somewhere around 2 to 4 hops for genuinely multi-hop questions — beyond that, the cost curve (linear in hops, with no parallelization available for iterative retrieval specifically) stops being justified by the accuracy gain, and I'd rather abstain than pay for a 5th hop that historically adds nothing."

23. How do you retrieve data from multiple sources?

Say it like this

"Each source is exposed as its own tool — vector search, a SQL query tool, a REST API client, a web-search tool — with its own schema and its own non-overlapping trigger description. Either a router picks one source up front per query (cheapest), or, for questions that genuinely need more than one source, the agent calls multiple tools ReAct-style and synthesizes their combined results — 'what's our current stock of SKU 4471, and does the spec sheet mention a recall' needs both a SQL lookup and a vector search, and no single source answers it alone."

•

24. How do you combine Vector DB, SQL, APIs, and Web Search?

Say it like this

"I treat the retriever as just one tool among several in a ReAct-style loop — the agent reasons about which tool(s) a question needs, calls them, and I synthesize the combined results with each fact attributed to its source, so if two sources disagree the synthesis step can surface the conflict rather than silently picking one. Each tool call is cached by (tool, args) where the call is deterministic — a repeated SQL lookup or API call returns instantly instead of re-hitting the source system, whether that's within the same run or a completely different one."

•

25. Does using multiple data sources automatically make a system Agentic?

Saymodel decides
Say it like this

"No — and this is a good interview trap to name explicitly. A system that always queries a fixed set of sources in a fixed order, every time, is still classic RAG with a wider fan-out, not agentic RAG. What makes it agentic is that a model decides, per query, whether to use a source at all, which one(s), and in what order — the decision-making is the defining property, not the number of sources. You can have single-source agentic RAG (grading and retrying against one vector store) and multi-source non-agentic RAG (always hitting three fixed sources and merging) — they're independent axes."

•

26. Rule-based routing vs LLM-based routing — and when to use which

Say it like this

"Rule-based routing is deterministic — keyword matches, regex, a lookup table mapping query patterns to sources — fast, free, completely predictable, but brittle to phrasing it wasn't explicitly written for. LLM-based routing is a small model or classifier call that generalizes across phrasing it's never seen, at the cost of latency, money, and occasional misclassification. I use rule-based routing when the distinguishing signal is genuinely structural — a query containing a ticket-ID pattern always goes to the tickets index, no judgment needed. I use LLM-based routing when the distinction is semantic — 'is this a policy question or a technical question' can't be captured by a keyword rule. In practice I often stack them: cheap rules catch the obvious cases, and only ambiguous queries fall through to the LLM router, which keeps the average routing cost low."

27. How does Tool Calling work in Agentic RAG?

Say it like this

"The model is given a set of tool schemas — name, description, and a typed argument spec — and at each step it can either answer directly or emit a structured call: which tool, with what arguments. My code validates those arguments against the schema before executing anything, runs the tool, and returns the result back into the model's context as the next observation. The model never executes code directly — it only ever proposes a call, and a constrained layer is what actually runs it, which is also where safety and validation live."

•

28. How do you bind tools to an agent?

Say it like this

"Concretely, I register each tool with a name, a natural-language description the model uses to decide when to call it, and a typed argument schema, usually Pydantic or JSON Schema. The framework (LangChain/LangGraph bind_tools, or a hand-rolled dispatch table) attaches that tool list to the model's context so it can emit structured tool-call outputs. The description is doing more work than people expect — it's the entire signal the model uses for tool selection, so I write it as precisely and non-overlapping with other tools as I would write a function's docstring for a human teammate."

29. How do you expose APIs as tools?

Say it like this

"I wrap the API call in a function with a typed signature and a description that states exactly what it's for and what it isn't, validate and sanitize whatever arguments the model provides before the request goes out, and normalize the response into a structured, model-readable shape rather than returning a raw payload. Failures come back as structured errors — {"error": "...", "hint": "..."} — not a stack trace, so the model can reason about what went wrong and retry differently. Anything the API call could do that's consequential — a write, a state change — gets treated as a dangerous action requiring approval, not just a read."

•

30. How do you expose SQL databases as tools?

Sayparametrized query function
Say it like this

"Never as raw SQL execution — I expose a parametrized query function with a fixed, reviewed set of allowed queries or a strict schema for the arguments (table, filters, columns), not free-text SQL the model writes itself, because that's a direct injection and data-integrity risk. I also enforce row-count limits and read-only credentials for anything that's meant to be a lookup tool, and any write path gets an explicit dangerous-action approval gate, never auto-executed just because the model asked for it. The response comes back structured — rows as JSON, not a raw cursor dump — so the model can reason about it."

31. What happens when a tool fails?

Say it like this

"I split it by whether the fault is transient or persistent. Transient — a timeout, a rate limit — gets retried with exponential backoff, invisible to the model so it doesn't waste a reasoning step on infrastructure noise. Persistent — a bad argument, a genuinely empty result — comes back as a structured error with a hint, so the model can retry differently instead of repeating the identical failing call. After a few consecutive failures on the same tool, a circuit breaker trips and that tool reports itself unavailable, so the agent plans around it or escalates instead of hammering a dead dependency."

•

32. How do you retry failed tool calls, and implement exponential backoff?

Say it like this

"Only transient faults get retried — retrying a malformed-argument error just wastes time, since retrying won't change the outcome. For transient faults I retry with exponential backoff and jitter: wait roughly one second, then two, then four, doubling each time with a small random offset so many clients don't all retry in lockstep, capped at a small number of attempts, three or four, before giving up and returning a structured error upstream." 

def with_backoff(fn, retries=3, base=1.0, retriable=(TimeoutError, RateLimitError)):
    for attempt in range(retries + 1):
        try:
            return fn()
        except retriable:
            if attempt == retries:
                raise
            time.sleep(base * 2 ** attempt + random.random())

33. When would you use a fallback tool?

Sayahead of time
Say it like this

"When the primary tool is down, degraded, or has exhausted its retries — a pre-planned alternative path, not an improvised one. Vector search down → fall back to keyword/BM25 search on separate infrastructure. Internal API down → fall back to a cached last-known-good response, or web search if the data is public. The key design point is that the fallback is decided ahead of time, per tool, not discovered mid-incident, and the response is labeled internally as degraded so downstream logic (and eventually the user, if relevant) knows it's not the primary-quality path."

34. How do you implement a circuit breaker for failing tools?

Say it like this

"After N consecutive failures on a given tool — typically three — the breaker opens: for a cooldown window, calls to that tool skip straight to the fallback (or a structured 'unavailable' error) instead of retrying the dead dependency, which protects both my system's latency budget and the struggling downstream service from being hammered further. After the cooldown, the breaker allows one trial call through, and a success resets it closed." 

class CircuitBreaker:
    def __init__(self, threshold=3, cooldown=30):
        self.fails, self.threshold, self.cooldown, self.opened_at = 0, threshold, cooldown, None
    def is_open(self):
        return self.opened_at and time.time() - self.opened_at < self.cooldown
    def record_failure(self):
        self.fails += 1
        if self.fails >= self.threshold:
            self.opened_at = time.time()
    def record_success(self):
        self.fails, self.opened_at = 0, None

35. How do you handle tool failures? (production angle)

Say it like this

"Q31 covers the per-call recovery mechanics — retry, structured error, circuit breaker. Operationally on top of that, I alert on circuit-breaker trip rate per tool, because a tool that's tripping frequently in production is a leading indicator of a downstream outage before it shows up as user-facing errors. I also track what fraction of runs hit a fallback path, since a rising fallback rate for one tool is exactly the kind of thing that should page someone before it becomes a full outage."

•

36. How do you debug failed agent executions?

Say it like this

"I pull the full trajectory trace for the failing run — every model call, every tool call with its arguments and result, every routing/grading decision — because agent failures are rarely a single exception, they're a wrong decision three steps upstream of where things visibly broke. I localize by walking the trajectory forward: did the router send it to the wrong source, did the planner decompose it badly, did a tool return a bad result the agent trusted forward uncritically, or did generation ignore good evidence. Then I check whether it's isolated to one query pattern or systemic — a systemic failure right after a deploy points hard at whatever config, prompt, or model just changed."

•

37. What logs would you collect?

Say it like this

"Per step in the trajectory: the model's reasoning/decision, which tool was called with what arguments, the tool's raw result, the grading/routing score if applicable, token count and latency for that step, and any error with a hint. At the run level: the original goal, the final answer, total steps/tokens/cost, and whether it terminated normally, via abstention, or by hitting a budget cap. The rule I follow is that nothing about why a decision was made should be reconstructable only from memory — if I can't answer 'why did it call this tool' from the logs alone, the logging is insufficient."

•

38. What metrics would you monitor?

Say it like this

"Split into system health and decision quality. System: p50/p99 latency per step type, error rate per tool, circuit-breaker trip rate, cost per run, steps per run. Decision quality: routing accuracy against a labeled set, grader calibration against human-labeled relevance, hop-cap-hit rate — a rising hop-cap-hit rate often means the corpus has a real coverage gap, not that the loop needs more hops. The metric most teams under-monitor is cost/steps per run as a distribution, not an average — a runaway loop shows up as an outlier in that distribution long before it shows up as a bill anomaly."

39. How do you trace an agent's execution?

Sayspan
Say it like this

"Every model call, tool call, and routing/grading decision gets instrumented as a span, linked by a propagated run/trace ID — OpenTelemetry is the vendor-neutral standard, LangSmith/Langfuse/Arize Phoenix are LLM-specific alternatives. Without per-span tracing a multi-step agent is opaque — you can see a run was slow or wrong, but not which hop. I make sure the trace captures inputs, outputs, latency, and token cost at every span, so I can reconstruct the full decision path after the fact, not just the final answer."

•

40. How do you monitor agent trajectories?

Say it like this

"I compare live trajectories against expected shapes on a sample: how many hops did it take, did it call the tools I'd expect for this query type, did routing/grading decisions match what a human reviewer would pick. This is trajectory evaluation, distinct from outcome evaluation — an agent can reach the right final answer via a wasteful or accidentally-correct path, and trajectory monitoring is what catches that a run 'worked' for the wrong reasons, which matters because that path won't generalize."

•

41. How do you detect excessive iterations?

Say it like this

"Two mechanisms. A hard numeric cap that force-stops a run at N steps — the non-negotiable backstop. And repeat detection underneath it — hashing recent (tool, args) pairs, and if the same call recurs with no meaningful state change, that's flagged (and usually stopped) well before the numeric cap is even reached, since a loop calling the same tool with near-identical arguments is a stronger signal than step count alone that nothing productive is happening."

42. How do you control latency in Agentic RAG?

SayLatency leversDistill routing and grading modelsCap hops tightlyStream the final synthesisTrace per-hop
Say it like this

"First, keep routing and grading calls on small/distilled models so they add tens of milliseconds, not hundreds. Second, parallelize whatever's genuinely independent — decomposed sub-questions that don't depend on each other's answers should retrieve concurrently, which is the single biggest latency lever available, collapsing N hops toward roughly one hop's wall-clock time. Third, cap hops tightly, since iterative retrieval specifically can't be parallelized — cost and latency there are strictly hops times per-hop cost. And a semantic/tool-result cache in front of the whole loop skips everything on a repeated or near-duplicate query."

Latency levers: - Parallelize decomposed sub-questions — independent sub-questions retrieve concurrently; collapses N hops toward ~1 hop's wall-clock time, the single biggest lever. - Distill routing and grading models — small/distilled models add tens of ms, not hundreds, for these narrow classification-shaped calls. - Cap hops tightly — iterative/recursive retrieval can't be parallelized; latency there is strictly hops × per-hop cost, so the cap is a latency ceiling. - Optimize the underlying single-pass pipeline first (file 26) — prefix caching, parallel dense+sparse retrieval, bounded reranker candidates — since the loop multiplies whatever one pass already costs. - Semantic/tool-result cache in front of the whole loop — a repeated or near-duplicate query skips every hop entirely. - Stream the final synthesis — cuts perceived latency even though total hop latency is unchanged. - Trace per-hop (routing, each retrieval, each grading call, synthesis) to find the actual bottleneck before optimizing.

Worked 3-hop latency budget (~2,025ms, ~2.3x vanilla RAG): Scaling Optimization Agentic RAG.

45. How do you create a Golden Dataset?

Say it like this

I use this especially on runs where the outcome was correct but I suspect the path was wasteful or accidentally right, since outcome-only eval would score those as a pass and hide the actual inefficiency."

50. How do you perform regression testing after prompt/model changes?

Say it like this

"I run the golden dataset (Q45) through the changed system in CI — comparing both outcome metrics (faithfulness, task success) and trajectory metrics (routing accuracy, hop count, tool-selection accuracy) against the last known-good baseline, not an absolute threshold alone. I specifically pin known-hard and previously-broken cases in that set so a regression that was already fixed once doesn't silently reappear. A prompt tweak that improves outcome accuracy by two points but doubles average hop count is a regression I want the CI gate to catch, even though a naive pass/fail on final-answer-correctness alone would miss it."

58. How do you scale Agentic RAG?

SayScaling leversAutoscale on queue depth/p99
Say it like this

"First, make sure the underlying RAG pipeline each hop calls is already optimized — the loop only multiplies whatever one pass already costs, so fixing that pass first (file 26's territory) pays off on every hop, not just once. Then at the loop layer: externalize agent state to a checkpointer so orchestration workers are stateless and horizontally scalable, parallelize independent sub-question retrieval, and put a global step/cost budget across the whole system, not just per run, so one runaway trajectory can't consume capacity meant for everyone else."

Scaling levers: - Fix the underlying RAG pipeline first (file 26) — the loop multiplies whatever one pass already costs, so pipeline-layer fixes (sharding the index, replicating retrieval/rerank, batching generation) pay off on every hop. - Shard the vector index for capacity, replicate it for read QPS/availability — not the same lever: sharding splits data across nodes once it no longer fits in RAM; replication adds read throughput and failover on top, and doesn't help if the index itself is too big for one node. - Externalize agent state to a checkpointer — orchestration workers become stateless and horizontally scalable behind a queue. - Parallelize independent sub-question retrieval — the biggest loop-layer win, same lever as latency. - Global step/cost budget across the whole system, not just per run — bounds blast radius from any single runaway trajectory. - Scale retrieval, reranking, and generation independently — stateless/read-heavy, memory-bound, and compute-bound respectively, with different bottlenecks. - Autoscale on queue depth/p99, not CPU% — for the generation-serving layer specifically. - Check the caching hierarchy cheapest-first (prefix → exact → semantic → tool-result) in front of the whole loop — a cache hit is the cheapest possible form of "scaling."

60. Which models would you use for Planner vs Generator?

Say it like this

"Planner, router, and grader are narrow classification or structuring tasks — 'which tool,' 'is this sufficient,' 'split this into sub-questions' — so a small or distilled model, often in the 1B–8B parameter range, handles them well at a fraction of the cost and latency. The final generator/synthesis step is open-ended, needs to weigh multiple pieces of evidence, produce fluent grounded prose, and get faithfulness right, so that's where I'd spend the budget on the frontier model. Using the frontier model for every routing decision is the single most common cost mistake I see in agentic RAG designs."

•

61. Small model vs reasoning model — when?

Say it like this

"Small/fast models for narrow, well-defined, repeated judgments — routing, grading, argument formatting — where the task is closer to classification than reasoning. A dedicated reasoning model for the genuinely hard step: final synthesis over conflicting or partial evidence, or a planning decision where the decomposition itself is non-obvious. I wouldn't reach for a reasoning model by default everywhere — its extra latency and cost only pays off where the task actually needs multi-step reasoning, not on a call that's really a classification problem wearing a reasoning-shaped prompt."

•

62. How do you cache Agentic RAG?

Say it like this

"Layered, cheapest first: a semantic/exact cache in front of the whole loop for repeated or near-duplicate top-level queries — a hit skips everything, routing through generation. Underneath that, a tool-result cache keyed on (tool, args) for deterministic calls — SQL lookups, static API responses — reusable not just within one run's retries but across completely different runs. And a prefix/prompt cache at the model-serving layer for the static system-prompt/tool-schema portion that's identical across every call."

•

63. How do you avoid unnecessary tool calls?

Say it like this

"Routing up front so trivial queries never enter the tool-calling loop at all. Tight, non-overlapping tool descriptions so the model doesn't hedge by calling multiple plausible tools 'just in case.' Caching so a repeated call returns instantly instead of re-executing. And repeat detection that interrupts a call being retried identically with no new information — if the arguments haven't meaningfully changed since the last call to the same tool, that's a strong signal the call shouldn't happen again without a different approach."

Say it like this

Say it like this

72. A tool keeps failing — how would you recover?

Say it like this

"First, is it transient or persistent — check the error type and recent success rate. If transient, backoff retries should already be handling it; if the circuit breaker has tripped, that's working as designed and the agent should already be on the fallback path or reporting the tool unavailable. If it's failing on every call regardless of arguments, that's likely a genuine outage or a broken integration — I'd check the tool's own health/logs directly, not just the agent side. If it's failing only on specific argument shapes, that's a validation or schema mismatch — I'd look at what the model's been passing versus what the tool actually expects, which is often a stale schema or description drift after an API change."

73. The agent keeps looping — how would you debug it?

Say it like this

"Pull the trajectory trace and look for a repeated (tool, args) pattern — that's the signature of a runaway loop, and it tells me why immediately: either a tool is returning a vague or empty result that never satisfies the model's goal, so it keeps re-trying the same thing, or a grading step is miscalibrated and never accepts evidence as sufficient. The fix follows directly from which one it is: a vague-result loop needs better structured error/hint messages from the tool so the model retries differently instead of identically; a grader-calibration loop needs the grader recalibrated against labeled samples. Either way, the hop cap and repeat-detection guard should already be limiting the blast radius while I fix the root cause."

•

74. The planner selects the wrong tool — how would you fix it?

Say it like this

"First I'd check whether the failure is isolated to one query pattern or systemic — systemic points at the tool descriptions themselves. The most common root cause is overlapping trigger conditions: if two tools could both plausibly handle the query, the model has no reliable signal for which to pick, so I'd rewrite the descriptions to be genuinely non-overlapping, or merge the two tools into one parametric tool if they truly overlap in scope. I'd also check tool-selection accuracy against the labeled eval set (Q46) — a wrong pick on one live query might be an outlier, but a systematically low score there means the fix needs to happen in the tool descriptions/schemas, not by patching one query."

•

75. Users report slow responses — how would you optimize?

Say it like this

"Trace first, don't guess — pull the per-hop latency breakdown for slow runs and see where the time actually goes. If it's concentrated in generation, that's usually prefix caching and model-serving optimizations (continuous batching, quantization). If it's spread across many sequential hops, check whether any of those hops were actually independent sub-questions running sequentially by mistake — parallelizing them is often the single biggest fix, bigger than any model-level change. If it's routing or grading calls adding up, check whether they're running on the frontier model when a distilled small model would do. And I'd check the hop-count distribution — if slow runs correlate with high hop counts, that's a hop-cap or grader-calibration problem, not a raw-speed problem."

•

76. Retrieved context is correct but the answer is wrong — how would you investigate?

Say it like this

"This isolates the bug to generation, not retrieval — so I stop looking upstream and check three things in order. First, is the context actually making it into the final prompt intact, or is something getting silently truncated by a context-window overflow — a genuinely easy thing to miss since it produces no error. Second, run a groundedness/faithfulness check on the specific bad answer — is the model ignoring the correct context and answering from its own parametric memory, or blending it with something else. Third, check the prompt instructions — is the model actually being told clearly to answer only from the provided context, or is that instruction weak or missing. This is exactly the diagnostic value of splitting RAGAS metrics into context precision/recall versus faithfulness — high context quality plus low faithfulness points straight at generation, not retrieval."

I'd also avoid it under a hard latency SLA where even a two-to-three-times cost multiplier isn't tolerable, or in a low-stakes application where the cost of an occasional imperfect vanilla-RAG answer is genuinely lower than the engineering and operational cost of running and monitoring a loop. My rule: classic RAG is the default, agentic RAG is something you earn the right to add by measuring a specific gap first."

1. What is an AI Agent?

Sayacts
Say it like this

"An AI agent is an LLM wrapped in a loop that can perceive its environment, decide on an action, execute that action through a tool, observe the result, and decide the next step — repeated until the goal is met or a stopping condition fires. The defining property is that it acts, not just answers: a plain LLM call takes an input and produces an output once; an agent takes a goal and produces a sequence of decisions and actions toward it."

2. What is Agentic AI?

Say it like this

"Agentic AI is the broader discipline of building systems where an LLM has autonomy over its own process — deciding what to do next, which tools to use, when it's done — rather than following a hand-coded sequence of steps. It covers single agents, multi-agent systems, planning, memory, and tool use as a whole design space, not one specific pattern."

3. How is Agentic AI different from traditional LLM applications?

Sayinto the model's own decisions
Say it like this

"A traditional LLM application is a fixed pipeline — call the model once (or in a hand-coded sequence of fixed calls) and return the output; the control flow is written by a developer and never changes at runtime. Agentic AI moves that control flow into the model's own decisions — the model chooses which step to take next, which tool to call, whether to loop again, based on what it's seeing right now. The practical consequence: a traditional app's cost and behavior are predictable and bounded by code; an agent's are decided at runtime and need explicit guardrails — step caps, budgets, approval gates — to stay bounded at all."

•

4. How is Agentic AI different from a chatbot?

Sayaccomplish a goal
Say it like this

"A chatbot's job is to hold a conversation — respond to messages, maintain some context, stay on topic. It doesn't need to take actions in the world or reason across multiple steps to get there; a good chatbot can be entirely built as a single LLM call per turn plus conversation history. An agent's job is to accomplish a goal, which often requires taking real actions — querying a database, calling an API, writing a file — and reasoning across multiple steps toward that goal. You can build a chatbot that's also an agent (it takes actions within the conversation), but 'holds a fluent conversation' and 'autonomously accomplishes multi-step goals' are genuinely different capabilities, and conflating them is a common interview trap."

5. How is Agentic AI different from RAG?

Say it like this

"RAG is about grounding generation in retrieved knowledge — fetch relevant documents, then generate an answer from them; the control flow is typically fixed, retrieve-then-generate. Agentic AI is about giving a model autonomy over a multi-step process with tools — which may or may not include retrieval as one of its tools. They're orthogonal: you can have RAG with no agency at all (classic RAG, always retrieves the same way), and you can have an agent that never touches a retriever (a SQL agent, a code-execution agent). Where they combine is Agentic RAG — an agent that specifically uses retrieval as one of its tools and reasons about when/how to use it."

7. When should you use an Agent?

"When the task is a fixed, known sequence of steps — that should be a deterministic pipeline or workflow, not an agent deciding the sequence at runtime, because a hard-coded pipeline is cheaper, faster, and can't go off-script. I'd also avoid it under a hard latency SLA an agent loop can't reliably hit, or for genuinely simple single-step tasks where the reasoning overhead buys nothing. My rule: an agent is justified when the value of runtime flexibility exceeds the cost of unpredictability — if I can write the correct sequence of steps in code, I should, and only hand control to the model where the sequence truly can't be known ahead of time."

10. Explain the architecture of an AI Agent

Say it like this

"At the core is a loop: the model receives the current state — goal, history, latest observation — decides on a next action, that action executes through a tool, the result becomes a new observation, and the loop repeats until a stopping condition. Around that loop sit the supporting components: a planner for breaking down complex goals up front, a router for picking among multiple possible paths or tools, memory for carrying relevant context across steps, and a reflection/verifier step for checking intermediate or final results before committing to them. None of these are mandatory for every agent — a simple agent might just be the loop plus tools — but as task complexity grows, each component earns its place by solving a specific failure mode."

11. Components of an Agent

Say it like this

"Planner, Router, Executor, Memory, and Reflection/Verifier — five roles, though not every agent needs all five as separate pieces; a simple agent might fold planning and routing into one reasoning step. I'd describe each one's job in one line: the Planner decomposes the goal into steps, the Router picks which tool or path handles a given step, the Executor actually runs the tool call, Memory carries relevant state across steps, and the Reflection/Verifier checks whether a step (or the final result) actually succeeded before moving on."

•

12. What is the Planner?

Say it like this

"The Planner is the component that turns a goal into an ordered (or partially ordered) set of steps before, or while, execution happens. For a simple task it might just be implicit in the reasoning step; for a complex task — 'plan a 5-day trip within this budget' — it explicitly decomposes into sub-goals: find flights, find hotels, check budget constraints, sequence them. A good planner also re-plans: if step 3 reveals new information that invalidates the original plan, it should be able to revise, not blindly execute a stale plan."

•

13. What is the Executor?

Say it like this

"The Executor is the component that actually runs an action — calls a tool with validated arguments, executes the API request, runs the SQL query — and returns a structured result. It's deliberately kept dumb and mechanical: the model only ever proposes an action, and the Executor is a separate, constrained layer that validates the arguments against a schema and enforces any approval gates before anything actually runs. Keeping this separation is what makes the system auditable and safe — the model never has raw execution power."

•

14. What is the Router?

Say it like this

"The Router is the decision point that picks which tool, which sub-agent, or which path handles the current step — either a cheap classifier making the call up front, or the reasoning model itself choosing from the available tool set. Its job is scoped and narrow: 'given this step, which of my available options handles it,' not the broader planning question of 'what are all the steps.' A well-designed router has few, non-overlapping options to choose from — routing accuracy degrades fast as the option set grows and overlaps."

•

15. What is the Memory component?

Say it like this

"Memory is whatever state persists and gets reused across steps or across runs — the running conversation, intermediate results from earlier steps, and any durable facts that should survive beyond this one session. It splits into short-term (this run's scratchpad — the trajectory of thought/action/observation so far) and long-term (durable facts about the user, past interactions, or the domain that should be available in future runs too). Full split: Q38."

•

16. What is the Reflection/Verifier component?

Sayverified
Say it like this

"Reflection is the agent (or a separate step) checking its own intermediate or final output before committing to it — 'did this tool call actually return what I expected,' 'is this draft answer actually supported by the evidence I gathered,' 'have I actually achieved the stated goal.' It's what turns a system that generates a plausible-looking result into one that generates a verified result — catching a bad intermediate step before it compounds into a worse final one, which matters because agents run their own output back into the next step without a human reading it in between."

•

17. How do these components interact?

Say it like this

"Goal comes in, the Planner (if the task warrants it) breaks it into steps. For each step, the Router picks which tool or sub-agent handles it, pulling relevant context from Memory. The Executor runs it, the result gets appended to Memory, and the Reflection/Verifier checks whether that step actually succeeded and whether the overall plan is still on track — if not, control goes back to the Planner to revise, or to the Router to retry differently. This repeats until Reflection confirms the goal is met or a hard budget/step cap is hit."

C — Planning & Reasoning
•

18. What is planning in Agentic AI?

Say it like this

"Planning is deciding the sequence of steps needed to reach a goal, either fully up front (plan-then-execute) or incrementally, one step at a time, revising as new information arrives (interleaved planning, the ReAct-style pattern). Plan-then-execute is more predictable and easier to validate before spending any execution budget; interleaved planning adapts better when the right next step genuinely depends on what earlier steps reveal. Most production systems use a hybrid: a coarse up-front plan, re-validated against reality every few steps."

•

19. Why do agents need planning?

Say it like this

"Because without it, a complex, multi-step goal gets attempted one greedy step at a time with no sense of the overall shape of the task — which tends to produce locally reasonable but globally wrong behavior: solving a sub-problem that doesn't actually serve the real goal, or missing a dependency between two steps that should have been sequenced differently. Planning gives the agent (and the person reviewing its behavior) an explicit, checkable structure — 'here's what I intend to do and in what order' — that can be validated before execution and re-checked against progress during it."

•

20. What is task decomposition?

Say it like this

"Breaking one complex goal into smaller, more tractable sub-goals that are each individually easier to execute and verify. 'Research competitor pricing and write a comparison report' decomposes into: identify competitors, gather each one's pricing, structure a comparison, draft the report — each sub-goal maps more cleanly to a bounded tool call or short reasoning step than the original goal does as one shot."

•

21. How does an agent break down a complex task?

Say it like this

"Typically the planner prompts the model to enumerate the sub-goals needed to reach the stated objective, checks whether those sub-goals have dependencies between them — does step 3 need step 2's output — and orders them accordingly, running independent ones potentially in parallel. I validate the resulting plan before execution starts: every referenced tool actually exists, the dependency order is achievable, the step count is within budget — a plan that fails that validation gets one bounded re-plan with the validation errors fed back in, not silently executed as-is."

•

22. What is iterative reasoning?

Say it like this

"Reasoning that unfolds across multiple steps, where each step's output informs the next — think, act, observe, think again — rather than answering everything in one shot. It's what lets an agent adapt: the third action can be genuinely different depending on what the first two actions revealed, which a single fixed-sequence pipeline can't do."

•

23. What is self-reflection?

Say it like this

"The agent (or a wrapping step) examining its own intermediate output and judging whether it's actually good — 'did this really answer the sub-goal,' 'is this evidence sufficient,' 'does this look right' — before proceeding. It's the mechanism that catches a plausible-but-wrong intermediate result before it gets built on, rather than discovering the problem only at the very end."

•

24. What is self-correction?

Say it like this

"The action taken after self-reflection flags a problem — revising the approach, retrying with different parameters, or backtracking to an earlier step, rather than reflection just being a passive observation with no consequence. Reflection without correction is just logging; the pairing of the two is what makes an agent actually recover from its own mistakes instead of merely noticing them."

•

25. How do you prevent infinite loops?

Say it like this

"A hard step cap, non-negotiable — the system-enforced backstop regardless of what the model 'thinks' it needs. Underneath that, repeat detection: hash recent (action, args) pairs, and if the same call recurs with no meaningful change in state, that's a stronger and earlier signal than the step count alone that nothing productive is happening, and I'll interrupt with a nudge ('this isn't working, try differently') or stop outright before the numeric cap is even reached." 

class LoopGuard:
    def __init__(self, max_steps=25, max_repeats=3):
        self.max_steps, self.max_repeats, self.step = max_steps, max_repeats, 0
        self.seen = {}
    def check(self, action, args):
        self.step += 1
        if self.step > self.max_steps:
            raise StepBudgetExceeded(self.step)
        key = (action, json.dumps(args, sort_keys=True))
        self.seen[key] = self.seen.get(key, 0) + 1
        if self.seen[key] > self.max_repeats:
            raise RepeatedActionDetected(key)

•

26. How do you limit reasoning steps?

Say it like this

"A hard maximum step count enforced by the harness, not the model's own sense of when it's done — plus, for cost specifically, a token and dollar budget tracked and enforced per run, since step count alone doesn't capture a run that takes few but very expensive steps. When any budget is hit, the agent must exit with whatever partial result and explanation it has, never a bare error — 'I completed X and Y but ran out of budget before Z' is a usable outcome, a silent failure is not."

D — Tool Calling
•

27. What is Tool Calling?

Say it like this

"The mechanism by which a model requests an external action — a function, API, or query — by emitting a structured call: which tool, with what arguments, rather than describing the action in prose. My code validates and executes that call, then returns the result back into the model's context as the next observation, so the model can reason about what it learned and decide the next step."

•

28. How does Tool Calling work?

Say it like this

"Each tool is registered with a name, a description the model uses for selection, and a typed argument schema. That tool set is attached to the model's context. When the model decides an action is needed, it emits a structured call matching one tool's schema instead of free text. My dispatcher validates the arguments, runs the tool, and returns a structured result (or a structured error) as the next message in the loop — the model never executes anything directly, it only ever proposes."

•

29. How do you expose APIs as tools?

Say it like this

"Wrap the API call in a typed function with a clear, narrow description of what it's for — and just as importantly, what it's not for, to keep it non-overlapping with other tools. Validate and sanitize arguments before the request goes out, normalize the response into a structured shape the model can reason about, and return failures as structured errors with a hint, not a raw exception. Anything the call could do that's consequential — a write, a state change — sits behind an explicit approval gate, treated as a dangerous action, not auto-executed."

•

30. How do you expose SQL databases as tools?

Say it like this

"Never as free-text SQL execution — a parametrized query function with a fixed, reviewed set of allowed queries or a strict argument schema (table, filters, columns), read-only credentials for lookup tools, row-count limits, and an explicit approval gate for any write path. Response comes back as structured rows, not a raw cursor dump, so the model can reason about it directly."

•

31. How do you expose Vector DBs as tools?

Say it like this

"A search function taking a query string (and optional metadata filters) and returning structured, ranked results with source attribution — the retrieval mechanics are the same as any RAG system, but treated here as just one tool among several the agent can choose to call, with a description precise enough to distinguish it from a SQL lookup tool or a web-search tool so the router isn't guessing between them."

Full retrieval-as-a-tool treatment: Agentic RAG Technical Interview QA Q13.

•

32. How does an agent decide which tool to use?

Say it like this

"It reasons over the current step against each available tool's description and picks the one whose description matches — which is why tool-selection accuracy is really a function of description quality: few tools, precisely scoped, non-overlapping trigger conditions. If two tools could both plausibly handle a step, selection accuracy drops measurably, so I fix that by rewriting descriptions or merging overlapping tools into one, rather than trying to prompt my way around ambiguous options."

•

33. How do you validate tool outputs?

Say it like this

"Schema-check the shape of what came back before it's trusted forward — never let a raw exception or malformed payload flow into the model's context as if it were valid data. I also sanity-check semantics where cheap to do so — an empty result set, an out-of-range value — and I treat all tool output as untrusted content, not just malformed-shape risk: a fetched document or API response could contain text that looks like instructions, so it gets scanned before being trusted, especially for anything the agent might act on next."

•

34. How do you handle tool failures?

Say it like this

"Split by whether the fault is transient or persistent. Transient — timeout, rate limit — retried with exponential backoff, invisible to the model. Persistent — bad arguments, a genuinely empty result — returned as a structured error with a hint so the model retries differently, not identically. Repeated failures on one tool trip a circuit breaker, so the agent stops hammering a dead dependency and either falls back or reports the tool unavailable."

Full retry/backoff/circuit-breaker code: Agentic RAG Technical Interview QA Q31–34.

•

35. How do you implement retries?

Say it like this

"Exponential backoff with jitter, only on transient faults, capped at a small number of attempts — wait roughly a second, then two, then four, doubling with a small random offset so retries don't stack in lockstep, giving up after three or four tries and surfacing a structured error rather than retrying forever."

•

36. When do you use fallback tools?

Say it like this

"When the primary tool is down, degraded, or exhausted its retries — a pre-planned alternative, decided ahead of time per tool, not improvised mid-incident. A primary payment API down might fall back to queuing the request for later rather than failing the whole task; a primary search tool down might fall back to a cached or simpler alternative. The response is labeled internally as degraded so downstream logic knows it didn't take the primary-quality path."

E — Memory
•

37. What is Memory in Agentic AI?

Say it like this

"Whatever state the agent carries across steps or across runs so it doesn't have to rediscover context it already has — the running trajectory within one task, and durable facts that should persist beyond it. Getting the split right matters: conflating a durable fact with the trimmable trajectory means a routine context-compaction step can silently delete something you actually needed to keep forever."

•

38. Short-term Memory vs Long-term Memory

Say it like this

"Short-term memory is the scratchpad for the current run — the sequence of thoughts, actions, and observations so far, needed to decide the next step, and safe to summarize or trim once it's no longer immediately relevant. Long-term memory is durable, meant to persist across runs entirely — user preferences, prior decisions, facts learned in past sessions — and needs its own storage independent of any one run's lifecycle, because it must survive after that run's short-term memory is discarded."

39. Conversation State vs Persistent Memory

Say it like this

"Conversation state is short-lived, scoped to the current session — message history, what's just been asked, what's just been retrieved — fine to disappear when the session ends. Persistent memory is durable, meant to survive across sessions entirely — a user's stated preference from last week should still apply today. The failure to watch for is storing the second inside the same object as the first: a routine trim of conversation state shouldn't be able to delete something meant to be permanent."

40. How does LangGraph Checkpointer work?

Say it like this

"A checkpointer persists the graph's full state after every node execution — to Postgres, Redis, SQLite, or in-memory for dev — keyed by a thread ID. That gives three things: crash recovery, since a failed run resumes from its last checkpoint instead of restarting from zero; human-in-the-loop pause/resume, since execution can stop at a node awaiting approval and pick back up later from exactly that point; and time-travel debugging, since you can inspect or replay from any prior checkpoint in a run's history. It's also what makes the graph-executing workers stateless — any worker can pick up any thread's next step because the state lives externally, not in that worker's memory." 

from langgraph.checkpoint.postgres import PostgresSaver

graph = builder.compile(checkpointer=PostgresSaver(conn))
result = graph.invoke(input, config={"configurable": {"thread_id": "run-123"}})
# a crash or pause here resumes from the last checkpoint for thread_id "run-123"

41. Where do you store long-term memory?

Say it like this

"Depends on the shape of what's being stored. Structured facts — user preferences, account settings — go in a regular database, keyed by user/entity ID, queried directly. Unstructured or semantically-searchable memories — 'things this user has discussed before,' relevant past interactions — go in a vector store, embedded and retrieved by similarity when relevant context is needed. I don't default to a vector store for everything; if a fact is a simple key-value lookup, a database read is faster, cheaper, and more precise than an embedding search."

•

42. When should you use Vector DB for memory?

Say it like this

"When the memory needs to be retrieved by semantic relevance rather than an exact key — 'what has this user told us that's relevant to their current question,' where I don't know in advance which specific past fact will matter. If I always know exactly which field I need — 'this user's subscription tier' — a database lookup by ID beats an embedding search on cost, latency, and precision every time. Vector-store memory earns its keep specifically for open-ended, similarity-shaped recall."

•

43. How do you retrieve memory efficiently?

Say it like this

"Same discipline as retrieval anywhere: don't pull everything, retrieve only what's relevant to the current step, cap how much gets pulled into context, and cache repeated lookups. For structured memory, index by the keys you'll actually query on (user ID, session ID). For semantic memory, the same retrieval-quality levers apply as RAG generally — right-sized top-k, metadata filtering by recency or relevance, and pruning stale or superseded facts rather than letting memory grow unbounded and noisy over time."

F — Multi-Agent Systems
•

44. What is a Multi-Agent System?

Say it like this

"Multiple specialized agents — each scoped to a narrower role or domain — coordinating on one overall task, instead of one agent trying to handle everything itself. A supervisor typically routes sub-tasks to the right specialist and synthesizes their results, though peer-to-peer coordination patterns exist too."

•

45. When should you use multiple agents?

Say it like this

"When a single agent's context or tool budget is genuinely overloaded by the breadth of what it's juggling — too many unrelated tools or domains for one agent to reason about well — or when different sub-tasks benefit from genuinely different system prompts, tools, or even models. I don't default to multi-agent; the coordination overhead is real, so I only split when a single well-guarded agent has demonstrably hit a scaling limit that splitting actually solves."

•

46. Supervisor Agent vs Specialized Agents

Say it like this

"The supervisor is the coordinator — it doesn't do domain work itself, it decides which specialist handles the current sub-task and synthesizes their results into a final answer. Specialized agents each own a narrower domain — a research agent, a coding agent, a data-lookup agent — with their own scoped tools and system prompt tuned for that domain. This topology bounds coordination cost predictably: one routing decision per hop from the supervisor, versus letting specialists freely hand off to each other, which can fan out unpredictably."

•

47. Planner Agent vs Worker Agents

Say it like this

"The Planner agent owns decomposition and sequencing — it doesn't execute domain work, it decides what needs to happen and in what order. Worker agents each execute one piece of that plan — a specific tool call or sub-task — and report results back. This split is useful when planning itself is complex enough to deserve its own dedicated reasoning, separate from the mechanics of executing any one step; it's a specialization of the general supervisor pattern, focused specifically on the planning role rather than domain routing."

•

48. How do agents communicate?

Say it like this

"Usually through shared state plus an orchestrator, not direct peer-to-peer messages — an agent writes its result into shared state (or returns it to a supervisor), and the next agent reads from that state rather than the two agents talking to each other freely. This keeps communication auditable and centrally controllable. True peer-to-peer handoff (a 'swarm' pattern) exists but trades that predictability for flexibility, and is harder to bound for cost and termination."

•

49. How do you coordinate multiple agents?

Say it like this

"A supervisor owns routing and termination — decides which specialist acts next and when the overall task is done — rather than letting agents freely delegate to each other indefinitely. I enforce a global step/cost budget across the whole system, not just per agent, since a per-agent cap alone doesn't stop N agents from collectively blowing the total. And I define explicit termination rules — 'stop when the critic approves' or 'after K rounds' — rather than leaving 'when are we done' as an implicit judgment call."

•

50. How do you prevent conflicting actions?

Say it like this

"A single source of truth for any shared state, with concurrency control on writes — two agents shouldn't be able to independently mutate the same resource without coordination. For genuinely conflicting outputs (two agents proposing different answers), the supervisor's synthesis step should surface the conflict explicitly rather than silently picking one, and for consequential actions specifically, I serialize execution through the supervisor rather than letting agents act on shared resources concurrently and unsupervised."

51. Why LangGraph instead of LangChain?

Saycyclic, stateful
Say it like this

"LangChain is built around linear or lightly-branching chains — good for a fixed pipeline of steps. LangGraph is built for cyclic, stateful control flow — an agent looping, re-planning, and conditionally branching based on runtime state, which a chain's DAG-without-cycles model doesn't naturally express. LangGraph also gives you first-class state persistence via a checkpointer, which is what makes crash recovery and human-in-the-loop pausing possible — LangChain's chains don't have that built in. I'd reach for LangGraph specifically when the control flow needs to loop or branch conditionally based on what happens at runtime, not just execute a fixed sequence."

52. What is StateGraph?

Say it like this

"The core LangGraph abstraction — a graph where nodes are functions (each takes the current state and returns updates to it) and edges define allowed transitions between them, some of them conditional on the state. It compiles into an executable graph that runs the loop: enter a node, apply its state update, follow an edge to the next node, repeat until reaching an end state."

graph.add_node("plan", plan_node)
graph.add_node("act", act_node)
graph.add_edge("plan", "act")

53. What is AgentState?

Say it like this

"The typed schema for everything that flows through the graph — messages, intermediate results, step count, whatever the agent needs to carry between nodes. Every node reads from it and returns updates to it; LangGraph merges those updates according to how each field is defined (e.g. append to a list, or overwrite a value). Keeping this schema tight and well-typed is what makes a graph's behavior predictable and debuggable — a sprawling, loosely-typed state object is a common source of bugs where one node accidentally clobbers a field another node needed." 

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]   # appends, doesn't overwrite
    plan: list[str]
    step_count: int

54. What are Nodes?

Say it like this

"Individual functions in the graph — each one takes the current state, does some work (a model call, a tool call, a routing decision), and returns an update to the state. A node is the unit of execution; the graph is just the wiring between nodes plus the rules for what happens next."

•

55. What are Edges?

Say it like this

"The connections that define what node runs next after a given node finishes. A plain edge is unconditional — node A always leads to node B. They're what make the graph a graph rather than just a list of functions — the execution order is defined by the edges, not by call-site sequencing in code."

•

56. What are Conditional Edges?

Say it like this

"Edges whose destination is decided at runtime by a function that inspects the current state — 'if the grading score is above threshold, go to generate; otherwise, go to retry.' This is the mechanism that gives LangGraph its branching/looping power: without conditional edges, a graph is just a fixed sequence; with them, the actual path taken depends on what happened during execution." 

graph.add_conditional_edges(
    "grade",
    lambda state: "generate" if state["score"] >= 0.7 else "retry",
    {"generate": "generate_node", "retry": "retry_node"},
)
•

57. What is a Checkpointer?

Say it like this

"The persistence layer that saves the graph's state after every node, keyed by thread ID — covered in depth in Q40. In short: it's what turns a graph run from an ephemeral in-process execution into something that survives a crash, can pause for human approval, and can be replayed or inspected after the fact."

•

58. What are Interrupts?

Say it like this

"An explicit pause point in the graph — execution stops before or after a specified node and waits for external input (usually a human decision) before continuing, using the checkpointer to persist state during the pause. This is the primitive human-in-the-loop is built on: interrupt_before=["execute_dangerous_action"] means the graph runs up to that node, saves state, and returns control to the caller, who can inspect the proposed action and choose to resume, modify state, or abort." 

app = graph.compile(checkpointer=checkpointer, interrupt_before=["execute_payment"])
app.invoke(input, config)          # runs up to execute_payment, then pauses
# ... human reviews the proposed action ...
app.invoke(None, config)            # resumes from the interrupt
•

59. Human-in-the-loop in LangGraph

Say it like this

"Built on interrupts (Q58): identify the dangerous or consequential node — a payment, a delete, a send — and set it as an interrupt point. The graph runs up to it, persists full state via the checkpointer, and hands control back. A human reviews the proposed action with full context, and either approves (resume as-is), edits the state (resume with modified arguments), or rejects (route to an alternate path or abort). This is a first-class part of the graph's design, not an afterthought bolted on — the interrupt point is chosen deliberately at design time, before any incident."

•

60. Parallel execution in LangGraph

Say it like this

"When multiple nodes are independent — don't depend on each other's output — LangGraph can fan them out to run concurrently, using something like the Send API to dispatch multiple parallel invocations of a node (e.g. one per independent sub-task) and then merge their results at a downstream join node. This is the mechanism behind, for example, running several independent tool calls or sub-question retrievals at once instead of sequentially — usually the single biggest latency win available before touching model-level optimizations at all."

Say it like this

"Never free-text SQL generation executed directly — the agent proposes a query intent, and a constrained layer either maps it to a fixed, reviewed set of parametrized queries, or validates a generated query against a strict allow-list (read-only, row-limited, no DDL/DML unless explicitly a write-capable tool behind approval). I'd add a schema-awareness step — giving the agent the actual table/column schema rather than letting it guess — and a result-sanity check (row count, expected shape) before the result is trusted forward into an answer."

•

65. Design a Code Generation Agent

Say it like this

"Tools: a code-execution sandbox (isolated, no network, dropped privileges, resource-limited), a test runner, and file read/write scoped to a working directory. Flow: generate code, run it in the sandbox, check test results or output against the goal, and if it fails, feed the error back and retry — a tight generate-execute-verify loop, capped at a small number of iterations. The sandbox isolation is the non-negotiable safety piece here — code execution is one of the highest-risk tool types, so it never runs with real system privileges or network access unless that's explicitly and narrowly granted for the task."

•

66. Design an Email Automation Agent

Say it like this

"Tools: an email-search/read tool and an email-send tool, kept as two separate tools with very different risk profiles. Reading is auto-executed; sending is a dangerous action behind human-in-the-loop approval by default — I'd surface the drafted email for review before it goes out, especially early in deployment, and only consider relaxing that gate for narrow, well-tested categories (like an auto-acknowledgment) once trust is established. This is a direct callback to the error-compounding risk in general agent failure modes: a wrong recipient or wrong fact built on an earlier bad lookup becomes an irreversible sent email if there's no approval gate."

•

67. Design a Travel Planning Agent

Say it like this

"Tools: flight search, hotel search, and a budget/constraint checker. The planner decomposes 'plan a trip within budget' into ordered sub-goals — find flight options, find hotel options, check the combination against the budget constraint, iterate if over budget. This is a good example of genuinely dependent sequential steps (the hotel search should be informed by how much budget the flight consumed) as opposed to independent ones — so it's not a candidate for the parallel-fan-out speedup that independent sub-questions get; it's inherently a step-by-step negotiation against a constraint."

I — Reliability
•

69. How do you handle tool failures? (system-level)

Say it like this

"Q34 covers per-call recovery. At the system level on top of that: alert on circuit-breaker trip rate per tool as a leading indicator of a downstream outage, and track fallback-path usage rate, since a rising fallback rate for one tool should page someone before it becomes a full outage. I also make sure every tool failure — even a successfully-recovered one — is logged with enough context to spot a pattern across many runs, not just handled silently in the moment."

•

70. How do you debug agent failures?

Say it like this

"Pull the full trajectory trace and walk it forward, because agent failures are rarely one exception — they're usually a wrong decision several steps upstream of where things visibly broke. I check: did the planner decompose badly, did the router pick the wrong tool, did the agent trust a bad tool result forward uncritically, or did the final synthesis ignore good intermediate evidence. Then I check whether it's isolated to one input or systemic, and if systemic, whether it correlates with a recent deploy, prompt change, or model version bump."

•

71. How do you retry failed executions?

Say it like this

"Same principle as tool-level retries (Q35), applied at whatever granularity makes sense — a failed tool call retries at the call level; a failed overall run, if worth retrying at all, should resume from its last checkpoint rather than restart from scratch, which is exactly what a persisted checkpointer (Q40) makes possible. I only retry when the failure looks transient — retrying a run that failed because of a genuinely bad plan just reproduces the same bad plan."

•

72. How do you implement circuit breakers?

Say it like this

"Same pattern as file 24's tool circuit breaker: after N consecutive failures on a dependency, open the breaker — for a cooldown window, skip straight to a fallback or a structured 'unavailable' response instead of continuing to call the failing dependency — then allow a trial call through after the cooldown, closing the breaker again on success."

Code: Agentic RAG Technical Interview QA Q34.

•

73. How do you handle API rate limits?

Say it like this

"Respect the provider's rate-limit signal (429s, Retry-After headers) with backoff sized to what the header actually tells me, rather than a generic retry schedule. At the design level, I bound concurrent calls with a semaphore so I'm not bursting past the limit in the first place, and for high-volume agent workloads I'd batch or queue requests rather than firing them as fast as the loop can go. A sustained rate-limit issue is also a signal to consider a secondary provider or a cached/degraded path rather than just retrying harder."

•

74. How do you implement fallback models?

Say it like this

"On a primary model's timeout, error, or sustained rate-limiting, route to a secondary model or provider — decided ahead of time, not improvised — and if even that's unavailable, degrade to a cached or canned response rather than a bare error. I keep the fallback model's prompt/output format compatible with the primary's so the rest of the pipeline doesn't need to know which one actually answered, and I log which model served each request so a quality dip is traceable to the fallback path, not silently blamed on the primary."

J — Evaluation
•

75. How do you evaluate AI Agents?

Say it like this

"Two axes: outcome — did the agent actually accomplish the goal, correctly — and trajectory — was the path it took to get there reasonable: right tools, right order, no wasted steps, sensible recovery from any bad intermediate result. A system can score well on outcome while being badly inefficient or having gotten lucky on trajectory, so I report both, especially when justifying an agent's extra cost and complexity over a simpler pipeline."

Full outcome/trajectory framework: Agent Evaluation.

•

76. How do you test planner decisions?

Say it like this

"Against a labeled set of (goal → expected decomposition) pairs — did the planner produce a reasonable set of sub-goals, in a workable order, without over- or under-decomposing. I score this independently of whether the final outcome happened to be correct, because a planner that decomposes a simple task into five unnecessary steps is a real cost bug even when the eventual answer comes out fine."

•

77. How do you evaluate tool selection accuracy?

Say it like this

"Against a labeled set of (step → correct tool) pairs, scored as a straightforward classification problem — precision/recall per tool — kept separate from end-to-end answer quality, since a wrong tool pick that accidentally still produces a right answer would otherwise hide the actual failure. This is usually the most fixable metric in the whole eval suite; a low score is very often just a tool description that needs rewriting."

•

78. How do you evaluate reasoning quality?

Say it like this

"An LLM-judge (or human reviewer) reads the intermediate reasoning steps, not just the final answer, and scores whether each step logically follows from the last and actually serves the stated goal — catching cases where the agent arrived at a correct answer through faulty or lucky reasoning, which matters because that reasoning pattern won't generalize to the next, slightly different input."

•

79. How do you perform regression testing?

Say it like this

"Run a version-controlled golden dataset — labeled (goal → expected outcome and, where possible, expected trajectory) pairs, including known past-incident cases — through the system in CI on every prompt, model, or tool-config change, comparing both outcome and trajectory metrics against the last known-good baseline, not an absolute threshold alone. A change that improves outcome accuracy but doubles average step count is a regression I want caught, which is exactly why trajectory metrics need to be part of the gate, not just outcome correctness."

•

80. How do you test agent trajectories?

Say it like this

"Compare a live or eval-set trajectory against an expected shape: how many steps did it take, did it call the tools I'd expect for this kind of goal, did any reflection/verification step actually catch and correct a bad intermediate result the way it should have. I sample this especially on runs where the outcome was correct but I suspect the path was wasteful, since outcome-only evaluation would score those as a pass and hide the inefficiency."

K — Observability
•

81. How do you monitor AI Agents?

Say it like this

"Three layers: distributed tracing so every model call, tool call, and decision is visible as a span; a metrics dashboard covering both system health (latency, error rates, cost) and decision quality (tool-selection accuracy, step efficiency); and sampled live evaluation running trajectory/outcome checks against real production traffic, not just an offline eval set that can drift out of date with actual usage patterns."

•

82. What metrics would you collect?

Say it like this

"System: p50/p99 latency per step type, error rate per tool, circuit-breaker trip rate, cost and steps per run — tracked as distributions, not just averages, since a runaway outlier hides inside an average. Decision quality: tool-selection accuracy, planner-decomposition quality against labeled samples, step-cap-hit rate — a rising step-cap-hit rate is often a sign the task distribution has shifted, not that the cap needs raising."

•

83. How do you trace an agent's execution?

Say it like this

"Every model call, tool call, and routing/planning decision instrumented as a span, linked by a propagated run/trace ID — OpenTelemetry as the vendor-neutral standard, or an LLM-specific tool like LangSmith/Langfuse. Without per-span tracing a multi-step agent is opaque: you can see a run was slow or wrong, but not which step, which is exactly the information needed to actually fix anything."

•

84. How do you monitor tool latency?

Sayper tool
Say it like this

"p50/p99 tracked per tool, not one aggregate number — tools have wildly different latency profiles, and an aggregate hides which specific one is the actual bottleneck. I alert on p99 crossing a threshold per tool, which is directly actionable, versus an aggregate 'agent is slow' alert, which isn't."

•

85. How do you monitor token usage?

Say it like this

"Per step, not just per run, to see whether tokens concentrate in one step (usually final synthesis, since it carries the most accumulated context) or spread evenly — that tells me where a context-trimming fix would actually help. Tracked as a distribution across runs, with outliers flagged, since a run consuming several times the median tokens for its task type is often a runaway loop or an unbounded context, not normal variance."

•

86. How do you monitor costs?

Say it like this

"Cost per run rolled up from per-step token usage and any per-call tool costs, tracked as a distribution with outlier alerting — the same discipline as token monitoring, since cost is downstream of it. I also track cost by task type/category so a cost regression is attributable to a specific workflow, not just visible as an aggregate bill increase after the fact."

•

87. How do you monitor agent loops?

Say it like this

"Repeat-action rate — how often the same (tool, args) pair recurs within a run — as the earliest signal of a stuck loop, well before the numeric step cap fires. Alongside that, step-cap-hit rate and average steps-to-completion by task type, since a creeping increase in either is often the first visible sign of a prompt or tool-description regression before it shows up as a user-facing complaint."

L — Security
•

88. How do you secure AI Agents?

Say it like this

"Least-privilege everywhere — the agent proposes, a constrained layer executes only allow-listed, validated actions, never raw execution power. Every tool input validated against a schema, every tool output treated as untrusted content. Dangerous actions sit behind human-in-the-loop approval. Access control (RBAC) governs which tools and data a given agent instance can even reach, scoped to the authenticated user or context it's running for. And everything is audit-logged, with a safe default (not-executed) on any approval timeout."

Full checklist: Agentic AI Failure Modes §7, LLM Guardrails and Safety.

•

89. How do you prevent prompt injection?

Say it like this

"Treat any content the agent didn't originate itself — a fetched web page, a tool result, a retrieved document — as untrusted data, never as instructions, and scan it for injection patterns before it's allowed to influence subsequent actions. Structurally, I separate the system prompt/instructions from untrusted content in the message structure so the model has a clearer signal about what's a command versus what's data, and I make sure fetched/tool-returned text can never grant new capabilities or silently bypass an approval gate, no matter what it says."

•

90. How do you validate tool inputs?

Say it like this

"Schema validation before execution — types, ranges, allow-lists — rejecting hallucinated or malformed arguments rather than executing them and hoping. Beyond shape validity, I add semantic guards for anything dangerous: row-count limits, scope restrictions, dry-run checks — validity isn't the same thing as safety, a perfectly well-typed DELETE WHERE 1=1 is still a disaster."

•

91. How do you implement RBAC for tools?

Say it like this

"Scope which tools an agent instance can even see and call based on the authenticated user or context it's running for — an HR agent serving employee A should not have access to a tool that can query employee B's records, enforced at the tool-authorization layer, not just hoped for via a well-written prompt. Concretely: tool registration/dispatch checks the caller's role/permissions before the tool is even exposed in that run's available tool set, and again before execution, so a compromised or confused planning step can't route around the restriction." 

def get_available_tools(user):
    return [t for t in ALL_TOOLS if user.role in t.allowed_roles]

def execute_tool(name, args, user):
    tool = TOOLS[name]
    if user.role not in tool.allowed_roles:
        return {"error": "forbidden", "hint": "insufficient permissions"}
    return tool.run(**args)
•

92. How do you prevent unauthorized tool execution?

Say it like this

"Authorization checks at the point of execution, not just at tool-listing time — verify the caller's permissions again right before the call runs, since state can change between when a plan was formed and when it's executed. Dangerous actions get an explicit human approval gate regardless of role. And every execution is audit-logged with who/what/when/args, so an unauthorized attempt — even a blocked one — is visible after the fact, not silently dropped."

•

93. How do you protect sensitive data?

Say it like this

"Scrub or mask PII/secrets in anything that flows into the model's context or gets logged, scope data access by RBAC (Q91) so an agent only ever sees what it needs for the current task, and run output scanners before a response ships to catch anything sensitive that slipped through generation. I also make sure tool results containing sensitive data aren't retained longer than the run needs them, and that long-term memory (Q41) specifically is audited for what it's persisting — a memory system is a much longer-lived exposure surface than a single run's context."

M — Production
•

94. How do you deploy AI Agents?

Say it like this

"Behind a versioned API, with the graph/workflow definition, prompts, and tool configs all version-controlled together as one deployable unit — so a rollback is a single version pointer change, not reconstructing which prompt went with which graph version from memory. State lives externally (a checkpointer), so the serving layer itself is stateless and can be deployed/scaled like any other stateless service. I'd gate a new version behind the same regression eval suite (Q79) before it takes production traffic, and roll out gradually — canary or percentage-based — rather than a hard cutover."

95. How do you scale AI Agents?

SayScaling leversStateless orchestrationParallelize independent workGlobal + per-run step/cost budgetsScale each layer independently
Say it like this

"Externalize state to a checkpointer so orchestration workers are stateless and horizontally scalable behind a queue. Parallelize independent tool/sub-agent calls — usually the biggest single latency and throughput win, before any model-level change. Enforce a global step/cost budget so one runaway run can't consume capacity meant for others. And scale each layer independently — the orchestration layer, the tool-execution layer, and the model-serving layer have different bottlenecks and shouldn't share one blanket autoscaling policy."

Scaling levers: - Stateless orchestration — externalize all state to a checkpointer so workers hold nothing in memory between steps; scale them horizontally behind a queue like any stateless service. - Shard/replicate the checkpointer store itself as thread/run volume grows — shard by thread_id/tenant once one node's checkpoint volume outgrows it (capacity), add read replicas for state reads like dashboards/audits so they don't compete with the write path (throughput/availability) — the same shard-for-capacity-vs-replicate-for-QPS distinction as scaling a vector index. - Parallelize independent work — fan out independent tool/sub-agent calls concurrently (Send-style fan-out); usually the single biggest throughput win before any model-level change. - Global + per-run step/cost budgets — bounds blast radius so one runaway trajectory can't starve capacity meant for everyone else. - Scale each layer independently — orchestration (I/O-bound), tool execution (bound by the downstream system), and model serving (compute-bound) don't share one bottleneck or one autoscaling policy. - Route by queue depth, not round-robin; prefer backpressure (a controlled reject) over unbounded queueing when a downstream tool/DB saturates. - Autoscale on queue depth/p99 latency, not CPU% — LLM-serving saturates memory/compute in ways CPU% doesn't reflect. - Few, scoped, non-overlapping tools per agent — group into specialist agents/MCP servers as the tool surface grows, rather than one agent holding every tool. - Supervisor topology by default for multi-agent — justify any split against a single-agent call-count baseline; N agents means N× the steps before coordination overhead. - Cache deterministic tool calls by (tool, args), reusable across entirely different runs, not just within one. - Distill narrow, repeated sub-tasks (routing, classification, arg-formatting) onto small models so they don't compete with frontier-model calls for capacity. - Distributed tracing with a propagated run ID — the prerequisite for knowing which layer actually needs scaling, not optional.

96. How do you reduce latency?

SayLatency leversReserve the frontier modelCache aggressivelyCap hops/steps tightlyPrefix/prompt caching
Say it like this

"Parallelize independent steps first — it's free, no model change needed, and usually the biggest win. Use small/distilled models for narrow, repeated judgment calls (routing, classification, arg formatting), reserving the frontier model for the step that actually needs deep reasoning. Cache aggressively — repeated or near-identical tool calls and prompts. And trace per-step so I'm optimizing the actual bottleneck, not guessing."

Latency levers: - Parallelize independent tool/sub-agent calls — free, no model change, usually the biggest single win (three independent tool calls run sequentially at ~1.8s often collapse to ~1.05s from fan-out alone). - Distill narrow, repeated judgment calls (routing, grading, arg-formatting) onto small models — tens of milliseconds instead of hundreds. - Reserve the frontier model for the one step that genuinely needs deep reasoning. - Cache aggressively — tool-result cache keyed on (tool, args) for deterministic calls; semantic/result cache in front of the whole loop for repeated or near-duplicate requests. - Cap hops/steps tightly — every extra step is a full extra round of latency; the step cap is a latency ceiling, not just a safety guardrail. - Prefix/prompt caching — cache the KV of the static system-prompt/tool-schema prefix shared across every call. - Stream tokens to the user — doesn't reduce total latency, but cuts perceived latency to first token, which is what's actually judged. - Continuous batching + autoscale on queue depth for the model-serving layer under bursty traffic. - Trace per-step first — never guess which layer is slow; optimize the actual bottleneck, not an assumed one.

97. How do you reduce costs?

SayCost leversModel cascading/distillationTight step/hop capCache deterministic tool callsCache at the semantic/result level
Say it like this

"Same core lever as latency: cheap/distilled models for narrow sub-tasks, frontier model reserved for the step that needs it. Cap steps tightly — the step cap is a cost ceiling as much as a safety guardrail. Cache deterministic tool calls so retries and repeated sub-tasks don't re-pay the same cost. And measure cost per run as a distribution regularly, since prompt or model drift can quietly grow average cost over time without anyone noticing until the bill does."

Cost levers: - Model cascading/distillation — cheap/distilled models for narrow, repetitive judgment calls (routing, grading, classification, arg-formatting); frontier model reserved only for the step that needs it. - Tight step/hop cap — the primary cost ceiling on the whole run, since every extra step is a full extra LLM (and often tool) call. - Cache deterministic tool calls by (tool, args) — retries and repeated sub-tasks don't re-pay the same cost. - Cache at the semantic/result level — a repeated or near-duplicate request pays nothing at all. - Global + per-run token/cost budgets enforced, not just monitored, so drift or a runaway run can't silently blow the bill. - Trim/summarize context — carrying the full trajectory into every call inflates every subsequent call's token cost; summarize older steps, keep the goal pinned outside the summarizable region. - Measure cost per run as a distribution, regularly — prompt or model drift quietly grows average cost over time without a single visible spike. - Justify multi-agent splits against a single-agent call-count baseline — coordination overhead is a real, quantifiable cost, not free.

•

98. How do you cache tool results?

Say it like this

"Keyed on (tool, args) for deterministic calls — a SQL lookup or a static API response with the same arguments returns the same result, so caching it means a repeat call is instant instead of re-hitting the downstream system, whether the repeat happens within one run's retries or across entirely different runs. Non-deterministic tools (anything with a time component, or genuinely live data) either aren't cached or get a short, explicit TTL — I never cache something that could silently serve stale data as if it were current."

•

99. How do you version agent workflows?

Say it like this

"The graph/workflow definition, the prompts, and the tool configurations are versioned together as one unit, not independently — a prompt change and a graph change shipped separately make it much harder to know which combination produced a given behavior. I tag each production run with the workflow version that served it, so a regression can be traced to exactly which version introduced it, and I keep the previous version deployable for rollback."

•

100. How do you safely update agents without downtime?

Say it like this

"Blue-green or canary rollout, same principle as any production service — the new version runs alongside the old one, takes a small percentage of traffic (or shadow traffic with no user-facing effect), gets compared against the old version's metrics and the regression eval suite (Q79), and only fully cuts over once validated. State compatibility matters specifically for agents: if the AgentState schema changed, in-flight runs checkpointed under the old schema need either a migration path or to be allowed to drain on the old version before it's fully retired."

N — Scenario-Based Questions
•

101. Design an end-to-end Agentic AI platform

Say it like this

"Layered: an orchestration layer (LangGraph-style state machine, stateless workers behind a checkpointer), a tool registry with schema validation and RBAC-scoped access per agent, a planning layer for decomposing complex goals, memory (short-term per-run + long-term persistent store), and a safety layer (approval gates for dangerous actions, guardrails on input/output). Underneath: distributed tracing, a metrics/cost dashboard, and a golden-dataset eval suite gating every deploy. On top: a supervisor pattern for multi-agent coordination when a single agent's scope genuinely outgrows what one agent should handle. The platform question interviewers are really asking is whether I understand that reliability, safety, and observability aren't features bolted onto an agent — they're structural layers the whole system is built around from the start."

•

102. Build a multi-agent customer support system

Say it like this

"A supervisor routes incoming tickets to specialist agents — a billing agent (order/payment API access), a technical-support agent (knowledge-base + diagnostics tools), and an escalation agent (human handoff). Each specialist owns its own scoped tools and system prompt; the supervisor synthesizes if a ticket spans domains and owns the overall conversation state across the interaction. Every consequential action (refund, account change) sits behind human approval. I'd measure this specifically against a single well-scoped support agent's call-count baseline before committing to the multi-agent split, per the general 'does the split earn its coordination overhead' rule."

•

103. Build an AI research assistant using LangGraph

Say it like this

"A StateGraph with nodes for plan (decompose the research question), search (a tool-calling node, possibly fanned out in parallel via Send for independent sub-questions), reflect (grade whether gathered evidence is sufficient — a conditional edge routes back to search if not, capped by a hop count in state), and synthesize (final cited write-up). A checkpointer persists state so a long-running research task survives an interruption and can resume. I'd add an interrupt_before on the synthesize node for high-stakes research so a human reviews the evidence before the final report is generated, not just after."

•

104. An agent keeps selecting the wrong tool — how would you debug it?

Say it like this

"Check whether it's isolated to one input or systemic — systemic points at the tool descriptions. The most common cause is overlapping trigger conditions: two tools that could both plausibly handle the step, leaving the model with no reliable signal for which to pick. I'd rewrite the descriptions to be genuinely non-overlapping or merge the tools if they truly overlap in scope, then verify against the tool-selection eval set (Q77) that the fix actually moved the metric, not just fixed the one example I was staring at."

•

105. An agent enters an infinite loop — how would you stop it?

Say it like this

"Immediately: the hard step cap and repeat-action guard (Q25) should already be limiting the blast radius — if they're not firing, that's the first bug to fix. Root cause: pull the trajectory and look at what's recurring — usually either a tool returning a vague/empty result that never satisfies the model, which needs a better structured error/hint so it retries differently, or a reflection/grading step that's miscalibrated and never accepts a result as sufficient, which needs recalibration against labeled samples."

•

106. Multiple agents return conflicting answers — how would you resolve it?

Say it like this

"The supervisor's synthesis step should never silently pick one — it should surface the conflict explicitly, attribute each claim to its source agent, and either apply an explicit tie-breaking rule (recency, source authority) if one exists for this domain, or escalate to a human when the conflict is genuinely unresolvable automatically. Silently picking one is the worst option: it hides that a disagreement happened at all, which means nobody investigates why two specialists disagreed in the first place."

•

107. A tool is unavailable — how should the agent recover?

Say it like this

"The circuit breaker (Q72) should already have tripped and be routing to a fallback path or reporting the tool unavailable rather than continuing to hammer it. If a fallback exists — a secondary data source, a cached last-known-good value — the agent uses it and labels the resulting output as degraded. If no fallback exists and the tool is essential to the goal, the agent should abstain and report clearly what it couldn't complete and why, rather than forcing a low-confidence result or silently omitting that step."

•

108. How would you add Human-in-the-Loop approval?

Say it like this

"Identify the consequential node — a payment, a delete, a send — and set it as a LangGraph interrupt point (Q58/Q59): the graph runs up to it, persists state via the checkpointer, and hands control back with the proposed action and full context surfaced for review. A human approves (resume as-is), edits (resume with modified arguments), or rejects (route to an alternate path). I'd choose these gate points deliberately at design time based on reversibility and blast radius, not retrofit them reactively after an incident."

•

109. When would you choose a single agent over multiple agents?

Say it like this

"By default, honestly — a single well-guarded agent with a good tool set handles most tasks, and the call-count math almost always favors it: three specialist agents at five steps each is fifteen calls before any retry, against a single agent doing the same task in maybe six larger steps. I'd only split into multiple agents when a single agent's context or tool budget is demonstrably overloaded — too many unrelated domains or tools for one agent to reason about well — not because multi-agent sounds more sophisticated."

•

110. Explain your Agentic AI architecture in under two minutes

Say it like this

"I build agents as a loop wrapped in guardrails, not a free-form autonomous system. The loop: decide, act through a validated tool call, observe, decide again — with a planner up front for complex goals and a reflection step checking results along the way. The guardrails: every tool call is schema-validated and RBAC-scoped before it runs, dangerous actions sit behind human approval, a hard step-and-cost budget bounds every run, and state is externalized so runs survive crashes and can be paused for review. State and memory are split cleanly — short-term trajectory that's safe to trim, long-term facts that aren't. Everything is traced end to end, because none of the recovery or safety behavior is worth anything if I can't see it happening. That combination — autonomy where it earns its keep, and hard boundaries everywhere else — is what makes the system something I'd actually put in front of real users and real actions, not just a demo."
