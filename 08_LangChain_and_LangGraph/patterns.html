Pattern 1: ReAct

Core Idea

Reason + Act in a loop. The LLM decides whether to: - Call a tool (Act) - Return a final answer (Reason)

You feed the tool result back into the message history, and loop until the model stops calling tools.

Why it's the baseline: It's simple, general-purpose, and works for ~80% of single-agent problems. Reach for anything fancier only when you can name what ReAct can't do.

From Scratch (Whiteboard Version)

from typing import Annotated, TypedDict
from langchain_core.messages import AnyMessage, HumanMessage, AIMessage
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode, tools_condition
from langchain_openai import ChatOpenAI
import json

# 1. Define state schema
class State(TypedDict):
    """State contains only messages; add_messages reducer appends new ones."""
    messages: Annotated[list[AnyMessage], add_messages]

# 2. Define tools
def get_weather(city: str) -> str:
    """Get the weather for a city."""
    return f"Weather in {city}: Sunny, 72°F"

def calculate(expression: str) -> str:
    """Evaluate a math expression."""
    try:
        result = eval(expression)
        return f"Result: {result}"
    except Exception as e:
        return f"Error: {str(e)}"

tools = [get_weather, calculate]

# 3. Create LLM with tools bound
llm = ChatOpenAI(model="gpt-4o", temperature=0)
llm_with_tools = llm.bind_tools(tools)

# 4. Agent node: calls LLM, LLM decides to call tool or answer
def agent(state: State):
    """Agent node: invoke LLM with current message history."""
    response = llm_with_tools.invoke(state["messages"])
    return {"messages": [response]}

# 5. Build graph
builder = StateGraph(State)
builder.add_node("agent", agent)
builder.add_node("tools", ToolNode(tools))

# 6. Wire edges
builder.add_edge(START, "agent")
builder.add_conditional_edges(
    "agent",
    tools_condition,  # If tool calls present -> "tools"; else -> END
)
builder.add_edge("tools", "agent")  # Loop back to agent after tool execution

graph = builder.compile()

# 7. Run it
result = graph.invoke({
    "messages": [HumanMessage(content="What's the weather in NYC? Then calculate 5 * 6.")]
})
print(result["messages"][-1].content)

Key insight: add_messages reducer is crucial — it appends new messages instead of overwriting. Without it, you'd lose the history and the loop would fail.

Prebuilt (One-Liner)

from langgraph.prebuilt import create_react_agent
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o")
agent = create_react_agent(llm, tools)

Trade-off: The one-liner hides the StateGraph; you lose control over the state schema and edge logic. For interviews, know both.

Interview Points

  • Explain the loop: agent → tools → agent → ... → agent (returns answer) → END
  • Why add_messages? Without the reducer, each new message overwrites the history; the loop breaks because context is lost.
  • Stopping condition: tools_condition checks if the latest AI message has tool_calls; if not, routes to END.
  • Latency concern: Every tool call triggers a new LLM invoke; unpredictable workflows can rack up token cost fast.
Pattern 2: Reflection (Reflexion)

Core Idea

Output quality as the bottleneck. A generator drafts an answer; a critic evaluates it; you loop back to regenerate with the critique in context. Stop on a quality signal or a hard iteration cap.

Reflection vs. Reflexion: - Reflection: Critique stays in-context (cheap, conversational, one pass). - Reflexion: Critique is distilled into durable lessons stored in persistent memory (expensive, reusable across attempts).

Use Reflection for single-request quality; use Reflexion for repeated agents that learn.

Code Example

from typing import Annotated, TypedDict
from langchain_core.messages import HumanMessage, AIMessage
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langchain_openai import ChatOpenAI

class ReflectionState(TypedDict):
    """Track drafts, critiques, and iteration count."""
    messages: Annotated[list, add_messages]
    iterations: int
    quality_score: float

generator_llm = ChatOpenAI(model="gpt-4o")
critic_llm = ChatOpenAI(model="gpt-4o")

def generate(state: ReflectionState):
    """Generate or revise the answer using full history (drafts + critiques)."""
    response = generator_llm.invoke(state["messages"])
    return {
        "messages": [response],
        "iterations": state.get("iterations", 0) + 1
    }

def critique(state: ReflectionState):
    """Critic evaluates the latest draft and provides actionable feedback."""
    feedback = critic_llm.invoke(
        state["messages"] + [HumanMessage(
            content="Rate this answer 1-5 and suggest improvements. Be specific."
        )]
    )
    return {"messages": [feedback]}

def should_continue(state: ReflectionState) -> str:
    """Route: either reflect again or end."""
    if state["iterations"] >= 3:  # Hard cap — non-negotiable in production
        return "end"
    # Could also check quality_score or keyword in latest message
    if "perfect" in state["messages"][-1].content.lower():
        return "end"
    return "critique"

builder = StateGraph(ReflectionState)
builder.add_node("generate", generate)
builder.add_node("critique", critique)
builder.add_edge(START, "generate")
builder.add_conditional_edges(
    "generate",
    should_continue,
    {"critique": "critique", "end": END}
)
builder.add_edge("critique", "generate")

graph = builder.compile()

# Run it
result = graph.invoke({
    "messages": [HumanMessage(content="Write a haiku about AI.")],
    "iterations": 0,
    "quality_score": 0.0
})
print(result["messages"][-1].content)

When to Use

  • High-stakes outputs: Legal docs, technical specifications, creative writing where revision matters.
  • Deterministic critiques: When you can define "good" clearly (length, tone, accuracy, format).
  • Token budget exists: Reflection multiplies tokens; only use if cost is acceptable.

Common Pitfalls

  1. No hard iteration cap: Critic keeps finding faults forever (runaway cost, infinite loop).
  2. Vague critique prompt: Critic says "improve quality" instead of "fix grammar and reduce jargon" — generator ignores it.
  3. Ignoring negative signal: If critique says "good as-is," stop immediately instead of looping.
Pattern 2B: Reflexion (Verbal RL with Episodic Memory)

Reflexion is Reflection's bigger sibling. Reflection improves one answer in one pass; Reflexion improves an agent across repeated attempts by turning each failure into a durable, reusable lesson. (Shinn et al., 2023 — "Reflexion: Language Agents with Verbal Reinforcement Learning".)

Core Idea

Learn from failure without touching the weights. The agent attempts the whole task, an evaluator scores the attempt, and a self-reflection step distills why it failed into a short verbal lesson. That lesson is written to an episodic memory buffer and injected into the next attempt's context. Over several trials the agent "learns" — purely through accumulated natural-language feedback. That's why it's called verbal reinforcement learning: the reflections act like a reward signal expressed in words instead of gradients.

The three roles

ComponentJobTypical implementation
ActorAttempt the task end-to-endOften a ReAct agent (tools + loop) or a CoT chain — Reflexion wraps an inner pattern
EvaluatorProduce a reward/score for the trajectoryUnit tests / exact-match / heuristic, or LLM-as-judge
Self-ReflectionConvert (trajectory + low score) → actionable verbal lessonA separate LLM call, higher temperature

The glue is the episodic memory: a list of lessons that survives across trials (and, with a checkpointer/store, across sessions).

Each retry sees all prior lessons, so the actor stops repeating mistakes. - Hard cap on trials (3–5) — every trial is a full task attempt, so cost grows fast. - No fine-tuning. Adaptation is entirely in-context (language), which is why it's cheap to ship vs. RLHF.

Code Example

import operator
from typing import Annotated, TypedDict
from langchain_core.messages import HumanMessage
from langgraph.graph import StateGraph, START, END
from langchain_openai import ChatOpenAI

class ReflexionState(TypedDict):
    task: str
    memory: Annotated[list[str], operator.add]  # lessons distilled from PAST failed trials
    last_attempt: str
    score: float
    trial: int

actor_llm     = ChatOpenAI(model="gpt-4o", temperature=0.4)
evaluator_llm = ChatOpenAI(model="gpt-4o", temperature=0)
reflect_llm   = ChatOpenAI(model="gpt-4o", temperature=0.7)

MAX_TRIALS = 3
PASS_SCORE = 0.8

def actor(state: ReflexionState):
    """Attempt the task. Crucially, lessons from PRIOR trials are injected as context."""
    lessons = "\n".join(f"- {m}" for m in state.get("memory", []))
    prompt = (
        f"Task: {state['task']}\n"
        + (f"\nLessons from your previous attempts:\n{lessons}\n" if lessons else "")
        + "\nProduce your best attempt."
    )
    # In production the actor is itself a ReAct agent (tools + loop), not a single call.
    attempt = actor_llm.invoke([HumanMessage(content=prompt)]).content
    return {"last_attempt": attempt, "trial": state.get("trial", 0) + 1}

def evaluator(state: ReflexionState):
    """Score the attempt — prefer unit tests / exact-match; LLM-as-judge as fallback."""
    judge = evaluator_llm.invoke([HumanMessage(content=(
        f"Task: {state['task']}\nAttempt: {state['last_attempt']}\n"
        "Return ONLY a number 0.0–1.0 for how well the attempt solves the task."
    ))]).content
    try:
        score = float(judge.strip().split()[0])
    except ValueError:
        score = 0.0
    return {"score": score}

def self_reflection(state: ReflexionState):
    """Turn (failed attempt + low score) into a durable VERBAL lesson — no weight update."""
    lesson = reflect_llm.invoke([HumanMessage(content=(
        f"Task: {state['task']}\nYour attempt: {state['last_attempt']}\n"
        f"It scored {state['score']:.2f} (below the bar). In 1–2 sentences write a concrete, "
        "actionable lesson that would make the NEXT attempt succeed."
    ))]).content
    return {"memory": [lesson]}   # operator.add APPENDS to episodic memory

def route(state: ReflexionState) -> str:
    if state["score"] >= PASS_SCORE or state["trial"] >= MAX_TRIALS:
        return "end"
    return "reflect"

builder = StateGraph(ReflexionState)
builder.add_node("actor", actor)
builder.add_node("evaluator", evaluator)
builder.add_node("reflect", self_reflection)
builder.add_edge(START, "actor")
builder.add_edge("actor", "evaluator")
builder.add_conditional_edges("evaluator", route, {"reflect": "reflect", "end": END})
builder.add_edge("reflect", "actor")          # retry — now with the new lesson in memory

graph = builder.compile()

result = graph.invoke({
    "task": "Write a regex that matches valid IPv4 addresses.",
    "memory": [], "last_attempt": "", "score": 0.0, "trial": 0,
})
print(result["last_attempt"], "| trials:", result["trial"], "| score:", result["score"])

When to Use

  • ✅ Hard, verifiable tasks: coding (run the tests), math, game/puzzle solving, SQL generation — anywhere you have an objective evaluator.
  • ✅ Repeated attempts are affordable and a single pass reliably under-performs.
  • ✅ You want learning without fine-tuning (lessons live in memory, not weights).
  • ❌ No reliable success signal → the evaluator is noise and reflections mislead (use plain Reflection instead).
  • ❌ Tight latency/cost budget → each trial re-runs the whole task.

Common Pitfalls

  1. Weak evaluator. If the score is noisy, the self-reflection learns the wrong lesson. Invest in the reward (unit tests beat LLM-judge).
  2. Memory bloat. Lessons accumulate; cap/deduplicate them or summarize, or they crowd the context window.
  3. Treating it like Reflection. Reflexion's loop is over trials with a persisted memory — if there's no cross-attempt memory, you've only built Reflection.
  4. No trial cap. Each trial is a full attempt; without MAX_TRIALS cost explodes far faster than a Reflection loop.

Interview Points

  • One-liner: "Reflexion = an Actor (often a ReAct agent) + an Evaluator that gives a reward + a Self-Reflection step that writes verbal lessons to episodic memory, looped over trials. It's reinforcement learning where the 'gradient' is natural language."
  • Why 'verbal RL'? The evaluator is the reward; the reflection is the policy update — but expressed as text injected into the next prompt, so no weights change.
  • Where does memory live? A list in graph state for one run; back it with a LangGraph Store/checkpointer to persist lessons across sessions.
  • Relation to other patterns: Reflexion composes — its Actor is usually ReAct; its inner quality step resembles Reflection. It's a meta-loop on top.
Pattern 3: Plan-and-Execute

Core Idea

Decompose first, then run. A planner produces an ordered step list up front; an executor (often a ReAct agent) runs each step; a replanner decides whether to continue, revise, or finish.

Use when: Planning itself is hard — long-horizon tasks where a pure ReAct loop drifts because it never commits to a structure.

Classic example: "Build a 3-chapter book outline, research each chapter, draft each, and compile."

Code Example

from typing import Annotated, List, TypedDict
from langchain_core.messages import HumanMessage
from langgraph.graph import StateGraph, START, END
from langgraph.prebuilt import create_react_agent
from langchain_openai import ChatOpenAI
import operator

class PlanExecuteState(TypedDict):
    """Plan-and-execute state."""
    input: str
    plan: List[str]
    past_steps: Annotated[List[tuple[str, str]], operator.add]  # [(step, result), ...]
    response: str
    retry_count: int

planner_llm = ChatOpenAI(model="gpt-4o")
replanner_llm = ChatOpenAI(model="gpt-4o")

# Executor is a simple tool-calling agent or function
def simple_executor(task: str) -> str:
    """Simulate executing a step (in reality, this'd be a full ReAct agent)."""
    # Placeholder: in production, wire a full agent here
    return f"Executed: {task}"

def plan_node(state: PlanExecuteState):
    """Planner: create an ordered list of steps."""
    planning_prompt = f"""
Break down this task into ordered, concrete steps:
{state['input']}

Output as a JSON list of strings, e.g., ["step 1", "step 2", "step 3"]
"""
    response = planner_llm.invoke([HumanMessage(content=planning_prompt)])
    import json
    plan = json.loads(response.content)
    return {"plan": plan}

def execute_node(state: PlanExecuteState):
    """Execute the first remaining step."""
    if not state["plan"]:
        return {}  # No more steps
    
    task = state["plan"][0]
    result = simple_executor(task)
    
    # Remove completed step from plan
    remaining_plan = state["plan"][1:]
    
    return {
        "past_steps": [(task, result)],
        "plan": remaining_plan
    }

def replan_node(state: PlanExecuteState):
    """Decide: continue, revise plan, or finish."""
    replan_prompt = f"""
Current task: {state['input']}
Steps completed so far:
{json.dumps(state['past_steps'], indent=2)}

Remaining steps to do:
{json.dumps(state['plan'], indent=2)}

Should we:
1. Continue with remaining steps?
2. Revise the plan based on what we've learned?
3. Finish and provide the final answer?

Respond with ONLY: "continue", "revise", or "finish".
If "finish", provide the final answer on the next line.
"""
    response = replanner_llm.invoke([HumanMessage(content=replan_prompt)])
    content = response.content.strip().lower()
    
    if "finish" in content:
        lines = content.split("\n")
        final_answer = "\n".join(lines[1:]) if len(lines) > 1 else "Task complete."
        return {"response": final_answer}
    elif "revise" in content:
        # Re-run planner with learned context
        revised_plan = plan_node(state)
        return revised_plan
    else:  # continue
        return {}

def route_after_execute(state: PlanExecuteState) -> str:
    """After execution, decide: replan or continue."""
    if state.get("response"):
        return "end"
    if not state["plan"]:  # No more steps
        return "replan"
    return "execute"

def route_after_replan(state: PlanExecuteState) -> str:
    """After replanning, decide: execute or end."""
    if state.get("response"):
        return "end"
    return "execute"

builder = StateGraph(PlanExecuteState)
builder.add_node("plan", plan_node)
builder.add_node("execute", execute_node)
builder.add_node("replan", replan_node)

builder.add_edge(START, "plan")
builder.add_edge("plan", "execute")
builder.add_conditional_edges(
    "execute",
    route_after_execute,
    {"replan": "replan", "end": END}
)
builder.add_conditional_edges(
    "replan",
    route_after_replan,
    {"execute": "execute", "end": END}
)

graph = builder.compile()

# Run it
result = graph.invoke({
    "input": "Write and deploy a Python API for a todo app",
    "plan": [],
    "past_steps": [],
    "response": "",
    "retry_count": 0
})
print(result["response"])

Pattern 4: Supervisor

Core Idea

Central manager routes to workers. One LLM reads the request, picks a worker (research agent, math agent, etc.), and reads the result. Workers only see what the supervisor hands them. Every routing decision is one place—easy to trace, easy to audit.

Architecture:

User Input→Supervisor LLM→Worker Agent→Supervisor→Answerclassifies

Code Example

from typing import Literal
from langchain_core.messages import HumanMessage
from langgraph.graph import StateGraph, START, END
from langgraph.prebuilt import create_react_agent
from langchain_openai import ChatOpenAI
from pydantic import BaseModel

# Define worker agents
def research_tools(query: str) -> str:
    """Simulate web search for research."""
    return f"Research findings on {query}: ..."

def math_tools(expression: str) -> str:
    """Math operations."""
    try:
        return f"Result: {eval(expression)}"
    except:
        return "Invalid expression"

research_agent = create_react_agent(
    ChatOpenAI(model="gpt-4o"),
    [research_tools],
    name="research"
)

math_agent = create_react_agent(
    ChatOpenAI(model="gpt-4o"),
    [math_tools],
    name="math"
)

# Supervisor state
class SupervisorState(BaseModel):
    messages: list
    current_worker: Literal["research", "math", "supervisor"]

supervisor_llm = ChatOpenAI(model="gpt-4o")

def supervisor_node(state: dict):
    """Classify the request and route to appropriate worker."""
    routing_prompt = """
You are a supervisor. Route this request to the appropriate worker:
- "research": For finding information, research, web searches
- "math": For calculations, math, numbers
- "answer": If you can answer directly

User request: {request}

Respond with ONLY the worker name or "answer". If "answer", provide the answer next.
""".format(request=state["messages"][-1]["content"])
    
    response = supervisor_llm.invoke([HumanMessage(content=routing_prompt)])
    decision = response.content.strip().lower()
    
    if "research" in decision:
        return {"current_worker": "research"}
    elif "math" in decision:
        return {"current_worker": "math"}
    else:
        return {"current_worker": "supervisor"}

def research_node(state: dict):
    """Call research agent."""
    result = research_agent.invoke(state)
    return {"messages": state["messages"] + [{"role": "assistant", "content": result["messages"][-1].content}]}

def math_node(state: dict):
    """Call math agent."""
    result = math_agent.invoke(state)
    return {"messages": state["messages"] + [{"role": "assistant", "content": result["messages"][-1].content}]}

def route_supervisor(state: dict) -> str:
    """Route based on supervisor's decision."""
    worker = state.get("current_worker", "supervisor")
    return worker

builder = StateGraph(dict)
builder.add_node("supervisor", supervisor_node)
builder.add_node("research", research_node)
builder.add_node("math", math_node)

builder.add_edge(START, "supervisor")
builder.add_conditional_edges(
    "supervisor",
    route_supervisor,
    {
        "research": "research",
        "math": "math",
        "supervisor": END
    }
)

graph = builder.compile()

result = graph.invoke({
    "messages": [{"role": "user", "content": "What's the capital of France? And calculate 15 * 8."}]
})
print(result["messages"][-1]["content"])

  1. Treating it like a swarm: Supervisor is hierarchical (top-down); swarm is peer-to-peer.
  2. Vague routing prompt: Supervisor can't classify if the prompt is ambiguous.
  3. Workers seeing unfiltered input: Don't pass the full conversation; give workers only the task they need.
Pattern 5: Swarm

Core Idea

Peer-to-peer handoff. Agents hand control to each other directly via handoff tools. No manager. The active agent persists in state, so a follow-up message goes to whoever's holding the conversation.

Good for: Support tickets, customer service, conversational flows where "who should handle this next" is a local decision, not a central plan.

Architecture:

Support Agent (active) ← can hand off to → Refunds Agent
    ↓ (handoff tool call)
Refunds Agent (now active) ← can hand off to → Support Agent

Code Example

from typing import Literal
from langchain_core.messages import HumanMessage, AIMessage
from langgraph.graph import StateGraph, START, END, Command
from langgraph.prebuilt import create_react_agent
from langchain_openai import ChatOpenAI

class SwarmState(dict):
    """Swarm state tracks active agent."""
    messages: list
    active_agent: Literal["support", "refunds"]

# Define handoff tool factories
def make_handoff_tool(target_agent: str):
    """Create a handoff tool that routes to another agent."""
    def handoff_to(reason: str) -> str:
        return f"Handing off to {target_agent}: {reason}"
    
    handoff_to.__name__ = f"handoff_to_{target_agent}"
    handoff_to.__doc__ = f"Hand off to the {target_agent} agent if needed."
    return handoff_to

# Create agents with handoff tools
support_agent = create_react_agent(
    ChatOpenAI(model="gpt-4o"),
    [make_handoff_tool("refunds")],
    name="support",
    prompt="""You are a support agent. Handle general customer inquiries.
If the customer asks about refunds or returns, use the handoff_to_refunds tool."""
)

refunds_agent = create_react_agent(
    ChatOpenAI(model="gpt-4o"),
    [make_handoff_tool("support")],
    name="refunds",
    prompt="""You are a refunds specialist. Handle refund and return requests.
If the customer has other support needs, use the handoff_to_support tool."""
)

def support_node(state: SwarmState):
    """Support agent node."""
    result = support_agent.invoke(state)
    new_state = state.copy()
    new_state["messages"] = result["messages"]
    
    # Check if handoff was triggered
    last_message = result["messages"][-1]
    if "Handing off to refunds" in str(last_message.content):
        new_state["active_agent"] = "refunds"
    
    return new_state

def refunds_node(state: SwarmState):
    """Refunds agent node."""
    result = refunds_agent.invoke(state)
    new_state = state.copy()
    new_state["messages"] = result["messages"]
    
    # Check if handoff was triggered
    last_message = result["messages"][-1]
    if "Handing off to support" in str(last_message.content):
        new_state["active_agent"] = "support"
    
    return new_state

def route_to_agent(state: SwarmState) -> str:
    """Route to the active agent."""
    return state.get("active_agent", "support")

builder = StateGraph(SwarmState)
builder.add_node("support", support_node)
builder.add_node("refunds", refunds_node)

builder.add_edge(START, "support")
builder.add_conditional_edges(
    "support",
    lambda s: "refunds" if s.get("active_agent") == "refunds" else END
)
builder.add_conditional_edges(
    "refunds",
    lambda s: "support" if s.get("active_agent") == "support" else END
)

graph = builder.compile()

result = graph.invoke({
    "messages": [HumanMessage(content="I want a refund for my order.")],
    "active_agent": "support"
})
print(result["messages"][-1].content)

The Secret: Command

In production LangGraph, handoffs use the Command primitive:

from langgraph.graph import Command

def support_node(state):
    # ... logic ...
    if should_handoff:
        return Command(goto="refunds")  # Jump to refunds node
    return {"messages": [...]}

This is the thing to mention in interviews: "Handoffs are implemented using Command(goto=node_name), which tells the graph to jump directly to another node."

When NOT to Use Agents

The Senior Differentiator

The strongest answer to "what kinds of agents are there" ends by demoting the question. Most production systems labeled "agent" shouldn't be agents at all.

Category 1: Fixed Sequence of Calls

# ❌ Don't build an agent for this:
builder = StateGraph(State)
builder.add_node("fetch_data", fetch_data)
builder.add_node("clean_data", clean_data)
builder.add_node("analyze_data", analyze_data)
builder.add_edge(START, "fetch_data")
builder.add_edge("fetch_data", "clean_data")
builder.add_edge("clean_data", "analyze_data")
builder.add_edge("analyze_data", END)

# ✅ Do use a simple chain/pipeline:
chain = fetch_data | clean_data | analyze_data
result = chain.invoke(input)

Why: No routing decision = no agent. Chains are cleaner, faster, easier to debug.

Category 2: Routing Among Known Paths

# ❌ Don't build an agent:
router_node decides between 3 fixed paths based on LLM classification

# ✅ Do use a router (one LLM call + branches):
def classify_intent(user_input):
    """Returns one of: "search", "math", "chat"."""
    return classifier_llm.invoke(user_input)

intent = classify_intent(user_input)
if intent == "search":
    result = search_agent.invoke(user_input)
elif intent == "math":
    result = math_agent.invoke(user_input)
else:
    result = chat_agent.invoke(user_input)

Why: A single classification call + branches is simpler than a full graph with state management.

Category 3: Single Retrieval + Answer

# ❌ Don't build an agent:
retriever + rerank + summarizer as an agentic loop

# ✅ Do use plain RAG:
docs = retriever.get_relevant_docs(query)
answer = summarizer.invoke(docs)

Why: No decisions = no agent. Plain retrieval pipelines are deterministic, cheaper, and faster.

Decision Tree: When Do I Actually Need an Agent?

Does the path depend on runtime decisions the LLM makes?
├─ NO → Use a chain or pipeline
└─ YES
   ├─ Is it a simple classification to known paths?
   │  └─ NO → Use a router
   └─ Does the LLM need to decide on every step (tool calls, follow-ups, etc.)?
      └─ YES → Now you have an agent
         ├─ Single agent, unpredictable tools? → ReAct
         ├─ Output quality critical? → Reflection
         ├─ Long-horizon, planning-heavy? → Plan-and-Execute
         ├─ Multiple domains, visibility required? → Supervisor
         └─ Conversational handoffs? → Swarm

Choosing the Right Pattern

Flowchart:

Start with a question that has an unpredictable path?
├─ NO → Use a chain or pipeline, not an agent
└─ YES
   ├─ Single agent, any tool mix? → ReAct (default)
   ├─ Output quality is the bottleneck? → Reflection
   ├─ Long multi-step task, planning is hard? → Plan-and-Execute
   ├─ Multiple domain experts, need visible routing? → Supervisor
   └─ Conversational flow, peers handle different parts? → Swarm

Failure Scenarios: 1. Tool Exception: Tool crashes (network error, timeout, API down) - Append error message to context: "Tool failed: {error_message}" - Agent re-invokes and may try different tool or answer with available info - Cap retries to prevent infinite loops

def agent_with_error_handling(state):
    try:
        response = llm_with_tools.invoke(state["messages"])
        return {"messages": [response]}
    except Exception as e:
        # Append error message for agent to see
        error_msg = AIMessage(content=f"Tool call failed: {str(e)}")

def should_retry_or_exit(state):
    # Check if we're in a retry loop
    last_tool = state["messages"][-1].tool_calls[0].name if state["messages"][-1].tool_calls else None
    prev_tools = [call.tool_calls[0].name for call in state["messages"][-3:-1] if call.tool_calls]
    
    if prev_tools.count(last_tool) >= 2:  # Same tool called 2+ times
        return END  # Force exit
    
    if state.get("iteration", 0) >= 15:  # Hard cap
        return END
    
    if state["messages"][-1].tool_calls:
        return "tools"
    return END

def generate_with_tracking(state):
    response = generator_llm.invoke(state["messages"])
    current_output = response.content
    
    # Check if output changed
    prev_output = state["prev_outputs"][-1] if state["prev_outputs"] else ""
    changed = current_output != prev_output
    
    new_state = {
        "messages": [response],
        "iterations": state.get("iterations", 0) + 1,
        "prev_outputs": state.get("prev_outputs", []) + [current_output],
    }
    
    if not changed:
        new_state["no_change_count"] = state.get("no_change_count", 0) + 1
    else:
        new_state["no_change_count"] = 0
    
    return new_state

def should_continue_reflection(state):
    if state["iterations"] >= 3:
        return "end"  # Hard cap
    
    if state["no_change_count"] >= 2:
        return "end"  # Stalled
    
    if "excellent" in state["messages"][-1].content.lower():
        return "end"  # Quality signal
    
    return "critique"

Failure Scenarios: 1. Step Returns Error: Tool unavailable, API rate-limited - Classify: is this step critical or optional? - Critical (e.g., "validate payment"): revise plan - Optional (e.g., "add metadata"): skip and continue - Recoverable (e.g., timeout): retry up to 3 times

  1. Step Takes Too Long: Execution timeout - Set timeout per step: timeout=60s - If timeout: mark as failed, don't retry (likely stuck) - Revise plan or skip

  2. Replanning Loops: Replan → execute → fail → replan forever - Track replan count - If replans >= 3: force finish or escalate to human

def execute_step_with_recovery(state):
    if not state["plan"]:
        return {}
    
    task = state["plan"][0]
    retry_count = 0
    max_retries = 3
    
    while retry_count < max_retries:
        try:
            result = executor_agent.invoke({"task": task}, timeout=60)
            return {
                "past_steps": [(task, result)],
                "plan": state["plan"][1:]
            }
        except TimeoutError:
            retry_count += 1
            if retry_count >= max_retries:
                # Mark as failed, don't retry again
                return {
                    "past_steps": [(task, f"FAILED: Timeout after {max_retries} retries")],
                    "plan": state["plan"][1:]
                }
        except Exception as e:
            return {
                "past_steps": [(task, f"ERROR: {str(e)}")],
                "plan": state["plan"][1:],
                "needs_replan": True  # Signal replanner to adapt
            }
    
    return {}

def replan_with_error_handling(state):
    if state.get("needs_replan"):
        # Force replanning
        return {"plan": revise_plan(state)}
    
    # Otherwise proceed normally
    return {}

def worker_with_validation(state):
    try:
        result = worker_agent.invoke(state, timeout=30)
        
        # Validate result (not empty, no error markers)
        if not result or "error" in result.lower():
            raise ValueError("Worker returned invalid result")
        
        return {"messages": state["messages"] + [{"role": "assistant", "content": result}]}
    except (TimeoutError, ValueError, Exception) as e:
        # Return failure, let supervisor retry
        return {"worker_failed": True, "error": str(e)}

def summarize_old_messages(state):

Monitoring & Observability

For each pattern, track:

  1. ReAct: - Iteration count (if > cap, alert). - Tool call distribution (which tools are used?). - Success rate (did the model reach an answer?).

  2. Reflection: - Iteration count & quality improvement per iteration. - Critic feedback (are critiques actionable?). - Did output quality improve? (define a metric).

  3. Plan-and-Execute: - Plan success rate (% of steps completed without re-planning). - Re-plan frequency (how often does the plan change?). - Total execution time (plan + all steps).

  4. Supervisor: - Routing accuracy (is the supervisor routing correctly?). - Worker utilization (which workers are called, why?). - Fallback rate (how often does "ask human" get triggered?).

  5. Swarm: - Handoff frequency (how many handoffs per conversation?). - Active agent distribution (do agents balance load?). - Conversation length (handoffs can extend conversations unintentionally).

Common Interview Mistakes & How to Avoid Them

Mistake 1: Treating All Patterns as "Agents"

Wrong: "We built a supervisor agent with 5 worker agents inside a swarm orchestration."

Right: "We built a supervisor graph that routes between 5 ReAct agents. Swarm wouldn't work here because we need centralized visibility."

Signal: Be precise about which pattern you're using and why.

Mistake 2: Forgetting the Iteration Cap

Wrong: "Our ReAct agent can loop as long as it needs."

Right: "Our ReAct agent caps at 15 iterations. If it hits 15, it returns the best answer so far and logs an alert."

Signal: You've learned (the hard way, probably) that uncapped loops are a liability.

Mistake 3: Over-Complicating for the Wrong Reason

Wrong: "We use a 5-agent swarm for simple customer classification."

Right: "Classification is a one-shot LLM call. We don't need a full agent. If it becomes multi-step, we'd promote it to a Supervisor."

Signal: You default to simple and add complexity only when necessary.

Mistake 4: Confusing Pattern Names

Wrong: "We use Hierarchical Reflection for multi-step tasks."

Right: "We use Plan-and-Execute for multi-step tasks and Reflection for quality refinement."

Signal: Know the patterns by name and use case, not by vague categories.

Mistake 5: Ignoring Debugging/Tracing

Wrong: "Our swarm is working great in production."

Right: "Our swarm works, and it's instrumented with Langfuse for distributed tracing. Without it, we wouldn't be able to debug handoff chains."

Signal: You've shipped agents to production and know what it takes to support them.

1. What Are Agentic Systems?

Agentic systems are AI architectures where one or more LLM-powered agents autonomously plan, reason, use tools, and take actions to accomplish complex goals with minimal human intervention. Unlike simple chatbots that respond to single prompts, agentic systems maintain state across multiple steps, make decisions, handle failures, and orchestrate workflows — representing the shift from AI as a tool to AI as a collaborator.

1.1 Definition

An agentic system is an AI system that can perceive its environment, reason about goals, plan multi-step actions, execute those actions using tools, and adapt based on feedback — all with varying degrees of autonomy.

2. Core Architecture Patterns

Architecture patterns define the control flow and decision-making structure of agentic systems. Key patterns include ReAct (interleaved reasoning and acting), Plan-and-Execute (upfront planning with step-by-step execution), Router (dispatching to specialized sub-agents), Reflection (self-critique and correction), and hierarchical multi-agent systems — each suited to different task complexity and reliability requirements.

        current = revised.content

2.4.1 How a Router Agent Decides the Sequence of Sub-Agents

The router agent decides WHICH sub-agents to call and in WHAT ORDER using one of these decision strategies:

HOW ROUTER DECIDES SEQUENCE — 5 STRATEGIES:

STRATEGY 1: LLM-BASED PLANNING (Most Common)
  The router LLM receives a system prompt describing all available
  sub-agents, their capabilities, and the task. It outputs a structured
  plan with the execution order.

  System prompt → "You have these agents: [Research, Code, Review].
                   Given the query, output the sequence of agents."
  
  User: "Research the latest Python frameworks, write a comparison script,
         and review it for errors."
  
  Router output: [
    {"step": 1, "agent": "research", "reason": "gather info first"},
    {"step": 2, "agent": "code",     "reason": "needs research results"},
    {"step": 3, "agent": "review",   "reason": "needs code to review"}
  ]

STRATEGY 2: DEPENDENCY GRAPH ANALYSIS
  The router analyzes task dependencies (what needs what):
  
  Task: "Analyze sales data, visualize trends, write a report"
  
  Dependencies:
    visualize_trends DEPENDS ON analyze_data (needs analysis results)
    write_report DEPENDS ON analyze_data AND visualize_trends
  
  Execution order: analyze_data → visualize_trends → write_report
  
  This is topological sorting of a dependency DAG.

STRATEGY 3: CLASSIFICATION + RULES
  Simple classification of query intent → predefined rules:
  
  IF intent == "code_review":    → [lint_agent, security_agent, style_agent]
  IF intent == "data_pipeline":  → [ingest_agent, transform_agent, validate_agent]
  IF intent == "customer_query": → [retrieval_agent, response_agent, tone_agent]
  
  Routes are deterministic based on classified intent.

STRATEGY 4: ITERATIVE (DYNAMIC ROUTING)
  Router calls one agent, evaluates the result, then decides the next:
  
  Step 1: Router → Research Agent → "Here are the findings"
  Step 2: Router evaluates → "Research is incomplete, need more data"
  Step 3: Router → Data Agent → "Here are the numbers"
  Step 4: Router evaluates → "Now ready for report"
  Step 5: Router → Writer Agent → Final report
  
  This is the most flexible but most expensive (multiple LLM calls).

STRATEGY 5: CAPABILITY MATCHING (Semantic)
  Each sub-agent has an embedding of its capabilities.
  Query is embedded and matched to the most similar agent.
  
  Agent embeddings:
    code_agent:     embed("writing code, debugging, programming")
    research_agent: embed("finding information, web search, papers")
    data_agent:     embed("data analysis, statistics, visualization")
  
  Query: "Plot a histogram of sales" → closest to data_agent

async def tree_of_thought(problem: str, breadth: int = 3, depth: int = 3):
    """Generate multiple thought branches, evaluate, prune."""
    root = ThoughtNode(problem)
    frontier = [root]
    
    for d in range(depth):
        new_frontier = []
        for node in frontier:
            # Generate multiple next thoughts
            thoughts = await generate_thoughts(node.thought, n=breadth)

        frontier = sorted(new_frontier, key=lambda x: x.score, reverse=True)[:breadth]

# ═══════════════ GOAL-ORIENTED ACTION PLANNING (GOAP) ═══════════════

class WorldState:
    def __init__(self, facts: dict):
        self.facts = facts  # e.g., {"has_data": True, "model_trained": False}
    
    def satisfies(self, conditions: dict) -> bool:
        return all(self.facts.get(k) == v for k, v in conditions.items())

class Action:
    def __init__(self, name: str, preconditions: dict, 
                 effects: dict, cost: float = 1.0):
        self.name = name
        self.preconditions = preconditions  # Required state
        self.effects = effects              # State changes after action
        self.cost = cost

def find_plan(initial_state: WorldState, goal: dict, 
              actions: list[Action]) -> list[Action]:
    """A* search through action space to reach goal state."""
    from heapq import heappush, heappop
    
    # Priority queue: (cost, state, plan)
    queue = [(0, id(initial_state), initial_state, [])]
    visited = set()
    
    while queue:
        cost, _, state, plan = heappop(queue)
        
        state_key = tuple(sorted(state.facts.items()))
        if state_key in visited:
            continue
        visited.add(state_key)
        
        if state.satisfies(goal):
            return plan
        
        for action in actions:
            if state.satisfies(action.preconditions):
                new_facts = {**state.facts, **action.effects}
                new_state = WorldState(new_facts)
                new_cost = cost + action.cost
                heappush(queue, (new_cost, id(new_state), 
                                new_state, plan + [action]))
    
    return []  # No plan found

4.2 Tool Selection & Execution Pipeline

from typing import Any
import json

class ToolRegistry:
    """Central registry for all available tools."""
    
    def __init__(self):
        self.tools: dict[str, callable] = {}
        self.schemas: dict[str, dict] = {}
        self.permissions: dict[str, list[str]] = {}  # tool → required roles
    
    def register(self, name: str, func: callable, schema: dict, 
                 required_roles: list[str] = None):
        self.tools[name] = func
        self.schemas[name] = schema
        self.permissions[name] = required_roles or []
    
    def get_available_tools(self, user_roles: list[str] = None) -> list[dict]:
        """Return tool schemas the user has access to."""
        available = []
        for name, schema in self.schemas.items():
            required = self.permissions.get(name, [])
            if not required or (user_roles and any(r in required for r in user_roles)):
                available.append(schema)
        return available
    
    async def execute(self, name: str, arguments: dict, 
                      user_roles: list[str] = None) -> Any:
        """Execute a tool with permission checking."""
        if name not in self.tools:
            return f"Error: Tool '{name}' not found"
        
        required = self.permissions.get(name, [])
        if required and not any(r in required for r in (user_roles or [])):
            return f"Error: Insufficient permissions for tool '{name}'"
        
        try:
            result = await self.tools[name](**arguments)
            return result
        except Exception as e:
            return f"Error executing {name}: {str(e)}"

# Tool execution loop
async def agent_tool_loop(query: str, registry: ToolRegistry, llm, 
                          max_steps: int = 10):
    """Core tool-use loop."""
    messages = [{"role": "user", "content": query}]
    available_tools = registry.get_available_tools()
    
    for step in range(max_steps):
        response = await llm.chat(messages, tools=available_tools)
        
        if response.tool_calls:
            for tool_call in response.tool_calls:
                result = await registry.execute(
                    tool_call.name,
                    json.loads(tool_call.arguments)
                )
                messages.append({
                    "role": "tool",
                    "tool_call_id": tool_call.id,
                    "content": str(result)
                })
        else:
            # No tool calls → final answer
            return response.content
    
    return "Max iterations reached without final answer"

class AgentMemory:

        })

            "metadata": {
                **(metadata or {}),
                "stored_at": datetime.now().isoformat()
            }

6.3 Agent Communication Protocols

from pydantic import BaseModel
from enum import Enum
from datetime import datetime

class MessageType(str, Enum):
    REQUEST = "request"         # Ask another agent to do something
    RESPONSE = "response"       # Reply with results
    INFORM = "inform"          # Share information
    DELEGATE = "delegate"       # Pass task to another agent
    FEEDBACK = "feedback"       # Critique or review
    ESCALATE = "escalate"       # Escalate to human

class AgentMessage(BaseModel):
    """Standard inter-agent communication protocol."""
    sender: str
    receiver: str
    type: MessageType
    content: str
    task_id: str
    timestamp: datetime = datetime.now()
    metadata: dict = {}
    priority: int = 5           # 1 = highest, 10 = lowest
    requires_response: bool = True

class MessageBus:
    """Central message bus for agent communication."""
    
    def __init__(self):
        self.queues: dict[str, list[AgentMessage]] = {}
        self.history: list[AgentMessage] = []
    
    def send(self, message: AgentMessage):
        if message.receiver not in self.queues:
            self.queues[message.receiver] = []
        self.queues[message.receiver].append(message)
        self.history.append(message)
    
    def receive(self, agent_id: str) -> list[AgentMessage]:
        messages = self.queues.get(agent_id, [])
        self.queues[agent_id] = []
        return sorted(messages, key=lambda m: m.priority)
    
    def broadcast(self, sender: str, content: str, 
                  msg_type: MessageType = MessageType.INFORM):
        """Send to all agents."""
        for agent_id in self.queues:
            if agent_id != sender:
                self.send(AgentMessage(
                    sender=sender, receiver=agent_id,
                    type=msg_type, content=content,
                    task_id="broadcast"
                ))

7.2 Error Recovery & Retry Patterns

import asyncio
from functools import wraps

class RetryConfig:
    max_retries: int = 3
    backoff_factor: float = 2.0
    initial_delay: float = 1.0

def with_retry(config: RetryConfig = RetryConfig()):
    """Decorator for retry with exponential backoff."""
    def decorator(func):
        @wraps(func)
        async def wrapper(*args, **kwargs):
            delay = config.initial_delay
            last_error = None
            
            for attempt in range(config.max_retries + 1):
                try:
                    return await func(*args, **kwargs)
                except Exception as e:
                    last_error = e
                    if attempt < config.max_retries:
                        await asyncio.sleep(delay)
                        delay *= config.backoff_factor
            
            raise last_error
        return wrapper
    return decorator

# Fallback chain pattern
async def execute_with_fallback(
    primary_fn, 
    fallback_fns: list,
    *args, **kwargs
):
    """Try primary, fall back to alternatives on failure."""
    try:
        return await primary_fn(*args, **kwargs)
    except Exception as primary_error:
        for i, fallback in enumerate(fallback_fns):
            try:
                return await fallback(*args, **kwargs)
            except Exception:
                continue
        raise primary_error  # All fallbacks failed

async def retrieve(state: RAGState):

    return {"retrieved_docs": [d.page_content for d in docs]}

async def grade_documents(state: RAGState):
    """Check if retrieved docs are relevant to the question."""
    grading_prompt = f"""Are these documents relevant to answering: "{state['question']}"?

Documents: {state['retrieved_docs'][:3]}

Respond YES or NO with reasoning."""
    
    result = await llm.ainvoke(grading_prompt)
    is_relevant = "YES" in result.content.upper()
    return {"is_relevant": is_relevant}

async def generate(state: RAGState):

Context: {context}

Question: {state['question']}

If the context doesn't contain the answer, say "I don't have enough information."
Cite specific sources."""

Answer: {state['answer']}
Sources: {state['retrieved_docs'][:3]}

Respond GROUNDED or NOT_GROUNDED."""

Original: {state['question']}

Rewrite this query to be more specific and likely to match relevant documents:"""

        "retry_count": state.get("retry_count", 0) + 1

class InputGuardrail:
    """Pre-process user input before agent sees it."""
    
    INJECTION_PATTERNS = [
        r"ignore (all |your |previous )?instructions",
        r"you are now",
        r"system prompt",
        r"pretend (to be|you are)",
        r"jailbreak",
        r"DAN mode",
    ]
    
    PII_PATTERNS = {
        "ssn": r"\b\d{3}-\d{2}-\d{4}\b",
        "credit_card": r"\b\d{4}[\s-]?\d{4}[\s-]?\d{4}[\s-]?\d{4}\b",
        "email": r"\b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Z|a-z]{2,}\b",
        "phone": r"\b\d{3}[-.]?\d{3}[-.]?\d{4}\b",
    }
    
    def check_injection(self, text: str) -> tuple[bool, str]:
        """Detect potential prompt injection attempts."""
        for pattern in self.INJECTION_PATTERNS:
            if re.search(pattern, text, re.IGNORECASE):
                return True, f"Potential injection detected: {pattern}"
        return False, ""
    
    def redact_pii(self, text: str) -> str:
        """Replace PII with placeholders."""
        for pii_type, pattern in self.PII_PATTERNS.items():
            text = re.sub(pattern, f"[REDACTED_{pii_type.upper()}]", text)
        return text
    
    def validate(self, text: str) -> tuple[bool, str]:
        """Full input validation pipeline."""
        # Check injection
        is_injection, reason = self.check_injection(text)
        if is_injection:
            return False, reason
        
        # Redact PII
        clean_text = self.redact_pii(text)
        
        # Length check
        if len(text) > 10000:
            return False, "Input too long (max 10,000 characters)"
        
        return True, clean_text

@dataclass
class EvalCase:
    """Single evaluation test case."""
    id: str
    input_query: str
    expected_output: Optional[str] = None
    expected_tools: Optional[list[str]] = None
    expected_steps_max: int = 10
    difficulty: str = "medium"
    category: str = "general"
    
@dataclass  
class EvalResult:
    """Result of evaluating one test case."""
    case_id: str
    passed: bool
    actual_output: str
    tools_used: list[str]
    steps_taken: int
    latency_ms: float
    tokens_used: int
    errors: list[str] = field(default_factory=list)
    scores: dict = field(default_factory=dict)

class AgentEvaluator:
    """End-to-end agent evaluation harness."""
    
    def __init__(self, agent, eval_llm=None):
        self.agent = agent
        self.eval_llm = eval_llm  # LLM-as-judge
        self.results: list[EvalResult] = []
    
    async def evaluate_case(self, case: EvalCase) -> EvalResult:
        """Run one evaluation case."""
        start = time.time()
        errors = []
        
        try:
            # Execute agent
            output = await self.agent.ainvoke({"input": case.input_query})
            actual = output.get("output", "")
            tools = output.get("tools_used", [])
            steps = output.get("steps", 0)
            tokens = output.get("tokens_used", 0)
        except Exception as e:
            return EvalResult(
                case_id=case.id, passed=False,
                actual_output=str(e), tools_used=[], steps_taken=0,
                latency_ms=(time.time()-start)*1000, tokens_used=0,
                errors=[str(e)]
            )
        
        latency = (time.time() - start) * 1000
        
        # Score dimensions
        scores = {}
        
        # 1. Correctness (LLM-as-judge)
        if case.expected_output and self.eval_llm:
            scores["correctness"] = await self._judge_correctness(
                case.input_query, actual, case.expected_output
            )
        
        # 2. Tool use accuracy
        if case.expected_tools:
            expected_set = set(case.expected_tools)
            actual_set = set(tools)
            scores["tool_accuracy"] = len(expected_set & actual_set) / max(len(expected_set), 1)
        
        # 3. Efficiency
        scores["efficiency"] = min(1.0, case.expected_steps_max / max(steps, 1))
        
        # 4. Determine pass/fail
        passed = all(s >= 0.7 for s in scores.values()) if scores else True
        
        result = EvalResult(
            case_id=case.id, passed=passed,
            actual_output=actual, tools_used=tools,
            steps_taken=steps, latency_ms=latency,
            tokens_used=tokens, errors=errors, scores=scores
        )
        self.results.append(result)
        return result
    
    async def _judge_correctness(self, question: str, actual: str, 
                                  expected: str) -> float:
        """Use LLM to judge answer correctness."""
        prompt = f"""Rate the correctness of the actual answer compared to expected.

Question: {question}
Expected answer: {expected}
Actual answer: {actual}

Score from 0.0 to 1.0. Consider semantic equivalence, not exact match.
Return ONLY the number."""
        
        result = await self.eval_llm.ainvoke(prompt)
        try:
            return float(result.content.strip())
        except ValueError:
            return 0.0
    
    def summary(self) -> dict:
        """Generate evaluation summary."""
        if not self.results:
            return {}
        
        total = len(self.results)
        passed = sum(1 for r in self.results if r.passed)
        
        return {
            "total_cases": total,
            "passed": passed,
            "failed": total - passed,
            "pass_rate": passed / total,
            "avg_latency_ms": sum(r.latency_ms for r in self.results) / total,
            "avg_steps": sum(r.steps_taken for r in self.results) / total,
            "avg_tokens": sum(r.tokens_used for r in self.results) / total,
            "avg_scores": {
                dim: sum(r.scores.get(dim, 0) for r in self.results) / total
                for dim in set().union(*(r.scores.keys() for r in self.results))
            }
        }

import time

class AgentObserver:
    """Track agent performance and behavior."""
    
    def __init__(self):
        self.metrics = {
            "total_requests": 0,
            "successful": 0,
            "failed": 0,
            "avg_latency_ms": 0,
            "avg_steps": 0,
            "tool_usage": {},
            "error_types": {},
        }
    
    def trace_agent_run(self):
        """Decorator for tracing agent execution."""
        def decorator(func):
            async def wrapper(*args, **kwargs):
                with tracer.start_as_current_span("agent_run") as span:
                    start = time.time()
                    self.metrics["total_requests"] += 1
                    
                    try:
                        result = await func(*args, **kwargs)
                        self.metrics["successful"] += 1
                        
                        # Record trace attributes
                        span.set_attribute("steps", result.get("steps", 0))
                        span.set_attribute("tools_used", str(result.get("tools_used", [])))
                        span.set_attribute("tokens", result.get("tokens", 0))
                        
                        return result
                    except Exception as e:
                        self.metrics["failed"] += 1
                        error_type = type(e).__name__
                        self.metrics["error_types"][error_type] = \
                            self.metrics["error_types"].get(error_type, 0) + 1
                        
                        span.set_status(trace.Status(trace.StatusCode.ERROR))
                        span.record_exception(e)
                        raise
                    finally:
                        latency = (time.time() - start) * 1000
                        span.set_attribute("latency_ms", latency)
                        
                        # Update running average
                        n = self.metrics["total_requests"]
                        self.metrics["avg_latency_ms"] = (
                            (self.metrics["avg_latency_ms"] * (n-1) + latency) / n
                        )
            return wrapper
        return decorator
    
    def alert_if_needed(self):
        """Check metrics against thresholds."""
        if self.metrics["total_requests"] > 100:
            error_rate = self.metrics["failed"] / self.metrics["total_requests"]
            if error_rate > 0.05:
                logger.critical(f"Error rate {error_rate:.1%} exceeds 5% threshold!")
            
            if self.metrics["avg_latency_ms"] > 30000:

        "gpt-4o": {"input": 2.50 / 1_000_000, "output": 10.00 / 1_000_000},
        "gpt-4o-mini": {"input": 0.15 / 1_000_000, "output": 0.60 / 1_000_000},
        "claude-sonnet": {"input": 3.00 / 1_000_000, "output": 15.00 / 1_000_000},
    }
    
    def __init__(self, budget_per_request: float = 0.10):
        self.budget = budget_per_request
        self.total_cost = 0.0
    
    def estimate_cost(self, model: str, input_tokens: int, 
                      output_tokens: int) -> float:
        pricing = self.PRICING.get(model, self.PRICING["gpt-4o-mini"])
        return input_tokens * pricing["input"] + output_tokens * pricing["output"]
    
    def select_model(self, task_complexity: str) -> str:
        """Route to cheaper model for simple tasks."""
        if task_complexity == "simple":
            return "gpt-4o-mini"     # $0.15/M input 
        elif task_complexity == "medium":
            return "gpt-4o-mini"     # Still cheap enough
        else:
            return "gpt-4o"          # Only for complex reasoning
    
    def should_cache(self, query: str) -> bool:
        """Decide if response should be cached."""
        # Cache factual queries, not dynamic ones
        dynamic_keywords = ["today", "current", "latest", "now", "recent"]
        return not any(kw in query.lower() for kw in dynamic_keywords)

13. LATS (Language Agent Tree Search)

LATS (Zhou et al., 2023) combines ReAct (reasoning + acting), Tree-of-Thought (branching exploration), and Monte Carlo Tree Search (MCTS) into a unified framework for complex agent reasoning.

Core Idea

Instead of following a single reasoning chain (ReAct) or a fixed plan (Plan-and-Execute), LATS explores multiple action trajectories as a tree, using LLM-based evaluation and MCTS to guide the search toward the best solution.

Algorithm

LATS Algorithm:

1. SELECT    — Use UCB1 to pick the most promising node to expand
2. EXPAND    — LLM generates N candidate actions from the selected state
3. EVALUATE  — LLM scores each candidate (self-reflection / value function)
4. SIMULATE  — Roll out the best candidate to completion (or depth limit)
5. BACKPROP  — Propagate the outcome value back up the tree
6. REPEAT    — Until solution found or budget exhausted

       [Root: Initial State]
          /       |       \
     [Action1] [Action2] [Action3]     ← EXPAND
       / \         |         \
   [A1.1] [A1.2] [A2.1]   [A3.1]     ← EXPAND deeper
     ✓       ✗      ✗         ✓        ← EVALUATE (LLM scores)
   (0.9)   (0.2)  (0.3)    (0.7)     ← BACKPROPAGATE values

Comparison with Other Approaches

FeatureReActPlan-and-ExecuteLATS
ExplorationSingle chainSingle planTree (multiple paths)
Error recoveryLimited backtrackingRe-plan on failureNatural backtracking via tree
LLM callsLow (1 per step)MediumHigh (branching factor × depth)
Best forSimple tool useMulti-step workflowsComplex reasoning with uncertainty
Self-reflectionNoOptionalBuilt-in (evaluation step)
OptimalityFirst valid solutionPlan qualitySearches for best solution

When to Use LATS

  • Complex multi-step reasoning where the first attempt often fails.
  • Tasks with multiple valid approachesLATS explores alternatives.
  • Code generation / debuggingtry multiple fixes, evaluate each.
  • Decision-making under uncertaintyMCTS naturally handles stochastic outcomes.
  • NOT suitable forSimple Q&A, real-time applications (high latency), cost-sensitive scenarios.

Pseudocode

def lats(initial_state, llm, max_iterations=10, n_candidates=3):
    root = Node(state=initial_state, value=0)
    tree = MCTSTree(root)
    
    for _ in range(max_iterations):
        # 1. SELECT: UCB1-guided tree traversal
        node = tree.select_best_leaf(exploration_weight=1.4)
        
        # 2. EXPAND: LLM generates candidate actions
        candidates = llm.generate_actions(node.state, n=n_candidates)
        
        # 3. EVALUATE: LLM scores each candidate
        for action in candidates:
            new_state = execute_action(node.state, action)
            value = llm.evaluate_state(new_state)  # Self-reflection
            child = Node(state=new_state, value=value, action=action)
            node.add_child(child)
        
        # 4. SIMULATE: Roll out best child
        best_child = max(node.children, key=lambda c: c.value)
        outcome = simulate_to_completion(best_child, llm)
        
        # 5. BACKPROPAGATE: Update ancestor values
        tree.backpropagate(best_child, outcome.reward)
        
        if outcome.is_solution:
            return outcome
    
    return tree.best_trajectory()

Q1. How would you design an agentic system that can reliably handle complex, multi-step tasks?

Answer:

I'd use a Plan-Execute-Reflect architecture with these components:

  1. Planner: LLM decomposes goal into ordered steps with dependencies
  2. Executor: Per-step execution with tool access and error handling
  3. Reflector: After each step, evaluate progress and re-plan if needed
  4. Memory: Short-term (current session) + long-term (vector store for knowledge)
  5. Guardrails: Token/step limits, tool permissions, human escalation gates

Key design decisions: - State persistence (LangGraph checkpointer) for crash recovery - Retry with fallback — try GPT-4o, fall back to Claude, then local LLM - Streaming for real-time user visibility into reasoning - Cost routing — simple sub-tasks use GPT-4o-mini, complex ones use GPT-4o

Q7. How do you design memory for a long-running agent?

Three-tier architecture:

  1. Working memory (context window): Current conversation, last 10-20 messages, summarize older ones
  2. Semantic memory (vector store): Facts, knowledge, entity information — retrieved via similarity search

class ContextHealthCheck:
    def __init__(self, context_limit=128_000):
        self.limit = context_limit
        self.warning_threshold = 0.5  # Warn at 50%

                "remaining": self.limit - total_tokens,

def hierarchical_summarization(messages, summarizer_llm, chunk_size=10, keep_recent=5):

    Multi-level summarization:
    1. Chunk messages into groups (e.g., every 10)
    2. Summarize each chunk
    3. Keep last N messages verbatim

        return messages

from langchain_core.embeddings import Embeddings

def relevance_filtering(messages, current_task, embedder, top_k=10):
    """
    Keep messages most relevant to current task.
    
    1. Embed all messages
    2. Embed current task
    3. Rank by similarity to task
    4. Keep top_k + recent messages
    """
    # Get embeddings
    message_texts = [m['content'] for m in messages]
    message_embeddings = [embedder.embed_query(text) for text in message_texts]
    task_embedding = embedder.embed_query(current_task)
    
    # Compute similarity (cosine)
    import numpy as np
    similarities = [
        np.dot(msg_emb, task_emb) / (np.linalg.norm(msg_emb) * np.linalg.norm(task_emb))
        for msg_emb in message_embeddings
    ]
    
    # Get top_k relevant + most recent
    top_indices = sorted(range(len(similarities)), key=lambda i: similarities[i], reverse=True)[:top_k]
    recent_indices = list(range(len(messages) - 5, len(messages)))
    
    # Combine (deduplicate and sort)
    kept_indices = sorted(set(top_indices + recent_indices))
    
    return [messages[i] for i in kept_indices]

def token_compression(messages, compression_ratio=0.7):
    """
    Compress messages by:
    1. Removing redundant phrases
    2. Shortening long outputs
    3. Abstracting common patterns
    
    Target: reduce to compression_ratio of original size.
    """
    compressed = []
    
    for msg in messages:
        content = msg['content']
        
        # Remove repeated words
        words = content.split()
        unique_words = []
        prev_word = None
        for word in words:
            if word != prev_word or len(unique_words) == 0:
                unique_words.append(word)
                prev_word = word
        deduplicated = " ".join(unique_words)
        
        # Truncate long messages
        max_len = int(len(deduplicated) * compression_ratio)
        truncated = deduplicated[:max_len] + ("..." if len(deduplicated) > max_len else "")
        
        compressed.append({
            "role": msg['role'],
            "content": truncated,
            "_original_len": len(content),
            "_compressed_len": len(truncated)
        })
    
    return compressed

class SummarizationTrigger:
    def __init__(self, context_limit=128_000):
        self.limit = context_limit
        self.triggers = {
            "token_threshold": 0.6,         # Summarize at 60% usage
            "message_count": 30,             # OR after 30 messages
            "iteration_count": 10,           # OR after 10 iterations
            "handoff_count": 5,              # OR after 5 handoffs
            "time_based": 300,               # OR every 5 minutes
        }
    
    def should_summarize(self, state):
        """Return (bool, reason_string)"""
        
        # Check token usage
        tokens_used = self._estimate_tokens(state)
        if tokens_used > self.limit * self.triggers["token_threshold"]:
            return True, f"Token usage: {tokens_used} tokens"
        
        # Check message count
        if len(state["messages"]) >= self.triggers["message_count"]:
            return True, f"Message count: {len(state['messages'])} messages"
        
        # Check iteration count
        if state.get("iteration", 0) >= self.triggers["iteration_count"]:
            return True, f"Iteration count: {state['iteration']}"
        
        # Check handoff count
        if state.get("handoff_depth", 0) >= self.triggers["handoff_count"]:
            return True, f"Handoff depth: {state['handoff_depth']}"
        
        return False, "No trigger met"

class HierarchicalSummarizer:

        self.llm = summarizer_llm
        self.levels = levels
        self.chunk_size = chunk_size
    
    def compress_to_hierarchy(self, messages, keep_recent=5):
        """
        Create hierarchical summaries:
        Level 0: Original messages (keep_recent verbatim)
        Level 1: Chunk summaries (10 messages each)
        Level 2: Meta summaries (summaries of summaries)
        """
        recent = messages[-keep_recent:]
        to_compress = messages[:-keep_recent]
        
        # Build L1 summaries
        l1_summaries = []
        chunks = [to_compress[i:i+self.chunk_size] for i in range(0, len(to_compress), self.chunk_size)]
        
        for i, chunk in enumerate(chunks):
            chunk_text = "\n".join([str(m) for m in chunk])
            summary = self._summarize(chunk_text, level=1, index=i)
            l1_summaries.append({"level": 1, "index": i, "summary": summary, "size": len(chunk)})
        
        # Build L2 summaries (if more than one L1)
        l2_summaries = []
        if len(l1_summaries) > 2:
            l1_text = "\n".join([f"[L1-{s['index']}] {s['summary']}" for s in l1_summaries])
            l2_summary = self._summarize(l1_text, level=2)
            l2_summaries.append({"level": 2, "summary": l2_summary})
        
        # Build final compressed state
        compressed = []
        
        # Add L2 (if exists)
        if l2_summaries:
            compressed.append(HumanMessage(content=f"[LEVEL 2 SUMMARY]\n{l2_summaries[0]['summary']}"))
        
        # Add L1 summaries
        for l1 in l1_summaries:
            compressed.append(HumanMessage(content=f"[L1 CHUNK {l1['index']}]\n{l1['summary']}"))
        
        # Add recent messages verbatim
        compressed.extend(recent)
        
        return compressed, {"l1_count": len(l1_summaries), "l2_count": len(l2_summaries)}

        """
        If agent needs more detail about L1 chunk, expand it.
        """

        return f"Expand L1 chunk {expand_l1_index} for details"

Fundamental

Q1. At what point should you start worrying about context size?

Expected Answer: - When usage exceeds 50% of context limit. - For gpt-4o (128K), that's 64K tokens (~48K words). - Red flag: if your agent-task pair reaches 50% before completing. - Interview signal: You monitor context proactively, not reactively.

Q2. What's the difference between a sliding window and summarization?

Expected Answer: - Sliding window: Discard old messages entirely (cheap, loses context). - Summarization: Compress old messages into summary (costs LLM call, preserves context). - Sliding window: fast, but agent forgets. - Summarization: slower, but agent retains history. - Interview signal: You understand the cost-context tradeoff.

Q3. When would you NOT summarize, and instead just truncate (sliding window)?

Expected Answer: - If token budget is tight and cost matters (many users, real-time). - If historical context isn't important (single-shot tasks). - If conversation is naturally short (< 20 turns). - Interview signal: You think about cost-benefit, not just technical correctness.

Q4. How do you handle a ReAct agent that keeps looping and growing context?

Expected Answer: - Hard iteration cap (15-25 max iterations). - Monitor context growth per iteration. - If iterations > cap: force END + return best answer so far. - Log the loop (why did it happen?) for post-analysis. - Interview signal: You've debugged runaway agents.

Advanced

Q5. Design a system that summarizes intelligently—not just by age, but by relevance.

Expected Answer: - Embed all messages. - Embed current task/goal. - Keep messages with high similarity to goal + recent messages. - Summarize low-relevance messages. - Trade-off: More expensive (embeddings), but keeps relevant context. - Interview signal: You think beyond simple strategies (time-based, count-based).

Q6. You have a Swarm where agents keep handing off to each other 10+ times. How do you manage context?

Expected Answer: - Track handoff depth; cap at 5-7. - After each handoff, check context growth. - If context > 70%: compress before next handoff. - Compress by: summarizing old handoffs + keeping recent 5 messages. - Alternative: Escalate to human after 3 failed handoffs. - Interview signal: You understand Swarm-specific context issues.

Q7. A customer's Reflection loop is stuck critiquing the same output endlessly. Why? How do you fix it?

# Calculate cost impact of summarization

def calculate_summarization_cost(
    avg_conversation_length=20,  # messages
    avg_message_length=500,       # chars
    summarizations_per_conversation=2,
    summarization_cost_usd=0.001  # cost per summarization (gpt-4o-mini)
):

    Calculate added cost of summarization.
    """
    # Main conversation cost (assume gpt-4o)
    total_chars = avg_conversation_length * avg_message_length

    return {
        "main_cost": gpt4_cost,
        "summarization_cost": summ_cost,
        "total_cost": total_cost,
        "cost_increase_pct": cost_increase_pct
    }

result = calculate_summarization_cost()

from langgraph.checkpoint.postgres import PostgresSaver
with PostgresSaver.from_conn_string("postgresql://u:p@localhost:5432/app") as cp:
    cp.setup()                       # FIRST run only: creates checkpoint tables
    app = graph.compile(checkpointer=cp)
    app.invoke(inputs, {"configurable": {"thread_id": "user-1"}})

8.2 What happens after the server restarts

The state is keyed by thread_id. With a durable backend (SQLite/Postgres), restarting the process loses nothing — you reconnect to the same backend and invoke with the same thread_id:

cfg = {"configurable": {"thread_id": "user-1"}}

# ── before restart ──
app.invoke({"messages": [("human", "My name is Alice")]}, cfg)

#  ⛔  process stops / crashes / redeploys …
#  ▶  process starts again, reopen the SAME sqlite file or Postgres DB, recompile the graph

# ── after restart: same thread_id → full state is restored ──
app.invoke({"messages": [("human", "What's my name?")]}, cfg)   # → "Alice"

# Or inspect/resume WITHOUT running a new turn:
snap = app.get_state(cfg)
print(snap.values["messages"])   # the restored conversation
print(snap.next)                 # which node it would run next (e.g. paused at an interrupt)
app.invoke(None, cfg)            # resume a paused/interrupted run from the last checkpoint

What exactly is persisted: the entire graph state for that thread at each step — every state key (messages + your custom fields), the next node to run, and any pending interrupt. That's why checkpointing powers three features at once: memory, crash recovery / resume, and time-travel (get_state_history).

⚠️ Gotchas: MemorySaver is not persistence — restarting wipes it. For SQLite/Postgres call .setup() once to create tables. A different thread_id = a different, empty conversation. For multiple server replicas you must use a shared DB (Postgres), not SQLite-on-local-disk.

1. The Distinction (interview answer first)

One-linerrouterdecomposertwo distinct control-flow patternsSupervisorOrchestrator-worker

One-liner: A supervisor is a router — each turn, an LLM picks which one worker acts next, sees the result, picks again. An orchestrator is a decomposer — it breaks the goal into subtasks up front, dispatches them (often in parallel), and synthesizes the results. Supervisor = sequential turn-by-turn control; orchestrator = plan → fan-out → fan-in.

The confusion exists because "orchestration" is also the umbrella word for any coordination (the graph itself "orchestrates"), and a supervisor is one way to orchestrate. When an interviewer asks the difference, they want the two distinct control-flow patterns:

class SupState(TypedDict):

def supervisor(state):

from langgraph.types import Send

class OrchState(TypedDict):
    goal: str
    plan: list                        # [(agent_name, subtask), ...]
    results: Annotated[list, add]     # reducer — parallel workers merge, not clobber
    final: str

class Plan(BaseModel):
    subtasks: list[tuple[str, str]]   # (which specialist, what to do)

def planner(state):                   # the DECOMPOSER — one LLM call plans everything
    p = llm.with_structured_output(Plan).invoke(f"Split into subtasks: {state['goal']}")
    return {"plan": p.subtasks}

def dispatch(state):                  # fan-out: one Send per subtask → ALL run in ONE superstep
    return [Send("worker", {"agent": a, "subtask": t}) for a, t in state["plan"]]

def worker(payload: dict):            # runs once per subtask, in parallel
    result = run_agent(payload["agent"], payload["subtask"])
    return {"results": [result]}

def synthesizer(state):               # fan-in: sees the merged results list
    return {"final": llm.invoke(f"Synthesize:\n{state['results']}").content}

og = StateGraph(OrchState)
og.add_node("planner", planner); og.add_node("worker", worker); og.add_node("synthesizer", synthesizer)
og.add_edge(START, "planner")
og.add_conditional_edges("planner", dispatch, ["worker"])   # map
og.add_edge("worker", "synthesizer")                        # reduce (waits for ALL workers)
og.add_edge("synthesizer", END)
orch = og.compile()

Three non-negotiables: the reducer on results (parallel writes without it → InvalidUpdateError), a k-of-N aggregation policy in the synthesizer (workers fail — see Failure Handling and Resilience §7), and a plan validator (a bad plan poisons every branch — cap N, check agent names).

4. Adding an Agent AFTER Deployment (the real question)

static topologytwice1. Registry + generic executorruntime lookup by name2. Agents as tools3. Recompile-on-change

4.1 Theory — why it's hard, and the three escape hatches

A compiled LangGraph is a static topology: nodes and edges are baked at compile(). The naive design (one node per agent, Literal router) hard-codes the team twice — in the graph shape and in the router schema. Adding an agent = code change + redeploy, and with a checkpointer you must also worry about in-flight runs resuming against a changed graph.

The fix is a design move, not a framework feature: stop making agents part of the graph's shape. Make them data.

ApproachHowRedeploy needed?
1. Registry + generic executor ★ONE executor node; the actual agent is a runtime lookup by name from a registry (dict → DB/config in prod). Graph shape never changes.No — insert a registry row
2. Agents as toolsEach sub-agent wrapped as a tool; bind_tools(registry.tools()) computed per requestNo — extend the tool list
3. Recompile-on-changeGraph built from config; rebuild + compile() on config change (cheap — compilation is wiring, not training), swap atomicallyNo process restart — hot swap
Naive (node per agent)Edit code, add node/edgesYes

★ = the pattern to lead with in an interview. Below it is implemented and verified against real LangGraph — including registering a new agent while the compiled app object stays the same.

4.2 The Registry + Generic-Executor pattern (verified code)

from typing import TypedDict, Annotated
from operator import add
from langgraph.graph import StateGraph, START, END

# ── The registry: the ONLY place agents live. A dict here; in prod a DB table /
#    config service so ops can insert a row without touching code.
AGENT_REGISTRY = {
    "researcher": {"description": "looks things up", "fn": research_agent},
    "coder":      {"description": "writes code",     "fn": coder_agent},
}

class SupState(TypedDict):
    tasks: list                       # pending work
    results: Annotated[list, add]
    next_agent: str
    next_task: str

def supervisor(state):
    # In prod this is an LLM router whose OPTIONS COME FROM THE REGISTRY (see 4.3) —
    # not a hard-coded Literal. Unknown names are rejected, not executed.
    if not state["tasks"]:
        return {"next_agent": "FINISH", "next_task": ""}
    name, task = state["tasks"][0]
    if name not in AGENT_REGISTRY:                       # validate against the registry
        return {"tasks": state["tasks"][1:], "next_agent": "SKIP", "next_task": "",
                "results": [f"UNROUTABLE[{name}:{task}]"]}
    return {"tasks": state["tasks"][1:], "next_agent": name, "next_task": task}

def executor(state):
    # ★ THE TRICK: one generic node. The agent is a RUNTIME LOOKUP, not a graph node.
    agent = AGENT_REGISTRY[state["next_agent"]]
    return {"results": [agent["fn"](state["next_task"])]}

def route(state):
    if state["next_agent"] == "FINISH": return "end"
    if state["next_agent"] == "SKIP":   return "supervisor"
    return "executor"

g = StateGraph(SupState)
g.add_node("supervisor", supervisor)
g.add_node("executor", executor)                         # ← the ONLY worker node, ever
g.add_edge(START, "supervisor")
g.add_conditional_edges("supervisor", route,
    {"executor": "executor", "supervisor": "supervisor", "end": END})
g.add_edge("executor", "supervisor")
app = g.compile()                                        # ← compiled ONCE

The deployment moment — service is live, and we add a translator:

# Day 30, system in production. No code change, no recompile, SAME `app` object:

    "description": "translates text",
    "fn": translator_agent,          # in prod: built from a DB row (model, prompt, tools)
}
# Next invocation routes to it. Done.

The translator task that was unroutable before is served after a plain dict mutation — the compiled topology never changed, because the topology only knows "supervisor ⇄ executor," and which agent runs is data.

The same registry serves the orchestrator: its worker node does AGENT_REGISTRY.get(payload["agent"]), so the planner can immediately plan subtasks for new agents too (also verified — the fan-out run included the runtime-added translator).

4.3 The router must learn the new options dynamically

A Literal["researcher", "coder", "FINISH"] schema would still reject the newcomer. Build the router's options from the registry at request time:

def make_router_schema():
    """Rebuild the routing enum from the live registry (cheap — per request is fine)."""
    from enum import Enum
    options = list(AGENT_REGISTRY) + ["FINISH"]
    AgentEnum = Enum("AgentEnum", {o: o for o in options})
    class Router(BaseModel):

    return Router

def supervisor(state):
    roster = "\n".join(f"- {n}: {a['description']}" for n, a in AGENT_REGISTRY.items())
    decision = llm.with_structured_output(make_router_schema()).invoke(
        [("system", f"Route to one worker or FINISH.\nAvailable workers:\n{roster}")]
        + state["messages"])
    return {"next": decision.next.value}

Two things happened: the schema now admits the new agent, and the prompt roster tells the LLM it exists and what it's for. The description field in the registry isn't decoration — it's the router's routing signal. A new agent with a vague description will be misrouted; that's an ops concern, not a code one.

4.4 Production concerns when adding an agent live

  • State schema stabilitythe registry pattern works because the shared state (tasks/results/next_agent) doesn't change per agent. If a new agent needs new state keys, that IS a schema change → version it (checkpointed old runs must still deserialize; additive keys with defaults are safe).
  • In-flight runsapproach 1 never changes the graph, so resuming old checkpoints is safe. With approach 3 (recompile), keep serving old runs on the old compiled graph and start new thread_ids on the new one (blue-green at the graph level).
  • Validation & securitythe supervisor must validate routed names against the registry (LLMs hallucinate worker names; the UNROUTABLE branch above is that guard). A new agent inherits real permissions: scope its tools/credentials before registering, gate side-effecting ones behind HITL (Failure Handling and Resilience §9).
  • Canary the newcomerregister with a traffic_fraction or enabled=False flag first; route a slice of matching tasks to it; watch its per-agent error rate/cost before full enrollment.
  • Registry as the control planebecause agents are rows, you also get: disable a misbehaving agent instantly (delete/flag the row), per-agent budgets, A/B two versions of the same specialty. The registry, not the graph, becomes what ops manages.
  • Remote agents (A2A)at larger scale the registry row holds an endpoint + agent card instead of a local function; the executor calls it over HTTP. Same pattern, network edition — see A2A in Agentic Systems and Patterns §14.

5. Interview Q&A

routerdecomposerQ: When would you pick each?registryone generic executor nodereducer

Q: What's the difference between an orchestrator and a supervisor? Supervisor = turn-by-turn router: an LLM looks at live state each iteration, picks one worker, sees its result, picks again until FINISH — sequential, reactive, great when each step depends on the last. Orchestrator(-worker) = decomposer: one planning call splits the goal into subtasks, dispatches them in parallel (Send in LangGraph), a synthesizer merges results — great for independent subtasks, latency ≈ slowest branch. "Orchestration" is also the umbrella term, and a supervisor is one form of it — but as patterns, that's the distinction.

Q: When would you pick each? Next step depends on previous result / conversational → supervisor. Subtasks independent once planned (research N topics, process N documents) → orchestrator, for the parallelism. Mixed jobs nest them: orchestrator top-level, supervisor loops inside workers.

Q: Your multi-agent system is deployed. Product wants one more agent. Walk me through it. If I built it naively — one node per agent, Literal router — it's a code change and redeploy. So I don't build it that way: agents live in a registry (DB/config), the graph has one generic executor node that looks the agent up by name at runtime, and the router's options + roster prompt are built from the registry per request. Adding an agent = inserting a registry row: the schema admits it, the roster advertises it, the executor can run it — zero recompile, zero redeploy, and in-flight checkpointed runs are unaffected because the topology never changed. Then the ops part: scope the new agent's tool permissions, canary it on a traffic slice, watch per-agent error rate and cost, and keep a kill-switch flag in the row.

Q: What breaks if two parallel orchestrator workers write the same state key? InvalidUpdateError — unless the key has a reducer (Annotated[list, operator.add]), which merges concurrent writes instead of conflicting. Any fan-in key needs one.

Q: What's the supervisor's biggest production weakness, and the orchestrator's? Supervisor: it's a serial bottleneck — every hop costs a router LLM call, and a bad router loops (cap steps, validate routes). Orchestrator: the plan is a single point of failure — a bad decomposition poisons all N branches (validate the plan, cap N), and the synthesizer must handle k-of-N partial failure instead of assuming all workers returned.
