1. Core Concepts

LangGraph is a stateful agent orchestration framework that models workflows as directed graphs with cycles, enabling LLM applications to loop, branch, and persist state across steps. Unlike linear LangChain chains, LangGraph provides explicit control over execution flow, built-in checkpointing, and human-in-the-loop capabilities.

WHY LANGGRAPH?
  LangChain chains = fixed pipelines (A → B → C)
  LangGraph = stateful GRAPHS with cycles, conditions, persistence

  ┌─────────────────────────────────────────────┐
  │  Agent Loop:                                │
  │    Start → LLM → Tool Decision?            │
  │              ↙ Yes       ↘ No              │
  │         Execute Tool    Return Answer       │
  │              ↓                              │
  │         Update State                        │
  │              ↓                              │
  │         Back to LLM (cycle!)                │
  └─────────────────────────────────────────────┘

  KEY DIFFERENTIATORS:
  - Cycles (agents that loop)
  - Persistence (checkpoint state, resume later)
  - Human-in-the-loop (pause, inspect, approve)
  - Streaming (token-level, node-level)
  - Controllability (explicit graph, not black box)
# pip install langgraph
from langgraph.graph import StateGraph, START, END
from typing import TypedDict, Annotated
from operator import add

# Simplest graph
class State(TypedDict):
    messages: Annotated[list, add]  # Append to list on update

def chatbot(state: State):
    response = model.invoke(state["messages"])
    return {"messages": [response]}

graph = StateGraph(State)
graph.add_node("chatbot", chatbot)
graph.add_edge(START, "chatbot")
graph.add_edge("chatbot", END)
app = graph.compile()

result = app.invoke({"messages": [("human", "Hello!")]})

2. StateGraph & State Schemas

privateWhy it matters

StateGraph is the central construct in LangGraph where you define the graph's state schema, add nodes and edges, and compile the executable workflow. State schemas (TypedDict, Pydantic, or MessagesState) define the data structure shared across all nodes, with reducers controlling how concurrent state updates are merged.

from typing import TypedDict, Annotated, Literal
from langgraph.graph import MessagesState
from pydantic import BaseModel

# ── Option 1: TypedDict (lightweight) ────────────────────
class AgentState(TypedDict):
    messages: Annotated[list, add]   # Reducer: append new messages
    context: str                      # Overwrite on update
    step_count: int
    final_answer: str | None

# ── Option 2: MessagesState (pre-built for chat) ─────────
# Includes 'messages' with proper reducer
class MyState(MessagesState):
    query: str
    documents: list[str]
    
# ── Option 3: Pydantic (with validation) ─────────────────
class ValidatedState(BaseModel):
    messages: Annotated[list, add]
    temperature: float = 0.7  # Default + type validation
    
# ── Reducers (how state updates are merged) ──────────────
# add: Append to list (for messages)
# Default: Overwrite (for strings, ints)
# Custom:
def keep_last_n(existing, new, n=10):
    return (existing + new)[-n:]

class State(TypedDict):
    messages: Annotated[list, keep_last_n]  # Keep last 10

Multiple schemas — input, output & private state

One graph can expose a narrower interface than its full internal state: callers pass only the input schema, receive only the output schema, and nodes can pass private scratch data that never leaks to the caller.

# ── input_schema / output_schema: hide internal state from callers ──
class InputState(TypedDict):        # what invoke() accepts
    question: str

class OutputState(TypedDict):       # what invoke() returns
    answer: str

class OverallState(TypedDict):      # full internal working state
    question: str
    docs: list                      # internal only — never returned
    answer: str

graph = StateGraph(OverallState, input_schema=InputState, output_schema=OutputState)
# invoke({"question": ...}) → {"answer": ...}; `docs` stays internal.

# ── Private state: node-to-node scratch channels ─────────
# A node can declare its OWN input schema; keys in it that aren't in the
# graph schema are private — visible only to nodes that declare them.
class PrivateState(TypedDict):
    scratch: str                    # not in OverallState → not in output

def step_a(state: OverallState) -> PrivateState:
    return {"scratch": "intermediate reasoning"}

def step_b(state: PrivateState):    # reads the private channel
    return {"answer": f"based on {state['scratch']}"}

Why it matters: subgraph/tool intermediate junk (raw retrieved docs, tool payloads, chain-of-thought) shouldn't pollute the public API of the graph. Same idea as a function's local variables vs its signature.

3. Nodes & Edges

Nodes are Python functions that read from and write to the graph's shared state, each performing a discrete step such as retrieval, generation, or grading. Edges define the execution flow between nodes, determining the order in which steps run from START to END.

from langgraph.graph import StateGraph, START, END

graph = StateGraph(AgentState)

# ── Nodes (functions that read/write state) ──────────────
def retrieve(state: AgentState):
    """Retrieve relevant documents."""
    docs = retriever.invoke(state["query"])
    return {"documents": [doc.page_content for doc in docs]}

def generate(state: AgentState):
    """Generate answer from documents."""
    context = "\n".join(state["documents"])
    response = model.invoke(f"Context: {context}\nQuestion: {state['query']}")
    return {"final_answer": response.content}

def grade(state: AgentState):
    """Grade document relevance."""
    # ... grading logic ...
    return {"documents": relevant_docs}

graph.add_node("retrieve", retrieve)
graph.add_node("grade", grade)
graph.add_node("generate", generate)

# ── Edges (connections between nodes) ────────────────────
graph.add_edge(START, "retrieve")
graph.add_edge("retrieve", "grade")
graph.add_edge("grade", "generate")
graph.add_edge("generate", END)

app = graph.compile()
result = app.invoke({"query": "What is RAG?"})

4. Conditional Routing

Conditional routing lets the graph dynamically choose the next node based on the current state, enabling the LLM to drive the execution path. A routing function inspects the state (e.g., checking for tool calls) and returns a string key that maps to the next node, supporting multi-way branching.

# ── Conditional edges (LLM decides next step) ────────────
def should_continue(state: AgentState) -> Literal["tools", "end"]:
    """Route based on whether the LLM wants to call tools."""
    last_message = state["messages"][-1]
    if last_message.tool_calls:
        return "tools"
    return "end"

graph.add_conditional_edges(
    "agent",  # Source node
    should_continue,  # Routing function
    {
        "tools": "tool_node",  # If returns "tools" → go to tool_node
        "end": END,            # If returns "end" → finish
    }
)

# ── Multi-way routing ────────────────────────────────────
def route_query(state) -> Literal["math", "code", "general"]:
    query = state["query"].lower()
    if "calculate" in query: return "math"
    if "code" in query: return "code"
    return "general"

graph.add_conditional_edges(
    "classifier",
    route_query,
    {"math": "math_agent", "code": "code_agent", "general": "general_agent"}
)

# ── Command API: route + update state in ONE return ──────
# Modern (v0.2+) idiom. A node returns Command instead of a dict,
# so you can skip separate add_conditional_edges wiring.
from langgraph.types import Command
from typing import Literal

def classifier(state) -> Command[Literal["math_agent", "general_agent"]]:
    topic = "math" if "calculate" in state["query"] else "general"
    return Command(
        goto="math_agent" if topic == "math" else "general_agent",  # routing
        update={"topic": topic},                                    # state update
    )
# The Literal return hint tells LangGraph which nodes are reachable
# (so .get_graph() can draw the edges). No add_conditional_edges needed.

# ── Command to hand off to a node in the PARENT graph ────
# Used heavily in multi-agent handoffs (see Multi-Agent section).
def specialist(state) -> Command:
    return Command(goto="supervisor", graph=Command.PARENT)

# ── Command + Send: fan out dynamically (map-reduce) ─────
from langgraph.types import Send
def planner(state) -> Command:
    return Command(goto=[Send("worker", {"task": t}) for t in state["tasks"]])

Routing pitfall: every value a router can return MUST be a key in the conditional-edges mapping (or a real node name for Command.goto). An unmapped/misspelled return raises InvalidUpdateError / sends the graph nowhere. Always include a default/fallback branch. Routers that can loop back to an earlier node create cycles — safe only with a guaranteed exit condition + recursion_limit (see Error Handling & Deadlocks).

5. Tool-Calling Agent

promptstatemodifierresponseformatpremodelhook

A tool-calling agent is a LangGraph workflow where the LLM decides which tools to invoke in a reasoning loop until it produces a final answer. LangGraph provides both a pre-built create_react_agent for quick setup and a customizable pattern using ToolNode with conditional edges for full control.

from langgraph.prebuilt import create_react_agent, ToolNode
from langchain_core.tools import tool

@tool
def search(query: str) -> str:
    """Search the web for current information."""
    return web_search(query)

@tool
def calculator(expression: str) -> float:
    """Evaluate a math expression."""
    return eval(expression)

# ── Pre-built ReAct agent ────────────────────────────────
agent = create_react_agent(
    ChatOpenAI(model="gpt-4o"),
    tools=[search, calculator],
    prompt="You are a research assistant. Be concise.",  # `state_modifier` is deprecated
)

result = agent.invoke({"messages": [("human", "What is 42^3?")]})

# ── Custom tool-calling agent ────────────────────────────
model_with_tools = ChatOpenAI(model="gpt-4o").bind_tools([search, calculator])

def call_model(state: MessagesState):
    response = model_with_tools.invoke(state["messages"])
    return {"messages": [response]}

tool_node = ToolNode([search, calculator])

def should_continue(state: MessagesState) -> Literal["tools", "__end__"]:
    if state["messages"][-1].tool_calls:
        return "tools"
    return "__end__"

graph = StateGraph(MessagesState)
graph.add_node("agent", call_model)
graph.add_node("tools", tool_node)
graph.add_edge(START, "agent")
graph.add_conditional_edges("agent", should_continue)
graph.add_edge("tools", "agent")

agent = graph.compile()

Modern create_react_agent options (v0.3+)

The prebuilt agent has grown well beyond model + tools:

from pydantic import BaseModel
from langgraph.checkpoint.memory import MemorySaver
from langgraph.store.memory import InMemoryStore

class Answer(BaseModel):
    summary: str
    sources: list[str]

agent = create_react_agent(
    model,
    tools=[search, calculator],
    prompt="You are a research assistant. Always cite sources.",  # replaces state_modifier
    response_format=Answer,         # coerce the FINAL answer into a schema
    checkpointer=MemorySaver(),     # short-term memory (per thread_id)
    store=InMemoryStore(),          # long-term cross-thread memory
    pre_model_hook=trim_or_summarize,   # runs BEFORE each model call — keep context in budget
    post_model_hook=guardrail_check,    # runs AFTER each model call — validation/guardrails
)
  • prompt replaces the deprecated state_modifier (accepts a string, message list, or callable).
  • response_format puts a typed final answer in result["structured_response"].
  • pre_model_hook is the idiomatic place to trim/summarize history each turn (see 12_Context_Management_and_Summarization.md).

5.5 Workflows vs Agents — Pattern Catalog (with diagrams)

Workflowcontrol flow is predefined by youAgentRule of thumbopen-ended, dynamictools

The single most important design decision. From Anthropic's Building Effective Agents, adopted by LangGraph. - Workflow = the control flow is predefined by you (the LLM fills in steps, but the path is fixed). Predictable, cheap, testable. - Agent = the LLM decides the control flow at runtime (which tool, how many steps, when to stop). Flexible, but less predictable and costlier.

Rule of thumb: start with the simplest thing that works — a single prompt, then a workflow. Reach for an agent only when the task needs open-ended, dynamic decisions you can't enumerate up front.

The building block — the Augmented LLM

Every pattern below is built from one unit: an LLM given tools, retrieval, and memory.

                ┌──────────────┐
   query ─────► │     LLM      │ ─────► response
                └──────┬───────┘
          ┌───────────┼────────────┐
          ▼            ▼            ▼
      [ Tools ]   [ Retrieval ]  [ Memory ]

Workflow 1 — Prompt Chaining (decompose into fixed sequential steps)

Use when a task splits into predictable sub-steps (e.g. outline → draft → polish). Add a gate to fail fast.

 in ─► [LLM 1] ─► (gate / check) ─► [LLM 2] ─► [LLM 3] ─► out
                       │ fail
                       └────► exit / fix
g = StateGraph(State)
g.add_node("outline", outline); g.add_node("draft", draft); g.add_node("polish", polish)
g.add_edge(START, "outline")
g.add_conditional_edges("outline", lambda s: "draft" if s["ok"] else END)  # gate
g.add_edge("draft", "polish"); g.add_edge("polish", END)

Workflow 2 — Routing (classify, then dispatch to a specialist)

Use when inputs fall into distinct categories each handled best differently (billing vs technical vs refund).

                    ┌─► [ Handler A ]
 in ─► [ Router ] ──┼─► [ Handler B ] ─► out
        (classify)  └─► [ Handler C ]
def route(s) -> Literal["billing","tech","refund"]:
    return classify_llm(s["query"])          # LLM/classifier picks the branch
g.add_conditional_edges("router", route, {"billing":"billing","tech":"tech","refund":"refund"})

Workflow 3 — Parallelization (run independent calls at once)

Two flavors. Sectioning: split the work into independent parts. Voting: run the same task several times and aggregate (majority / best-of-N) for reliability.

 SECTIONING                          VOTING
        ┌►[LLM: tone ]┐                  ┌►[LLM]┐
 in ─►──┼►[LLM: facts]┼►[Aggregate]►out  in►──┼►[LLM]┼►[Vote / pick best]►out
        └►[LLM: style]┘                  └►[LLM]┘

In LangGraph: add multiple edges out of one node (fan-out runs in parallel), and a reducer (Annotated[list, add]) collects results into a join node.

Workflow 4 — Orchestrator-Workers (dynamic number of subtasks)

Like sectioning, but the orchestrator decides how many workers and what each does at runtime — you don't know the subtasks in advance (e.g. "edit these N files", "research these M sub-questions"). This is LangGraph's Send / map-reduce.

                      ┌─► [ Worker 1 ]┐
 in ─► [ Orchestrator ]┼─► [ Worker 2 ]┼─► [ Synthesizer ] ─► out
       (plans subtasks)└─► [ Worker N ]┘
       (# workers chosen at runtime)
def assign(s):                       # orchestrator fans out dynamically
    return [Send("worker", {"task": t}) for t in s["subtasks"]]
g.add_conditional_edges("orchestrator", assign, ["worker"])
g.add_edge("worker", "synthesizer")  # results merged via a reducer

Workflow 5 — Evaluator-Optimizer (generate → critique → refine loop)

Use when output quality improves with feedback and you have clear eval criteria (translation, code that must pass tests). One LLM generates, another evaluates and returns feedback, loop until "accept".

 in ─► [ Generator ] ──┬─► [ Evaluator ] ── accept ──► out
            ▲          │         │ reject (+ feedback)
            └──────────┴─────────┘   (loop, capped by a step budget)
def gate(s) -> Literal["generator","__end__"]:
    return END if s["verdict"] == "accept" or s["iters"] >= 3 else "generator"
g.add_edge("generator", "evaluator")
g.add_conditional_edges("evaluator", gate)

This is the Reflection pattern. When the critique is distilled into durable lessons stored in memory and reused across full retries, it becomes Reflexion — full build-outs (code, diagrams, interview Q&A) in 11_Agentic_Systems_and_Patterns.md.

Agent — LLM-directed control flow (the loop is not fixed)

A true agent runs an open-ended loop: the LLM repeatedly decides which tool to call, observes the result, and continues until it decides it's done (or hits a budget). This is the ReAct loop / create_react_agent.

              ┌──────────────────────────────────────┐
              ▼  (observation fed back into context)  │
 query ─► [ LLM: think + act ] ─► tool call? ─yes─► [ Tool ] ─┘
              │
              └─ no ─► final answer
   (loops an unknown number of times — guard with recursion_limit)
from langgraph.prebuilt import create_react_agent
agent = create_react_agent(model, tools=[search, calculator, db_query])
agent.invoke({"messages": [("user", "…")]}, {"recursion_limit": 25})

When to use which

NeedUse
Fixed, known stepsPrompt chaining
Distinct input categoriesRouting
Independent subtasks / reliability via votingParallelization
Subtasks unknown until runtimeOrchestrator-workers (Send)
Iterative refinement against criteriaEvaluator-optimizer
Open-ended, dynamic tool use, unknown #stepsAgent (ReAct)

Interview soundbite: "Workflows give predictability and lower cost; agents give flexibility at the cost of predictability. I default to the simplest workflow that solves the task and only escalate to an agent when the control flow genuinely can't be predefined — and even then I cap it with a recursion limit, budgets, and human-in-the-loop."

6. Human-in-the-Loop

Human-in-the-loop is a LangGraph feature that pauses graph execution before a specified node, allowing a human to inspect, approve, modify, or reject the pending action. This is critical for high-stakes operations like database writes or financial transactions where automated tool execution requires human oversight.

from langgraph.checkpoint.memory import MemorySaver

# ── Interrupt before a node (require approval) ──────────
graph = StateGraph(MessagesState)
graph.add_node("agent", call_model)
graph.add_node("tools", tool_node)
# ... edges ...

agent = graph.compile(
    checkpointer=MemorySaver(),
    interrupt_before=["tools"]  # Pause before executing tools
)

config = {"configurable": {"thread_id": "1"}}

# First invocation — pauses before tools
result = agent.invoke({"messages": [("human", "Delete all files")]}, config)
# Agent wants to call a tool — but execution is paused

# Inspect what the agent wants to do
snapshot = agent.get_state(config)
print(snapshot.values["messages"][-1].tool_calls)

# Option A: Approve — resume execution
result = agent.invoke(None, config)  # Continue from checkpoint

# Option B: Reject — modify state and continue
agent.update_state(config, {"messages": [("human", "Actually, don't delete anything")]})
result = agent.invoke(None, config)

Dynamic interrupts — the interrupt() function (v0.2+, recommended)

interrupt_before pauses at fixed nodes. The modern approach calls interrupt() inside a node to pause exactly where needed (e.g. only when an action is risky), surface a payload to the human, and resume with their input via Command(resume=...). Requires a checkpointer.

from langgraph.types import interrupt, Command

def approval_node(state):
    # Execution pauses here; the value is shown to the human.
    decision = interrupt({
        "question": "Approve this action?",
        "action": state["pending_action"],
    })
    # Resumes here with whatever the human passed to Command(resume=...)
    if decision == "approve":
        return {"messages": [AIMessage(content="Action approved and executed.")]}
    return {"messages": [AIMessage(content="Action rejected.")]}

graph_app = graph.compile(checkpointer=MemorySaver())
config = {"configurable": {"thread_id": "1"}}

# First call pauses at interrupt() — inspect the surfaced payload
result = graph_app.invoke({"pending_action": "delete DB"}, config)
print(result["__interrupt__"])     # the {"question": ..., "action": ...} payload

# Resume by sending the human's answer back into interrupt()
result = graph_app.invoke(Command(resume="approve"), config)

interrupt() (dynamic, in-node) vs interrupt_before/after (static, at compile time): prefer interrupt() for conditional approvals and for collecting human input mid-run; use static breakpoints for simple "always pause before tools".

7. Memory & Checkpointing

contentSemanticEpisodictask episodesfew-shot examplesProcedural

Checkpointing saves the complete graph state at each step to persistent storage, enabling short-term memory (conversation history within a thread), long-term memory (cross-conversation facts), and time travel (replaying from any past state). LangGraph supports in-memory checkpointers for development and PostgreSQL-backed stores for production.

from langgraph.checkpoint.memory import MemorySaver
from langgraph.checkpoint.postgres import PostgresSaver
from langgraph.store.memory import InMemoryStore

# ── Short-term memory (conversation within thread) ──────
checkpointer = MemorySaver()  # In-memory (dev)
# checkpointer = PostgresSaver.from_conn_string("postgresql://...")  # Production

agent = graph.compile(checkpointer=checkpointer)

config = {"configurable": {"thread_id": "user-123"}}
agent.invoke({"messages": [("human", "My name is Alice")]}, config)
agent.invoke({"messages": [("human", "What is my name?")]}, config)
# → Remembers "Alice" from the same thread

# ── Long-term memory (cross-conversation facts) ─────────
store = InMemoryStore()

# Save facts about a user
store.put(("users", "alice"), "preferences", {"language": "Python", "level": "senior"})

# Retrieve in a node
def personalized_agent(state, config, *, store):
    user_id = config["configurable"]["user_id"]
    prefs = store.get(("users", user_id), "preferences")
    # Use prefs to customize response
    ...

# ── Semantic search over long-term memory ───────────────
# Index memories by embedding → retrieve by MEANING, not by exact key.
from langchain_openai import OpenAIEmbeddings
store = InMemoryStore(index={
    "embed": OpenAIEmbeddings(model="text-embedding-3-small"), "dims": 1536,
})
store.put(("users", "alice", "memories"), "m1",
          {"text": "Prefers concise, code-first answers"})
hits = store.search(("users", "alice", "memories"),
                    query="how should I format my replies?", limit=3)
# hits → most semantically relevant memories (RAG-over-memory for personalization)

# ── Time travel (inspect & replay past states) ──────────
# Get all checkpoints for a thread
for state in agent.get_state_history(config):
    print(state.config, state.values["messages"][-1])

# Replay from a specific checkpoint
past_config = state.config  # Config from a past state
agent.invoke(None, past_config)  # Resume from that point

The three types of long-term memory — semantic · episodic · procedural

The Store above is mechanism. The content you put in it falls into three memory types (borrowed from cognitive science — the canonical LangGraph framing). Short-term memory = the thread (checkpointer); long-term memory = the Store, and it comes in three flavors:

TypeHuman analogyWhat it holdsAgent useWhere it lives
SemanticFacts you knowUser facts, preferences, domain knowledgePersonalization; RAG-over-memoryStore namespace, often embedded for semantic search
EpisodicExperiences you've hadPast task episodes — the input + the trajectory that worked (or failed)Retrieve similar past episodes as few-shot examples ("last time this worked…")Store, keyed/embedded by the task
ProceduralSkills / how-toThe agent's own rules & instructions (evolving system prompt)Self-improvement: rewrite its own guidance from feedbackStore (or versioned prompt), injected into the system prompt
from langgraph.store.memory import InMemoryStore
from langchain_openai import OpenAIEmbeddings

# Embed episodic/semantic memories so we retrieve by MEANING, not exact key.
store = InMemoryStore(index={
    "embed": OpenAIEmbeddings(model="text-embedding-3-small"), "dims": 1536,
})

# ── SEMANTIC MEMORY: durable facts about the user/domain ─────────────────
store.put(("alice", "facts"), "role", {"text": "Alice is a senior Python backend dev"})

# ── EPISODIC MEMORY: store a WHOLE past episode (task → what worked) ──────
# After a task finishes successfully, write the episode. Later, on a NEW task,
# retrieve the most similar past episodes and inject them as few-shot examples.
def save_episode(task: str, actions: list[str], outcome: str, success: bool):
    store.put(("alice", "episodes"), f"ep-{hash(task)}", {
        "task": task, "actions": actions, "outcome": outcome, "success": success,
    })

def recall_episodes(new_task: str, k: int = 3):
    # semantic search over past episodes → "how did I handle tasks like this before?"
    hits = store.search(("alice", "episodes"), query=new_task, limit=k)
    return [h.value for h in hits if h.value["success"]]   # learn from wins

def agent_node(state, config, *, store):
    examples = recall_episodes(state["task"])
    few_shot = "\n".join(f"- Task: {e['task']} → did: {e['actions']}" for e in examples)
    prompt = f"Similar past episodes that worked:\n{few_shot}\n\nNow do: {state['task']}"
    return {"messages": [llm.invoke(prompt)]}
# ↑ This is exactly the mechanism behind Reflexion (§ 11 / Agentic Patterns file):
#   episodic memory = the verbal lessons that survive across trials/sessions.

# ── PROCEDURAL MEMORY: the agent edits its OWN instructions over time ─────
def get_instructions():
    got = store.get(("alice", "procedures"), "system_prompt")
    return got.value["text"] if got else "You are a helpful assistant."

def update_instructions(feedback: str):
    """After a failure/correction, ask the LLM to revise its own rulebook, then persist it."""
    current = get_instructions()
    revised = llm.invoke(
        f"Current instructions:\n{current}\n\nFeedback:\n{feedback}\n\n"
        f"Return improved instructions."
    ).content
    store.put(("alice", "procedures"), "system_prompt", {"text": revised})
# Next run injects get_instructions() into the system prompt → the agent has "learned".

Which type to reach for: semantic = "remember what" (facts/preferences), episodic = "remember how it went" (few-shot from experience), procedural = "remember how to behave" (self-improving instructions). Most production agents use semantic + episodic; procedural is the advanced self-tuning layer. Semantic and episodic are naturally embedded for similarity search; procedural is usually a single evolving document.

Don't hand-roll it — LangMem: the langmem SDK packages exactly this on top of BaseStore: create_manage_memory_tool() / create_search_memory_tool() give the agent tools to write/search its own memories in the hot path, and a background memory manager extracts facts from finished conversations asynchronously (so extraction doesn't add latency to every turn). Interview one-liner: hot-path memory tools vs background consolidation — LangMem provides both patterns prebuilt.

8. Subgraphs & Map-Reduce

Intuitionsameeach one in parallellistmapreducer

Subgraphs allow you to encapsulate complex workflows as reusable, self-contained graphs that can be nested as nodes within a parent graph. The map-reduce pattern uses LangGraph's Send() API to fan out tasks to multiple parallel node instances, then collect and reduce the results back into the parent state.

# ── Subgraphs (nested graphs as nodes) ───────────────────
research_graph = StateGraph(ResearchState)
# ... build research subgraph ...
research_app = research_graph.compile()

writing_graph = StateGraph(WritingState)
# ... build writing subgraph ...
writing_app = writing_graph.compile()

# Parent graph uses subgraphs as nodes
parent = StateGraph(OverallState)
parent.add_node("research", research_app)
parent.add_node("writing", writing_app)
parent.add_edge(START, "research")
parent.add_edge("research", "writing")
parent.add_edge("writing", END)

Map-Reduce — the Send API (dynamic fan-out → fan-in)

Intuition. You have a list of items (topics, documents, files) and want to run the same node on each one in parallel, then combine the results. You don't know the count until runtime, so static edges won't do. Send("node", payload) means "spin up one fresh instance of node and hand it exactly this payload as its state." Return a list of Sends and LangGraph launches them all in one superstep (the map). Each writes to a list key guarded by a reducer, so their outputs merge instead of clobbering each other; a final node reads that merged list (the reduce).

                     ┌─► [worker]  topic="GPUs"   ─┐
 [plan] ──Send×N──►  ├─► [worker]  topic="RAG"    ─┼─►[reduce]─► END
 (split into topics) └─► [worker]  topic="Agents" ─┘   (joins the list)
                          (one instance PER item, all in ONE superstep)
import operator
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.constants import Send          # also re-exported from langgraph.types

# 1) STATE: the fan-in key MUST have a reducer, or the parallel workers
#    writing the same key raise InvalidUpdateError.
class State(TypedDict):
    topics:    list[str]
    summaries: Annotated[list[str], operator.add]   # ← reducer merges fan-in
    report:    str

# 2) MAP router — returns a LIST of Send objects (NOT a state dict).
#    Each Send carries the PRIVATE state for one worker instance.
def fan_out(state: State):
    return [Send("worker", {"topic": t}) for t in state["topics"]]

# 3) WORKER — runs once per item. Its input is the Send payload,
#    so it sees {"topic": ...}, not the whole parent state.
def worker(payload: dict):
    summary = llm.invoke(f"Summarize the topic: {payload['topic']}").content
    return {"summaries": [summary]}      # append-via-reducer → merges safely

# 4) REDUCE — runs ONCE, after ALL workers finish; sees the merged list.
def reduce(state: State):
    joined = "\n".join(state["summaries"])
    return {"report": llm.invoke(f"Synthesize one report:\n{joined}").content}

g = StateGraph(State)
g.add_node("worker", worker)
g.add_node("reduce", reduce)
g.add_conditional_edges(START, fan_out, ["worker"])  # map: START → N workers
g.add_edge("worker", "reduce")                       # fan-in to the join node
g.add_edge("reduce", END)
app = g.compile()

app.invoke({"topics": ["GPUs", "RAG", "Agents"], "summaries": [], "report": ""})

Worked trace for topics=["GPUs", "RAG", "Agents"]:

superstep 1  fan_out(START) → [Send(worker,{topic:GPUs}),
                               Send(worker,{topic:RAG}),
                               Send(worker,{topic:Agents})]
superstep 2  worker×3 run IN PARALLEL, each returns {"summaries":[<one>]}
             reducer (operator.add) concatenates →
                 summaries = [sumGPUs, sumRAG, sumAgents]
superstep 3  reduce() sees all 3, writes report

Gotchas - fan_out returns a list of Send, not a {...} update — it's a router, wired with add_conditional_edges, and you pass ["worker"] as the allowed targets. - The fan-in key needs a reducer (Annotated[list, operator.add]). Without it, the parallel workers writing summaries crash with InvalidUpdateError. - The whole fan-out of N workers is one superstep, not N — recursion_limit counts supersteps, so N=1000 workers is still 1 step. - Each worker's state is its Send payload, not the parent state — pass everything it needs in the payload.

8.1 Execution-control knobs — deferred fan-in, node caching & durability

Three production knobs that rarely get their own section but matter a lot:

# ── defer=True : make a fan-in node WAIT for ALL upstream paths ──
# Without defer, a join node can fire as soon as ONE branch reaches it.
# With defer, LangGraph holds it until every pending branch finishes — the
# correct way to "reduce" after a Send fan-out of UNEVEN-length branches.
builder.add_node("reduce", reduce, defer=True)

# ── Node-level caching : skip re-running a node on identical input ──
from langgraph.types import CachePolicy
from langgraph.cache.memory import InMemoryCache

builder.add_node("embed", embed_node, cache_policy=CachePolicy(ttl=600))
graph = builder.compile(cache=InMemoryCache())
# Same input within the TTL → cached result, node body skipped (great for
# expensive deterministic steps: embedding, retrieval, pure transforms).

# ── Durability : how often state is persisted to the checkpointer ──
graph.invoke(inputs, config, durability="async")
#   "sync"  → write the checkpoint BEFORE continuing (safest, slowest)
#   "async" → write WHILE the next step runs (balanced; a good default)
#   "exit"  → persist only at the end (fastest, least crash-durable)

Reach for them when: uneven parallel branches feed one reducer → defer=True; a node repeats identical expensive work → cache_policy; long human-in-the-loop pauses or crash-recovery matters → durability="sync"; raw throughput matters more than mid-run durability → "exit".

9. Streaming

Streaming in LangGraph provides real-time visibility into graph execution by emitting events at the node level (state updates after each node completes) and at the token level (individual LLM output tokens). Multiple stream modes can be combined to simultaneously observe both high-level workflow progress and granular model output.

# ── Stream by node updates ───────────────────────────────
for event in agent.stream({"messages": [("human", "...")]}, config):
    for node_name, state_update in event.items():
        print(f"Node: {node_name}, Output: {state_update}")

# ── Stream tokens (LLM output) ──────────────────────────
for event in agent.stream(
    {"messages": [("human", "...")]}, 
    config, 
    stream_mode="messages"
):
    msg, metadata = event
    if metadata.get("langgraph_node") == "agent":
        print(msg.content, end="")

# ── Multiple stream modes ────────────────────────────────
for event in agent.stream(
    {"messages": [("human", "...")]},
    config,
    stream_mode=["updates", "messages"]  # Both node updates AND messages
):
    print(event)

# ── stream_mode="values": full state snapshot after each step ──
for state in agent.stream(inputs, config, stream_mode="values"):
    print(state["messages"][-1])      # the ENTIRE state each step (vs only the delta)

# ── stream_mode="custom": emit progress from INSIDE a node ──
from langgraph.config import get_stream_writer

def long_node(state):
    writer = get_stream_writer()
    writer({"status": "fetching docs…"})       # surfaces immediately to the consumer
    docs = retriever.invoke(state["query"])
    writer({"status": f"got {len(docs)} docs"})
    return {"documents": docs}

for chunk in agent.stream(inputs, config, stream_mode="custom"):
    print(chunk)                                # your {"status": ...} payloads, live

# ── Stream nested subgraphs too ──────────────────────────
for ns, event in agent.stream(inputs, config, stream_mode="updates", subgraphs=True):
    print(ns, event)          # ns = namespace path saying WHICH (sub)graph emitted it
# Modes: "updates" (deltas) · "values" (full state) · "messages" (LLM tokens)
#        · "custom" (writer payloads) · "debug" (everything)

10. Error Handling, Retries & Deadlocks

node-level RetryPolicydeadlock-like / stuck statessuperstepsRule of thumb

Error handling in LangGraph prevents runaway agent loops and gracefully recovers from transient failures during graph execution. Key mechanisms include recursion limits (capping the maximum number of steps), node-level RetryPolicy (LangGraph's native retry, no external library), ToolNode error capture, model fallbacks, and dedicated error-routing nodes. Equally important is recognizing deadlock-like / stuck states — LangGraph uses a superstep (bulk-synchronous parallel) model, so classic thread deadlocks are rare, but cyclic handoffs, concurrent-write conflicts, dead-end nodes, and unresumed interrupts all hang or crash a graph.

from langgraph.errors import GraphRecursionError

# ── Recursion limit (prevent infinite loops) ─────────────
agent = graph.compile()
try:
    result = agent.invoke(
        {"messages": [("human", "...")]},
        config={"recursion_limit": 25}  # Max SUPERSTEPS, not LLM calls
    )
except GraphRecursionError:
    # Hit the cap — agent likely stuck in a cycle. Return a safe fallback.
    result = {"messages": [AIMessage(content="Couldn't finish in time.")]}

Native node-level retries (RetryPolicy)

Prefer LangGraph's built-in RetryPolicy over wrapping nodes in tenacity — it integrates with checkpointing (a retried node re-runs from the same state).

from langgraph.types import RetryPolicy   # older path: langgraph.pregel
import httpx

graph.add_node(
    "call_api",
    call_api_node,
    retry=RetryPolicy(
        max_attempts=3,
        initial_interval=0.5,
        backoff_factor=2.0,            # exponential backoff
        jitter=True,
        retry_on=(httpx.HTTPStatusError, ConnectionError),  # only transient
    ),
)
# tenacity still works for fine-grained control, but RetryPolicy is the default.

Tool errors (ToolNode)

By default a tool raising an exception kills the graph. ToolNode can instead catch it and feed the error back to the LLM as a ToolMessage, so the agent can self-correct (retry with different args) on the next loop.

from langgraph.prebuilt import ToolNode

# True  → catch all, return a generic error ToolMessage to the model
# str   → catch all, return this custom message
# tuple → catch only these exception types
# callable → catch and format with your function
tool_node = ToolNode(
    [search, calculator],
    handle_tool_errors="That tool failed — check the arguments and try again.",
)

Model fallbacks inside a node

# Same with_fallbacks() pattern as LangChain — swap providers on failure.
primary  = ChatOpenAI(model="gpt-4o")
backup   = ChatAnthropic(model="claude-sonnet-4-20250514")
llm = primary.with_fallbacks([backup]).bind_tools(tools)

def call_model(state):
    return {"messages": [llm.invoke(state["messages"])]}

Error routing (try → catch → recover)

# Use a conditional edge (or Command) to send failures to a recovery node.
def call_node(state):
    try:
        return {"result": risky_op(state), "error": None}
    except Exception as e:
        return {"error": str(e)}            # don't raise — record it

def route_on_error(state) -> Literal["error_handler", "continue"]:
    return "error_handler" if state.get("error") else "continue"

def handle_error(state):
    """Graceful recovery node — log, fallback answer, or escalate to human."""
    return {"messages": [AIMessage(
        content=f"I hit an issue: {state['error']}. Let me try differently.")]}

graph.add_node("error_handler", handle_error)
graph.add_conditional_edges("call_node", route_on_error,
                            {"error_handler": "error_handler", "continue": "next"})

Deadlocks, cycles & stuck states (and how to avoid them)

LangGraph executes in supersteps: all scheduled nodes in a step run (potentially in parallel), then their updates are merged before the next step. This BSP model avoids classic lock deadlocks, but several failure modes behave like a deadlock — the graph never reaches END:

COMMON "DEADLOCK" / STUCK-STATE MODES
  Symptom                         Cause                          Fix
  ──────────────────────────────┼──────────────────────────────┼─────────────────────────────
  GraphRecursionError            │ Infinite cycle — agent keeps  │ Guaranteed exit branch in the
                                 │ looping (LLM never returns a  │ router + recursion_limit; add a
                                 │ stop / two agents ping-pong)  │ step counter to force a stop
  InvalidUpdateError:            │ Two parallel branches write   │ Add a reducer (Annotated[list,
  "can receive only one value"   │ the SAME state key in one     │ add]) so concurrent writes merge
                                 │ step with no reducer          │ instead of conflict
  Graph silently halts           │ A node has NO outgoing edge   │ Every node must route to another
  (no error, no END)             │ and isn't wired to END        │ node or END (a "dead end")
  Hangs forever after invoke()   │ interrupt()/interrupt_before  │ Resume with invoke(Command(
                                 │ fired but you never resumed   │ resume=...)) / invoke(None, cfg)
  Branch never fires             │ Router returns a key missing  │ Map every possible return value;
                                 │ from the edge mapping         │ include a default branch
# 1) Break agent ping-pong loops with an explicit step budget
class State(TypedDict):
    messages: Annotated[list, add]
    steps: int

def agent(state):
    return {"messages": [llm.invoke(state["messages"])], "steps": state["steps"] + 1}

def should_continue(state) -> Literal["tools", "end"]:
    if state["steps"] >= 8:          # hard cap inside the router
        return "end"
    return "tools" if state["messages"][-1].tool_calls else "end"

# 2) Prevent concurrent-write InvalidUpdateError with a reducer
from operator import add
class FanOutState(TypedDict):
    # WITHOUT the reducer, two parallel workers writing 'results' deadlock-crash.
    results: Annotated[list, add]    # concurrent appends merge safely

# 3) Multi-agent handoff loops: cap handoffs or use a supervisor as the
#    single arbiter so two specialists can't bounce control forever.

Rule of thumb: any graph with cycles needs (a) a guaranteed exit condition the router can reach, (b) a sane recursion_limit, and (c) reducers on every key that parallel branches might write. recursion_limit counts supersteps, not LLM calls — a fan-out of N nodes is still one step.

11. Multi-Agent Architectures

Multi-agent architectures coordinate multiple specialized LLM agents to solve complex tasks that exceed a single agent's capabilities. LangGraph supports three primary patterns: supervisor (one LLM routes tasks), swarm (agents hand off to each other peer-to-peer), and hierarchical (tree of supervisors managing agent teams).

# ── Supervisor Pattern ───────────────────────────────────
# One LLM coordinates multiple specialized agents
def supervisor(state):
    """Route to the appropriate specialist agent."""
    response = supervisor_model.with_structured_output(Router).invoke(
        f"Route this task to the appropriate agent: {state['messages'][-1].content}\n"
        f"Options: researcher, coder, writer"
    )
    return {"next_agent": response.agent}

graph.add_node("supervisor", supervisor)
graph.add_node("researcher", researcher_agent)
graph.add_node("coder", coder_agent)
graph.add_node("writer", writer_agent)
graph.add_conditional_edges("supervisor", lambda s: s["next_agent"])

# ── Swarm Pattern ────────────────────────────────────────
# Agents hand off to each other directly (no central coordinator)
# Each agent decides which agent should handle the next step
# Good for: customer service routing, multi-step workflows

# ── Hierarchical Pattern ─────────────────────────────────
# Supervisor → Team Leads → Individual Agents
# Good for: complex tasks requiring multiple specialized teams
MULTI-AGENT COMPARISON:
  Pattern      │ Coordination  │ Best For              │ Complexity
  ─────────────┼───────────────┼───────────────────────┼──────────
  Supervisor   │ Central LLM   │ Clear task routing    │ Medium
  Swarm        │ Peer-to-peer  │ Dynamic handoffs      │ Medium
  Hierarchical │ Tree structure│ Complex multi-team    │ High
  Map-Reduce   │ Fan-out/in    │ Parallel independent  │ Low

For the two common topologies, use the official packages instead of wiring graphs by hand:

Tool-based handoffs & state-aware tools

A handoff is just a tool that returns a Command, and tools can read live graph state via InjectedState (the model never fills injected args):

from typing import Annotated

from langchain_core.messages import ToolMessage

    """Hand the conversation to the refunds agent."""
    return Command(
        goto="refunds", graph=Command.PARENT,
        update={"messages": [ToolMessage("Transferred to refunds", tool_call_id=tool_call_id)]},
    )

@tool

    """Summarize the chat by reading graph state directly (not model-supplied)."""
    return summarize(state["messages"])

Double-texting — user sends a NEW message mid-run

A real chat user doesn't wait for the agent to finish. The Platform names four strategies for the second message ("double text") — know all four:

StrategyBehaviorUse when
rejectRefuse the new message until the run finishesStrict one-at-a-time flows (payments)
enqueueQueue it; process after the current run completesEvery message matters (support tickets)
interruptStop the current run, keep its partial work in state, handle the new messageChat UX default — user changed their mind
rollbackCancel the run AND delete its partial checkpoints, start cleanNew message invalidates the old task entirely

Self-hosted equivalent: key an in-flight-run lock by thread_id and implement one of these yourself — the hard part is what to do with half-written state, which is exactly what interrupt-vs-rollback encodes.

    model_name = config["configurable"].get("model", "gpt-4o")

Modern Context API — context_schema + Runtime (v0.6+)

Stuffing user config into config["configurable"] works but is stringly-typed. The modern API declares a typed context schema on the graph and hands nodes a Runtime object:

from dataclasses import dataclass
from langgraph.runtime import Runtime

@dataclass
class Context:                       # typed, IDE-completable — not a magic dict
    user_id: str
    model: str = "gpt-4o-mini"

graph = StateGraph(State, context_schema=Context)

def agent_node(state: State, runtime: Runtime[Context]):
    llm = init_chat_model(runtime.context.model)     # typed access
    runtime.store                                    # long-term Store also lives here
    runtime.stream_writer({"progress": "thinking"})  # custom-mode streaming
    return {"messages": [llm.invoke(state["messages"])]}

# Pass context at invoke time — separate from config:
graph.invoke(inputs, context=Context(user_id="alice"),
             config={"configurable": {"thread_id": "t1"}})

The three data planes — interview framing: state = dynamic, written by nodes, checkpointed; context = static per-run inputs (user id, model choice, db handles) — read-only, not checkpointed; config configurable = run identity for the framework (thread_id, checkpoint_id). Old code merges the last two; the Context API separates them.

17. LangGraph Functional API

The functional API is an alternative to StateGraph — instead of defining nodes/edges, you write a regular Python function decorated with @entrypoint and delegate work to @task functions. Tasks run as separate steps with automatic checkpointing. Simpler for straightforward workflows.

from langgraph.func import entrypoint, task
from langgraph.checkpoint.memory import MemorySaver

@task
def analyze(text: str) -> str:
    return llm.invoke(f"Analyze: {text}").content

@task  
def summarize(analysis: str) -> str:
    return llm.invoke(f"Summarize: {analysis}").content

@entrypoint(checkpointer=MemorySaver())
def pipeline(text: str) -> str:
    result = analyze(text).result()    # .result() waits for completion
    summary = summarize(result).result()
    return summary

# Call like a normal function
output = pipeline.invoke("Long document...", config={"configurable": {"thread_id": "1"}})

18. Interview Deep Dive

CyclesState managementCheckpointingConditional routingFine-grained controlShort-term

Q1: What is LangGraph and how does it differ from LangChain chains?

A: LangGraph is a framework for building stateful, controllable agent workflows as directed graphs with cycles. Key differences from LangChain chains: (1) Cycles: Agents can loop (call LLM → execute tool → call LLM again). Chains are linear pipelines. (2) State management: Explicit state schema (TypedDict/Pydantic) that persists across steps. (3) Checkpointing: Save and resume execution, enabling human-in-the-loop and fault tolerance. (4) Conditional routing: LLM decides which node to execute next. (5) Fine-grained control: You see and control every step, unlike black-box agent frameworks.

Q2: Explain the ReAct agent pattern in LangGraph.

A: ReAct (Reason + Act) is a loop: (1) The LLM receives the conversation + available tools. (2) It either calls a tool (action) or returns a final answer (stop). (3) If a tool is called, the result is appended to messages. (4) Loop back to step 1. In LangGraph: the "agent" node calls the LLM with bound tools. A conditional edge checks if the response has tool_calls. If yes → route to "tools" node → back to "agent". If no → route to END. The graph is: START → agent → (tools → agent)* → END.

Q3: How does human-in-the-loop work?

A: Compile the graph with interrupt_before=["dangerous_node"] and a checkpointer. When execution reaches that node, it pauses and saves state. The developer/user can: (1) Inspect the pending action via get_state(). (2) Approve by calling invoke(None, config) to resume. (3) Reject by calling update_state() to modify state before resuming. (4) Edit tool call arguments. This is critical for high-stakes actions (database writes, API calls with side effects, financial transactions) where you want human approval before execution.

Q4: How do you handle memory across conversations?

A: Two types: (1) Short-term (within a conversation): Checkpointer stores all messages for a thread_id. Use MemorySaver (dev) or PostgresSaver (prod). Same thread_id = same conversation with full history. (2) Long-term (across conversations): InMemoryStore or PostgresStore for persistent facts — user preferences, past summaries, extracted entities. Accessed in nodes via the store parameter. Pattern: After each conversation, extract key facts and save to long-term store. At conversation start, retrieve relevant facts and inject into system prompt.

Q5: Compare supervisor vs. swarm vs. hierarchical multi-agent patterns.

A: Supervisor: One LLM routes tasks to specialized agents. Simple, centralized control, but supervisor is a bottleneck and may make routing errors. Swarm: Agents hand off to each other directly based on context. More flexible, no single point of failure, but harder to debug (no central coordinator). Hierarchical: Tree of supervisors → team leads → workers. Scales to complex tasks with multiple teams. Most complex to implement but handles large, multi-domain tasks well. Choose: simple routing → supervisor. Dynamic customer service → swarm. Complex research/analysis → hierarchical.

Q6: How do you deploy a LangGraph agent to production?

A: Options: (1) LangGraph Platform: Managed hosting with built-in API, streaming, cron jobs, webhooks. Deploy with langgraph deploy. (2) Self-hosted: Wrap in FastAPI/Flask, use PostgresSaver for checkpointing, deploy on Kubernetes. Key considerations: PostgreSQL for persistent checkpoints, Redis for caching, LangSmith for observability, rate limiting per user, authentication/authorization, graceful error handling with retry logic, recursion limits to prevent runaway agents.

Q7: How do you test LangGraph workflows?

A: Three levels: (1) Unit test nodes: Test each node function in isolation with mock state. Verify state mutations are correct. (2) Test routing logic: Call conditional edge functions with crafted state and verify they return the expected route. (3) Integration test: Compile the full graph and invoke with test inputs. Use mock LLMs (patch ChatOpenAI) for deterministic tests, real LLMs for smoke tests. (4) Snapshot testing: Use get_state_history() to verify the agent visited expected nodes in expected order. Always test edge cases: empty input, tool errors, recursion limit hit.

Q8: What is checkpointing and why is it important?

A: Checkpointing saves the complete graph state (messages, custom state, metadata) at each step to persistent storage. Importance: (1) Human-in-the-loop: Pause execution, resume after approval. (2) Fault tolerance: If the process crashes mid-execution, resume from last checkpoint. (3) Time travel: Inspect any past state, replay from any point. (4) Long-running workflows: Tasks that span hours/days can be checkpointed and resumed. (5) Debugging: See exactly what happened at each step. Implementation: MemorySaver for development (in-memory), PostgresSaver for production (persistent).

Q9: How do you handle errors in a LangGraph agent?

A: Layered: (1) Node retries — add_node(..., retry=RetryPolicy(max_attempts=3, backoff_factor=2)) for transient failures (timeouts, 429s); it re-runs the node from the same checkpointed state. (2) Tool errors — ToolNode(tools, handle_tool_errors=...) catches a tool exception and returns it to the LLM as a ToolMessage so the agent can self-correct instead of crashing. (3) Model fallbacks — llm.with_fallbacks([backup_model]) swaps providers on failure. (4) Error routing — nodes record errors in state ({"error": ...}) and a conditional edge routes to a recovery/escalation node rather than raising. (5) Recursion limit — catch GraphRecursionError to stop runaway loops. Choose per layer: retry transient infra errors, route logical errors, escalate to a human for high-stakes failures.

Q10: Can a LangGraph graph deadlock, and how do you prevent it?

A: Not in the classic mutex sense — LangGraph runs in supersteps (bulk-synchronous parallel): all scheduled nodes run, then updates merge, then the next step starts, so there are no threads waiting on locks. But several states act like a deadlock (graph never reaches END): (1) Infinite cycles — an agent that never returns a stop, or two agents handing off forever; surfaces as GraphRecursionError. Fix with a guaranteed exit branch in the router + a step-count cap + sane recursion_limit. (2) Concurrent-write conflict — two parallel branches write the same state key in one step with no reducer → InvalidUpdateError: can receive only one value per step. Fix by adding a reducer (Annotated[list, add]) so writes merge. (3) Dead-end node — a node with no outgoing edge that isn't wired to END; the graph silently halts. (4) Unresumed interrupt — interrupt/interrupt_before paused execution and nobody resumed; resume with invoke(None, config) or Command(resume=...). Rule: cyclic graphs need a reachable exit condition, a recursion limit, and reducers on every key parallel branches might touch.

Q11: How does routing work, and when do you use Command vs conditional edges?

A: Conditional edges (add_conditional_edges(src, router_fn, mapping)) separate deciding (the router returns a key) from wiring (the mapping points keys to nodes) — clean when one source fans to many destinations. Command lets a node return its routing decision and a state update together (return Command(goto="next", update={...})), so you don't wire a separate conditional edge; add a Literal[...] return hint so the graph can still be visualized. Use Command(goto=..., graph=Command.PARENT) for multi-agent handoffs (jump to a node in the parent graph) and Command(goto=[Send(...)]) for dynamic fan-out. Either way, every value the router can return must map to a real node or END, and always include a default branch — an unmapped return sends the graph nowhere.

Q12: A user sends a second message while the agent is still working on the first. What are your options?

A: This is double-texting. Four strategies (LangGraph Platform implements them natively; self-hosted you build one with a per-thread_id in-flight lock): reject (refuse until the run finishes — strict transactional flows), enqueue (queue and process after — when every message matters), interrupt (stop the run but keep its partial state, then handle the new message — the chat-UX default, user changed their mind), rollback (cancel AND delete the run's checkpoints, start clean — the new message invalidates the task). The interview follow-up is always about half-written state: interrupt keeps it, rollback discards it, and any tool side-effects already executed need idempotency keys or compensation regardless of strategy.

Q13: What's the difference between state, context, and config in LangGraph?

A: Three data planes. State is dynamic — nodes write it, reducers merge it, the checkpointer persists it. Context (context_schema + Runtime, v0.6+) is static per-run input — user id, model choice, db handles — read-only inside nodes via runtime.context, not checkpointed. Config configurable is framework run-identity — thread_id, checkpoint_id. Legacy code stuffs user values into configurable (stringly-typed dict); the Context API gives them a typed dataclass instead. Rule of thumb: if a node computes it → state; if the caller provides it → context; if the framework needs it to find the checkpoint → config.
