1. SQL Basics & SELECT

•

Q1. What is the difference between WHERE and HAVING?

WHERE filters rows before aggregation; HAVING filters groups after aggregation. WHERE cannot use aggregate functions; HAVING can.

•

Q2. What is the order of SQL clause execution?

FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT. Note: this is logical order, not written order.

•

Q3. Difference between DISTINCT and GROUP BY?

DISTINCT removes duplicates from result set. GROUP BY groups rows for aggregation. GROUP BY without aggregation functions behaves like DISTINCT but can also include aggregate calculations.

•

Q4. What does NULL mean in SQL?

NULL represents missing/unknown data. It is not zero or empty string. NULL = NULL is FALSE (use IS NULL). Any arithmetic with NULL returns NULL. Use COALESCE() or IFNULL() to handle NULLs.

•

Q5. Explain UNION vs UNION ALL.

UNION combines results and removes duplicates (slower). UNION ALL combines all results including duplicates (faster). Use UNION ALL when you know there are no duplicates or duplicates are acceptable.

•

Q6. What is the difference between DELETE, TRUNCATE, and DROP?

DELETE: removes specific rows (can use WHERE), logged, can rollback. TRUNCATE: removes all rows, faster, resets auto-increment. DROP: removes entire table structure and data.

•

Q7. Explain BETWEEN — is it inclusive?

Yes, BETWEEN is inclusive on both ends. WHERE x BETWEEN 1 AND 10 is equivalent to WHERE x >= 1 AND x <= 10.

•

Q8. What is the difference between IN and EXISTS?

IN checks a value against a list (materializes subquery). EXISTS checks if subquery returns any row (stops at first match). EXISTS is generally faster for large subqueries.

•

Q9. How does LIKE differ from REGEXP?

LIKE: simple pattern matching (% = any characters, _ = one character). REGEXP: full regular expression support (more powerful but slower).

•

Q10. What is an alias and when would you use one?

Alias renames a column or table temporarily using AS. Used for: readability, required for calculated columns, self-joins, and when column names conflict.

•

Q11. Explain CASE WHEN with an example.

SELECT name,
       CASE WHEN score >= 90 THEN 'A'
            WHEN score >= 80 THEN 'B'
            WHEN score >= 70 THEN 'C'
            ELSE 'F'
       END AS grade
FROM students;
•

Q12. What is COALESCE and how is it used?

Returns the first non-NULL argument. COALESCE(col1, col2, 'default'). Useful for replacing NULLs and providing defaults.

•

Q13. Difference between CHAR and VARCHAR?

CHAR: fixed length (padded with spaces). VARCHAR: variable length (stores only actual length). Use CHAR for fixed-format data (country codes), VARCHAR for variable text.

•

Q14. What are DML, DDL, DCL, and TCL?

DDL: CREATE, ALTER, DROP (structure). DML: SELECT, INSERT, UPDATE, DELETE (data). DCL: GRANT, REVOKE (permissions). TCL: COMMIT, ROLLBACK, SAVEPOINT (transactions).

•

Q15. How to handle NULL in ORDER BY?

NULLs sort first or last depending on the database. Use ORDER BY col NULLS LAST (PostgreSQL) or ORDER BY COALESCE(col, 'zzz') for control.

•

Q16. What is the difference between COUNT(*), COUNT(col), and COUNT(DISTINCT col)?

COUNT(*): counts all rows including NULLs. COUNT(col): counts non-NULL values in column. COUNT(DISTINCT col): counts unique non-NULL values.

•

Q17. Explain INSERT INTO ... SELECT.

Inserts rows from a SELECT query into another table. Useful for data migration, creating derived tables, and backups.

•

Q18. What does LIMIT/OFFSET do?

LIMIT restricts number of returned rows. OFFSET skips rows before starting to return. Used for pagination: LIMIT 10 OFFSET 20 returns rows 21-30.

•

Q19. What is a temporary table?

A table that exists only for the session/transaction. Created with CREATE TEMPORARY TABLE. Useful for intermediate calculations in complex queries.

•

Q20. Explain the difference between implicit and explicit joins.

Implicit: FROM t1, t2 WHERE t1.id = t2.id (old style). Explicit: FROM t1 JOIN t2 ON t1.id = t2.id (preferred, clearer, supports OUTER joins).

2. JOINs

•

Q21. Explain all types of JOINs with examples.

INNER: matching rows only. LEFT: all from left + matching right (NULL if no match). RIGHT: all from right + matching left. FULL OUTER: all from both (NULLs where no match). CROSS: every row × every row (Cartesian product).

•

Q22. What is a self-join? Give an example.

Joining a table with itself. Example: find employees and their managers:

SELECT e.name AS employee, m.name AS manager
FROM employees e LEFT JOIN employees m ON e.manager_id = m.id;
•

Q23. What is a CROSS JOIN and when would you use it?

Produces Cartesian product (every combination). Use for: generating date ranges, creating all possible pairings, combinatorial analysis.

•

Q24. Explain NATURAL JOIN.

Automatically joins on columns with same name in both tables. Risky: if column names change, join behavior changes silently. Prefer explicit JOIN ON.

•

Q25. How to do a LEFT JOIN excluding matching rows (anti-join)?

SELECT a.* FROM table_a a
LEFT JOIN table_b b ON a.id = b.id
WHERE b.id IS NULL;

Alternative: WHERE NOT EXISTS (SELECT 1 FROM table_b WHERE table_b.id = table_a.id)

•

Q26. What happens when you join on a column with NULLs?

NULL = NULL evaluates to FALSE in joins, so rows with NULL join keys are never matched. They appear in OUTER joins with NULLs for the other table's columns.

•

Q27. Explain the difference between ON and WHERE in a LEFT JOIN.

ON: conditions for matching rows (non-matching still appear with NULLs). WHERE: filters entire result (removes non-matching rows, converting LEFT to INNER effectively).

•

Q28. How to join more than two tables?

Chain JOINs: FROM a JOIN b ON ... JOIN c ON .... Order matters for performance but not for correctness (optimizer may reorder).

•

Q29. What is a semi-join?

Returns rows from left table that have a match in right table, without duplicating. Implemented via EXISTS or IN subquery. No SQL keyword, but optimizer recognizes the pattern.

•

Q30. How to handle many-to-many relationships in SQL?

Use a junction/bridge table with foreign keys to both related tables. Join through the bridge table.

•

Q31. What is a lateral join/CROSS APPLY?

Allows the subquery to reference columns from the outer query (correlated). Each row from outer table feeds into the subquery. PostgreSQL: LATERAL. SQL Server: CROSS APPLY.

•

Q32. How does join order affect performance?

Query optimizer usually determines optimal join order. For manual optimization: start with smaller/filtered tables, join on indexed columns, use hash joins for large unsorted data.

•

Q33. Write a query to find customers who ordered all products.

SELECT customer_id
FROM orders
GROUP BY customer_id
HAVING COUNT(DISTINCT product_id) = (SELECT COUNT(*) FROM products);
•

Q34. How to perform a range join?

SELECT e.name, s.level
FROM employees e JOIN salary_bands s
ON e.salary BETWEEN s.min_salary AND s.max_salary;
•

Q35. Explain hash join vs nested loop join vs merge join.

Nested loop: for each row in outer, scan inner (good for small datasets, indexed). Hash join: build hash table on smaller set, probe with larger (good for unsorted, no index). Merge join: sort both, merge (good if already sorted or indexed).

3. GROUP BY, HAVING & Aggregations

•

Q41. List all aggregate functions in SQL.

COUNT, SUM, AVG, MIN, MAX, GROUP_CONCAT/STRING_AGG, VARIANCE/VAR_POP, STDDEV, PERCENTILE_CONT, PERCENTILE_DISC, ARRAY_AGG.

•

Q42. Can you SELECT a non-aggregated column without grouping by it?

No (in standard SQL). Every column in SELECT must be in GROUP BY or inside an aggregate function. MySQL allows it with default settings but gives unpredictable results.

•

Q43. Explain GROUPING SETS, CUBE, and ROLLUP.

GROUPING SETS: specify exact grouping combinations. ROLLUP: hierarchical sub-totals (left to right). CUBE: all possible sub-total combinations.

SELECT region, product, SUM(sales)
FROM sales_data
GROUP BY ROLLUP(region, product);  -- totals by region, grand total
•

Q44. Write a query to find the second highest salary.

SELECT MAX(salary) FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);
-- OR using DENSE_RANK:
SELECT salary FROM (
    SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rk
    FROM employees
) t WHERE rk = 2;
•

Q45. How to count occurrences and filter groups?

SELECT department, COUNT(*) AS emp_count
FROM employees
GROUP BY department
HAVING COUNT(*) > 5
ORDER BY emp_count DESC;
•

Q46. Find duplicates in a table.

SELECT email, COUNT(*) as cnt
FROM users
GROUP BY email
HAVING COUNT(*) > 1;
•

Q47. What is the difference between SUM(CASE WHEN...) and COUNT(CASE WHEN...)?

SUM(CASE WHEN condition THEN 1 ELSE 0 END) — counts matching rows. COUNT(CASE WHEN condition THEN 1 END) — same (COUNT ignores NULLs). Both create conditional aggregations (pivot-like).

•

Q48. How to calculate a running total without window functions?

SELECT a.date, a.amount,
       (SELECT SUM(b.amount) FROM sales b WHERE b.date <= a.date) AS running_total
FROM sales a ORDER BY a.date;

Window function version: SUM(amount) OVER (ORDER BY date).

•

Q49. Compute median in SQL.

-- Using PERCENTILE_CONT (PostgreSQL/SQL Server):
SELECT PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY salary) AS median_salary
FROM employees;
•

Q50. How to pivot rows to columns?

SELECT customer_id,
       SUM(CASE WHEN product = 'A' THEN amount ELSE 0 END) AS product_a,
       SUM(CASE WHEN product = 'B' THEN amount ELSE 0 END) AS product_b,
       SUM(CASE WHEN product = 'C' THEN amount ELSE 0 END) AS product_c
FROM orders GROUP BY customer_id;

4. Window Functions

•

Q61. What is a window function? How does it differ from GROUP BY?

Window function computes across a set of rows related to current row WITHOUT collapsing them. GROUP BY aggregates and reduces rows. Window functions preserve individual rows.

•

Q62. Explain the syntax: func() OVER (PARTITION BY ... ORDER BY ... ROWS/RANGE ...)

OVER: defines the window. PARTITION BY: divides into groups (like GROUP BY but keeps rows). ORDER BY: sorts within partition. ROWS/RANGE: defines frame boundaries relative to current row.

•

Q63. List the main window functions.

Ranking: ROW_NUMBER, RANK, DENSE_RANK, NTILE. Aggregate: SUM, AVG, COUNT, MIN, MAX (over window). Value: LAG, LEAD, FIRST_VALUE, LAST_VALUE, NTH_VALUE.

•

Q64. Difference between ROW_NUMBER, RANK, and DENSE_RANK?

Data: 100, 100, 90, 80
ROW_NUMBER: 1, 2, 3, 4  (always unique)
RANK:       1, 1, 3, 4  (skips after ties)
DENSE_RANK: 1, 1, 2, 3  (no gaps)
•

Q65. How do LAG and LEAD work?

LAG(col, n): value n rows BEFORE current row. LEAD(col, n): value n rows AFTER current row. Used for: calculating differences between consecutive rows, detecting changes.

SELECT date, revenue,
       revenue - LAG(revenue, 1) OVER (ORDER BY date) AS daily_change,
       LEAD(revenue, 1) OVER (ORDER BY date) AS next_day_revenue
FROM daily_sales;
•

Q66. Calculate running average of last 7 days.

SELECT date, amount,
       AVG(amount) OVER (ORDER BY date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS avg_7d
FROM daily_sales;
•

Q67. Explain ROWS vs RANGE in window frames.

ROWS: physical offset (exact number of rows). RANGE: logical offset (rows with same ORDER BY value treated as one). ROWS is more predictable; RANGE groups ties.

•

Q68. Find top 3 salaries per department.

SELECT * FROM (
    SELECT *, DENSE_RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS rk
    FROM employees
) t WHERE rk <= 3;
•

Q69. Calculate cumulative distribution.

SELECT name, salary,
       CUME_DIST() OVER (ORDER BY salary) AS cumulative_pct,
       PERCENT_RANK() OVER (ORDER BY salary) AS percent_rank
FROM employees;
•

Q70. Calculate month-over-month growth rate.

SELECT month, revenue,
       ROUND(100.0 * (revenue - LAG(revenue) OVER (ORDER BY month))
             / LAG(revenue) OVER (ORDER BY month), 2) AS mom_growth_pct
FROM monthly_revenue;
•

Q71. What is NTILE and how is it used?

Divides rows into N approximately equal buckets. NTILE(4) OVER (ORDER BY score) creates quartiles. Useful for percentile calculations and bucketing.

•

Q72. Find consecutive days with sales above threshold.

WITH flagged AS (
    SELECT date, sales,
           date - ROW_NUMBER() OVER (ORDER BY date)::int AS grp
    FROM daily_sales WHERE sales > 1000
)
SELECT MIN(date) AS start_date, MAX(date) AS end_date, COUNT(*) AS streak_days
FROM flagged GROUP BY grp ORDER BY streak_days DESC;

5. Subqueries & CTEs

•

Q86. What is a CTE? Advantages over subqueries?

Common Table Expression: named temporary result set using WITH clause. More readable, can reference itself (recursive), can be referenced multiple times, easier to debug.

•

Q87. Explain recursive CTEs with an example.

WITH RECURSIVE org_tree AS (
    SELECT id, name, manager_id, 1 AS level
    FROM employees WHERE manager_id IS NULL  -- anchor
    UNION ALL
    SELECT e.id, e.name, e.manager_id, t.level + 1
    FROM employees e JOIN org_tree t ON e.manager_id = t.id  -- recursive
)
SELECT * FROM org_tree ORDER BY level;
•

Q88. Correlated vs non-correlated subquery?

Non-correlated: executes once independently. Correlated: references outer query, executes once per outer row (slower). Example correlated: WHERE salary > (SELECT AVG(salary) FROM employees e2 WHERE e2.dept = e1.dept).

•

Q89. When to use EXISTS vs IN with subqueries?

EXISTS is faster for large subqueries (stops at first match). IN materializes entire subquery result. EXISTS handles NULLs correctly. Use EXISTS for correlated checks, IN for small value lists.

•

Q90. Write a CTE to generate a date series.

WITH RECURSIVE dates AS (
    SELECT '2024-01-01'::date AS dt
    UNION ALL
    SELECT dt + INTERVAL '1 day' FROM dates WHERE dt < '2024-12-31'
)
SELECT dt FROM dates;

Q91-105. Additional patterns: multiple CTEs chained together, CTE vs temp table performance, subqueries in SELECT/FROM/WHERE clauses, scalar subqueries, and lateral subqueries for row-dependent computations.

7. Advanced SQL

•

Q126. Explain ACID properties.

Atomicity: all-or-nothing transactions. Consistency: valid state transitions only. Isolation: concurrent transactions don't interfere. Durability: committed data survives crashes.

•

Q127. What are isolation levels?

READ UNCOMMITTED (dirty reads), READ COMMITTED (no dirty reads), REPEATABLE READ (no non-repeatable reads), SERIALIZABLE (no phantom reads). Higher isolation = more consistency but less concurrency.

•

Q128. Explain optimistic vs pessimistic locking.

Pessimistic: lock rows when reading (SELECT FOR UPDATE). Optimistic: no locks, check for conflicts at commit time (version column). Optimistic is better for low-contention scenarios.

•

Q129. What are stored procedures and functions?

Stored procedure: named block of SQL statements, can modify data, doesn't return a value inline. Function: returns a value, can be used in SELECT. Procedures for complex logic; functions for reusable calculations.

•

Q130. What is a view? Materialized view?

View: virtual table (saved query, computed on access). Materialized view: physically stored query result (refreshed periodically). Materialized views are faster but can be stale.

•

Q131. Explain triggers.

Automatic actions fired before/after INSERT/UPDATE/DELETE. Use for: audit logging, maintaining derived columns, enforcing complex constraints. Caution: can cause performance issues and implicit behavior.

•

Q132. What are indexes? Types?

Data structures that speed up queries. B-tree (default, range queries), Hash (equality), GIN (full-text, arrays), GiST (geometric, range), BRIN (sorted physical data).

•

Q133. Composite index vs multiple indexes?

Composite: one index on multiple columns, best for queries filtering on leftmost columns together. Multiple: separate indexes, optimizer picks best one. Composite is more efficient for multi-column queries.

•

Q134. What is query execution plan? How to read it?

EXPLAIN/EXPLAIN ANALYZE shows how database executes a query. Look for: Seq Scan (full scan, slow), Index Scan (good), Sort (costly), Hash Join vs Nested Loop, estimated vs actual rows.

8. Performance & Optimization

•

Q151. How to identify slow queries?

Enable slow query log. Use EXPLAIN ANALYZE. Check: sequential scans on large tables, missing indexes, large sorts, many row estimates being wrong.

•

Q152. Index best practices for ML data pipelines.

Index join columns, WHERE clause columns, ORDER BY columns. Don't over-index (slow writes). Use partial indexes for filtered queries. Monitor unused indexes.

•

Q153. When does an index NOT help?

Small tables (<1000 rows), low cardinality columns, queries reading >10-20% of table, frequent writes (index maintenance overhead), functions on indexed column (use functional index).

•

Q154. Explain query optimization techniques.

-- Use indexed columns in WHERE (avoid functions on them)
WHERE date_col >= '2024-01-01'  -- good
WHERE YEAR(date_col) = 2024     -- bad (can't use index)

-- Select only needed columns
SELECT col1, col2  -- good
SELECT *           -- bad

-- Use EXISTS instead of IN for large subqueries
-- Use JOINs instead of correlated subqueries
-- Filter early, aggregate late
-- Use UNION ALL instead of UNION when possible
•

Q155. What is query plan caching?

Database stores execution plans for reuse. Parameterized queries benefit from plan caching. Dynamic SQL may not. Plan cache bloat can be a problem.

•

Q156. Explain table partitioning strategies.

Range: by date ranges (most common for time-series). List: by category values. Hash: distributed by hash of column. Improves query performance through partition pruning.

Q157-170. Additional optimization: connection pooling, batch inserts, VACUUM/ANALYZE, covering indexes (include columns), index-only scans, join algorithms, materialized views for expensive aggregations, and database-specific tuning.

9. Database Design & Theory

•

Q171. What is normalization? Explain 1NF through 3NF.

1NF: atomic values, no repeating groups. 2NF: 1NF + no partial dependencies (each non-key column depends on entire primary key). 3NF: 2NF + no transitive dependencies (no non-key depends on another non-key).

•

Q172. When is denormalization appropriate?

Read-heavy workloads, reporting/analytics, reducing complex joins. Common in data warehouses (star schema). Trade-off: faster reads vs. data redundancy and update complexity.

•

Q173. Explain primary key, foreign key, and unique constraints.

Primary key: unique + not null, identifies each row. Foreign key: references primary key in another table, enforces referential integrity. Unique: ensures no duplicates (allows one NULL).

•

Q174. What is an ERD (Entity Relationship Diagram)?

Visual representation of database entities (tables), their attributes (columns), and relationships (1:1, 1:N, M:N). Used for database design and communication.

•

Q175. CAP theorem — explain with examples.

Consistency: all nodes see same data. Availability: every request gets a response. Partition tolerance: system works despite network failures. Can only guarantee 2 of 3: CP (MongoDB), AP (Cassandra), CA (traditional RDBMS).

Q186. Write SQL to compute feature statistics for ML.

SELECT
    AVG(feature_1) AS mean_f1,
    STDDEV(feature_1) AS std_f1,
    PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY feature_1) AS median_f1,
    MIN(feature_1) AS min_f1,

Q187. Create train/test split in SQL.

WITH numbered AS (
    SELECT *, ROW_NUMBER() OVER (ORDER BY RANDOM()) AS rn,
           COUNT(*) OVER () AS total
    FROM dataset
)
SELECT *, CASE WHEN rn <= total * 0.8 THEN 'train' ELSE 'test' END AS split
FROM numbered;
•

Q188. Detect target leakage in features.

-- Features shouldn't have near-perfect correlation with target
SELECT feature_name,
       CORR(feature_value, target) AS correlation
FROM features_unpivoted
GROUP BY feature_name
HAVING ABS(CORR(feature_value, target)) > 0.95
ORDER BY ABS(correlation) DESC;
•

Q189. Compute time-based features for ML.

SELECT user_id,
       COUNT(*) OVER (PARTITION BY user_id ORDER BY event_time
                      RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW) AS events_7d,
       AVG(amount) OVER (PARTITION BY user_id ORDER BY event_time
                         RANGE BETWEEN INTERVAL '30 days' PRECEDING AND CURRENT ROW) AS avg_amount_30d,
       EXTRACT(EPOCH FROM event_time - LAG(event_time) OVER (PARTITION BY user_id ORDER BY event_time)) AS time_since_last
FROM events;
•

Q190. Compute class distribution and check imbalance.

SELECT target_class,
       COUNT(*) AS count,
       ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 2) AS percentage
FROM dataset
GROUP BY target_class
ORDER BY count DESC;

Q191. Stratified sampling in SQL.

WITH ranked AS (
    SELECT *,
           ROW_NUMBER() OVER (PARTITION BY target_class ORDER BY RANDOM()) AS rn,
           COUNT(*) OVER (PARTITION BY target_class) AS class_count
    FROM dataset
)
SELECT * FROM ranked WHERE rn <= class_count * 0.2;  -- 20% sample per class

SELECT CORR(feature_a, feature_b) AS correlation,

Q193. Create lagged features for time series.

SELECT date, value,
       LAG(value, 1) OVER (ORDER BY date) AS lag_1,
       LAG(value, 7) OVER (ORDER BY date) AS lag_7,

Q194. Compute confusion matrix in SQL.

SELECT
    SUM(CASE WHEN actual = 1 AND predicted = 1 THEN 1 ELSE 0 END) AS true_positive,
    SUM(CASE WHEN actual = 0 AND predicted = 1 THEN 1 ELSE 0 END) AS false_positive,
    SUM(CASE WHEN actual = 1 AND predicted = 0 THEN 1 ELSE 0 END) AS false_negative,
    SUM(CASE WHEN actual = 0 AND predicted = 0 THEN 1 ELSE 0 END) AS true_negative
FROM predictions;

Q195. Detect data drift with SQL.

-- Compare distribution of a feature between two time periods
WITH current_stats AS (
    SELECT AVG(feature) AS mean, STDDEV(feature) AS std
    FROM data WHERE date >= CURRENT_DATE - 7
),
historical_stats AS (
    SELECT AVG(feature) AS mean, STDDEV(feature) AS std
    FROM data WHERE date BETWEEN CURRENT_DATE - 37 AND CURRENT_DATE - 7
)
SELECT
    ABS(c.mean - h.mean) / NULLIF(h.std, 0) AS z_score_drift,
    CASE WHEN ABS(c.mean - h.mean) / NULLIF(h.std, 0) > 2 THEN 'DRIFT' ELSE 'OK' END AS status
FROM current_stats c, historical_stats h;
•

Q197. Text-to-SQL: explain the concept.

Given a natural language question, generate the corresponding SQL query. Used in: NL2SQL (converting user questions to database queries), chatbots for business analytics. LLM-based approaches (GPT, fine-tuned models) now dominate.

Q198. Write SQL for customer RFM analysis.

SELECT customer_id,

FROM orders
GROUP BY customer_id;

Q199. Compute AUC-ROC components in SQL.

-- Calculate TPR and FPR at different thresholds
WITH thresholds AS (
    SELECT DISTINCT prediction_score AS threshold FROM predictions
),
metrics AS (
    SELECT t.threshold,
           SUM(CASE WHEN p.actual = 1 AND p.prediction_score >= t.threshold THEN 1 ELSE 0 END)::float

           SUM(CASE WHEN p.actual = 0 AND p.prediction_score >= t.threshold THEN 1 ELSE 0 END)::float
           / NULLIF(SUM(CASE WHEN p.actual = 0 THEN 1 ELSE 0 END), 0) AS fpr
    FROM thresholds t CROSS JOIN predictions p
    GROUP BY t.threshold

Q23. What are the broadcasting rules?

  1. Prepend 1s to the shape of the smaller array until ndim matches.
  2. Arrays with size 1 in a dimension are stretched to match the other.
  3. If neither is 1 and they differ, raise an error.

Example: (3, 1, 4) + (5, 4) → (3, 5, 4) ✓

Performance (Q51–Q70)

•

Q51. Why is NumPy faster than Python loops?

NumPy operations execute in compiled C/Fortran code. Vectorized operations avoid Python interpreter overhead, utilize CPU SIMD instructions, and benefit from memory locality (contiguous arrays).

Q52. What is memory layout (C-order vs F-order) and why does it matter?

  • C-order (row-major): Last axis varies fastest. Efficient for row operations.
  • F-order (column-major, Fortran-order): First axis varies fastest. Efficient for column operations. Many operations are faster on C-contiguous arrays. Check with a.flags.

Q53. What is np.ascontiguousarray?

Ensures an array is stored in C-contiguous memory layout. Often needed before passing to C extensions or when performance is degraded by non-contiguous strides:

Q54. What are strides in NumPy?

Strides define how many bytes to step in each dimension to reach the next element:

a = np.zeros((3, 4), dtype=np.float64)
a.strides  # (32, 8) — 32 bytes per row, 8 bytes per element

Clever stride tricks enable zero-copy reshaping (sliding windows, etc.).

Q56. When should you use np.float32 vs np.float64?

  • float32: Half the memory, faster on modern GPUs. Acceptable precision for ML model weights and activations.
  • float64: Default; needed for scientific computing where precision matters (numerical integration, statistics).

Q57. What is cache blocking / tiling and how does NumPy benefit from it?

Matrix operations split large arrays into tiles that fit in CPU cache, reducing memory bandwidth bottlenecks. NumPy uses BLAS/LAPACK libraries that implement cache-aware algorithms automatically.

Arrays are broadcast together if for each dimension (from right): 1. Dimensions are equal, OR 2. One of them is 1 (it's "stretched" to match the other).

Q197. How do you implement Gram-Schmidt orthogonalization in NumPy?

def gram_schmidt(A: np.ndarray) -> np.ndarray:
    """Orthogonalize columns of A"""
    Q = np.zeros_like(A, dtype=float)
    for j in range(A.shape[1]):
        v = A[:, j].copy()
        for i in range(j):
            v -= np.dot(Q[:, i], A[:, j]) * Q[:, i]
        norm = np.linalg.norm(v)
        if norm > 1e-10:
            Q[:, j] = v / norm
    return Q

# NOTE: Use np.linalg.qr for numerically stable version
