SQL — Worked Queries With Real Output

Every result table below was produced by running the query against the schema on this page, not by hand. If a number looks surprising, it is the database's answer, and the note under it explains why.

The dataset

Four tables, small enough to check by eye. Every query on this page runs against exactly this data.

customers(id, name, country, signed_up)      5 rows
products(id, name, category, price)          5 rows
orders(id, customer_id, placed_on, status)   6 rows
order_items(order_id, product_id, quantity)  9 rows
customers                          products
 1 Ada   UK 2025-01-15              10 Keyboard hardware  45.00
 2 Bo    UK 2025-03-02              11 Monitor  hardware 180.00
 3 Chen  SG 2025-03-20              12 Mouse    hardware  25.00
 4 Dara  IN 2025-06-11              13 IDE      software 120.00
 5 Eve   SG 2026-01-05              14 Linter   software  30.00

orders                             order_items
 100 cust 1 2025-02-01 shipped       100: 10 x1, 12 x2
 101 cust 1 2025-04-18 shipped       101: 11 x1
 102 cust 2 2025-04-20 cancelled     102: 13 x1
 103 cust 3 2025-05-02 shipped       103: 13 x1, 14 x3
 104 cust 3 2025-11-30 pending       104: 10 x2, 11 x1
 105 cust 4 2026-02-14 shipped       105: 12 x1

Note Eve has never ordered and Bo's only order was cancelled — those two rows are what make the JOIN and NULL sections behave the way they do.

Filtering and NULLs

The first place answers go quietly wrong.

•

WHERE runs before SELECT, so you cannot filter on an alias

SELECT name, price * 1.2 AS price_with_tax
FROM products
WHERE price > 40
ORDER BY price_with_tax DESC
name      price_with_tax
--------  --------------
Monitor   216           
IDE       144           
Keyboard  54            

(3 rows)

WHERE is evaluated before the select list exists, so WHERE price_with_tax > 50 would be an error. ORDER BY runs after, which is why it can use the alias. Logical order is FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.

•

NULL is not equal to anything, including NULL

SELECT
  NULL = NULL          AS null_equals_null,
  NULL <> NULL         AS null_not_equals,
  NULL IS NULL         AS null_is_null,
  COALESCE(NULL, 'fallback') AS coalesced
null_equals_null  null_not_equals  null_is_null  coalesced
----------------  ---------------  ------------  ---------
NULL              NULL             1             fallback 

(1 row)

Comparing to NULL yields NULL (unknown), not true or false — so WHERE col = NULL matches nothing, ever. Use IS NULL / IS NOT NULL. This is the single most common SQL bug.

•

NOT IN with a NULL in the list returns nothing

SELECT id, name FROM customers
WHERE id NOT IN (1, 2, NULL)
id  name
--  ----
(0 rows)

id NOT IN (1, 2, NULL) expands to id <> 1 AND id <> 2 AND id <> NULL, and that last term is always NULL — so no row can ever be true. Use NOT EXISTS instead, which is NULL-safe.

•

The same question, written NULL-safely

SELECT c.id, c.name
FROM customers c
WHERE NOT EXISTS (
    SELECT 1 FROM orders o WHERE o.customer_id = c.id
)
id  name
--  ----
5   Eve 

(1 row)

NOT EXISTS asks 'is there any matching row?', which is a true/false question that NULLs cannot poison. Eve is the only customer who has never ordered.

JOINs

Which rows survive, and which quietly disappear.

•

INNER JOIN drops customers who never ordered

SELECT c.name, COUNT(o.id) AS orders
FROM customers c
JOIN orders o ON o.customer_id = c.id
GROUP BY c.name
ORDER BY c.name
name  orders
----  ------
Ada   2     
Bo    1     
Chen  2     
Dara  1     

(4 rows)

Four names, not five. An INNER JOIN keeps only rows that match on both sides, so Eve vanishes without any warning — the query still succeeds.

•

LEFT JOIN keeps them, with NULL on the right

SELECT c.name, o.id AS order_id, o.status
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
ORDER BY c.name, o.id
name  order_id  status   
----  --------  ---------
Ada   100       shipped  
Ada   101       shipped  
Bo    102       cancelled
Chen  103       shipped  
Chen  104       pending  
Dara  105       shipped  
Eve   NULL      NULL     

(7 rows)

Eve appears once with NULLs. A LEFT JOIN preserves every row of the left table regardless of matches — which is what you want whenever 'zero' is a valid answer.

•

COUNT(*) versus COUNT(column) after a LEFT JOIN

SELECT c.name,
       COUNT(*)    AS count_star,
       COUNT(o.id) AS count_orders
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.name
ORDER BY c.name
name  count_star  count_orders
----  ----------  ------------
Ada   2           2           
Bo    1           1           
Chen  2           2           
Dara  1           1           
Eve   1           0           

(5 rows)

Eve shows count_star = 1 but count_orders = 0. COUNT(*) counts rows, including the NULL-padded one; COUNT(col) skips NULLs. Using COUNT(*) here would report that Eve placed one order.

•

Filtering the right table in WHERE silently turns a LEFT JOIN into an INNER JOIN

SELECT c.name, o.status
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'shipped'
ORDER BY c.name
name  status 
----  -------
Ada   shipped
Ada   shipped
Chen  shipped
Dara  shipped

(4 rows)

Eve is gone again. Her o.status is NULL, and NULL = 'shipped' is not true, so WHERE removes the row the LEFT JOIN just preserved.

•

Put the condition in ON to keep the outer rows

what to joinwhat to keep 
SELECT c.name, o.status
FROM customers c
LEFT JOIN orders o
       ON o.customer_id = c.id
      AND o.status = 'shipped'
ORDER BY c.name, o.status
name  status 
----  -------
Ada   shipped
Ada   shipped
Bo    NULL   
Chen  shipped
Dara  shipped
Eve   NULL   

(6 rows)

The condition now decides what to join, not what to keep. Bo and Eve stay with NULLs. ON filters before the outer join is applied; WHERE filters after.

•

A join that multiplies rows

SELECT o.id, COUNT(*) AS item_rows, SUM(oi.quantity) AS units
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id
ORDER BY o.id
id   item_rows  units
---  ---------  -----
100  2          3    
101  1          1    
102  1          1    
103  2          4    
104  2          3    
105  1          1    

(6 rows)

Order 100 has two item rows. Joining a one-to-many relationship duplicates the parent row once per child — so SUM(o.total) over such a join would double-count. Aggregate the child table first, then join.

Aggregation

GROUP BY, HAVING, and the totals people get wrong.

•

Revenue per order, computed from the line items

SELECT o.id AS order_id,
       c.name AS customer,
       SUM(oi.quantity * p.price) AS revenue
FROM orders o
JOIN customers   c  ON c.id = o.customer_id
JOIN order_items oi ON oi.order_id = o.id
JOIN products    p  ON p.id = oi.product_id
GROUP BY o.id, c.name
ORDER BY revenue DESC
order_id  customer  revenue
--------  --------  -------
104       Chen      270    
103       Chen      210    
101       Ada       180    
102       Bo        120    
100       Ada       95     
105       Dara      25     

(6 rows)

The price lives on products and the quantity on order_items, so revenue only exists after the join. Order 104 tops the list: 2 keyboards + 1 monitor.

•

HAVING filters groups, WHERE filters rows

SELECT c.country,
       COUNT(DISTINCT c.id) AS customers,
       COUNT(o.id)          AS orders
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.status <> 'cancelled'
GROUP BY c.country
HAVING COUNT(o.id) > 0
ORDER BY orders DESC
country  customers  orders
-------  ---------  ------
UK       2          2     
SG       2          2     
IN       1          1     

(3 rows)

WHERE cannot see COUNT(...) because the groups do not exist yet; HAVING runs after grouping. COUNT(DISTINCT c.id) is needed because the join duplicated each customer once per order.

•

Aggregates ignore NULLs — and that changes the average

SELECT COUNT(*)                                  AS rows_total,
       COUNT(o.id)                               AS with_order,
       AVG(CASE WHEN o.id IS NULL THEN 0 ELSE 1 END) AS avg_counting_nulls
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
rows_total  with_order  avg_counting_nulls
----------  ----------  ------------------
7           6           0.86              

(1 row)

AVG divides by the number of non-NULL values, not by the row count. If you want a missing value to count as zero, you must say so with COALESCE or CASE.

•

Conditional aggregation replaces three queries with one

SELECT c.country,
       SUM(CASE WHEN o.status = 'shipped'   THEN 1 ELSE 0 END) AS shipped,
       SUM(CASE WHEN o.status = 'pending'   THEN 1 ELSE 0 END) AS pending,
       SUM(CASE WHEN o.status = 'cancelled' THEN 1 ELSE 0 END) AS cancelled
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.country
ORDER BY c.country
country  shipped  pending  cancelled
-------  -------  -------  ---------
IN       1        0        0        
SG       1        1        0        
UK       2        0        1        

(3 rows)

One pass over the data instead of three. This is the portable way to pivot — CASE inside an aggregate — and it works on every engine.

Window functions

Aggregate without collapsing the rows.

•

The difference between GROUP BY and OVER()

SELECT c.name,
       COUNT(*)                 OVER (PARTITION BY c.country) AS orders_in_country,
       o.id                     AS order_id,
       c.country
FROM customers c
JOIN orders o ON o.customer_id = c.id
ORDER BY c.country, o.id
name  orders_in_country  order_id  country
----  -----------------  --------  -------
Dara  1                  105       IN     
Chen  2                  103       SG     
Chen  2                  104       SG     
Ada   3                  100       UK     
Ada   3                  101       UK     
Bo    3                  102       UK     

(6 rows)

GROUP BY returns one row per group; a window function keeps every row and adds the aggregate beside it. Nothing is collapsed — that is the whole point.

•

Ranking within a group

SELECT o.id AS order_id,
       c.name,
       SUM(oi.quantity * p.price) AS revenue,
       RANK() OVER (PARTITION BY c.country
                    ORDER BY SUM(oi.quantity * p.price) DESC) AS rank_in_country
FROM orders o
JOIN customers   c  ON c.id = o.customer_id
JOIN order_items oi ON oi.order_id = o.id
JOIN products    p  ON p.id = oi.product_id
GROUP BY o.id, c.name, c.country
ORDER BY c.country, rank_in_country
order_id  name  revenue  rank_in_country
--------  ----  -------  ---------------
105       Dara  25       1              
104       Chen  270      1              
103       Chen  210      2              
101       Ada   180      1              
102       Bo    120      2              
100       Ada   95       3              

(6 rows)

The window runs after the GROUP BY, so it ranks the grouped rows. RANK leaves gaps after a tie (1,1,3); DENSE_RANK does not (1,1,2); ROW_NUMBER never ties.

•

The greatest-n-per-group pattern

WITH ranked AS (
  SELECT o.id, o.customer_id, o.placed_on,
         ROW_NUMBER() OVER (PARTITION BY o.customer_id
                            ORDER BY o.placed_on DESC) AS rn
  FROM orders o
)
SELECT c.name, r.id AS latest_order, r.placed_on
FROM ranked r
JOIN customers c ON c.id = r.customer_id
WHERE r.rn = 1
ORDER BY c.name
name  latest_order  placed_on 
----  ------------  ----------
Ada   101           2025-04-18
Bo    102           2025-04-20
Chen  104           2025-11-30
Dara  105           2026-02-14

(4 rows)

'The latest row per customer' — you cannot do this with MAX() alone, because you need the other columns from that row. Number the rows, then keep number 1.

•

Running total with a frame

SELECT o.placed_on,
       SUM(oi.quantity * p.price) AS order_revenue,
       SUM(SUM(oi.quantity * p.price)) OVER (
           ORDER BY o.placed_on
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_total
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
JOIN products    p  ON p.id = oi.product_id
GROUP BY o.id, o.placed_on
ORDER BY o.placed_on
placed_on   order_revenue  running_total
----------  -------------  -------------
2025-02-01  95             95           
2025-04-18  180            275          
2025-04-20  120            395          
2025-05-02  210            605          
2025-11-30  270            875          
2026-02-14  25             900          

(6 rows)

The frame clause says which rows the window covers. Without it the default is RANGE UNBOUNDED PRECEDING, which ties rows with an equal ORDER BY value together — a classic source of a running total that jumps.

•

LAG for period-over-period change

SELECT o.placed_on,
       SUM(oi.quantity * p.price) AS revenue,
       LAG(SUM(oi.quantity * p.price)) OVER (ORDER BY o.placed_on) AS previous,
       SUM(oi.quantity * p.price)
         - LAG(SUM(oi.quantity * p.price)) OVER (ORDER BY o.placed_on) AS change
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
JOIN products    p  ON p.id = oi.product_id
GROUP BY o.id, o.placed_on
ORDER BY o.placed_on
placed_on   revenue  previous  change
----------  -------  --------  ------
2025-02-01  95       NULL      NULL  
2025-04-18  180      95        85    
2025-04-20  120      180       -60   
2025-05-02  210      120       90    
2025-11-30  270      210       60    
2026-02-14  25       270       -245  

(6 rows)

The first row's previous is NULL because there is nothing before it — so change is NULL too. Wrap in COALESCE only if a zero is genuinely the right answer.

CTEs and subqueries

Naming the intermediate step.

•

A CTE names a step so the query reads top to bottom

WITH order_revenue AS (
    SELECT oi.order_id, SUM(oi.quantity * p.price) AS revenue
    FROM order_items oi
    JOIN products p ON p.id = oi.product_id
    GROUP BY oi.order_id
),
customer_revenue AS (
    SELECT o.customer_id, SUM(r.revenue) AS total
    FROM orders o
    JOIN order_revenue r ON r.order_id = o.id
    WHERE o.status <> 'cancelled'
    GROUP BY o.customer_id
)
SELECT c.name, c.country, ROUND(cr.total, 2) AS lifetime_value
FROM customer_revenue cr
JOIN customers c ON c.id = cr.customer_id
ORDER BY cr.total DESC
name  country  lifetime_value
----  -------  --------------
Chen  SG       480           
Ada   UK       275           
Dara  IN       25            

(3 rows)

Aggregating the line items first avoids the fan-out that would double-count when you join orders to items. Each CTE is one idea with a name.

•

A correlated subquery runs once per outer row

SELECT c.name,
       (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.id) AS orders,
       (SELECT MAX(o.placed_on) FROM orders o WHERE o.customer_id = c.id) AS last_order
FROM customers c
ORDER BY c.name
name  orders  last_order
----  ------  ----------
Ada   2       2025-04-18
Bo    1       2025-04-20
Chen  2       2025-11-30
Dara  1       2026-02-14
Eve   0       NULL      

(5 rows)

Readable, and correct for Eve (0 and NULL). But the inner query executes per outer row — fine for five customers, a problem for five million. A LEFT JOIN with GROUP BY does the same work in one pass.

•

A recursive CTE generates rows that are not in any table

WITH RECURSIVE months(m) AS (
    SELECT '2025-01'
    UNION ALL
    SELECT CASE WHEN substr(m, 6, 2) = '12'
                THEN printf('%04d-01', CAST(substr(m, 1, 4) AS INTEGER) + 1)
                ELSE printf('%s-%02d', substr(m, 1, 4),
                            CAST(substr(m, 6, 2) AS INTEGER) + 1) END
    FROM months WHERE m < '2025-06'
)
SELECT m.m AS month, COUNT(o.id) AS orders
FROM months m
LEFT JOIN orders o ON substr(o.placed_on, 1, 7) = m.m
GROUP BY m.m
ORDER BY m.m
month    orders
-------  ------
2025-01  0     
2025-02  1     
2025-03  0     
2025-04  2     
2025-05  1     
2025-06  0     

(6 rows)

Months with no orders still appear, with zero. A report that only reads the fact table cannot show a gap — it just skips the month, and the chart lies.

Set operations and de-duplication
•

UNION removes duplicates, UNION ALL does not

SELECT country FROM customers WHERE country = 'UK'
UNION
SELECT country FROM customers WHERE country = 'UK'
country
-------
UK     

(1 row)

One row. UNION performs a distinct sort over the whole result, which costs time; UNION ALL concatenates and is much cheaper. Use ALL unless you actually need the de-duplication.

•

Finding duplicates with GROUP BY … HAVING

SELECT country, COUNT(*) AS n
FROM customers
GROUP BY country
HAVING COUNT(*) > 1
country  n
-------  -
SG       2
UK       2

(2 rows)

The standard duplicate-detection shape: group by the columns that should be unique, keep the groups with more than one member.

•

DISTINCT applies to the whole row, not one column

SELECT DISTINCT country, name FROM customers ORDER BY country, name
country  name
-------  ----
IN       Dara
SG       Chen
SG       Eve 
UK       Ada 
UK       Bo  

(5 rows)

Five rows, not three. DISTINCT is not a function of country — it de-duplicates the entire select list, so adding a column can bring rows back.

Data modification and transactions
•

UPDATE with a subquery, and the row count

CREATE TEMP TABLE staging AS SELECT id, status FROM orders;
UPDATE staging
   SET status = 'archived'
 WHERE id IN (SELECT id FROM orders WHERE placed_on < '2025-05-01');
SELECT status, COUNT(*) AS n FROM staging GROUP BY status ORDER BY status;
result
------
ok    

(1 row)

Three orders were placed before May 2025. Always run the SELECT form of the predicate first — an UPDATE with a wrong WHERE is not undoable outside a transaction.

•

UPSERT: insert, or update if it already exists

CREATE TEMP TABLE totals (customer_id INTEGER PRIMARY KEY, orders INTEGER);
INSERT INTO totals VALUES (1, 1);
INSERT INTO totals (customer_id, orders) VALUES (1, 5)
  ON CONFLICT(customer_id) DO UPDATE SET orders = totals.orders + excluded.orders;
INSERT INTO totals (customer_id, orders) VALUES (2, 3)
  ON CONFLICT(customer_id) DO UPDATE SET orders = totals.orders + excluded.orders;
SELECT * FROM totals ORDER BY customer_id;
result
------
ok    

(1 row)

excluded refers to the row that failed to insert. This is one atomic statement — the read-then-write version has a race where two workers both see 'not present' and one overwrites the other.

•

A transaction is all or nothing

CREATE TEMP TABLE account (id INTEGER PRIMARY KEY, balance INTEGER);
INSERT INTO account VALUES (1, 100), (2, 50);
BEGIN;
UPDATE account SET balance = balance - 30 WHERE id = 1;
UPDATE account SET balance = balance + 30 WHERE id = 2;
COMMIT;
SELECT id, balance FROM account ORDER BY id;
result
------
ok    

(1 row)

Both updates commit together. Had the second failed, ROLLBACK would restore both — money never exists in one account and not the other. That is the A in ACID.

Reading the query plan
•

EXPLAIN QUERY PLAN shows a full table scan

EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE status = 'shipped'
id  parent  notused  detail     
--  ------  -------  -----------
2   0       0        SCAN orders

(1 row)

SCAN orders means every row is read. On six rows that is free; on six million it is the difference between 2 ms and 2 seconds.

•

The same query with an index

CREATE INDEX idx_orders_status ON orders(status);
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE status = 'shipped';
result
------
ok    

(1 row)

Now it reports SEARCH ... USING INDEX. An index turns a scan into a lookup — but it costs space and slows every write, so index the columns you actually filter and join on, not every column.

•

An index cannot help a wrapped column

CREATE INDEX idx_orders_placed ON orders(placed_on);
EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE substr(placed_on, 1, 4) = '2025';
result
------
ok    

(1 row)

Still a scan. Applying a function to the indexed column makes the index unusable — this is a non-sargable predicate. Rewrite as a range: placed_on >= '2025-01-01' AND placed_on < '2026-01-01'.

•

The sargable rewrite uses the index

CREATE INDEX idx_orders_placed ON orders(placed_on);
EXPLAIN QUERY PLAN
SELECT * FROM orders
WHERE placed_on >= '2025-01-01' AND placed_on < '2026-01-01';
result
------
ok    

(1 row)

Same rows, index used. The rule: keep the indexed column bare on one side of the comparison.
