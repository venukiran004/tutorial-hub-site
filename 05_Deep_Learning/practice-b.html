Scenario 1. What is transfer learning?

AnswerExplanation

Answer: Leveraging knowledge from one task/domain to improve performance on another:

Source task: Large dataset, general domain (ImageNet, Wikipedia)
Target task: Smaller dataset, specific domain (medical images, legal text)
Transfer: Pre-trained features → adapt to target

Explanation: Low-level features (edges, textures, basic syntax) are universal. High-level features are task-specific. Transfer saves training time and data requirements.

Scenario 3. How do you decide which layers to freeze during fine-tuning?

AnswerRule of thumb

Answer:

Strategy: Start from the end, progressively unfreeze
Phase 1: Freeze all, train classification head only
Phase 2: Unfreeze last block, train with low LR
Phase 3: Unfreeze more blocks as needed

Rule of thumb: - Similar domain → freeze more (features transfer well) - Different domain → freeze less (need to adapt features) - Small data → freeze more (prevent overfitting) - Large data → freeze less (can learn domain-specific features)

Scenario 7. What is domain shift and how does it affect transfer learning?

AnswerImpactExplanation

Answer: Difference in data distribution between source and target:

Types:
1. Covariate shift: P(X) differs, P(Y|X) same
2. Label shift: P(Y) differs
3. Concept shift: P(Y|X) differs (meaning changes)

Impact: Greater domain shift → worse transfer. Medical X-rays → natural photos = large shift. Medical X-rays → CT scans = smaller shift. Explanation: Measure shift: compare feature distributions. If large: need more fine-tuning or domain adaptation.

Scenario 12. What is Prototypical Networks?

AnswerExplanation

Answer: Few-shot classification by computing class prototypes:

  1. Embed support examples: eᵢ = f(xᵢ)
  2. Compute class prototype: cₖ = mean(embeddings of class k)
  3. Classify query: nearest prototype in embedding space

Explanation: Simple and effective. Learns metric space where same-class examples cluster. Distance-based classification. Works well for 1-shot and 5-shot settings.

Scenario 13. What is Siamese network?

AnswerTrainingApplicationsExplanation

Answer: Twin networks sharing weights that learn similarity:

embeddings_1 = network(input_1)
embeddings_2 = network(input_2)
similarity = distance(embeddings_1, embeddings_2)

Training: Contrastive loss: same class → close, different class → far. Applications: Face verification (same person?), signature verification, one-shot learning. Explanation: Learns embedding space where similar items are close. Weights shared between branches. Triplet loss: anchor, positive, negative.

Scenario 14. What is contrastive loss?

AnswerExplanation

Answer:

L = (1-y) × ½ D² + y × ½ max(0, margin - D)²

y=0: same class → minimize distance D y=1: different class → push apart (at least margin) Explanation: Learns embedding space where same-class examples are close, different-class examples are far. Foundation for many metric learning approaches.

Scenario 15. What is triplet loss?

AnswerTripletGoalHard miningExplanation

Answer:

L = max(0, d(anchor, positive) - d(anchor, negative) + margin)

Triplet: (anchor, positive from same class, negative from different class) Goal: Positive closer to anchor than negative by at least margin. Hard mining: Use hardest negatives (most similar to anchor from different class). Explanation: More informative than contrastive loss (considers relative distances). Hard negative mining essential for good performance. Used in FaceNet.

Scenario 17. What is LoRA and how does it enable efficient fine-tuning?

AnswerTrainingParametersExplanation

Answer:

Original weight: W ∈ ℝ^(d×k)
LoRA: W' = W + ΔW = W + B·A
where B ∈ ℝ^(d×r), A ∈ ℝ^(r×k), r << min(d,k)

Training: Freeze W, only train A, B. Parameters: d×k → r×(d+k). For d=k=4096, r=8: 32M → 65K parameters. Explanation: Low-rank update captures task-specific adjustments. Merge W+BA at deployment (no latency cost). Multiple LoRA adapters for different tasks on same base model.

Scenario 18. What is QLoRA?

AnswerBenefitExplanation

Answer: Combine quantization with LoRA:

  1. Quantize base model to 4-bit (NF4 data type)
  2. Add LoRA adapters (small, FP16)
  3. Train only LoRA adapters
  4. Gradients computed in FP16, weights stored in 4-bit

Benefit: Fine-tune 65B model on single 48GB GPU (normally needs ~130GB). Explanation: Paged optimizers handle memory spikes. 4-bit NormalFloat (NF4) is information-theoretically optimal for normally distributed weights. Quality matches full fine-tuning.

Scenario 23. What is SimCLR?

AnswerKey ingredientsExplanation

Answer: Contrastive learning framework:

  2. All other images in batch → negative pairs

Scenario 52. What are contrastive learning methods?

AnswerExplanation

Answer: Learn by contrasting similar (positive) and dissimilar (negative) pairs:

Core idea:
- Positive pair: two views of same image (different augmentations)
- Negative pairs: views from different images
- Loss: pull positives together, push negatives apart

InfoNCE loss:
L = -log[exp(sim(z_i, z_j)/τ) / Σ_k exp(sim(z_i, z_k)/τ)]

Explanation: SimCLR, MoCo, CLIP use contrastive learning. Quality depends on: augmentations, number of negatives, temperature τ.

Scenario 53. What is SimCLR?

AnswerKey findings

Answer: Simple framework for contrastive representation learning:

  1. Take image x
  2. Create two augmented views: x_i, x_j
  3. Encode both: h_i = f(x_i), h_j = f(x_j)
  4. Project: z_i = g(h_i), z_j = g(h_j)
  5. Contrastive loss on (z_i, z_j)
  6. Discard projection head g, use encoder f for downstream

Key findings: Stronger augmentations help. Large batch size matters (more negatives). Projection head improves representation quality.

Scenario 54. What is MoCo (Momentum Contrast)?

AnswerAdvantage over SimCLRExplanation

Answer: Contrastive learning with momentum-updated encoder:

Query encoder: f_q(x) — updated by gradient descent
Key encoder: f_k(x) — momentum update: θ_k ← m×θ_k + (1-m)×θ_q

Queue of keys: stores recent key representations (large negative set)

Advantage over SimCLR: Doesn't need enormous batch sizes. Queue provides large negative set efficiently. Explanation: Momentum update keeps key encoder consistent, preventing sudden representation changes. m=0.999 typical.

Scenario 55. What is BYOL (Bootstrap Your Own Latent)?

AnswerKey insightExplanation

Answer: Self-supervised learning WITHOUT negative pairs:

Online network: encoder → projector → predictor → q
Target network: encoder → projector → z  (momentum updated)
Loss: ||q - z||²  (predict target from online)

Key insight: No negatives needed. Momentum target prevents collapse. Explanation: Challenged assumption that negatives are essential. Simpler than contrastive methods. Performance comparable to SimCLR/MoCo. The predictor head + momentum combination prevents trivial (collapsed) solutions.

Scenario 108. How does MAML (Model-Agnostic Meta-Learning) work?

AnswerKey insightExplanation

Answer:

Outer loop (meta-update):
  For each task T_i:
    1. Copy model parameters: θ' = θ
    2. Inner loop: Take K gradient steps on support set of T_i
       θ' = θ - α∇L(T_i_support, θ)

Key insight: Learn initialization θ that adapts quickly (in few gradient steps) to any new task. Explanation: MAML is model-agnostic — works with any differentiable model. The inner loop simulates "what would happen if I fine-tuned on this task?"

Scenario 53. How does DARTS (Differentiable Architecture Search) work?

AnswerExplanation

Answer:

Standard NAS: Discrete choice of operations → not differentiable
DARTS: Continuous relaxation

Instead of choosing ONE operation per edge:
   output = operation_k(x)

Use weighted mixture of ALL operations:
   output = Σ α_k × operation_k(x)
   α = softmax(architecture parameters)

Joint optimization:
1. Update weights w on training data
2. Update architecture α on validation data
3. After search: discretize — pick argmax α per edge

Explanation: DARTS makes NAS differentiable — use gradient descent for architecture search. Orders of magnitude faster than RL/evolution.

Scenario 64. What is Hyperband and how does it differ from random search?

AnswerExplanation

Answer:

Hyperband = Random Search + Successive Halving

Successive Halving:
1. Start N random configurations with small budget (few epochs)
2. Keep top 1/η (e.g., top 1/3)
3. Give survivors more budget (more epochs)
4. Repeat until 1 survivor trained fully

Example (η=3):
Round 1: 81 configs × 1 epoch    → keep top 27
Round 2: 27 configs × 3 epochs   → keep top 9
Round 3: 9 configs × 9 epochs    → keep top 3
Round 4: 3 configs × 27 epochs   → keep top 1
Round 5: 1 config × 81 epochs    → final result

Explanation: Hyperband explores MORE configs by giving less budget to poor performers. Efficient when good configs are identifiable early.

3. Only 2 hyperparameters: N, M

1. Apply ONE random augmentation with random magnitude
2. Zero hyperparameters!
3. Competitive with AutoAugment

Explanation: AutoAugment found policies humans wouldn't design. RandAugment and TrivialAugment achieve similar results with MUCH less search cost.

Scenario 3. What is the dying ReLU problem and how do you detect it?

AnswerExplanation

Answer: Neurons that always output zero (negative pre-activation) → permanent death.

# Detection: Check neuron activation rates
def check_dead_neurons(model, data_loader):
    activation_counts = {}
    hooks = []
    
    def hook_fn(name):
        def hook(module, input, output):
            active = (output > 0).float().mean(dim=0)
            if name not in activation_counts:
                activation_counts[name] = active
            else:
                activation_counts[name] += active
        return hook
    
    # Register hooks on ReLU layers
    for name, module in model.named_modules():
        if isinstance(module, nn.ReLU):
            hooks.append(module.register_forward_hook(hook_fn(name)))
    
    # Run data through model
    for data, _ in data_loader:
        model(data)
    
    # Check for dead neurons (activation rate < 1%)
    for name, counts in activation_counts.items():
        dead = (counts < 0.01 * len(data_loader)).sum()
        print(f"{name}: {dead} dead neurons")

Explanation: Causes: large learning rate, large negative bias, poor initialization. Solutions: Leaky ReLU, ELU, GELU, careful initialization (He init for ReLU).

    loss.backward()  # Accumulate gradients
    
    if (i + 1) % accumulation_steps == 0:
        optimizer.step()  # Update weights
        optimizer.zero_grad()  # Reset gradients

Explanation: If you need batch=32 but GPU fits batch=8: accumulate over 4 steps. Mathematically equivalent to large batch. Training is ~4× slower but uses 4× less memory.

Scenario 26. What is the difference between teacher forcing and scheduled sampling?

AnswerExplanation

Answer:

   Input: "translate: Hello" → "Bonjour" (use ground truth for each step)
   Step 1: <BOS> → predict "Bon" (correct!)
   Step 2: "Bon" (ground truth) → predict "jour" (correct!)

Explanation: Teacher forcing trains faster but creates train-test discrepancy. Scheduled sampling bridges the gap. Modern autoregressive models mostly use teacher forcing + careful decoding strategies.

Explanation: Lottery tickets in Transformers concentrate in attention — specific head-layer combinations are "winning tickets" for specific tasks.

Scenario 48. What is the connection between attention and kernel methods?

AnswerExplanation

Answer:

Softmax attention:
   A(Q, K, V) = softmax(QK^T / √d) V

Kernel interpretation:
   softmax(q_i^T k_j / √d) ≈ κ(q_i, k_j) / Σ_j κ(q_i, k_j)
   where κ is a kernel function (softmax kernel)

Linear attention (replace softmax with φ):
   A(Q, K, V) = φ(Q) (φ(K)^T V)
   Compute φ(K)^T V first: O(n × d²) instead of O(n² × d)

Random Feature Attention:
   φ(x) = exp(-||x||²/2) × [cos(w^T x), sin(w^T x)]
   Approximates softmax kernel with random features

Implication: Attention = soft, learnable, non-parametric kernel
   → Explaining why Transformers are so flexible

Explanation: The kernel interpretation explains linear attention alternatives and connects Transformers to classical kernel theory, providing theoretical grounding for their success.

Production Issue #13: Deep Learning Training Instability

Scope: Deep Learning Training Instability — exploding/vanishing gradients, NaN/Inf losses, loss spikes & divergence, dead neurons, mixed-precision overflow, and distributed-training failures (NCCL, stragglers, sharded checkpoints, dataloader bottlenecks).

•

Overview

One-sentence ideablow up to infinityshrink to zerono exceptionkeeping numbers in a sane range

One-sentence idea: Training a deep net is a long numerical balancing act — multiply enough numbers together through enough layers and they tend to blow up to infinity or shrink to zero. When they do, your loss becomes NaN, your gradients vanish, and hours of GPU time produce a dead model.

Unlike a serving bug, training instability often shows no exception until it's too late — the loss quietly diverges, or silently flat-lines, and you discover it from a useless final checkpoint. The fixes are mostly about keeping numbers in a sane range at every layer and every step.

Healthy training:   loss ↓ smoothly,  grad-norm steady,  no NaNs
Unstable training:  loss → NaN  |  loss spikes then diverges  |  loss flat (learns nothing)
•

Why It Happens (the intuition)

A forward pass is a long chain of multiplications: x → W₁x → activation → W₂(...) → .... Backprop multiplies gradients through the same chain in reverse.

If each layer multiplies the signal by ~1.5:   1.5^50  ≈ 6 × 10⁸   → EXPLODES
If each layer multiplies the signal by ~0.7:   0.7^50  ≈ 2 × 10⁻⁸  → VANISHES
Only signals near ×1.0 per layer stay stable across depth.

That's the whole problem in one line: deep = many multiplications = numbers drift exponentially unless you actively keep them near 1. Everything below (normalization, careful init, residual connections, clipping) exists to hold that balance.

1. NaN / Inf Losses

everything downstream becomes NaNCommon sourcesExploding gradientsLR too highBad math on dataUnnormalized inputs

The single most common "my training broke" issue. Once a NaN appears, everything downstream becomes NaN — so you must catch it at the source.

Common sources: - Exploding gradients → weight becomes huge → activation overflows. - LR too high → the very first updates overshoot into a bad region. - Bad math on data: log(0), sqrt(negative), divide-by-zero, 0/0 in a custom loss. - Unnormalized inputs (pixel values 0–255 instead of 0–1; un-scaled features). - FP16 overflow (see §4).

import torch

def assert_finite(name, t):
    if not torch.isfinite(t).all():
        raise FloatingPointError(f"{name} has NaN/Inf")  # fail loudly, at the source

# Guard the training step
def train_step(model, batch, optimizer, clip=1.0):
    optimizer.zero_grad()
    out = model(batch["x"])
    assert_finite("logits", out)                 # catch before it spreads
    loss = loss_fn(out, batch["y"])
    assert_finite("loss", loss)
    loss.backward()

    grad_norm = torch.nn.utils.clip_grad_norm_(model.parameters(), clip)  # exploding-grad cure
    if not torch.isfinite(grad_norm):
        optimizer.zero_grad()                    # skip this bad step instead of poisoning weights
        return {"loss": float("nan"), "skipped": True}

    optimizer.step()
    return {"loss": loss.item(), "grad_norm": grad_norm.item()}

Debugging trick: set torch.autograd.set_detect_anomaly(True) — it points at the exact op that produced the first NaN in the backward pass. Slow, so use it only while debugging.

2. Exploding & Vanishing Gradients

Cures for explodingGradient clippingLower learning rateLR warmupNormalization layersCures for vanishing

Detect by watching the gradient norm. A healthy run keeps it in a stable band; exploding = it shoots up; vanishing = it decays toward 0.

def global_grad_norm(model):
    total = 0.0
    for p in model.parameters():
        if p.grad is not None:
            total += p.grad.detach().norm() ** 2
    return total ** 0.5
# Log this every step. Exploding: 1e3→1e6.  Vanishing: 1e-1→1e-7.

Cures for exploding: - Gradient clipping (clip_grad_norm_) — the standard fix; cap the norm to e.g. 1.0. - Lower learning rate + LR warmup (start tiny, ramp up over the first few hundred steps). - Normalization layers (BatchNorm / LayerNorm) keep activations in range.

Cures for vanishing: - Better initialization — He init for ReLU, Xavier/Glorot for tanh — so each layer starts near ×1.0. - Residual/skip connections — give gradients a "highway" straight back (why ResNets/Transformers train deep). - Non-saturating activations — ReLU/GELU instead of sigmoid/tanh in deep stacks. - Normalization (BatchNorm/LayerNorm) again — helps both directions.

3. Loss Spikes & Divergence

jumpsCauses & fixesLR too high for the current regionwarmupdecay scheduleA pathological batch

The loss is going down nicely, then suddenly jumps and never recovers.

step 1000: loss 2.1
step 1100: loss 1.8
step 1150: loss 1.7
step 1160: loss 9.4   ← spike
step 1170: loss NaN   ← diverged

Causes & fixes: - LR too high for the current region → add warmup + a decay schedule (cosine/linear). - A pathological batch (outliers, a corrupt sample) → gradient clipping bounds its damage; consider data cleaning. - No warmup on large-batch / Transformer training → warmup is near-mandatory there. - Recover from a spike: keep periodic checkpoints so you can roll back to before the spike and resume with a lower LR (ties to 24_Model_Versioning_and_Reproducibility.md).

# LR warmup + cosine decay (the standard recipe for stable deep training)
import math
def lr_at(step, base_lr, warmup, total):
    if step < warmup:
        return base_lr * step / warmup                       # ramp up gently
    p = (step - warmup) / max(1, total - warmup)
    return 0.5 * base_lr * (1 + math.cos(math.pi * p))       # decay smoothly

4. Dead Neurons (Dead ReLU)

alwaysFixesLeakyReLU/GELU/ELU

A ReLU outputs 0 for any negative input, and its gradient there is also 0 — so if a neuron's input is always negative, it's stuck at 0 forever and never recovers. A large LR or bad init can kill a big fraction of the network.

def dead_relu_fraction(activations):   # activations from a ReLU layer over a batch
    # a unit is "dead" if it's 0 for EVERY example in the batch
    import torch
    never_active = (activations <= 0).all(dim=0)
    return never_active.float().mean().item()   # 0.4 = 40% of this layer is dead

Fixes: lower LR, He initialization, LeakyReLU/GELU/ELU (small negative slope keeps a gradient alive), and BatchNorm.

5. Mixed-Precision Pitfalls

tiny numeric rangeLoss scalingPrefer BF16much wider range

FP16 is fast and memory-light but has a tiny numeric range — values overflow to Inf or underflow to 0 easily. The classic symptom: training is fine in FP32 but NaNs in FP16.

  • Loss scaling (automatic with GradScaler) multiplies the loss before backward so small gradients don't underflow to 0, then unscales before the step.
  • Prefer BF16 where the hardware supports it (A100/H100, TPU): same speed/memory benefit, much wider range, usually no loss scaling needed.
from torch.cuda.amp import autocast, GradScaler
scaler = GradScaler()                       # FP16 loss scaling

for batch in loader:
    optimizer.zero_grad()
    with autocast():                        # run forward in FP16/BF16
        loss = loss_fn(model(batch["x"]), batch["y"])
    scaler.scale(loss).backward()           # scale up so small grads survive FP16
    scaler.unscale_(optimizer)              # unscale before clipping
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    scaler.step(optimizer)
    scaler.update()                         # adapt the scale factor (halves on overflow)

6 & 7. Distributed-Training Failures

hangsCauseFixcollective timeoutwait at each syncCauses

Scaling to many GPUs adds a whole new failure surface. The model trains by synchronizing gradients across GPUs every step (all-reduce via NCCL) — so any one GPU being slow, dead, or out-of-step stalls everyone.

NCCL hangs / deadlocks

The most dreaded distributed bug: training simply hangs with no error. - Cause: ranks disagree on a collective (one GPU calls all-reduce, another doesn't — often due to a if rank == 0: branch that skips a sync, or divergent batch counts), or a network/NVLink issue. - Fix: ensure every rank executes the same collectives in the same order; set a collective timeout so a hang fails loudly instead of forever; debug with NCCL_DEBUG=INFO; verify all ranks see the same world size and step count.

Stragglers

One slow GPU/node makes every other GPU wait at each sync → throughput drops to the slowest worker. - Causes: thermal throttling, a slow disk on one node, network imbalance, uneven shard sizes. - Fixes: monitor per-rank step time; balance shards evenly; isolate/replace the slow node; consider elastic training.

Sharded checkpoints (large models)

A model too big for one GPU is sharded across many (FSDP / DeepSpeed ZeRO). Checkpointing must save/restore all shards consistently. - Failure: saving only rank-0's shard → an unloadable checkpoint; or a crash mid-save → corrupt checkpoint. - Fixes: use the framework's sharded-checkpoint API (FSDP state_dict / DeepSpeed), checkpoint atomically (write to temp, then rename), and test that a checkpoint actually reloads before trusting it.

Dataloader bottleneck (GPUs starved)

GPUs sit idle (<50% util) because the CPU can't feed data fast enough — the GPU finishes the batch before the next one is ready. - Symptom: low GPU utilization despite a "GPU-bound" job. - Fixes: more num_workers, pin_memory=True, prefetch_factor, faster storage/format (WebDataset, sharded files), do augmentation on GPU, cache decoded data. (Cross-ref the utilization metric in 21_Latency_and_Performance.md.)

loader = torch.utils.data.DataLoader(

    num_workers=8,          # parallel CPU data prep so the GPU never waits
    pin_memory=True,        # faster host→GPU copy
    prefetch_factor=4,      # workers stage batches ahead
    persistent_workers=True,
)
